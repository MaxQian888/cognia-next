## Initial audit assessment (before optimization)

The current PiP is a usable screenshot-preview component with meaningful lifecycle and interaction coverage. It is not yet justified to call the whole automation preview reliable, continuously stream-ready, or equivalent to Codex. This audit changes no product source and does not commit or publish anything.

### Availability and correctness

- `components/chat/chat-view.tsx:1179` mounts the overlay inside the chat message host. It is an absolutely positioned renderer element, not a separate native desktop window.
- `lib/plugin/api/automation-api.ts:133` publishes get_app_state/zoom/perform_action activity; get_app_state and zoom publish returned screenshots. perform_action itself does not return/publish a new screenshot. OCR publishes capture frames with temporary overlay suppression.
- `lib/external-bridge/handlers/computer-use.ts:79` directly calls the desktop API. Its Node path (`computer-use-proxy.ts`) forwards to the native socket proxy. `crates/cognia-mcp-server/src/automation_proxy.rs:352` explicitly has `session_key: None` and no AppHandle. There is no PiP event bridge on these paths. Legacy `screenshot`, click, type and similar plugin methods also call desktop directly.
- The actual component passed image decode/display, hide/restore, corner movement, keyboard resize, enlarged dialog, and capture suppression/restore in Chromium 153.0.8010.12 and Playwright WebKit 26.6. Existing Jest tests additionally cover pointer drag/resize, reduced motion, completion collapse, errors, run boundaries and session cleanup, but mock Motion.
- **Ordering defect:** `lib/automation/computer-use-pip.ts:197` accepts any valid frame for an existing session without checking capture time, run ID or activity ID. The deterministic probe publishes timestamps 2000 then 1000 and observes 1000 as current. It then begins run 2 and publishes a simulated late previous-run frame with timestamp 500; that frame is accepted too. Real delivery frequency is unmeasured.

### Performance findings

The fixture bundles the unchanged PiP component, actual React production build, Motion, Radix controls, store and layout helpers. It stubs settings, session/sandbox/artifact boundaries and translation context; no model, native capture, account access or real chat data is involved. The theme is an isolated Tailwind fixture. The workload uses 1280×800 synthetic PNGs, 60 distinct updates at 10 Hz for six seconds, followed by a 1.5-second quiet period and a four-frame 1 Hz control. These synthetic PNGs are around 53–61 KB in base64 and do not represent every real desktop screenshot.

The exact current timings are in `.cache/pip-audit-2026-10-27/browser-results.json`. The final run measured decoded-DOM P95 of 15.9 ms in Chromium and 15 ms in WebKit. This metric checks that the matching image exists and has decoded at an animation-frame sample; it is **not** physical screen latency, transition completion, capture-to-preview latency or automation throughput. Chromium observed no ≥50 ms Long Tasks during that six-second stream; WebKit does not expose the Long Tasks entry type. No process CPU, RSS, GPU memory or provider/network latency was measured.

**The important limit is retained frames.** Both engines retained 60 image nodes while 60 distinct frames arrived, then dropped to one after the quiet period. At 1 Hz the control peaked at two and settled to one. `components/chat/computer-use-picture-in-picture.tsx:592` gives each data URL its own image key inside AnimatePresence with an exit transition, and there is no explicit bound on retained transition frames. This is temporary accumulation under continuous updates, not evidence of a permanent leak. Its long-run native memory cost remains open.

Frame-only updates at unchanged dimensions caused zero extra getBoundingClientRect calls in this fixture. A burst of 100 synthetic document scroll events caused 200 rect reads with one obstacle. The scroll/resize observer update is not coalesced to one animation frame, so dense chat scrolling deserves a follow-up profile; the probe establishes call amplification, not a measured scrolling slowdown.
