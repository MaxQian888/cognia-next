## Problem frame

The sizing follow-up first compared visible model/container geometry and multiple projects sharing the “大肥鱼” name. G4 then authorized transparent video/frame support. The implemented default is a 256 CSS px desktop box for unconfigured pets, preserving all existing saved sizes and neutral Live2D transforms. Import original local media and map its semantic actions into the existing pet runtime; do not execute upstream scripts or import provider credentials. Broader upstream feature parity and cross-platform media acceptance remain outside this increment.

Assess current Live2D support (G1), interpreting “怼” as “对”. Trace import, rendering, configuration, recovery, persistence and shell boundaries. Deliver a support matrix and reproducible evidence; The follow-up G2 authorizes implementation and bounded macOS native acceptance; broad model/OS compatibility remains outside this repair acceptance.

## Baseline findings (before repair)

### F1 — Saved customization can remain stale

`updatePetModelCustomization` (`lib/db/pet-models.ts:192`) only updates Dexie. `loadLive2dSkinAsset` (`lib/pet/skin-assets.ts:10`) caches the complete row through `skin-runtime.ts:158`. The canvas copies customization on load and initializes by readiness/model ID; it does not subscribe to customization changes.

The probe loads scale 1, saves scale 2, confirms the database returns 2, then receives scale 1 from the asset loader. The cached row also contains motion/parameter mappings. An already mounted canvas has a propagation gap beyond that cache. Separate WebViews mean the settings preview lease does not invalidate the overlay cache. The native visual symptom was not exercised.

### F2 — Disabling mouth movement still activates the default parameter

`resolveLive2dParameterMapping` omits the role for `{ mouthOpen: null }`. The canvas passes that absent value (`live2d-canvas.tsx:467`) into a hook whose default argument (`use-live2d-lip-sync.ts:43`) restores `ParamMouthOpenY`. The probe expects no subscription but receives one `beforeModelUpdate` handler. This also affects mappings with no usable mouth parameter.

### F3 — Current sample catalog omits metadata

Live settings fetches on 2026-10-23 returned HTTP 200. Both Hiyori and Haru now reference `<Name>.userdata3.json` and `<Name>.cdi3.json`, which `SAMPLE_MODEL_CATALOG` omits. The validator would remove these optional references and record metadata warnings, so successful listed downloads do not imply a clean `ready` import. This outcome follows from source; full asset downloads/imports were not run.

Product sample URLs follow upstream `develop` without integrity/revision pins. The separate test corpus pins Hiyori/Haru revisions and SHA-256, but its tests cover fetch integrity. Repository search found no real-rendering E2E consuming that corpus.

### F4 — Compatibility and test evidence stop short of native acceptance

- Import `ready` checks graph presence and basic image headers; it does not run Cubism, validate MOC binary versions, fully decode textures, or parse every optional JSON. It does not prove arbitrary rigs render.
- Canvas tests mock Pixi, loader and asset lookup. Config-dialog tests mock canvas/database updater. Their combined boundaries omit F1/F2.
- Browser appearance E2E checks the desktop-only explanation. Tauri pet E2E checks cursor IPC, nurture persistence and gaze preference; it does not import/render Live2D.
- No native macOS/Windows/Linux visual run, real GPU context-loss injection, broad model matrix or performance measurement was performed.
- Core uses an unversioned download URL and reuses existing populated files. A successful build does not prove support for a particular new MOC version.
