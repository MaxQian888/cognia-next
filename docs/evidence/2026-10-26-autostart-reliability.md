## Problem frame

Improve error propagation, serialize registration changes, verify writes, and synchronize settings and tray state (O2, G1), while preserving the existing login entry and hidden-host policy (C1). Extend existing modules rather than adding another startup service or preference store. This evidence file is new because no existing autostart ledger covers these obligations. The reference-specific source comparison is complete; actual login and unattended-service acceptance remain open.

## Assessment

The desktop already uses the official Tauri autostart plugin. On macOS its default is LaunchAgent, which supports the existing login marker; changing to the AppleScript launcher would not preserve arbitrary arguments. `--autostart`, hidden host startup, watchdog reveal suppression and second-instance focus handling are already wired. Retain these paths.

The completed change centralizes a per-webview operation queue, preserves native read failures, verifies writes, publishes the registration actually read back, refreshes consumers on window focus, rejects stale reads, and disables the settings switch while its write is pending. The settings error states and registration mismatch are localized in both locales. Host activation now relies on registration events instead of overwriting a newer value when its other setup finishes.

The next platform improvement would be richer effective-status reporting on macOS (O3). A migration to SMAppService needs a separate design for approval states, migration of existing entries, supported macOS versions and login-launch identification. The Tauri 2.7.0 builder currently exposes LaunchAgent and AppleScript. Registration readback alone is not proof that a real login launch succeeds. Startup latency was not measured, so this task makes no speed improvement claim.

A separate existing limitation remains in `lib/tauri/host-mode.ts`: host mode is persisted before autostart/close-behavior prerequisites finish. A prerequisite failure can leave a partially configured enabled host. This task preserves the orchestration contract and improves its autostart reporting; atomic host-mode configuration remains future work.

Sources: [Tauri autostart documentation](https://v2.tauri.app/plugin/autostart/), [official plugin source](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/autostart/src/lib.rs), and the installed version-pinned Cargo sources noted above.

### Recommended implementation sequence and acceptance

1. **Expose the existing local Host lifecycle.** Add narrow Tauri commands over `cognia-host-service` for inspection and supported lifecycle operations, with explicit service scope and capability grants. Distinguish installed, enabled-at-boot, manager-loaded/active, process-running and application-ready. Today macOS `ServiceStatus.running` means `launchctl print` succeeded (loaded), so a new UI must also inspect runtime/readiness rather than treating that flag as a healthy process. Verification: pure plan/status tests and native command/ACL smoke.
2. **Present independent controls.** Keep “Launch Desktop at login”; add “Start the background Host at system boot” backed by actual native lifecycle operations. An absent service offers an installation action and states the required permission. Preserve existing desktop host-mode behavior during migration. Verification: toggle independence, declined/failed administrator authorization, unreadable status, and zero OS writes from browser or unsupported platforms.
3. **Complete macOS/Linux installation and handoff.** Reuse the signed Host archive, stable install home, service-account key file/systemd credential handling and existing work-migration machinery. Inspect and offer migration of work/credentials rather than silently opening Desktop data in the daemon. Detect an already-running local Host before starting another Companion listener: Desktop and standalone Host share default port `27890`. Verification: correct scope and identity, least privilege, no duplicate task owner/listener, no login-Keychain dependency before login, repair/uninstall keeps data by default.
4. **Keep Windows visibly unsupported until SCM exists.** Implement service installation/control/recovery as a platform backend, then connect the same product contract. Verification: service start/stop/restart before user login, correct account/ACLs, session-agent separation and upgrade rollback. Do not substitute the existing logon task for a boot service.
5. **Run real unattended acceptance.** Test cold boot without desktop login, desktop exit/crash while Host work continues, Host/brain crash restart, logout/login, unavailable network, and task-class recovery with no duplicate side effect. Test GUI control separately in unlocked, locked and logged-out sessions. The present session has no real reboot/unattended proof.

The comparison and sequence are an assessment and implementation plan, not a claim that the missing local control or Windows backend was implemented in this follow-up. No system service was installed or reconfigured.

Platform sources: [Apple launchd daemon/agent lifecycle](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [systemd service supervision](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), [Microsoft interactive-service separation](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services). Apple documents that per-user agents are tied to login/logout; Microsoft recommends a separate GUI process communicating with a service through IPC. These support the session boundary, not platform acceptance of Cognia itself.
