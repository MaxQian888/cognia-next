# Microsoft Agent Host Protocol (AHP): Research and Cognia Relevance

> Retrieval date: **2026-08-13**  
> Scope: Microsoft-owned primary sources only: the official repository, specification, guides, generated types, releases, and reference-implementation links.  
> Repository: <https://github.com/microsoft/agent-host-protocol>

## Executive conclusion

The Agent Host Protocol is a **client-to-host state-synchronization protocol for live AI agent sessions**. It is designed for one authoritative host to expose the same session to multiple IDE, web, CLI, mobile, or automation clients while keeping all clients converged through immutable state, ordered actions, snapshots, subscriptions, replay, and optimistic reconciliation. It is not an agent-to-agent protocol, an agent runtime, or a tool protocol. The host can use ACP or provider-specific adapters below AHP and can expose MCP-backed capabilities through AHP without replacing MCP. ([overview](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/what-is-ahp.md), [doctrine](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md), [AHP and ACP](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/ahp-and-acp.md))

For an AI desktop app such as Cognia, the most valuable ideas are:

1. a provider-neutral, display-ready session projection at the UI boundary;
2. URI-addressed lazy subscriptions instead of one monolithic session payload;
3. one ordered mutation stream plus snapshot/replay recovery;
4. write-ahead optimistic UI with authoritative reconciliation;
5. capability-based feature discovery and graceful degradation;
6. explicit state machines for turns, tool approvals, input requests, terminals, changesets, authentication challenges, and plugin/MCP lifecycles. ([state model](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/state-model.md), [subscriptions](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/subscriptions.md), [reconciliation](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/reconciliation.md), [versioning](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/versioning.md))

The recommended posture is **learn from and prototype against AHP, but do not make Cognia's core persistence or public API depend directly on it yet**. The official specification labels itself a working draft, warns that wire types/actions/state shapes can break, and says not to rely on backward compatibility before production status. The latest published specification found during this review is `0.7.0`, released on 2026-07-31. ([draft status](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/overview.md), [releases](https://github.com/microsoft/agent-host-protocol/releases))

## 1. What problem AHP solves

Without a host synchronization layer, a live agent session is usually bound to the app or harness that started it: conversation turns, streaming output, tool approvals, terminals, and pending input are not automatically available to another client. AHP turns that session into a host-owned shared resource that multiple clients can attach to and drive concurrently. The host owns authoritative state and sequencing; clients render a synchronized projection. ([official site](https://microsoft.github.io/agent-host-protocol/), [what is AHP](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/what-is-ahp.md))

The protocol intentionally does **not** define agent reasoning, model routing, a universal backend tool registry, agent-to-agent coordination, a mandatory filesystem/Git model, or a UI layout. Hosts translate backend-specific events into AHP's presentation-facing state and actions. ([doctrine and anti-goals](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md), [AHP and ACP boundaries](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/ahp-and-acp.md))

This makes AHP complementary to, rather than competitive with:

- **ACP or a provider SDK below the host:** one host-to-agent communication path for prompts, streaming events, tools, and permissions;
- **MCP at the tool/resource boundary:** the host owns the MCP connection and projects lifecycle/auth/display state to AHP clients; optional MCP App traffic uses a constrained `mcp://` side channel;
- **OpenTelemetry for observability:** AHP can relay standard OTLP/JSON logs, traces, and metrics through advertised stateless telemetry channels without redefining the OTel data model. ([AHP and ACP](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/ahp-and-acp.md), [MCP integration](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/mcp.md), [telemetry channel](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/telemetry-channel.md))

## 2. Architecture and state model

### 2.1 Host-authoritative channels

Every push-style AHP interaction belongs to a URI-addressed **channel**. The root catalogue, each session, chat, terminal, changeset, resource watcher, and telemetry stream are separate resources. State-bearing channels hold immutable state; stateless channels carry live event streams. Every command and notification carries a top-level `params.channel`, allowing routing by `(method, channel)` without decoding the full payload. ([channel model](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/subscriptions.md), [formal overview](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/overview.md))

| Channel                    | Responsibility                                                                                 |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `ahp-root://`              | Available agents/models, host configuration, terminal catalogue, lightweight global state      |
| `ahp-session:/<uuid>`      | Session metadata, chat catalogue, active clients, aggregate status, customizations, changesets |
| `ahp-chat:/<id>`           | Turns, streaming output, tool calls, queued/steering messages, input requests, draft           |
| `ahp-terminal:/<id>`       | PTY/terminal state and data flow                                                               |
| `ahp-changeset:/<id>`      | Reviewable change state and operations                                                         |
| `ahp-resource-watch:/<id>` | File/directory change events                                                                   |
| `ahp-otlp:...`             | Stateless OTLP/JSON logs, traces, or metrics                                                   |

The channel responsibilities and URI forms are normative in the subscription and channel specifications. ([subscriptions](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/subscriptions.md), [session channel](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/session-channel.md), [chat channel](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/chat-channel.md), [telemetry channel](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/telemetry-channel.md))

### 2.2 State changes only through actions

For state-bearing channels, the host returns an initial snapshot and then broadcasts ordered `ActionEnvelope`s. Actions are discriminated, typed mutations applied through pure reducers on the host and clients. The host assigns a monotonically increasing `serverSeq`, which creates a single authoritative ordering across mutations and enables deterministic convergence. ([what is AHP](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/what-is-ahp.md), [action delivery](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/subscriptions.md), [actions guide](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/actions.md))

This design deliberately exposes **display-ready durable state**, not raw backend events. A host adapter maps provider/ACP events into common actions such as `chat/delta`, `chat/toolCallStart`, `chat/toolCallReady`, and `chat/toolCallComplete`. ([doctrine](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md), [AHP–ACP mapping](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/ahp-and-acp.md))

### 2.3 Optimistic writes and reconciliation

A client immediately applies its own dispatch to `optimisticState`, retains the action in `pendingActions`, and waits for the host echo. The host echo carries `origin.clientId` and `origin.clientSeq`; the client then confirms, rebases against foreign/server actions, or rolls back a rejected action. The UI always renders the optimistic projection while the host remains authoritative. ([reconciliation algorithm](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/reconciliation.md))

This works especially well for append-oriented chat state. True conflicts use server-wins ordering, and invalid client actions are returned with a `rejectionReason` where the channel rules require rejection. ([reconciliation rationale](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/reconciliation.md), [chat action validation](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/chat-channel.md))

## 3. Connection lifecycle

1. The client opens a previously agreed transport and sends `initialize` with an ordered list of supported protocol versions, an opaque `clientId`, and optional client identity, locale, capabilities, and initial subscriptions.
2. The server selects exactly one offered version and returns its current sequence, implementation identity, optional defaults/telemetry, and snapshots for requested state channels.
3. The client creates or discovers sessions and subscribes lazily to root, session, chat, terminal, or other channels as needed.
4. The host emits ordered actions and ephemeral channel notifications during the live connection.
5. After a drop, the client sends `reconnect(clientId, lastSeenServerSeq, subscriptions)`. The server either replays buffered action envelopes or returns fresh snapshots if the gap is too old. Missing/disposed resources are reported separately.
6. Ephemeral protocol notifications and stateless-channel messages are not replayed; the client re-fetches/re-subscribes and resumes from the live edge. ([lifecycle](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/lifecycle.md), [subscriptions](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/subscriptions.md))

Unexpected host termination makes in-progress turns fail; the surrounding host environment may restart the server, after which clients use the normal reconnection path. ([unexpected disconnection](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/lifecycle.md))

## 4. Transport and wire format

AHP uses **JSON-RPC 2.0** request, response, and notification shapes. It is transport-agnostic, but the transport must be reliable, ordered, bidirectional, and message-complete. WebSocket is the common remote/cross-process choice and the VS Code implementation's choice; each WebSocket text frame contains exactly one complete JSON-RPC message. The protocol also defines a transport-independent `ping` request. ([protocol overview](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/overview.md), [transport requirements](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/transport.md))

Commands cover imperative work such as initialization, subscription, session/chat creation, historical-turn loading, filesystem resource operations, authentication, terminal creation, and completion requests. Notifications cover fire-and-forget client actions and server broadcasts. Some resource operations are bidirectional, allowing the host to request resources exposed by a client. ([message categories](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/overview.md), [channel routing table](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/subscriptions.md))

The repository publishes generated JSON Schema 2020-12 documents for states, actions, commands, notifications, and errors. The canonical types are TypeScript, from which client types are generated for other ecosystems. ([JSON Schema](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/overview.md), [client generation](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/clients.md))

## 5. Extension and capability model

### 5.1 Version negotiation

Protocol versions are SemVer strings negotiated once during `initialize`. For pre-1.0 releases, compatibility is guaranteed only within the same minor line. A client should offer several versions, and a host should select the highest version it implements; otherwise it returns `UnsupportedProtocolVersion`. Unknown additive fields/actions must be ignored within compatible ranges. ([versioning](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/versioning.md))

### 5.2 Capabilities before baseline requirements

New behavior is expected to appear first behind an advertised capability, allowing hosts and clients to upgrade independently, and may later become required in a future protocol version. Feature detection should use capability declarations rather than provider IDs or implementation version strings. Current examples include agent-side multi-chat/fork/side-chat and multi-working-directory support, client-side MCP App rendering, changeset review support, and per-MCP-App host capabilities. ([versioning strategy](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/versioning.md), [agent capability types](https://github.com/microsoft/agent-host-protocol/blob/main/types/channels-root/state.ts), [client capability types](https://github.com/microsoft/agent-host-protocol/blob/main/types/common/commands.ts), [MCP Apps](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/mcp.md))

### 5.3 Typed customizations plus an explicit escape hatch

AHP models plugins, directories, custom agents, skills, prompts, rules, hooks, and MCP servers as typed session customizations. Hosts remain authoritative over the effective expanded tree and enablement. Active clients can publish plugins and tools into a session, while host-internal execution details such as hook commands or MCP process environment remain hidden from clients. Optional `_meta` fields provide provider-specific data that minimal clients may ignore. ([customizations](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/customizations.md))

The doctrine is to keep provider metadata optional and graduate broadly necessary behavior into typed state or capability-gated features. This is an important constraint: escape hatches enhance a baseline experience rather than becoming the only way to render it. ([doctrine](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md))

## 6. Security and trust model

AHP defines useful authentication primitives, but it does **not** define a complete security perimeter.

| Boundary                                 | What AHP specifies                                                                                                                                                                | What remains with the implementation                                                                                                   |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Access to the AHP endpoint               | Nothing at the AHP message layer                                                                                                                                                  | Connection authentication, authorization, TLS, origin/network restrictions, and admission control occur during the transport handshake |
| Agent or backing-resource authentication | Per-agent protected-resource metadata based on RFC 9728; bearer-token delivery based on RFC 6750 semantics through `authenticate`; structured `AuthRequired` errors/notifications | OAuth UX, secure token acquisition/storage/refresh, token audience validation, and secret handling                                     |
| State authority                          | Host sequences all accepted mutations, validates client actions, and echoes rejection                                                                                             | Host integrity, durable-state protection, tenant isolation, client roles, policy enforcement, abuse/rate limits                        |
| MCP Apps                                 | Client declares renderer capability; App View is treated as untrusted; client constructs local UI capabilities and sandbox                                                        | Actual iframe/sandbox/CSP, link/download policy, local-resource permissions, and content isolation                                     |
| Client-provided tools/plugins            | The active-client state records provenance and advertised schemas/customizations                                                                                                  | Whether a client is trusted to register or execute a capability, and what permissions it receives                                      |

The endpoint split is explicit: access to the AHP endpoint is a transport-layer concern outside the wire protocol, while `authenticate` manages entitlements to individual agents/protected resources after connection. ([transport authentication](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/transport.md), [resource authentication](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/authentication.md))

Authentication state is per connection and deliberately excluded from globally shared root state. Tokens are correlated by the protected resource URI, and the server may challenge dynamically for expired or insufficient-scope access, including during an MCP tool call. ([authentication design](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/authentication.md), [MCP authentication states](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/mcp.md))

**Security inference for Cognia:** AHP's coordination semantics alone are not an authorization model. The official AHP/ACP guide says any connected client can resolve a pending tool approval and any client can cancel a running turn, with the host arbitrating the first valid action. Combined with transport authentication being out of scope, a multi-user or cross-device Cognia host would need its own principal identity, session membership, roles/ACLs, approval policy, audit trail, token vault, encrypted transport, and revocation behavior before exposing AHP-like remote control. ([multi-client arbitration](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/ahp-and-acp.md), [transport authentication boundary](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/transport.md))

## 7. Implementation maturity and ecosystem

The protocol is substantial but not stable:

- the formal overview labels it a draft under active development and explicitly warns of breaking wire/state/action changes;
- the latest published spec discovered on 2026-08-13 is `0.7.0` from 2026-07-31, and that release still includes changed and removed wire concepts;
- the spec and language libraries release independently, each with its own SemVer track and supported-protocol registry;
- the repository ships official clients for TypeScript, Rust, Kotlin/JVM, Swift, and Go;
- the official implementation page identifies the VS Code agent host as the reference server and VS Code's Agent Sessions support as a client; it also lists AHPX as an external CLI/Node.js client. ([draft status](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/overview.md), [0.7.0 release](https://github.com/microsoft/agent-host-protocol/releases), [release model](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/versioning.md), [implementations](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/implementations.md))

The breadth of generated clients, schemas, reducers, reconnection logic, and a real VS Code reference server makes AHP credible as an architecture to study and an interoperability target to experiment with. The draft warning and the current single named reference server make it premature to treat as a stable cross-vendor contract for Cognia's core. This is an assessment based on the official maturity signals above, not a claim from Microsoft.

## 8. Cognia-specific architecture mapping

It is to standardize the product-facing session projection above them and, if interoperability proves valuable, expose that projection through an AHP adapter.

### 8.1 The most important separation

Cognia currently has three distinct contracts that should stay distinct:

1. **Execution contract:** `ResolvedAgentExecutionSpec`, `AgentExecutionHandle`, and canonical execution events decide and observe how one agent run executes.
2. **Host/security contract:** Companion RPC, WebSocket/WebRTC transport, command manifests, grants, idempotency, and audit decide who can reach which host operation.
3. **Product-state contract:** sessions, chats, turns, approvals, drafts, terminals, changesets, and input-needed state as clients render and mutate them.

AHP is most applicable to the third contract. It can ride the second contract and be fed by the first. Collapsing all three into AHP would discard Cognia-specific policy, recovery, workflow, and security work while making a draft UI projection the database and execution authority.

### 8.2 Where an AHP integration should live

Two directions are useful, but they are not the same adapter:

- **Cognia as an AHP client:** connect to VS Code or another AHP host, discover its agents/sessions, and render them in Cognia. Because one AHP connection exposes a root catalogue and many shared sessions, this is conceptually a **remote Agent Host** integration. It should live beside Cognia's remote-host/session aggregation boundary, not be forced into the point-to-point `ProtocolAdapter` interface used for ACP/Codex/OpenCode agents.
- **Cognia as an AHP host:** project Cognia-owned sessions to external AHP clients. In headless mode, the Node brain already owns business state while Rust owns the authenticated front door; the AHP projection belongs with the brain and should be published through the existing governed host transport. ([headless architecture](../content/docs/en/adr/0059-cloud-deployment-headless-brain.md))

The first direction is cheaper and safer as an interoperability probe. The second has greater strategic value—VS Code, CLI, web, and mobile clients sharing Cognia sessions—but requires a stable projection, authorization rules for every client action, and stronger compatibility evidence.

## 9. What Cognia can borrow

The following are high-level product/architecture inferences for an AI desktop application; they should be validated against Cognia's current session, connector, sidecar, mobile, Tauri, workflow, and plugin implementations before implementation.

### Borrow now as internal design principles

1. **A provider-neutral session projection.** Keep backend-specific Agent SDK/CLI events behind an adapter, and expose common durable states for turns, content parts, tools, confirmations, input requests, usage, errors, and completion. This is AHP's presentation-model boundary and reduces provider conditionals in UI components. ([doctrine](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md), [AHP–ACP translation](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/ahp-and-acp.md))
2. **Explicit state machines instead of boolean clusters.** Model session creation, turns, tools, MCP servers, authentication challenges, and customization loading as discriminated states with valid transitions. AHP's channel specifications make invalid or stale client actions rejectable and observable. ([state model](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/state-model.md), [chat validation](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/chat-channel.md), [MCP lifecycle](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/mcp.md))
3. **Capability-first UI.** Render or enable UI from explicit capabilities, not inferred provider names or version-string checks. Optional capabilities let a minimal client remain coherent while richer clients add side chats, worktrees, MCP Apps, terminal views, or changeset review. ([versioning](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/versioning.md), [agent capability types](https://github.com/microsoft/agent-host-protocol/blob/main/types/channels-root/state.ts))
4. **Typed extension surface with optional metadata.** Standardize the common plugin/skill/hook/MCP lifecycle and keep vendor-only fields in an ignorable `_meta` bag until they deserve promotion. ([customizations](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/customizations.md), [doctrine](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md))
5. **Durable truth versus ephemeral signal.** Ensure every user-visible result is reconstructible from persisted/replayed state; reserve notifications for live hints. AHP makes this a design test. ([doctrine](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md), [reconnect behavior](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/lifecycle.md))

### Prototype behind an adapter

1. **AHP-compatible client in Cognia.** The official TypeScript package is browser-friendly and includes wire types, reducers, a client, multi-host support, and WebSocket transport, making it the lowest-cost way to validate Cognia as a client of a VS Code-compatible host without changing Cognia's internal persistence model. ([TypeScript client](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/implementations.md))
2. **AHP-like host facade over Cognia sessions.** A narrow, experimental adapter could project existing Cognia sessions as root/session/chat channels and support subscribe, snapshot, action streaming, and reconnect before terminals, changesets, resource operations, or MCP Apps are attempted. This follows AHP's stated incremental-adoption doctrine. ([doctrine](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md))
3. **Cross-window/device handoff.** Snapshot plus ordered replay is a strong basis for reconnecting desktop, mobile, browser, and automation clients to the same live task. ([lifecycle](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/lifecycle.md), [reconciliation](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/reconciliation.md))
4. **Lazy high-volume surfaces.** Split chats, terminals, telemetry, and changesets into independently subscribable channels so a client loads only what it displays. ([subscriptions](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/subscriptions.md))
5. **OTLP pass-through for agent diagnostics.** Adopting standard OTLP/JSON envelopes would make session/turn/tool observability consumable without inventing another proprietary log schema. ([telemetry channel](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/telemetry-channel.md))

### Defer or guard carefully

1. **Do not replace Cognia's persistence schema with AHP types.** AHP state is a client-facing synchronization projection and is still unstable; it need not be the database source of truth. ([doctrine](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md), [draft status](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/overview.md))
2. **Do not expose a remote endpoint before an authorization layer exists.** Transport admission and multi-client roles are outside the protocol; Cognia must define them explicitly. ([transport](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/transport.md), [multi-client arbitration](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/ahp-and-acp.md))
3. **Do not allow untrusted client tools/plugins by advertisement alone.** A registry entry is not a permission grant; execution ownership, sandboxing, confirmation, and audit policy remain Cognia responsibilities. ([client tools and plugins](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/customizations.md))
4. **Do not implement the entire draft upfront.** Root/session/chat synchronization and reconnection test the unique value. Resource RPC, terminals, changesets, telemetry, MCP Apps, and multi-host aggregation can remain capability-gated follow-ons. ([incremental adoption](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md), [versioning](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/versioning.md))

| 4. | 7. Adoption decision    | Compare adapter maintenance, latency, memory, interoperability value, and upstream churn                             | Evidence supports either a maintained AHP compatibility boundary or continued use of only the internal patterns | Premature protocol lock-in                                     |

### Recommended decision now

**Adopt the design invariants; run a narrow client-side compatibility spike; defer a public Cognia AHP server.**

- **Now:** use channel-like resource identities, pure reducers, typed state machines, and capability-first behavior when evolving Cognia's cross-device session projection.
- **Near term:** prototype a read-only TypeScript AHP client against the VS Code reference host and test multi-host catalogue aggregation. Pin the AHP package/spec version and keep all wire mapping inside one adapter.
- **After evidence:** add a minimal Cognia host facade for root/session/chat only, behind a feature flag and existing Companion authentication. Mutating actions should start with prompt, cancel, and approval, each with explicit ACL and idempotency rules.
- **Not now:** replace Dexie, the canonical event log, `AgentExecutionService`, Companion RPC, MCP governance, or agent-team/workflow orchestration with AHP; expose terminals/files/client tools before the authorization matrix is complete; or promise stable public compatibility while the spec remains pre-1.0 draft.

## 11. Final assessment

AHP is most useful to Cognia as a **reference architecture for turning agent execution into a synchronized product surface**. Its sharpest contribution is the separation between an agent-specific backend and a host-authoritative, provider-neutral, replayable presentation state shared by many clients. That directly addresses cross-window consistency, remote session handoff, mobile/desktop coexistence, resumability, and uniform tool/approval UX. ([doctrine](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/doctrine.md), [AHP and ACP](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/ahp-and-acp.md))

Its present weaknesses are equally important: draft compatibility, only one named reference server in the official implementation list, a deliberately out-of-scope transport security layer, and no built-in multi-client role/authorization model. Cognia should therefore copy the invariants, prototype the TypeScript client and a narrow compatibility facade, and keep AHP at an adapter boundary until the protocol stabilizes and the product has an explicit remote trust model. ([draft status](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/overview.md), [implementations](https://github.com/microsoft/agent-host-protocol/blob/main/docs/guide/implementations.md), [transport security boundary](https://github.com/microsoft/agent-host-protocol/blob/main/docs/specification/transport.md))
