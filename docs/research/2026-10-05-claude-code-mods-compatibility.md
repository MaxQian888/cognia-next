# Claude Code Mods compatibility research

Date: 2026-10-05 (Asia/Shanghai)
Status: research only; no runtime implementation or dependency upgrade performed.

## Conclusion

**Cognia can plausibly host a selected subset of Claude Mods through its existing Claude Agent SDK integration. It cannot currently claim native, universal Mods compatibility.** Reuse the plugin installation/contribution model to retain a Claude bundle and opt a Claude session into loading it. Treat this as foreign executable code with its own trust boundary. Port selected UI features through Cognia's existing plugin UI contracts when they need to appear in Cognia. Do not build another marketplace, hook bus, agent runtime, or general-purpose Mods interpreter at this stage.

The immediate compatibility defect is in the existing converter: mixed bundles can be reported as successfully converted while their Mods module is never activated. The research reproduced this without executing any Mod. Fixing that reporting gap should precede any support announcement.

## Scope and evidence

This report distinguishes loading a Claude plugin bundle, executing its Mods handlers in Claude Code, and projecting its interface into Cognia. Those are separate compatibility claims. Upstream facts below were checked against Anthropic documentation, release notes, and public repositories on 2026-10-05. Documentation and generated declarations can describe different versions; the deployed engine must be checked independently.

## Upstream findings

### Release and product identity

Claude Mods shipped in Claude Code **v2.1.287 on 2026-10-01**. The release notes explicitly announce deeper plugin customization. [Release v2.1.287](https://github.com/anthropics/claude-code/releases/tag/v2.1.287)

Mods reuse the Claude plugin distribution model. They contain JavaScript or TypeScript functions, rather than introducing another marketplace format. Unlike instructions in a skill or tools supplied by MCP, these handlers participate directly in the Claude Code engine. Existing settings hooks can coexist with Mods in one plugin. [Mods launch guide](https://claude.dev/blog/getting-started-with-claude-code-mods/)

### Packaging and version contract

The current reference describes v2.1.289. A bundle contains:

```text
example-mod/
  .claude-plugin/plugin.json
  hooks/hooks.json
  hooks/register.ts
  types/index.d.ts        # when using typed state or custom API namespaces
```

The manifest needs no new mandatory Mods field. `hooks/hooks.json` uses `modules`, an array containing exactly one path relative to that file; classic settings hooks can remain under `hooks`. The entry exports `register(on, options)`, where options come from manifest `userConfig`. Supported JavaScript/TypeScript extensions all load as ES modules. A manifest `types` declaration describes typed state or added namespaces. The API includes lifecycle, tools, prompts, commands, agents, model requests, UI, and other-mod events such as `plugin.register` and `engine.create`; reproducing a few lifecycle names does not reproduce this contract. [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)

The built-in diff mod supplies a concrete source example:

```json
{ "modules": ["./register.ts"] }
```

[Built-in diff hooks manifest](https://github.com/anthropics/claude-code/blob/main/mods/diff/hooks/hooks.json)

The published declaration file inspected during research identifies itself as generated by **2.1.277**, earlier than the launch. Its header documents no DOM, Node, or CommonJS `require`; it is useful evidence of the interface design, but cannot establish the current binary's exact ABI. [Published generated declarations](https://github.com/anthropics/claude-code/blob/main/mods/types/claude-code.d.ts)

The launch guide says the engine writes build-specific declarations into each loaded mod's `.claude-plugin/types/`; these take precedence over an older public snapshot. API changes remain possible between versions. The guide also explains that the module stays loaded and can share state across handlers. [Mods launch guide](https://claude.dev/blog/getting-started-with-claude-code-mods/)

### Execution and host support

Mods are enabled by default from v2.1.287. The early-access `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` variable is ignored at these versions, including when set to `0`. Native plugin enable/disable and managed policy are the relevant controls. [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)

| Claude Code host                               | Handlers execute when plugin loads | Mod interface appears           |
| ---------------------------------------------- | ---------------------------------- | ------------------------------- |
| Interactive CLI, including integrated terminal | Yes                                | Yes                             |
| Claude Desktop Code tab                        | Yes                                | Yes, subject to element support |
| Desktop WSL session                            | No: plugins unavailable there      | No                              |
| VS Code chat panel                             | Yes                                | No                              |
| `claude -p` and Agent SDK                      | Yes                                | **No**                          |
| Remote Control                                 | On the user's machine              | In the local terminal           |
| Cloud session                                  | If the plugin reaches that session | No                              |

This is the central constraint for Cognia: official SDK support for behavior does not establish an SDK protocol for the custom drawings. [Official host support table](https://code.claude.com/docs/en/plugins/mods/overview#where-mods-run)

### Event semantics

Registration uses `on(eventName, matcher?, handler)`. The handler receives `($, e, next)`: the host API, an immutable event, and a continuation. It can pass a changed copy downstream, await the downstream result and alter that result, or return without forwarding to replace the remaining chain. Tool interception includes subagent and MCP calls. Matchers filter fields using values, alternatives, or regular expressions. Repeated registration of the same event without a matcher is rejected.

These semantics matter for compatibility: a generic notification bus or a before/after callback cannot automatically emulate middleware ordering, short-circuiting, cancellation, or downstream result ownership. [React to events](https://code.claude.com/docs/en/plugins/mods/events)

### Interface contract

`ui.render` returns an element tree for a named render site. `$.ui.resolve(e)` supplies the constructors supported by the current surface, including containers, text, buttons, and inputs. This is a host-rendered description, not a React component imported into an arbitrary application. A pane is opened separately with `$.ui.open`; invalidation redraws it, and input callbacks execute in the mod.

Sites include panes, the band above the prompt, spinner, and transcript rows. Existing drawings can be retained as an engine reference. Permission prompts cannot be replaced. Some elements differ by surface: SVG is Desktop-only; raster/image elements are terminal-only. `Client` runs a separate drawing module without the Mods API and communicates through `ui.message`.

Consequently, transporting only text or terminal output cannot provide native Cognia widget compatibility. [Draw in the interface](https://code.claude.com/docs/en/plugins/mods/interface)

### Host API and lifecycle ownership

The `$` API mediates filesystem, process, network, settings, environment, session, state, persistent storage, timers, model requests, commands, tools, and MCP calls. Commands and tools are registered in `session.start`, before the first prompt. A registered tool is named `mcp__<plugin>__<name>`, although its handler still belongs to the mod rather than an external MCP server.

Model calls use the session's credentials; `model.complete` has no conversation history and `model.fork` uses current conversation context. Timers can outlive one event and stop when the module reloads. `next.signal` communicates abandoned events. Host API calls are themselves interceptable events. Files/process/network have user-account authority even though the JavaScript module itself lacks those globals.

Any Cognia-hosted runtime would therefore need explicit mapping for ownership, cancellation, credentials, data flow, and side effects, not just module loading. [Use the mods API](https://code.claude.com/docs/en/plugins/mods/api)

### Security boundary

Current administration documentation explicitly says Mods are **not sandboxed**. They execute with the installing user's permissions. The built-in `sec-default` guard protects managed organization policy when managed settings exist or the account is Team/Enterprise. It does not restrict all filesystem/process/network activity: tool deny rules do not cover a mod's direct `$.fs` or `$.process` calls. Organizations can reject user Mods with `allowManagedModsOnly`, or place policy mods earlier in the chain.

This resolves an apparent terminology conflict: the launch tutorial calls the module environment a sandbox, while the administration guide describes the actual host-authority boundary. Lack of Node/DOM is not a filesystem or process sandbox. Cognia should not describe a hosted Claude Mod as protected by Cognia's WASM capability policy unless enforcement is demonstrated at the actual call boundary. [Manage mods](https://code.claude.com/docs/en/plugins/mods/admin)

### Existing upstream verification tools

`claude plugin validate <dir>` inspects the manifest, module, events, and API calls. `claude plugin test <dir>` runs mod tests without a live session, authentication, or network. Test files use `claude-code/testing`, exercise events and stub host responses, and can drive an element tree's controls. These tests do not demonstrate real terminal/Desktop painting or Cognia transport integration. They are suitable for a later fixture suite alongside actual SDK and terminal checks. [Test a mod](https://code.claude.com/docs/en/plugins/mods/test)

### Source and licensing evidence

The public `anthropics/claude-code` repository's root license reserves rights and refers to Anthropic's Commercial Terms. Its recursive tree did not contain a separate `LICENSE` or `COPYING` beneath `mods/` when checked. Public readability of built-in source therefore must not be treated as an Apache/MIT redistribution grant. This records source provenance; it is not a legal determination about interoperability. [Claude Code license](https://github.com/anthropics/claude-code/blob/main/LICENSE.md)

By contrast, `anthropics/claude-code-playground` declares Apache-2.0, subject to any entry-specific third-party notices. Its README also describes the examples as unsupported experimental material. These samples are a better starting point for future compatibility fixtures than copying built-in Mods source into Cognia. [Playground README](https://github.com/anthropics/claude-code-playground), [Playground license](https://github.com/anthropics/claude-code-playground/blob/main/LICENSE)

None of that establishes a Claude Mods runtime: a module exporting `register(on)` is not a Cognia plugin exporting its activation contract. Renaming an entry file, embedding it in an iframe, or passing it to the existing JavaScript loader cannot supply the missing `$`, event, UI and lifecycle semantics.

### Reproduced conversion gap

The current `convertHookDocuments` selects `document.hooks` when it exists; otherwise it interprets the entire document as a legacy hook event map ([`ecosystem.ts`](../../lib/plugin/convert/ecosystem.ts), around lines 892–906). It does not separately account for sibling `modules`.

Two in-memory fixtures were passed to the real `convertPluginBundle(files, "cognia")` with `pnpm exec tsx`. Each used an ordinary `.claude-plugin/plugin.json` and an inert `hooks/register.js`; no plugin was loaded and no shell hook ran.

| `hooks/hooks.json` fixture                                                                                       | Observed result                                                                                                                |
| ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `{"modules":["./register.js"]}`                                                                                  | `unsupported`; reports `hook event "modules" has no Cognia hook-runtime equivalent`. Safe rejection, but inaccurate diagnosis. |
| `{"modules":["./register.js"],"hooks":{"SessionStart":[{"hooks":[{"type":"command","command":"echo ready"}]}]}}` | `fidelity: "structured"`, `blocking: []`, `warnings: []`, `capabilities: ["command-hooks"]`; module file retained.             |

The second result preserves a file, not its behavior. No Mods contribution is created or activated. This is a concrete false-positive conversion result, not evidence of compatibility. A first follow-up should detect module declarations regardless of ordinary hooks and give a specific unsupported/native-runtime-required report. Cases should cover modules-only, mixed and empty legacy hook maps, inline/custom hook documents, manifest `types`/`userConfig`, missing module paths and path escapes. Merely admitting `modules` as another ordinary hook event would not fix the problem.

### Compatibility matrix

| User expectation                                                                    | Assessment                                                                               | Suitable existing path                                                                                 |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Manage a Mod's package alongside other Cognia plugins                               | Feasible design, not implemented Mods support                                            | Existing plugin provenance, install/update, contribution and enablement lifecycle                      |
| Run a non-UI Mod inside a Cognia Claude SDK session                                 | Best candidate for first runtime experiment; version and trust validation still required | Existing `claudeAgentSdk.plugins` and sidecar runtime                                                  |
| Run the same Mod on Cognia's AI SDK, Pi, Codex or other agent runtimes              | No automatic compatibility                                                               | Deliberate semantic port through Cognia SDK/interceptors; runtime-specific assumptions must be removed |
| Show a Mod's pane, spinner or transcript customization in Cognia's native interface | Not provided by the Claude Agent SDK                                                     | Port selected UI through panels/slots/renderers, or separately evaluate a bounded UI adapter           |
| Keep the original interactive Claude interface                                      | Possible to investigate as terminal-hosted Claude, not native Cognia UI support          | Existing terminal/process hosting; discovery, isolation and lifecycle need their own verification      |
| Convert a Mod into an MCP server or skill automatically                             | Cannot preserve its engine hooks, continuation or UI behavior                            | Only extract truly independent tools or instructions, with explicit fidelity reporting                 |

Even a seemingly headless guard may require a pane to complete its decision. For example, a tool guard that waits for a button click is not suitable for SDK hosting just because its event is `tool.call`. Eligibility must be based on exercised behavior, not file extensions or event names alone.

### Recommended architecture

```text
Existing Cognia plugin management
  ├─ existing portable contribution conversion
  ├─ proposed retained Claude bundle + explicit session opt-in
  │    └─ existing trusted SDK option boundary → existing Claude runtime
  │         └─ supported non-UI Mod behavior (to be verified)
  └─ selected Cognia-native ports
       └─ existing SDK / interceptors / UI panels and slots
```

This separates package management from execution ownership. It also prevents the same bundle's tools, skills, MCP servers and settings hooks from being both converted into Cognia contributions and independently loaded again by Claude. The importer must choose and explain ownership per contribution rather than silently running both.

Native package resolution cannot be implemented by blindly adding the entire app-data directory to `trustedWorkspaceRoots`: the present gate deliberately binds trust to active workspace roots. A later design must use host-derived, narrowly scoped grants or a verified managed projection of the selected immutable bundle, with canonical-path checks. The Pi implementation is a precedent for such review, not a drop-in solution.

For native Mods, the trust description must remain distinct from Cognia's normal plugin permissions. Direct Mod filesystem/process/network/model APIs execute inside the foreign runtime. The existence of `canUseTool` or a Cognia plugin permission manifest does not prove those APIs are governed. Validate actual process containment, session credentials, outbound data handling, billing attribution and approval ordering before deciding which native Mods can be enabled. If required host guarantees cannot be enforced, restrict the offering to the appropriate trusted foreign-runtime mode or use a governed Cognia-native port.

### Staged follow-up and acceptance checks

These are proposed next steps, not work performed in this research.

1. **Accurate detection and reporting.** Extend the existing converter and co-located tests. Verify that every unsupported module is reported, mixed bundles cannot appear fully converted, and package retention is never labelled execution support.
2. **Isolated SDK conformance experiment.** Use a pinned, compatible engine and SDK pair with original minimal fixtures or appropriately licensed samples. Exercise `session.start`, tool observation/transformation, cancellation, resume and reload on the real Cognia sidecar path. Verify selected-session-only activation, no global configuration mutation, no duplicate registration, cleanup after disable, and actionable load failures.
3. **Trust and host matrix.** Verify direct Mod API calls against the real execution boundary, not only normal Claude tools. Include background/concurrent sessions, account isolation, remote-host path ownership and mobile-as-controller behavior. Do not advertise browser/mobile local execution from a desktop-side result. Fail or decline activation when required interaction is unavailable; never substitute approval.
4. **Plugin contribution design.** Only after the experiment passes, define the minimal Claude bundle contribution and per-agent/session selection using existing catalog, install origins, enablement and runtime option plumbing. Update the relevant ADR and generated contract mirrors; do not create a parallel registry or configuration store.
5. **Selective UI port if needed.** Pick an actual Mod users want, map its UI and behavior to existing panels/slots, and test the rendered interaction and unload lifecycle. A universal `$` shim and renderer are a separate substantial project, justified only by demonstrated demand and a bounded compatibility target.

No new model path, module runner or UI implementation is justified by this research alone. The existing infrastructure substantially reduces the work for native hosting and deliberate ports, but it does not remove the compatibility and authority differences.

## Evidence limits

- Upstream host support is documented behavior, not a successful Cognia integration test.
- No new Mod was installed, executed, or granted access during this research.
- No dependency or runtime source was changed for this report.
- SDK behavior, actual embedded engine version, plugin discovery, and permission boundaries require verification in Cognia's existing execution path before support can be claimed.
- The converter probe completed successfully and established only the two reported conversion outcomes. No end-to-end Mods session, full build, test suite or device validation was run for this documentation-only research.
