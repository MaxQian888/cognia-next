# Maintenance and scheduled-task gap research

Date: 2026-10-21 (Asia/Shanghai). Research only against the current shared working tree; no application data, production code, or timers changed. CodeGraph had no index, so evidence comes from literal searches and checked-out source. Tests below are proposed acceptance checks, not claimed executions. Source comments and ADRs can lag implementation. Recommendations were revised after the independent checks recorded in [the adversarial review](2026-10-21-scheduler-hardening-adversarial-review.md).

## Candidate backlog

### 1. Correct the local backup cadence's history scope — concrete logic gap

**Evidence.** [backup-scheduler.ts:112–118](../../lib/data/backup-scheduler.ts#L112) asks for the latest successful backup across all data-backup types/destinations, then discards it if its type is not `scheduled`. [backup-history.ts:113](../../lib/db/backup-history.ts#L113) implements that unscoped query. Remote cron legs also record `type: scheduled`: [backup-executor.ts:232–240](../../lib/scheduler/executors/backup-executor.ts#L232). Interval WebDAV rows omit `destination`: [backup-scheduler.ts:249–258](../../lib/data/backup-scheduler.ts#L249).

**Consequence.** A recent manual success can mask a still-recent local scheduled success, making the interval loop treat the schedule as never run. Conversely, a newer remote scheduled success can postpone a due local backup. This follows from query/filter composition; no live data-loss incident or production frequency was measured. The current test [backup-scheduler.test.ts:265](../../lib/data/backup-scheduler.test.ts#L265) only mocks one latest row and misses the mixed-history case.

**Smallest extension.** Select the intended producer/destination before limiting to one history row, stamp destination explicitly, and state whether cron-local runs intentionally satisfy interval-local cadence. Because the shared 50-row history cap can evict that row, also define durable cadence authority and migration for capped/cleared history; a filtered history query alone is incomplete. No new timer. Follow the existing backup opt-in; successful checks remain silent.

**Acceptance.** Seed an earlier recent scheduled-local row plus a newer manual row: no local write. Seed an old local row plus a recent remote row: local write is due. Cover legacy rows without destination, subscription-vault rows, history cap/clear, and document migration/default semantics.

### 2. Serialize scheduled backup writers — conditional correctness risk

**Evidence.** [startBackupScheduler:283–300](../../lib/data/backup-scheduler.ts#L283) starts an asynchronous tick and repeats with `setInterval`; it has no in-flight guard. Due checks and writes in [runScheduledBackupOnce:107–146](../../lib/data/backup-scheduler.ts#L107) do not claim ownership before writing. The output name is only day-granular: [build-package.ts:492–500](../../lib/data/build-package.ts#L492). The atomic Node sink protects partial files, but its final rename does not serialize concurrent writers: [backup-filesystem.ts:27](../../cli/src/serve/backup-filesystem.ts#L27).

**Consequence.** A tick lasting over 30 minutes, two mounted renderer owners, or an interval/cron overlap can each observe the same due state and write the same daily path. Duplicate work and last-writer replacement are plausible; no such race was exercised live. Independent hosts with independent databases are not asserted to share this race.

**Smallest extension.** Put the guard at the shared backup operation boundary, including the cron-local leg. Serialize conflicting operations while preserving distinct requests; coalesce only when producer, path, content scope and authorization are equivalent. If multiple windows can write the same host directory, reuse a host/database-scoped lease with rechecking after acquisition. Avoid inventing a global cross-host scheduler. Existing opt-in and silent-success behavior stay in force.

**Acceptance.** Block the first write, advance two tick intervals and invoke the cron-local leg; assert at most one conflicting writer is concurrent, while every distinct request still executes. Test different cron content and directories as well as equivalent interval checks. Release it and confirm the next due check sees its success. Stop during a pending tick and confirm no later tick is scheduled. Test lease expiry/recovery only if a durable lease is introduced.

### 3. Let opted-in memory maintenance become due without a chat turn — enhancement

**Evidence.** The only production callers of the daily lifecycle/vector/claim enqueue functions are [maintenance.ts:182–206](../../lib/memory/lifecycle/maintenance.ts#L182). Cold compaction/dedup can queue when chat learning is off, but still need this post-turn entry. Vector reconciliation additionally sits after learning, provenance, and minimum-turn guards. The worker itself only drains existing jobs: [job-worker.ts:159–182](../../lib/memory/lifecycle/job-worker.ts#L159). Day-bucketed durable dedupe already exists: [enqueue-reconcile.ts:53](../../lib/memory/lifecycle/enqueue-reconcile.ts#L53), [enqueue-reconcile.ts:127](../../lib/memory/lifecycle/enqueue-reconcile.ts#L127).

**Consequence.** An otherwise-running idle brain can have no daily cold-memory work queued after a day boundary until another eligible chat turn. This is a trigger limitation, not evidence of a missing lifecycle implementation. Storage retention of governance rows is a different owner and already runs daily. No recall-quality improvement is claimed.

**Smallest extension.** Add a cheap day-due enqueue step to the existing memory worker tick; reuse the durable daily keys. Read effective user configuration before enqueuing and again immediately before execution; a previously queued job must not mutate persistent memory after the user switches to temporary mode or disables the operation. Preserve enabled/temporary flags, cold-pass opt-ins, namespace isolation, and existing PII/provider gates. Do not enable learning, embeddings, or model spend merely because the process is idle. Make the outcome visible in the memory activity view; no routine notifications.

**Acceptance.** Advance an idle worker across UTC day boundaries without chat events: exactly one eligible lifecycle job per day across two workers. Disabled/temporary memory queues none; queued-then-temporary/disabled work also performs no persistent mutation. `learnFromChats: false` still permits explicitly enabled cold compaction, while no session distillation is created. Existing revision/evidence and namespace protections must still pass.

### 4. Enforce usage retention on long-running hosts — concrete trigger gap

**Evidence.** The only production calls to `pruneSessionUsageOlderThan` / `pruneProviderCostOlderThan` are boot initializers: [provider-cost-mirror-initializer.tsx:101–102](../../components/providers/initializers/provider-cost-mirror-initializer.tsx#L101), [headless initializers.ts:378–398](../../lib/headless/runtimes/initializers.ts#L378). [table-catalog.ts:1768–1772](../../lib/data-governance/table-catalog.ts#L1768) declares a 90-day domain TTL for usage. The indexed pruning helpers already exist: [session-usage.ts:885–900](../../lib/db/session-usage.ts#L885), [provider-cost-daily.ts:184–198](../../lib/db/provider-cost-daily.ts#L184). Usage-ledger commits update rows/projections but do not call these helpers.

**Consequence.** Records that age past 90 days after boot remain until the next initializer run. This matters more to a continuously running brain; disk/RSS and query-performance impact were not measured and must not be quantified from source alone.

**Smallest extension.** Register one catalog-backed usage-retention executor in the already-daily storage sweep, updating catalog enforcement to match. Define exact-time versus local-day cutoff semantics and coordinated failure/retry behavior with the usage owner before reusing the domain helpers and central error isolation; do not add a provider-cost interval or re-run ledger projection rebuilds daily. Keep the existing 90-day policy, silently collect counts, and preserve current-day budget mirrors.

**Acceptance.** Boot with an 89-day-old usage row, advance two days without restarting, then run the ordinary sweep: old usage and matching expired rollups disappear; recent rows and today's cost totals stay intact. A pruning failure must not block other targets. Cover midday cutoff-day records, partial failure between helpers, retry and idempotency receipts; do not assume strict equality between differently retained views without an owning contract.

### 5. Add non-mutating backup verification before destructive rotation — enhancement

**Evidence.** The shared local writer returns after host output completes: [backup-scheduler.ts:38–89](../../lib/data/backup-scheduler.ts#L38). The interval path rotates older files before appending success: [backup-scheduler.ts:148–178](../../lib/data/backup-scheduler.ts#L148). There is no read seam in `BackupFilesystem`. Integrity verification already exists in the v4 reader, including checksums, authenticated records, hash chain and mandatory footer: [stream-format.ts:198–285](../../lib/data/stream-format.ts#L198). V3 decrypt/checksum support also exists in [crypto.ts:236](../../lib/data/crypto.ts#L236).

**Consequence.** A successful write is evidence of output completion, not a readback/restore check. Later corruption or an unreadable auto-key is only discovered at import. Existing atomic writes already mitigate partial output; no corruption incident was reproduced.

**Smallest extension.** Add a bounded read-stream seam and reuse the format-appropriate decoder to verify a distinct pending artifact before final commit/rotation, or use independent immutable generations. Same-day output can overwrite the previous daily filename before readback starts, so verifying after overwrite is insufficient. Preserve a previously verified recovery point if verification fails. For V4, consume `readBackupStream` records without materializing a full package. V3 decrypts the full buffer: cap pre-read file size and KDF cost; over-budget files remain untouched with blocked/unsupported status. Record written/verified timestamps separately. If recurring re-verification is desired, make its I/O budget and cadence opt-in and reuse the backup owner; do not create another backup scheduler or silently restore user data.

**Acceptance.** Correct encrypted backup verifies without any database writes. The sole previously verified same-day file survives a corrupt new artifact or failed verification. Missing footer, tampered chunk, unavailable key and read failure produce distinct failure states and prevent rotation of the last verified file. Exercise large V4 input with bounded record buffering and separately reject oversized/KDF-over-budget V3 input before reading/decryption. Distinguish format verification from a separately authorized restore drill.

### 6. Expose maintenance failures without making every tick noisy — enhancement

**Evidence.** [RetentionResult:225–228](../../lib/storage/retention.ts#L225) only contains target ID/count; the catch path [255–257](../../lib/storage/retention.ts#L255) reports the same `{ removed: 0 }` as a healthy empty sweep. `sweepOnce` discards returned counts in [retention.ts:290](../../lib/storage/retention.ts#L290). Silent scheduler maintenance is deliberate, including errors: [maintenance-tasks.ts:41–49](../../lib/scheduler/maintenance-tasks.ts#L41). Retention is not itself represented by those scheduler run histories.

**Consequence.** The retention API cannot distinguish failure from no eligible rows, and the runtime can remain started while an individual target repeatedly fails. Logs do carry failures; no claim is made that errors are completely invisible.

**Smallest extension.** Return content-free target/substep status codes distinguishing partial, blocked, off, failed and no-work completion. Reuse existing source attempt/success fields and a bounded owner summary where needed. Extend user-opened diagnostics/maintenance detail; do not infer success from no thrown exception. Keep routine maintenance failures silent too, including notification-center rows, navigation/OS badges and tab titles. Any later escalation requires a separate explicit opt-in contract.

**Acceptance.** One rejecting target records failed status while another still succeeds; row pruning succeeding while file sweeping fails records partial status; a later successful run clears the unhealthy state; empty healthy runs remain distinguishable. Ensure diagnostics contain no transcript, file contents, secrets or raw error payloads, and repeated unchanged failures do not create repeated notifications.

## Rejected duplicate / unsupported proposals

- **Another storage/audit cleanup timer:** both are already boot/daily and brain-wired. Extend their executor/policy lists.
- **Generic Sites/video artifact GC:** already present in the central storage owner. Sites GC preserves active deployments, unfinished operations and rollback versions: [artifact-gc.ts:10–27](../../lib/sites/artifact-gc.ts#L10). There is no evidence here supporting deleting arbitrary user artifacts/caches by age.
- **Another failed-job recovery service:** memory retry/lease recovery and opt-in background-task redispatch already exist. Do not automatically replay arbitrary side effects just because a row failed.
- **Brain ignores a configurable automation-audit retention setting:** off-Tauri audit retention indeed uses defaults, but `automation_settings_get` explicitly rejects headless at [service_plane.rs:1781–1785](../../crates/cognia-companion-rpc/src/rpc/service_plane.rs#L1781). A configurable brain automation policy would be a new feature, not a proven dropped setting.
- **Companion idempotency receipt cleanup:** already owned by the shared Rust server; [server.rs:133](../../crates/cognia-companion/src/server.rs#L133) and [345–351](../../crates/cognia-companion/src/server.rs#L345) schedule completion-aware retention. Do not add a renderer sweep.

## Verification boundary

No broad tests, app launch, provider calls, destructive cleanup, or network/production calls were run. Findings 1 and 4 identify source-level gaps; 2 is a source-supported race hypothesis requiring a deferred-write reproduction; 3, 5 and 6 are product/operability enhancements. All candidates need adversarial review and scoped acceptance tests before implementation. Highest-value first checks are mixed backup history and continuously running usage retention; neither requires a new timer subsystem.
