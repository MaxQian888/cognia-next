# Capacitor camera and scanner API audit sources

Research date: 2026-10-02. Scope: current official documentation, installed plugin contracts, Android/iOS capture permissions, recovery, and web fallbacks. This is a source audit; no physical camera or authenticated mobile runtime was exercised.

## Version baseline

`mobile/package.json`, `pnpm-lock.yaml`, and installed package metadata resolve Camera **8.2.4**, ML Kit Barcode Scanning **8.2.1**, App **8.1.1**, and Capacitor core/platforms **8.5.2**. Direct read-only npm registry queries on the research date returned camera 8.2.4, scanner 8.2.1, and core 8.5.2 as `latest`.

The Camera repository is now [`ionic-team/capacitor-camera`](https://github.com/ionic-team/capacitor-camera). The old `capacitor-plugins/main/camera` subtree still reports 8.0.2 and must not be used to judge this installed 8.2.4 contract. [Camera 8.2.4 definitions](https://github.com/ionic-team/capacitor-camera/blob/v8.2.4/src/definitions.ts), [scanner package metadata](https://github.com/capawesome-team/capacitor-mlkit/blob/main/packages/barcode-scanning/package.json).

## Camera contract and migration boundary

- Since 8.1.0, `takePhoto` and `chooseFromGallery` supersede deprecated `getPhoto` and `pickImages`. The old methods remain implemented in 8.2.4; deprecation alone is not a present runtime failure. [Current Camera documentation](https://capacitorjs.com/docs/apis/camera).
- Installed `ImageOptions` accepts source values `CAMERA`, `PHOTOS`, `PROMPT` and result types `base64`, `uri`, `dataUrl`. `Photo.base64String`, `.dataUrl`, `.webPath`, `.path`, and `.format` match `lib/capacitor/camera.ts`. `pickImages` returns `{ photos: GalleryPhoto[] }`, with a browser-renderable `webPath`. The wrapper's literal enum values and returned property names are correct. [Exact 8.2.4 definitions](https://github.com/ionic-team/capacitor-camera/blob/v8.2.4/src/definitions.ts).
- Migration changes data semantics: new methods return `MediaResult`; `uri` replaces `path`, `metadata.format` requires `includeMetadata`, and native `thumbnail` is a reduced-resolution image. Full-resolution base64 requires reading the native URI. There is no automatic Prompt UI, and `targetWidth`/`targetHeight` must be supplied together. A method rename without preserving full-resolution upload/ingest would regress existing behavior. [Camera migration guide](https://capacitorjs.com/docs/apis/camera#migrating-to-the-new-api).
- New native methods provide structured error codes, including camera denial `OS-PLUG-CAMR-0003`, photo cancellation `0006`, and gallery cancellation `0020`; these codes do not apply retroactively to legacy `getPhoto`/`pickImages`. Legacy iOS cancellation rejects with `User cancelled photos app`, which the camera wrapper's `/cancel/i` branch handles. [Errors](https://capacitorjs.com/docs/apis/camera#errors), [8.2.4 iOS implementation](https://github.com/ionic-team/capacitor-camera/blob/v8.2.4/ios/Sources/CameraPlugin/CameraPlugin.swift).

## Camera permission facts and a rejected false positive

The installed Android Camera plugin returns `photos: granted` for the system picker. Camera permission is required when the host manifest declares `CAMERA`; absent that declaration, the plugin synthesizes camera permission as granted and uses the external camera app. Cognia declares `CAMERA` for its other camera paths, so the Camera wrapper's native camera permission check must not be labeled unnecessary by applying the documentation's general permission statement without this manifest exception. [Camera 8.2.4 Android source](https://github.com/ionic-team/capacitor-camera/blob/v8.2.4/android/src/main/java/com/capacitorjs/plugins/camera/CameraPlugin.kt).

The iOS legacy implementation's `showPhotos()` only tests `.authorized`, but calls the old `PHPhotoLibrary.authorizationStatus()` and `requestAuthorization(_:)` overloads. Apple explicitly documents that these old overloads return `.authorized` for limited access for compatibility. Therefore this code is **not evidence that limited access fails**. The wrapper's newer `checkPermissions()` sees `limited`, treats it as usable, and can issue a redundant photo permission request; a failure claim needs real evidence beyond the enum comparison. [Apple WWDC20 limited photo library API explanation](https://developer.apple.com/videos/play/wwdc2020/10641/?time=516).

Apple's system Photos picker can operate without broad library authorization, returning only selected items. The legacy plugin itself adds a library authorization gate before presenting that picker. Migrating to `chooseFromGallery` is the documented direction, but acceptance of a permission-free/denied-library path should be verified against its IONCameraLib implementation and on-device behavior before claiming the migration fixes it. [Apple photo selection sample](https://developer.apple.com/documentation/PhotoKit/selecting-photos-and-videos-in-ios), [8.2.4 iOS delegation](https://github.com/ionic-team/capacitor-camera/blob/v8.2.4/ios/Sources/CameraPlugin/CameraPlugin.swift).

## ML Kit scanner contract and concrete mismatches

`scan({ formats: ['QR_CODE'] })` correctly invokes the ready-made native UI and returns `{ barcodes: [...] }`; `rawValue` is the appropriate payload. This API is native-only. Web scanning instead uses `startScan` with a video element and Barcode Detection API support/polyfill. On Android, `scan` uses Google Play Services, requires its downloadable barcode module, and **does not require the app's camera permission**; `startScan` does. iOS native scanning requires camera permission. [Capawesome API documentation](https://capawesome.io/docs/sdks/capacitor/mlkit/barcode-scanning/).

Concrete source-backed issues:

1. Both `lib/qr/barcode-scanner.ts:67-72` and the permission gate in `lib/capacitor/barcode.ts` reject Android users who denied the app camera permission before attempting the permission-free `scan` API. This confuses `scan` with `startScan`. [Google code scanner privacy/permission model](https://developers.google.com/ml-kit/vision/barcode-scanning/code-scanner).
2. Native user cancellation rejects with `scan canceled.` on Android and iOS. Both facade catch blocks normalize all rejections to `error`; their `cancelled` path only covers an empty successful result. [Android rejection implementation](https://github.com/capawesome-team/capacitor-mlkit/blob/main/packages/barcode-scanning/android/src/main/java/io/capawesome/capacitorjs/plugins/mlkit/barcodescanning/BarcodeScannerPlugin.java), [iOS cancellation implementation](https://github.com/capawesome-team/capacitor-mlkit/blob/main/packages/barcode-scanning/ios/Plugin/BarcodeScanner.swift).
3. The legacy QR facade has no module availability/install flow. The Android plugin checks availability internally and rejects if missing; declaring installation-time metadata alone does not establish immediate availability. `lib/capacitor/barcode.ts` adds installation, but must treat `installGoogleBarcodeScannerModule` resolution as acceptance, await terminal progress, and clean up rejection paths. [Module installation implementation](https://github.com/capawesome-team/capacitor-mlkit/blob/main/packages/barcode-scanning/android/src/main/java/io/capawesome/capacitorjs/plugins/mlkit/barcodescanning/BarcodeScanner.java).
4. `lib/qr/barcode-scanner.ts:33-40` keeps an ignored bare module import and returns the Capacitor proxy directly. It does not reuse the global registered plugin loader/non-thenable protection in `lib/capacitor/_shared.ts`, unlike the newer facade. Its native usability depends on the actual bundled call path; establish current callers before assigning user impact.

## Native setup and recovery

Cognia's iOS 16.0 target satisfies Capacitor 8's iOS 15.0 and Capawesome's documented scanner 15.5 requirements; Android minSdk 24 exceeds Google's scanner minimum 23. iOS Camera needs camera, photo-library, and photo-add usage strings. Android scanner setup includes `CAMERA` plus `com.google.mlkit.vision.DEPENDENCIES=barcode_ui`. Cognia has the camera permission and iOS descriptions; native metadata/dependency freshness must be audited independently. [Capacitor 8 upgrade requirements](https://capacitorjs.com/docs/updating/8-0), [scanner setup](https://capawesome.io/docs/sdks/capacitor/mlkit/barcode-scanning/), [Google scanner minimum/configuration](https://developers.google.com/ml-kit/vision/barcode-scanning/code-scanner).

External camera/scanner Activities can outlive the WebView/app. `App.addListener('appRestoredResult', ...)` receives `pluginId`, `methodName`, `success`, `data`, and optional `error`. The normal JavaScript promise cannot restore a composer after Android destroys it. No `appRestoredResult` occurrence was found in `lib/`, `components/`, `hooks/`, `app/`, or `stores/`. Recovering data also needs preserved attachment/session context. Scanner documentation warns a killed process can produce an unrecoverable scan error, so recovery must handle failure as well as success. [App restoration API](https://capacitorjs.com/docs/apis/app#addlistenerapprestoredresult), [scanner scan lifecycle](https://capawesome.io/docs/sdks/capacitor/mlkit/barcode-scanning/#scan).

The checked-in iOS `Podfile`/lock currently pin older core 8.4.2, Camera 8.2.0, and scanner 8.1.0 pnpm paths, while installed dependencies use the newer versions above. A JS-only/API audit does not establish an updated iOS binary; native sync/pod resolution is a separate gate.

## Browser and WebView boundaries

- `getUserMedia` requires a secure context and permission. Camera streams should stop their tracks when the owning flow ends, including asynchronous acquisition after that flow closes. Track lifetime is independent of React component lifetime. [Media Capture and Streams specification](https://www.w3.org/TR/mediacapture-streams/).
- Android WebView must grant/deny `onPermissionRequest`; Capacitor 8.5.2 already maps video capture to `CAMERA`, and audio capture to `RECORD_AUDIO` plus `MODIFY_AUDIO_SETTINGS`. Its iOS delegate grants WebKit's media capture decision, while OS privacy permissions still apply. Do not infer the host omits delegates simply because Cognia has no override. [Android host API](<https://developer.android.com/reference/android/webkit/WebChromeClient#onPermissionRequest(android.webkit.PermissionRequest)>), [Apple delegate](<https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:requestmediacapturepermissionfor:initiatedbyframe:type:decisionhandler:)>), [Capacitor Android bridge](https://github.com/ionic-team/capacitor/blob/8.5.2/android/capacitor/src/main/java/com/getcapacitor/BridgeWebChromeClient.java).
- `capture="environment"` with `accept="image/*"` is a valid rear-camera preference, with user-agent fallback behavior. It does not promise a camera UI on all desktop browsers. `lib/capacitor/camera.ts` correctly uses this file-picker mechanism, but its web multiple-selection flow discards the requested `limit`, and file-reading rejection escapes its declared outcome contract. [HTML Media Capture standard](https://www.w3.org/TR/html-media-capture/).

## Acceptance still required

Source and mocked tests do not establish actual iOS/Android camera access. Cover a fresh Android install with an absent Google module; Android denied app camera permission while using Google scanner UI; native cancel/back; no Google Play Services; iOS camera denial and limited photo selection; app destruction during external capture; browser cancellation; and unmount/background acquisition races. Keep native dependency sync/build, JavaScript tests, and physical-device acceptance as separate evidence.
