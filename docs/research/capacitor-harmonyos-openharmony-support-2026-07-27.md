# Capacitor support for Huawei HarmonyOS and OpenHarmony

Date: 2026-07-27  
Access date for all linked sources: 2026-07-27  
Scope: official Capacitor, Huawei, and OpenHarmony documentation; package metadata and source repositories maintained by the adaptation projects themselves. Third-party tutorials and unofficial API wrappers are excluded.

## Executive conclusion

Capacitor does **not** officially support HarmonyOS, HarmonyOS NEXT, or OpenHarmony. Ionic documents and ships iOS, Android, and Web targets, and closed both the [HarmonyOS request](https://github.com/ionic-team/capacitor/issues/7173) and the later [HarmonyOS NEXT request](https://github.com/ionic-team/capacitor/issues/7818) as **not planned** ([Capacitor documentation](https://capacitorjs.com/docs), [Capacitor 8.4.2 release](https://github.com/ionic-team/capacitor/releases/tag/8.4.2)).

Two external ports now merit evaluation:

- CPF-Ionic's [`@capacitor-ohos/ohos` 8.0.2](https://www.npmjs.com/package/@capacitor-ohos/ohos) has the broadest plugin catalog and is the only credible migration starting point for Cognia's existing Capacitor 8 shell. It is active, but its `hionic` CLI, automated-test evidence, custom networking stack, and commercial-HarmonyOS positioning all require independent validation ([CPF-Ionic organization](https://gitcode.com/CPF-Ionic), [platform README](https://gitcode.com/CPF-Ionic/openHarmony-capacitor/blob/main/README.en.md)).
- Eclipse Oniro's [`@oniroproject/capacitor-openharmony` 0.1.2](https://www.npmjs.com/package/@oniroproject/capacitor-openharmony) has a simpler ArkTS architecture and declares Capacitor 6/7/8 compatibility, but its own plan and status documents describe an MVP with seven plugin families, incomplete methods, and future security/CI work ([repository](https://github.com/eclipse-oniro4openharmony/capacitor-openharmony), [phase status](https://github.com/eclipse-oniro4openharmony/capacitor-openharmony/blob/main/docs/phase4_status.md)).

The evidence supports a **conditional go for a time-boxed CPF-Ionic spike, not a production port**. The smallest useful slice should load Cognia's static export, pair by manually entered endpoint/token, store the token through a new Asset Store adapter, reconnect, list conversations, and send/receive text. QR scanning, biometrics, voice, mDNS, and UI chrome can remain outside that first slice. Production is a no-go until Capacitor 8 coexistence, secure storage, TLS behavior, signing, a commercial target device, and AppGallery package acceptance are demonstrated.

OpenHarmony and commercial HarmonyOS also cannot be treated as interchangeable release targets. Any OpenHarmony success must therefore be repeated with the Huawei SDK, signing identity, intended commercial device, and AppGallery workflow.

## Cognia dependency impact

Cognia is structurally suitable for an ArkWeb experiment because its mobile shell already consumes the shared Next.js static export through `webDir: "../out"` ([mobile configuration](../../mobile/capacitor.config.ts), [ADR-0014](../content/docs/en/adr/0014-capacitor-mobile-shell.md)). The bridge and native capability surface—not the React bundle—is the dominant migration risk.

`mobile/package.json` contains 25 native integration packages when `@capacitor/android` is excluded ([mobile dependencies](../../mobile/package.json)):

- CPF-Ionic offers candidate ports for the 18 first-party families: App, Browser, Camera, Clipboard, Device, Dialog, Filesystem, Geolocation, Haptics, Keyboard, Local Notifications, Network, Push Notifications, Screen Orientation, Share, Splash Screen, Status Bar, and Toast ([CPF-Ionic catalog](https://gitcode.com/CPF-Ionic)).
- It also offers `@capacitor-ohos/native-settings`, covering the family used by Cognia's `capacitor-native-settings` dependency ([package metadata](https://www.npmjs.com/package/@capacitor-ohos/native-settings)).
- Six exact packages have no published drop-in counterpart: `@capacitor-mlkit/barcode-scanning`, `@capgo/capacitor-navigation-bar`, `@capgo/capacitor-native-biometric`, `capacitor-secure-storage-plugin`, `capacitor-voice-recorder`, and `capacitor-zeroconf`.

Cognia's top-level runtime detection is relatively portable because it classifies any bridge whose `isNativePlatform()` returns true as `mobile` ([runtime detection](../../lib/platform/detect.ts)). Platform-specific helpers are not yet portable:

- Oniro injects `getPlatform() === "openharmony"` ([bridge source](https://github.com/eclipse-oniro4openharmony/capacitor-openharmony/blob/main/capacitor-openharmony/assets/native-template/entry/src/main/ets/capacitor/CapacitorBridge.ets)). CPF-Ionic's shipped JavaScript bridge has no HarmonyOS identifier: it returns only `android`, `ios`, or `web`, and selects `android` when an `androidBridge` proxy is present ([bridge source](https://gitcode.com/CPF-Ionic/openHarmony-capacitor/blob/main/src/main/resources/rawfile/native-bridge.js)). The exact runtime value must be recorded on-device rather than inferred.
- Cognia forwards that value during pairing and uses it in device identity ([pairing helper](../../components/mobile/pair/pair-helpers.ts), [device identity](../../lib/device/device-identity.ts)). Oniro would therefore introduce a new value; CPF may incorrectly label a HarmonyOS device as Android.
- Cognia's mobile WebDAV autosync currently runs only when the value is `ios` or `android` ([autosync provider](../../components/providers/webdav-mobile-autosync-provider.tsx)). It would remain enabled if CPF reports `android`, but would be disabled under Oniro until Cognia explicitly accepts `openharmony`.

This is a small TypeScript adaptation compared with writing plugins, but it is a concrete reason that “the web bundle loads” is not equivalent to behavioral parity.

System bar handling is low risk relative to the other gaps. The core networking path also needs special scrutiny. ## Toolchain, signing, and distribution

### Host tooling

Huawei's current DevEco Studio page lists Windows 10/11 64-bit and macOS x86 11–15/26 or Apple Silicon 12–15/26; it does not list Linux. It also requires substantial local disk and memory, and bundles the Hvigor build workflow ([DevEco Studio](https://developer.huawei.com/consumer/cn/deveco-studio)). This means:

- **macOS is officially supported by DevEco Studio**, including Apple Silicon within Huawei's listed OS range.
- **Windows is officially supported** and is the safest host for CPF-Ionic automation because the `hionic` repository documents `open` and `buildapp` as Windows-only and requires `DEVECO_SDK_HOME`/`DEVECO_IDE_PATH` ([hionic repository](https://gitcode.com/CPF-Ionic/capacitor-cli)).
- **Linux is not an officially listed DevEco Studio host**. A headless Hvigor experiment may be useful, but production signing/build CI must not be planned on Linux until Huawei documents and the team proves that exact configuration.
- On macOS, expect to create/open/build the native project through DevEco Studio or direct Hvigor commands if `hionic open/buildapp` refuses the host. This is a CLI limitation, not an IDE limitation.

### Signing and device installation

HarmonyOS controls application integrity with a signing certificate and Profile; only signed applications may be installed on physical devices. Previewer/emulator use does not require signing, while real-device testing does, and DevEco Studio offers automatic and manual signing ([Huawei getting-started guide](https://developer.huawei.com/consumer/cn/develop-novice-guide/)). The spike must therefore record:

1. the AGC app identity and exact bundle/package name;
2. development and release signing ownership, certificate/Profile issuance, expiry, rotation, and protected storage;
3. the signed HAP/APP artifact hash and signing-certificate fingerprint;
4. installation on the intended device through DevEco Studio or `hdc`—Huawei documents `hdc app install` for HAP installation ([installation guide](https://developer.huawei.com/consumer/cn/doc/doccenter-deveco-studio/ide-emulator-install-upload)).

Do not accept emulator-only evidence. Camera, biometrics, secure hardware-backed storage, mDNS, notifications, TLS, and release signing all have material real-device behavior.

### AppGallery

The official AppGallery flow requires a verified Huawei ID, an AppGallery Connect app, an uploaded package, localized name/introduction/screenshots/category, pricing and release countries/regions, a privacy-policy URL, and review submission ([AppGallery release overview](https://developer.huawei.com/consumer/en/appgallery/)). The bundle name/app identity configured in AppGallery Connect must be reconciled with the DevEco project before signing and upload; Huawei's preparation flow creates a HarmonyOS app in AppGallery Connect and associates the project identity ([HarmonyOS AGC preparation](https://developer.huawei.com/consumer/en/codelab/AGCPreparation-HarmonyOS/)).

AppGallery Connect provides Integration Check, Open Testing, App Release, App Signing, and phased release capabilities ([AGC overview](https://developer.huawei.com/consumer/en/doc/distribution/app/agc-help-overview-0000001100246618), [AGC product page](https://developer.huawei.com/consumer/en/agconnect/)). Publishing is asynchronous: Huawei's API documentation requires package and visual assets before review, says uploaded packages are parsed asynchronously, and notes that App Signing compilation must complete before release submission ([Publishing API](https://developer.huawei.com/consumer/en/doc/development/AppGallery-connect-Guides/agcapi-release_app)).

Geography must be confirmed with Huawei for Cognia's app category before product planning. Huawei's current **HarmonyOS game** instructions state that HarmonyOS NEXT apps are globally available only on smart watches and that other device types are limited to mainland China; because that page is game-specific, it is evidence of a potential distribution constraint, not proof that the same rule applies unchanged to Cognia ([HarmonyOS game region policy](https://developer.huawei.com/consumer/en/doc/app/agc-help-release-game-area-0000002399129161)). An app-specific written policy answer or successful target-region console configuration is a release gate.

## Time-boxed go/no-go spike

Run the experiment in a disposable branch or fixture. Do not introduce `hionic` into Cognia's production dependency graph until its Capacitor 3 CLI dependency and the Capacitor 8 platform package have coexisted successfully.

### Smallest viable feature slice

The slice is deliberately narrower than mobile parity:

1. package and launch the existing `out/` static export in ArkWeb;
2. expose App, Device, Network, and Browser bridge calls used by the pairing/text path;
3. let the user manually enter the desktop endpoint and one-time token;
4. store only the resulting credential in a custom Asset Store adapter;
5. restart the app, restore the credential, connect over the intended TLS/WebSocket transport, list conversations, and send/receive text;
6. sign and install the package on one intended commercial HarmonyOS device, then upload it to AppGallery Connect far enough to obtain package parsing/Integration Check results.

This slice excludes QR, biometrics, voice recording, mDNS discovery, custom navigation-bar appearance, push notifications, background jobs, and feature parity. Excluding them is not a production waiver; it isolates the bridge, credential, transport, signing, and distribution risks that could invalidate the entire approach.

If the CLI cannot create a Capacitor 8-consistent project, record that failure and try CPF-Ionic's documented manual route once: create the DevEco project, integrate the `@capacitor-ohos/ohos` native source/module, and copy `capacitor.config.json`, `capacitor.plugins.json`, and `www` assets ([platform README](https://gitcode.com/CPF-Ionic/openHarmony-capacitor/blob/main/README.en.md)). Needing the manual route is not itself a no-go, but the resulting project must be reproducible by a checked-in script or documented deterministic build; an IDE-only hand-edited project is not a production foundation.

### Required artifacts

- dependency resolution report showing the exact `@capacitor/core`, `@capacitor/cli`, `@capacitor-ohos/ohos`, `hionic`, plugin, OpenSSL, HarmonyOS SDK, and Hvigor versions;
- generated native project, `oh-package-lock.json5`, plugin registry, permissions, and a diff from the untouched fixture;
- signed debug HAP and release upload artifact, SHA-256 hashes, signing fingerprint, and certificate/Profile ownership record;
- DevEco/Hvigor build log, `hdc` install/run log, `hilog`, ArkWeb console log, and screenshots/video of the real-device flow;
- method-level bridge contract results for App, Device, Network, Browser, and the new Asset Store adapter;
- TLS/WebSocket evidence for valid certificate, invalid chain, hostname mismatch, expired certificate, and pin mismatch;
- cold-start, restart, foreground/background, network-switch, offline/reconnect, permission denial, and crash-recovery results;
- AppGallery Connect package parsing, Integration Check/Open Testing output, target-region availability evidence, privacy declaration, and any review feedback;
- software-composition/license report plus review of the CPF C/C++, OpenSSL, ArkTS bridge, and outbound network path.

### Acceptance checks

| Gate                | Pass condition                                                                                                                                                                   | No-go signal                                                                                                              |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Capacitor 8 build   | The fixture resolves and builds without downgrading or shadowing Cognia's Capacitor 8 runtime; repeated clean builds produce the same dependency graph.                          | Requires Capacitor 3 application runtime, unresolved bridge ABI, or manual edits that cannot be reproduced.               |
| Commercial target   | Signed package installs and launches on the intended commercial HarmonyOS device/OS, not only OpenHarmony or emulator.                                                           | No access to the target SDK/device/signing identity, or success only on an OpenHarmony board/emulator.                    |
| Static shell        | All routes/assets/fonts/workers required by the slice load from `out/` with no broken paths, origin/CORS surprises, or debug-only flags.                                         | Static export cannot run under the packaged ArkWeb origin.                                                                |
| Bridge/lifecycle    | Used methods and listener behavior match their TypeScript contracts across cold start, pause/resume, relaunch, and permission failures.                                          | Silent fallback, placeholder IDs/listeners, duplicated events, or unrecoverable lifecycle state.                          |
| Credential security | Token uses Asset Store, survives allowed restart/upgrade scenarios, is absent from logs/preferences/plain files/backups, and is removed on logout/uninstall according to policy. | Any fallback to Web storage/plain files, token leakage, inability to delete, or undefined restore/backup behavior.        |
| Transport security  | Authenticated HTTP/WebSocket traffic succeeds with the expected trust/pin and reliably fails closed for invalid chain, hostname, expiry, or pin.                                 | Trust-all behavior, inconsistent OpenSSL/system trust, pin bypass, or credentials sent before verification.               |
| Useful text flow    | After manual pairing and restart, the app reconnects, lists conversations, and sends/receives text under online/offline/network-switch tests.                                    | Only a static page demo or one-shot happy path works.                                                                     |
| Distribution        | Release artifact is signed, parsed by AppGallery Connect, passes Integration Check/Open Testing prerequisites, and the intended category/region is confirmed.                    | Package/signature rejection, unresolved bundle identity, missing compliance material, or unavailable target distribution. |
| Maintainability     | Pinned source and deterministic build are auditable; critical adapters have contract/unit/device tests and an owner/update plan.                                                 | Dependency source cannot be reproduced/audited, or the team cannot own the native fork and security fixes.                |

The spike is a **go to a larger pilot only if every gate passes**. It is a no-go if any security, commercial-device, Capacitor 8, deterministic-build, or AppGallery gate fails. Feature gaps such as QR or voice may proceed to a second phase only after the platform-level gates pass.

## Options and recommendation

1. **Keep the Android build for verified compatible Huawei devices.** This is the lowest-cost legacy route. Maintain an explicit model/OS matrix and audit Google-only dependencies; do not market it as HarmonyOS NEXT support.
2. **Use web/PWA as the HarmonyOS NEXT fallback.** This preserves web-safe Cognia features while native work matures, but it cannot claim native parity for secure storage, push, biometrics, LAN discovery, background behavior, or the other integrations.
3. **Run the CPF-Ionic spike above if native HarmonyOS distribution is a near-term requirement.** It has candidate coverage for 19 of 25 Cognia integration families and the closest Capacitor 8 lineage, but Cognia must own the six missing adapters, networking/security verification, build reproducibility, and device/distribution CI.
4. **Keep Oniro as a monitored alternative, not the current implementation choice.** Its architecture and Eclipse hosting are useful, but six of 25 Cognia integrations and explicit MVP gaps make its present migration cost substantially higher.
5. **Consider a fully native ArkTS shell only after the spike.** If the CPF bridge or lifecycle is the blocker while Huawei APIs themselves pass, a narrow native shell may be more maintainable than carrying an under-tested Capacitor fork. That is a separate product investment, not a fallback hidden inside this estimate.

**Evidence-based recommendation:** approve only a two- to three-week, isolated CPF-Ionic feasibility spike with Windows and macOS build evidence and at least one intended commercial HarmonyOS device. Keep the existing Android and web routes as the shipping strategy meanwhile. Do not approve a production schedule or parity claim until the spike passes all platform gates and the six-plugin roadmap is separately estimated. Based on current release breadth CPF-Ionic is the stronger experiment; based on current tests, CLI metadata, native networking surface, signing, and distribution evidence, neither CPF-Ionic nor Oniro is ready to be treated as a supported production target.
