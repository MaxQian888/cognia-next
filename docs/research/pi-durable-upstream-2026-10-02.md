**Research date:** 2026-10-02 (Asia/Shanghai).

## Contracts worth studying

### 1. Durable effect boundaries, rather than merely saving a chat

Model requests and tool executions are durable tasks. For a tool, preparation validates arguments and runs the pre-tool hook, then commits execution intent before calling the implementation. Recovery reruns only when **both the recorded policy and the currently resolved implementation say `replay: "safe"`**. The default is unsafe. Otherwise it writes an interrupted result containing committed partial output and informs the model that execution may have partially happened. This does not undo an external effect. ([tool implementation](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/tool.ts#L37-L110), [replay policy tests](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/harness-tools-recovery.test.ts#L109-L211))

A model request interrupted after a committed partial response retains that partial as an aborted transcript entry and resends the prepared request. Separate recovery tests cover interruption before preparation commit, requests without partials, retry backoff, deferred-response polling, and unavailable pinned models. These are inspected test cases, not tests run during this research. ([generation recovery tests](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/harness-generation-recovery.test.ts#L41-L268))

`requestId` deduplicates **submissions within one conversation**. The code returns the original submission before any write, rejecting only a different submission type. Same-type reuse with different content still returns the old submission; the tests explicitly submit `"hi"` and then `"different"` with the same ID. This is admission idempotency, not payload-conflict detection or exactly-once model/tool side effects. ([admission](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/submissions.ts#L148-L166), [tests](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/harness-submissions.test.ts#L82-L105))

### 2. Explicit ownership, idle, cancellation, and background lifetimes

Tasks can own tasks and conversations. An owner with a decided result can remain `completing` while its owned foreground work finishes. Failure and abort cascade through owned foreground work; cleanup proceeds from children toward parents. A `background` task is an ownership boundary: its subtree does not keep the parent busy and survives ordinary parent cancellation. Directly cancelling that task or explicitly including background work still stops it. Conversation abort withdraws queued inputs but retains queued writes. Cancelling a caller's wait does not cancel shared work. ([ownership tests](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/harness-ownership.test.ts#L173-L319), [wait cancellation](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/harness-ownership.test.ts#L462-L490))

Custom task phases commit checkpoints, wait for child task outcomes, and support `allSettled` or `failFast`. Missing or incompatible task definitions leave work blocked rather than guessing how to execute it. The scheduler enforces invocation-bound APIs: code cannot keep committing after its invocation ends. ([scheduler](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/scheduler.ts))

The latest substantive durable change adds lifecycle conformance and a live task graph for owner edges, states, background flags, abort flags, and owned conversations. Missing-definition diagnostics are separate from the graph. This is useful source material for a task panel whose status comes from committed runtime state. ([commit](https://github.com/earendil-works/pi/commit/49683a36476e3a3fdbb40008745073375df563b7), [task graph](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/task-graph.ts))

### 3. Typed application state and product-defined fork semantics

Transcript entries, document changes, task creation, and checkpoints participate in the same Session transaction. Applications can therefore store plans, task state, or environment references with the entries that explain them. Documents explicitly choose `latest` or `rewindable` history and `initial`, `current`, or `asOf` fork behavior; `asOf` requires rewindable history. This is logical application state, not filesystem rollback. ([transaction implementation](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/session/transaction.ts), [document definitions](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/documents.ts))

Fork tests distinguish the historical entry-owning ancestor from the immediate parent: `asOf` state follows the selected entry's commit, while `current` uses the parent's current committed state. A fork point inside a commit uses the final document state of that commit. Task-scoped state is not copied; session-scoped state remains outside conversation copying. Tests cover rollback of copied bases, invalid fork points, retirement/recreation, and paginated document families. ([fork implementation](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/session/forks.ts#L25-L96), [fork tests](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/session-forks.test.ts))

### 4. One admission queue and committed observation for multiple clients

Busy submissions distinguish steer, follow-up, and write. Steers join after the tool round, follow-ups start after the current run answers, and writes add entries without requesting a model answer. `reject` admits nothing when busy. Failed runs retain queued work until another submission places it. These semantics should be visible to users and adapters, rather than inferred from whichever transport delivered the input. ([admission and settlement](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/submissions.ts), [inbox](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/inbox.ts))

Conversation views and coding-agent-style events are derived from committed state. Late joiners receive a snapshot; subsequent updates are deltas. Slow event consumers receive a replacement snapshot after falling more than 100 batches behind, so the stream is not an exhaustive audit log. Immutable entries or a journal remain necessary when every transition matters. The architecture assumes clients attach to one owning process; it is not offline multi-writer collaboration. ([events](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/events.ts), [view](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/view.ts), [observation](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/session/observation.ts))

### 5. Background compaction with controlled placement

Compaction is its own durable task: range selection, summary generation, and placement are distinct. Automatic background summarization begins before the blocking threshold; generation waits only when necessary. Completed background/manual summaries enter the submission path and land at a boundary. A summary with a cut older than the active context becomes stale. Provider context overflow triggers one compaction recovery path; it is not unlimited retry. Reset/handoff changes the active context while retaining historical entries. ([compaction implementation](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/compaction.ts), [generation implementation](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/generation.ts))

**Do not copy the compaction race unchanged.** An upstream test deliberately documents an edit/redaction written while summarization is in flight: the summary request still contains the old entry, and resulting model context lacks the replacement. The canonical edit is not demonstrated to be deleted; its target has left the active range, while the summary was derived from stale content. Concurrent custom head changes can similarly be semantically undone. Cognia should invalidate or rebase such summaries on relevant edit/redaction/context revisions. ([precise test](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/harness-compaction.test.ts#L1753-L1769), [specification caveat](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/docs/spec.md#L4473-L4479))

### 6. Extensions participate in durable execution

Extensions bundle tools, prompt sections, hooks, wrappers, and task definitions. Per-conversation configuration persists names. Code is installed by the process; an in-flight invocation keeps the code it resolved, while subsequent phases can resolve updated code. Prompt/tool changes are recorded positionally. Hook decisions can use small first-writer-wins task memos to avoid asking again after recovery; memos are not an external transaction or a permanent approval ledger. ([definition APIs](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/define.ts), [registry](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/harness/registry.ts), [reload example](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/examples/31-reload-and-restart.ts))

Selection is not a mandatory security boundary: a conversation that omits a guard extension omits its hooks; the spec explicitly states there is no registry-wide hook. Recovered safe tools also build their environment from the conversation's current `cwd`, which may differ from the original attempt. Mandatory PII/permission gates and execution-identity checks therefore need host enforcement. ([guard caveat](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/docs/spec.md#L4555-L4568), [current-environment recovery test](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/harness-tools-recovery.test.ts#L165-L211))

## Storage, runtime, and deployment limits

| Area        | Verified boundary                                                                                                                                                                                                                             |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime     | Package requires Node `>=22.19.0`. Portable storage cores need platform adapters; this is not evidence of a shipped Cloudflare/Postgres deployment.                                                                                           |
| Memory      | `MemoryStorage` does not survive process loss.                                                                                                                                                                                                |
| SQLite      | Node adapter uses built-in `node:sqlite` and synchronous SQLite operations behind an async interface, WAL, and `synchronous = NORMAL`; process-crash durability is not a guarantee against losing the newest commit after power/host failure. |
| JSONL       | Default `fsync` is false. Even true flushes affected sidecars before appending the main marker; ordinary publication does not explicitly flush that marker. Acknowledged tail commits may disappear on power/host failure.                    |
| Ownership   | One process owns a storage; the package supplies no cross-process ownership lock. SQLite file locks are not a substitute for a harness lease/fencing protocol.                                                                                |
| Scalability | Session mutations serialize. A commit callback awaiting a network request, model, human, or nested commit can stall the shared mutation line. There is no offline CRDT merge contract.                                                        |
| Retention   | JSONL does not globally compact `main.jsonl`; no automatic corruption repair is promised. Long histories and retained terminal receipts still need product retention policy.                                                                  |
| Shutdown    | Non-cooperative hooks/tools can keep close pending. Cancelling the close wait does not force-terminate their code.                                                                                                                            |

Sources: [package runtime](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/package.json), [SQLite adapter](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/storage/sqlite/node.ts#L131-L200), [JSONL publication](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/src/storage/jsonl/storage.ts#L276-L310), [storage README](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/README.md#storage), [non-goals](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/docs/spec.md#L4587-L4601), [shutdown tests](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/harness-lifecycle.test.ts#L127-L254).

The per-conversation sandbox example uses ordinary temporary directories and a faux model, explicitly leaving real container execution to the application. A working-directory parameter alone is not a sandbox. Similarly, subagent examples demonstrate application composition; they do not establish a built-in production multi-agent service. ([sandbox example](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/examples/29-sandbox-per-conversation.ts#L1-L82), [foreground example](https://github.com/earendil-works/pi/blob/7fbbd5f4a1d982bb02d63472dde0774fa639f99b/packages/durable/test/examples/22-subagent-foreground.ts))

## Recommended use of this research

Study the contracts independently of adopting the experimental package: durable admission before dispatch, effect-intent/checkpoint/result boundaries, explicit cancellation ownership, state-aware forks, commit-derived UI, and asynchronously prepared summaries with revision-safe placement. Evaluate Cognia's existing implementations first. Any adoption experiment should separately prove storage-failure admission rejection, restart at each effect boundary, identity-safe replay, foreground/background cancellation, reconnect catch-up, and summary invalidation after edits or redaction. These are proposed acceptance checks, not completed validation.
