# 常驻群聊参与者：外部实现与研究证据

调研日期：2026-10-20（Asia/Shanghai）。本文件补充普通群聊 Bot 调研，专门回答“像一个常驻群友那样旁听、判断、插话、等待和记住”的机制。普通通道接入与本仓审计保留在[普通 Bot 参考](./2026-10-20-astrbot-group-chat-reference.md)和[可行性研究](./2026-10-20-cognia-group-chat-bot-feasibility.md)，因此新增独立证据文件，避免覆盖其原始范围。

**结论：可以参考 MaiBot 的会话控制机制，结合 AstrBot 的通道与配置分层；不能把“放开非 @ 消息 + 配一个人格 Prompt”视作完整常驻群友能力。** 模型生成一句像人的话，和系统在群聊中持续、克制、及时地参与，是两个验收对象。

本次只浏览一手资料并读取固定源码快照。没有部署上游项目、连接真实群、调用模型、测量自然度/延迟/成本，也没有修改 Cognia 业务代码。文中的“源码已确认”“推论”“建议”分别表示静态证据、由证据推导的判断、尚未实现的设计。

## 2. “被叫到才回应”和“持续参与”具有不同控制面

| 维度       | 普通 @ 助手              | 常驻群聊参与者的验收要求（建议）                                   |
| ---------- | ------------------------ | ------------------------------------------------------------------ |
| 感知       | 主要处理被明确叫到的消息 | 允许范围内持续记录旁听上下文，识别发言者、引用链、话题和消息批次   |
| 何时思考   | @、引用、命令或关键词    | 先用低成本规则过滤，再判断相关性、信息增量、群氛围和当前发言份额   |
| 何时开口   | 触发后生成答案           | 发言、继续旁听、短暂等待、结束本轮均是一等结果                     |
| 新消息到达 | 排队处理下一回合         | 能合并碎片、修正当前意图、取消过时草稿，避免抢话和重复答复         |
| 连续性     | 当前会话历史             | 群内近期上下文、可溯源的长期共同经历、人设稳定性；不能混入私人资料 |
| 成功标准   | 问题是否答对             | 除答对外，还要衡量该不该说、何时说、是否打扰和沉默是否恰当         |

这张表是产品和工程分类，不是断言所有普通助手均没有旁听，也不是断言上游项目已经满足全部右列要求。

## 3. MaiBot 值得参考的是控制机制，不是“生命体”表述

### 3.1 先收消息，再决定是否进入规划

**源码已确认：** `register_message` 先记录接收时间、更新触发状态和防抖，再加入 `message_cache`；之后才经过 focus 准入，申请 Planner 中断并调度会话。focus 没有槽位时可以仅缓存、不进入决策。接收、存储与发言不是同一个动作。[runtime.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/runtime.py#L996-L1090)

**源码已确认：** 动态门控输入包括是否提及 Bot、是否 @ 他人、问号、占位内容、最近 Bot 发言占比、最近消息量、距 Bot 上次发言时间及待处理消息数；它使用本地概率估计和频率控制来决定是否进入 Planner。另有按新消息数工作的 frequency 模式。它们是可配置门控，并非对每条群消息强制调用一个昂贵 LLM。[gates.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/turn_trigger/gates.py#L20-L170)、[模式配置](https://docs.mai-mai.org/en/manual/configuration/bot-config)

**推论：** 类似特征可作为 Cognia 进入思考的启发式信号，但不能当“这次发言有价值”的事实证明。问号可能属于两名真人之间的对话；Bot 发言比例低，也不意味着必须补齐份额。

### 3.2 消息聚合具有上限，明确呼叫可以走快路

**源码已确认：** 固定防抖有 `fast / natural / steady`；natural 档在安静开批等 2 秒、活跃开批等 5 秒，同人续发等 2 秒、换人等 0.5 秒，整批上限 8 秒；@/名字提及等待上限 1 秒。裸图开批至少等 4 秒；纯表情包不继续延长已有批次。已到期但模型忙碌的批次不能被新消息无限续长。这里是调度等待值，**不是端到端响应延迟保证**。[controller.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/chat/debounce/controller.py#L17-L105)

**建议：** Cognia 需要“安静窗口 + 最大批次年龄 + 显式呼叫优先级”，并把媒体预处理时间算入批次年龄。这能处理“我想问 / 这张截图 / 是什么问题”这样的三段输入。上游秒数仅是实验起点，不能直接当作飞书或 Telegram 的产品默认值。

### 3.3 wait、stop 与 reply 需要有不同语义

**源码已确认：** `wait(seconds)` 暂停当前循环，达到连续次数上限后进入休息。该快照是否允许新消息提前结束 wait，取决于 `experimental.planner_message_steering`：开时可提前结束，关时固定等待。不能只看工具描述就宣称所有配置都支持即时唤醒。[wait.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/builtin_tool/wait.py#L12-L79)

`stop` 结束本轮思考，不发消息、不设定时等待，等待新消息；与“再等一会儿也许对方没说完”的 wait 不同。[stop.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/builtin_tool/stop.py#L12-L38)

**源码已确认：** reply 工具需要目标 `msg_id` 和 `reply_reference`，后者提供方向、上下文和事实，随后由 Replyer 生成可见回复；支持短/正常/长回复风格。回复生成前会检查最近是否已经回复相同目标并加入提醒。这是降低重复的上下文手段，不等于出站幂等。[reply.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/builtin_tool/reply.py#L123-L153)

**建议：** 产品状态至少区分 `listen / collect / decide / wait / compose / validate / send / rest`。listen 不是不断调用模型的无限空转循环，wait 不是用睡眠把同群队列锁死，stop 也不是退出群聊。

### 3.4 新消息可以中断 Planner，但发出前仍需独立防过时门

**源码已确认：** 新消息可设置 Planner 中断信号，存在连续中断上限/实验开关；`_handle_planner_interrupt` 处理流式请求中止并重新摄入待处理消息。[runtime 中断](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/runtime.py#L1048-L1090)、[reasoning_engine.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/reasoning_engine.py#L572-L644)

**未证实：** 该机制是否能在任意 Replyer 生成、工具执行或多段发送阶段无遗漏地取消旧回复。本次检查的 reply 路径是在历史快照上生成、后处理、发送；未找到足以证明“每次发送前必比较当前话题版本”的契约。因此不能把 Planner 可中断等同于所有过时回复均被阻止。

**建议：** Cognia 在草稿上保存 `conversationRevision / targetMessageId / topicEpoch / expiry`；每个可见消息发送前复查模式、权限、目标存在、更新消息、预算与有效期。发生更正、撤回、停止、话题切换时优先丢弃或重新规划。无关新消息不必一律丢弃，以免活跃群永远发不出回复。已发生的外部工具副作用不能靠取消文本生成回滚。

### 3.5 不发言也有计算成本，应退避并封顶

**源码已确认：** 连续空闲轮次使用指数退避，支持基础等待、上限、起始次数及积压消息数绕过；私聊不采用该群聊退避，focus 模式也有区别。它是减少重复无行动判断的机制，不保证群聊质量。[idle_backoff.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/turn_trigger/idle_backoff.py#L24-L94)

**推论：** 自主性不是“持续产生内部独白”。应先控制检查频次、单群预算、最大等待/重规划次数，再研究更复杂的社会决策模型；否则群越热闹，取消和重算越贵。

## 4. AstrBot 提供旁听和概率接话，但定时主动任务是另一条机制

**源码已确认：** `GroupChatContext` 按 UMO 在内存中缓存群消息和记录 ID，附昵称、时间、引用及 @ 信息；请求模型时注入当前消息之前的记录，并保留之后并发到达的记录。`group_icl_enable` 为独立开关，不能仅因打开 active reply 就假设全部旁听内容也已注入。[group_chat_context.py](https://github.com/AstrBotDevs/AstrBot/blob/f2404c191716a64daaa422be7f3c567cace50d39/astrbot/builtin_stars/astrbot/group_chat_context.py#L43-L198)、[main.py](https://github.com/AstrBotDevs/AstrBot/blob/f2404c191716a64daaa422be7f3c567cace50d39/astrbot/builtin_stars/astrbot/main.py#L188-L260)

该快照主动接话的已实现匹配分支是 `possibility_reply`：群消息、未显式唤醒、通过可选白名单后，比较随机数与概率。默认 `active_reply.enable=false`、概率 `0.1`；群上下文和独立持久历史开关也默认关闭。不能描述为默认具备基于社会语义的自主决策。[默认配置](https://github.com/AstrBotDevs/AstrBot/blob/f2404c191716a64daaa422be7f3c567cace50d39/astrbot/core/config/default.py#L235-L248)

**源码已确认：** @ 自身、引用 Bot 消息和唤醒前缀走显式唤醒路径；@ 他人的前缀消息有专门限制。它们与随机接话入口可区分。[waking_check/stage.py](https://github.com/AstrBotDevs/AstrBot/blob/f2404c191716a64daaa422be7f3c567cace50d39/astrbot/core/pipeline/waking_check/stage.py#L91-L145)

**文档已确认：** AstrBot 的“主动型能力”是创建未来任务后按时唤醒，可调用工具并发回会话；官方明确它不是持续自主监控，需要进程在线、工具和投递平台分别可用。[主动型能力](https://docs.astrbot.app/use/proactive-agent.html)

**推论：** 概率接话适合做受控基线；它不能区分“没有人回复因为已经聊完”和“没有人回复因为 Bot 插话不合适”。定时提醒、沉默后破冰、消息驱动自主插话应分别建模，避免一个名叫 proactive 的开关混合三种行为。

## 5. 记忆和人设要支持连续性，同时保留事实来源

**源码已确认：** MaiBot 将裁切的历史生成结构化聊天摘要，含 summary 和 recall cues，并有中期回想召回。它明确把内部摘要建成参考消息，不能当作平台原始发言。[mid_term.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/memory/mid_term.py#L49-L140)

长期记忆工具有语义、时间、经历、综合与混合检索模式，并能按人物过滤。其存在只能证明提供了检索接口，不能证明记忆准确、不跨群泄漏或删除已完整传播。[query_memory.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/builtin_tool/query_memory.py#L19-L81)

**建议：** Cognia 分开保存短期群上下文、话题摘要、群内长期共同经历、人格设置。长期条目必须带原始消息引用、创建时间、适用群/主体、置信度、过期/撤回状态；个人偏好不自动跨群共享，私聊、桌面记忆和工作文档不得因“更像真人”自动注入群聊。旧记忆与新更正冲突时，新更正可压制并修订旧条目。

**建议：** 人设定义语气、兴趣、表达习惯和行为边界；不把运营者或某个真实成员的身份、私有经历冒用为 Bot 自己的经历。Bot 可以口语化、幽默和承认不知道，仍应保留可识别的 Bot 身份。MaiBot 的项目定位是作者设计意图，并不证明程序具备意识或人类情感；Cognia 不需要复制这类命名才能实现有连续性的参与。

## 6. 工具权限与运行条件不能由人设越权

**源码已确认：** MaiBot 内置工具表除 reply/wait/stop，还包含记忆、历史、工具搜索、subagent 等；部分工具可配置禁用或延迟发现。工具丰富不是自治权限模型的证据。[内置工具注册](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/builtin_tool/__init__.py#L76-L130)

**建议：** 旁听/社交决策仅允许无副作用分析；自主插话默认仅文本/表情和群授权的只读检索。执行任务、写文件、登录账号、发送到其他会话等行为进入既有明确授权流程。群里一句“帮我删掉”不能继承桌面 owner 的工具权限；引用内容、图片 OCR 和历史记忆也不能改变系统权限。所有出站模型、摘要和 embedding 路径都必须经过 Cognia 既有 PII 边界。

**文档/配置已确认：** MaiBot 可运行独立 Python 进程或 Docker，官方 Compose 包含 core、NapCat 等配套；仅运行 core 不等于平台已经连接。[MaiBot 部署](https://docs.mai-mai.org/manual/deployment/docker)。AstrBot Compose 持久化 `data` 并设置自动重启，WebUI 与 OneBot 接入有独立端口。[AstrBot compose](https://github.com/AstrBotDevs/AstrBot/blob/f2404c191716a64daaa422be7f3c567cace50d39/compose.yml#L1-L24)

**建议：** Cognia 的静态导出 Web UI 负责配置和观测，常驻 runtime 才拥有平台连接、群状态、预算、计时器和 outbox。桌面睡眠、退出、网络重连、崩溃恢复和多实例接管要单独验收；“常驻”不等于保证 24 小时在线。重启后可以恢复摘要与游标，默认不补发已过时的自主插话。

## 7. 论文支持“贡献与时机联合判断”，不能证明长期群聊效果

作者的 Inner Thoughts 框架区分触发、检索、候选想法生成、评估和参与；研究强调相关性、信息缺口、原创性、对话平衡等信号。论文包含 24 人形成性研究及模拟会话/Slack Bot 评价，报告优于 next-speaker+persona 基线；同时承认想法可能无关、矛盾或重复。它支持将“有没有值得说的内容”和“现在能不能说”联合判断，**不证明对真实中文熟人群、长期关系、Cognia 选定模型或大规模部署同样有效**。[作者论文 §§4–8](https://arxiv.org/html/2501.00383v2)

**建议：** 内部候选应保存简洁的结构化参与意图，例如 `intent=clarify / target=msg_42 / novelty=missing_fact / expiresAt=...`，不要求公开或持久保存模型的详细推理。可解释日志记录决策特征、结果和版本即可。先用离线标注对比规则、随机和模型门控，再决定是否需要多阶段持续思考。

## 8. 成本和指标必须覆盖“没说话的工作”

**文档已确认：** MaiBot 把 Planner、Replyer 和辅助任务分配到不同模型；文档将一次接收至回复流程描述为典型 3–6 次 LLM 调用。这是上游描述，不是本次实测，也不代表 Cognia 的模型、价格或耗时。[模型配置](https://docs.mai-mai.org/en/manual/configuration/model-config)

**源码已确认：** MaiBot 的 reply-effect 数据模型保留目标消息、发出消息 ID、后续关联、反馈类别、贡献类别和证据置信度；评分区分响应、接纳和对话贡献。它说明可以做有归因的观测，但自动评分本身仍会误判。[models.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/reply_effect/models.py#L18-L140)、[scoring.py](https://github.com/Mai-with-u/MaiBot/blob/ff0fe42500f5f7581e9655d1e78379407233207a/src/maisaka/reply_effect/scoring.py#L8-L129)

**建议的成本模型：**

```text
单群日成本 = 门控调用 + 发言生成 + 取消后已计费 token
           + 摘要/记忆提取/embedding + 媒体理解 + 工具与基础设施
模型费用 = Σ(输入 token × 该模型输入单价 + 输出 token × 输出单价)
```

规则门控可不调用模型，但不能把本地 CPU、存储和连接成本记为零。应分别计量每百条入站消息的模型调用/费用、每次实际发言费用、每次“判断后沉默”费用、被取消草稿浪费和后台记忆费用。价格必须按实际供应商与缓存计费核算；本次没有提供人民币承诺值。

| 指标（建议）                                   | 为什么需要                                        | 不该据此推出什么                   |
| ---------------------------------------------- | ------------------------------------------------- | ---------------------------------- |
| 显式呼叫完成率、首个有效回复 P50/P95           | 保持 @/引用可依赖，区分排队、批次、模型、发送延迟 | 自主插话率高不等于更好             |
| 自主插话适当率、错误对象率、重复/过时发送率    | 判断内容与时机是否适合                            | 模型自评高不等于真人认可           |
| 人工标注的“该沉默却发言”和“该回应却沉默”       | 同时评价 precision 与 recall                      | 静默零投诉不等于没有错过重要呼叫   |
| 每群主动消息数、Bot 消息份额、无人回应连续次数 | 发现抢话、刷屏与自说自话                          | 冷清群必须被 Bot 填满              |
| 成员后续引用/接话、纠正/拒绝、管理员降频/静音  | 衡量群体实际接纳，保留证据与置信度                | 后续讨论增加不必然由 Bot 造成      |
| 预算触顶、门控命中、超时、中断、过期草稿丢弃   | 确认保护机制运行且成本可控                        | 取消很多不一定是好事，可能门控过早 |

## 9. 对方案的反证与最小验证设计

以下为建议验收，不是已经通过的结果。

| 需要反驳的假设             | 最小验证场景                                                                     | 失败后如何缩小方案                 |
| -------------------------- | -------------------------------------------------------------------------------- | ---------------------------------- |
| 全量消息入模型就会更自然   | 同一段真实授权脱敏记录，对比 @、旁听+规则、旁听+模型门控；盲评相关性、时机、打扰 | 保留旁听，关闭自主插话             |
| 随机 10% 足以像群友        | 真人两人互聊、@ 他人、重复问句、争论、告别、安静群等分层记录                     | 用随机做基线，不作正式社会决策     |
| 规划中断解决所有过时回复   | 生成时新消息更正事实、撤回目标、切换话题；发送前管理员静音；工具返回迟到         | 增加出站版本/权限/时效检查         |
| 连续思考一定增益           | 分别测安静群和每分钟高频群的自然度、调用量、取消浪费                             | 事件驱动、合批、退避、预算封顶     |
| 长期记忆越多越像熟人       | 同名不同人、昵称变更、两群相反偏好、删除原消息、后续纠正                         | 缩到群内有来源的共同经历           |
| 高回复率代表受欢迎         | 对比主动占比与人工不合适标签、成员静音/要求停止、无人接话                        | 降频；连续无人响应后休息           |
| 一个人格适合所有群         | 工作群、熟人闲聊、陌生人大群分别评价相同策略                                     | 独立群配置和保守默认值             |
| 常驻可以自动执行群成员任务 | 混入引用指令、工具输出提示注入和未授权成员请求                                   | 限定社交只读能力，任务进入既有授权 |

推荐先回放与 shadow 决策（只记录建议动作），再在明确授权的小群验证。进入真实试点前必须已有管理员静音、预算上限、出站幂等、防过时门和跨群/私人记忆隔离；试点不能先靠“它应该懂分寸”的 Prompt 兜底。是否自然、可接受的发言频率、模型调用成本、全天在线与平台实际可见性，均保留为需要真实环境验证的结果。
