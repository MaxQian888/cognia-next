# Lima backend contract evidence

Date: 2026-10-20 (Asia/Shanghai).

Scope: primary-source research for an extensible Cognia execution-backend proposal. No production changes, installation, VM launch, configuration mutation, benchmark, or runtime acceptance test was performed. This new note records release-specific evidence that the earlier feasibility note did not establish.

Evidence labels: **Confirmed** means documented or implemented upstream, not tested in Cognia; **Inferred** means a design consequence; **Open** means a qualification gate remains.

## Lifecycle, execution, and file-transfer contracts

**Confirmed:** `limactl list --format json` / `--json` emits one object per instance, i.e. JSON Lines when captured without a TTY, not a JSON array. Named unmatched instances return failure; an empty inventory can succeed without records. Status values include `Uninitialized`, `Installing`, `Broken`, `Stopped`, `Running`, and empty/unknown. Instance metadata includes driver, architecture, resources, SSH endpoint, and Lima version. **Inferred:** parse a bounded stream, tolerate unknown fields/states, and distinguish missing, broken, stopped, and application-ready. [List implementation](https://github.com/lima-vm/lima/blob/v2.2.1/cmd/limactl/list.go), [Instance model](https://github.com/lima-vm/lima/blob/v2.2.1/pkg/limatype/lima_instance.go)

**Confirmed:** the CLI has create/start/stop/delete operations and global `--tty=false` for automation. Graceful stop signals the hostagent and waits for shutdown; force stop kills driver/hostagent processes. **Inferred:** use explicit desired-state reconciliation and post-operation inspection; process exit alone does not resolve an interrupted create/start/delete. [Command registry](https://github.com/lima-vm/lima/blob/v2.2.1/cmd/limactl/main.go), [Start/create](https://github.com/lima-vm/lima/blob/v2.2.1/cmd/limactl/start.go), [Stop](https://github.com/lima-vm/lima/blob/v2.2.1/pkg/instance/stop.go), [Delete](https://github.com/lima-vm/lima/blob/v2.2.1/cmd/limactl/delete.go)

**Confirmed:** `shell` quotes arguments into a guest login-shell command, launches host SSH, and attaches stdin/stdout/stderr. It is not a direct guest `execve` RPC. `--workdir` is explicit; `--preserve-env` defaults false. The source provides no proof that cancelling the local SSH process kills all guest descendants. With `--sync`, configured mounts are rejected, `--workdir` conflicts, and noninteractive `!tty` immediately calls `rsyncBack()` without review. Copy-back follows successful SSH completion. **Inferred:** use a fixed guest helper with framed requests, explicit argv/env/cwd, bounded streams, job identity, and cancellation receipts. Never equate disconnect with job cancellation. [Release shell source](https://github.com/lima-vm/lima/blob/v2.2.1/cmd/limactl/shell.go)

**Confirmed:** `--mount-none` removes configured mounts; `--mount-only` replaces rather than appends. Default templates expose host home read-only. The documented sync workflow requires rsync on both ends and a sufficiently deep host directory. **Inferred:** distinguish guest-private storage, staged transfer, and live read/write mounts. A live writable mount has immediate host effects. Product review needs Cognia-owned staging, a base revision/digest, diff inspection, explicit apply, and conflict detection. [Mount flags](https://github.com/lima-vm/lima/blob/v2.2.1/cmd/limactl/editflags/editflags.go), [AI examples](https://github.com/lima-vm/lima/blob/v2.2.1/website/content/en/docs/examples/ai.md)

**Confirmed:** QEMU uses `qemu-img snapshot` while stopped and HMP `savevm`/`loadvm` while running. Snapshot listing is textual. **Inferred:** disk-only and memory-bearing checkpoints are distinct capabilities; neither captures external live host mounts. Snapshot existence is not a portable suspend/resume contract. [QEMU implementation](https://github.com/lima-vm/lima/blob/v2.2.1/pkg/driver/qemu/qemu.go), [Snapshot CLI](https://github.com/lima-vm/lima/blob/v2.2.1/cmd/limactl/snapshot.go)

## Security boundary and the network qualification blocker

**Confirmed:** released network documentation says default slirp makes host loopback reachable at `192.168.5.2` / `host.lima.internal`. `--network` adds networks. QEMU source creates its default user network when no user-v2 network is selected; `networks: []` therefore does not mean offline. user-v2 additionally enables VM-to-VM connectivity. Guest-to-host port forwarding is a different direction from outbound network access. [Default network](https://github.com/lima-vm/lima/blob/v2.2.1/website/content/en/docs/config/network/user.md), [user-v2](https://github.com/lima-vm/lima/blob/v2.2.1/website/content/en/docs/config/network/user-v2.md), [Network flags](https://github.com/lima-vm/lima/blob/v2.2.1/cmd/limactl/editflags/editflags.go), [QEMU network construction](https://github.com/lima-vm/lima/blob/v2.2.1/pkg/driver/qemu/qemu.go)

**Open:** no released Lima profile was qualified here that simultaneously enforces offline or an allowlist outside an attacker-controlled guest, excludes host/LAN destinations, covers IPv4/IPv6 and alternate protocols, and retains a safe control path. This is not a claim that such a design is impossible. QEMU documents engine-level `restrict=on`, but that does not establish a supported Lima setting or a VZ equivalent. [QEMU networking options](https://www.qemu.org/docs/master/system/invocation.html#network-options)

**Inferred, release gate:** first Lima support must report outbound networking as open/unqualified and reject tasks requiring enforced offline or allowlisted networking. `HTTP_PROXY`, DNS selection, guest firewall rules, and disabling passwordless sudo do not independently prove that a guest-root attacker cannot bypass policy. Qualifying a non-root task plus an OS sandbox is a different threat model and must be named separately.

**Confirmed:** the release template enables proxy-environment propagation by default. Global default/override files under `LIMA_HOME` affect each start and can modify mounts. Templates can include privileged guest provisioning and host-facing mounts. The project's self-assessment explicitly excludes tolerance of malicious templates; its current maintainer threat model treats guest root as adversarial and templates/control configuration as trusted. The latter file is newer `master` context, not a v2.2.1 release guarantee. [Release template](https://github.com/lima-vm/lima/blob/v2.2.1/templates/default.yaml), [Self-assessment linked by released docs](https://github.com/cncf/tag-security/blob/main/community/assessments/projects/lima/self-assessment.md), [Current threat model](https://github.com/lima-vm/lima/blob/master/.oss-scanner/threat_model.md)

**Inferred:** keep a Cognia-owned `LIMA_HOME`, controlled templates, immutable identity/config digests, and a sanitized host environment. Revalidate effective configuration before reuse. Never put VM-control sockets, host credentials, Docker socket, SSH agent, or arbitrary host mounts into a guest by convenience. Guest root must not obtain credentials that authorize controlling other instances or the host. A read-only mount still discloses its contents.

**Inferred:** cancellation needs two guarantees: a best-effort guest-job termination, and a host-enforced VM stop escalation for a dedicated isolation domain. A guest-root attacker can falsify in-guest acknowledgements; stop confirmation must come from the host/hypervisor. Do not stop a shared VM to cancel one tenant. Destruction must be scoped to an owned instance plus generation, with audit and crash recovery.

## Provider-independent capability design consequences

These are proposed boundaries, not an upstream API or implemented Cognia behavior:

1. Separate environment lifecycle from execution sessions. Describe provider identity/version, host OS/architecture, guest OS, isolation unit, and owner/generation.
2. Negotiate individual guarantees: structured execution, stream framing, TTY, job versus environment cancellation, staged versus live files, preview ports, GUI, disk checkpoint, memory checkpoint, and network enforcement point/threat model.
3. Keep desired policy separate from observed capabilities. A request for offline networking must fail when the selected instance only proves VM filesystem separation; no weakening to open egress or host execution.
4. Bind a tool call to an environment identity before execution. MCP is a transport/tool catalog, not evidence that other tools use the same environment.
5. Publish facts with qualification provenance: supported upstream, verified on this driver/image/host, or unavailable. Requalify when release, image, driver, or security profile changes.

## Required runtime qualification before support claims

- Capture version and JSONL fixtures from the actual packaged executable; test missing/broken/partially created instances and host restart recovery.
- Verify exact argument, stdin, stdout/stderr, exit status, streaming limits, timeout, disconnected controller, and guest-daemon restart behavior.
- Test adversarial descendants/detached processes and cancellation escalation; record whether job, session, or whole-environment termination is guaranteed.
- Prove file separation and safe export against symlinks, path traversal, conflicts, archive expansion, and concurrent host edits.
- If networking is constrained, test guest-root bypass attempts, host loopback, LAN/link-local, DNS rebinding, IPv6, UDP, existing connections, and configuration changes outside the guest.
- Qualify snapshots separately for driver, image, running/stopped state, and external resources; do not advertise VZ snapshots or generic Lima suspend.

All these checks remain **Open**. This evidence supports a research-first adapter design, not a claim that Lima integration is delivered or that a VM automatically confines every Cognia tool.
