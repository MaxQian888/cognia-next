# Grok Bot updates compared with current Cognia

Assessment date: 2026-10-24 (Asia/Shanghai).

## Conclusion

Cognia already has much of the execution infrastructure behind the recent Grok Bot capabilities. The best opportunities are to connect those implementations into understandable, reliable user flows. The clearest additional capability gaps are shared Bots for human teams, cross-tool authorization grounded in the user's request, a Bot-owned email inbox, remote credential autofill, and larger attachment transport.

Prioritize authorization and cancellation correctness before making unattended work more autonomous. Next, unify the Bot experience and support continuously maintained, collaboratively edited deliverables. Treat hosted cloud provisioning as a product and operating-model decision: Cognia deliberately supports user-provided always-on Hosts.

This is a research assessment, not an implementation proposal or a claim of production parity.

## Evidence scope

- Inspected the current shared working tree on branch `dev`, with HEAD `08b7ab034`. It contains substantial concurrent, uncommitted changes, including sandbox/Lume work. Findings describe files read during this assessment, not a clean release snapshot.
- Followed owning types, runtime registrations, UI mounts and call sites. Three read-only research agents independently inspected Bots/scheduling, artifacts/connectors, and security/automation.
- Attempted CodeGraph navigation; the checkout has no `.codegraph` index. Used `rg` and direct source reads without creating an index.
- Rechecked the official Grok Bot changelog, overview and Team Bots announcement. Release-log dates can cover bundled releases; they are not necessarily every capability's first rollout date.
- No production code was changed. No tests, build, browser/native UI, external provider, real VM, hosted deployment, or multi-user acceptance was run for this comparison. Existing test files establish intended contracts only; their presence is not a fresh passing result.
- “Not found” below is bounded by the inspected contracts and paths. An external MCP/plugin can supply capabilities beyond the built-in implementation.

## The most important correctness gap: authorization semantics

Cognia already has permission rules, approval requests, durable receipts, subagent approval routing, AbortSignal/TTL waiters and unattended execution policy. It should extend those contracts rather than add another approval platform.

The current model-assisted Auto-mode path is narrower than request-grounded authorization:

- `runAutoModeForTool` extracts a shell command and returns `null` for other tools. [Applicability gate](../../lib/claude/permissions/auto-mode-runner.ts#L53).
- The command judge receives the command, working directory and locale. `contextKey` scopes cache invalidation; `promptContext` resolves customized judge guidance. Neither is the user's current request text. [Judge input](../../lib/claude/permissions/command-judge.ts#L189), [custom guidance](../../lib/claude/permissions/command-judge.ts#L43).
- ActionReview already records the authority behind a resolution. That is an audit/projection foundation, not by itself evidence that every tool is checked against the user's authorized recipient, purpose and stopping point. [Authority contract](../../lib/policy/action-review/chat-tool-channel.ts#L14).
- A denied approval ends the current waiter. In the inspected general gates, there is no action fingerprint tied to a user-instruction epoch that prevents the same denied action from being reissued through a different call or child. A “do not retry” model instruction is weaker than such a state constraint. [Waiter](../../sidecar/src/policy/permission/approval.ts#L60), [permission gate](../../sidecar/src/policy/permission/ai-sdk-gate.ts#L247).

Recommended extension: represent the human request, allowed action/recipient/resource scope, draft-only boundary, approving authority and denial lifetime in the existing review/receipt system. Use model judgment as one input; keep deterministic ceilings and revocation authoritative. Do not infer authorization merely because a command appears safe.

## A specific cancellation edge needs a behavioral check

The external-delegation path executes with its own watchdog `AbortSignal.timeout`. `cancelDelegation` cancels background, twin and team targets but has no external-target cancellation branch. [External execution](../../lib/ai/agent/team/delegation-orchestrator.ts#L133), [cancel branches](../../lib/ai/agent/team/delegation-orchestrator.ts#L838).

This is a confirmed source-level disconnect in the inspected path. It is not an observed production incident, and it does not imply every Stop path is broken. A focused reproduction should determine whether cancelling a running external delegation actually stops its process and whether a late completion can trigger follow-up work. Existing Squad Stop and approval expiry should be preserved. [Squad control](../../lib/ai/agent/team/squad/squad-control.ts#L271).

## What should not be copied mechanically

- **A fixed routine count or hourly quota.** Cognia already has concurrency, time and cost ceilings. Gateway execution can enforce a hard token allowance; native CLI execution has a soft boundary between calls. Capacity should follow Host/provider limits, queue delay and spend, not a competitor's headline number. [Policy ceilings](../../lib/bot/policy/ceilings.ts#L134), [cost enforcement distinction](../../lib/bot/runtime/run-cost.ts#L9).
- **A fixed enabled-Skill count.** Cognia already has explicit token budgeting and named degradation for Skill catalogs/bodies. Preserve discoverability and protect the relevant Skills instead of maximizing an integer. The separate eight-container-Skill limit belongs to a specific provider bridge, not all Cognia Skills. [Prompt budget](../../lib/skills/prompt-budget.ts#L1), [provider bridge](../../lib/claude/skills-bridge.ts#L136).
- **Another memory store, workflow scheduler, app iframe container or video subsystem.** Existing modules already own these concerns; most work is integration, capability parity and user-facing state.
- **An account-wide shared computer as a default security model.** Grok documents that a user's Bots share files and sessions. Cognia's existing task/workspace/sandbox boundaries should be evaluated on their own merits; convenient handoff does not require widening every Bot's access.
- **Payments or bundled subscription economics as immediate engineering work.** These need product demand, commercial decisions and operational scope beyond the capability audit.
