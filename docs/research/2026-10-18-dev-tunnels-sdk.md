# Microsoft Dev Tunnels SDK and existing VS Code tunnel reuse

Initial source audit retrieved: 2026-10-18. It performed no package installation, authentication, token access, live tunnel access, or product implementation. The later user-authorized isolated live validation is recorded below.

## Live validation follow-up — 2026-10-18

After the source research, the user authorized an isolated TypeScript SDK experiment. It succeeded with SDK `1.3.61` against a remote VS Code CLI `1.142.0`, protocol `6`: discover the existing named tunnel, obtain a connect-scoped token, establish the relay/control stream, run `fs_stat` and `fs_readdir` against the user-specified test workspace, and execute a harmless `spawn` request. The directory contained four entries; the command returned its expected marker and working directory, exit code `0`, and empty stderr. All output streams reached EOF, the SDK was disposed, and the local probe exited with code `0`.

Authentication reused the user's already-authenticated GitHub CLI session through a user-token callback, without reading VS Code credential stores. No local port listeners were opened. Dependencies and probe artifacts were kept outside the repository; Cognia implementation/dependencies were unchanged. Credentials stayed in memory and were excluded from the saved results. The experiment requested no remote file writes or service changes. Target/account identifiers and the workspace path are intentionally omitted from this repository note.

This verifies native transport plus filesystem/process RPC for that tested CLI version. It does not verify a dedicated Cognia OAuth application, interactive PTY support, file writes, or reconnection. The sections below retain the original source-research context and its then-open questions.

## Conclusion

The SDK is a credible transport foundation for Cognia. More significantly, the current VS Code CLI source already exposes filesystem and process RPC through a `code tunnel`, so a native integration might use those operations without embedding the entire VS Code frontend. This is an engineering inference, not a verified connection or a stable API guarantee. Cognia would still need its own authentication, discovery, stream/RPC adapter, version handling, reconnect behavior, and workspace integration.

The SDK alone does not turn a machine name into a shell. There are two layers: Microsoft Dev Tunnels transports authorized port streams; VS Code's CLI protocol on top provides files/processes/server connections. The current VS Code CLI actually uses this same SDK to connect to existing named tunnels. [CLI connection flow](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/dev_tunnels.rs#L448-L522)

## Rust SDK: exact package and APIs

The repository package is **`tunnels` version `0.1.0`**, edition 2021. Its optional `connections` feature enables the relay client/host. The registry index currently contains only a non-yanked `0.1.0`, published on 2024-03-17; the relay client was added to Git source on 2026-05-04 while the manifest version remained `0.1.0`. Thus `tunnels = "0.1.0"` must not be treated as equivalent to the current Git API. The current VS Code CLI uses a **Git revision pin**, rather than the registry version. [SDK manifest](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/Cargo.toml), [official registry index](https://github.com/rust-lang/crates.io-index/blob/master/tu/nn/tunnels), [relay-client addition](https://github.com/microsoft/dev-tunnels/commit/64048c1409ff56cb958b879de7ea069ec71edc8b), [CLI dependency](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/Cargo.toml)

| Purpose                 | Actual Rust API                                                                                                                                                                                |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Build management client | `management::new_tunnel_management(user_agent) -> TunnelClientBuilder`; configure `.authorization(...)` or `.authorization_provider(...)`; convert with `.into()` to `TunnelManagementClient`. |
| Discover / retrieve     | `list_all_tunnels(&TunnelRequestOptions)`, `get_tunnel(&TunnelLocator, &TunnelRequestOptions)`. Options include `labels`, `require_all_labels`, `include_ports`, `token_scopes`.               |
| Connect relay           | `connections::RelayTunnelClient::new(mgmt).connect(&endpoint, &connect_token) -> ClientRelayHandle`.                                                                                           |
| Open a remote stream    | `ClientRelayHandle::connect_to_port(port: u16) -> PortConnection`.                                                                                                                             |
| Forward to local TCP    | `ClientRelayHandle::forward_port_locally(port) -> SocketAddr`.                                                                                                                                 |
| Stream IO / close       | `PortConnection::{send, recv, close, into_rw}`; `into_rw()` yields `AsyncRead + AsyncWrite`. `ClientRelayHandle::{is_closed, close}` controls the relay.                                       |

Sources: [management builder](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/management/http_client.rs#L733-L851), [request options](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/management/tunnel_request_options.rs), [relay client](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/connections/relay_tunnel_client.rs#L60-L258), [stream API](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/connections/relay_tunnel_client.rs#L315-L385).

The client needs endpoint metadata including `client_relay_uri` and host public keys, plus a tunnel access token with `connect` scope. It sends `Authorization: tunnel <token>` on a relay WebSocket, then SSH `direct-tcpip` channels carry port traffic. Its host-key handler checks the key against endpoint keys. This is not normal SSH password/key login to the remote machine. [Relay handshake](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/connections/relay_tunnel_client.rs#L68-L175), [host-key verification](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/connections/relay_tunnel_client.rs#L387-L419)

Management supports `Authorization::{Anonymous, AAD, Github, Tunnel, Bearer}` and an async `AuthorizationProvider::get_authorization`. These are token/provider inputs; a production OAuth login flow is not supplied by simply constructing the client. Per-request authorization is documented for tunnel tokens; user tokens belong in the client provider. [Authorization types](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/management/authorization.rs), [request-token distinction](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/management/tunnel_request_options.rs#L6-L12)

Rust limitations confirmed against source:

- README marks automatic reconnect, SSH reconnect, tunnel-token refresh, and SSH keep-alive unsupported for Rust. The relay client does send **WebSocket pings** every 60 seconds with a 10-second timeout; that is not SSH session resumption or automatic reconnect. An authorization provider can refresh user credentials on a later management request, but the connected relay takes a fixed token and has no refresh/reconnect callback. [Feature matrix](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/README.md#sdk-feature-matrix), [client implementation](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/connections/relay_tunnel_client.rs#L60-L258)
- `forward_port_locally` documentation mentions a fallback when the port is busy, but the actual body binds exactly `127.0.0.1:<port>` and returns an error if binding fails. Do not build a design around the claimed fallback. [Actual bind](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/connections/relay_tunnel_client.rs#L199-L243)
- The SDK declares `russh`/`russh-keys` `0.37.1`; VS Code patches them from `microsoft/vscode-russh`. The parent task reports Cognia uses `russh 0.63.3`. Different Cargo versions can coexist; no build was performed to establish whether Cognia would need those patches or encounter native/dependency conflicts. [SDK dependencies](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/Cargo.toml), [VS Code patches](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/Cargo.toml)

## Existing VS Code tunnel: discovery, authentication, and protocol

The CLI pins `tunnels` to the exact SDK revision above with `default-features = false` and `features = ["connections"]`. Its `DevTunnels::connect_to_tunnel_port` performs this flow:

1. List tunnels filtered by **labels** `vscode-server-launcher` and the friendly machine name, requiring both labels. The friendly name is not assumed to be the service `tunnelId` or DNS name.
2. Convert metadata to `TunnelLocator`, preferring the returned **cluster + tunnel ID**.
3. Retrieve metadata including ports and request `token_scopes: ["connect"]`.
4. Read the connect-scoped token and endpoint; call `RelayTunnelClient::connect`, then `connect_to_port(port)`.

This directly demonstrates that the current SDK can carry an existing `code tunnel` connection when authentication and metadata are available. It does not prove that Cognia's future OAuth application will receive the same discovery/access rights. [Flow and labels](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/dev_tunnels.rs#L448-L522), [name labels](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/dev_tunnels.rs#L763-L770), [locator resolution](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/rs/src/management/tunnel_locator.rs)

The official CLI owns a GitHub OAuth app ID and implements device flow, with default scopes `read:user+read:org`. It supplies management authorization in the form `github client_id=<official_app_id> <user_token>`. Reproducing this shape does not establish permission to borrow Microsoft's app identity, nor does it prove that a PAT or a token from Cognia's existing GitHub login will be accepted. A dedicated Cognia OAuth identity and its tunnel-service acceptance remain open questions. No local credential stores were read. [Provider and scopes](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/auth.rs#L65-L98), [management authorization](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/auth.rs#L497-L509), [device flow](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/auth.rs#L780-L805)

The audited CLI constants are **`CONTROL_PORT = 31545`**, **`AGENT_HOST_PORT = 31546`**, **`PROTOCOL_VERSION = 6`**. The current code uses these constants; this is not evidence of a configurable `VSCODE_CLI_TUNNEL_PORT` setting. `code tunnel` registers direct tunnel endpoints for both ports. Port 31545 carries the CLI's **MessagePack control protocol**, rather than an HTTP website or an SSH shell. Port 31546 serves the separate agent-host path. [Constants and protocol history](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/constants.rs#L14-L35), [endpoint registration](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/control_server.rs#L205-L215), [RPC setup](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/control_server.rs#L388-L425)

The control server already registers:

| Capability       | Actual RPC methods / semantics                                                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Filesystem       | `fs_stat`, `fs_read`, `fs_write`, `fs_readdir`, `fs_mkdirp`, `fs_rename`, `fs_rm`, `fs_connect`. Read/write/socket operations use duplex streams.       |
| Processes        | `spawn` and `spawn_cli`, using three streams for stdin/stdout/stderr; `command`, `args`, `cwd`, `env`; returns exit status. `sys_kill` is also present. |
| Network / server | `net_connect`, `forward`, `unforward`, `serve`, `servermsg`, `callserverhttp`, `get_env`, `gethostname`.                                                |

Sources: [filesystem RPC registrations](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/control_server.rs#L425-L485), [server/process registrations](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/control_server.rs#L493-L551), [process implementation](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/control_server.rs#L1318-L1371), [parameter types](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/protocol.rs#L149-L275).

These process streams are not evidence of a PTY, terminal resizing, or a stable public terminal API. The standard incoming relay path sets `AuthRequired::None` at the control-protocol layer **after** tunnel authentication; other stream paths can require VSDA challenges. This must not be misread as an unauthenticated public endpoint. The server sends its version on an already authenticated control stream. The user's installed remote CLI version and supported RPC set remain unknown until a future authorized handshake. [Relay dispatch](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/control_server.rs#L313-L357), [version delivery](https://github.com/microsoft/vscode/blob/789f2c470d13c4760f2b5cc6a9e1919c05d04f7d/cli/src/tunnels/control_server.rs#L618-L640)

## TypeScript SDK: parent-audited package and source evidence

The parent task queried official npm package metadata and read package tarball declarations in memory without installing anything. `@microsoft/dev-tunnels-connections`, `@microsoft/dev-tunnels-management`, and `@microsoft/dev-tunnels-contracts` were all `1.3.61`; the older `^1.3.6` in samples must not be treated as the latest version. [Connections registry](https://registry.npmjs.org/@microsoft%2fdev-tunnels-connections/latest), [management registry](https://registry.npmjs.org/@microsoft%2fdev-tunnels-management/latest), [contracts registry](https://registry.npmjs.org/@microsoft%2fdev-tunnels-contracts/latest)

The verified flow is `new TunnelManagementHttpClient(userAgent, apiVersion, userTokenCallback, ...)`, obtain metadata with `getTunnel(tunnel, { includePorts: true, tokenScopes: ["connect"] })`, then `new TunnelRelayTunnelClient(managementClient)`, `connect`, `waitForForwardedPort(port)`, and `connectToForwardedPort(port) -> Duplex`. Set `acceptLocalConnectionsForForwardedPorts = false` when only streams are needed: Node otherwise accepts local connections by default, listening on loopback. The user-token callback returns a **complete authorization header value**; `options.accessToken` means a **tunnel access token**, not a GitHub user token. [Management constructor](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/ts/src/management/tunnelManagementHttpClient.ts), [request options](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/ts/src/management/tunnelRequestOptions.ts), [client contract](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/ts/src/connections/tunnelClient.ts), [relay client](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/ts/src/connections/tunnelRelayTunnelClient.ts)

TypeScript has retry/reconnect enabled by default and a configurable SSH keep-alive whose default is zero. Supplying the management client supports automatic tunnel-token refresh by requesting the required token scope again. OAuth credential acquisition/refresh remains the application's responsibility. The actual `refreshingTunnelAccessToken` event uses `{ tunnelAccessScope, cancellation, tunnelAccessToken?: Promise<string | null> }`; generic examples with `args.scopes` or `args.tunnel` do not match this source. [Connection options](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/ts/src/connections/tunnelConnectionOptions.ts), [refresh implementation](https://github.com/microsoft/dev-tunnels/blob/b73b0eb774b86a5b519c300f2f41c9072a66f663/ts/src/connections/tunnelConnectionSession.ts)

## Decision implications and remaining unknowns

For an eventual minimal research spike, TypeScript in the existing Node sidecar offers more reconnect/token lifecycle support; Rust fits Tauri directly but needs a deliberate Git pin and more connection lifecycle code. This is a tradeoff inferred from the source, not a selected implementation.

The next decisive evidence would be: dedicated app authentication accepted by the tunnel service; discovery of the existing friendly name; connect-scoped metadata and host-key validation; a version handshake on 31545; read-only RPC and a disposable command; disconnection/reconnect behavior. PTY support, cancellation, platform semantics, compatibility with older CLI versions, and Cognia's filesystem/agent policy integration remain to be designed and verified. No step in that live experiment was performed.

Source availability and technical feasibility do not settle redistribution terms for Microsoft's packaged VS Code Server or Remote - Tunnels extension. That separate boundary is documented in the [preceding feasibility note](./2026-10-18-vscode-remote-tunnels-feasibility.md#relevant-distribution-boundary).
