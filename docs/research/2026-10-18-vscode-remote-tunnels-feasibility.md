# VS Code Remote Tunnels feasibility for Cognia

Date: 2026-10-18

Scope: primary-source research and a read-only local implementation audit. No tunnel connection, account authentication, service changes, or product implementation were performed. The user's existing VS Code connection is user-reported evidence; it was not independently retested. Host names, account names, profiles, and workspace paths are deliberately replaced with placeholders here.

Later user-authorized SDK validation succeeded for native tunnel discovery, directory listing, and command execution against CLI `1.142.0` / protocol `6`. See the [live validation follow-up](./2026-10-18-dev-tunnels-sdk.md#live-validation-follow-up--2026-10-18); the original research scope above describes the initial audit, not that later experiment.

## Finding

Cognia cannot currently open an existing VS Code Remote Tunnel as a native Cognia remote workspace. The practical next candidate is to open Microsoft's **official web workbench** inside Cognia's general browser surface. That might reuse the existing tunnel, but needs a real login and remote-workspace smoke test. It would remain a VS Code web session displayed by Cognia; it would not automatically give Cognia's editor, terminal tools, or agent access to the remote filesystem.

An external official VS Code launch is already demonstrated by the user. Replacing that client with Cognia's own editor or extension shim is a separate integration project, with protocol, authentication, runtime, and distribution questions still unresolved.

Follow-up SDK audit (2026-10-18): the current VS Code CLI source itself uses the Rust Dev Tunnels SDK to connect to existing named tunnels, and its control protocol already exposes filesystem and process operations. A native Cognia adapter may therefore reuse those operations without embedding the full VS Code frontend. This is source-based feasibility, not a live compatibility result; see the [pinned SDK and control-protocol audit](./2026-10-18-dev-tunnels-sdk.md).

## Official architecture and client entry points

`code tunnel` starts VS Code Server and creates access through Microsoft Dev Tunnels. The supported clients are VS Code desktop with Remote - Tunnels, or the official web workbench at `https://vscode.dev/tunnel/<machine_name>`. The browser route can include a folder, and the web workbench loads the Remote - Tunnels extension. Hosting and connecting require the same GitHub or Microsoft account. Both ends make outbound Azure connections; SSH supplies encryption inside the tunnel. This does **not** make `tunnel+<name>` an ordinary SSH hostname that Cognia can dial using an SSH username/key. [Remote Tunnels documentation](https://code.visualstudio.com/docs/remote/tunnels)

Microsoft's documented browser route is `https://vscode.dev/tunnel/<machine_name>/<folder_name>`. The exact conversion of an absolute Linux path was not established in this research; use the machine-root URL and open the folder in the workbench rather than guessing slash or encoding rules. Microsoft's own testing instructions use the machine-root form. [VS Code sanity testing](https://github.com/microsoft/vscode/wiki/Sanity-Check#server-and-cli-testing-steps)

The server is the remote development backend; the Remote - Tunnels extension connects the workbench to it. Microsoft distinguishes this server from the client and describes the deployment as single-user. Neither a tunnel name nor a URL is itself a file API or terminal API for another application. [VS Code Server documentation](https://code.visualstudio.com/docs/remote/vscode-server)

## Public SDK versus full remote-workspace integration

There **is** a public standalone Microsoft Dev Tunnels SDK. Its repository lists management and client connections for TypeScript and Rust, among other languages. Therefore, saying that no public tunnel client exists would be incorrect. This SDK addresses the underlying tunnel service, rather than providing a complete independent VS Code workbench client. [Dev Tunnels SDK feature matrix](https://github.com/microsoft/dev-tunnels/blob/main/README.md)

The TypeScript `TunnelClient` connects using the owner identity or a tunnel token with `connect` scope. It can obtain a duplex stream for a forwarded port; browsers use streams because they cannot listen on local TCP sockets. The official sample separately obtains tunnel metadata and then calls `TunnelRelayTunnelClient.connect`. These are useful building blocks, but do not establish that a third-party OAuth application can discover and open an already-created VS Code tunnel with the same behavior as Microsoft's client. That requires separate verification. [TunnelClient interface](https://github.com/microsoft/dev-tunnels/blob/main/ts/src/connections/tunnelClient.ts), [official client sample](https://github.com/microsoft/dev-tunnels/blob/main/samples/ts/client/index.ts)

VS Code's open CLI source includes a control server using MessagePack RPC and server-stream bridging. Its protocol carries server launch parameters such as commit, quality, extensions, connection token, and stream identifiers. These sources make investigation possible; they are not evidence of a stable, documented, end-to-end API promised to arbitrary editor clients. Source links here target the mutable `main` branch and must be rechecked before implementation. [CLI control server](https://github.com/microsoft/vscode/blob/main/cli/src/tunnels/control_server.rs), [CLI protocol definitions](https://github.com/microsoft/vscode/blob/main/cli/src/tunnels/protocol.rs)

The `registerRemoteAuthorityResolver` and `ManagedResolvedAuthority` contracts exist in VS Code's **proposed** `resolvers` API. They provide a remote-address or message-stream boundary inside a VS Code workbench. Proposed APIs are explicitly unstable. Adding these names to an extension shim would not create the missing workbench transport, remote extension host, filesystem, terminal, and lifecycle implementations. Monaco alone also does not run ordinary VS Code extensions. [Resolver declarations](https://github.com/microsoft/vscode/blob/main/src/vscode-dts/vscode.proposed.resolvers.d.ts), [proposed API policy](https://code.visualstudio.com/api/advanced-topics/using-proposed-api), [Monaco FAQ](https://github.com/microsoft/monaco-editor/blob/main/README.md#faq)

## Options and evidence level

| Option                                                                      | Assessment                                        | What it provides                                                                                                                  |
| --------------------------------------------------------------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Continue launching official VS Code externally                              | User-reported success; not independently retested | Full official desktop tunnel client; Cognia is only a launch point if later wired.                                                |
| Open `https://vscode.dev/tunnel/<machine_name>` in Cognia's general browser | **Inferred feasible candidate**, not verified     | Official browser workbench using the existing server/tunnel.                                                                      |
| Put that URL in the current Pro IDE webview                                 | Blocked by current local URL validation           | Would require a deliberate surface/security change and runtime verification.                                                      |
| Install Remote - Tunnels into Cognia's current extension shim               | Not currently supported                           | Missing resolver and workbench capabilities prevent equivalence with VS Code.                                                     |
| Connect Cognia's own editor and agent through Dev Tunnels                   | Research project; not implemented                 | Requires an authenticated transport plus remote filesystem/process/workspace integration; SDK availability alone is insufficient. |

The browser candidate must be tested as its own client session. Microsoft's web documentation covers current Chrome, Edge, Firefox, and Safari, notes browser-specific behavior, and describes popup/clipboard permission configuration. It does not establish support for Cognia's embedded webview. OAuth redirects, popup handling, cookie/storage persistence, workers, remote terminal operation, and relay connectivity remain concrete validation items. No claim is made that iframe embedding is supported or prohibited; neither response headers nor an authenticated embedded session were tested. [VS Code for the Web](https://code.visualstudio.com/docs/remote/vscode-web#browser-support)

## Relevant distribution boundary

The proprietary **VS Code Server product** license permits development use “with Microsoft Visual Studio Code” and restricts supplying the product alone or combined with another application for others. The same page distinguishes the server's MIT-licensed source from the distributed product. Therefore, public CLI/SDK source is not blanket permission to redistribute Microsoft's server or extension inside Cognia. Any proposed product distribution must be assessed against the exact artifacts and terms; this research does not decide the legal status of merely displaying the official hosted web client. [VS Code Server license, Installation and Use Rights / Scope of License](https://code.visualstudio.com/license/server)

## Next experiment, if authorized later

Use the existing tunnel without starting a second host: open its machine-root `vscode.dev` URL in Cognia's general browser; authenticate interactively as the tunnel owner; open a disposable remote workspace; verify read, edit/save, terminal execution, reconnect, and authentication persistence. Success would prove the **official browser workbench inside Cognia** path only. Native Cognia editor or agent access would still need a separate design and implementation.
