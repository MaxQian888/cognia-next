# Architecture Decision Records

This catalogue preserves the context, decision, consequences, and verification intent of Cognia's major architectural choices. It is a decision history, not a generated description of the current runtime.

## Source-of-truth rule

For current behavior, verify the implementation, co-located tests, and runtime registration or bootstrap point. An ADR explains why a direction was chosen. If those sources diverge, implementation-facing documentation must describe what is actually shipped and explicitly identify the ADR drift.

Do not create an ADR merely to fill a numeric gap, and do not renumber an existing ADR to repair the sequence. Numbers are stable historical identifiers, not proof that every preceding number exists or is unique.

## Catalogue health snapshot

As of 2026-08-12, the current working tree contains:

- 112 English ADR files and 112 matching Chinese files.
- Complete English/Chinese sidebar parity: every ADR file is listed once in each locale.
- Three historical numeric collisions: `0013`, `0025`, and `0026` each identify two records.
- Five unused numbers: `0029`, `0080`, `0099`, `0103`, and `0105`. No missing decision can be inferred from those gaps alone.
- A remaining review queue of older records whose `Proposed` label may not reflect their current implementation state. They are not promoted without checking code, tests, and registration points.

The detailed evidence and follow-up queue are in the [2026-08-12 ADR gap audit](../audits/adr-gap-audit-2026-08-12).

## Reading statuses

- **Proposed** records a direction that has not yet been confirmed as the accepted repository contract.
- **Accepted** records an adopted decision. It does not, by itself, prove every rollout phase is complete.
- **Implemented** is historical wording used by some records; verify the current code before relying on it.
- **Superseded** or **removed** means the record remains useful as history but is no longer the current authority for the replaced scope.
- Rollout qualifiers such as partial, experimental, dark launch, or default-off describe delivery state separately from the decision state.

## Maintenance checklist

When adding or reviewing an ADR:

1. Search existing ADRs and the implementation before assigning a new number or describing a gap.
2. State decision status separately from rollout status.
3. Link the implementation, tests, and registration points that prove the current contract.
4. Add the same slug to both locale trees and both `meta.json` sidebars.
5. Record supersession or implementation drift explicitly; preserve historical files and slugs.
6. Run the docs build so MDX, links, and both locale routes are verified.
