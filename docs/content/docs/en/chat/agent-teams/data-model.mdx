# Data Model & Store

A Squad is described by one type module, `types/agent/agent-team.ts`, and held at runtime by one Zustand store under `stores/agent/agent-team-store/`. Since **persist v8** the store is no longer where a Squad lives. Dexie owns squads, teammates and tasks, and the `localStorage` blob is down to templates, the default config and a few view preferences.

<Callout title="Two nouns, one subsystem">
  ADR-0140 renamed the product noun to **Squad** (中文「小队」) and deliberately left the code
  noun alone. Every type, store, action and Dexie table below is still spelled `AgentTeam*`,
  including the tables added after the rename, because `teams` was already taken by Character
  Teams, a different feature entirely (`lib/db/agent-team-definitions.ts:12-17`).
</Callout>

<TLDR>
  `types/agent/agent-team.ts` is the authoritative schema: `AgentTeam` (`:1409`),
  `AgentTeamConfig` (`:410`), `AgentTeammate` (`:955`), `AgentTeamTask` (`:1018`). The store
  (`stores/agent/agent-team-store/store.ts:83`) is `persist` **v8**, and its `partialize`
  (`:263`) keeps only `templates`, `defaultConfig`, `tasksView`, `editorSession`,
  `lastAdapterSyncVersion` plus two fields kept inert on purpose. Squads, teammates and tasks
  are authoritative in Dexie (`agentTeams`, `agentTeammates`, `agentTeamTasks`, added at schema
  v215), mirrored by `dexie-bridge.ts`. Live ephemera such as messages, events, consensus,
  shared memory and delegations stay in RAM. Run history is durable in `agentTeamRuns` and
  `workflowRuns`.
</TLDR>

### `AgentTeamConfig`

Roughly fifty fields, too many to print. They fall into six groups.

| Group | Fields |
| --- | --- |
| Durable runtime | `runtimeVersion`, `writeMode`, `repositories`, `environmentRef`, `resourcePolicy`, `evidencePolicy`, `retrospectivePolicy`, `githubDeliveryPolicy` |
| Sizing and mode | `maxTeammates`, `maxConcurrentTeammates`, `executionMode`, `preferredExecutionPattern`, `displayMode` |
| Teammate defaults | `defaultProvider`, `defaultModel`, `defaultApiKey`, `defaultBaseURL`, `defaultSystemPrompt`, `defaultTemperature`, `defaultMaxSteps`, `defaultTimeout`, `defaultExecution` |
| Gates and governance | `requirePlanApproval`, `riskGating`, `taskReview`, `governancePolicy`, `userConstraints`, `maxRetries`, `maxPlanRevisions`, `enableTaskRetry`, `enableDeadlockRecovery` |
| Tools and sandbox | `allowedTools`, `disallowedTools`, `defaultPermissionMode`, `sandboxEnabled`, `sandboxPolicy`, `capabilities`, `maxTeamDelegationDepth` |
| Memory and workspace | `sharedMemoryAdapterId`, `autoCleanSharedMemory`, `maxSharedMemoryEntries`, `knowledgeTwinIds`, `workingDir`, `workspaceIsolation`, `ultracode`, `progressLedger`, `adaptiveReplan`, `nudges`, `prFeedback`, `streamProgress` |

`riskGating` (ADR-0070) only ever *raises* the plan gate. An operator-set `requirePlanApproval` is never lowered by a risk assessment. `allowedTools`, `disallowedTools`, `defaultPermissionMode` and `sandboxPolicy` are ceilings: a teammate may narrow them and never widen past them.

### `AgentTeam`

The aggregate is identity plus config plus id lists plus a roll-up.

- **Identity and scope**: `id`, `projectId`, `name`, `description`, `task`, `sessionId`, `metadata`
- **Config and routing**: `config`, `routingAssessment`, `selectedExecutionPattern`, `dispatchDecision`, `externalPickup`
- **Membership**: `leadId`, `teammateIds`, `taskIds`, `messageIds`
- **Collaboration**: `sharedMemory`, `consensusIds`, `delegationIds`, `parentDelegationId`
- **Roll-up**: `status`, `progress`, `totalTokenUsage`, `finalResult`, `error`, `executionReport`
- **Timing**: `createdAt`, `startedAt`, `completedAt`, `totalDuration`

`projectId` is the workspace boundary. Before the Dexie move it existed but was only a filter three list surfaces applied, so a workspace purge never removed a Squad. Now it is an index on the table.

## The Store

### State

`AgentTeamState` (`stores/agent/agent-team-store/types.ts:32`) holds ten data fields (`teams`, `teammates`, `tasks`, `messages`, `templates`, `events`, `consensus`, `sharedMemory`, `delegations`, `lastAdapterSyncVersion`), five view fields, and `defaultConfig`.

Three of the view fields are deliberate dormancy, labelled at the type, in the initial state, and pinned by `store.test.ts` and `selectors.test.ts`.

| Field | Status |
| --- | --- |
| `activeTeamId` | Written by `createTeam` only. Read as a last-resort fallback by `selectActiveTeamConsensus`, by `getActiveTeam`, and by `DelegationsPanel`. Not persisted, so it is empty after a reload, which is why every real surface names its own team id. |
| `displayMode` | **Intentionally inert.** Persisted so an older build's blob round-trips, read by nothing since the compact/expanded toggle went with the workspace. |
| `workspaceTab` | **Intentionally inert**, same reason. Its type carries the type-level half of the same label. |

`tasksView` and `editorSession` are live view preferences with real readers.

### Persistence

```ts
// stores/agent/agent-team-store/store.ts:263-277
export function partializeAgentTeamState(state: AgentTeamState) {
  return {
    templates: state.templates,
    defaultConfig: state.defaultConfig,
    displayMode: state.displayMode,
    workspaceTab: state.workspaceTab,
    tasksView: state.tasksView,
    lastAdapterSyncVersion: state.lastAdapterSyncVersion,
    // teams / teammates / tasks are Dexie's from v8 on. Leaving them here as
    // well would give the subsystem two durable copies with no rule for which
    // wins, and the localStorage one cannot be workspace-scoped or synced.
    // `dexie-bridge.ts` owns them; only what is left is UI-shaped preference.
    editorSession: state.editorSession,
  }
}
```

Storage key `cognia-agent-teams`, re-pointed per account by `activateAgentTeamAccountStorage` (`:303`) to `cognia-agent-teams:<accountId>`. That path bypasses `migrate` and `onRehydrateStorage`, so it re-runs `resetStaleTeamStatuses` and `backfillTeamProjectIds` itself.

`PERSIST_VERSION` is **8**. The migration ladder in the file header records every step, and two of them matter for reading old data.

- **v3 to v4** made `teams`, `teammates` and `tasks` durable at all, so a scheduled `agent-team` task could re-instantiate its Squad after a restart.
- **v7 to v8** moved those three back out of `localStorage` into Dexie. The migration does *not* move the rows itself. It leaves them in the rehydrated state and lets `dexie-bridge.ts` write anything memory holds that the tables do not, on its first sync, because a synchronous storage callback has no way to await an account database.

`migrate` and `onRehydrateStorage` both reset any Squad left in `planning`, `executing` or `paused` to `idle`. `migrate` alone is not enough: it short-circuits on a same-version reload, which would rehydrate a phantom "executing" run.

### The Dexie mirror

Dexie is authoritative for definitions from persist v8 on. `dexie-bridge.ts` subscribes once and diffs by identity rather than threading an `await` through 1,300 lines of synchronous `set()` calls, debouncing bursts by **400 ms**, because a running Squad emits progress on nearly every token. It carries the two safety rules every dexie-bridge in this repo pays for.

1. **Never write to a database it was not built against.** Locking an account clears the Dexie selection *before* the store, so a live subscription would otherwise observe an empty store pointed at another account's database and delete every row in it.
2. **A failed hydration disables the mirror entirely.** Deletes are derived from "in the mirror, absent from memory", and if hydration threw then memory is an unknown subset of the tables.

Templates and `defaultConfig` are not mirrored. Squad templates are profile-shared by design and the unified template platform owns them. The bridge is started by `components/providers/initializers/agent-team-bridge-initializer.tsx`.

| Table | Key and indexes | Row type |
| --- | --- | --- |
| `agentTeams` | `&id, projectId, status, createdAt, updatedAt, [projectId+createdAt]` | `AgentTeamRow` |
| `agentTeammates` | `&id, teamId, role, updatedAt, [teamId+createdAt]` | `AgentTeammateRow` |
| `agentTeamTasks` | `&id, teamId, status, assignedTo, updatedAt, [teamId+order]` | `AgentTeamTaskRow` |

Rows flatten `Date` to epoch milliseconds and add an `updatedAt` the domain types never had, because sync needs a cursor and the mirror is the only place that knows a row actually changed (`lib/db/agent-team-definitions.ts:24-49`). The three tables arrived at schema **v215**. The runtime half (`agentTeamRuns` plus ten child tables) has been in Dexie since v145. `lib/db/schema.ts` now declares one collapsed schema at `CURRENT_SCHEMA_VERSION` **217** rather than replaying a migration chain, so those numbers are history rather than `version(N)` blocks.

### Persistence matrix

| Data | Where it lives | Survives reload |
| --- | --- | --- |
| Squads, teammates, tasks | Dexie `agentTeams` / `agentTeammates` / `agentTeamTasks` | Yes, workspace-scoped |
| Templates, `defaultConfig` | `localStorage` blob, plus the template platform's `templateDefinitions` table | Yes, profile-wide |
| `tasksView`, `editorSession`, `lastAdapterSyncVersion` | `localStorage` blob | Yes |
| `displayMode`, `workspaceTab` | `localStorage` blob | Yes, but read by nothing |
| Messages, events, consensus, shared memory, delegations | RAM only | No |
| `activeTeamId` | RAM only | No |
| Run history | Dexie `agentTeamRuns` and children, plus `workflowRuns` with `triggerKind: "team"` | Yes |
| Chat binding | `sessions.squadId`, indexed. Introduced at Dexie v177, today part of the collapsed schema | Yes |

`sessions.squadId` (which Squad runs this conversation) is deliberately distinct from `sessions.teamId` (which Character Team this conversation *is*). `lib/db/schema.test.ts` pins the pair.

The backup snapshot for this subsystem is `lib/data/snapshots/agent-teams.ts`, which warns about the same naming collision: the Dexie `teams` table is Character Teams, not Squads.

## Action Surface

Fifty-three actions on one slice, `slices/actions.slice.ts`, grouped as the type declares them.

| Group | Actions |
| --- | --- |
| Squad CRUD | `createTeam`, `upsertTeam`, `updateTeam`, `updateTeamConfig`, `updateTeamCapabilities`, `deleteTeam`, `purgeProject`, `setTeamStatus` |
| Teammate CRUD | `addTeammate`, `upsertTeammate`, `updateTeammate`, `updateTeammateCapabilities`, `removeTeammate` |
| Task CRUD | `createTask`, `upsertTask`, `updateTask`, `deleteTask`, `setTaskStatus`, `moveTask`, `reorderTask`, `assignTask`, `addTaskComment`, `attachTaskFile` |
| Messages and events | `addMessage`, `removeMessage`, `addEvent`, `clearEvents` |
| Templates | `addTemplate`, `deleteTemplate`, `duplicateSquad`, `saveAsTemplate`, `updateTemplate` |
| Read views | `getTeam`, `getTeammate`, `getTeammates`, `getTeamTasks`, `getTaskComments`, `getTeamMessages`, `getActiveTeam` |
| Consensus | `upsertConsensus`, `deleteConsensus`, `clearTeamConsensus` |
| Shared memory | `writeSharedMemory`, `deleteSharedMemory`, `clearTeamSharedMemory`, `setAdapterSyncVersion` |
| Delegations | `upsertDelegation`, `updateDelegationStatus`, `clearTeamDelegations` |
| Execution reports | `upsertExecutionReport`, `addExecutionCheckpoint` |
| View state and reset | `setTasksView`, `reset` |

`moveTask` is the human-owned board move. It validates through `canMoveTask`, the single guard shared with the board UI, the Companion RPCs and `ctx.team.moveTask`, and applies the status side-effects (claim release on a move back to `pending`, completion stamps on terminal statuses).

`upsertExecutionReport` and `addExecutionCheckpoint` are kept although the runtime does not yet stamp a report. Three live readers, `ctx.team.getRunStatus`, `getExecutionReport` and `listCheckpoints`, would be permanently unfillable without them.

`purgeProject` is registered as the subsystem's workspace-purge hook (`registerProjectBucketPurger("agent-teams", …)`).

## Selectors

`selectors.ts` exports ten base selectors (`selectTeams`, `selectTeammates`, `selectTasks`, `selectMessages`, `selectTemplates`, `selectDefaultConfig`, `selectConsensus`, `selectSharedMemory`, `selectDelegations`, `selectEvents`) plus `selectTeamCount`, and then the derived ones that matter.

| Selector | Line | Notes |
| --- | --- | --- |
| `selectTeamTeammates(state, teamId)` | `:45` | Roster of a NAMED Squad, in roster order with its lead first |
| `selectTeamConsensus(state, teamId)` | `:69` | Consensus rows of a NAMED Squad |
| `selectActiveTeamConsensus(state)` | `:83` | The only remaining `activeTeamId` fallback selector |
| `selectTeamDelegations(state, teamId)` | `:162` | Delegations a NAMED Squad is the source of |
| `selectActiveDelegations(state)` | `:170` | Every in-flight delegation, across Squads |
| `selectResolvedCapabilities(teamId, teammateId)` | `:131` | Runs the ADR-0032 resolver against store state |
| `selectSharedMemoryEntriesForReader(teamId, readerId)` | `:114` | ACL-aware projection. `isEntryReadableBy` (`:103`) is the predicate and `OPERATOR_READER_ID` (`:94`) sees everything |

The barrel re-exports sixteen of these. `OPERATOR_READER_ID`, `isEntryReadableBy`, `selectSharedMemoryEntriesForReader` and `selectResolvedCapabilities` are imported from `./selectors` directly.

There is no `selectActiveTeamDelegations`. Its one caller, `DelegationsPanel`, resolves `teamId ?? activeTeamId` itself and names the answer, so the "whatever was created last in this session" fallback lives at one call site instead of being a second selector. `selectors.test.ts` pins its absence from the barrel.

## What ADR-0140 Removed

The `/agent-teams/workspace` shell owned a cluster of store state and actions that nothing else ever called. They are gone. This list exists so a reader with an old bookmark stops looking.

| Removed | Replacement |
| --- | --- |
| `setActiveTeam`, `setWorkspaceTeamFromRoute`, `closeAgentTeamWorkspaceDetail`, `setIsPanelOpen`, `setDisplayMode`, `setWorkspaceTab`, `setWorkspaceFocus`, `setSelectedTeammate` | Nothing. Surfaces pass a `teamId` prop. |
| `selectedTeammateId`, `isPanelOpen`, `workspaceFocus`, `workspaceDetailOpen` | Nothing. The consensus panel picks its voter from the roster instead. |
| `setTeammateStatus`, `setTeammateProgress`, `claimTask` | The runtime writes through `updateTeammate`, `setTaskStatus` and `moveTask`. |
| `cancelAllTasks`, `shutdownAllTeammates`, `cleanupTeam`, `requestTeammateShutdown`, `addStructuredMessage` | `agentTeamManager.shutdown` and `addMessage`. |
| `upsertMessage`, `markMessageRead`, `markAllMessagesRead`, `markTeamMessagesRead`, `getUnreadMessages` | `addMessage` and `removeMessage`. Read state had no reader left. |
| `importTemplates`, `exportTemplates` | `service.exportPackage` and `service.importPackage` on the template platform. |
| `updateDefaultConfig`, `clearStaleCapabilityIds` | `defaultConfig` is edited through the Settings form. Stale ids are surfaced by the capability-audit gate, which outlives the action that used to clean up after it. |
| The whole `selectActiveTeam*` family, plus `selectActiveTeamId`, `selectSelectedTeammateId`, `selectDisplayMode`, `selectIsPanelOpen`, `selectWorkspaceTab`, `selectWorkspaceFocus`, `selectWorkspaceDetailOpen`, `selectTeamUnreadCount`, `selectTotalUnreadCount` | The team-scoped selectors above. `selectActiveTeamConsensus` is the one survivor. |
| `dispatchAgentTeam` on `agent-team-compat.ts` | `startSquadRun`, ADR-0140's single dispatch funnel. |

## Adjacent Modules

- `lib/ai/agent/agent-team-compat.ts` is now two pure normalizers, `normalizeAgentTeamConfig` and `normalizeAgentTeamTask`, which the store calls on every create and update. They trim strings and clamp counts, and return the original reference when nothing changed.
- `stores/agent/pending-gates-store.ts` is the HITL gate queue, shared by the ADR-0022 Squad gates and the ADR-0045 plan gates. Seven gate types: `budget`, `deadlock`, `plan`, `teammate_fix`, `replan`, `capability_audit`, `plan_step`. `gateTypeFromScope` maps approval-bus scopes onto them, and rehydration stamps every restored gate `interrupted`, because the approval-bus waiter died with the page. See [HITL Gates](./hitl-gates).
