# Setup & Credentials

<TLDR>
  Enable the `github-delivery` plugin in Settings → Plugins → Marketplace, then go to Settings →
  GitHub Delivery → Credentials to choose a credential mode (App recommended / PAT quick-start) and
  add repositories in the Repos Tab. The webhook URL is assigned a random port by the Tauri Rust
  receiver and can be exposed with a single cloudflared click; if your machine has no public
  ingress, switch to ETag polling (every 5 minutes) instead.
</TLDR>

## Prerequisites

| Requirement                                   | Required | Notes                                                                                                       |
| --------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------- |
| cognia 0.1.0+                                 | Yes      | Plugin manifest specifies `engines.cognia >= 0.1.0`                                                         |
| Tauri desktop build (macOS / Windows / Linux) | No       | Web mode still runs nodes + polling, but cannot register webhooks                                           |
| GitHub account + repo write access            | Yes      | App mode requires installing the App in a repo or org; PAT mode requires a token with at least `repo` scope |
| Public ingress or cloudflared                 | No       | Only needed for webhook triggers; otherwise continue using polling                                          |

## 1. Enable the Plugin

<Steps>
<Step>
**Open the Plugin Marketplace.** Settings → Plugins (`?section=plugins`) → Marketplace. Find
"GitHub Delivery" in the list.
</Step>
<Step>
**Click Enable.** The plugin manager will:

1. Validate the 4 table schemas in `manifest.dexie.tables`, then inject `repos` / `workOrders` / `events` / `audit`
   into CogniaDB via `applyPluginTables(db, "github-delivery", ...)`.
2. Write a `pluginDexieMeta` row marking the schema version as applied.
3. Call `activate(ctx)` (`plugins/github-delivery/src/index.ts`), which:
   - Touches all 4 tables (schema mismatches throw here).
   - Registers 13 `action.github.*` node executors into the workflow registry.
   - Installs the runtime singleton via `setGithubRuntime(...)` (`getRepo` / `getOctokit` / `recordAudit` /
     `checkPolicy` / `getWorkOrder` / `upsertWorkOrder`).
   - Registers the Claude sidecar driver for the Issue → PR loop.
   - Registers the `github` connector adapter into the ConnectorBus via `registerPluginAdapters`.
</Step>
<Step>
**Confirm Settings → GitHub Delivery is visible.** The sidebar shows a GitHub Delivery entry under the "Extensions" group.
Click it to see 5 tabs: Repos / Credentials / Policies / Audit / Usage.
</Step>
</Steps>

<Callout type="warn">
**Desktop prerequisite.** When the Tauri desktop app starts, the built-in axum receiver (`src-tauri/src/workflow/triggers/webhook_router.rs`)
binds webhook routes on `127.0.0.1:<random-port>`. Web mode lacks this layer, so `trigger.github.webhook` nodes cannot run on the web —
the Repos Tab will show a "desktop only" notice.
</Callout>

## 2. Choose a Credential Mode

<Tabs items={['GitHub App (Recommended)', 'PAT (Quick Start)']}>
<Tab value="GitHub App (Recommended)">

**Characteristics**

- 5K Octokit calls per hour (single-repo PAT is usually 5K per account; App is 5K per installation).
- Isolated by installation with fine-grained audit granularity.
- Tokens automatically expire after 1 hour and refresh 5 minutes early (`lib/github/auth-app.ts:getInstallationToken`).
- cognia does not hold a shared App; the App private key belongs to the user.

**Steps**

<Steps>
<Step>
**Create an App on GitHub.** Settings → Developer settings → GitHub Apps → New GitHub App.

- Repository permissions (minimum required):
  - Contents: Read & write
  - Issues: Read & write
  - Pull requests: Read & write
  - Metadata: Read
  - Checks: Read (for CI failure diagnosis)
- Subscribe to events: check the following (covers all 11 `NormalizedGhEventKind` types supported by cognia):
  - Pull request, Pull request review, Issues, Issue comment, Check run, Release.
- Webhook URL: leave blank for now; we will fill it in after cognia provides the real path.
- Generate a private key and download the PEM file.
</Step>
<Step>
**Install the App in the target repo or org.** After installation, grab the `installation_id` from the URL
(e.g. `https://github.com/settings/installations/12345678` → 12345678).
</Step>
<Step>
**Enter credentials in cognia.** Settings → GitHub Delivery → Credentials, choose App mode, and fill in:

| Field             | Source                                      |
| ----------------- | ------------------------------------------- |
| App ID            | Top of the GitHub App settings page         |
| Installation ID   | From the URL path after installing the App  |
| Private key (PEM) | Full contents of the downloaded `.pem` file |

On desktop, the private key is moved to the OS keyring (`ctx.secrets.set`) and wiped from the IndexedDB row;
on web, it remains in an encrypted blob.

</Step>
</Steps>

</Tab>
<Tab value="PAT (Quick Start)">

**Characteristics**

- Simplest configuration: paste a token and go.
- Rate limit is 5K per hour per token, shared across all applications using that token.
- No installation concept; audit granularity is only to "this person".
- Must use a fine-grained PAT or a classic PAT with minimal scopes.

**Steps**

<Steps>
<Step>
**Create a PAT.** GitHub → Settings → Developer settings → Personal access tokens
→ Fine-grained tokens → Generate new token.

- Select the target repository.
- Repository permissions: Contents (RW), Issues (RW), Pull requests (RW), Metadata (Read),
  Checks (Read).
- Do not check Organization permissions (principle of least privilege).
</Step>
<Step>
**Paste the token in cognia.** Settings → GitHub Delivery → Credentials → choose PAT,
paste the token. On desktop, it is saved to the OS keyring and the `patToken` field in the row is cleared
(`patKeyringId` becomes the single source of truth).
</Step>
</Steps>

</Tab>
</Tabs>

## 3. Register a Repository

Settings → GitHub Delivery → Repos:

| Field                    | Meaning                                                                   |
| ------------------------ | ------------------------------------------------------------------------- |
| Full name (`owner/name`) | Standard full name of the repository                                      |
| Credential mode          | `app` or `pat` (determines the `octokit-factory` path)                    |
| Trigger mode             | `webhook` or `polling` (see next section)                                 |
| Worktree mode            | `local` (default, simple git clone) or `e2b` (via the e2b-sandbox plugin) |
| Push target              | `source-branch` (default) or `fork` (push to a fork)                      |
| Policy                   | Optional, repo-level override. Full fields in [policies](./policies)      |

The row is written to the `github-delivery:repos` table; primary key = `fullName`.

## 4. Expose the Webhook URL (Optional)

Webhook mode is more real-time than polling, but requires a publicly reachable URL. Three approaches:

<Tabs items={['cloudflared One-Click (Recommended)', 'Self-Hosted Reverse Proxy', 'Use Polling']}>
<Tab value="cloudflared One-Click (Recommended)">

Desktop includes a one-click cloudflared expose:

<Steps>
<Step>
**Confirm cloudflared is in PATH.** macOS: `brew install cloudflared`; Windows: `scoop install cloudflared`;
Linux: `apt install cloudflared`. Tauri already has an allow rule for cloudflared in `tauri.conf.json`.
</Step>
<Step>
**Click "Expose webhook" in the Repos Tab.** cognia calls `lib/github/cloudflared-tauri.ts`:
starts a quick tunnel, routing `https://<random>.trycloudflare.com/<repo-id>` to the local
Rust receiver. The returned URL is automatically written back to the Repo row.
</Step>
<Step>
**Fill the URL back into the GitHub App / repo webhook settings.** Content type: `application/json`,
Secret: any strong random string (cognia will prompt you to enter and store it in the OS keyring), Events: check
"Send everything" or the events listed above. Click "Update webhook".
</Step>
<Step>
**Test delivery.** GitHub Webhook → Recent Deliveries → Redeliver. The Audit Tab should immediately show
a record.
</Step>
</Steps>

</Tab>
<Tab value="Self-Hosted Reverse Proxy">

If using ngrok, Caddy, or nginx as a reverse proxy to your local machine:

1. In the Repos Tab, click "Show local webhook URL" to see a local URL like `http://127.0.0.1:<port>/<repo-id>`.
2. In your own reverse proxy, map an external domain to this URL.
3. Fill the external domain into the GitHub Webhook URL.
4. In Settings → GitHub Delivery → Credentials → Webhook secret, enter a strong random string,
   and fill the same value into GitHub's Webhook → Secret field.

</Tab>
<Tab value="Use Polling">

When there is no public ingress, change the repo's `triggerMode` to `polling`:

Polling fallback is not available. Configure a publicly reachable webhook URL, using the built-in
cloudflared tunnel when direct ingress is unavailable. Existing repositories saved with
`triggerMode: "polling"` must be switched to `"webhook"`.

</Tab>
</Tabs>

## 5. Verification

<Steps>
<Step>
**Register a webhook trigger.** Workflow editor → New → drag in a `trigger.github.webhook` node,
select `pull_request.opened` for events, save.
</Step>
<Step>
**Trigger manually.** Open a draft PR in the target repo (or "Redeliver" a recent webhook on an existing PR).
</Step>
<Step>
**Confirm the event lands in the database.** Settings → GitHub Delivery → Audit Tab should show a `pull_request.opened`
record with `source: "webhook"` and a `deliveryId` matching GitHub's Recent Deliveries.
</Step>
<Step>
**Confirm the Inbox appears.** Open `/inbox`; the left sidebar will show a new `gh:<owner>/<repo>/pr-<n>` session
with the latest message being `<sender> opened PR #<n> in <repo>`.
</Step>
</Steps>

## Troubleshooting Quick Reference

| Symptom                                           | Likely Cause                                                        | How to Check                                                                                                 |
| ------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Webhook arrives but audit has no rows             | Signature verification failed                                       | Confirm `x-hub-signature-256` is in the headers; verify Settings → Webhook secret matches the GitHub side    |
| `401 Bad credentials`                             | Wrong App private key or unauthorized installation                  | Check the PEM is complete (including `-----BEGIN` / `-----END` lines); confirm the installation still exists |
| `404 Not Found` (read-only endpoint)              | Necessary repo permissions were not checked during App installation | Modify GitHub App permissions, then "Re-authorize" the App in the repository                                 |
| Repository receives no events                    | Repository still has legacy `triggerMode: "polling"`                | Change the repository to webhook mode and verify the public webhook URL                                     |
| Node throws `No issue-loop AI driver`             | Sidecar not started                                                 | Connect the Claude Code provider in Settings → Providers, then restart the plugin                            |
| `tauri.conf.json` shell scope rejects cloudflared | Old config from before upgrade                                      | Pull main and confirm the shell scope contains an allow line for `cloudflared`                               |
