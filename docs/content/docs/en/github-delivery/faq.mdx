# FAQ

<TLDR>
  This page collects common issues: webhook 401 / signature failures, silent polling, and the origin
  of `No issue-loop AI driver`. Questions are grouped by "symptom"; each includes a troubleshooting
  checklist and source code location.
</TLDR>

## Credentials / Authentication

<Accordions>
<Accordion title="GitHub webhook deliveries return 401 / 403">

**Symptom.** GitHub Webhook settings page shows `401` or `403` in Recent Deliveries,
and the Audit Tab has no corresponding rows.

**Causes + Troubleshooting Checklist.**

1. **Signature verification failure.** Settings → GitHub Delivery → Credentials → Webhook secret
   must match the GitHub-side Webhook → Secret **character-for-character**, including trailing newlines.
   `webhook-verify.ts:verifyGithubSignature` reads the `x-hub-signature-256` header → `sha256=<hex>`,
   and compares it with cognia's own HMAC-SHA-256 computed with the same secret using `timingSafeEqual`.
2. **Body modified by an intermediate layer.** cloudflared / nginx / Caddy don't modify the body by default,
   but gzip decompression / utf-8 normalization middleware will break HMAC — verify your reverse proxy
   uses `proxy_pass` rather than `body_filter_by_lua`.
3. **GitHub doesn't send `x-hub-signature-256`.** When no Secret is set on the webhook, GitHub won't sign it;
   cognia returns 401 in this case. Add a Secret to fix it.

</Accordion>

<Accordion title="Octokit throws `401 Bad credentials`">

**Symptom.** Workflow node fails, error message contains `Bad credentials`.

**Causes + Troubleshooting Checklist.**

1. **App private key truncated.** Settings → Credentials → re-paste the complete PEM (must include
   `-----BEGIN RSA PRIVATE KEY-----` and `-----END` lines).
2. **PAT revoked / expired.** Check GitHub → Settings → Developer settings → tokens;
   regenerate and paste into the Credentials Tab.
3. **Installation uninstalled.** Confirm the App is still installed on the target repository at
   GitHub → Settings → Installations. If the installation was "Suspended" on the GitHub side,
   all tokens become invalid immediately.
4. **Token cache hit on stale value.** Rare, but `lib/github/auth-app.ts:evictInstallationToken(appId, installationId)`
   can force a clear. Restarting cognia also clears the in-process cache.

</Accordion>

<Accordion title="GitHub App vs PAT — which should I choose?">

| Scenario                                              | Recommendation | Reason                                                                                                         |
| ----------------------------------------------------- | -------------- | -------------------------------------------------------------------------------------------------------------- |
| Personal toy repo, automation only for yourself       | **PAT**        | Simplest setup: paste one token                                                                                |
| Company / organization collaborative repo             | **App**        | Install / uninstall granularity is independent of individuals; one installation gets a 5K/h independent bucket |
| Multi-repo shared bot                                 | **App**        | Same as above                                                                                                  |
| Personal use, but worried about the 5K/h shared limit | **App**        | Does not share the rate bucket with your other automations                                                     |
| Temporary experiment or one-off task                  | **PAT**        | Revoke when done; creating an App has relatively higher one-time cost                                          |

</Accordion>
</Accordions>

## Triggers

<Accordions>
<Accordion title="Webhook trigger doesn't work in Web mode">

**Symptom.** In Web mode (browser / no Tauri desktop app), registering a `trigger.github.webhook`
workflow: GitHub delivers the webhook but cognia doesn't respond at all.

**Cause.** Web mode has no Rust axum receiver (`src-tauri/src/workflow/triggers/webhook_router.rs`
is only compiled into Tauri). The Repos Tab shows a "desktop only" notice, and the workflow editor's
connection validator also rejects dragging a webhook trigger onto the canvas
(`lib/workflow/editor/connection-validator.ts`).

**Workarounds.**

- Run cognia on desktop, or
- Switch the Repo `triggerMode` to `polling` (no desktop required).

</Accordion>

<Accordion title="Polling enabled but Audit Tab shows no new rows">

**Symptom.** `triggerMode` set to `polling`, but 5 minutes later the Audit Tab is still empty.

**Troubleshooting Checklist.**

1. **Is the repository still configured for the retired polling mode?** Change `triggerMode` to `webhook`.
2. **Has the repository had events in the last 90 days?** The `/repos/{owner}/{repo}/events` endpoint only returns events from the past 90 days.
   Long-inactive repositories will "appear to have nothing happening."
3. **Is `pollEtag` staying the same?** Check Dexie DevTools for the `github-delivery:repos` row;
   if `pollEtag` never changes = GitHub truly has no new events, and the 304 path is working correctly.
4. **Does the credential have `events` permission?** App permissions must include Metadata: Read (events is implicit).
   PAT must have `repo` scope.

</Accordion>

<Accordion title="Same event received by both webhook and polling — will it trigger twice?">

The polling transport has been retired. GitHub events enter through the Rust webhook path and use
the `x-github-delivery` header as their stable delivery id.

</Accordion>
</Accordions>

## Nodes / Workflows

<Accordions>
<Accordion title="`action.github.runIssueLoop` throws `No issue-loop AI driver is registered`">

**Cause.** Issue → PR loop requires the Claude sidecar driver (`plugins/github-delivery/src/drivers/sidecar-driver.ts`).
When the plugin activates:

```ts title="plugins/github-delivery/src/index.ts"
setIssueLoopDriver(new SidecarIssueLoopDriver())
```

But the driver itself checks whether the Claude sidecar is ready during `driver.run`. If the Claude provider
is not configured (Settings → Providers → Claude field is empty), or the sidecar process isn't running,
the driver throws inside `run` and returns `{ status: "failed", reason: "..." }`.

**Workarounds.**

1. Configure Claude in Settings → Providers (can be OAuth or API key).
2. Confirm login in Settings → Subscription (if using OAuth).
3. Restart the plugin: Settings → Plugins → GitHub Delivery → Disable / Enable.
4. Re-run the workflow.

</Accordion>

<Accordion title="`action.github.mergePr` always rejected, reason is `requires explicit human approval`">

**Cause.** Default policy `requireHumanApproval: true`. This is a "soft denial" (`needsApproval: true`),
routed by `guardedExecutor` to the Inbox HITL draft. Open `/inbox`, find the conversation for the corresponding PR,
and click Approve / Reject / Edit body.

**Workarounds (choose one).**

- Actually review it in Inbox (recommended).
- Set `policyOverride: { requireHumanApproval: false }` on the PR node (node-level, use with caution).
- Turn off repo-level `requireHumanApproval` in Settings → GitHub Delivery → Policies.

</Accordion>

<Accordion title="`mergePr` throws `daily merge cap of N reached`">

**Cause.** Default `maxDailyMerges: 5`. The bot's merge count per UTC day is scanned from the audit table
via the `[repoFullName+at]` index, filtering `action.kind === "merge" && decision.allow === true`.

**Workarounds.** Increase repo-level or node-level `maxDailyMerges`, or wait for the next UTC day.

</Accordion>

<Accordion title="`action.github.openPr` throws `branch 'main' matches protection regex '^main$'`">

**Cause.** `openPr` passes `head` as the push branch into the policy gate. Default `branchProtection`
includes `^main$` / `^master$` — this is usually correct, because cognia should not point a PR's head directly at the main branch.

**Workaround.** Make sure you're using `head: "cognia/feature-xxx"` instead of `head: "main"`.

</Accordion>
</Accordions>

## cloudflared / Networking

<Accordions>
<Accordion title="Clicking 'Expose webhook' does nothing">

**Troubleshooting Checklist.**

1. **Is cloudflared in PATH?** Run `cloudflared --version` in a terminal. Tauri's shell scope only
   allows calling cloudflared from PATH.
2. **Does the Tauri shell scope include cloudflared?** Check `src-tauri/tauri.conf.json` for
   `"name": "cloudflared", "command": "cloudflared", "args": true` or similar allow entries.
3. **Check Diagnostics logs.** Settings → Diagnostics, search for "cloudflared". Common errors:
   - `EACCES`: macOS Gatekeeper unsigned binary block — `xattr -d com.apple.quarantine $(which cloudflared)`.
   - `proxy connection refused`: local port already in use — restart cognia, Rust will pick a new port.

</Accordion>

<Accordion title="Can I use other tunnel tools (ngrok / localtunnel / Caddy)?">

**Yes.** On the Repos Tab, click "Show local webhook URL" to see `http://127.0.0.1:<port>/<repo-id>`,
then reverse-proxy that with your tunnel tool of choice. Note:

- The `x-hub-signature-256` header must be forwarded unchanged.
- Don't let the intermediate layer do gzip compression / decompression (will break HMAC).
- The port is randomly assigned at cognia startup; it changes after restart. The Repos Tab has a "Refresh URL" button.

</Accordion>
</Accordions>

## Inbox / Outbound

<Accordions>
<Accordion title="GitHub PR comment won't send from Inbox Composer">

**Symptom.** Typing + sending in the `/inbox/c/gh:owner/repo/pr-42` conversation, but no comment appears on GitHub,
and Composer shows "queued" state for a long time.

**Troubleshooting Checklist.**

1. **Is the plugin enabled?** Settings → Plugins. The `PlatformAdapter` adapter is registered during plugin activation;
   without it, the `github` adapter is unavailable.
2. **Is the outbound queue circuit-broken?** Settings → Connections → Outbound to check the circuit breaker status for `github`.
   Failure rate ≥ 50% (10-event window) triggers a 30-second trip.
3. **In quiet hours?** The same quiet-hours tooling also applies to the outbound runner. Settings → Connections
   → Conversations to check mute status.

</Accordion>
</Accordions>

## Data / Dexie

<Accordions>
<Accordion title="How to recover audit data after plugin uninstall">

**Prerequisite.** Default uninstall is "keep data" (`removePluginTables(..., "keep")`). In this case:
re-enable the plugin, and the 4 tables reappear automatically with data intact.

**If "Delete data" was chosen during uninstall.** Data has been dropped. If you previously saved a file via
"Export CSV" in the Audit Tab, you can import it back (post-M4): Audit Tab → Import CSV.
**Do not rely on this capability for production data — please export regularly.**

</Accordion>

<Accordion title="What is the `pluginDexieMeta` row for?">

Records the dynamic schema version applied to CogniaDB for each plugin. When GitHub Delivery is enabled,
`applyPluginTables` writes the current table declaration hash; on next enable, if the hash hasn't changed,
schema upgrade is skipped — it's idempotent. See the
[Plugin Dexie Tables developer guide](/en/plugin-dev/dexie-tables) (written at M3 stage).

</Accordion>
</Accordions>

## Other

<Accordions>
<Accordion title="Why is the number 0018 instead of 0012?">

When the earliest GitHub Delivery ADR was drafted, the file path was under `docs/content/docs/adr/`
(before the zh/en tree split), with a temporary number 0012. Later it was discovered that
`zh/adr/0012-transport-abstraction.md` already occupied 0012, causing a conflict. After normalization,
GitHub Delivery was changed to 0018, and transport-abstraction kept 0012.
The original `docs/content/docs/adr/0012-github-delivery.md` has been removed; use
[/en/adr/0018-github-delivery](/en/adr/0018-github-delivery) for references.

</Accordion>

<Accordion title="What is all that `{{ ... }}` syntax in templates?">

The workflow expression language. See [Workflows → Expression language](/en/workflows/expression-language)
(written at M2 stage). You can index `$trigger.payload.body...` (webhook raw payload),
`$node['n_id'].out.<field>` (upstream node output), `$static.<key>` (workflow static variables), etc.
All fields labeled "supports {{ }} expressions" in the Inspector accept this syntax.

</Accordion>

<Accordion title="How do I avoid actually opening PRs / commenting during testing?">

The "Run" button in the top-right of the workflow editor has a "Dry run" mode — nodes are executed but
`guardedExecutor` returns `{ output: { skipped: true } }` on all deny paths.
For each executor's specific dry-run behavior, see the
[nodes reference](/en/github-delivery/nodes). Use real Run for production paths; review history can be
re-run from the same snapshot (the `runs/[runId]` detail page has "Re-run from snapshot").

</Accordion>
</Accordions>
