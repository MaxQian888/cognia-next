# Vector store

Cognia needs a vector index for the [Employee Digital Twin](../subsystems/employee-twin) RAG path. The store lives behind a thin abstraction (`packages/vector/src/store.ts`) so the rest of the app doesn't care which backend is active.

The full design rationale is in [ADR-0004](../adr/0004-vector-native-backend).

## Why sqlite-vec on desktop

ADR-0004 picked sqlite-vec because:

- **Single file** — easy to back up, copy across devices, and inspect with any sqlite tool.
- **No server** — zero ops cost; data lives next to the user's other Cognia data.
- **Bundled in Tauri** — `sqlite-vec = "0.1"` is loaded as a SQLite **auto-extension** before any connection opens. The crate has no rusqlite dependency, so the only constraint is that the host SQLite supports loadable extensions (Tauri's bundled SQLite via `rusqlite` with `bundled` feature does).
- **Fast enough** — for the scale of one user's twin (typically < 100k chunks), sqlite-vec's brute-force scan with SIMD is fine and avoids the complexity of HNSW maintenance.

## Native backend internals

```
src-tauri/src/vector/
  mod.rs          # Public API: register_extension, open_store, etc.
  db.rs           # Connection pool, migration runner
  schema.rs       # Table definitions (vectors + metadata)
  filters.rs      # WHERE clause builder for metadata filters
  types.rs        # Insert / Query / Result structs
  commands.rs     # #[tauri::command] wrappers
  error.rs        # Vector-specific error type
```

### Schema

Two tables per collection:

```sql
CREATE TABLE vec_<name> (
  id        INTEGER PRIMARY KEY,
  embedding BLOB    -- sqlite-vec FIXED-VECTOR encoded
);

CREATE VIRTUAL TABLE vec_<name>_idx USING vec0(
  embedding float[<dim>]
);

CREATE TABLE meta_<name> (
  id        TEXT    PRIMARY KEY,
  source    TEXT    NOT NULL,
  metadata  TEXT    NOT NULL  -- JSON
);
```

The `vec0` virtual table is the sqlite-vec index; the metadata table is plain SQL so we can filter by source / chunk type / etc. before / during similarity search.

### Auto-extension load

`db.rs` registers the sqlite-vec extension via `unsafe { Connection::load_extension_enable() }` **once at process start**, before any connection opens. This mirrors the pattern from sqlite-vec's own integration tests. Subsequent connections inherit the extension.

### Querying

The native `query` command takes:

- A query embedding (Float32 array).
- A collection name.
- Optional metadata filters (key/value JSON match).
- A `topK` cap.

It returns `(id, score, metadata)` triples sorted by cosine similarity. The score range is `[0, 1]` (sqlite-vec returns `1 - cosine`).

## Frontend abstraction (`lib/vector/`)

```
lib/vector/
  index.ts            # Public API (createStore, fromSettings)
  store.ts            # Implementation switch
  embedding.ts        # Embedding client (also used by twin ingest)
  readiness.ts        # Health check (used by SettingsSyncProvider)
  pinecone-client.ts  # Cloud client implementations
  qdrant-client.ts
  weaviate-client.ts
  chroma-client.ts
  milvus-client.ts
```

`store.ts` exposes a single `VectorStore` interface:

```ts
interface VectorStore {
  upsert(rows: VectorRow[]): Promise<void>
  query(input: QueryInput): Promise<QueryResult[]>
  delete(ids: string[]): Promise<void>
  collectionExists(name: string): Promise<boolean>
  ensureCollection(name: string, dim: number): Promise<void>
}
```

Each backend has its own implementation; `fromSettings(settings)` reads the user's vector settings from Dexie and returns the right one. The native backend goes through `lib/tauri.ts` (commands defined in `src-tauri/src/vector/commands.rs`); cloud backends call their respective SDKs directly.

## Settings

The user picks their backend in **Settings → Twin → Vector store**:

- Backend (radio: sqlite-vec / Pinecone / Qdrant / Weaviate / Chroma / Milvus). Native is hidden in web mode.
- Connection details (URL, API key, namespace) for cloud backends.
- Embedding dimension — must match the chosen embedder's output (default 1536 for OpenAI text-embedding-3-small).

`readiness.ts` runs a health check on save: a tiny upsert + query round-trip. If it fails, the user sees a clear error and the previous backend stays active.

## Re-ingest on backend switch

Switching backends does **not** automatically migrate. Rebuild each twin's index (**Rebuild index** in the twin workbench Settings tab, `rebuildTwinIndex` in `lib/twin/lifecycle.ts`): it re-runs ingestion of every source against the current backend with the twin's effective embedding. This is the only safe way: dimensions, distance metrics, and metadata schemas may differ.

## Per-twin embedding and the index fingerprint

Embedding settings belong to the **twin**, not to a character. Every twin inherits the global `TwinRuntimeSettings.embedding` unless its row carries an override:

```ts title="types/twin/index.ts"
export interface TwinEmbeddingOverride {
  provider: RagEmbeddingProvider
  model?: string // blank = the catalog default model for that provider
}
```

**Precedence** (`resolveTwinEmbeddingConfig` in `lib/twin/runtime/twin-embedding.ts`): `Twin.embedding` first, then the global config. The override stores no secrets. On the global provider it reuses the global key / base URL / Bedrock settings; on another provider it resolves the key from **Settings → Providers** through `resolveEmbeddingApiKey` (the same seam the plugin vector API uses), and a local engine's base URL from its provider settings, falling back to the engine's default localhost port. Memory, project knowledge, and agent knowledge bases are **not** affected: they keep the global model.

**Fingerprint.** After an ingest writes chunks, the job worker records on the twin row:

```ts
Twin.embeddingIndex = { provider, model, dimensions, fingerprint: `${provider}::${model}::${dimensions}`, builtAt }
```

The same fingerprint stamps each source's retrieval generation (`persistChunks`' `profileFingerprint`) instead of the dimension-only `legacy:<backend>:<dim>`. The record is written only when it is true for **every** chunk of the twin (a fresh twin, a full re-ingest, or a rebuild).

**Retrieval** (`applyTwinContext`):

- The twin's effective embedding is resolved per turn. When it differs from the shared `deps.embedding` (the global model, also used by memory / KB legs), the query is embedded again with the twin's config and a caller's `precomputedQueryEmbedding` is ignored.
- When the recorded `embeddingIndex` names another provider/model, the turn degrades with `rebuild-required: …`: twin RAG is skipped, style few-shot falls back to token-overlap scoring, and the chat still runs. Dimension checks stay with the existing guard (`dimension-mismatch: …`).
- An override without credentials degrades with `twin-embedding-unconfigured: <provider>`.
- A **legacy** index (no record) keeps the old behaviour — dimension guard only — so a swap between same-dimension models (cohere / mistral / voyage / bedrock are all 1024-dim) is not detected there. The workbench recommends a rebuild for it.

**Ingest guard.** An ingest job fails without retry (`rebuild-required: …`) when the recorded model differs from the effective one and chunks from the recorded model would survive the job — two models never share one index. An override without credentials fails the job with `twin-embedding-unconfigured: …`.

**Rebuild** (`rebuildTwinIndex`): pre-flight first (runtime ready — worker enabled, vector store configured — and effective embedding has credentials; nothing is destroyed otherwise), then cancel the twin's active ingest jobs, drop every collection its chunks point at (plus `cognia_twin_{twinId}`), and in one Dexie transaction delete the chunk rows, reset live sources to `pending`, drop cached style-sample vectors, and clear `embeddingIndex`. Finally one ingest job is queued over those sources; the worker embeds them with the effective config and records the new fingerprint. Until it finishes the twin has no index and answers without retrieved context.

The workbench card (`components/twin/twin-embedding-card.tsx`) holds the override picker, the "index built with …" status line, the rebuild-required warning, and the **Rebuild index** button. Other surfaces read the same state through `getTwinEmbeddingStatus(twinId)` in `lib/twin/runtime/twin-embedding-status.ts`.

<Callout type="info" title="Don't mix models">
  Switching the embedding model can switch the vector dimension — rebuild the index before querying.
  A different dimension is caught by the dimension guard (`packages/vector/src/dimension-guard.ts`)
  before any write or search. A same-dimension model swap is caught only on twins that recorded an
  `embeddingIndex` (`rebuild-required`); a legacy index can still return nearest-neighbour garbage.
</Callout>
