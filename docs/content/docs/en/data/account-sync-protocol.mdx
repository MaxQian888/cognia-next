# Account Sync Protocol v1

<Status variant="beta">§2–7 and §9 implemented behind a build flag · §8, §10–13 planned</Status>

Normative companion to [ADR-0215](../adr/0215-one-person-one-encrypted-sync-space-many-writable-hosts).
The ADR records *why*; this page records *the bytes*. It may be refined
without amending the ADR as long as the invariants in §0 hold. Every change
bumps `protocolVersion` or adds an optional field. Phase 2 implements §2–5
(keys and enrollment), phase 3a §6, §7 and §9 (the op log, live updates and
merge); snapshots (§8), blobs, leases, counters and the account lifecycle are
not implemented yet.

## 0. Invariants (fixed by the ADR)

1. The server never receives plaintext row content, field names, table names,
   resource names or secret values.
2. The server never holds a key that decrypts user data.
3. Every op is signed by an enrolled, non-revoked device; the registry of
   devices is itself a signature chain clients verify.
4. Merge happens on clients only. The server orders, dedupes, stores and
   relays.
5. One account ⇄ one Durable Object. One account ⇄ at most one LocalProfile per
   device.

## 1. Primitives

All primitives are available in WebCrypto on every shell and in the Rust crates
the repo already uses (`p256`, `hkdf`, `aes-gcm`).

| Use | Primitive |
| --- | --------- |
| Device signing | ECDSA P-256, SHA-256, IEEE P1363 signature (64 bytes) |
| Sealing a key to a device | HPKE base mode (RFC 9180): DHKEM(P-256, HKDF-SHA256), HKDF-SHA256, AES-256-GCM |
| Symmetric encryption | AES-256-GCM, 96-bit random nonce |
| Key derivation | HKDF-SHA256 |
| Hashing | SHA-256 |
| Binary on the wire | base64url, no padding |

`label(x)` below means the ASCII string `cognia-sync/v1/x`.

## 2. Identifiers

| Id | Form |
| -- | ---- |
| `spaceId` | `base64url(SHA-256(label(space) ‖ 0x00 ‖ iss ‖ 0x00 ‖ sub))`. The DO is `idFromName(spaceId)`. Bound to the issuer, so staging, production and a self-hosted issuer never share a space. |
| `deviceId` | `dev_` + 26 Crockford-base32 characters of 16 CSPRNG bytes (`^dev_[0-9A-HJKMNP-TV-Z]{26}$`) |
| `requestId` | `req_` + the same 26-character form |
| `epoch` | unsigned integer, starts at 1 |
| `entryHash` | `SHA-256(label(entry-hash) ‖ 0x00 ‖ JCS(entry))`, over the entry **without** its signatures (an ECDSA signature can be re-written as `(r, n−s)` without the key, so it must never feed a hash) |
| `genesisHash` | `entryHash` of registry entry 0 |
| `serverSeq` | unsigned 53-bit integer, assigned by the DO, gapless per account (phase 3) |
| `deviceSeq` | unsigned integer, per device, starts at 1, gapless (phase 3) |
| `opId` | `(deviceId, deviceSeq)` (phase 3) |
| Row ids (inside ciphertext) | UUIDv7 for new rows; existing ids kept verbatim (phase 3) |

Canonical encoding everywhere a hash or signature covers structured data is
RFC 8785 JCS. Binary values inside JCS are base64url without padding; numbers
are integers below 2^53. Every hash, signature and HKDF `info` below is over
`utf8(label) ‖ 0x00 ‖ bytes`.

## 3. Keys

### 3.1 Device keys

Each device generates:

- `signKey`: ECDSA P-256.
- `encKey`: ECDH P-256 (HPKE recipient key).

Public keys travel as raw uncompressed points (65 bytes, base64url), the form
HPKE serializes. They are distinct from the companion P-256 ES256 key
(ADR-0021/0059) so that revoking sync access never breaks pairing and vice
versa. Locally both private keys are a JWK in the LocalProfile vault
(`lib/runtime/browser-vault.ts`) and are used through non-extractable
re-imports.

### 3.2 Recovery key

- `rk`: 128 random bits, displayed as 26 Crockford-base32 characters,
  `XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XX` (the last character carries two zero
  bits). Parsing ignores case and hyphens/spaces and maps `I`/`L` → `1`, `O` → `0`.
- `seed = HKDF-SHA256(ikm = rk, salt = utf8(spaceId), info = label(recovery), L = 32)`.
- `encIkm = HKDF-Expand(seed, label(recovery-enc), 32)`,
  `signIkm = HKDF-Expand(seed, label(recovery-sign), 32)`.
- Each becomes a P-256 key pair by RFC 9180 §7.1.3 `DeriveKeyPair`
  (DHKEM(P-256), bitmask `0xff`, candidate counter): `recoveryEnc` (ECDH, the
  HPKE recipient) and `recoverySign` (ECDSA). Only the public halves are ever
  uploaded.
- Any device can seal a new epoch key to `recoveryEncPub` without knowing `rk`.
  `recoverySign` lets the recovery-key holder add a device when no other
  device is at hand, and countersigns every change of the recovery keys, so
  nobody else (the server included) can set them.

### 3.3 Epoch keys

- `SK_e`: random 256-bit sync key for epoch `e`.
- Subkeys: `HKDF(SK_e, salt = utf8(spaceId), info = label(<purpose>))`:
  - `commit` → `keyCommit_e = HMAC-SHA256(commitKey, JCS({spaceId, epoch: e}))`,
    published in the signed registry entry that starts the epoch;
  - `chain` → `prevWrap_e = AES-256-GCM(chainKey, nonce, SK_{e-1}, AAD = label(chain) ‖ 0x00 ‖ JCS({spaceId, epoch: e-1}))`,
    published in the same entry, so the current key opens all history;
  - `name` → device display names (`nameCt`, §4);
  - `op` → op encryption (§7.1, phase 3a);
  - later phases add `snap`, `blob-id`, `res-id`.
- Stored on the server only sealed: one HPKE base-mode envelope per active
  device and one for `recoveryEncPub`, `info = label(epoch-envelope)`,
  `AAD = JCS({v: 1, spaceId, epoch, recipient, recipientEncPub})`.
- A device uses an envelope only for the chain's **current** epoch and only if
  the opened key matches that epoch's signed `keyCommit`. Base-mode HPKE does
  not authenticate the sealer; the commitment does.
- Locally, a device keeps the key chain as a vault secret.

### 3.4 Epoch rotation triggers

- A device is revoked (the revoke entry starts the new epoch).
- The recovery key is used to add a device.
- The recovery key is regenerated (old recovery envelope deleted).
- Explicit "rotate keys" by the user.

Each rotation deletes the previous epoch's envelopes; history stays reachable
through the signed `prevWrap` chain.

## 4. Device registry

An append-only hash chain. Each element is `{entry, sigs: [{signer, sig}]}`,
where `signer` is a `deviceId` or `"recovery"` and `sig` is ECDSA over
`label(entry) ‖ 0x00 ‖ JCS(entry)`.

```
entry = { v: 1, spaceId, seq, prev, type, at, ... }     // prev = null at seq 0, else the previous entryHash
DeviceDescriptor = { deviceId, platform: "desktop"|"mobile"|"web", signPub, encPub, nameCt: { epoch, nonce, ct } }
EpochBlock       = { epoch, keyCommit, prevWrap?: { nonce, ct } }   // prevWrap required when epoch > 1
RecoveryKeys     = { signPub, encPub }
```

| type | Fields | Signed by | Effect |
| ---- | ------ | --------- | ------ |
| `genesis` (seq 0) | `device`, `recovery`, `epoch` (1) | the device **and** `recovery` | first device; pins the recovery keys |
| `add-device` | `device`, `via: "approval"`, `requestId`, `transcriptHash` | the approving active device | adds a device in the current epoch |
| `add-device` | `device`, `via: "recovery"` | `recovery` **and** the new device | adds a device; must be followed in the same batch by an `epoch-rotate` from it |
| `revoke-device` | `deviceId`, `epoch` (n+1) | an active device other than the target | revokes; new epoch |
| `recovery-rotate` | `recovery` (new), `epoch` (n+1) | an active device **and** the new `recovery` | replaces the recovery keys; new epoch |
| `epoch-rotate` | `epoch` (n+1) | an active device | new epoch |

`platform: "headless"` is reserved; phase 2 refuses it (a headless host has no
vault yet).

`validateAppend` (shared by the client and the Worker): `seq` = head + 1,
`prev` = head hash; every signer active in the state before the entry; a
`deviceId`, `signPub` or `encPub` is never reused (revoked ones included); no
self-revoke; the last active device cannot be revoked; at most 32 active
devices; an entry is at most 8 KiB; an epoch block's `epoch` = current + 1.

`nameCt` is the display name under the `name` subkey of `nameCt.epoch`:
`AES-256-GCM(nameKey, nonce, pad64(utf8(name)), AAD = JCS({spaceId, deviceId, epoch}))`.

### 4.1 Client verification (`foldRegistry`)

1. Entry 0 is a `genesis` whose two signatures verify. A device that already
   has a pin requires `genesisHash` = the pinned one. A device without a pin
   trusts it only through the approval transcript (§5.2) or a recovery-key
   match (§5.3).
2. Every later entry passes `validateAppend`.
3. **Rollback and fork:** the vault pin is `{genesisHash, seq, hash, epoch}`. A
   fetched chain must contain `entries[pin.seq]` with `hash = pin.hash`. A
   shorter chain, or another hash there, is the error "the server returned an
   older or different device list": nothing is written or deleted. The pin
   only moves forward.
4. **Epochs:** open the own envelope only for the current epoch, check
   `keyCommit`; walk `prevWrap` back to the oldest epoch not yet held, checking
   each unwrapped key against its own `keyCommit`.
5. Every public key a device seals to or trusts comes from the folded chain,
   never from another server response.

### 4.2 Residual risk

The server could show different, individually valid chains to different
devices (equivocation). The device list shows a "device list fingerprint"
(the head hash) that a person can compare across devices. Phase 3a ops do not
carry the signer's head yet; adding it as an optional envelope field is left
to phase 3b.

## 5. Enrollment

Requests that act as a device carry
`Cognia-Device-Proof: b64url(JCS({v: 1, spaceId, deviceId, method, path, bodySha256, iat})) "." b64url(sig)`,
signed by the device's `signKey` (`label(device-proof)`), accepted for
`|iat − now| ≤ 120 s`. Every response carries `Cognia-Server-Time` so a client
can correct its clock.

### 5.1 Genesis (first device)

1. `GET /v1/space` answers `empty`.
2. Generate device keys, `rk`, `SK_1`.
3. Recovery confirmation gate: the user retypes four randomly chosen
   characters, or downloads the recovery kit and confirms storing it. Nothing
   uploads before.
4. `POST /v1/space/genesis` with the genesis entry (two signatures) and two
   envelopes (self, recovery). `409 space_exists` means another device won the
   race; the client switches to §5.2.
5. Only after the server confirms does the device store its keys, the key
   chain and the pin.

### 5.2 Approval by an existing device

Commit-then-reveal, so the server cannot grind the six-digit code against
substituted keys.

1. New device R fetches and folds the registry; its `genesisHash` (`G_R`) is
   so far unverified.
2. R generates keys and `nonceR` (32 bytes),
   `commit = SHA-256(label(sas-commit) ‖ 0x00 ‖ nonceR)`, and seals its display
   name to each active device (`info = label(request-name)`,
   `AAD = JCS({spaceId, deviceId, recipient})`).
3. `POST /v1/enroll/requests` `{deviceId, platform, signPub, encPub, commit, names, pop}`
   (`pop` = signature by `signKey` over the body, `label(enroll-request)`)
   → `{requestId, expiresAt}` (15 min).
4. Active devices see it in their poll (§5.6) and raise a notification.
5. The approver A, when the person opens it, generates `nonceA`, keeps it in
   memory and posts it. The server accepts one approver per request.
6. R sees `nonceA` and posts `nonceR`; the server checks it against `commit`.
7. Both compute, each from its own values,
   `T = JCS({v: 1, spaceId, genesisHash, requestId, deviceId, platform, signPub, encPub, commit, approverDeviceId})`,
   `code = uint64be(HKDF-SHA256(ikm = nonceR ‖ nonceA, salt = SHA-256(label(sas) ‖ 0x00 ‖ T), info = label(sas-digits), L = 8)) mod 10^6`,
   shown as `123 456`. A never re-reads `nonceA` from the server; R shows no
   code before its reveal was accepted.
8. When the person confirms the codes match, A appends
   `add-device {via: "approval", requestId, transcriptHash: SHA-256(T)}` and an
   envelope of `SK_e` for R.
9. R fetches the chain and requires `genesisHash = G_R`, its own entry signed
   by the active `approverDeviceId`, and `transcriptHash = SHA-256(T)`; then it
   opens its envelope, checks `keyCommit` and stores everything.

The server fixes the keys it shows A before A picks `nonceA`, and the nonce it
shows R before R reveals `nonceR`; a substitution succeeds with probability
10^-6 per visible attempt. A forged chain shown to R changes `genesisHash` and
so the code.

### 5.3 Recovery

1. Fold the chain; derive the recovery keys from the typed key; they must equal
   the chain's current `recovery` keys ("this recovery key does not match this
   account" otherwise).
2. `GET /v1/envelopes/recovery`, open it, check `keyCommit`.
3. Generate device keys and post one atomic batch: `add-device {via: "recovery"}`
   (signed by `recovery` and the new device) followed by `epoch-rotate`
   (signed by the new device) with envelopes for every active device, itself
   and recovery.
4. Offer to regenerate the recovery key (default yes). Other devices show
   "a device joined with your recovery key".

### 5.5 Revocation, regeneration, rotation

- **Revoke:** `revoke-device` with the new epoch and envelopes for `(active − target) ∪ {recovery}`. The revoked device learns of it from `403 device_revoked`
  and acts only after finding a validly signed revoke entry for its own id:
  it deletes its device keys and key chain, keeps the pin, and records when and
  by which device it was removed. An unverifiable 403 deletes nothing. (Locking
  the profile and deleting synced secrets come with the secrets class, phase 5.)
- **Regenerate the recovery key:** a new `rk` passes the confirmation gate,
  then `recovery-rotate`; the server deletes the old recovery envelope.
- **Rotate:** `epoch-rotate`.

### 5.6 Phase-2 server API

| Route | Auth | Purpose |
| ----- | ---- | ------- |
| `GET /v1/space` | bearer | `{state: empty \| ready, genesisHash?, head, epoch, protocolVersion}` |
| `GET /v1/registry?after=N` | bearer | entries |
| `POST /v1/space/genesis` | bearer | genesis; `409 space_exists` |
| `GET /v1/envelopes/recovery` | bearer | current recovery envelope |
| `POST /v1/enroll/requests` | bearer + `pop` | create (≤ 3 pending, ≤ 10 per hour) |
| `GET /v1/enroll/requests/:id` | pending-device proof | state, approver nonce |
| `POST /v1/enroll/requests/:id/reveal` | pending-device proof | `nonceR` |
| `DELETE /v1/enroll/requests/:id` | pending-device proof | cancel |
| `GET /v1/enroll/requests` | active-device proof | the poll (every 20 s while foregrounded) |
| `POST /v1/enroll/requests/:id/nonce` | active-device proof | `nonceA`, once |
| `POST /v1/enroll/requests/:id/deny` | active-device proof | `denied` or `mismatch` |
| `GET /v1/envelopes/self` | active-device proof | current envelope |
| `POST /v1/registry` | signing-device proof | atomic append of 1–2 entries + envelopes; `409 head_moved` |

The server enforces `validateAppend`, complete envelope sets (exactly the
active devices after the entry plus recovery, each `recipientEncPub` equal to
the registry's key), request state and expiry, and refuses a revoked device on
every proof route before reading anything. Bearer = the issuer's access token
(`aud` = the sync API, `typ` = `at+jwt`, ES256, first-party client).

### 5.4 Joining with existing local data (ADR Q5)

Phase 3a. Once enrolled, the device that leads for a database (one window per
database, or the headless brain) arms change capture and decides what to do
with the synced rows it already holds:

- **Seed**, on its own, when this device holds no synced rows or the account's
  op log is empty (the first device): every synced row gets field clocks
  synthesized as `hlc = (row.updatedAt ?? row.createdAt ?? now, 0, deviceId)`
  and goes into the outbox whole.
- **Ask**, when both hold data, with a preview (rows per table here, ops in
  the account's log):
  - **merge** (the default): seed as above; the account's ops then merge
    field by field (§9);
  - **replace**: delete this device's synced rows in a transaction capture
    ignores, then pull the account's log from 0.

Both change local data, so an encrypted ADR-0001 backup is written first and
recorded in backup history; a failed backup changes nothing. A headless host
takes the answer given ahead of time with
`cognia-agent account-sync data --merge|--replace`. A device removed and
joined again keeps its field clocks (still true orderings in the space) but
starts its cursor and sequence over. Phase 3b replaces "pull from 0" with the
latest snapshot plus the ops after it.

## 6. Sessions and live updates

Phase 3a. There is no separate session token: every call carries the bearer
token and the device proof of §5, as in phase 2.

1. `POST /v1/socket/ticket` (active-device proof) → `201 {ticket, expiresAt}`:
   32 random bytes, single-use, valid 60 s, bound to the space and the device.
2. WebSocket `GET /v1/socket?space=<spaceId>&ticket=<ticket>`. A browser cannot
   set headers on a WebSocket, so this route skips the bearer check: the
   Worker forwards it to the space, which consumes the ticket and refuses an
   unknown, used or expired one (`401 bad_ticket`) or a revoked device
   (`403 device_revoked`). The Durable Object accepts it with the hibernation
   API and sends `{type: "hello", lastSeq, registryHead}`.
3. The server sends `{type: "ops", lastSeq}` after every stored push and
   `{type: "registry", head}` after every registry append, so a connected
   device sees a waiting enrollment at once instead of on its next 20 s poll.
   The client sends `ping` every 30 s, answered `pong` without waking the
   object. A revoked device's sockets are closed with code `4403`.
4. Fallback: long-poll `GET /v1/ops?after=<serverSeq>&wait=25` while the
   socket is refused, drops or is unavailable (mainland China risk, ADR
   §Risks); the socket is retried with backoff meanwhile.

The socket only announces. Ops always arrive through the pull of §7.5.

## 7. Ops

### 7.1 Envelope

```
Op {
  deviceId, deviceSeq,         // deviceSeq: gapless per device, from 1
  hlc: { ms, c },              // the latest clock among the fields it carries
  epoch, schemaVer,            // schemaVer: the writer's sync schema version (§9)
  cls: "c"|"s"|"k"|"x"|"a",    // content, settings, secrets, crdt, append-only
  nonce, ct,                   // ct padded to the next bucket (§7.4)
  sig                          // ECDSA P-256 (P1363) by the device's signKey
}
opKey = HKDF(SK_epoch, salt = utf8(spaceId), info = label(op))
ct    = AES-256-GCM(opKey, nonce, pad(utf8(JSON(payload))), AAD)
AAD   = label(op)     ‖ 0x00 ‖ canonical(spaceId, cls, schemaVer, epoch, deviceId, deviceSeq)
sigIn = label(op-sig) ‖ 0x00 ‖ canonical(spaceId, deviceId, deviceSeq, hlc.ms, hlc.c,
                                          epoch, schemaVer, cls, nonce, ct)
```

`canonical(...)` is the concatenation, in the order given, of each field as
`u32-be length ‖ bytes` (integers as decimal ASCII, `nonce` and `ct` as their
base64url text). Table names travel inside `ct`; only the coarse class is
visible. Phase 3a writes `c` (content) and `s` (settings); the other classes
are reserved. A payload larger than 512 KiB before padding is not sent: the
row stays local and the device says so.

### 7.2 Plaintext payload

```
{ t: <table>, id: <rowId>, k: "upsert",
  f: { <field>: [<value>, <hlc>] },   // the fields this op writes, each with its clock
  u?: { <field>: [<value>, <hlc>] } } // fields from a newer schema, kept untouched (§9)

{ t: <table>, id: <rowId>, k: "delete", at: <hlc> }
```

Clocks are encoded HLCs (§9). Each field carries its own clock, so one op can
carry fields written at different times: the outbox keeps only *which* fields
changed, and the op is built at push time from the row's current values, which
coalesces a stream of writes (a reply being generated) into one op. Settings
travel as virtual rows `t: "settings", id: <key>` with the value in field `value`.
`k: "append"` and `k: "crdt"` (Yjs updates) are reserved.

### 7.3 Push

`POST /v1/ops` `{ops: Op[]}` (1–256 ops, ≤ 1 MiB body), active-device proof.
The DO:

1. refuses the push when the op log is over the read-only quota (§14);
2. checks every op comes from the pushing device with consecutive
   `deviceSeq`; ops at or below the device's last stored seq are acknowledged
   without storing (a resend after a lost answer), and a gap after it answers
   `409 seq_gap {expected}`;
3. checks every new op is under the registry's current epoch, else
   `409 epoch_stale {epoch}` (the client fetches the new key and re-seals);
4. verifies each `sig` against the device's registry `signPub`;
5. stores the new ops as **one SQL row** `{firstSeq, lastSeq, deviceId, at, bytes}`
   with a contiguous `serverSeq` range;
6. answers `{deviceSeq, firstSeq, lastSeq}` (`firstSeq`/`lastSeq` are `null`
   when nothing was new) and announces `{type: "ops", lastSeq}` (§6).

The client settles only the ops the answer says were stored, so a push whose
answer was lost and that is resent with newer ops never drops an op.

### 7.4 Padding

Plaintext is padded with a `0x80 0x00…` suffix to the next PADMÉ bucket
before encryption, so ciphertext lengths leak at most O(log log n) bits.

### 7.5 Pull

`GET /v1/ops?after=<serverSeq>[&wait=<0–25>]`, active-device proof →
`{batches: [{firstSeq, lastSeq, deviceId, ops}], more, lastSeq, registryHead}`:
whole batches in order, up to about 1 MiB or 64 batches (at least one). With
`wait` and nothing new, the answer is held until a push arrives or the wait
runs out. `after` is recorded as the device's acknowledged seq (used by 3b's
tombstone collection). Phase 3b adds `410 {snapshot: <manifestId>}` when
`after` is older than the compaction floor.

The client trusts the server for ordering only. It checks each op's signer
against its verified device list (a removed device's op counts only if sealed
under an epoch before its removal, and a device's epochs never go backwards),
verifies the signature, opens it with the epoch's key, then merges (§9) and
moves its cursor in one local transaction per batch.
It skips its own ops (already applied when written), and parks an op it
cannot apply yet (§9 schema skew, or an epoch key it does not hold) in a local
inbox as received, replaying it when it can.

## 8. Snapshots

- Only the holder of the `compaction` lease (§11) writes snapshots.
- Content: the materialized state at `upToSeq` (rows plus per-field clocks),
  chunked at 4 MiB, each chunk AES-GCM under the `snap` subkey with
  `AAD = label(snap) ‖ spaceId ‖ snapshotId ‖ chunkIndex ‖ chunkCount`.
- `PUT /v1/snapshots/{snapshotId}/chunks/{i}` streams to the blob store under
  a random key; `POST /v1/snapshots/{snapshotId}` registers
  `{upToSeq, epoch, schemaVer, chunks: [{key, size, sha256}], sig}`.
- The DO keeps the two newest snapshots and deletes op batches with
  `lastSeq < upToSeq − 10 000`.
- Tombstones (`isDeleted` rows) are dropped from snapshots only when every
  active device's acknowledged `serverSeq` is past them. A device not seen for
  90 days is marked `stale` and must restart from a snapshot.

## 9. Merge rules (client)

- HLC: `{ms, c}` (48-bit wall clock, 16-bit counter), encoded as `ms` in 12
  hex digits, `c` in 4, then the `deviceId`, so string order is clock order.
  `send = max(local, now)`, with the counter breaking ties within a
  millisecond; on receive, adopt `remote` only up to `now + 5 min`. A remote
  clock beyond that is applied but does not advance the local clock (a skewed
  device cannot win forever).
- Clocks are kept per row in the local side table `syncFieldClocks`
  (`[table+rowId] → {fields: {field: hlc}, tombstone?}`), never in the user's
  row.
- `upsert`: per field, the greater clock wins.
- `delete`: row-level. It records the tombstone clock and removes the row,
  unless the row holds a field written after it; then the row survives and
  the device that kept it re-sends the whole row, so a device that already
  removed it rebuilds it. An upsert older than the tombstone never revives
  the row; a newer one recreates it with every field it carries.
- Messages merge per field like other rows, not append-only: the app edits
  messages in place while a reply streams and in the image workbench.
- `local` fields (paths, runtime ids, the vector index, references to tables
  that do not sync yet) are never sent and never applied.
- Schema skew: a client parks, without applying, ops with a `schemaVer`
  greater than its own and shows "update Cognia to see changes from your other
  devices". Fields it does not know are kept in `u` with their clocks and
  re-emitted untouched on its next write of that row.
- Ops of a class the device switched off are passed over; switching the class
  back on re-seeds it and pulls from 0.

## 10. Blobs

- Blob id: `HMAC(blob-id subkey, SHA-256(plaintext))` → dedupe without revealing
  the plaintext hash.
- Each blob has its own random content key, carried inside the op that
  references it; content AES-GCM in 4 MiB chunks.
- `PUT /v1/blobs/{id}` (409 if present), `GET /v1/blobs/{id}`.
- Blob store interface: Cloudflare R2 binding, or any S3-compatible endpoint
  (self-host, §15).

## 11. Leases (execution placement)

```
POST /v1/leases/{resId}/acquire  {ttlMs: 30000}  → {generation, expiresAt} | 409 {holder, expiresAt}
POST /v1/leases/{resId}/renew    {generation}    → {expiresAt} | 409 lost
POST /v1/leases/{resId}/release  {generation}
```

- `resId = HMAC(res-id subkey, resourceName)`; resource names (`connector:<id>`,
  `schedule:<id>`, `session-turn:<id>`, `credential-refresh:<id>`,
  `compaction`) never reach the server.
- Renew every 10 s; generation is monotonic per `resId` and must accompany
  every externally visible effect so stale holders are fenced.
- Placement is client-side: on expiry, devices retry after
  `rank × 5 s` where rank follows headless → most recently active desktop →
  other desktops; a pinned resource is attempted only by its device. Phones and
  web never acquire execution leases.
- A device that cannot reach the DO stops a held resource when its lease would
  have expired and never self-grants.

## 12. Counters

`POST /v1/counters/{counterId}/next` → `{value}`; `counterId` is an HMAC like
`resId`. Used for human issue numbers (`issueCounters`).

## 13. Account lifecycle

| Action | Endpoint | Effect |
| ------ | -------- | ------ |
| Revoke device | `POST /v1/devices/{id}/revoke {wipe}` (signed record) | sockets closed; requests refused; revoker rotates the epoch |
| Remove this device | self-revoke with `wipe: true`, then local deletion | |
| Sign out | none (local) | outbox kept; resumes only for the same `spaceId` |
| Delete account | `POST /v1/account/deletion` → `{purgeAt: now + 7 d}`; `DELETE` cancels | DO alarm at `purgeAt` deletes DO storage, the blob prefix, and the IdP user; devices are told to unbind and keep local data as a plain local profile |

## 14. Quotas

Server-side, tunable. Defaults: op log + snapshots soft 2 GB, blobs soft
10 GB. Above soft: blob uploads `413 {code: "quota_blob"}`, ops still accepted.
Above soft × 1.25: everything but deletes refused (`413 quota_readonly`). The
client shows usage and a cleanup entry.

Phase 3a enforces only the op-log cap: above 2.5 GB of stored op bytes every
push answers `413 quota_readonly`. The server cannot tell a delete from other
ops inside `ct`, so deletes are refused too until 3b's compaction frees space.

## 15. Self-host

The same Worker runs under `workerd` with Durable Object SQLite on local disk
and the S3-compatible blob store (MinIO already ships with the diagnostic
server stack). Packaged as a profile in `deploy/compose`. Verify both claims in
the Phase 3 spike before relying on them.

## 17. Test vectors

`packages/sync-protocol/fixtures/` (a zero-`@/` package shared by the client and the Worker) holds the frozen
vectors: `v1.json` (canonical encoding, signatures, HPKE seals, the registry)
and `v1-ops.json` (HLC order, padding, canonical ops and AAD, a sealed op, merge). The client, the
Worker and any Rust consumer must all pass them. That is the only defense
against format drift (cf. the three grant-format copies today).
