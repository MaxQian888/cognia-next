# Local storage and database governance

<TLDR>
  Cognia uses several local stores. The account data database, browser credentials, Headless
  persistence, and native SQLite databases have different owners and recovery rules. The core table
  catalog governs CogniaDB tables; it is not a registry of every local database.
</TLDR>

## Core data and schema

`lib/db/schema.ts` declares `CURRENT_SCHEMA_VERSION` and the cumulative `CURRENT_SCHEMA`. The constructor registers one current schema declaration. The old append-only version chain is no longer the implementation: do not assume historical row migrations run on every open.

Database identity comes from the account/runtime initialization path. `cognia-claude` is the legacy/default constructor name, not the name of every account database. Use `lib/accounts/account-db.ts` and existing runtime selectors instead of inventing or renaming databases.

`lib/db/storage-layout.ts` checks the storage-layout marker before opening existing account data. A missing marker store, different layout, or newer schema is refused; the data stays on disk. Reset is a separate explicit user action. Lower schema versions within the supported layout can acquire new stores, but this does not transform old row shapes automatically.

The policy authority is `lib/data-governance/table-catalog.ts`: table role, protection, account scope, backup/sync participation, retention owner, cascade relationships, and query budgets. `docs/data-governance.generated.json` records current schema and sync coverage. Run:

```bash
pnpm db:governance:write
pnpm audit:data-governance
pnpm audit:data-governance:test
```

When adding a core table, extend the existing domain module, declare its row type and `Table` field, update `CURRENT_SCHEMA`, increase `CURRENT_SCHEMA_VERSION`, and register its policies in the catalog. Check backup, sync, deletion, and retention callers. Test supported reopening and failure behavior; a schema bump alone is not a data migration.

## Browser and mobile ownership

| Store family                                  | Source owner                                                                        | Governance boundary                                                                  |
| --------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Account content and dynamic plugin tables     | `lib/db/schema.ts`, `lib/plugin/dexie/`                                             | Account selection, content encryption, catalog policies, transactional domain writes |
| Account registry                              | `lib/accounts/account-db.ts`                                                        | Account metadata and binding/profile state; independent of content reset             |
| Runtime target registry                       | `lib/runtime/target-registry.ts`                                                    | Target definitions and active target per account                                     |
| Browser vault                                 | `lib/runtime/browser-vault.ts`                                                      | Credential material; do not treat it as a disposable cache                           |
| Target migration and mobile adoption journals | `lib/runtime/target-database-migration.ts`, `lib/companion/mobile-host-adoption.ts` | Resume/recovery evidence; not ordinary TTL data                                      |
| Quick unlock and browser keyring              | `lib/accounts/quick-unlock/device-pepper.ts`, `lib/keyring/index.ts`                | Device-bound unlock material and credential storage                                  |
| Wallpaper blobs                               | `lib/appearance/wallpaper-storage.ts`                                               | Separate raw IndexedDB storage                                                       |
| Companion pairing configuration               | `lib/tauri/companion-storage.ts`                                                    | Platform-specific secure storage and browser fallback                                |
| Persisted UI preferences                      | `stores/persist-storage.ts`                                                         | Web Storage adapter; not the authoritative account database                          |

The legacy scheduler adapter in `lib/scheduler/scheduler-db.ts` now accesses account data. Check its current implementation before treating SchedulerDB as a separate writable database.

## Headless durability and recovery

`cli/src/db/bootstrap.ts` restores the default per-table snapshot format: a manifest and one JSON file per table. Dirty-table flushing avoids serializing unrelated tables, but still reads and serializes the whole dirty table. Production snapshot-v3 file operations are asynchronous while keeping file-sync, backup, replacement and directory-sync ordering. Whole-table JSON serialization remains on the JavaScript thread; async file I/O does not make serialization incremental.

Snapshots use temporary files, file sync, a previous-generation backup, and replacement. Invalid or incompatible snapshots are quarantined. When the canonical file is absent and a quarantine generation remains, startup continues to refuse the store until a compatible canonical snapshot is restored; a supervisor restart must not turn corruption into a fresh empty database. A repaired canonical snapshot takes precedence over older quarantined generations.

The ledger path in `cli/src/serve/persistence/` has its own snapshot/journal and optional SQLite backends. Compaction must include commits accepted while the checkpoint is being prepared, preserve sequence continuity, and be awaited by shutdown. Backend selection is a separate runtime decision; changing its implementation does not switch an existing installation automatically.

| Scheduler metadata                              | `crates/cognia-scheduling/src/scheduler/metadata_store.rs`    |
| Workflow runs, waitpoints, cursors and events   | `crates/cognia-scheduling/src/workflow/run_mirror.rs`         |
| Integration spool and deadletters               | `crates/cognia-scheduling/src/workflow/integration_spool.rs`  |
| Task workspace registry, bundles and blob files | `crates/cognia-task-workspace/src/store.rs`                   |
| Per-plugin SQL and managed IDE state            | `crates/cognia-plugin-runtime/src/api_bridge.rs`              |
| Companion messages and sessions                 | `src-tauri/src/companion_api/store.rs`                        |
| Companion security state                        | `src-tauri/src/companion_api/security_store.rs`               |
| Signaling registrations                         | `src-tauri/src/companion_api/signaling/registration_store.rs` |
| RPC idempotency receipts                        | `src-tauri/src/companion_api/idempotency.rs`                  |

The integration spool shares the workflow mirror database path. Companion AppStore and SecurityStore can also share a file. Count owners and files separately; changing connection settings can affect another owner. WAL does not make operations parallel when callers still share one connection mutex.

External agent-session, CCSwitch, and browser-cookie imports read databases owned by other applications. They are outside Cognia's write/retention authority.

Native vector Tauri commands dispatch database initialization, SQLite work, mutex waits and filesystem metadata through a blocking worker. Cloned `VectorState` values share the same lazy store and reset lock. This protects the async executor; it does not parallelize the underlying connection or change search results. Already-started work continues if its caller cancels the wait.

## Deletion and retention

Use the domain deletion entry points, including `lib/db/sessions.ts` and `lib/db/project-scope.ts`. Deleting parent rows must also clean their owned projections and references in a transaction and record applicable sync tombstones. Ordinary conversation branches and shared media have independent ownership.

Media cleanup uses reference hashes and the existing grace period in `lib/db/message-media-refs.ts`. A small candidate list must not scan the entire media library. A failed post-commit garbage collection must not report that an already-committed parent deletion rolled back.

Draft revision allocation and writes share a transaction with the parent/deletion-marker check. An optimistic draft may precede its parent; a known-deleted missing parent cannot receive a late draft. Unread writes require an existing parent. Project deletion captures membership and commits deletion markers in the same transaction, including rollback if the markers cannot be written.

The governed tombstone sweep reconciles historical draft, unread, input-history, transcript and media-reference rows only when an explicit session deletion marker exists and both the session and its message history are absent. It reads marker pages of 250 and candidate blobs individually. Shared media, in-flight upload grace periods and retry evidence survive; a missing parent without a marker is preserved. Markers normally expire after 90 days; unfinished reconciliation keeps the evidence it still needs. No database scan is run merely by editing this code.

Plugin SQL uses one cached connection per plugin. Host-owned managed IDE state has a separate cache and file, with existing scope partitions. Both caches reject a locked/unbound account and clear on account change and teardown. This prevents stale cache reuse; it does not cancel SQL that already obtained a connection.

`lib/storage/retention.ts` runs existing retention executors. Extend the owning policy/executor when adding high-write tables. Audit history, deadletters, migration journals, and consumed upload receipts are not automatically disposable: document retention and retry requirements before pruning them.

## Performance and validation

- Use indexes and bounded pages on interactive reads; loading a whole encrypted table also pays decode/decrypt costs for every row.
- Prepare batch SQLite statements once within the transaction, while retaining rollback and payload/vector consistency.
- Test overlapping writes, shutdown, failed writes, recovery retries, shared references, and account boundaries.
- Measure controlled before/after fixtures separately from real desktop/mobile latency. Unit tests and temporary SQLite benchmarks do not establish end-user performance.
