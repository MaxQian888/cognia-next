# Unified Subscription

<Status variant="stable">Stable · ADR-0025 · vault schema v4</Status>

<TLDR>
  Built-in and registered subscription providers — including Anthropic, Codex, OpenCode, and CommandCode — share one account model, one vault format
  and one limits surface. The interesting piece is the **limits-source registry**
  (`lib/subscription/limits/registry.ts`): a flat ordered list where windowed sources come *before* the
  generic balance source, so the runner prefers a real utilization window and only falls through to a
  credit meter when no window applies. Aggregation (`limits/aggregate.ts`) queries every configured
  account and returns them with the active one pinned first — which is what both the TUI `/limits` panel
  and the desktop multi-provider view consume. Every seam is injected, so the same code runs offline in
  tests and in the CLI with a Node-`fetch`-backed `authedGet`.
</TLDR>

## Order is the design

A "limit" can mean two different things: a rolling utilization window (Anthropic, Codex) or a credit
balance (most OpenAI-compatible resellers). Presenting a credit meter when a real window exists would be
a downgrade, so the registry encodes the preference as list order — windowed sources first, the generic
balance source last. The runner walks the returned candidate list and stops at the first source that
yields a snapshot.

Plugin-contributed sources overlay in front of the built-ins, resolved through
`lib/plugin/registries/limits-source-registry.ts`. The registry itself is pure: a list plus a resolver
that returns *every* matching source rather than picking one, which keeps the fallback decision in the
runner where it can be tested.

## Adding a provider without adding a new integration

The account panels consume one registry (`core/provider-registry.ts`). Account Center, onboarding,
chat and character account selectors reuse the same dispatcher and managed-key form. For a standard
OpenAI Chat Completions or Anthropic Messages service, choose **Add custom service** and enter its
name, API base URL, protocol, model IDs, and API key. Endpoint/model metadata uses the existing custom
provider settings; the key goes only into the local account's encrypted subscription vault.

A plugin can contribute the same metadata through `subscriptionProviders[]` with the
`subscription-provider` capability; the TypeScript SDK provides `defineSubscriptionProvider`.
The host namespaces its ID as `pluginId:providerId`, registers its model catalog, and supplies the
account form, presets, default-account selection, credential resolution, and encrypted backup.
Disabling the plugin removes its setup and model registration while keeping stored accounts available
for inspection/removal. Encrypted backups include custom service definitions, but do not reactivate plugins.
See the [manifest reference](../../plugin-dev/manifest) for a declaration example.

The declaration supports API-key authentication with the two standard protocols. OAuth, token refresh,
CLI discovery, a vendor-specific wire protocol, and live quota queries still require their existing
host adapters or separate quota extensions. No login flow or quota endpoint is inferred from a name.

## CommandCode API subscriptions

CommandCode GOAT, Pro, Max, Team, and Provider plans connect with the API key from
[Settings → API Keys](https://commandcode.ai/settings/keys). The Go plan is CLI-only and cannot use
this integration. Add an account from Account Center, the subscription settings, onboarding, or the
chat/character account picker. These entry points share the same key dialog and endpoint-preset binding.
Keys stay in the encrypted subscription vault; account selection, editing, activation, removal,
encrypted export/import, and synchronization use the existing account lifecycle.

The official base URL is `https://api.commandcode.ai/provider/v1`. Claude models use Anthropic Messages
(`/messages`); other models use OpenAI Chat Completions (`/chat/completions`). This selection applies to
chat, compaction, feature model calls, and the local Gateway. A bound preset takes precedence over the
account URL and may supply custom headers such as `x-cmd-zdr: 1`; internal `x-cognia-*` headers are excluded.

Model discovery uses the public `/models` endpoint. Connection testing makes a minimal authenticated
generation request and may consume a small amount of plan credits; fetching the public model list alone
cannot validate a key. No public quota API is documented, so the UI directs users to CommandCode Studio
for usage instead of displaying an invented balance. OAuth and CLI credential discovery are not exposed.

Verified against the [official Provider API documentation](https://commandcode.ai/docs/provider)
on 2026-09-11.

## Account Center and credential boundaries

### Subscription and relay behavior (2026-09-11)

Account Center, onboarding, express sign-in, and the Anthropic provider reuse entry share the same
provider account dialogs. Managed Anthropic, Codex, and OpenCode accounts can choose an existing
endpoint preset while being added and change that binding later. External OpenCode discovery pointers
remain read-only. Anthropic subscription/Console sign-in is OAuth; vendor API and Coding Plan keys
belong in the existing Providers configuration, not in an invented OAuth credential.

An account's bound preset wins; otherwise queries use the vault's actual default preset. Merely having
another preset in the library never selects it. Limits snapshots retain the vault `provider` and
`accountId` as their storage identity and carry `sourceId` for the actual quota or balance adapter.
One failing account cannot discard the other accounts or prevent independent custom sources from
being queried. Custom sources use unique IDs across editor mounts and preserve every quota window
and request header when edited.

Codex and OpenCode chat bridges forward preset request headers, excluding internal `x-cognia-*`
configuration. Codex's selected ChatGPT identity remains authoritative. OpenCode chat and compaction
requests identify Cognia and carry the same conversation ID in `x-opencode-session`, following the
[OpenCode Go client contract](https://opencode.ai/docs/go/#where-can-i-use-it). Go is intended for coding
agent traffic; this integration does not imply unrestricted general API use or vendor certification.
Endpoint/header configuration is documented in the
[Codex configuration reference](https://developers.openai.com/codex/config-reference/) and
[OpenCode provider documentation](https://opencode.ai/docs/providers/).

Subscription vault commands are `client.local` / `internal` in the current Companion command manifest.
Web and mobile clients therefore show desktop-management guidance rather than receiving vault secrets
through generic RPC. Sanitized remote provider diagnostics are a separate capability under ADR-0104.
Provider documentation was checked on 2026-09-11; offline tests do not certify live quota endpoints.

Settings → Subscription → Accounts is the only account CRUD surface. Claude, Codex, and OpenCode
provider pages keep provider-specific usage, probe, and routing controls; they do not duplicate account
mutation controls. “Active now” projects one credential into the provider runtime. “Default for new
sessions” is a resolver fallback and does not activate or rewrite a running tool.

The list and detail panes consume `AccountSummary` / `AccountDetail`, which cannot serialize access
tokens, refresh tokens, ID tokens, or API keys. Settings mutations are scoped operations: rename,
preference changes, credential replacement, identity-safe Codex reauthentication, and local removal.
Secret-bearing full-account resolution remains confined to runtime consumers and explicit encrypted
backup/export flows.

Vault schema v4 adds non-secret Codex identity facts and lifecycle state. Codex refresh is host-owned,
single-flight per account, atomically persists rotated access/refresh/ID tokens, and shares a lifecycle
lock with removal. A targeted reauthentication may replace an account only when the stored and incoming
workspace plus subject match. Legacy accounts without a verifiable fingerprint fail closed and must be
added separately. Terminal refresh errors persist `reauth_required`; transient network failures remain
retryable and do not invalidate the account.

<Callout type="warn">
  “Deactivate” only clears Cognia's active projection. “Remove from Cognia” only deletes the local vault
  entry and migrates Cognia references. Neither operation revokes an upstream token, logs out an external
  CLI, edits CCSwitch, or changes an external credential file/keychain entry. OpenCode and other external
  credential representations are read-only until the user explicitly creates a Cognia-managed copy.
</Callout>

The v3 → v4 migration is a pure payload migration: it derives an optional fingerprint only from the ID
token already present in the supplied vault payload. It performs no host discovery, keychain lookup,
configuration-file read, or network request.

## Export is encrypted with the backup primitives

`core/encrypted-package.ts` reuses the same crypto as the Dexie-wide backup in `lib/data/` —
PBKDF2-SHA256 at 600,000 iterations plus AES-GCM-256 — but ships a simpler envelope sized for just the
registered provider vaults (`SUBSCRIPTION_PACKAGE_VERSION = "subscription-v1"`). The smaller payload keeps
backup files readable in tooling and makes it obvious which vaults are inside.

<Callout type="warn">
  Writes must go through the settings store, not straight to Dexie. Bypassing it leaves the in-memory
  store stale — a real bug that has been fixed once already in the ccswitch path.
</Callout>
