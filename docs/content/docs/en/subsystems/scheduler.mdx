# Scheduler

<Status variant="stable" />

<TLDR>
  Two-layer scheduler — an in-app cron loop for tasks that only matter while Cognia is open, and a
  native promotion path that mirrors selected tasks to Windows Task Scheduler / launchd / systemd so
  they fire even when the app is closed.
</TLDR>

Cognia ships its own scheduler subsystem that runs in two layers:

- **In-app layer** — `lib/scheduler/` runs cron-defined tasks while the app is open.
- **Native layer** — `src-tauri/src/scheduler/` promotes tasks to the OS scheduler (Windows Task Scheduler, macOS launchd, Linux systemd) so they fire even when Cognia is closed.

Promotion is opt-in per task: lightweight tasks stay in-app; heavy or background-required tasks go native.

The full design rationale is in [ADR-0002](../adr/0002-scheduler-full-agent-resolution).

The `Trigger` and `Executor` shapes:

```ts
type Trigger =
  | { type: "cron"; expression: string; timezone?: string }
  | { type: "interval"; everyMs: number }
  | { type: "once"; runAt: string }
  | { type: "event"; eventName: string }

type Executor =
  | { type: "claude-send"; characterId: string; messageTemplate: string }
  | { type: "shell"; command: string; cwd?: string }
  | { type: "script"; language: "js"; code: string }
  | { type: "backup"; folder: string }
  | { type: "twin-ingest"; sourceId: string }
  | { type: "twin-distill"; twinId: string }
  | { type: "plugin"; pluginId: string; jobId: string }
```

The full type set lives in `lib/scheduler/`. Adding a new executor means adding a discriminated-union member and an implementation file under `executors/`.

## Cron parser

`lib/scheduler/cron-parser.ts` implements a 5- and 6-field cron parser (with seconds when 6 fields are given). Features:

- Standard wildcards (`*`, `,`, `-`, `/`).
- Named day-of-week (`MON`, `TUE`, …).
- Named month (`JAN`, …).
- Time zone aware via the trigger's `timezone` field; defaults to system local.

The parser produces a `next(after: Date)` iterator. The scheduling loop calls `next()` to compute the next fire time, sleeps until then, runs the executor, and repeats.

Tasks default to `promoted: false`. The user can promote a task in the workbench; promotion synthesises:

- **Windows** — a Task Scheduler entry pointing at `cognia.exe --workspace <id> --task <task-id>`.
- **macOS** — a launchd `.plist` in `~/Library/LaunchAgents/`.
- **Linux** — a systemd `.timer` + `.service` unit pair under `~/.config/systemd/user/`.

`metadata_store.rs` keeps the link between the task UUID and the native task ID (PowerShell task name, plist label, systemd unit name). On task delete, the metadata store also removes the native entry.

## Tab lock

`lib/scheduler/tab-lock.ts` ensures **exactly one tab** runs the in-app loop. Implementation:

- A heartbeat row in Dexie (`schedulerLock`) updated every 5s.
- On startup, every tab checks: if the heartbeat is older than 15s, claim the lock; otherwise sleep.
- If the holder tab closes / crashes, the next tab claims within 15s.

This prevents duplicate fires when the user has Cognia open in multiple windows.

## Conversational task authoring

`conversational-task-authoring.ts` and `conversational-task-intent.ts` let the user describe a schedule in plain language ("every weekday at 9 send a stand-up reminder") and have the LLM emit a `ScheduledTask` JSON object. The intent extractor pulls structured fields; the authoring agent fills in defaults and validates.

This surfaces in the workbench's "Create with AI" panel.

## Executors

`registerBuiltInExecutors()` in `lib/scheduler/executors/index.ts` registers every built-in executor. All chat-like types (chat / agent / skill / goal / plan / agent-team) go through the same `resolveSendOptions` pipeline the interactive composer uses, so a scheduled prompt has exactly the semantics of a manual send.

| Type                                                     | Purpose                                                                                                        | Key dependency                                                                          |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `chat` / `agent` / `skill`                               | Run one Claude turn (optionally with a bound persona / one-shot skill)                                         | `lib/claude/ipc.sendPrompt` + `resolveSendOptions`                                      |
| `goal` / `plan` / `agent-team`                           | Advance a goal, run a plan, or launch a built-in team                                                          | ADR-0019 / ADR-0022 runtimes                                                            |
| `external-agent`                                         | Hand the task to an ACP external agent (Claude Desktop, Cursor, …)                                             | `lib/ai/agent/external/manager.executeOnExternalAgent`                                  |
| `script` / `background-command` / `monitor`              | Run a user script or command through the host shell                                                            | `script-executor.ts` (`shell_exec` on desktop, jobs supervisor on headless)             |
| `workflow`                                               | Run a published visual workflow with `triggeredBy.source = "schedule"`                                         | `executeDeployedWorkflow` (ADR-0011)                                                    |
| `im-push`                                                | Push a message into a bound IM conversation through the governed outbound queue                                | `enqueueGoverned` + `hasNoLeakingPii` + per-conversation `proactivePush` opt-in         |
| `backup`                                                 | Build + encrypt a snapshot and fan it out to every configured destination (local, WebDAV / S3, GitHub, Drive)  | `lib/data/destinations/`, `lib/data/backup-host-filesystem.ts`                          |
| `wiki-rebuild` / `wiki-lint`                             | Rebuild / lint the wiki (needs a host filesystem)                                                              | `lib/wiki/rebuild-runner.ts`                                                            |
| `plugin`                                                 | Fire a plugin-registered scheduled job (see [Plugin system](./plugin-system))                                  | `executors/plugin-executor.ts`                                                          |
| `twin`, `connection:*`, `github-issue-sync`              | Card-authored types (created by their own subsystem, not by the form)                                          | their subsystem                                                                         |
| `test`                                                   | Diagnostic: echoes its payload to validate the trigger chain end-to-end on any host                            | `executors/test-executor.ts`                                                            |
| `custom`                                                 | Fails with `EXECUTOR_NOT_FOUND` unless a handler was registered                                                | `registerTaskExecutor("custom-<name>", fn)`                                             |
| `sync`, `ai-generation`                                  | **Deprecated** — no executor; existing rows are auto-paused at init and labelled in the detail view            | —                                                                                       |

Each executor returns:

```ts
interface TaskExecutorResult {
  success: boolean
  output?: Record<string, unknown>
  error?: string
  /** "unsupported-on-host" | "deprecated-type" | "executor-not-found" | … */
  terminalReason?: string
}
```

Results are written to `schedulerHistory` (capped at 200 newest per task).

## Which host runs a task (ADR-0128)

Placement is **host-owned**: the desktop, the headless brain (`cognia-server`), and a web / companion webview each keep their own `CogniaSchedulerDB`, and nothing hands tasks between hosts. What differs is which types a host can *run*. `lib/scheduler/host-support.ts` declares the requirement per type; the executor refuses with a structured `unsupported-on-host` result, and the task form shows unsupported types **disabled with the reason** (never hidden).

| Type                                                     | Requires            | Desktop | Headless brain | Web / companion webview |
| -------------------------------------------------------- | ------------------- | ------- | -------------- | ----------------------- |
| `chat` `agent` `skill` `goal` `plan` `agent-team`        | `sidecar`           | ✓       | ✓              | ✗                       |
| `external-agent` `script` `background-command` `monitor` | `shell`             | ✓       | ✓              | ✗                       |
| `backup` `wiki-rebuild`                                  | `host-filesystem`   | ✓       | ✓              | ✗                       |
| `im-push`                                                | `connector-runtime` | ✓       | ✓              | ✗                       |
| `workflow` `test` `plugin` `custom` (with handler)       | —                   | ✓       | ✓              | ✓                       |
| `system` (native OS tasks)                               | `desktop-shell`     | ✓       | ✗              | ✗                       |
| `sync` `ai-generation`                                   | deprecated          | paused  | paused         | paused                  |

Timing drivers follow the host too: the Rust daemon on Tauri, `NodeTimingDriver` on headless, the renderer loop + tab lock on web / mobile.

**Which schedule the page manages.** A client can look at two schedules: `local` (this device) and `paired` (the host it drives or is paired with, via the `scheduled_task_*` companion RPCs). Companions and a desktop driving a remote host default to `paired`; the scheduler page's **host bar** says which one you are managing and lets you switch (`lib/scheduler/scheduler-host-target.ts`). The type picker resolves the *target* host's capabilities through the `host_capabilities` RPC.

**Headless bridges.** Workflow triggers on the brain arrive through the Companion `subscribe` control frame (`lib/headless/runtimes/workflow-trigger-bridge.ts`); toast / OS notifications raised on the brain are published once through `remote_notification_publish` and ingested into the local notification center by connected clients (`lib/notifications/remote-subscription.ts`).

**OS promotion is wake-and-delegate.** A promoted task's native entry opens `cognia://scheduler/task/<id>?run=<token>`; the app verifies the token and runs the task through the ordinary in-app executor, so promoted and in-app runs never diverge. Headless hosts do not promote (they are always on).

## Notifications

`notification-integration.ts` watches the scheduler-history stream and surfaces:

- A toast on every run (configurable, default "errors only").
- A native OS notification on failure (via `tauri-plugin-notification`).
- A badge in the menu / system tray when there are unread failures.

## Event triggers

A task can also fire on app events (e.g., "every time a new chat is created"). `event-integration.ts` subscribes to the event bus and triggers the matching tasks.

## Workbench UI

Route: `app/scheduler/`. Components: `components/scheduler/`. Tabs:

- **Tasks** — list, with quick toggle / promote / run-now / delete actions.
- **History** — combined run history across all tasks, filterable by status.
- **Templates** — pre-defined task templates from `task-templates.ts` (e.g., "Daily backup", "Weekly twin re-distill").
- **Authoring** — the "Create with AI" panel.
