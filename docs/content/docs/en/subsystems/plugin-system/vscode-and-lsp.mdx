# VS Code extensions & LSP

<Status variant="experimental" />

<TLDR>
Cognia runs **real** VS Code extensions as plugins on the desktop. A `.vsix` from Open VSX (signature checked against a pinned key) or a dropped file (trusted by the user, one extension at a time) is unpacked by the Rust runtime into `<data>/cognia/vscode-extensions/<id>`, and its manifest is adapted into a Cognia `PluginManifest`. Each running extension gets its own Node host (`sidecar/vscode-ext-host`) that mounts the VS Code 1.91 API. The host's calls reach the renderer as JSON-RPC and land on Cognia's own services: Monaco for language features, the terminal dock for terminals and tasks, the extension rail for webviews, the configured AI provider for `vscode.lm`. What Cognia does not provide (debug, SCM, notebooks, tests, comments, menus, keybindings, tree views, ESM bundles) is declared, shown on the plugin's page, and refused with a reason. Browser and mobile builds cannot run extensions.
</TLDR>

## 1. Where things live

| Layer | Path | Owns |
| --- | --- | --- |
| Rust runtime | `crates/cognia-plugin-runtime/src/vscode/` | install (`installer.rs`), Open VSX download and signature check (`openvsx_download.rs`), host processes (`host.rs`), Mementos (`memento.rs`), the Tauri commands (`commands.rs`, behind `tauri-host`) |
| Extension host | `sidecar/vscode-ext-host/src/` | `host.ts` (JSON-RPC on stdio), `extension-runner.ts` (sandbox and lifecycle), `require-hook.ts` (module gate), `vscode-shim/` (the API, one file per namespace) |

## 2. Install

Every install goes through `install-vscode-extension.ts`, so manifest adaptation cannot be skipped.

- **Open VSX** (`openvsx-install-flow.ts`). The Rust command `plugin_vscode_download_vsix` downloads the `.vsix` and its SHA-256, and checks the `.sigzip`: a raw Ed25519 signature over the whole file, verified against Open VSX's key, which is pinned in Cognia (`OPENVSX_SIGNING_KEY`), never read from the registry. A signature that does not match, or one the registry advertises that cannot be read, stops the install. A verified download is remembered in the Rust state, and installing it writes a `signature` verification receipt. The marketplace card shows **Signed by Open VSX**.
- **Dropped `.vsix`** (desktop only). It is installed with no receipt, and the dialog says it will need trust before it starts. Outside the desktop app the drop is refused with a message.
- **Development folder**. Trusted as the user's own code.

The renderer side (`vsix-installer.ts`) unpacks `extension/`, and `manifest-adapter.ts` maps `package.json` to a `PluginManifest`:

- id `publisher.name`, `type: "vscode-extension"`, `vscodeMain`, and the `vscodeExtension` block (`VsCodeExtensionBlock`) with the raw activation events, bundle format, contributed commands, configuration schema, `unsupportedContributions` and `unsupportedApis`;
- permissions inferred by `permission-inference.ts` (a Babel AST walk with a minified-code fallback): `fs` → `filesystem:read/write`, `child_process` → `process:spawn` + `shell:execute`, `http`/`https` → `network:fetch`, `net`/`ws` → `network:websocket`, `vscode.tasks.executeTask` → `terminal:spawn`.

The Rust installer writes the unpacked files to `<data>/cognia/vscode-extensions/<id>` and discards any verification receipt shipped inside the archive. Each extension's storage, Mementos and log live apart from the install, in `<data>/cognia/vscode-extension-state/<id>/{global,workspace/<hash>,log}`, so they survive updates and reinstalls. Uninstall removes the install directory, and backups include both.

### Trust before start

`PluginManager` does not run VS Code extensions through the Cognia plugin signature check (no VS Code extension carries a Cognia signature). Instead `requireVscodeExtensionTrust` lets one start when:

- its install has a `signature` receipt from a verified Open VSX download, or
- it comes from a development folder, or
- the user trusted it (the **Trust this extension** switch on its Permissions tab).

Otherwise enabling it fails with `PluginFrontendTrustError` (`reason: "unsigned-vscode-extension"`), which the plugin list shows as "trust this extension first". Extensions installed before receipts existed need to be trusted once.

## 3. Running an extension

`vscode-loader.ts` builds the plugin definition. A theme, grammar, icon theme, snippet or language-only extension runs in the renderer and starts no host. Anything with `main` is started through `plugin_activate_vscode`:

1. Rust spawns `host.js` for that one extension (`COGNIA_VSCODE_EXTENSION_ID`) with the user's proxy in its environment (proxy changes apply when the host restarts).
2. `extension:load` sends the install path, `main`, the bundle format and `grantedModules`: the sensitive Node modules the extension's live permissions allow (`commands.rs:granted_node_modules`).
3. `require-hook.ts` answers `require("vscode")` with that extension's API object and refuses any sensitive module (`fs`, `child_process`, `worker_threads`, `http`/`https`, `net`/`tls`, `ws`) not granted, with `EPERM`. A `require` is attributed by where the requiring file lives, so an extension's own `node_modules` (including a bundled `vscode-languageclient`) is gated as the extension.
4. `extension-runner.ts` runs the CommonJS bundle in a `vm` context with `queueMicrotask`, `structuredClone`, `AbortController`, `performance`, `atob`/`btoa`, `crypto` and a `process` that cannot exit the host. `fetch` and `WebSocket` work only with `network:fetch` / `network:websocket`, checked per call. ESM bundles are refused with a reason.
5. Before `activate`, the renderer sends the workspace folders, configuration, installed extensions and window state, and the host awaits them.

**Activation** (`activation-triggers.ts`). An enabled extension starts at launch only for `*`, `onStartupFinished` or contributed views. Otherwise it stays dormant while its contributed commands and languages are listed, and starts on `onCommand:<id>` (then runs the command), `onLanguage:<id>` (an editor opens a document of that language), or `workspaceContains:<glob>` (checked when it becomes dormant and when folders change). Other activation events are recorded as unsupported.

**Crashes** (`host-supervisor.ts`). Rust reports `host:exited` with the stderr it collected (stderr also goes to the plugin log). The supervisor reloads the extension after 1 s·2ⁿ, capped at 30 s, gives up after `MAX_RESTARTS` (5) and forgets earlier crashes after five minutes up. A host that gives up leaves the plugin in an error state until the user enables it again.

**Output channels** and the host's own warnings go to the plugin's runtime log, which the plugin pane links to.

## 4. The API and what backs it

The host mounts the VS Code 1.91 API (`sidecar/vscode-ext-host/src/vscode-shim/index.ts`). `scripts/gates/vscode-api-coverage.mjs` diffs `@types/vscode` against it into `vscode-api-coverage.generated.json` (`pnpm audit:vscode-api-coverage`): every member is implemented or listed as unsupported with a reason, and none is missing. `engine-compat.ts` reads the same report to warn about extensions that use unsupported namespaces. That warning is advisory and never blocks an install.

Calls the host makes arrive as `vscode://rpc/<pluginId>` events. `rpc-dispatcher.ts` routes them by method to the handlers `setup-handlers.ts` installs, and replies through `plugin_vscode_send_response`. Every handler checks the request is the calling extension's own.

| API | Renderer side | Backed by |
| --- | --- | --- |
| `languages.*` providers, diagnostics, language configuration | `languages-handler.ts`, `monaco-bridge.ts`, `monaco-results.ts` | Monaco (see section 5) |
| documents and editors | `document-sync.ts`, `editor-handlers.ts`, `workspace-document-handlers.ts`, `file-doc-pool.ts` | Monaco models, confined file reads and `applyEdit` writes |
| messages, quick pick, input box, progress, status bar, dialogs | `window-handlers.ts`, `window-ui-store.ts`, `native-dialogs.ts` | `components/plugins/vscode/` presenter, toasts, `statusbar.*` slots, Tauri dialogs |
| `window.state`, `activeColorTheme` | `window-environment.ts` | window focus and activity (inactive after 10 s idle), the app theme |
| terminals, `Pseudoterminal` | `terminal-handlers.ts`, `extension-pty-session.ts` | tabs in the terminal dock |
| tasks | host `tasks.ts`, `lib/plugin/commands/tasks-registry.ts` | shell and process tasks run in a dock terminal, custom executions in an extension terminal |
| webview panels and views | `webview-handlers.ts`, `webview-bridge.ts`, `webview-document.ts` | the extension rail, sandboxed frames with `acquireVsCodeApi()` |
| `workspace.fs`, `findFiles`, file watchers, folders | `workspace-file-handlers.ts`, `root-watchers.ts` | file access confined to project folders, `filesystem:read/write` |
| configuration | `configuration-handlers.ts`, `vscode-configuration-schema.ts` | each plugin's config store, `contributes.configuration` defaults |
| `extensions.all/getExtension`, `activate()` | `extensions-handlers.ts` | the plugin manager |
| commands | `runtime-handlers.ts` | `lib/plugin/commands/registry.ts` (contributed titles, categories, `when`) |
| `env` (clipboard, `openExternal`, `asExternalUri`, URI handler) | `env-handlers.ts` | Tauri clipboard and opener, Cognia deep links |
| `vscode.lm` | `lm-handler.ts` | the provider and model the user configured, as vendor `cognia`, streaming. Needs `ai:chat`, the plugin rate limit and the PII gate. Extensions never bring their own key |
| `vscode.chat` participants | `chat-participant-registry.ts` | registered as virtual characters (`vscode-chat:<pluginId>:<id>`). Not invoked yet |
| secrets, Mementos | `runtime-handlers.ts`, `memento.rs` | the secret store, files in the extension's state directory |

`unavailable-methods.ts` lists host methods the renderer cannot serve. It is empty while every method is backed.

## 5. Language features

**Providers.** `vscode.languages.register*Provider` sends `languages:register` with a token the host minted. `languages-handler.ts` looks the kind up in `PROVIDER_REGISTRY` (28 kinds, kept equal to the host's list by its test) and registers it with Monaco. When Monaco asks, `monaco-bridge.ts` sends `extension:call {extensionId, token, method, callId, payload}` back to that host. Disposing the registration unregisters it.

**Documents.** `document-sync.ts` keeps each host's documents in step with Monaco (`workspace:documentOpened/Changed/Closed`, `window:editorsChanged`). The host keeps them as real `TextDocument`s, and a provider call made against a newer version waits for that edit. Cancellation from Monaco reaches the provider's `CancellationToken`.

**Diagnostics.** A `DiagnosticCollection` sends `languages:setDiagnostics` / `clearDiagnostics`, which become Monaco markers.

**Language servers in extensions.** Most language extensions use `vscode-languageclient`. It runs unchanged: its `child_process` is the extension's `process:spawn`, the server process is the extension's own, and the client's providers and diagnostics take the path above. `tests/host-languageclient.test.mjs` runs a real `vscode-languageclient` against `tests/fixtures/echo-lsp.mjs` on the built host, with the client's dependencies copied into the fixture the way an unbundled extension ships them, and checks the registrations, the server's diagnostics, completion and hover.

**Grammars, themes, snippets, languages.** Contributed languages are registered with Monaco (`contributed-languages-monaco.ts`). Themes and icon themes go through the theme bridges. Grammars color code in chat and previews (`grammars-bridge.ts`, Shiki), not in the Monaco editor. A dormant extension's grammars, themes and snippets appear once it runs.

## 6. Not supported (labelled)

Each item is typed, shown in the plugin detail's **VS Code compatibility** section (`plugin-vscode-compat-section.tsx`), and pinned by tests.

**Contributions** (`VsCodeUnsupportedContribution`, from `manifest-adapter.ts:vscodeUnsupportedContributions`):

| Value | Meaning |
| --- | --- |
| `debuggers` | `contributes.debuggers` / `breakpoints`. Cognia has no debugger |
| `notebooks` | `contributes.notebooks` / `notebookRenderer` |
| `menus` | menu entries other than `commandPalette`. The commands still run from the command lists |
| `keybindings` | no shortcut is bound |
| `views` | tree views, view containers, welcome content. Only webview views are shown, in the extension rail |
| `editor-grammars` | grammars color chat and previews, not the code editor |
| `extension-pack` | the listed extensions are not installed with it |
| `esm-bundle` | an ES module bundle cannot start. The host loads CommonJS, as VS Code 1.91 does |

**API namespaces** (`unsupportedApis`, found in the extension's code): `debug`, `scm`, `tests`, `comments`, `notebooks`. Their registrations return inert disposables, their events never fire, and calls that would act throw `NotSupportedError` with the reason. The host reports each unsupported member once per extension (`vscode:unsupportedApi`), and the plugin log names it.

**Other gaps:** chat participants are registered but not invoked, task problem matchers are ignored, and `createTelemetryLogger` sends nothing. `Terminal.processId` is the shell's process id for a terminal running on this machine, and `undefined` for an extension's `Pseudoterminal`.

**Browser and mobile.** There is no extension host. The Open VSX origin is hidden, a dropped `.vsix` is refused, and an installed extension with `main` loads as a stub that marks itself in the plugin list.

## 7. Cognia's own language servers

Separate from extensions, the editor runs language servers the user or project configures (`lib/plugin/lsp/`):

| File | Role |
| --- | --- |
| `lsp-bootstrap.ts` | `bootstrapLspRegistry` layers builtin ← `settings.lsp` ← project `.cognia/lsp.json`, and follows settings and project changes |
| `lsp-user-servers.ts` | `editorEligibleServers` drops pure builtins (agent-only, to avoid noisy "crashed" states), `syncUserLspServers` registers the rest |
| `lsp-registry.ts` | `registerLspServer` / `registerPluginLspServers` (servers a plugin manifest declares), keyed `${ownerId}:${serverId}` |
| `lsp-client-adapter-tauri.ts` | `TauriLspClientAdapter` over the one `cognia.lsp-service` channel, multiplexed by owner. Routes `lsp:publishDiagnostics` to Monaco markers |
| `lsp-monaco-runtime.ts` | `registerLspMonacoProviders` registers only the providers an initialized server declared |
| `vscode-shim/lsp-binary-policy.ts` | `evaluateLspBinary` gates a plugin-declared server binary |

**Binary policy.** A binary outside the plugin's install directory always prompts. One inside prompts until the user approves that exact `(pluginId, path)`, and again if its SHA-256 changes. The plugin's own claims about its publisher are never evidence. `settings.lsp.unsignedAllowed` (dev) turns a prompt into allow-with-prompt. Every decision is written to `automationAuditLog`. User-added servers are registered with `confirmedConsent: true`, as the user configured them.

This policy covers servers Cognia spawns. A server an extension starts itself (as `vscode-languageclient` does) is the extension's `child_process`, gated by its `process:spawn` permission.

## 9. Testing

- **Host** (`pnpm sidecar:vscode:test`, which builds `dist/` first): `tests/host-*.test.mjs` drive the built `host.js` over stdio with fixture extensions under `tests/fixtures/` (providers, documents, window, terminals, tasks, webviews, workspace, `vscode.lm`, the sandbox, and `vscode-languageclient` with `echo-lsp.mjs`). The other suites test one module each.
- **Rust**: `cargo test -p cognia-plugin-runtime --features tauri-host --lib -- vscode::` covers install, uninstall, the state directory, signatures and receipts, and host stderr and exit.
- **Renderer**: co-located Jest suites under `lib/plugin/vscode-shim/` and the plugin detail components. The coverage gate is `pnpm audit:vscode-api-coverage`.

## 12. Gotchas

- **Trust is per extension, and the receipt is per install.** Reinstalling from Open VSX writes a fresh receipt. Installing a dropped `.vsix` over a signed install replaces the directory, receipt included, so that copy needs the user's trust.
- **Permissions decide modules at load.** `grantedModules` is computed when the host starts, because `require()` is synchronous. Granting a permission later takes effect when the extension restarts.
- **Proxy** settings are read when a host starts.
- **One host per extension.** `vscode.extensions.getExtension(other).exports` is not shared across hosts. `activate()` on another extension starts it in its own host.
- **Desktop only.** Everything with `main` needs the Tauri runtime. `isVscodeHostAvailable()` is the check the UI uses.
