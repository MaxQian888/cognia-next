# Live sharing

<Status variant="beta">P2 and P3 shipped</Status>

<TLDR>
  A share link is a frozen, encrypted copy. A **live share** is a grant: access to some folders or files of
  one conversation, served live from the machine that holds them, until it expires or you revoke it. A grant
  is for whoever holds its WebDAV/SFTP sign-in, or — in a conversation shared through an organization — for
  that conversation's members, who reach the files through the collaboration server without any sign-in.
  `crates/cognia-file-share` owns the grants, the credentials, a gateway every request goes through, the
  built-in WebDAV/SFTP listener, the optional SFTPGo provider and the responder that answers members. The
  app manages it from the Files panel and Settings → Connectivity → Network drive; an agent can share too,
  only inside its own conversation and only once you approve.
</TLDR>

Decision record: [ADR-0222](/docs/adr/0222-a-conversations-files-are-a-view-and-sharing-them-is-a-grant)
§4–§10 (§8 amends [ADR-0162](/docs/adr/0162-sftp-is-shell-equivalent)).

## Using it

1. **Turn on the network drive** once: Settings → Connectivity → Network drive. Choose who can connect —
   this computer only, the local network (WebDAV over HTTPS with this host's certificate, SFTP with its own
   host key), or the internet through a cloudflared tunnel (WebDAV only) — and which protocols, on which
   ports. Turning it on exposes nothing by itself: a client sees only what a grant gives it.
2. **Share** from a conversation's **Files** panel: the hard-drive button on a folder or file row, or
   **Share as network drive…** in the "Shared as network drive" section. Pick paths, whether the person
   may download and change files, how long it lasts and over which protocols. An SSH public key lets an
   SFTP client sign in without the password.
3. **Hand over the card.** Each protocol gets its own username and a password shown **once**, the addresses
   to dial, the fingerprints to check, and steps for macOS Finder, Windows (`net use`), rclone and OpenSSH.

Every share appears in the Files panel of its conversation and, across conversations, under Settings →
Connectivity → Network drive → Live file access, with **Suspend**, **Resume**, **Revoke**, **New password**
(per protocol) and **Activity** (the audit trail of that share).

What a share cannot do:

- reach outside the paths it names, follow a symlink out of them, or read a file that looks like a
  credential (`.env`, private keys, `.ssh/`, …) — the sensitive floor no grant overrides;
- write to uploads, artifacts, or a folder this conversation cannot change;
- outlive the file-sharing policy: the longest live access, whether network-drive credentials and writes
  are allowed at all, and an organization's stricter policy all apply, and a share above a policy that was
  tightened later is suspended;
- survive its conversation being archived (suspended) or deleted (revoked), or its folder moving
  (it becomes **Needs attention** until resumed against the new place).

macOS Finder writes `._name` sidecars (a file's extended attributes) and `.DS_Store` next to what it copies
onto a WebDAV volume. The built-in WebDAV listener accepts those writes and drops them, and never lists or
serves the names, so they do not end up in your folders or a repository's `git status`.

## Status and reasons

| Status | Reason | Meaning |
| --- | --- | --- |
| Active | — | serving |
| Suspended | `owner` | you suspended it; Resume brings it back |
| Suspended | `policy` | goes beyond the current file-sharing policy |
| Suspended | `session_archived` | the conversation was archived |
| Suspended | `org_policy` | the collaboration server refused it under the organization's file-sharing policy |
| Needs attention (`stale`) | `mount_changed` | a granted folder now points somewhere else; Resume rebinds it |
| Expired | `expired` | past its lifetime |
| Revoked | `revoked`, `session_deleted`, `provider_failed` | permanently off |
| Revoked | `collab_host_removed` | a members share whose host registration was replaced or removed |

A card with no addresses says why: `listener_off` (the network drive is off), `sftpgo_unconfigured`, or
`sftpgo_no_public_endpoint` (SFTPGo has no public address configured).

## Sharing with a shared conversation's members

In a conversation shared through an organization, the share dialog asks **Share with**: a network-drive
sign-in, or **Members of this shared conversation**. A members share creates no credential at all. Choose
everyone from a role up (viewer, member, maintainer, owner) or only the members you pick; a viewer only ever
reads, whatever the share allows.

Members open the files from the conversation's **Files** section in the shared-conversation panel: browse,
download, and — where the share allows changes and their role is not viewer — upload, make folders, rename
and delete. The files never leave the device that holds them except as the answer to one request, so that
device must be online; the section says when it is not.

```
member ──► collab-server ──────────► host (cognia-file-share/collab.rs)
  POST file-requests        claim (long poll, host token)
  (files.readLive /         ─► gateway: grant, admission, mount, policy, path, sensitive floor
   files.writeLive +        ─► answer: JSON, or a read's bytes as a request-scoped object
   a covering grant)
  GET  file-requests/{id} ◄── complete
```

- **Registration.** Sharing with members first registers this device as the conversation's file host
  (`ensureCollabFileHost`): the request is made with *your* sign-in, which must hold `files.share`, and the
  server answers with a host token it keeps only as a SHA-256. The host receives that token alone
  (`file_collab_host_set`, kept in the system keychain) and authenticates every later call with it. Every
  host call re-checks that the person who registered it still holds `files.share`. A conversation has one
  host: registering again replaces it, and the old registration's members shares are revoked on both sides
  (`collab_host_removed`).
- **Mirror.** The host mirrors each members grant to the server (who, which paths, which permissions, until
  when), and again on every change, so members can list what is shared with them. The server clamps the
  mirror to the organization's file-sharing policy; a refusal suspends the grant on the host (`org_policy`).
  The host's own grant stays authoritative and is re-checked on every request.
- **Requests.** A member's request names one operation (list, stat, read, write, mkdir, delete, rename)
  under one grant that admits them. The server checks `files.readLive` (plus `files.writeLive` for a change)
  and the grant; the host claims it, checks it again in its gateway with the principal `member:<user id>`
  on the `collab` channel, does it, and answers. A write's bytes are uploaded before the host can claim it;
  a read's bytes are stored for the requester alone. Transfers are capped at 50 MiB, listings at 1,000
  entries.
- **Offline host.** A request nobody claims expires after two minutes, and the member sees the host as
  offline. A conversation holds at most 32 unanswered requests (8 per member).
- **Watching and ending it.** In a shared conversation the "Shared as network drive" section shows which
  host serves the members, whether it is answering, shares that have not reached the server yet and the
  last problem. Revoking one share revokes its mirror. **Stop sharing with members** there, or deleting the
  conversation, unregisters the host on the server and revokes every members share made under it. A member
  who may share the files can also **Remove sharing device** from the conversation's Files section, which is
  how a lost or unreachable device's sharing is ended from anywhere else. Locking or switching the account stops answering until
  the account is unlocked again; a server that no longer accepts the host token ends the registration.

## Agents

An agent can see and manage the sharing of **its own conversation** through the `filespace_*` tools:

| Tool | Consent | Does |
| --- | --- | --- |
| `filespace_list` | allowed | the conversation's mounts, a folder's entries, its share links and its live grants (with who each admits) |
| `filespace_share` | asks every time | a snapshot link, or live access: a network-drive sign-in, or `audience: "members"` with a lowest role |
| `filespace_enable_webdav` | asks every time | live WebDAV access, `/workspace` by default |
| `filespace_revoke_share` | allowed | revokes one link or grant of this conversation |
| `filespace_disable_webdav` | allowed | revokes this conversation's WebDAV access |

The sharing tools are offered only while the file-sharing policy allows agent sharing, cannot be turned into
"allow always" by any rule, grant or permission mode, and classify as `external-send` in the risk policy.
Every path must lie in the calling conversation's files, and the sensitive floor has no agent override. A
tool result never holds a password: the result card in the chat has an **Issue password** button that
rotates the credential on the host serving it and shows the new password once. A grant an agent made is
marked **By an agent**, and the host re-checks the agent-sharing policy for it while it lives. An agent shares
with members by role only; picking individual members is left to the dialog.

## Lifecycle

| Event | Live grants | Share links |
| --- | --- | --- |
| Conversation archived / restored | suspended (`session_archived`) / resumed | kept |
| Conversation deleted | revoked (`session_deleted`); a members registration is removed from the server | kept as independent copies; the delete confirmation offers to revoke them |
| Conversation forked | not copied | not copied |
| A granted folder moves | **Needs attention** until resumed | unaffected |

The writers that archive, restore or delete conversations (`lib/chat/session-archive-writes.ts`,
`deleteSessionsWithTeardown`, and the host applying a paired client's change) announce it through
`lib/filespace/lifecycle.ts`, and the running host sync pushes the affected mount tables at once rather than
on its next minute.

## How it works

```
Files panel / Settings ──┐                       ┌── WebDAV (dav-server)
paired device (RPC) ─────┼─► rpc.rs ─► service ──┤
brain / WebView push ────┘     │                 └── SFTP (russh, subsystem only)
                               ▼                          │
                         file-share.sqlite ◄── gateway ◄──┘ every operation
                         (per account)          grant → mount → policy → path → sensitive floor
```

- **One command surface.** `crates/cognia-file-share/src/rpc.rs` holds the fifteen `file_*` commands; the
  desktop's Tauri shells (`commands.rs`, `tauri-host` feature) and the companion RPC
  (`crates/cognia-companion-rpc/src/rpc/file_share.rs`) both dispatch into it, so a paired phone sends the same
  arguments the WebView does. Host-only: `file_share_activate`, `file_space_sync`, `file_share_policy_set`.
  Reads (`file_share_status`, `file_grant_list`, `file_audit_list`) need `host.observe` and page by token.
  Grant changes (`file_grant_create/revoke/suspend/resume`, `file_credential_rotate`) are `workspace.write`
  control commands. `file_share_listener_set`, `file_share_sftpgo_set` and `file_collab_host_set` are
  `host-admin` with step-up; `file_collab_host_status` is a `host.observe` read.
- **Mount tables.** The host serves a conversation from the table the app gave it: which directory each disk
  mount is, which uploads and artifacts are listed. The app pushes tables for conversations with grants
  (`lib/filespace/host-sync.ts`, mounted as `FileShareHostSyncInitializer` on the desktop and as a brain
  runtime on a headless server), and the host pulls one itself on every grant creation, on resume and once a
  minute per conversation with a grant (`companion://filespace-mounts-request`, answered by
  `lib/filespace/mount-table.ts`). Upload and artifact bytes are read the same way, at most 4 MiB a slice
  (`lib/filespace/asset-responder.ts`).
- **Shareable roots.** A disk mount must lie under a root the host would share: an active project root or the
  managed execution directory on the desktop (`is_shareable_workspace_path`), the spawn policy's workspace
  root on a headless server.
- **The account.** The host serves the unlocked account's grants only. On the desktop the account session
  binds it on unlock and unbinds it on lock; the renderer can only confirm it. A headless server binds its
  local account at boot.
- **Credentials.** Random usernames that carry no session information, 160-bit passwords stored as Argon2id,
  persisted backoff per username and address, failed sign-ins only charged. Revoking or rotating drops the
  live connections that used it.
- **Process registry.** The listeners and the tunnel child appear under the **Network drive** subsystem on the
  Performance page, with kill and restart.

## SFTPGo

On a server whose workspaces SFTPGo already serves, set Settings → Connectivity → Network drive → SFTPGo
(admin API URL, an admin-scope API key kept in the system keychain, home base, path mappings from host paths
to the paths SFTPGo sees, and the public SFTP/WebDAV address). Choosing **Served by: SFTPGo** in the share
dialog then creates one SFTPGo user per credential, with a virtual folder per granted path, the sensitive
floor as denied patterns and the grant's expiry; revoking deletes it. A path with no mapping refuses the grant
(`sftpgo_path_unmapped`). A share served by SFTPGo starts as SFTP only: SFTPGo's WebDAV never sends
a hidden file such as `.env`, but answers that it exists, with its size and date, before refusing it, so
WebDAV is an explicit choice there and the dialog says what it reveals. Failed SFTPGo changes are retried in the background while the grant stays revoked
locally. Deployment: `deploy/compose/compose.sftpgo.yaml` (see the compose README). SFTPGo is AGPL-3.0 and is
never bundled into the app.
