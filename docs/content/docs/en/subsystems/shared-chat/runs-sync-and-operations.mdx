# Runs, sync, and operations

## A shared session has at most one executing Agent Run

The initiating client requests a lease with its stable device id, Run id, operation id, and a randomly
generated token retained across retries. The service verifies `session.run`, stores only the token
digest, and returns the token with a short-lived lease bound to the user, device, session, and Run.
Reusing an operation id with different credentials or a different Run is rejected. Heartbeat and release
both require the matching session, device id, and token. An expired heartbeat cannot revive execution.
The local model/tool runtime publishes Run events with that token. A competing start
receives `409`. Its input is queued rather than executed.

Only the initiator, maintainer, or owner may steer. Heartbeat loss pauses the Run and then fails it after
the grace deadline. Another device never silently takes over, because repeating an irreversible tool is
worse than asking a user to restart explicitly.

Ordinary tools use initiator approval. High-risk, irreversible, or permission-expanding tools require a
maintainer, owner, or non-Guest approver. Approval resolution compares the current revision and consumes
one transition atomically, so double-clicks cannot approve twice.

Ordinary human messages receive the authenticated member's author identity and must have the `user`
role. Preserving historical authors and assistant/system roles is allowed only for the creator-owner
while the session is explicitly importing a private transcript, before activation.

## HTTP repairs and WebSocket accelerates

HTTP owns commands and every read of stored events. The WebSocket, opened with a single-use stream
ticket, tells a member that something changed: each stored event it announces makes the client pull
from its cursor, and the reducer applies only `lastSequence + 1`. A gap, reconnect, or policy change
triggers the same pull. Every policy-changing event is followed by a fresh membership check before more
events are sent.

## Members watch a run live

A run's reply is not only stored as it grows (ADR-0241). On a server that reports `shared-chat-live-v1`
in `/health`, the executor also posts live frames (the transcript codec's patches and 2 s keyframes,
about four a second) with its run token to `…/runs/{run}/live`. The server checks the lease, the holder's
standing and the shared-chat rollout on every frame, relays it to members whose socket negotiated
`cognia.chat.v2`, and stores nothing. A `cognia.chat.v1` socket never receives one. Live frames lag the
truth by design, never lead it: the stored corrections stay the record, written on settle and at most
every 10 s while live carries the reply (every second on a server without live).

What members see is one projection for both channels:

- **Text** is redacted as one whole message. While the reply streams, its last 256 characters stay with
  the executor, and a private key, JWT or URL credential is held from its opener until it is redacted.
- **Tools** follow the session's tool-detail tier. `summary` (the default) shows the tool, the workspace
  paths it touched and diff stats. `full`, which only an owner or maintainer can turn on, also shows the
  commands, edits, searches and to-dos, redacted. A publication carries the tier revision it was
  projected under; the server refuses an older one (`409 tool_detail_stale`) and the executor
  re-projects. MCP and plugin tools never share their input.
- A part that fails the PII gate is replaced by an inert "withheld" row; the rest still publishes.

A member drops a streaming reply after 6 s without a frame, at once on its redaction or a socket close,
and keeps a settled one until its pull has read past the final correction (10 s at most). A redaction
also stops the server from relaying any queued frame for that message.

Membership removal closes the person's stream, invalidates attachment tickets, cancels their queued
input, and ends their active lease. The client purges the corresponding shared projection. Offline mode
keeps cached reads and drafts only. There is no delayed message or Run outbox.

## Break-glass is not implicit org-admin access

Org administrators do not discover private session content through normal membership APIs. For an
incident, an org admin with workspace-manage capability must provide a reason and choose a duration from
one minute to one hour. The resulting grant is bound to that admin and session. Each raw event read
validates expiry and writes a metadata-only `session.breakGlassRead` audit with `rawContentAccessed=true`.

## Operating and rolling back

1. Apply additive migrations with both flags disabled.
2. Enable the service flag for selected organizations. Verify protocol v2 health.
3. Ship a client build with its flag enabled to the same canary population.
   Deploy lease-credential changes with the matching client: acquisition sends a stable token, and
   release sends `{ deviceId, token }` in the request body. Older clients cannot release a lease through
   the hardened endpoint; the lease expires normally if they disconnect.
4. Stop rollout on any cross-tenant allow, stale access after removal, event gap that cannot recover, or duplicate tool execution.
5. Roll back by disabling either flag. Do not down-migrate or delete shared data.

The collaboration service must never log bodies, tokens, emails, prompts, tool input, or attachment URLs.
Operational dimensions are limited to action/event/risk/stage/reason classes. Private local chat remains
available during service outage or rollback.
