# Unified Agent Execution

# ADR-0090 · flag-gated rollout (`agentExecutionResolverV2`) · spec version 1

Cognia has exactly **three agent runtime rails** — the Claude Agent SDK, the
provider-neutral AI SDK loop (both hosted by the Node sidecar), and external
agents behind the `ExternalAgentManager`. Everything else is a *dimension*,
not a rail: gateway vs direct is a **route**, desktop vs headless is a
**host**, native vs orchestrated is a **delegation mode**, and the text-only
`executeAgent` channel is a **completion fallback**, never a fourth runtime.

## The authority chain

```
AgentExecutionPolicy (caller intent, declarative)
        │
        ▼
resolveAgentExecutionSpec()          ← the ONLY decision authority
        │   lib/ai/agent/execution/resolve-agent-execution-spec.ts
        ▼
ResolvedAgentExecutionSpec (FROZEN: runtime · route · host · bindings ·
        │                   capabilities · credential REF · fingerprint)
        ▼
AgentExecutionService                ← the ONLY execution entry
        │   lib/ai/agent/execution/agent-execution-service.ts
        ├── agent rail      → resolveSendOptions stamps SendOptions.execution
        │                     → sidecar dispatch routes on runtimeAdapter
        ├── completion rail → explicit-only fallback, result carries
        │                     degradedReason
        └── external rail   → ExternalAgentManager
```

Once a spec exists for a session, **nobody re-derives** runtime, route, host
or credentials from anything else. The spec's `executionFingerprint`
(canonical-JSON FNV-1a-128, volatile fields excluded) is the identity that
tickets, budgets, recovery and audits key on.

## Fail-closed rules

- A hard capability (`policy.requires`) the frozen runtime cannot serve
  rejects **before any provider call** — a completion is never silently
  consumed instead (`AgentCapabilityUnsatisfiedError`).
- Losing the agent host degrades to the completion rail **only** when the
  policy explicitly allows it (`fallbackPolicy: "completion"`), and the
  result then carries a machine-readable `degradedReason` that surfaces on
  workflow node outputs, team dispatch results, and plugin meta.
- Headless/managed installs prohibit the legacy completion fallback outright.

## Where the process starts

A stdio external agent needs a process table. Three runtimes can offer one, and
for a long time only the first two were counted:

| Runtime | How the child starts |
| --- | --- |
| Tauri desktop, headless brain, CLI | It spawns the agent itself. |
| A companion (browser tab, phone) paired to a Host | The Host spawns it. `agentInvoke` routes `spawn_external_agent` and its siblings over the companion RPC plane. |
| A browser with nothing paired | Nowhere. This is the only genuinely blocked case. |

`supportsExternalAgents()` answers `isTauri() || isHeadlessHost()`, which is the
first row alone, so every companion was refused with "the stdio transport
requires the desktop (Tauri) runtime" about a Host that could have run it.
`lib/ai/agent/external/process-plane.ts` is the three-state answer, and it
returns a REASON rather than a boolean because four situations produce "no" and
each needs different advice: nothing paired, a Host still handshaking, a Host
too old to spawn, and a Host that has not granted this device Agent Control.

That last one is not optional. `spawn_external_agent` is declared
`capability: "process.spawn"`, which a paired device holds only through the
separate Agent Control grant (`GrantKind::AgentControl`), so a client that
checks the feature but not the grant offers a Run button the Host answers with
403. A Host declares the plane as the `external-agent.process-plane` feature,
per operation, so a build that ships spawn before detection is describable.

## Which agent CLIs a host already has

`external_agent_detect_runtimes` reads the machine that would run the child, in
one call for the whole catalog, and the Add Agent picker badges each preset with
the answer. It installs nothing: a runtime whose catalogued probe is
`npx -y <package> --version` is reported as `package-runner` rather than
downloaded, because presence there cannot be settled without a network install
and drawing a badge is not worth one. The version string is parsed client-side
by the catalogued parser; the certification verdict stays with
`assessRuntimeVersion`.

## Choosing an agent's model, and knowing it can run

An agent answers "which models do you have" in two unrelated shapes, and a
caller that understands one sees an empty list from half of them:

| Shape | Who uses it |
| --- | --- |
| A `model`-category **config option** (`session/config_options`) | ACP, and what Pi's RPC adapter projects its `get_available_models` reply into |
| **Session model state** (`session/new`'s `models`) | Older ACP agents that populate this and no config option |

`lib/ai/agent/external/session-models.ts` reads both and, more importantly,
resolves where a WRITE goes: a config option is the agent's own declared
control, so it wins, and `session/set_model` is the fallback. That precedence
already lived inside `AgentManager.applyModelToSession`, which runs when a
session is created with a requested model. Two writers disagreeing about which
call reaches the agent is how a picker changes nothing.

Nothing used to ask. The only path that populated the list was a
`config_options_update` the agent chose to push, so ACP agents worked by luck
and Pi rendered no model row at all. `AgentManager.fetchSessionModelSurface` is
the async twin the synchronous capabilities could not be (both report a
promise-returning adapter as `unsupported`, which is correct for them), and
`model-surface-cache` shares one fetch between the composer chip and the session
panel, which mount together.

The composer chip leads with the agent's models and keeps the configured
providers underneath: a model configured in Cognia is still a legitimate choice
for an agent that accepts one, and the reserved group id is what tells the
handler to write through the agent rather than through a session override.

Credentials are the other half of "can this run". `pi auth check --provider <id>
--json --no-refresh` (ADR-0119) already ran on connect and was rendered only in
the settings page, which is not where a runtime is chosen. It now shows as a
badge on the runtime selector and the Manage Agents card, keeping the four
answers apart: signed in, partly signed in, signed into nothing, and could not
check. An unreadable probe is never drawn as unauthenticated, because Pi exits
`1` both for missing credentials and for a malformed call.

## Wire shape

The spec rides `SendOptions.execution` (`AgentExecutionSendSpec`) — secret
free by construction: gateway routes carry an endpoint plus a ticket **id**;
direct routes carry a credential **profile reference**. Raw keys stay on the
existing `sendOptions.env` redaction path. The Rust `SendOptions` flattens
unknown fields, so the sidecar receives the spec unchanged and its dispatch
(`sidecar/dispatch/index.mjs`) routes on `execution.runtimeAdapter`, counting
spec-less sends as `legacy_dispatch` telemetry.
