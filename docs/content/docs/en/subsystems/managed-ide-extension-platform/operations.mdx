# Operations, updates, and troubleshooting

Local operation stays in Tauri. For a paired host, code-server, profiles,
plugins, permissions, secrets, proxies, and protocol processes run on the
remote Cognia host. The desktop does not upgrade that binary. It reaches the
remote workbench through a local ephemeral relay that pins the paired
certificate SPKI fingerprint, then sends the existing device JWT in an
`Authorization` header. The real remote port and credentials stay loopback-only.

The relay is mounted on the companion entry point at `/ide/relay/<opaque-id>/`
(`protocol/companion-api-routes.json`) behind `require_device_access`, so the
credential it forwards is an ordinary device access token — the same one every
other device request carries. Those live five minutes, and only the renderer
holds the device private key needed to mint one, so `lib/codeserver/remote-relay.ts`
re-mints ahead of expiry and re-`ensure`s the relay. A re-ensure for the same
host, path and fingerprint swaps the token **in place** and keeps the bound
port: rebinding would give the webview a new URL and restart the workbench,
losing exactly the session the pane exists to protect.

The paired host can be another Cognia desktop as well as a headless server. A
desktop serves its workbench through the same `/ide/relay/` entry point, but its
code-server runs with `--auth none` and full terminals for its owner, so a
device's Remote Control capability is not enough. The first time a device opens
a project there, the desktop shows its owner a prompt naming the device and the
folder, and the device's request fails with `CODESERVER_RELAY_GRANT_REQUIRED`
until the owner allows it. The approval is per device and per project, persists
in `relay-grants.json` (mode `0600`) under the code-server root, and is listed
and revocable in Settings → Pro IDE. Revoking it, unpairing the device, or
withdrawing Remote Control closes an open session within two seconds. Relay ids
are bound to one code-server process: when the workbench restarts, the device
calls `ensure` again and gets a new id. A browser on the same machine is not
relayed; it reaches the workbench over the loopback plane and gets the port
directly in the `codeserver_ensure` reply.

Plugin updates use a durable transaction:

1. `plugin_stage_version` downloads and verifies checksum/signature, extracts
   into host-owned transaction storage, validates the manifest and resources,
   and leaves the working package untouched.
2. The renderer validates permission expansion and the declarative migration
   plan, then stages the deterministic proxy.
3. The host snapshots the old package and `.host-state`, including managed IDE
   SQLite state and secret indexes.
4. The old runtime is disabled/unloaded and
   `plugin_commit_staged_update` atomically renames the staged package into
   place.
5. The exact staged proxy is activated. The code-server host attempts live
   activation first, restarts only the extension host when required, and
   restores the old proxy on handshake failure.
6. Runtime verification succeeds before the transaction is finalized.

A failure after commit restores package and host state, rescans the runtime,
and re-enables the old version. A full Pro IDE restart is offered only when the
old package/state are confirmed restored but old runtime activation still
cannot complete. Uncommitted artifacts have no activation marker and are
ignored on code-server restart.

On first profile migration, native Open VSX installs move to the isolated native
profile. The old shim remains export-only for one major release. Settings,
keybindings, and theme are filtered before synchronization; extension state,
secrets, trust decisions, and tickets are never copied.

That synchronization is a **one-shot seed**, guarded by its own
`.portable-preferences-v1` marker beside the migration marker, and it is
**additive** — it writes only the allowlisted keys and leaves everything else in
the managed profile alone. After the seed, managed `settings.json` belongs to
the renderer's theme sync and to whatever you set from inside VS Code, and
managed `keybindings.json` belongs to you outright. Re-running it on every
launch would hand the native profile the last word on the keys both allowlists
name, and would delete the rest.

## Dev Mode

Dev Mode lives in Plugin DevTools → Managed IDE Dev Mode, on the desktop. The
switch is the host's (`plugin_managed_ide_dev_mode_set`): off by default,
never saved, and gone when the app quits. It uses the same catalog and
authorization path as normal operation and adds:

- **RPC inspection.** The agent channel records every frame it exchanges with
  an editor in a 2,000-entry ring: direction, kind, method, id, generation,
  plugin, size, round-trip time and error code. Payloads keep only their shape
  (keys, lengths, leaf types) unless you opt into values, which the panel runs
  through `@cognia/redact` before showing. Nothing is recorded while Dev Mode
  is off, and switching it off empties the trace.
- **Permission simulation.** Decide one permission for one plugin, for the
  session: Allow and Deny answer without asking, Ask always prompts. The
  broker's authorization path consults it only while Dev Mode is on. A plugin
  with a simulation in force is badged in the plugin list and in the trace.
- **Schema diagnostics.** Each registered plugin folder shows its
  `manifest.ide` problems, from the locked JSON Schema and from normalization,
  re-checked when a file in the folder changes.
- **Resource watching and temporary proxy rebuilds.** With Watch plugin
  folders on, an edit in a registered folder reinstalls the plugin from it and
  reloads it. During Dev Mode a local plugin's proxy is activated as a
  temporary build: no activation marker is written, so a restart still gets
  the committed proxy, and switching Dev Mode off restores it (or removes the
  proxy of a plugin that never had one committed).
- **Local development signing.** There is no development key. A plugin
  installed from a folder registered in the panel gets a `local-dev`
  verification receipt, minted by the host only while Dev Mode is on and only
  for registered folders. The signature check accepts it only after asking the
  host that Dev Mode is still on, the frontend trust prompt still applies, and
  proxies are still signed with the host's `managed-signing.key`, which the
  host uses only for plugins it holds a receipt for. Switching Dev Mode off
  forgets the folders, the host stops honouring `local-dev` receipts, and the
  plugins trusted that way are disabled.

No install can bring its own receipt: every installer discards a
`.cognia-verification.json` found in the content it copies before writing the
one its own verification earned.

For an unavailable contribution:

1. Verify plugin status and Workspace Trust.
2. Compare plugin version, manifest hash, catalog hash, platform version, and
   connection generation.
3. Check the `cognia.<pluginId>.*` namespace for conflicts.
4. Inspect redacted local traces for permission, path, deadline,
   backpressure, cancellation, or circuit-breaker errors.
5. Verify the proxy activation marker still points to a signed cached artifact.
6. Rebuild the proxy; restart the extension host only after the old artifact
   remains recoverable.
