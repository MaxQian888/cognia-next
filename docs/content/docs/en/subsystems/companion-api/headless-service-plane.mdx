# Headless Service Plane

<Status variant="beta">developer surface</Status>

<TLDR>
  `pnpm dev:headless` starts the native Companion server and all configured agent runtimes without
  launching Next.js or a WebView. The local Brain connects through `/internal/events`,
  `/internal/bridge`, and `/internal/_rpc/{name}`. Add `--local-debug` for a loopback-only listener
  and an automatically generated, process-scoped Apifox/Postman credential.
</TLDR>

## Start without the frontend

```bash
pnpm dev:headless --local-debug --data-dir .cache/headless-apifox
```

The launcher supervises the native server and enabled agent runtime processes, forwards their logs,
and shuts the process group down together. CLI options are available through:

```bash
pnpm dev:headless --help
```

`--data-dir` owns the master key, encrypted secret store, SQLite databases, and TLS certificate. An
existing directory whose encrypted store outlived its original master key cannot be recovered and
fails with `secret-store decrypt failed`. Use an isolated directory for local API debugging rather
than generating an unrelated new key beside an unknown old store. After the first build, add
`--skip-build` for a fast restart.

## Automatic local-debug authentication

The launcher writes a `0600` Postman environment under the data directory, prints its path, and
deletes it when the server exits. Import it into Apifox or read the `serviceToken` variable from that
file while the process is running. The random token is accepted only from loopback on
`/internal/*` and `/ide/content*`; it is not accepted by paired-device routes.

For a direct shell smoke test, use the existing persistent-token fallback in another shell:

```bash
TOKEN="$(pnpm --silent dev:headless token --data-dir .cache/headless-apifox)"
curl --insecure \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"limit":20,"offset":0}' \
  https://127.0.0.1:27890/internal/_rpc/session_list
```

The token is service-scoped, expires after 24 hours, and is accepted only when the peer is loopback.
It is intentionally unsuitable for mobile or remote-device authentication. Token issuance and the
running server must use the same `--data-dir`, or they will use different signing secrets.

For graphical API debugging, follow [Local debugging with Apifox](./apifox-debugging) for import,
certificate, and environment setup.

## Driving it from a browser

`pnpm dev:web-headless` is the same headless server with a Next dev server beside it — the
topology you want when the thing you are changing is the UI but the thing that has to run the
turn is the native host. It is `pnpm dev` on `:3000` plus `pnpm dev:headless` on `:27890`,
supervised together.

```bash
pnpm dev:web-headless
```

Two facts about it are easy to lose an afternoon to.

**The page and the API are different origins.** `http://localhost:3000` talking to
`https://127.0.0.1:27890` is cross-origin, and the server's origin policy is exact-match with an
empty default — every unlisted origin gets `403 web_origin_forbidden` **without CORS headers**,
which a browser reports identically to a closed port. The launcher already sets
`COGNIA_ALLOWED_WEB_ORIGINS` to `http://localhost:3000,http://127.0.0.1:3000` for you, so this
only bites when you start `cognia-server` yourself:

```bash
COGNIA_ALLOWED_WEB_ORIGINS="http://localhost:3000,http://127.0.0.1:3000" \
COGNIA_ALLOW_PRIVATE_NETWORK=true \
cargo run --bin cognia-server -- serve --port 27890
```

**A browser cannot reach the HTTPS listener at all.** `tls.rs` mints the certificate with rcgen
and no CA, on `127.0.0.1` exactly as on a LAN address. A mobile client is fine — it pins the SPKI
hash at the native layer, outside any trust store — but a browser validates against the system
roots and has no JavaScript escape hatch. So `https://127.0.0.1:27890` is not the browser's door.

The browser's door is `browser_access.rs`'s **plaintext, loopback-only** listener. `http://127.0.0.1`
is "potentially trustworthy" per Secure Contexts, so it needs no certificate chain and is exempt
from mixed-content blocking. `pnpm dev:web-headless` opens it on `:27891` for you; starting the
server yourself, name the port:

```bash
COGNIA_ALLOWED_WEB_ORIGINS="http://localhost:3000,http://127.0.0.1:3000" \
cargo run --bin cognia-server -- serve --port 27890 --browser-listener-port 27891
```

The flag is hard-bound to `127.0.0.1` — the whole justification for dropping TLS is that the bytes
cannot leave the machine — and it refuses to start without an allowlist, because a listener with an
empty one answers `403 web_origin_forbidden` to every request a browser makes while looking, from
the outside, exactly like a working port. It also turns on Private Network Access for those
origins, which Chrome preflights before a page on `:3000` may reach loopback at all.

Then issue the invitation **against that plane**, not the HTTPS one:

```bash
pnpm --silent dev:headless pair --device-name browser --skip-build \
  --advertise-url http://127.0.0.1:27891
```

Without `--advertise-url` the payload carries `https://127.0.0.1:27890`, and the pair screen will
correctly refuse its own suggestion. The screen's copyable Development command already includes the
flag.

Paste the `cgnp3|…` string into `http://localhost:3000/pair`. A failure here is classified rather
than reported as "Failed to fetch": a plaintext non-loopback address is refused before the
invitation is spent, an untrusted certificate reads as **This browser can't verify the Host's
certificate**, and a missing allowlist entry names the exact origin to add.

**The Cognia browser extension takes a different code.** `pair` mints an Owner invitation for the
pair *screen*; the extension spends a **browser enrollment**, which grants `browser.submit` and
`browser.read-own` and nothing else (ADR-0154). The two are not substitutable in either direction —
the extension's decoder rejects a `cgnp3|` string on sight — so it has its own action:

```bash
pnpm --silent dev:headless browser-enroll --skip-build --browser-listener-port 27891
```

It prints a `cgnb1|…` code, and refuses to print one at all unless `/healthz` on that port answers
with this deployment's own `server_id`: "the listener is bound" and "another process holds 27891"
are different answers, and only one of them produces a code that works. The extension's own origin
has to be allowed too, so add `chrome-extension://<id>` to `COGNIA_ALLOWED_WEB_ORIGINS` before you
paste, or every request it makes answers `403`.

## Internal routes

| Route | Purpose |
| --- | --- |
| `POST /internal/_rpc/{name}` | Invoke any command accepted by the shared dispatcher |
| `GET /internal/operations/{operation_id}` | Read a durable operation without replaying the original mutation |
| `GET /internal/events?token=…&since=…` | Brain event stream with replay cursor |
| `GET /internal/bridge?token=…` | Bidirectional Rust-to-Brain data-plane bridge |
| `GET /integrations/mcp/oauth/callback` | Complete a pending MCP authorization-code + PKCE flow |
| `POST /ide/content` | Publish managed IDE content through the loopback broker |
| `GET /ide/content/{handle_id}` | Resolve a brokered content handle |

The generated HTTP contract is `docs/api/headless-service-api.openapi.yaml`; the event and bridge
frames are generated into `docs/api/headless-service-api.asyncapi.yaml`. They are deliberately
separate from the paired-device specification so a service-only command can never be mistaken for a
public mobile endpoint.

The current catalog contains **450** Headless commands. The server compiles the embedded Draft
2020-12 input and output schemas at startup, validates input before dispatch, and validates output
before recording a successful receipt. A request violation returns `422 contract_input_violation`;
an implementation/schema mismatch returns `500 contract_output_violation`. Violation details contain
instance and schema paths, never the rejected value. `COGNIA_HEADLESS_CONTRACT_ENFORCEMENT=off` is an
emergency rollback switch, not a compatibility mode.

Mutating commands return `202` when their durable operation is still active. `cognia host call`
polls the operation route until the receipt is terminal; it only replays the identical `POST` against
an older server that returns `404` for the operation route. On process restart, interrupted
`queued`, `running`, or recovery states become terminal `operation_interrupted` failures instead of
remaining permanently pending.

## MCP OAuth in Headless mode

The existing `mcp_oauth_status`, `mcp_oauth_load_entry`, `mcp_oauth_authenticate`,
`mcp_oauth_refresh`, and `mcp_oauth_clear` commands are service-owned and account-isolated. Set
`COGNIA_PUBLIC_URL` to the externally reachable HTTPS origin; the authorization redirect is
`$COGNIA_PUBLIC_URL/integrations/mcp/oauth/callback`. Authentication stores PKCE state and dynamic
client information in the encrypted secret store, returns an authorization URL, and accepts each
256-bit state value once for at most three minutes. Access tokens are never included in callback
HTML or completion events. Loopback HTTP callbacks are only accepted in the explicit local-debug
configuration.

## Agent-first operator CLI

The Rust `cognia` binary embeds the generated Headless command catalog and exposes it through
`cognia host`. Discovery, schema inspection, skills, and dry-run work offline; calls and events stay
on the loopback service-token boundary.

```bash
cognia host categories
cognia host resources --category development
cognia host skills list
cognia host skills list --kind workflow
cognia host skills install --scope project
cognia host skills read cognia-host-development
cognia host commands --query session
cognia host commands --resource git --operation read
cognia host schema session_list
cognia host call session_list --data '{"limit":20,"offset":0}'
cognia host events --event claude://message
```

When `COGNIA_SERVICE_TOKEN` is absent, the CLI invokes the colocated
`cognia-server issue-service-token` and retains the token only in memory. The CLI trusts the
persisted self-signed certificate under `COGNIA_DATA_DIR`; it does not offer an insecure TLS mode.
High- and critical-risk commands require an interactive confirmation or a user-approved global
`--yes`. This is an operator safety prompt, not a second authorization authority.

The generated catalog classifies every command into exactly one stable domain: `sessions`,
`agents`, `tasks`, `automation`, `connectors`, `extensions`, `knowledge`, `development`, or
`system`. `cognia host categories` reports per-domain operation/risk counts and the matching
embedded skill. `cognia host resources` exposes generated resource groups within those domains, and
`commands --resource <id>` narrows discovery without copying or guessing the RPC tree. The core
`cognia-host` skill owns shared safety and output rules; nine domain skills provide focused command
selection, while six workflow skills cover observation, safe Git, agent incidents, backup recovery,
extension rollout, and connector delivery. Filter the inventory with
`skills list --kind core|domain|workflow`.

### Installing the embedded Agent Skills

Installation is offline and requires an explicit destination:

```bash
# Available to compatible agents for the current user.
cognia host skills install --scope user

# Available from the nearest Git worktree root, or the current non-Git directory.
cognia host skills install --scope project
```

Both scopes use the shared Agent Skills layout, `$HOME/.agents/skills` or
`<project>/.agents/skills`, so Codex, Gemini CLI, OpenCode, and compatible clients can discover the
same 16 skills. Refresh the client's skill inventory or restart its session after installation.
The command does not contact `cognia-server` and does not read credentials.

The hidden `.cognia-host-manifest.json` records the CLI bundle version and the SHA-256 hash of every
managed file. A later install updates or removes only files that still match the previous manifest.
The complete bundle is preflighted before writing; modified or untracked managed files, a corrupt
manifest, or a symlinked `.agents`, skills root, or managed destination returns
`skill_install_conflict` with zero writes. Fully written Cognia temporary files that match the
current bundle are recovered on the next successful retry, and the manifest is replaced last;
other temporary content conflicts instead of being deleted. Preserve intentional edits elsewhere
and restore each reported file from
`cognia host skills read <skill> [path]`, or move all Cognia-managed directories and the manifest
aside before retrying. There is deliberately no force or partial-install mode.

In Compose and Kubernetes, execute `cognia host` inside the server container or Pod. A separate
management Pod is intentionally unsupported because a service token is rejected from a non-loopback
peer.

## Contract maintenance

Headless RPC paths are generated from the same command manifest and Rust allowlist as the public
specification:

```bash
pnpm companion-api:gen
pnpm companion-api:check
pnpm companion-api:lint
```

When a command is added to the dispatcher, the generator and Rust parity test require the Headless
spec to expose it. Public exposure still requires the stricter target and transport classification.
The same generator owns the embedded catalog hash, the compact Brain bridge identity module, the
OpenAPI document, and the AsyncAPI document. Bridge protocol v2 refuses `hello`/`hello_ack` when the
catalog hash or contract version differs, so a stale Brain never becomes ready.
