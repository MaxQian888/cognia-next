# A2UI System

<Status variant="experimental" />

<TLDR>
  Claude (or any external agent) generates a declarative component tree through four MCP tools; the renderer turns it into a real React panel inside the webview; user actions and data model changes flow back to the agent via an event bus. Renderer, catalog, parser, and events all run in the browser layer; the sidecar MCP server + Rust bridge let external agents connect as well.
</TLDR>

## What It Solves

Models can do more than output markdown text — they can output **real UI**: a form, a chart, a dashboard.
A2UI (Agent-to-UI) standardizes this:

- Agent calls an MCP tool (`a2ui_create_surface`) → webview renders a panel.
- Agent calls `a2ui_update_components` → component tree is replaced, DOM diff updates the view.
- User clicks a button → renderer pushes `userAction` back to the agent through the event bus.
- Agent receives the event and continues orchestrating the next round.

This loop runs entirely within cognia-next's own process boundary — the sidecar's `claude-host.mjs` lands in the webview via embedded MCP; external agents (Claude Code CLI, Cursor, Codex, Gemini) connect through a standalone stdio MCP server `sidecar/a2ui-mcp.mjs`, with dispatch relayed back to the webview over a local socket. See [./mcp-server-sidecar](./mcp-server-sidecar) for details.

## Surface Types

| Type         | Behavior                                    | Persistence                              |
| ------------ | ------------------------------------------- | ---------------------------------------- |
| `inline`     | Rendered inside the current chat message bubble | Not stored in Dexie; the message itself is the boundary |
| `dialog`     | Radix Dialog popup; draggable               | Not stored in Dexie                      |
| `panel`      | Embedded in sidebar / workbench panel       | Persisted in `a2uiSurfaces` table        |
| `fullscreen` | Takes over the main area; typically used for mini-app editors | Persisted in `a2uiSurfaces` table        |

`inline` messages are bound to a chat message id and are destroyed along with the message; `panel` and `fullscreen` need to survive across restarts, so they go through Dexie.

## Component Catalog

`lib/a2ui/catalog.ts:DEFAULT_CATALOG_ID = "cognia-standard-v1"` — a catalog is a type → React component mapping table. 50+ built-in components are grouped by category:

| Category       | Examples                                                                               |
| -------------- | -------------------------------------------------------------------------------------- |
| **Layout**     | `Row` `Column` `Card` `Tabs` `Accordion` `Dialog` `Divider` `Spacer`                   |
| **Display**    | `Text` `Image` `Icon` `Link` `Badge` `Alert` `Progress` `Loading` `Empty`              |
| **Form**       | `Button` `TextField` `Select` `Checkbox` `RadioGroup` `Slider` `DatePicker` `Combobox` |
| **Data**       | `Table` `List` `Chart` `DataExplorer`                                                  |
| **Overlay**    | `Tooltip` `Popover` `HoverCard` `DropdownMenu` `ContextMenu`                           |
| **RichOutput** | `RichOutput` `ComparisonCards` `WidgetStatus` academic scenario adapter                |

Third-party catalogs can be registered via `createCatalog()` + `registerCatalog()`; the agent specifies `catalogId` when calling `createSurface`. `FALLBACK_COMPONENT_TYPE` handles unknown component types — no crash, just a clear placeholder.

## Data Model + Binding

Each surface holds a `dataModel: Record<string, unknown>`; components read and write via JSON Pointer:

```ts title="lib/a2ui/data-model.ts"
// Any property accepting string | { path } is parsed
resolveStringOrPath({ path: "/form/name" }, dataModel, "")
resolveBooleanOrPath({ path: "/checked" }, dataModel, false)
```

- `setValueByPath(model, "/items/0/done", true)` triggers a `dataModelChange` event.
- `watchPaths()` registers subscriptions across multiple paths.
- `resolveComputedFields()` allows derived fields like `{ "@computed": "sum:/items/*/price" }` — the agent writes the expression once, and the client recalculates automatically.

## Event Loop

The renderer does not call the agent directly. It emits events to `globalEventEmitter` (`lib/a2ui/events.ts`):

```ts title="lib/a2ui/events.ts (excerpt)"
emitter.emitAction({
  type: "userAction",
  surfaceId,
  action: "click",
  componentId: "btn-submit",
  data: { value: 42 },
  timestamp: Date.now(),
})
```

The chat loop (`lib/claude/build-options.ts`) subscribes to the event bus and appends `formatActionForAI(...)` into the next user message — so the agent sees in the next round of context:

```
User action: click
Data: { value: 42 }
```

`batchEventsForAI()` merges multiple consecutive events into a single message, preventing the agent from being interrupted repeatedly in quick succession.

## Output Profiles — Letting the Model Know Which UI to Pick

`lib/a2ui/output-profiles.ts` maps 21 common request intents ("draw an architecture diagram", "show a comparison", "build a dashboard"...) to recommended output type + tech stack + host strategy:

| Category                      | Output  | Tech    | Host Strategy         |
| ------------------------- | ------- | ------- | ---------------- |
| `how-it-works-physical`   | svg     | svg     | artifact-preview |
| `database-schema-erd`     | mermaid | mermaid | native           |
| `trends-over-time`        | chart   | chartjs | native           |
| `design-a-ui`             | html    | html    | sandboxed-html   |
| `3d-visualization`        | html    | threejs | lazy-runtime     |
| `physics-math-simulation` | canvas  | canvas  | sandboxed-html   |

`routeRichOutputProfile()` is the agent-side dispatch function: given an intent and context, it returns whether to open a surface or fall back to an artifact. See [./artifacts-sandbox](./artifacts-sandbox) to understand the difference between the two paths — A2UI is declarative interactive components; Artifact is one-shot content output.

## Cross-Process Bridge (External Agent Access)

To let Claude Desktop / Cursor / Codex write A2UI, we need to bypass cognia-next's own sidecar — the MCP servers they spawn **have their own stdin/stdout**, not Tauri's.

Solution: `src-tauri/src/a2ui_bridge/`

1. When Tauri starts, it listens on a Unix domain socket / Windows named pipe under `app_local_data_dir` (path written to the `COGNIA_BRIDGE_SOCKET` environment variable).
2. `sidecar/a2ui-mcp.mjs`, spawned as a standalone MCP server by an external agent, reads the socket path from the environment variable and establishes a side channel.
3. Tool calls complete locally first (agent gets an ok response), then a line `{"type":"a2ui_dispatch", "message": ...}` is written through the socket to cognia-next.
4. The Rust bridge (`forward_line`) parses it and calls `app.emit("a2ui://dispatch", ...)`; the webview side `lib/a2ui/ipc.ts:subscribeA2UIDispatch()` listens and lands it in the store.

If cognia-next is not running / the socket refuses connection — the agent still receives a success response, but no surface appears. This is intentional: don't let external agents get stuck in a loop just because we aren't running.

## Dexie Schema (v13)

```ts title="lib/db/a2ui-types.ts (excerpt)"
a2uiApps: "id, name, updatedAt, createdAt, isBuiltIn, category, isFavorite, sortOrder"
a2uiSurfaces: "id, appId, sessionId, updatedAt, createdAt, type"
a2uiTemplates: "id, name, category, updatedAt, source"
a2uiEventHistory: "id, surfaceId, [surfaceId+timestamp], timestamp, type"
```

- **a2uiApps** — mini-app definitions saved by the user in the Hub. Built-in rows are injected by `lib/db/seed.ts`; the CRUD layer protects them from destructive edits.
- **a2uiSurfaces** — runtime snapshots of `panel` / `fullscreen` surfaces, used for cross-restart recovery.
- **a2uiTemplates** — user-defined templates (the 14 built-in templates are static and not stored in the table).
- **a2uiEventHistory** — audit trail capped at 1000 rows, used by Settings → A2UI → Debugger.

The v13 upgrade also writes an `a2ui-bridge` MCP server row (`enabled: false`, for external agent projection only).

## App Hub and Workspace

`app/a2ui/page.tsx` is a dual-mode page:

- **Hub** — browse all mini-app cards, filter by category, and use `Flash Generate` mode to create an app from natural language in one click (`generateAppFromDescription` goes through `lib/a2ui/app-generator/` rule matching, **no LLM required**).
- **Workspace** — enter `A2UIWorkspace` via `?app=<id>`, visually edit the component tree, adjust the dataModel, and save versions.

14 built-in templates are distributed across `lib/a2ui/templates/{data,form,productivity,social,utility}.ts`, covering todo list, calculator, forms, dashboards, timers, notes, sticky notes, exchange rates, habit tracking, and more.

## Security & Sandbox

A2UI components are **rendered directly into the main React tree** — unlike Artifacts/Sandbox, which use iframe isolation. This means:

- The component tree can only use **pre-registered** React components from the catalog — if the agent supplies an unknown `component` field, the fallback path catches it and does not interpret it as code.
- No inline HTML / script strings are allowed. The `Text` component's `text` property is rendered as plain text, not via `dangerouslyInnerHTML`.
- User actions go through the event bus; callback strings supplied by the agent are never executed directly.
- When widget metadata's `hostStrategy` is set to `sandboxed-html` / `artifact-preview`, content is routed to an iframe-based artifact panel instead of inline A2UI rendering.

If you are extending the component catalog, **audit every new component** for XSS surface area: rich text / iframe / SVG foreign object / data: URL all require whitelist filtering.
