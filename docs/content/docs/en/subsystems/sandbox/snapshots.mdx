# Cold snapshots and forks

A snapshot pairs a stopped Docker container image with an immutable Task
Workspace checkpoint. The image preserves system packages, global installs and
home-directory files. The checkpoint preserves the host-mounted workspace,
including tracked, untracked, ignored and generated files, empty directories
and file modes.

An active agent or task turn returns `snapshot_busy`. This feature captures
filesystem state only: memory, running processes, services, sockets and tmpfs
are not restored. Git administration is reconstructed from the pinned base;
the source worktree's `.git` pointer must never become the fork's pointer.
The checkpoint manifest records reconstructed metadata and declared exclusions.

## Host API

All commands use the Host's deployment identity and workspace authorization.
Caller-provided Docker labels are not ownership evidence.
The Docker driver records acquisition receipts for runtime ownership. A runtime
created before this feature must be acquired again before it can be snapshotted.

| Command                    | Input                                                                                       | Result                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `sandbox_snapshot_create`  | `request` with `projectId`, `workspaceId`, `provider`, `containerId`, optional `exclusions` | Snapshot record                                                            |
| `sandbox_snapshot_list`    | `projectId`                                                                                 | Snapshot records                                                           |
| `sandbox_snapshot_get`     | `snapshotId`                                                                                | Snapshot record                                                            |
| `sandbox_snapshot_delete`  | `snapshotId`                                                                                | Tombstoned snapshot record                                                 |
| `sandbox_snapshot_pin`     | `snapshotId`, `pinned`                                                                      | Updated snapshot record                                                    |
| `sandbox_snapshot_fork`    | `request` with `snapshotId`, `taskId`, `sessionId`                                          | New workspace and container                                                |
| `sandbox_snapshot_restore` | Fork request plus optional `workspaceId`                                                    | Restored workspace and container; `restoredInPlace` identifies the outcome |

The TypeScript adapter lives under `lib/sandbox/`. The response includes the
fork's `portLease`, so the preview client can resolve a workspace-relative
port offset without retaining the source workspace's port block.

## Capture and failure recovery

The Host records the creation journal in `task-workspaces.sqlite`:

```mermaid
flowchart LR
  Preparing[preparing] --> Captured[workspaceCaptured]
  Captured --> Committed[imageCommitted]
  Committed --> Ready[ready]
  Preparing --> Cleanup[Compensate and recover]
  Captured --> Cleanup
  Committed --> Cleanup
```

The ledger tables are `workspace_checkpoints`, `sandbox_snapshots`,
`snapshot_artifact_refs` and `snapshot_operations`. A checkpoint owns its Git
ref pin and content storage. The image is named
`cognia-snapshot-<deploymentHash>:<uuid>` and recorded by immutable image ID.
Interrupted operations are reconciled at startup; a partially created snapshot
is not a ready restore source.

Acquisitions share a lock for their canonical workspace root. Snapshot and
restore transitions require an exclusive lock and return `snapshot_busy` if
an acquisition is active. Durable journal reservations protect the workspace
between transitions. Capture, Git pinning, blob writes and materialization run
outside the ledger mutex; publishing rechecks the journal state and current
budget, so unrelated workspaces remain usable during large captures.

The full capture profile fails if any required content exceeds the budget.
It does not apply the normal workspace capture's generated-file filtering.
Exclusions are an explicit request and remain visible in the record and
manifest, so a caller can explain what a restore will omit.
They are workspace-relative paths or directory prefixes; glob patterns and
escaping paths are rejected. Unsupported special files are listed in the
manifest. Git control metadata is rebuilt rather than copied between roots.

## Fork isolation

A fork receives a new task, workspace, execution directory and ADR-0229 port
lease. It reconstructs the recorded Git commit and checkpoint overlay, then
creates a new container from the snapshot image. Source mounts, leases,
sessions, grants and egress bridges are not copied. Network admission is
checked again; an allowlisted fork gets a fresh egress lease.
The injected agent bundle digest is recorded and checked before restoring a
workspace; bundle drift refuses the fork rather than silently substituting
another runtime bundle.

Only `postStart` and `postAttach` hooks run again. Creation and installation
hooks must not overwrite a checkpoint's already-installed filesystem.
In-place restore is allowed only for an archived/restorable workspace;
otherwise the restore operation creates a fork.
During in-place restore, the previous stopped container and image association
remain available for rollback until both the workspace and new runtime succeed.

## Budgets and deletion

`sandboxSnapshotBudgetBytes` is part of the workspace lifecycle policy and
defaults to 1 GiB. It is independent of `blobBudgetBytes`, also defaulting to
1 GiB. Checkpoint data and committed image storage count against the sandbox
snapshot budget. Over-budget creation fails and compensates.

Unpinned snapshots expire after 30 days. Pinning prevents retention expiry.
Deletion tombstones the record, invokes the preview-revocation integration
hook, and removes the image only after runtime, fork and in-flight references
are gone. Checkpoint pins and blobs are released after image removal. Cleanup
is scoped to the current deployment and never invokes `docker system prune`.

## Local preview links

The Runtime environment section in Settings and the workspace overview shares
the snapshot and preview panels. Snapshot controls create checkpoints with
optional workspace-relative exclusions, show age, image size, pinning and
phase, and expose pin, delete, fork and permitted restore operations. Budget
usage comes from the Host ledger, including checkpoint storage; summing image
sizes in the UI would undercount it. Busy and over-budget failures remain
visible without discarding the current list.

Preview links serve the local owner on this machine or one paired desktop
(see [Paired-device previews](#paired-device-previews)). There are no anonymous
public links.

Desktop commands run through trusted local IPC. A headless owner uses the
authenticated, loopback-only internal service plane; paired-device RPC cannot
invoke these commands. Create/open responses contain transient credentials
and are excluded from durable idempotency receipts. Headless opening returns
the bootstrap URL; the desktop UI hands that URL to the embedded browser.

| Command | Input | Result |
| --- | --- | --- |
| `sandbox_preview_context` | `projectId` | Host-owned runtime targets, approved ports and snapshot budget usage |
| `sandbox_preview_create` | `request` with target, port, audience and optional `expiresInSeconds` | Grant and one-shot bootstrap URL |
| `sandbox_preview_list` | `projectId`, optional `workspaceId`, `pageSize`, `pageToken` | Page of grant metadata without credentials |
| `sandbox_preview_revoke` | `grantId` | Revoked grant with updated revision |
| `sandbox_preview_open` | `grantId` | Fresh bootstrap URL for the embedded browser |

The TypeScript adapter is `lib/sandbox/previews.ts`; hooks live under
`hooks/sandbox/`. The UI offers 5-minute, 15-minute, 30-minute and one-hour expiry choices,
a live countdown, copy-once access, embedded-browser opening and revocation.
Opening uses the existing embedded-browser request flow. If that surface
cannot open a pane, the failure is visible rather than silently opening a
different browser.

`PreviewGrantV1` records the target runtime generation, resolved port, port
lease, audience, expiry and revision in `task-workspaces.sqlite`. A fixed port
must be approved by the target's current environment spec. A
`workspace-lease-offset` is resolved against that workspace's own lease, so a
new fork follows its new block. Snapshot cleanup invokes the installed preview
revoker before releasing artifacts.

The link contains a one-shot, 60-second credential in the URL fragment:
`/__cognia_bootstrap#<token>`. The bootstrap page exchanges it by POST for an
HttpOnly, host-only, SameSite=Strict cookie, clears the fragment, and navigates
to `/`. Tokens never appear in URL queries or list responses. Saved browsing
history and persisted dock tabs exclude bootstrap pages. The grant lasts
15 minutes by default and cannot exceed one hour; process restart invalidates
its credentials even though metadata remains in the ledger.

Preview traffic uses a dedicated loopback listener, separate from Companion.
The origin is `http://p-<id>.localhost:<port>`. Exact Host matching prevents
alternate names from reaching a grant. The planned compatibility mode
`http://127.0.0.1:<per-grant-port>` is disabled in the UI and rejected by the
Host: cookies are shared across ports, so that mode cannot isolate application
sessions. Targets unable to resolve `*.localhost` remain unsupported until
an isolated-storage or separately validated hostname alternative is available.
Each request and WebSocket upgrade
rechecks the grant and runtime authority; revocation and expiry terminate live
responses, including SSE and upgraded streams. The existing `open_port` relay
works without Docker port publishing, including with `network=none`.

The client collects every list page using the shared paging adapter and refuses
an incomplete or repeated-cursor result. Reopening a grant replaces any
unredeemed bootstrap credential; an older copied URL then cannot be redeemed.

## Paired-device previews

The owner can share a grant with one paired desktop by choosing it as the
audience (`{ kind: "pairedDevice", deviceId }`). Creating it requires that the
device still holds `workspace.write`; choosing it is the owner's approval for
that device, project and port. A paired grant has no listener and no bootstrap
secret: its origin is the device route `/api/sandbox/previews/<id>/`, and the
owner cannot open it locally (`sandbox_preview_open` refuses with
`preview_paired_grant_opens_on_device`).

| Route | Purpose |
| --- | --- |
| `GET /api/sandbox/previews` | Live grants shared with the calling device whose project it may still reach |
| `/api/sandbox/previews/{grant}/…` | Opaque HTTP and upgrade proxy for that grant |

Both are device routes: bearer + DPoP, then `device_can_control` and the
`environment_port_access` approval authority for the grant's project. A grant
shared with another device answers 404, exactly like a missing one; withdrawn
control answers 403; a revoked, expired or invalidated grant answers 410. Each
request also rechecks the runtime generation and port approval, and the relay
re-authorizes the device every two seconds while a stream is open. Revocation,
expiry and lost control close live bodies and upgraded streams. Preview cookies
are stripped on the way in and made host-only on the way out.

The paired desktop opens a grant through the same native loopback relay as
forwarded environment ports (`crates/cognia-codeserver/src/relay.rs`), which
accepts only `/api/sandbox/previews/<32 lowercase hex>/`, pins the Host
certificate and signs every proxied request with the device key. The system
browser only sees `http://127.0.0.1:<port>/`. Settings on a paired desktop
lists "Shared with this device" (`lib/sandbox/paired-previews.ts`,
`hooks/sandbox/use-shared-sandbox-previews.ts`); a grant that leaves the list
closes its relay.

Phones and browsers are intentionally inert: a WebView cannot attach DPoP and
the WAN carrier transports RPC frames, not HTTP streams. `PairedPreviewSupport`
documents this, the owner picker lists such devices disabled with an inactive
label, and tests pin both.

## Audit and metrics

Every mutating snapshot operation (`create`, `delete`, `pin`, `fork`, `restore`)
and every preview `create`, `open` and `revoke` writes an audit record
(`sandbox_snapshot_<op>`, `sandbox_preview_<op>`) scoped to the project, with
`host-service` as the actor because these commands require the Host's service
scope. Failed snapshot operations record only the error code. Refused device
requests are audited with the device id (`sandbox_preview_device_request`);
admitted ones are only counted, since a page loads many assets. Revocations
record their reason: `owner`, `invalidated` or `snapshot_deleted`.

`/metrics` exposes `cognia_sandbox_preview_events_total{event}` (`created`,
`created_paired`, `opened`, `redeemed`, `revoked`, `device_request`,
`device_denied`) and
`cognia_sandbox_snapshot_operations_total{operation,outcome}`. Both label sets
are closed.

## Providers and verification

Capabilities are separate flags: `filesystemCheckpoint`, `forkFromCheckpoint`,
`pauseResume` and `memoryResume`. Local Docker supports filesystem checkpoints
and forks. E2B retains pause/resume but refuses checkpoint forks with a labelled
unsupported reason until its API is verified. Each remote provider declares its
own flags and the Host narrows them to what it can drive. An older Host
omitting capability flags must not be assumed to support snapshots.

The targeted compilation check is:

```sh
cargo check --offline -p cognia-task-workspace -p cognia-sandbox-pool --tests
```

Co-located tests use `FakeContainerApi` for failure paths and isolation checks.
Real-Docker round-trip tests are marked
`#[ignore = "requires a real Docker daemon"]`; their doc comments give the
exact invocation. They require a daemon and are separate from compile and fake
test evidence. The round-trip test uses the preloaded image named by
`COGNIA_TEST_SNAPSHOT_IMAGE` (default `alpine:3.20`) and never pulls it.
Tests that bind sockets cannot run in a socket-restricted sandbox.

Verified on 2026-10-17 (macOS 26.5): the system resolver maps any
`*.localhost` name, nested ones included, to `127.0.0.1` and `::1`, so the
macOS system WebView resolves per-grant hostnames; Chromium resolves
`*.localhost` itself. The preview listener tests, including the dedicated
loopback origin, ran against real sockets on the Host. Not yet verified:
WebView2 on Windows, WebKitGTK on Linux, and a full create/redeem/open/revoke
pass inside the native app (the Tauri agent-debug bridge was unavailable).
The numeric-host fallback stays unavailable. Unit tests and offline Rust
compilation do not prove native cookie behavior.

See [ADR-0231](/docs/adr/0231-sandbox-snapshots-join-rootfs-and-workspace).
