# microVM & Web

<Status variant="beta" />

<TLDR>
  `lib/sandbox/microvm-bridge.ts` exposes the currently accepting e2b adapter; per-session tier,
  policy, target, and the bound adapter live on an immutable `SandboxRuntimeRef`. Unregister starts
  a graceful drain: new bindings fail while existing owners continue. The e2b pool separately tracks
  workspace-handle and runtime-ref ownership, closes after the final owner, and retains failed closes
  for retry. Application shutdown forces best-effort disposal.
</TLDR>

## The adapter registry — `microvm-bridge.ts`

**One** registry: the E2B plugin registers and unregisters its exec adapter on
activate/deactivate. The per-session "active tier" map this module used to own is gone — the tier
now travels on the immutable `SandboxRuntimeRef` that `resolveSendOptions` binds
(see [Execution overview](./execution-overview)), so it can no longer drift away from the ceiling
and the GUI target that were resolved with it.

```ts title="lib/sandbox/microvm-bridge.ts (registry)"
let registeredImpl: MicrovmExecAdapter | null = null

/** Register the microvm exec adapter (called by the e2b plugin on activate). */
export function setMicrovmExec(impl: MicrovmExecAdapter | null): void {
  if (registeredImpl && registeredImpl !== impl) drainingImpls.add(registeredImpl)
  registeredImpl = impl
}
export function getMicrovmExec(): MicrovmExecAdapter | null {
  return registeredImpl
}
```

The adapter is **owner-scoped**: every call names the runtime ref it belongs to, so one E2B
workspace can be claimed, reused across a session's calls, and released with the session.

The disposer returned by adapter registration means “stop accepting new bindings and drain existing
owners.” A bound runtime record keeps the adapter instance it acquired; it does not re-read the
global registry on execute or release. Retire/release failures stay in a cleanup-only ledger and are
retried by later session release. The existing `APP_CLOSING` path calls `disposeMicrovmAdapters()` as
the force-clean boundary.

```ts title="lib/sandbox/microvm-bridge.ts (adapter)"
export interface MicrovmExecAdapter {
  preflight?(ownerRef: string, workspaceRoot?: string, ownerGroup?: string): Promise<void> | void
  execute(ownerRef: string, payload: MicrovmExecPayload): Promise<MicrovmResult>
  release?(ownerRef: string): Promise<void> | void
  dispose?(): Promise<void> | void
}
```

The payload shapes mirror the Rust `SandboxCommand` / `PolicyRequest` so the OS path and the microVM
path are interchangeable from the plugin's point of view. `ceiling` is the session's resolved cap,
carried separately from the per-call `request` so the adapter can tell "the operator capped this"
from "this call simply needs less":

```ts title="lib/sandbox/microvm-bridge.ts (shapes)"
export interface MicrovmResult { exit_code: number; stdout: string; stderr: string; duration: number; timed_out: boolean; stdout_truncated?: boolean; stderr_truncated?: boolean }
export interface MicrovmCommand { argv: string[]; cwd: string; env: Record<string, string>; stdin: string | null; timeout: number }
export interface MicrovmRequest { writable: string[]; readable: string[]; targetFiles: string[]; maxCpuSeconds: number; maxMemoryMb: number; network: "off" | "on" | "allowlist"; networkHosts: string[] }
export interface MicrovmCeiling { network?: "off" | "on" | "allowlist"; maxCpuSeconds?: number; maxMemoryMb?: number }
export interface MicrovmExecPayload { tool: string; command: MicrovmCommand; request: MicrovmRequest; ceiling?: MicrovmCeiling }
```

## The e2b exec adapter — `microvm-exec.ts`

`buildMicrovmExec` executes against the sandbox already claimed by the runtime ref. It does not
provision or close a VM per command. Preflight requires a live E2B-backed workspace handle, and the
pool increments runtime ownership before execution. Releasing the workspace handle stops new claims;
the VM remains alive until its final runtime owner exits. Close is idempotent, and a failed close
leaves the pool entry available for a later cleanup retry.

Both E2B response streams are UTF-8-truncated to 1,000,000 bytes before crossing the tool boundary.
The visible `... (truncated)` marker and independent `stdout_truncated` / `stderr_truncated` flags
preserve which stream exceeded the cap; downstream tool rendering may still apply its existing
30,000-character display limit.

`buildBashCommand` (`microvm-exec.ts:84-92`) exports env vars inline and pipes stdin via `<<<`, with
both env names and values shell-escaped. The default factory dynamically imports `@e2b/sdk` and calls
`Sandbox.create`, surfacing a one-line install hint when the SDK is absent — the same strict-mode
pattern used everywhere in the sandbox layer:

```ts title="plugins/e2b-sandbox/src/microvm-exec.ts:112-123 (excerpt)"
try {
  mod = (await (Function("s", "return import(s)") as (s: string) => Promise<unknown>)(
    "@e2b/sdk"
  )) as { Sandbox?: unknown }
} catch {
  throw new Error(
    "@e2b/sdk is not installed. Install it with `pnpm add @e2b/sdk -w`, then configure " +
      "E2B Sandbox in Settings → Plugins."
  )
}
```

<Callout type="warn">
  AgentENV requires a Linux 6.8+ host with `/dev/kvm`; `127.0.0.1:8000` works only when Cognia
  runs on that same host and network namespace. For a remote AgentENV host, use its reachable IP
  address or domain. Follow the [AgentENV single-node quick
  start](https://github.com/kvcache-ai/AgentENV#-quick-start-single-node) to install and start the
  server. AgentENV currently has no built-in authorization, so keep it on a trusted network or put
  it behind an authenticated proxy.
</Callout>

For the frontend workspace/T4 bridge, open Settings → Plugins → E2B Sandbox and set "AgentENV /
E2B API URL" to the reachable endpoint; leave it empty to use E2B Cloud. To use the MCP server,
separately open Settings → MCP Servers, configure the E2B preset, and attach it to the current
character. The preset passes its own `E2B_API_KEY` and `E2B_API_URL` values to the spawned process.
The workspace/T4 bridge reads the plugin settings and maps the URL to the SDK's `domain` option; it
does not read host process environment variables or reuse the MCP preset values.

## The e2b workspace backend — `workspace-backend.ts`

The same plugin also implements `E2BWorkspaceBackend` for Marketplace integrations. When an
integration selects `worktreeMode: "e2b"`, its AI loop runs inside a fresh Firecracker microVM
instead of the host filesystem. Each `clone()` provisions a sandbox and clones into
`/tmp/cognia/<repo>/<stamp>`; `commitAndPush()` runs `git add/commit/push` inside the sandbox.

```ts title="plugins/e2b-sandbox/src/workspace-backend.ts:74-90 (clone)"
const stamp = this.opts.now().toString(36)
const safeRepo = opts.repoFullName.replace(/[^a-zA-Z0-9._-]/g, "_")
const cwd = `/tmp/cognia/${safeRepo}/${stamp}`
await execChecked(sandbox, { cmd: `mkdir -p ${shellEscape(cwd)}` })
const remote = `https://x-access-token:${opts.token}@github.com/${opts.repoFullName}.git`
await execChecked(sandbox, {
  cmd: `git clone --branch ${shellEscape(opts.branch)} --depth 20 ${shellEscape(remote)} ${shellEscape(cwd)}`,
})
```

<Callout type="info">
  The workspace backend and T4 exec share the same live plugin-configuration resolver. The default
  factory dynamically imports `@e2b/sdk` and calls `Sandbox.create`.
</Callout>

## Browser code execution — not a sandbox family

`lib/sandbox/web/index.ts` held a `getWebSandboxService()` stub whose `execute` always returned
`ok: false`, described as the surface "a plugin reaches through `executeCode(language, code)`". No
such caller existed anywhere in the tree, and the `PluginSandbox` the description referred to is gone
too. The stub was removed rather than left as a placeholder for a runtime nothing asked for.

The real browser execution path is `lib/native/code-execution-strategy.ts`
(`executeCodeWithSandboxPriority`). JavaScript, HTML, and CSS run in an opaque-origin
`sandbox="allow-scripts"` `srcdoc` iframe with `connect-src 'none'`. Each run has a nonce and accepts
messages only from that iframe's `contentWindow`; timeout and abort remove listeners, timers, abort
handlers, and the frame. Python routes to `canvas_run_python` on desktop. TypeScript, JSX, and TSX
return the existing unsupported result because no compiler/runtime is installed.

## Cross-boundary types — `types/system/sandbox.ts`

The result shape returned by sandboxed plugin script executions, plus the consumption metadata the
scheduler uses to carry quota bookkeeping across the boundary:

```ts title="types/system/sandbox.ts:6-28 (entrypoints + consumption)"
export type SandboxEntrypointId =
  | "chat-code-block"
  | "ai-code-block"
  | "workflow-code-step"
  | "scheduler-script"
  | "computer-operation"
  | "designer-preview"

export type SandboxConsumptionMode = "interactive" | "background"
export type SandboxDegradedBehavior = "disable" | "blocked-result" | "bypass"

export interface SandboxConsumptionMetadata {
  entrypoint: SandboxEntrypointId
  mode: SandboxConsumptionMode
  degraded_behavior: SandboxDegradedBehavior
  requires_preflight: boolean
  sandbox_enabled: boolean
  blocked: boolean
  bypassed: boolean
  used_quick_run: boolean
  policy_profile?: string | null
}
```

`SandboxExecutionResult` (`types/system/sandbox.ts:35-47`) — `ok`, `value?`, `logs?`, `error?`,
`durationMs?`, `consumption?` — never throws across the boundary.
