# Lark / Feishu Setup Guide

This guide walks you through creating a Lark (Feishu) bot app and connecting it to cognia-next.

## Prerequisites

- A Lark / Feishu account with permission to create custom apps.
- Access to the [Lark Developer Console](https://open.feishu.cn/app).

---

## 1. Create a Lark Custom App

1. Open the [Lark Developer Console](https://open.feishu.cn/app).
2. Click **Create custom app**.
3. Enter an app name (e.g. "cognia-bot") and description, then click **Create**.
4. Note the **App ID** (`cli_...`) and **App Secret** on the **App Credentials** page
   (Menu: App settings → App credentials).

---

## 2. Configure Event Subscriptions

Lark sends messages to your bot via an event subscription. cognia-next supports two transport modes.

### Option A — Long Connection (Recommended)

Long connection establishes a persistent WebSocket from cognia-next to Lark's servers.
No public webhook URL is required.

1. Go to **Event subscriptions** in your app's menu.
2. Under **Subscription method**, select **Use long connection to receive events**.
3. Subscribe to the following event:
   - `im.message.receive_v1` — Bot receives a message

Click **Save**.

### Option B — Webhook

A public HTTPS endpoint on the same machine is required.

1. In cognia-next, create the Lark adapter with **Webhook** selected, then reopen the saved adapter.
2. Start the Cloudflared tunnel from **Settings → Companion → Tunnel**.
3. Copy the generated callback URL from the Lark configuration dialog. It has the shape `https://.../webhook/lark/<adapterId>`.
4. In Lark, go to **Event subscriptions** in your app's menu.
5. Under **Subscription method**, select **Configure request URL** and paste the generated callback URL.
6. Lark will send a verification request; cognia-next's Rust HTTP proxy handles the handshake.
7. Subscribe to the following event:
   - `im.message.receive_v1` — Bot receives a message

Click **Save**.

---

## 3. Obtain the Verification Token and Encrypt Key

Still on the **Event subscriptions** page:

- **Verification Token**: Copy the token shown under "Verification Token". This is required.
- **Encrypt Key** (optional): If you want payload encryption, toggle **Enable Encrypt Key** and
  copy the generated key. Store it securely — it is required to decrypt incoming events.

> **Note**: If Encrypt Key is enabled, cognia-next will automatically decrypt events using
> AES-256-CBC with the key you provide.

---

## 4. Grant Required Scopes

Your app needs the following permissions. Go to **Permission management** and add:

| Scope                              | Purpose                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| `im:message.p2p_msg:readonly`      | Receive user private messages                                                              |
| `im:message.group_at_msg:readonly` | Receive user group @mentions                                                               |
| `im:message.group_msg`             | Receive unmentioned user group messages; required alongside history read for group history |
| `im:message.history:readonly`      | Read history (alternatively `im:message:readonly` or `im:message`)                         |
| `im:message:send_as_bot`           | Send as the bot                                                                            |
| `im:chat`                          | Access chat information                                                                    |
| `im:resource`                      | Access images/files                                                                        |

For bot-driven tests, add `im:message.group_at_msg.include_bot:readonly` for @mentions and `im:message.group_msg.include_bot:read` for the unmentioned second reply. These scopes are optional for initial human-only testing. Subscribe to `card.action.trigger` for interactive card callbacks, and publish changes to permissions, events and callbacks. Credential/history probes do not verify target subscriptions or real card clicks. See [local live testing](./local-live-testing) for separate App ID/Open ID configuration and the acceptance table.

Click **Apply permissions** and wait for approval (self-service for custom apps in the same org).

---

## 5. Install the Bot to Your Workspace

1. Go to **Bot** in the menu. Enable the bot feature.
2. Go to **Version management & release** → Click **Create version**.
3. Fill in version details and click **Apply for online release** (or "Release internally" for
   org-only bots).
4. After approval, add the bot to the chats or groups where you want it to operate.

---

## 6. Configure in cognia-next

1. Open **Settings → Connections → Add adapter → Lark**.
2. Fill in the fields:

| Field                  | Value                                           |
| ---------------------- | ----------------------------------------------- |
| **App ID**             | `cli_...` from App credentials                  |
| **App Secret**         | App Secret from App credentials                 |
| **Verification Token** | Token from Event subscriptions                  |
| **Encrypt Key**        | (Optional) Encrypt Key from Event subscriptions |
| **Transport**          | "Long connection" (recommended) or "Webhook"    |

3. Use the **Setup guide** in the dialog to review app creation, feature-specific permissions,
   event and card callback subscriptions, publishing, and first-message checks. Copy the scope
   list for the features you plan to use; optional scopes are not enabled automatically.
4. Click **Validate** to verify App ID + App Secret. This checks credentials only, not event
   delivery, granted permissions, or card callbacks. Editing either credential clears the result.
5. Click **Create** to save. The adapter will start automatically. If the developer console
   requires a live long connection before saving subscriptions, return to it after this step.
6. For an existing connection, **Configuration and setup guide** reopens the same guide.
   Confirm bot identity and connection health, configure the Agent and reply/admission policy,
   then verify a private message, a group @mention, and a real card click in Feishu.

---

## 7. Resolving the Bot's Own open_id

The adapter uses `selfBotOpenId` to detect when the bot is mentioned. cognia-next resolves this
at startup via the Lark API. If the bot's open_id cannot be resolved, mention detection falls back
to checking the `app_id` in event headers.

You can also find your bot's open_id by calling:

```
GET https://open.feishu.cn/open-apis/bot/v3/info
Authorization: Bearer <tenant_access_token>
```

The response includes `bot.open_id`.

## 8. Bot Menu / Quick Commands (快捷指令)

Feishu bot menus (快捷指令) are configured in the developer console — Feishu exposes
no API to create them. cognia-next maps each menu item's `event_key` to an action
you choose, then runs an assistant turn when the menu is clicked.

1. In the Lark console, open **Bot → Bot menu** (机器人 → 机器人自定义菜单) and add a
   menu item. Set its action to **push an event** and give it an `event_key`
   (e.g. `agenda`).
2. Under **Event subscriptions**, also subscribe:
   - `application.bot.menu_v6` — Bot menu clicked
3. Release a new version so the menu and the new event subscription take effect.
4. In cognia-next, open **Settings → Connections → Lark → Quick commands** and add
   a row mapping the `event_key` to an action:
   - **Prompt** — free text sent to the assistant (e.g. `Summarize my unread messages`).
   - **Slash command** — a command line (e.g. `/agenda today`).
5. Clicking the menu in Lark now drives an assistant reply in that 1:1 chat. An
   `event_key` with no mapping falls back to its label / raw key as the prompt, so
   the click is never silently dropped.

Bot menus are static developer-console configuration and are mainly useful in
direct bot chats. Keep them to commands such as `status`, `new`, and `help`;
they are not a per-topic progress surface. CardKit progress cards are used for
live Agent status inside topics.

Feishu exposes follow-up bubbles through
`POST /im/v1/messages/:message_id/push_follow_up`. In **bot-user direct chats**,
cognia-next projects up to three temporary Stop, status, and approval controls
from the latest progress card. A click is authorized using the real inbound
sender. The feature requires Feishu 7.20+ and a latest bot message no older than
600 seconds. The API rejects groups and topics with `230003`, so durable CardKit
buttons remain the topic control surface. Expired, superseded, or ambiguous
bubble delivery degrades only this temporary enhancement, never the progress
card or final reply.

### Run progress cards

Open the Feishu connection editor and expand **Card appearance** to configure
header colors, spacing, width, process display, history expansion, a custom title,
and the visibility of elapsed time, progress, artifacts, final-reply quotes and
footers. **Reset card appearance** restores the defaults in the form; save to
apply them. Saving preserves settings from other panels and restarts the connection.

Appearance applies to native and fallback progress cards and final replies.
Warning and error headers retain their status colors. Custom titles are limited
to 60 characters and sanitized before delivery. Process display changes apply to
new runs; an existing native timeline finishes in its original mode. Final-reply
quote visibility controls the card's quote, independently of native reply quoting.

Advanced appearance includes desktop/mobile text sizes, a subtitle, an uploaded
header image key, up to three comma-separated tags, and a pair of light/dark
process-panel colors. Invalid image keys, color pairs or template settings block
saving and show an explanation. Panel colors apply to the in-card process panel;
Feishu's native process timeline controls its own appearance.

**Use a card template for successful replies** accepts a published template ID and
a fixed version. Define the template variables `answer`, `status`, `title`,
`quote`, `elapsed_ms`, and `details_url` in the Feishu card builder. Error and
interrupted replies keep the built-in status card. Replies that combine a result
with other segments use the built-in card to preserve the surrounding content.
An explicit template rejection falls back to that card using the same message
UUID; network, permission and rate-limit errors retain normal delivery handling.

When native process events are available, execution details appear in Feishu's
process timeline. Otherwise, the same Card 2.0 message shows an expandable process
panel. Status, elapsed time, artifacts, and approval guidance stay outside that
panel; completed or cancelled history starts collapsed and remains readable.

Heartbeats update changed status only, without rewriting unchanged history or
buttons. Approval, pause, recovery, and completion bypass the normal progress
refresh delay. Restart recovery reuses the acknowledged card state and reconciles
uncertain writes before applying new content. Streaming timeout (`200850`) or
closed-stream (`300309`) errors repair the existing Card 2.0 entity.

Changed non-streaming components can share one CardKit batch update. Streaming
text keeps its dedicated endpoint. Batch retries and restart recovery retain the
original sequence and UUID before applying newer state.

### Interactive cards

Generated interactive replies use Card 2.0 (Feishu client 7.20+). They support
native checkboxes, multiline inputs, dates/times, multi-selects, form submit/reset
and required fields, columns and collapsible panels. Form values are delivered
together as one callback to the Agent. This does not imply local A2UI data-model
writeback. Tables and charts render natively where Feishu permits their placement;
unsupported row/chart interactions remain informational. Native person pickers
can be supplied in platform card JSON; the generic A2UI schema has no person-picker
component. Unsupported/oversized layouts retain readable content as a fallback.
Incoming Card 2.0 bodies and nested containers are preserved in Inbox; unsupported
components remain inspectable in the raw view.

### Recipient-only group cards (plugin API)

Plugins with `connectors:send` can opt a queued card into private delivery by
setting `request.metadata.larkEphemeral = { recipientOpenId: "ou_..." }` before
calling `ctx.connectors.enqueueSend(adapterId, conversationKey, request)`.
Use exactly one card or A2UI segment, the original bot identity, and an ordinary
group destination. Grant a chat-read scope (`im:chat:read`, `im:chat:readonly`, or
`im:chat`) as well as the bot message scope so group mode can be verified.

Feishu only shows these temporary cards to online recipients, without a message
notification; they must not be the only approval notification. Topic groups,
thread replies, send-as-user, normal edits, and sibling-adapter rerouting are
rejected. They never fall back to public messages. A lost POST response is marked
`delivery_unknown` instead of being resent automatically. After use, call
`ctx.connectors.deleteEphemeralCard(adapterId, platformMessageId)` to remove it.

Official contracts: [Card 2.0 components](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/feishu-cards/card-json-v2-components/component-json-v2-overview),
[batch updates](https://open.feishu.cn/document/cardkit-v1/card/batch_update), and
[recipient-only cards](https://open.feishu.cn/document/server-docs/im-v1/message-card/send-message-cards-that-are-only-visible-to-certain-people).

### Verify topic no-@ delivery

Enabling `im:message.group_msg` in the console is not enough: permission and
event-subscription changes only take effect after a new app version is released.

1. Grant `im:message.group_msg`, keep `im.message.receive_v1` subscribed, and release the app.
2. Add the released bot to a test group and create two separate topics.
3. In cognia-next open **Settings → Connections → Lark → Admission** and click
   **Start delivery probe** (or run `/agent verify` as an operator).
4. Within ten minutes, send one ordinary group/topic message without @-mentioning the bot.
5. Confirm readiness becomes **All messages verified**. The probe message is audited and is not
   executed as an Agent turn.
6. @-mention the Agent once inside topic A, then continue without @. Topic B and the parent group
   must remain mention-gated until independently activated.

Topic controls:

- `/agent status` — policy, expiry, dispatch mode, queue depth, active run, readiness, and recovery count.
- `/agent off` — close activation (activator or configured operator).
- `/agent verify` — start the ten-minute no-@ probe (configured operator only).

Choose **Queue** to preserve every new message as an independent FIFO turn. Choose **Steer** to
request live injection into an active run. The built-in Anthropic sidecar first persists the real
sender's message, then uses acknowledged SDK streaming input to queue it into the current query.
After a short burst window it closes that query's input so the run settles normally. A missing
acknowledgement, closed input, or non-Anthropic provider keeps the message and attachments durable
for replay at the earliest safe boundary. This guarantees live queued input; it does not claim to
rewrite a model HTTP request that has already been issued.

## 9. Help & Welcome Cards

cognia-next can greet users with an interactive card and answer `/help` with a
capability card. This is a **cross-provider** feature (every IM adapter shares it);
the card lists your configured quick commands as clickable buttons and explains the
bot's @-mention strategy. Clicking a quick-command button runs the same action as
the native bot menu.

- **On-demand help** — a message that exactly matches a help trigger (`/help` or
  `帮助` by default) serves a help card instead of running the assistant. Configure
  the trigger words under **Settings → Connections → Lark → Help & Welcome**.
- **Welcome on join / first message** — sent once per conversation. To receive the
  bot-join signal, subscribe these events in the Lark console and grant the scope:
  - `im.chat.member.bot.added_v1` — bot added to a group
  - `im:chat.access_event.bot_p2p_chat:read` — first 1:1 chat opened (scope)
- Sending interactive cards requires the **`cardkit:card:write`** scope.

Toggle the welcome card, edit trigger words, and set a custom welcome message under
**Settings → Connections → Lark → Help & Welcome** (the section appears on every
adapter's detail panel). The welcome card is on by default.

## 10. Send as Me (User OAuth)

By default the bot replies under its own identity. **Send as me** lets replies go out under
_your_ Lark identity instead, via an OAuth 2.0 authorization-code flow. This is optional — the
bot works fully without it, and falls back to the bot identity if the authorization ever expires.

Because Feishu only accepts **http/https** redirect URLs (custom app schemes like `cognia://`
cannot be registered in the console), cognia-next relays the callback through the same Cloudflared
tunnel used for webhooks: `https://<your-tunnel-host>/oauth/lark/callback` bounces the result back
into the desktop app.

### Setup

1. **Start a stable tunnel.** Open **Settings → Mobile Companion → Tunnel** and start the
   Cloudflared tunnel. Use a **named tunnel** so the host stays stable across restarts — Feishu
   matches the exact registered URL on every authorization.
2. **Grant user scopes.** In the Lark console → **Permission management**, enable and get approval
   for:
   - `offline_access` — **required**; Feishu only issues a refresh token when this is granted.
   - `im:message` and `im:message.send_as_user` — both are required to send as the user. See the [official send-message contract](https://open.feishu.cn/document/server-docs/im-v1/message/create). Reauthorize existing accounts after publishing the added scope.

   Re-release the app version after changing scopes.

3. **Register the redirect URL.** In the Lark console → **Security Settings → Redirect URL**, add
   the exact URL shown in cognia-next under **Settings → Connections → Lark → Send as me** (the
   "OAuth redirect URL" field, e.g. `https://<tunnel>/oauth/lark/callback`). Leave the field blank
   in cognia-next to use the tunnel-derived URL, or paste a custom one if you front the relay with
   your own domain.
4. **Connect.** Click **Connect account**. Your browser opens the Feishu consent page; approve it,
   and the relay returns you to cognia-next, which shows **Connected as \<name\>**.
5. **Enable.** Toggle **Send replies as me** on.

The flow uses PKCE (`S256`) — the verifier never leaves your device — and refreshes the user token
automatically, falling back to the bot identity if a refresh fails.

## Troubleshooting

| Symptom                                          | Likely cause                                                                                                                       |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| "Connection failed" on Test                      | Incorrect App ID or App Secret                                                                                                     |
| Events not received (long connection)            | Check that `im.message.receive_v1` is subscribed                                                                                   |
| Events not received (webhook)                    | Verify the webhook URL is reachable and returns 200                                                                                |
| Decrypt error                                    | Encrypt Key mismatch — ensure the key matches the one in Event subscriptions                                                       |
| Bot not responding in groups                     | Ensure the bot is installed to the group and has `im:message` scope                                                                |
| Bot menu click does nothing                      | Subscribe `application.bot.menu_v6` and map the `event_key` under Quick commands                                                   |
| No welcome card on join                          | Subscribe `im.chat.member.bot.added_v1`; ensure Welcome card is enabled under Help & Welcome                                       |
| Interactive cards render as plain text           | Grant the `cardkit:card:write` scope and re-release the app version                                                                |
| "Connect account" fails / `redirect_uri unmatch` | The redirect URL isn't registered in Security Settings, or the tunnel host changed — use a named tunnel and register the exact URL |
| "Send as me" still sends as the bot              | `offline_access` + `im:message` + `im:message.send_as_user` not granted/approved, or the authorization expired — reconnect the account                         |

Sources verified 2026-10-01: [message receive](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive), [history](https://open.feishu.cn/document/server-docs/im-v1/message/list), [card callbacks](https://open.feishu.cn/document/feishu-cards/card-callback-communication).
