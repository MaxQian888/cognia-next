# Extension Points v2

ADR-0026 (2026-05) closed 17 gaps in the cognia-next plugin platform. This
page is the practical reference: every new manifest field, runtime point,
and `ctx.*` namespace introduced, with the minimum viable shape a plugin
author needs.

For background and rationale, see
[ADR-0026 — Plugin Extension-Point Expansion](../adr/0026-plugin-extension-point-expansion).

## Manifest fields

Every new contribution uses the same lazy-factory shape:

```jsonc
// plugin.json — root level, parallel with themes / connectors / mcpServerPresets
{
  "ocrProviders": [
    {
      "id": "baidu",
      "label": "Baidu OCR",
      "entry": "providers/baidu.js",
      "export": "createBaiduProvider",
    },
  ],
}
```

`entry` is a relative path inside the plugin install root (no `..`, no
absolute paths, no NUL bytes). `export` is the named function the host
dynamic-imports on first use.

The six new manifest blocks:

| Field               | Drives                              | Permission      |
| ------------------- | ----------------------------------- | --------------- |
| `ocrProviders`      | OCR registry contributions          | `network:fetch` |
| `workspaceBackends` | Issue-loop / sandbox runners        | `process:spawn` |
| `messageRenderers`  | Custom `part.type` React components | `extension:ui`  |
| `aiProviders`       | Plugin-internal LLM / embedding     | `network:fetch` |
| `modalMounts`       | Declarative modal pre-registration  | `extension:ui`  |
| `chatMiddlewares`   | Around-style chat pipeline          | `agent:control` |

Plus `configComponent?: { entry, export }` for a per-plugin custom
settings UI panel.

## ctx.ocr — register an OCR provider

```ts
export async function activate(ctx: PluginContext) {
  const handle = ctx.ocr.registerProvider({
    id: "my-engine", // prefixed automatically as `<pluginId>:my-engine`
    label: "My OCR Engine",
    category: "specialist",
    shells: { browser: true, tauri: true, capacitor: false },
    credentialKeys: ["myocr-key"],
    extract: async (input, providerCtx) => {
      // ... call your backend and return OcrResult
    },
  })

  // Optional — the host calls this automatically on plugin disable.
  ctx.onDeactivate?.(() => handle.unregister())
}
```

## ctx.workspace — register an issue-loop backend

`E2BBackend`-shaped runtime (the same `clone / commitAndPush / remove`
contract `lib/github/workspace.ts` has always required). Replaces the
legacy `setE2BBackend()` singleton:

```ts
ctx.workspace.registerBackend({
  id: "my-sandbox",
  label: "My Sandbox",
  backend: {
    async clone({ repoFullName, branch, token }) {
      /* ... */
    },
    async commitAndPush({ workspace, message, remoteBranch }) {
      /* ... */
    },
    async remove(handle) {
      /* ... */
    },
  },
})
```

## ctx.renderer — custom message-part renderer

Plugins ship a React component keyed on `part.type`. Reserved types
(`tool-*`, `text`, `reasoning`, `file`, `a2ui`, `subagent`,
`agent-team-dispatch`, `artifact`, `sources`, `canvas`) are rejected — use a
plugin-prefixed type:

```ts
ctx.messagePart.registerPartRenderer("x-my-custom-block", MyBlockRenderer)
```

Or declaratively via `manifest.messageRenderers[]`:

```jsonc
{ "partType": "x-my-block", "entry": "renderer.js", "export": "MyBlockRenderer" }
```

## ctx.ai — plugin-internal LLM / embedding

**Important:** the main chat pipeline never resolves a plugin AI
provider. Use these calls for plugin-internal background tasks
(summarization, classification, embedding for plugin-owned vector
stores). Influence the main chat via `ctx.chat.use()` instead.

```ts
const { text } = await ctx.ai.chat([{ role: "user", content: "Summarize this." }])

const vectors = await ctx.ai.embed(["hello", "world"])
```

## ctx.modal — open a modal from anywhere

```ts
const handle = ctx.modal.openModal(MyModalComponent, { initialTab: "general" })
// Later:
handle.close()
```

The plugin component receives `{ onClose, modalId, args }`. Calling
`onClose()` pops the entry from the stack.

A modal declared in `manifest.modalMounts[]` is registered (lazily — the
component is imported on first open) and can be opened by its id:

```ts
const handle = await ctx.modal.openById("wizard", { step: 1 })
// → null if the id is unknown or its component fails to load
```

## ctx.chat — around-style middleware

A middleware wraps the **non-streaming full-reply** turn
(`runAndCaptureAssistantReply` — the connector / headless reply path), not
the streaming UI chat (where text is already on screen before any final
response exists). **Execution is gated behind a default-off flag**
(`setChatMiddlewareExecutionEnabled(true)`); registration always happens but
no middleware runs until the flag is enabled, so the feature is zero-overhead
by default. For the streaming UI chat, use the lighter `onBuildOptions` hook
to tweak options. Safety net: per-middleware timeout (5s default, 60s max),
error isolation (one throw skips that middleware), 3-strike circuit breaker
disables on repeated failure.

```ts
const dispose = ctx.chat.use(
  async (req, next) => {
    const before = Date.now()
    const res = await next()
    ctx.logger.info(`turn took ${Date.now() - before}ms`)
    return res
  },
  { id: "telemetry", priority: 10, timeoutMs: 3000 }
)
```

For a _transform-only_ hook (no short-circuit, no async wrapping), use
the lighter `onBuildOptions` hook instead:

```ts
export const hooks: PluginHooks = {
  async onBuildOptions(options) {
    if (options.systemPrompt) {
      return {
        ...options,
        systemPrompt: options.systemPrompt + "\n\nBe concise.",
      }
    }
  },
}
```

## ctx.capabilities — platform detection

Replaces direct `isTauri()` / `isMobile()` imports:

```ts
if (ctx.capabilities.tauri) {
  // Tauri-only path
} else if (ctx.capabilities.mobile) {
  // Capacitor mobile path
} else {
  // Browser path
}
```

## Per-plugin custom settings UI

Add `configComponent` to your manifest. The host renders your component
in the plugin's settings tab _instead of_ the auto-generated form derived
from `configSchema`:

```jsonc
{
  "configComponent": { "entry": "settings.js", "export": "MySettings" },
}
```

```tsx
export const MySettings: ConfigComponent = ({ config, onSave }) => {
  return <button onClick={() => onSave({ ...config, enabled: true })}>Enable</button>
}
```

## Theme CSS variables

Plugins can now contribute themes that override CSS custom properties at
runtime (variable names are constrained to `^--[a-z][a-z0-9-]*$`, values
≤200 chars, `</style>` rejected):

```jsonc
{
  "themes": [
    {
      "id": "midnight",
      "name": "Midnight",
      "isDark": true,
      "cssVariables": {
        "--background": "#0a0a0a",
        "--foreground": "#fafafa",
        "--accent-1": "oklch(0.7 0.15 220)",
      },
    },
  ],
}
```

## Slot revivals

Two previously deprecated slots are revived in v2:

- **`chat.message.actions`** — hover-action bar above each message,
  separate from the `chat.message.footer` host actions row.
- **`settings.ai`** — top of `api-key-section`, the canonical home for
  unified AI-settings plugin cards.
- **`sidebar.right.top` / `sidebar.right.bottom`** — above and below the
  resource panel inside the shared Context Workbench.
- **`panel.header` / `panel.footer`** — immediately around the active
  Context Workbench panel.

## Resource panels in the Context Workbench

Trusted frontend plugins can contribute panels declaratively:

```jsonc
{
  "permissions": ["extension:ui", "canvas:read", "project:read"],
  "contextPanels": [
    {
      "id": "insights",
      "entry": "context/insights.js",
      "export": "InsightsPanel",
      "resourceKinds": ["canvas-document", "project-file"],
      "activity": "inspect",
      "labelKey": "context.insights",
      "label": "Insights",
      "icon": "search-code",
      "requiredCapabilities": ["inspect"],
      "preferredMode": "wide",
      "retention": "stateful",
      // Optional behaviour hooks, resolved as named exports of the same
      // `entry` module as the renderer.
      "onFirstActivateExport": "onInsightsOpened",
      "getBadgeExport": "insightsBadge"
    }
  ]
}
```

`activity` must be one of `ai`, `comments`, `inspect`, `review`,
`preview-run`, `templates`, or `workspace`.

`resourceKinds` must be a non-empty subset of `canvas-document`,
`project-file`, `artifact`, `workflow`, and `session`. **`session` is the
chat right rail's fallback resource** — the dock shows it whenever no
artifact is open, so a panel that omits it will not appear in the rail's
default state.

The label is resolved through the plugin's existing i18n bundle; `label` is
the deterministic fallback. Unsupported icons fall back to the host panel
icon.

`retention` decides what happens to a panel the user switches away from:
`stateful` (default) keeps it mounted behind React's `<Activity>` so its
state and scroll position survive, while `ephemeral` unmounts it. Prefer
`ephemeral` for panels holding something expensive, such as a live
connection.

The imperative API uses the same namespaced registry, and accepts the same
fields inline instead of as export names:

```ts
const dispose = ctx.contextPanels.register({
  id: "live-insights",
  activity: "inspect",
  labelKey: "context.liveInsights",
  label: "Live insights",
  resourceKinds: ["canvas-document"],
  icon: "search-code",
  getBadge: (resource) => unreadFor(resource),
  onFirstActivate: (resource) => warmUp(resource),
  renderer: LiveInsightsPanel,
})

ctx.contextPanels.reveal("live-insights", "wide")
const context = ctx.contextPanels.getActiveContext()
const unsubscribe = ctx.contextPanels.onDidChangeActiveContext((next) => {
  // Identity, revision, selection, and capabilities only; never resource content.
})
```

`reveal()` can target only the calling plugin's applicable panels. It
respects user pinning, so a request can become pending instead of replacing
the selected panel. It also asks the host to bring its own container back on
screen first, so revealing into a collapsed chat dock or a closed mobile
sheet opens it rather than silently switching a panel the user cannot see.

Every panel requires `extension:ui` plus each declared resource permission:
`project:read`, `canvas:read`, `artifact:read`, `workflow:read`, or
`session:read`. Registration fails closed when one is missing, and a panel
already registered disappears from the rail the moment a permission is
revoked. Sandboxed Webview renderers are not supported.

### Driving the workbench

Registration alone cannot tell a panel whether it is on screen, how wide the
rail is, or push a count onto its activity icon. The same API covers all of
it:

```ts
// Activity-rail badge. Added to whatever the definition's own `getBadge`
// returns; 0 clears it.
ctx.contextPanels.setBadge("live-insights", 3)

// What the right rail is showing right now, or null when none is mounted.
const state = ctx.contextPanels.getWorkbenchState()
// { resource, mode, activePanelId, ownsActivePanel, userPinned, panelIds }

// Fires for both halves: which resource is in front, and how it is laid out.
const stop = ctx.contextPanels.onDidChangeWorkbenchState((next) => {
  if (next?.ownsActivePanel) startExpensiveWork()
  else stopExpensiveWork()
})

// Layout control, honoured only while this plugin owns the visible panel.
ctx.contextPanels.setMode("focus") // "collapsed" | "narrow" | "wide" | "focus"
ctx.contextPanels.setPinned(true) // queue automatic reveals as badges
```

`setMode()` / `setPinned()` return `false` when another contributor's — or a
native — panel is the visible one, so a plugin can never full-screen the
right rail out from under the user. `panelIds` lists only this plugin's own
panels; the rest of the workbench stays invisible to it. Every method here
also requires `extension:ui`, and `getWorkbenchState()` additionally requires
the read permission for the resource kind in front.

<Callout type="warn">
  `setMode("narrow")` and `setMode("wide")` are host-dependent. Where the
  workbench owns its own width — the editor and workflow side panels — they
  resize it. In the **chat dock** the width belongs to the surrounding
  resizable panel, so those two only update the recorded mode and nothing
  moves on screen; `"focus"` and `"collapsed"` work everywhere. Treat the
  narrow/wide pair as a hint, and don't build a layout that depends on it.
</Callout>

## Status & reference plugins

As of the SDK-completion pass, every surface below is **fully host-wired** —
the host renderer / consumer exists, not just the registry:

| Surface            | Host consumer                                                         | Reference plugin                        |
| ------------------ | --------------------------------------------------------------------- | --------------------------------------- |
| `themePacks`       | Appearance → **Theme packs** tab + one-click `applyThemePack`          | `cognia-appearance-demo` (declarative)  |
| `wallpapers`       | Appearance → **Wallpaper** tab (plugin entries merged + "Plugin" badge) | `cognia-appearance-demo` (declarative)  |
| `densityPresets`   | Resolved by name via `applyDensityPresetVars` (e.g. from a theme pack) | `cognia-appearance-demo` (declarative)  |
| `scheduledTasks`   | Real `ScheduledTask` Dexie row created on enable                      | `cognia-scheduling-demo` (declarative)  |
| `configComponent`  | Rendered in the plugin settings panel (falls back to the schema form) | bridge unit tests (`config-component-bridge`) |
| `modalMounts`      | Lazy declared-modal registry → `ctx.modal.openById`                   | bridge unit tests (`modal-mount-bridge`) |
| `chatMiddlewares`  | `runAndCaptureAssistantReply` (default-off flag)                      | bridge unit tests (`chat-middleware-bridge`) |
| `contextPanels`    | Context Workbench activity rail (chat dock, editor, workflow)        | `cognia-prompt-templates` (imperative)  |

> **Builtin limitation.** Import-based fields (those with an `entry` /
> `export` module — `ocrProviders`, `workspaceBackends`, `messageRenderers`,
> `aiProviders`, `modalMounts`, `chatMiddlewares`, `configComponent`,
> `contextPanels`) resolve their module only for **disk / marketplace-installed**
> plugins, where the install path is a real fetchable directory. Built-in plugins
> (`builtin://…`) cannot fetch a separate entry file, so they must register
> those surfaces imperatively via the `ctx.*` APIs instead. The
> declarative-data fields (`themePacks`, `wallpapers`, `densityPresets`,
> `scheduledTasks`, `modes`) work for builtins too — that is why the
> reference demos above are builtins.

## Migration cheat-sheet

If your plugin still uses the old paths, the host accepts them under
`@deprecated` shims. Migrate when convenient:

| Old                                       | New                                                              |
| ----------------------------------------- | ---------------------------------------------------------------- |
| `installOcrRuntime()` global              | `ctx.ocr.registerProvider(...)`                                  |
| `setE2BBackend(impl)`                     | `ctx.workspace.registerBackend({ id: "e2b", ... })`              |
| `registerNodeExecutor` side-effect import | `ctx.workflow.registerNode(...)` or `manifest.workflows.nodes[]` |
| `registerPluginI18n({ ... })`             | `manifest.i18n` (auto-wired)                                     |
| Direct `isTauri()` import                 | `ctx.capabilities.tauri`                                         |
