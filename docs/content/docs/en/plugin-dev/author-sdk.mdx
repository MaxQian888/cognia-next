# Public Plugin SDK and Runtime Contract

Use the packed `@cognia/plugin-sdk` package as the only Cognia dependency in a third-party TypeScript plugin. The package ships ESM, CommonJS, and declarations; it does not expose host registries, executors, factories, test reset functions, PKCE helpers, or internal session constructors.

## Public import map

| Import | Supported content |
| --- | --- |
| `@cognia/plugin-sdk` | `define*` helpers, stable constants, and public author types |
| `@cognia/plugin-sdk/manifest` | manifest, capability, permission, and contribution types |
| `@cognia/plugin-sdk/context` | `PluginContext`, `FullPluginContext`, and callable context API interfaces |
| `@cognia/plugin-sdk/hooks` | hook payloads and hook interfaces |
| `@cognia/plugin-sdk/contracts` | read-only canonical contract metadata |
| `@cognia/plugin-sdk/events` | stable event constants and event payload types |
| `@cognia/plugin-sdk/permissions` | public permission values and permission types |
| `@cognia/plugin-sdk/extensions` | extension-point constants and contribution types |
| `@cognia/plugin-sdk/api/tool`, `/api/native-anthropic-tool` | explicitly supported compatibility subpaths |

Never import `@/lib`, `@/types`, `@cognia/plugin-sdk/host`, or an app-private `@cognia/*` package. The `host` entry exists only for one repository migration window and is deliberately absent from npm exports and tarballs.

## Contract-driven authoring

Use `cognia plugin contract` before editing a manifest or choosing a runtime. It reads the generated canonical catalog, so new capabilities, contributions, permissions, entries, and path fields become discoverable without updating an authoring checklist.

```bash
# New plugin: select only the contracts needed for a tool and context panel.
cognia plugin contract \
  --plugin-type frontend \
  --capability tools \
  --contribution contextPanels \
  --point chat.input.actions \
  --point-kind ui-slot \
  --permission extension:ui \
  --json
cognia plugin new support-panel --kind ts --json

# Existing plugin: inspect first, then query the records for the extension.
cognia plugin info . --json
cognia plugin contract \
  --plugin-type hybrid \
  --capability python \
  --contribution tools \
  --json

# Compare compatible runtime-entry rules before committing to a runtime.
cognia plugin contract --plugin-type frontend --plugin-type hybrid --json
```

Selectors are repeatable. Point kinds are `ui-slot`, `hook`, `activation`, and `runtime`. An unfiltered query returns the complete inventory; a filtered query returns the selected and related contract records while retaining full-catalog counts. The v2 JSON envelope includes the generated `pluginPoints` catalog alongside capabilities, contributions, permissions, runtime entries, and path fields. Unknown selectors fail with a structured input error, and the command never writes files.

Inspect `support`, `pythonExecution`, `execution`, point `status`/`stability`, `formFactor`, replacement ids, permissions, entry paths, minimum host versions, and path-field contracts in the result. Require explicit user confirmation before generating anything marked experimental, and carry that warning into the completion report. Do not target a deprecated point for new work; use its `replacementId`. A JavaScript-executed contribution cannot be authored for a Python-only or WASM runtime; stop before mutation and offer compatible types reported by the contract, commonly `frontend` or `hybrid`.

After approval, scaffold new work with `cognia plugin new ... --json`, or preserve unrelated files when extending an existing plugin. Run `cognia plugin sync-types`, implement only against `@cognia/plugin-sdk` and `@cognia/plugin-ui`, then verify with `doctor`, `lint --json`, runtime tests/typecheck, `build --json`, and `info --json`. Key generation, signing, installation, reload, export, and publishing are separate explicit operations.

## Runtime matrix

| Manifest type | Required entry | JavaScript lazy contributions | Notes |
| --- | --- | --- | --- |
| `frontend` | `main` | allowed | Browser/Tauri availability follows `runtimeCompatibility` |
| `python` | `pythonMain` | rejected | Python declarations cannot execute JavaScript contribution factories |
| `hybrid` | `pythonMain`; `main` when JS contributions exist | allowed with `main` | Each runtime is loaded independently |
| `wasm` | `wasmMain` and `wasm.apiVersion` | rejected | Desktop Component Model host |
| `vscode-extension` | one of `vscodeMain`, themes, grammars, icon themes, snippets, or languages | VS Code contributions only | Declarative-only extensions do not need `vscodeMain`; code extensions do |

## UI extension requirements

Query the exact UI point before writing its component. The returned `formFactor` is the host layout contract: `icon` for a square control, `row` for compact actions, `block` for a stacked band, and `panel` for an owned scrolling region. Import UI primitives from `@cognia/plugin-ui`; `cognia plugin build` keeps both it and React external so the plugin uses the host's shared React and theme. Do not import host components or use `react-dom` portals.

Plugins own their displayed copy. Provide manifest i18n entries and localized accessible names, placeholders, empty/error states, and dialog close labels. `@cognia/plugin-ui` cannot read the host's `next-intl` catalog.

`engines.cognia` is the compatibility authority. Lint and install reject unknown capabilities and a lower bound older than any declared capability's catalog minimum.

Desktop JavaScript plugins execute under Cognia's checksum-pinned bundled Node 26 runtime, with 26.3.1 as the minimum patched version. A plugin cannot choose a system Node binary. Filesystem grants are canonical, symlink-free paths; each path is passed as a separate Node permission flag, and grants cannot overlap the immutable install tree or host-owned permission ledger.

## Path rules

Every executable or asset entry is relative to the plugin root. Empty paths, control/NUL bytes, URI schemes, POSIX or Windows absolute paths, drive-relative paths, UNC or Windows device-namespace paths, encoded path controls, and `..` using either slash style are rejected. Installed archives may contain regular files and directories only: symbolic and hard links are rejected. Runtime loaders re-check containment and reject symlinked path segments before consuming executable entries.

Character-pack avatars accept only `webDataUrl`. The former `avatarImage.tauriPath` field was removed because it had no runtime consumer and bypassed the contained asset reader.

Valid: `dist/index.js`, `providers/session/importer.js`.

Invalid: `../outside.js`, `C:outside.js`, `C:\\outside.js`, `\\\\server\\share\\entry.js`, `dist/%2e%2e/outside.js`.

## Context surface

`PluginContext` describes the intentionally partial/base context. `FullPluginContext` describes the host-created runtime surface. In the full context, `memory`, `pet`, `webview`, `auth`, and `uri` are required, alongside the core logger, storage, UI, agent, and all other callable APIs. Implementations and `create*API` factories remain host-only.

```ts
import { definePlugin, type PluginContext } from "@cognia/plugin-sdk"

export default definePlugin({
  manifest,
  activate(ctx: PluginContext) {
    ctx.agent.registerTool(tool)
    return {
      onCommand(command, args) {
        if (command !== "example.greet") return false
        ctx.ui.showToast(`Hello, ${args.join(" ") || "world"}`)
        return true
      },
    }
  },
})
```

## Migration

| Previous author code | Supported replacement |
| --- | --- |
| `@/types/plugin` | types from package root, `/manifest`, or `/context` |
| direct slash-command registry | declare `commands` and return `hooks.onCommand` from `activate` |
| host registry/executor imports | manifest contribution plus the corresponding `ctx.*` callable API |
| `create*API` factory | use the API already mounted on `ctx` |
| public PII helper assumption | provide a plugin-owned `canUseTool`/guardrail; host PII gates are internal |

Generate new projects with `cognia plugin new <name> --kind ts`. `pnpm plugin:create` is only a compatibility adapter over that command.
