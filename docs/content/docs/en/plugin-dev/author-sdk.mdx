# Public Plugin SDK and Runtime Contract

Use the packed `@cognia/plugin-sdk` package as the only Cognia dependency in a third-party TypeScript plugin.
The package includes ESM, CommonJS, and declarations.
It does not expose host registries, executors, factories, test reset functions, PKCE helpers, or internal session constructors.

## Public import map

| Import | Supported content |
| --- | --- |
| `@cognia/plugin-sdk` | `define*` helpers, stable constants, and public author types |
| `@cognia/plugin-sdk/manifest` | manifest, capability, permission, and contribution types |
| `@cognia/plugin-sdk/context` | `PluginContext`, `FullPluginContext`, and callable context API interfaces |
| `@cognia/plugin-sdk/hooks` | hook payloads and hook interfaces |
| `@cognia/plugin-sdk/contracts` | read-only canonical contract metadata |
| `@cognia/plugin-sdk/events` | stable event constants and event payload types |
| `@cognia/plugin-sdk/permissions` | public permission values and permission types |
| `@cognia/plugin-sdk/extensions` | extension-point constants and contribution types |
| `@cognia/plugin-sdk/api/tool`, `/api/native-anthropic-tool` | explicitly supported compatibility subpaths |

Never import `@/lib`, `@/types/index`, `@cognia/plugin-sdk/host`, or an app-private `@cognia/*` package. The `host` entry exists only for one repository migration window and is deliberately absent from npm exports and tarballs.

## Contract-driven authoring

Use `cognia plugin contract` before editing a manifest or choosing a runtime. It reads the generated canonical catalog, so new capabilities, contributions, permissions, entries, and path fields become discoverable without updating an authoring checklist.

```bash
# New plugin: select only the contracts needed for a tool and context panel.
cognia plugin contract \
  --plugin-type frontend \
  --capability tools \
  --contribution contextPanels \
  --point chat.input.actions \
  --point-kind ui-slot \
  --permission extension:ui \
  --json
cognia plugin new support-panel --kind ts --json

# Existing plugin: inspect first, then query the records for the extension.
cognia plugin info . --json
cognia plugin contract \
  --plugin-type hybrid \
  --capability python \
  --contribution tools \
  --json

# Compare compatible runtime-entry rules before committing to a runtime.
cognia plugin contract --plugin-type frontend --plugin-type hybrid --json
```

Selectors are repeatable. Point kinds are `ui-slot`, `hook`, `activation`, and `runtime`. An unfiltered query returns the complete inventory; a filtered query returns the selected and related contract records while retaining full-catalog counts. The v2 JSON envelope includes the generated `pluginPoints` catalog alongside capabilities, contributions, permissions, runtime entries, and path fields. Unknown selectors fail with a structured input error, and the command never writes files.

Inspect `support`, `pythonExecution`, `execution`, point `status`/`stability`, `formFactor`, replacement ids, permissions, entry paths, minimum host versions, and path-field contracts in the result. Require explicit user confirmation before generating anything marked experimental, and carry that warning into the completion report. Do not target a deprecated point for new work; use its `replacementId`. A JavaScript-executed contribution cannot be authored for a Python-only or WASM runtime; stop before mutation and offer compatible types reported by the contract, commonly `frontend` or `hybrid`.

After approval, scaffold new work with `cognia plugin new ... --json`, or preserve unrelated files when extending an existing plugin. Run `cognia plugin sync-types`, implement only against `@cognia/plugin-sdk` and `@cognia/plugin-ui`, then verify with `doctor`, `lint --json`, runtime tests/typecheck, `build --json`, and `info --json`. Key generation, signing, installation, reload, export, and publishing are separate explicit operations.

## Runtime matrix

| Manifest type | Required entry | JavaScript lazy contributions | Notes |
| --- | --- | --- | --- |
| `frontend` | `main` | allowed | Browser/Tauri availability follows `runtimeCompatibility` |
| `python` | `pythonMain` | rejected | Python declarations cannot execute JavaScript contribution factories |
| `hybrid` | `pythonMain`; `main` when JS contributions exist | allowed with `main` | Each runtime is loaded independently |
| `wasm` | `wasmMain` and `wasm.apiVersion` | rejected | Desktop Component Model host |
| `vscode-extension` | one of `vscodeMain`, themes, grammars, icon themes, snippets, or languages | VS Code contributions only | Declarative-only extensions do not need `vscodeMain`; code extensions do |

## UI extension requirements

Query the exact UI point before writing its component. The returned `formFactor` is the host layout contract: `icon` for a square control, `row` for compact actions, `block` for a stacked band, and `panel` for an owned scrolling region. Import UI primitives from `@cognia/plugin-ui`; `cognia plugin build` keeps both it and React external so the plugin uses the host's shared React and theme. Do not import host components or use `react-dom` portals.

Plugins own their displayed copy. Provide manifest i18n entries (`i18n.locales`, flat unprefixed keys) and localized accessible names, placeholders, empty/error states, and dialog close labels. Translate in non-React code with `ctx.i18n.t(key, params)`, and in components with `usePluginTranslations(pluginId)` from `@cognia/plugin-sdk/api/i18n` — the same keys and the same locale → English → key fallback, re-rendering on a language switch.

### Modules the host shares, and the ones it does not

An installed plugin is a CommonJS bundle evaluated inside the host. The host hands it its own instance of `react`, `@cognia/plugin-ui`, `lucide-react`, `@cognia/plugin-sdk` **and every published `@cognia/plugin-sdk/<subpath>`** — most subpaths are registries, and a bundled copy would register into a map the host never reads. `cognia plugin build` marks all of them external.

Everything else is bundled into the plugin. That is fine for ordinary libraries (`docx`, `exceljs`), and wrong for host framework modules, which only work bound to the host's own instance. `pnpm plugin:author-imports` rejects them in runtime code:

| Do not import | Use instead |
| --- | --- |
| `next-intl` | `usePluginTranslations(pluginId)` (`@cognia/plugin-sdk/api/i18n`) or `ctx.i18n.t` |
| `next/navigation` | `ctx.ui.navigate("/settings?section=mcp")` — in-app paths only |
| `dexie-react-hooks`, `dexie` | `useLiveQuery` from `@cognia/plugin-ui` over `ctx.dexie` tables |
| `@tauri-apps/*`, `@capacitor/*` | the matching `ctx.*` API (`ctx.clipboard`, `ctx.fs`, `ctx.files`, `ctx.capabilities`) |

`ctx.files.save({ suggestedName, mimeType, bytes })` saves where the user can find the file on every shell — a dialog on desktop, `Documents/cognia/exports/` on mobile, a download on web — and returns `{ saved, platform, location }` so a tool can say where it went.

### Testing

`createTestPluginContext()` from `@cognia/plugin-sdk/testing` returns a fully mounted context built from the contract catalog: recording stubs for every method, in-memory `storage` and `secrets`, `lifecycle.onDispose` disposers you can run, and per-namespace `overrides`. Test against it instead of a partial `{ … } as never` context, which is how optional chaining on always-present APIs creeps into plugin code.

`engines.cognia` is the compatibility authority. Lint and install reject unknown capabilities and a lower bound older than any declared capability's catalog minimum.

Desktop JavaScript plugins execute under Cognia's process-wide Node runtime profile. The default build uses the checksum-pinned bundled Node 26 runtime, with 26.3.1 as the minimum patched version; the lightweight build requires a validated system Node 26 or newer. A plugin cannot select or override that profile. Filesystem grants are canonical, symlink-free paths; each path is passed as a separate Node permission flag, and grants cannot overlap the immutable install tree or host-owned permission ledger.

## Path rules

Every executable or asset entry is relative to the plugin root. Empty paths, control/NUL bytes, URI schemes, POSIX or Windows absolute paths, drive-relative paths, UNC or Windows device-namespace paths, encoded path controls, and `..` using either slash style are rejected. Installed archives may contain regular files and directories only: symbolic and hard links are rejected. Runtime loaders re-check containment and reject symlinked path segments before consuming executable entries.

Character-pack avatars accept only `webDataUrl`. The former `avatarImage.tauriPath` field was removed because it had no runtime consumer and bypassed the contained asset reader.

Valid: `dist/index.js`, `providers/session/importer.js`.

Invalid: `../outside.js`, `C:outside.js`, `C:\\outside.js`, `\\\\server\\share\\entry.js`, `dist/%2e%2e/outside.js`.

## Context surface

`PluginContext` is the complete surface the host passes to `activate` and `deactivate`: every namespace is mounted, so call `ctx.agent.registerTool(…)`, not `ctx.agent?.registerTool?.(…)` — optional chaining there only hides a failure. (`ctx.dexie` is the one optional member; it exists when the manifest declares a `dexie` block.) `ctx.config` reads the plugin's current settings on every access. `FullPluginContext` is a deprecated alias. Implementations and `create*API` factories remain host-only.

Author the manifest with `definePluginManifest({ ...manifestJson, …typedContributions })` and tools with `definePluginTool(…)`; a cast such as `as never` erases the manifest type, so a misspelled contribution field compiles and contributes nothing. A tool without `definition.timeoutMs` gets a 30-second budget — declare one for anything that waits on the network, a model, a sandbox or a file dialog.

```ts
import { definePlugin, type PluginContext } from "@cognia/plugin-sdk"

export default definePlugin({
  manifest,
  activate(ctx: PluginContext) {
    ctx.agent.registerTool(tool)
    return {
      onCommand(command, args) {
        if (command !== "example.greet") return false
        ctx.ui.showToast(`Hello, ${args.join(" ") || "world"}`)
        return true
      },
    }
  },
})
```

## Migration

| Previous author code | Supported replacement |
| --- | --- |
| `@/types/plugin/index` | types from package root, `/manifest`, or `/context` |
| direct slash-command registry | declare `commands` and return `hooks.onCommand` from `activate` |
| host registry/executor imports | manifest contribution plus the corresponding `ctx.*` callable API |
| `create*API` factory | use the API already mounted on `ctx` |
| public PII helper assumption | provide a plugin-owned `canUseTool`/guardrail; host PII gates are internal |

Generate new projects with `cognia plugin new <name> --kind ts`. `pnpm plugin:create` is only a compatibility adapter over that command.

## Document directory and progressive reading

The existing `ctx.project` API provides `listKnowledgeDocuments`, `readKnowledgeOutline`, `readKnowledgeRange`, and `locateKnowledgeDocument`. The directory returns metadata only. Read the selected original section before composing an answer; heading summaries are navigation hints and source text is untrusted evidence. Offsets are UTF-16, half-open; pages and lines are one-based.

Declare `project:read` for these methods. An Agent-library scope also requires the explicit `knowledge:read` grant:

```json
{
  "type": "frontend",
  "capabilities": ["tools", "webview"],
  "permissions": ["project:read", "knowledge:read", "project:write"]
}
```

This is a manifest fragment: retain the required identity, engines, entries, and contributions of your plugin. `tools` and `webview` are needed only when your plugin contributes those surfaces. Remove `project:write` if it does not index or change project files.

```ts
import type { PluginContext, PluginKnowledgeScope } from "@cognia/plugin-sdk"

export async function readProcedure(ctx: PluginContext, projectId: string) {
  const scope: PluginKnowledgeScope = { kind: "project", projectId }
  const directory = await ctx.project.listKnowledgeDocuments({ scope, query: "guide", limit: 10 })
  const document = directory.documents[0]
  if (!document) return null
  const identity = { scope, knowledgeBaseId: document.knowledgeBaseId,
    sourceId: document.sourceId, generationId: document.generationId }
  const outline = await ctx.project.readKnowledgeOutline(identity)
  const section = outline.nodes.find((node) => node.level > 0)
  if (!section) return null
  const evidence = await ctx.project.readKnowledgeRange({ ...identity,
    sectionId: section.id, maxChars: 4_000 })
  const location = await ctx.project.locateKnowledgeDocument({ ...identity,
    sectionId: section.id })
  return { evidence, location }
}
```

For an Agent library, use the host-created `toolContext.project` API supplied to your registered tool’s `execute(args, toolContext)` call, and `{ kind: "agent", sessionId: toolContext.sessionId }` as the scope. The module `ctx.project` and ordinary iframe clients cannot authorize Agent-library access. The host must have registered a reader for that actual Agent run with progressive reading enabled. The host captures its authorized library IDs, source ACL identity, immutable revision bindings, and shared budget. A missing or mismatched invocation binding produces `session_scope_unavailable`; a removed/replaced reader produces `session_reader_unavailable`. The API closes when tool execution ends, including failures, so a retained reference cannot read a later run. A plugin cannot supply a library allowlist, principal, revision grant, or trusted-local flag. Naming a different session does not broaden authority. Naming a library outside the host scope produces `source_unavailable`; a revocation is checked on the next call. Directory queries reuse the existing BM25 implementation for navigation; indexed RAG remains the host's configured vector/hybrid retrieval path.

Project indexing reuses `addKnowledgeFile(projectId, { name, content, embeddableContent?, structure? })`, `updateKnowledgeFile`, and `removeKnowledgeFile` with `project:write`. `content` is the parsed original, `embeddableContent` is a separate embedding projection, and `structure` is the parser's canonical navigation result. The existing hash/reconcile and indexing lifecycle handles the write. Project directory generations identify the current original's content hash; an old generation after an edit fails with `revision_unavailable`, and a deleted document fails with `source_unavailable`. Agent-library historical reads are available only inside the host's frozen revision grant. There is no plugin write API for arbitrary Agent libraries.

Host `knowledgeReading` settings control `enabled`, `maxCalls`, `maxReadChars`, `totalReadChars`, `maxOutlineNodes`, summary settings, and retrieval settings. Agent scopes share the host run's budget across tools and plugin calls. Project scopes retain their bounded reader for the plugin API lifetime and observe live host setting changes. `maxChars` can lower the read size, but cannot raise the host limit. Continue truncated reads from `nextCharStart`; handle `reading_disabled`, `invalid_arguments`, `call_budget_exhausted`, `read_budget_exhausted`, and missing-page/section/version errors explicitly.

Frontend and hybrid module plugins receive these APIs on `ctx.project`. Sandboxed webviews declaring project read/write permissions receive the same operations through `window.acquireCogniaProjectApi()`; its asynchronous client also mirrors the three existing indexing writes. The host checks live grants before executing and again before returning reads, validates the method allowlist, bounds concurrent requests, and detaches on plugin disable. Acquire once per iframe. Closing the frame rejects pending reads; timeouts reject after ten seconds. This channel uses the existing webview transport and never exposes `getKnowledgeFiles` as an unrestricted sandbox read.

The project catalog supports frontend/hybrid on desktop, web, and mobile. Python, WASM, and headless runtimes are not advertised for these APIs. Desktop Node activation-call replay does not implement asynchronous host-return reads; use the sandboxed webview transport for that surface instead of relying on replayed calls.

The permission tier `forbid` denies access even when a manifest grant remains stored. Revoking a permission in the host UI also takes effect on the next call and before a pending read returns: the host records an explicit revocation across its existing permission stores. `hasPermission` and `getGrantedPermissions` report these effective grants. Regranting requires a host-approved grant; retained plugin state cannot undo revocation. Public workflow invocations cannot use legacy project metadata or whole-file methods to bypass their bound document scope, and their project-scope reads are denied.
