# Run an always-on host

An always-on host is a machine you own that runs Cognia's headless server and brain
around the clock (ADR-0224). It is a peer of your desktop, not a replacement for it.
It runs whatever lives on it: chats you start from your phone, scheduled tasks, bots and
connectors, so they keep working while your laptop sleeps.

There are two ways to run one:

| Machine                      | How                                                |
| ---------------------------- | -------------------------------------------------- |
| Linux VPS, NAS, home server  | Docker Compose, `server` profile                   |
| Mac (for example a Mac mini) | The host archive, installed as a LaunchDaemon      |
| A desktop you leave running  | The desktop app's **Always-on host mode** (below)  |

Either way, phones and desktops pair over Cognia's encrypted relay, so the machine can
sit behind a home router with no public domain and no open port.

<Callout title="Status">
  This page covers installing, pairing and keeping the host's data safe. Moving existing bots,
  schedules and connectors from the desktop to the host, per-item ownership, container-per-task
  execution and automatic updates are being built (ADR-0224 phase A); until then, create what should
  run around the clock directly on the host.
</Callout>

## Linux with Docker Compose

```bash
git clone https://github.com/MaxQian888/cognia-next.git && cd cognia-next/deploy/compose
cp .env.example .env
# edit .env: set SHARE_UPLOAD_SECRET (openssl rand -hex 32)

docker compose --profile server run --rm cognia-server init   # writes /data/master.key once
docker compose --profile server up -d --wait
docker compose exec cognia-server cognia-server pair
```

`init` creates the master key inside the data volume. It never replaces an existing
key. The container restarts on its own (`restart: unless-stopped`) and starts again
with Docker when the machine boots.

## Mac with the host archive

Download `cognia-host-<version>-darwin-arm64.tar.gz` (or `darwin-x64`), unpack it
somewhere permanent such as `/opt/cognia-host`, then:

```bash
sudo /opt/cognia-host/bin/cognia-server service install
```

This installs a LaunchDaemon (`/Library/LaunchDaemons/com.cognia.server.plist`) that
starts at boot without anyone logging in and runs as **your** account, not root. It
creates the data dir (`~/Library/Application Support/cognia-server`) and a master key
in it, and prints the pairing command. Useful flags:

| Flag             | Default                 | Meaning                                             |
| ---------------- | ----------------------- | --------------------------------------------------- |
| `--scope user`   | `system`                | A LaunchAgent that starts at login instead; no sudo |
| `--run-as NAME`  | the user who ran `sudo` | Account the daemon runs as (never root)             |
| `--data-dir DIR` | that account's default  | Where the host keeps its data and master key        |
| `--public-url`   | none                    | A public HTTPS origin, if you have one              |
| `--no-mdns`      | advertise on the LAN    | Do not announce the host over mDNS                  |

```bash
sudo /opt/cognia-host/bin/cognia-server service status      # installed, running, and ready
sudo /opt/cognia-host/bin/cognia-server service uninstall   # keeps data and the key
```

On a Linux machine without Docker the same command installs a systemd unit; a system
service there reads its master key as a root-only systemd credential from
`/etc/cognia-server/master.key`.

For a Mac that should behave like a server, also set System Settings → Energy to
start up automatically after a power failure and to prevent sleep while the display
is off.

## A desktop you leave running

If the machine that should stay on already runs the Cognia desktop app, it can be the host
itself: turn on **Settings → Desktop → Always-on host mode**. While the mode is on, the app:

- holds a system wake assertion, so the computer does not idle-sleep (the display may still
  turn off; `pmset -g assertions` lists it as "Cognia is the always-on host for this account");
- registers launch at login and starts **hidden** when the OS launches it at login. Click the
  tray icon (or the Dock icon on macOS) to open the window;
- closes to the tray when you click the window's close button. The tray menu's **Quit** still
  exits, and stops hosting until the app runs again.

Turning the mode off releases the wake assertion and makes the next login launch open the
window again. Launch at login and the close-button choice stay as they are; change them on
the same page.

The mode is a setting of this computer only and never syncs to your other devices.
**Settings → Connectivity → Overview** shows whether the desktop is hosting, or standing by
while it drives another host. Unlike the host archive, the desktop app needs someone to sign
in to the computer after it restarts, so use the archive for a machine that must come back on
its own after a power cut.

## Pair your phone and desktop

```bash
COGNIA_DATA_DIR="$HOME/Library/Application Support/cognia-server" \
  /opt/cognia-host/bin/cognia-server pair
```

`pair` asks the running server for an invitation and prints a `cgnp4|…` string with a
relay room, a QR code to scan off the terminal, and when it expires (five minutes).
Paste or scan it on the device's pair screen; it works from any network. Whoever
redeems it becomes an owner of the host, so hand it only to your own device.

| Flag          | Meaning                                                          |
| ------------- | ---------------------------------------------------------------- |
| `--port N`    | The port the host serves on, when it is not 27890                |
| `--direct`    | Accept an invitation without a relay room (see below)            |
| `--no-qr`     | Print only the string                                            |

`pair` only hands out an invitation once the relay has accepted its pairing room. When
it cannot (the host is not running, the relay is switched off or unreachable) it stops
and says why, instead of printing an invitation that only works on the host's own
network. Fix the cause, or pass `--direct` if the device can reach the host directly.

### From the desktop

Open Settings → Connectivity → Remote hosts, paste the invitation, and switch on
**Always-on host**. The desktop records it as an always-on host and keeps working on
its own: it does not switch to it, and the list marks it **Always-on**.

The desktop then checks on the host about once a minute over a separate connection of
its own, without routing anything there, and over the relay when the host's address
does not answer. **Devices** shows the host as **Always-on** with whether it is online,
and its Presence card has **Last check** with the last answer (or why there was none)
and a **Check now** button. The scheduler's timing authority reads the same answer,
so it no longer takes schedules back from an always-on host that is simply not the one
the desktop is driving. A host that stops answering is checked less often, up to every
ten minutes.

### From the command line

```bash
cognia-agent host login home --invitation 'cgnp4|…'
```

The CLI reaches the host directly when it can, and otherwise pairs through the relay
room in the invitation. Pairing also gives the CLI a relay room of its own on the host
(kept in `hosts.json` with the device key; `host show` prints it redacted). Commands
try the host's address first and go through that room when the address does not
answer, so a host behind a home router stays usable from anywhere. Raw `api request`
routes and `--wait` have no relay form and still need the address to be reachable.

## Move work to the host

Scheduled tasks, Bots and connections run on whichever device owns them. Open the
host in **Devices** and use its **Always-on work** section to move them there, so they
keep running while your desktop sleeps. **Move work to …** asks the host about every
item first and lists them in three groups:

- **Ready to move.** Selected by default.
- **Need plugins on the host.** The host lacks a plugin the item uses, or has another version of
  it. The desktop app can send them: it packs the plugins as one signed cogpack and
  the host installs it under its **own** plugin policy, so a host that refuses
  unsigned or unknown publishers refuses this too. The host is then asked again.
- **Stays on this device.** Items tied to this machine, each with the reason: a task that looks
  after this device's own data, a desktop, file-watch or terminal trigger, a local
  project folder, an OS-level schedule, a stdio MCP server, or something the host
  cannot run.

Moving an item copies it to the host paused, then stops the copy here, then starts it
on the host. A connection takes its credentials (into the host's keychain) and its
scheduled chat messages with it. The copy left here is a placeholder: it does not run,
and its list row and detail say **Runs on** with the host's name.

The host may first ask for a person to approve this device. The dialog shows the code
to approve on the host, or from another device that administers it, and continues
once you have.

**Take back** reverses a move: the host's copy is removed and the item runs here again,
as it was on the host. When the host cannot be reached you can still take an item
back; it runs here at once, and the host's copy is removed the next time the host
answers, so for a while it may run in both places. A move or take-back that was cut
off (the app closed, the network dropped) is listed under **Stopped partway** with
**Resume** or **Finish**, and picks up where it stopped.

While an always-on host is online, creating a scheduled task, installing a Bot or
adding a connection asks where it runs, with the host chosen. Keep it on **This
device** to stay local; otherwise it is created here and moved straight away, and
anything the host cannot take stays here with the reason shown.

## Secrets on the host

Work that runs while nobody is at the desktop still needs keys. A model provider key
is a setting of each device and never syncs, so the host's own settings usually have
none. Open the host in **Devices** and use **Secrets on this host** to seal keys on it:

- **Provider keys.** The host uses one for any provider its own settings have no key
  for, in scheduled tasks, Bots and every other run. A key in the host's settings
  always wins.
- **Git tokens**, by git host (`github.com`). Used when the host clones a repository
  from that host and was given no token.
- **Connection credentials** are listed too. They belong to their connection, which
  sets and removes them, including when a connection is moved to the host.

A key is sent once over this device's own connection to the host and sealed there under
the host's master key. The list shows names, when each was set and by which device,
never a value. Sealing or removing one needs the host's approval, like other host
administration, and only an owner device can do it. When a device is revoked, the
secrets it set on the host are deleted with it.

Pushing credentials, changing a Bot installation and arming its triggers from a paired
device now ask for the same approval.

## What unattended runs may do

Bots and scheduled tasks run on the host with nobody watching. Each one carries a
permission profile that sets, for four kinds of action, whether the run may go ahead
or must ask you:

| Kind                         | Default                        | Can be lowered to |
| ---------------------------- | ------------------------------ | ----------------- |
| Workspace files and commands | Allowed in a verified sandbox  | Ask me, Never     |
| Outbound messages            | Ask me                         | Never             |
| Secret use                   | Ask me                         | Never             |
| Host configuration           | Ask me                         | Never             |

Workspace work is allowed without asking only when the run's sandbox tools execute in
an isolated sandbox the host has verified. Anywhere else it asks, like the other three.
Nothing can be raised above these defaults.

Set the profile in a Bot's **Settings** under **When nobody is watching**, or in a
scheduled chat or goal task's editor under the same name. A plugin or your organisation
can lower a Bot's profile further, and the Bot's **Policy ceiling** shows which layer
lowered what. Lowering it stops the Bot's live runs.

When a run needs you, it pauses rather than failing. Your paired phone gets a
notification that says only what kind of approval is waiting, never what the run
wants to send. Open it to see the request on the **Bots** or **Scheduled tasks** page
and approve or deny it there. A run nobody answers is denied after 30 minutes. The
time it spends waiting does not count against the task's timeout. A Bot's own approval
steps arrive in the same list.

## Keep the master key safe

Everything the host stores encrypted (device identities, provider and connector
credentials) is sealed under its master key. Losing the key makes those unreadable.
Back up `master.key` from the data dir. The host reads its key from, in order:

1. `COGNIA_MASTER_KEY` (64 hex characters)
2. `COGNIA_MASTER_KEY_FILE`
3. the systemd credential `cognia-master-key`
4. the Keychain item `com.cognia.server`, when `COGNIA_MASTER_KEY_SOURCE=keychain`
   (create it with `cognia-server init --keychain`; not available to a LaunchDaemon)
5. `<data dir>/master.key`

## Durability

The brain stores its data in SQLite (`<data dir>/serve/durability/<account>/`), so a
crash or power cut loses nothing that was already committed. A host that ran an older
build is imported from its previous snapshot store on first start; the old store is
left untouched as a fallback.
