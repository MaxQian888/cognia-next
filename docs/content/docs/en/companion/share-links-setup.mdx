# Public share links (zero-knowledge)

Cognia can share an artifact through a short URL that anyone can open in a browser.
Supported artifacts include chat transcripts, workflow diagrams, A2UI apps, and backup packages.
Cognia **encrypts the content on your device** and generates a random key locally.
It places the key in the URL `#fragment` and **never uploads the key**.
The worker stores only opaque ciphertext. The recipient's browser decrypts it, and the `#fragment` never reaches a server.
The host therefore cannot read your shares.

This is a **self-hosted, single-tenant** model, like the signaling server.
Deploy the worker to *your own* Cloudflare account. Configure the app to use it.
Anyone with the link can read the shared content.
Creating and revoking links requires a bearer secret that only you hold.

<Callout type="info">
  Free-tier friendly: Cloudflare R2 (10&nbsp;GB free), Workers KV, and Workers
  all have free tiers sufficient for personal use.
</Callout>

## What gets shared

| Artifact | Viewer renders it as |
| --- | --- |
| Chat export (HTML / animated) | Inline, in a sandboxed iframe |
| Chat export (Markdown / JSON / text) | Preformatted text |
| Workflow image | A PNG |
| Backup package | A download (re-import under Settings → Data) |
| A2UI app | Rendered live in the browser (read-only) |
| Files from a conversation (alone, or with a chat export) | A file list: download, and in-browser preview for images, PDFs and text |

## Prerequisites

- A Cloudflare account, and `wrangler` installed (`npm i -g wrangler`, then `wrangler login`).
- Optional: a domain on Cloudflare DNS if you want a custom hostname
  (`share.example.com`); otherwise the worker is reachable on `*.workers.dev`.

## Deploy the worker (the API)

The worker lives in `services/share-server/worker/`. It is a standalone project (not part
of the app's pnpm workspace) and is now a pure JSON API — the viewer is the
app's own `/share/view` route, deployed separately to Cloudflare Pages (next
section).

```bash
# 1. Install deps (standalone — ignore the app workspace)
cd services/share-server/worker && pnpm install --ignore-workspace

# 2. Create the storage the worker binds to
wrangler r2 bucket create cognia-shares
wrangler kv namespace create SHARE_KV
#   → paste the printed namespace id into services/share-server/worker/wrangler.toml
#     under [[kv_namespaces]] id = "..."

# 3. Set the bearer secret the app will use to create/revoke links
wrangler secret put SHARE_UPLOAD_SECRET
#   → enter a long random string; keep a copy for the app config below

# 3b. Set the key that signs file read tickets (links that carry files)
wrangler secret put SHARE_TICKET_KEY
#   → 64 hex characters, e.g. the output of `openssl rand -hex 32`.
#     Without it, links work but cannot carry files.

# 4. Deploy the API
wrangler deploy
```

<Callout type="info">
  `wrangler.toml` scopes the Worker to `share.cognia.cn/v1/*` so Cloudflare Pages
  can serve the viewer on the same host — change the hostname to your own
  (requires that zone active on your account), or comment the `routes` line out
  to use the `*.workers.dev` subdomain only.
</Callout>

## Deploy the viewer (Cloudflare Pages)

The viewer is the app's `/share/view` route, shipped in the normal static
export. Build the app and deploy `out/` to Pages on the same host:

```bash
# from the repo root
pnpm build
wrangler pages deploy out --project-name cognia-share-viewer
```

Bind the Pages project to your share host (e.g. `share.cognia.cn`). The Worker
route `…/v1/*` takes precedence, so `/v1/*` hits the API and `/share/view` (plus
the rest of the static app) is served by Pages. See
`services/share-server/pages/README.md` for details and the note that the full app shell
becomes publicly reachable at that host.

Run the test suite any time without an account — it uses miniflare:

```bash
cd services/share-server/worker && pnpm test
```

## Point the app at it

In Cognia: **Settings → Data → Public share links**.

1. **Share worker URL** — the deployed origin, e.g. `https://share.example.com`
   (no trailing `/v1`). Also settable at build time via `NEXT_PUBLIC_SHARE_URL`.
2. **Upload secret** — paste the same value you gave to
   `wrangler secret put SHARE_UPLOAD_SECRET`. It is stored in your OS keyring
   (desktop) / encrypted IndexedDB (web), never in plaintext settings.

Now a **Share via link** action appears in the chat export dialog, the workflow
editor's overflow menu, the A2UI workspace toolbar, and the backup export card.

## Link controls

When you create a link you can set:

- **Expiry** — 1 hour / 24 hours / 7 days / up to 30 days. Both server
  implementations enforce a maximum of 30 days by default; an operator can set
  a shorter limit. Omitting the TTL requests the server maximum, not permanent
  storage. After creation, the dialog shows the actual expiry returned by the server.
- **View limit / burn-after-reading** — the link self-destructs after N views.
- **Extra passphrase** — derives the key from `urlKey ‖ passphrase`, so even
  someone with the full link can't open it without the passphrase (share it
  out-of-band). Still zero-knowledge: the server never sees either.

Manage and revoke existing links under the same settings panel
(**My shared links**). Revoking deletes the object from the server immediately.
**Extend expiry** requests at least seven days from now (subject to the server
limit), preserves any later existing expiry, and reports the returned expiry.
It never shortens a link’s lifetime.

The viewer first reads `GET /v1/share/:code/metadata`, which does not consume a
view. This metadata exposes only lifecycle controls and whether an extra
passphrase is required; the passphrase itself remains secret. A protected link
waits for a passphrase before fetching its encrypted content. A link with a
view limit asks the recipient to open it before spending a view. For a protected
burn-after-reading link, unlocking spends the single view; the viewer keeps the
envelope in memory so an incorrect passphrase can be retried while the page
stays open.

Upgrade the deployed Rust server or Cloudflare Worker together with the viewer
to enable the metadata endpoint. The viewer does not fall back to a consuming
content request when an older server lacks this endpoint.

## Sharing files

A link can carry files from a conversation (ADR-0222):

- **Share files…** in a conversation's **Files** panel (or the share action on
  one of its rows) makes a link that is just those files.
- **Share via link** in the chat export dialog has a **Files** section, so a
  conversation and its files travel together. Images in the conversation are
  carried too, either inline or as attachments; one that is no longer stored on
  this device is shared by name only, and the dialog says so.

Pick files or whole folders. A folder brings everything under it except files
that look like credentials (`.env`, private keys, `.ssh/`, and so on), which
are counted and left out; a credential-like file you pick by name needs its own
tick. One link carries at most 200 files, 512&nbsp;MiB per file and 2&nbsp;GiB
in total.

Each file is encrypted in the app before upload, with a key derived from the
link's own key, so files are as zero-knowledge as the rest of the link. If a
file changes while it is being shared, or the upload fails, nothing stays
published. A recipient's view unlocks the files for an hour (never past the
link's expiry): a burn-after-reading link can still be downloaded within that
hour after it is opened.

**File sharing policy** (Settings → Data) decides whether files may be shared as
links and the longest such a link may last. If you belong to an organization,
its owners and admins set an organization policy too, and sharing follows
whichever is stricter. In a shared conversation, sharing its files also needs
the `files.share` permission (owners and maintainers). Live access, network
drive (WebDAV/SFTP) access, writes and agent sharing appear in the policy but
are not available yet.

## Security notes

- The worker is **untrusted by design** — it stores ciphertext, lifecycle counters and a
  non-secret passphrase-required flag. Losing the link means losing the content (there is no recovery).
- Sharing a backup that includes API keys puts those (encrypted) on a public
  URL — only do so when you trust the link's distribution and ideally add a
  passphrase.
- Because shares are zero-knowledge, there is no server-side search or preview;
  the artifact's type and title live inside the ciphertext.
- File names, sizes and checksums are inside the ciphertext as well; the server
  sees only how many encrypted chunks a link has and their sizes.
