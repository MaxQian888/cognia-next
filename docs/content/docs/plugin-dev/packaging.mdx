---
title: Packaging & Publishing
description: Build, sign, install, and distribute cognia plugins. Covers both WASM Component Model plugins and frontend TypeScript plugins.
---

Cognia plugins are distributed as `.zip` bundles containing the manifest, code artifact, and any auxiliary assets. The `cognia` CLI (Rust crate at `crates/cognia-cli/`) builds, validates, signs, and installs them.

> **Install the CLI once** (see [CLI Prerequisites](/en/dev/cli-prerequisites) for prebuilt binaries and platform tabs):
>
> ```bash
> cargo install --locked --path crates/cognia-cli
> cognia --help
> ```
>
> The same binary handles both plugin kinds described below; sub-commands dispatch on the `type` field in `plugin.json`.

## Global flags

Every `cognia plugin *` command accepts the same five global flags:

| Flag                              | Effect                                                                                                                                                                  |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--color [auto\|always\|never]`   | Color mode for stdout/stderr. Default `auto` follows TTY detection and the standard `NO_COLOR` / `FORCE_COLOR` env vars.                                                |
| `--no-color`                      | Shortcut for `--color=never`. Takes precedence over `--color`.                                                                                                          |
| `--quiet`, `-q`                   | Suppress spinners, progress bars, and informational chatter. Errors and JSON output still print.                                                                        |
| `--verbose`, `-v`                 | Increase log verbosity. Repeatable up to `-vv`. Human `plugin info` emits a command diagnostic on stderr; JSON and `--quiet` modes stay silent.                         |
| `--yes`, `-y`                     | Pre-confirm every interactive prompt. **Required for CI**. See [Confirmation prompts](#confirmation-prompts) for the list of gates this skips.                          |

Every plugin subcommand with a bounded execution also accepts `--json` (see [JSON output](#json-output));
`plugin dev --json` requires `--once` so stdout stays a single parseable report.

## TTY vs non-TTY behavior

The CLI auto-degrades on a non-TTY (CI, redirected stdout, `docker exec` without `-it`):

- **No ANSI colors** — output stays grep-friendly even when `--color=auto` is in effect. `FORCE_COLOR=1` overrides if you want colors in piped output.
- **No spinners or progress bars** — `plugin build` and `plugin dev` switch to plain `println!` lines so logs remain line-oriented.
- **Prompts refuse to ask** — any subcommand that would have prompted (e.g. `plugin new` without `<name>`) exits with an actionable error pointing at the flag to pass instead. Pass that flag, or `--yes`, to script the command end-to-end.

## Scaffold

Two starters ship with the CLI:

```bash
# Rust + cargo-component WASM plugin
cognia plugin new my-wasm-plugin
# or
cognia plugin new my-wasm-plugin --kind wasm

# Frontend TypeScript plugin (esbuild + jest pre-wired)
cognia plugin new my-ts-plugin --kind ts
```

What you get:

| Kind     | Layout                                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **wasm** | `Cargo.toml`, `src/lib.rs`, `wit/world.wit`, `plugin.json`, `README.md`, `.gitignore`                                                               |
| **ts**   | `package.json`, `tsconfig.json`, `jest.config.cjs`, `plugin.json`, `src/index.ts`, `src/index.test.ts`, `src/__shims__/`, `README.md`, `.gitignore` |

Run the CLI's printed next-steps to get a green build on either kind.

### Interactive wizard

Omitting `<name>` on a TTY drops into an interactive wizard that fills in the same fields you'd otherwise pass via flags. Each prompt has a default that mirrors the obvious choice:

```text
$ cognia plugin new
  ? Plugin name       › my-plugin              # default: current directory's basename
  ? Template kind     › ● wasm   ○ ts          # default: wasm
  ? Short description › A cognia WASM plugin
  ? Author name       › Max Qian               # default: git config user.name
  ? Author email      ›                        # optional — blank to skip
  ? Generate a signing keypair now and embed the public key? › Y/n
```

Each answer can also be supplied up front via the equivalent flag — when **all** flags are passed, the wizard never runs:

| Field         | Flag                  | Default when missing on TTY        | Default when missing on non-TTY      |
| ------------- | --------------------- | ---------------------------------- | ------------------------------------ |
| Name          | _positional_          | _prompt_                           | error — required                     |
| Kind          | `--kind wasm\|ts`     | _prompt_                           | `wasm`                               |
| Description   | `--description "..."` | _prompt_                           | `A cognia <kind> plugin`             |
| Author name   | `--author "..."`      | _prompt, defaults to git config_   | git config `user.name` or `Anonymous`|
| Author email  | `--author-email "..."`| _prompt — optional_                | omitted                              |
| With keygen   | `--with-keygen=Y\|N`  | _prompt, default Yes_              | `false`                              |

When `--with-keygen` runs, the CLI generates an Ed25519 keypair under `<plugin>/.cognia/` and embeds the public key into `plugin.json`'s `author.publicKey` field — equivalent to running `cognia plugin keygen` separately and then pasting the value in by hand.

## Validate

`cognia plugin lint` mirrors the host's [manifest validation](./manifest) rules in Rust so editors and CI can fail fast on a malformed `plugin.json`:

```bash
cognia plugin lint                 # human report, exit 1 on errors
cognia plugin lint --json          # machine-readable diagnostics
```

The lint runs implicitly during `cognia plugin build`; you almost never need to invoke it standalone outside an editor integration.

## Build

```bash
cognia plugin build                # uses ./plugin.json by default
cognia plugin build --path my-plugin --out custom.zip
cognia plugin build --skip-build   # repack an existing artifact without rebuilding
```

Dispatch is by `manifest.type`:

| Type       | Build pipeline                                                                                                                 | Output                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------- |
| `wasm`     | `cargo component build --release` → embed `cognia:api-version` custom section → zip                                            | `target/cognia/<id>-<version>.zip` |
| `frontend` | `npx --no-install esbuild src/index.ts --bundle --format=cjs --platform=neutral --target=es2022 --outfile=dist/index.js` plus the `--external:` flags below → zip | `target/cognia/<id>-<version>.zip` |
| `python` | validate `pythonMain` → copy existing Python entry file + `bundle_include[]` → zip | `target/cognia/<id>-<version>.zip` |
| `hybrid` | copy existing `main`, `pythonMain`, optional `styles`, and `bundle_include[]` → zip | `target/cognia/<id>-<version>.zip` |
| `vscode-extension` | validate `vscodeMain` → copy existing extension entry file + optional `styles` + `bundle_include[]` → zip | `target/cognia/<id>-<version>.zip` |

For frontend plugins, **`plugin.json`'s `main` field must point at the bundled JS** (`dist/index.js` by default) — the host does not transpile TypeScript on the fly. It reads that file at runtime and evaluates it as CommonJS in a module wrapper, which is why the build emits `--format=cjs`.

### Externals

The build marks a fixed set of specifiers external, and the host supplies its own already-loaded instances for them when the bundle calls `require`:

| Specifier | Why |
| --- | --- |
| `react`, `react/jsx-runtime`, `react/jsx-dev-runtime` | Two React instances do not share a hook dispatcher, so a bundled copy makes every hook in your components throw `Invalid hook call`. `--external:react` alone is insufficient — esbuild matches import paths literally, so the jsx runtime needs its own entry. |
| `@cognia/plugin-sdk`, `@cognia/plugin-ui` | Shared so every plugin gets one instance of the SDK's registries and one copy of the component kit. |
| `react-dom` | Externalised but **not** supplied. Keeping it external means it is never bundled; a `require` for it fails at load with an explicit message rather than a second reconciler rendering into a tree the host does not own. |
| `@/types/plugin`, `@/lib/*` | Host path aliases, resolved by the host at runtime. |

Everything else is bundled normally. Requiring a specifier that is neither bundled nor host-shared fails at load with an error naming it. See [Surfaces](./surfaces#sharing-the-hosts-react).

For Python, hybrid, and VS Code-extension plugins, `cognia plugin build` is intentionally build-free: it packages files already named in the manifest instead of guessing at your Python, JS, or VSIX toolchain. Missing entry files and paths that escape the plugin directory fail the build.

### Adding extra files to the bundle

By default the bundle contains `plugin.json` plus the type-specific artifact (`wasmMain`, `main`, `pythonMain`, `vscodeMain`, and optional `styles` where applicable). Add `bundle_include` in `plugin.json` to ship more:

```json
{
  "bundle_include": ["assets/icon.svg", "themes/dark.json", "README.md"]
}
```

Paths are relative to `plugin.json`. Missing files surface as build errors.

## Inspect

`cognia plugin info <bundle.zip|directory>` inspects a packaged bundle or an unpacked plugin directory and prints what the host would see at install time — manifest summary, declared capabilities + permissions, file list, signature status, public-key fingerprint, and (for WASM inputs) the embedded `cognia:api-version` section. Useful before shipping to confirm you packaged the right artifact.

```bash
cognia plugin info target/cognia/my-plugin-0.1.0.zip            # compact summary
cognia plugin info target/cognia/my-plugin-0.1.0.zip --detailed  # full file table + sig breakdown
cognia plugin info . --json                                      # inspect an unpacked plugin directory
cognia plugin info target/cognia/my-plugin-0.1.0.zip --json      # machine-readable payload
```

The default mode is compact: manifest summary, file count + total inner bytes, one-line signature verdict. `--detailed` adds a comfy-table file listing and a multi-line signature breakdown. `--json` emits a versioned payload (see [JSON output](#json-output)). Directory inputs skip symlinks, report signature status as `not-applicable`, and only probe `wasmMain` files that stay inside the selected plugin root; escaping, missing, or corrupt WASM entries simply omit `wasmApiVersion`.

## Signing

Plugins distributed outside a trusted channel should ship with an Ed25519 detached signature. The host displays the signing key's fingerprint on first install and auto-trusts subsequent updates from the same key.

```bash
# One-time, per author:
cognia plugin keygen                                  # writes .cognia/plugin.private.b64 + .public.b64
# Embed the printed public key in plugin.json:
#   "author": { "name": "...", "publicKey": "<base64>" }

# Per release:
cognia plugin sign target/cognia/<id>-<version>.zip --key .cognia/plugin.private.b64
# → target/cognia/<id>-<version>.zip.sig

cognia plugin verify target/cognia/<id>-<version>.zip
# ✓ valid; public key: ...; fingerprint: ...
```

`cognia plugin verify` reads `author.publicKey` from the bundle's manifest by default. Pass `--public-key <b64>` to override (useful when verifying a bundle whose manifest you don't yet trust). `--json` emits a versioned `{schemaVersion, ok, action, bundle, signature, publicKey, fingerprint, stage?, error?}` payload — convenient for scripted release gates. Successful verification omits `stage`; failure payloads use `stage: "bundle" | "public-key" | "signature" | "verify"` so scripts can separate local input/read/key failures from the final signature check.

### Overwriting existing key / signature files

By default, `cognia plugin keygen` and `cognia plugin sign` **refuse** to silently overwrite an existing `plugin.private.b64` / `plugin.public.b64` / `.sig` file. On a TTY the CLI prompts; on a non-TTY (no `--yes`) it bails with an actionable message. Pass `--yes` / `-y` to overwrite without prompting (CI flow). See [Confirmation prompts](#confirmation-prompts) for the full list.

## Install into a running cognia

`cognia plugin install` and `uninstall` drive a running cognia desktop instance over a loopback HTTP bridge — no need to walk through Settings → Plugins by hand:

```bash
cognia plugin install target/cognia/<id>-<version>.zip
cognia plugin uninstall <plugin-id>
cognia plugin uninstall <plugin-id> --purge-data   # also drop the plugin's Dexie tables
```

The CLI discovers the running cognia by reading `<config_dir>/cognia/cli-endpoint.json`, which cognia writes at startup. If no cognia is running, the CLI returns a clear "no running cognia detected" error rather than hanging.

**Security model:** the bridge binds to `127.0.0.1` only and gates every request on a per-launch dev token in the endpoint file. The token rotates each time the desktop launches, so a stale file from a previous run can't talk to a fresh instance.

### Same-id preflight on `install`

Before POSTing the bundle, `cognia plugin install` asks the bridge `GET /api/v1/dev/plugins/installed` for the currently loaded plugins. If your bundle's `id` matches one that's already installed, the CLI surfaces `<id> is already installed (v<from> → v<to>)` and prompts before replacing. Pass `--yes` to skip the prompt (equivalent to "yes, replace"). A failed preflight call is non-fatal — the CLI proceeds and lets the bridge enforce its own idempotency policy.

### `--purge-data` confirmation on uninstall

`cognia plugin uninstall <id>` without `--purge-data` is reversible (re-install the same bundle), so it runs straight through. **With** `--purge-data`, the CLI prints a preview (version, install dir, data scope, "no — Dexie wipe is one-way") and prompts for explicit confirmation. `--yes` skips the prompt for scripted teardowns.

## Dev loop (watch + auto-reload)

```bash
cognia plugin dev                         # rebuild on save, no reload
cognia plugin dev --reload-url <URL>      # rebuild + POST to a running cognia to hot-reload
```

If a running cognia is discoverable via the endpoint file, `cognia plugin dev` auto-fills `--reload-url` so the rebuild -> reload loop works out of the box. It watches the standard source/build paths (`src/`, `wit/`, `dist/`, `Cargo.toml`, `package.json`, `plugin.json`) plus manifest-declared runtime entries such as `main`, `pythonMain`, `vscodeMain`, `styles`, and `bundle_include[]`.

### Status panel

On a TTY, `plugin dev` renders a 4-line sticky panel at the bottom of the terminal while cargo / esbuild output scrolls above:

```text
cognia plugin dev  /path/to/plugin
  Status      Watching
  Endpoint    http://127.0.0.1:5183/...
  Last build  3.21s @07:14:22 ok
  Rebuilds    7
```

The panel updates in place — no log spam — while every rebuild's full subprocess output prints above it. On a non-TTY (CI, redirected stdout), the panel collapses to plain `println!` lines (`[07:14:22] rebuild #7 ok in 3.21s`) so logs stay grep-friendly.

### Quitting cleanly

Press **Ctrl+C twice** to quit. The first press prints `Press Ctrl+C again to quit` and lets the in-flight rebuild finish; the second press exits the loop. This mirrors `cargo-watch` and `vitest --watch`.

## Confirmation prompts

The CLI guards five destructive or surprising operations behind an interactive prompt. Every prompt is skippable with `--yes` (global flag) — required for CI.

| Command                              | Trigger                                                                | Default answer | Skip with |
| ------------------------------------ | ---------------------------------------------------------------------- | -------------- | --------- |
| `cognia plugin keygen`               | `plugin.private.b64` or `plugin.public.b64` already exists in out dir   | **No**         | `--yes`   |
| `cognia plugin sign`                 | destination `<bundle>.sig` already exists                              | **No**         | `--yes`   |
| `cognia plugin install`              | bridge reports same `id` already installed (preflight collision)        | **No**         | `--yes`   |
| `cognia plugin uninstall --purge-data` | always — Dexie wipe is one-way                                       | **No**         | `--yes`   |
| `cognia plugin dev`                  | first Ctrl+C press (graceful exit before second press)                 | _two presses_  | _N/A_     |

A "No" answer (or a non-TTY without `--yes`) **aborts** the operation without writing anything. The prompts are intentionally cautious — the cost of an accidental clobber (lost keys, dropped tables) is much higher than the cost of typing `y`.

## JSON output

Every bounded plugin subcommand accepts `--json` for machine-readable output:

| Command                          | Schema                                                                                                            |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `cognia plugin new --json`       | `{schemaVersion, ok, action, pluginId, pluginType, templateKind, directory, manifestPath, files[], keygen}`       |
| `cognia plugin lint --json`      | `{schemaVersion, manifestPath, valid, diagnostics: [{severity, field, code, message, hint?}, ...]}`                |
| `cognia plugin build --json`     | `{schemaVersion, ok, action, pluginId, version, pluginType, bundle}`                                              |
| `cognia plugin info --json`      | `{schemaVersion, ok, action, inputKind, path, sizeBytes, manifest, files, signature: {status, ...}, wasmApiVersion?}` |
| `cognia plugin sign --json`      | `{schemaVersion, ok, action, bundle, signature, publicKey, fingerprint}`                                          |
| `cognia plugin verify --json`    | `{schemaVersion, ok, action, bundle, signature, publicKey, fingerprint, stage?, error?}`                          |
| `cognia plugin keygen --json`    | `{schemaVersion, ok, action, privateKeyPath, publicKeyPath, publicKey, fingerprint}`                              |
| `cognia plugin install --json`   | `{schemaVersion, ok, action, pluginId, inputKind, path, warnings[]}`                                              |
| `cognia plugin uninstall --json` | `{schemaVersion, ok, action, pluginId, purgeData}`                                                               |
| `cognia plugin list --json`      | `{schemaVersion, ok, action, plugins[]}`                                                                          |
| `cognia plugin reload --json`    | `{schemaVersion, ok, action, pluginId, inputKind?, path?, warnings[]}`                                            |
| `cognia plugin status --json`    | `{schemaVersion, ok, action, running, endpointFile?, baseUrl?, error?}`                                           |
| `cognia plugin dev --once --json` | `{schemaVersion, ok, action, mode, pluginId, version, pluginType, bundle, reload}`                              |
| `cognia plugin embed-version --json` | `{schemaVersion, ok, action, version, input, output}`                                                         |

Every payload carries a `schemaVersion` integer; new fields can be added without bumping it, but a breaking shape change will increment it. `cognia plugin build --json` failure payloads use `stage: "input"` for missing or unreadable plugin roots/manifests, `stage: "lint"` for manifest diagnostics, and stage-specific build/pack payloads after the manifest is known. `cognia plugin keygen --json` failure payloads add `stage: "prepare" | "overwrite" | "write"` with `privateKeyPath`, `publicKeyPath`, and `error`; write failures stay on stdout and keep stderr empty for CI. `cognia plugin verify --json` uses `stage: "bundle" | "public-key" | "signature" | "verify"` only on failures. `cognia plugin dev` watch mode stays human-oriented and rejects `--json`; use `cognia plugin dev --once --json` for CI/editor smoke checks.

## Manual / marketplace distribution

The `.zip` bundle plus its `.zip.sig` are the unit of distribution. For self-hosted marketplaces, expose a JSON feed pointing at the bundle URL:

```json
{
  "plugins": [
    {
      "id": "com.example.my-plugin",
      "version": "1.0.0",
      "downloadUrl": "https://example.com/my-plugin-1.0.0.zip",
      "signatureUrl": "https://example.com/my-plugin-1.0.0.zip.sig",
      "publicKey": "<base64 — must match plugin.json author.publicKey>"
    }
  ]
}
```

In Cognia Settings → Plugins → Marketplace, add your feed URL.

## Versioning

Use semantic versioning. Bumps:

| Change                                                                                       | Bump  | Example           |
| -------------------------------------------------------------------------------------------- | ----- | ----------------- |
| Bug fix or non-breaking polish                                                               | Patch | `1.0.0` → `1.0.1` |
| New capability / additive feature                                                            | Minor | `1.0.0` → `1.1.0` |
| Renamed node kinds, removed permissions, changed connector interfaces, contract version bump | Major | `1.0.0` → `2.0.0` |

For WASM plugins, the WIT contract version lives in `wasm.apiVersion` and the CLI embeds it as a custom section in every `.wasm`. The host routes by that section, so old plugins keep loading after a host update unless the host explicitly drops the linker for their version.

## Uninstall behavior

By default, uninstalling preserves the plugin's data tables (Dexie). The user can select "Delete data" in Settings → Plugins, or pass `--purge-data` to `cognia plugin uninstall`. To clean up programmatically inside the plugin, hook `deactivate`:

```ts
export async function onDeactivate(ctx) {
  await ctx.storage.clear()
}
```
