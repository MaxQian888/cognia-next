# Workflow Nodes

Plugins can register custom `action.*` nodes that appear in the workflow editor's node palette and execute when a workflow run reaches them.

## Declaration

```json title="cognia-plugin.json"
{
  "workflowNodes": [
    {
      "kind": "action.custom.report",
      "factory": "./workflow/report.js"
    }
  ]
}
```

## Executor factory

```ts title="workflow/report.js"
export function createExecutor(ctx) {
  return {
    kind: "action.custom.report",
    async run(step) {
      const { repoFullName, format } = step.params

      // Your logic here
      const report = await generateReport(repoFullName, format)

      // Return output that downstream nodes can reference
      return {
        output: {
          reportUrl: report.url,
          rowCount: report.rows,
        },
      }
    },
  }
}
```

## Node kind naming

- Use reverse-DNS prefix: `action.<your-plugin-id>.<verb>`.
- Keep it descriptive: `action.com.example.report` not `action.com.example.n1`.
- The `action.` prefix is required; the editor groups by it.

## Params and output

The orchestrator passes `step.params` (from the node's Inspector form) and expects an object with an `output` key:

```ts
interface StepResult {
  output: Record<string, unknown>
  error?: { message: string; code?: string }
  skipped?: boolean
}
```

## Inspector form

Node parameters use the host's schema-driven Inspector. Do not mount an invented
`workflow-inspector` UI slot: only extension points listed in the generated
plugin-point catalog are accepted. A node without a specialized host renderer
uses the generic JSON editor.

## Reusable node groups

A node group is an authoring-time graph fragment, not a custom executor. When a
user inserts one from the workflow editor's **Templates** tab, Cognia rebases
every node and edge id and adds the fragment under the existing visual
`annotation.group` container in one undoable operation. Execution continues to
use the normal node registry and orchestrator.

Define node groups through the unified template SDK and register the collection
atomically through `ctx.templates`. Do not add them to the deprecated
`workflowTemplates` manifest field.

```ts
import {
  createTemplateDefinition,
  defineWorkflowNodeGroup,
  defineWorkflowNodeGroups,
} from "@cognia/plugin-sdk/templates"

export async function activate(ctx) {
  const review = defineWorkflowNodeGroup(
    await createTemplateDefinition({
      id: `${ctx.pluginId}:review-group`,
      domain: "workflow",
      status: "published",
      revision: 1,
      version: "1.0.0",
      metadata: {
        name: "Review group",
        description: "Review input and expose the structured result",
      },
      payload: {
        kind: "cognia.workflow/node-group/v1",
        nodes: [
          {
            id: "review",
            type: "ai.prompt",
            typeVersion: 2,
            position: { x: 0, y: 0 },
            data: {
              label: "Review",
              params: { prompt: "Review {{ $trigger.payload }}" },
            },
          },
          {
            id: "output",
            type: "io.output",
            typeVersion: 1,
            position: { x: 300, y: 0 },
            data: { label: "Output", params: {} },
          },
        ],
        edges: [{ id: "review-output", source: "review", target: "output" }],
      },
      inputs: [],
      dependencies: [],
      capabilities: [],
      compatibility: { platforms: ["desktop", "web", "mobile"] },
      provenance: {
        source: "plugin",
        pluginId: ctx.pluginId,
        trust: "unsigned",
      },
    })
  )

  const groups = defineWorkflowNodeGroups([review])
  ctx.templates.registerMany(groups)
}
```

Dynamic definitions require the `templates:contribute` permission, must use an
id prefixed with the active plugin id, and must be immutable published releases.
A group is limited to 256 nodes and 1,024 internal edges. Batch registration
validates every definition before publishing any of them and emits one catalog
revision for the entire collection.

## Error handling

Throw from `run()` to mark the step as failed. The orchestrator applies the node's `retryPolicy` if configured:

```ts
if (!repoFullName) {
  throw new Error("repoFullName is required")
}
```
