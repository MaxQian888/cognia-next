# FAQ

## 凭据 / 鉴权

<Accordions>
<Accordion title="GitHub 端 webhook 投递返回 401 / 403">

**症状.** GitHub Webhook 设置页的 Recent Deliveries 看到 `401` 或 `403`,
Audit Tab 没有任何对应行。

**原因 + 排查清单.**

1. **签名校验失败.** Settings → GitHub Delivery → Credentials → Webhook secret 与 GitHub
   端 Webhook → Secret 必须**字符级一致**,包括末尾换行。`webhook-verify.ts:verifyGithubSignature`
   会读 `x-hub-signature-256` 头 → `sha256=<hex>`,与 cognia 自己用同一个 secret 计算的
   HMAC-SHA-256 做 `timingSafeEqual` 比较。
2. **Body 被中间层改过.** cloudflared / nginx / Caddy 默认不会改 body,但 gzip 解压 / utf-8
   规范化等中间件会让 HMAC 失效 —— 验证 reverse-proxy 是 `proxy_pass` 而非 `body_filter_by_lua`。
3. **GitHub 端不发 `x-hub-signature-256`.** 当 webhook 没设 Secret 时,GitHub 不会签名;
   cognia 此时直接 401。补一个 Secret 即可。

</Accordion>

<Accordion title="Octokit 抛 `401 Bad credentials`">

**症状.** 工作流节点失败,error message 含 `Bad credentials`。

**原因 + 排查清单.**

1. **App 私钥被截断.** Settings → Credentials → 重新粘贴完整的 PEM(必须包含 `-----BEGIN
RSA PRIVATE KEY-----` 和 `-----END` 行)。
2. **PAT 已被吊销 / 过期.** GitHub → Settings → Developer settings → tokens 检查;
   重新生成后到 Credentials Tab 粘贴。
3. **Installation 已被卸载.** 在 GitHub → Settings → Installations 确认 App 仍安装于目标仓库。
   若曾在 GitHub 端 "Suspend installation",所有 token 立即失效。
4. **Token 缓存命中已过期值.** 极少见,但 `lib/github/auth-app.ts:evictInstallationToken(appId, installationId)`
   可强清。重启 cognia 也会清掉进程内缓存。

</Accordion>

<Accordion title="GitHub App vs PAT 该怎么选?">

| 场景                            | 推荐    | 原因                                                    |
| ------------------------------- | ------- | ------------------------------------------------------- |
| 个人玩具仓库,自动化只对自己负责 | **PAT** | 配置最简单,只需要粘贴一个 token                         |
| 公司 / 组织内的协作仓库         | **App** | 安装 / 卸载粒度独立于个人;一个 installation 5K/h 独立桶 |
| 多仓共用一个机器人              | **App** | 同上                                                    |
| 个人手痒,但担心 5K/h 共享       | **App** | 不与你其他自动化共享速率桶                              |
| 临时实验或一次性任务            | **PAT** | 用完就吊销;App 创建一次性成本相对高                     |

</Accordion>
</Accordions>

## 触发器

<Accordions>
<Accordion title="Webhook 触发器在 Web 模式下不工作">

**症状.** 在 Web 模式(浏览器 / 没装 Tauri 桌面应用)注册 `trigger.github.webhook`
工作流,GitHub 投递了 webhook 但 cognia 完全没反应。

**原因.** Web 模式没有 Rust axum 接收器(`src-tauri/src/workflow/triggers/webhook_router.rs`
只在 Tauri 里编入)。Repos Tab 会显示一个 "desktop only" 提示,工作流编辑器的连接验证器也会
拒绝把 webhook 触发器拖到画布上(`lib/workflow/editor/connection-validator.ts`)。

**对策.**

- 桌面端跑 cognia,或
- 把 Repo 的 `triggerMode` 切到 `polling`(无桌面前提)。

</Accordion>

<Accordion title="Polling 启用了但 Audit Tab 不出新行">

**症状.** `triggerMode` 设了 `polling`,但 5 分钟过去 audit Tab 还是空的。

**排查清单.**

1. **仓库是否仍配置为已停用的 polling 模式？** 将 `triggerMode` 改为 `webhook`。
2. **仓库在最近 90 天有过事件吗?** `/repos/{owner}/{repo}/events` 端点只回 90 天内的事件。
   长时间没活动的仓库会"看起来什么都没发生"。
3. **`pollEtag` 一直是同一个值吗?** Dexie DevTools 看 `github-delivery:repos` 行,如果
   `pollEtag` 一直不变 = GitHub 端真的没新事件,304 路径正确。
4. **凭据有 `events` 权限吗?** App 的 permissions 必须含 Metadata: Read(events 是隐式的)。
   PAT 必须有 `repo` scope。

</Accordion>

<Accordion title="同一个事件被 webhook 和 polling 都收到了,会重复触发吗?">

轮询 transport 已停用。GitHub 事件只通过 Rust webhook 路径进入，并使用
`x-github-delivery` header 作为稳定 delivery id。

</Accordion>
</Accordions>

## 节点 / 工作流

<Accordions>
<Accordion title="`action.github.runIssueLoop` 抛 `No issue-loop AI driver is registered`">

**原因.** Issue → PR loop 需要 Claude sidecar 驱动器(`plugins/github-delivery/src/drivers/sidecar-driver.ts`)。
当插件 activate 时:

```ts title="plugins/github-delivery/src/index.ts"
setIssueLoopDriver(new SidecarIssueLoopDriver())
```

但 driver 自己会在 `driver.run` 时检查 Claude sidecar 是否就绪。如果 Claude provider 没配
(Settings → Providers → Claude 一栏空),或 sidecar 进程没起来,driver 就在 `run` 内部抛错,
返回 `{ status: "failed", reason: "..." }`。

**对策.**

1. Settings → Providers 配置 Claude(可以是 OAuth 也可以是 API key)。
2. Settings → Subscription(如果你用 OAuth)登录确认。
3. 重启插件:Settings → Plugins → GitHub Delivery → Disable / Enable。
4. 再跑一次工作流。

</Accordion>

<Accordion title="`action.github.mergePr` 总被拒,reason 是 `requires explicit human approval`">

**原因.** 默认策略 `requireHumanApproval: true`。该决定是"软拒绝"(`needsApproval: true`),
会被 `guardedExecutor` 路由到 Inbox HITL 草稿。打开 `/inbox`,找到对应 PR 的会话,
点 Approve / Reject / Edit body。

**对策(三选一).**

- 在 Inbox 实际人审一下(推荐)。
- 给该 PR 节点设 `policyOverride: { requireHumanApproval: false }`(节点级,谨慎)。
- 在 Settings → GitHub Delivery → Policies 把仓库级 `requireHumanApproval` 关掉。

</Accordion>

<Accordion title="`mergePr` 抛 `daily merge cap of N reached`">

**原因.** 默认 `maxDailyMerges: 5`。每个 UTC 日机器人 merge 计数从 audit 表
`[repoFullName+at]` 索引扫出,filter `action.kind === "merge" && decision.allow === true`。

**对策.** 拉高仓库级或节点级 `maxDailyMerges`,或等到第二天 UTC 日切换。

</Accordion>

<Accordion title="`action.github.openPr` 抛 `branch 'main' matches protection regex '^main$'`">

**原因.** `openPr` 把 `head` 当成 push 分支送进策略门。默认 `branchProtection`
含 `^main$` / `^master$` —— 这通常是合理的,因为 cognia 不应该直接把 PR 的 head 指到主干。

**对策.** 确认你写的是 `head: "cognia/feature-xxx"` 而不是 `head: "main"`。

</Accordion>
</Accordions>

## cloudflared / 网络

<Accordions>
<Accordion title="点 'Expose webhook' 后什么都没发生">

**排查清单.**

1. **cloudflared 在 PATH 里吗?** 终端跑 `cloudflared --version`。Tauri 的 shell scope 只
   允许调用 PATH 中的 cloudflared。
2. **Tauri shell scope 是否含 cloudflared.** 看 `src-tauri/tauri.conf.json` 是否有
   `"name": "cloudflared", "command": "cloudflared", "args": true` 或类似的 allow 行。
3. **看 Diagnostics 日志.** Settings → Diagnostics,搜 "cloudflared"。常见错误:
   - `EACCES`:macOS 上 Gatekeeper 未签名拦截 —— `xattr -d com.apple.quarantine $(which cloudflared)`。
   - `proxy connection refused`:本机端口已被占用 —— 重启 cognia,Rust 会重新挑端口。

</Accordion>

<Accordion title="可以用其它隧道工具(ngrok / localtunnel / Caddy)吗?">

**可以。** Repos Tab 上点 "Show local webhook URL" 看到 `http://127.0.0.1:<port>/<repo-id>`,
然后让你选择的隧道工具反向代理这一段。注意:

- 必须保留 `x-hub-signature-256` 头原样转发。
- 不要让中间层做 gzip 压缩 / 解压(会破坏 HMAC)。
- 端口在 cognia 启动时随机分配;重启 cognia 后端口会变。Repos Tab 有 "Refresh URL" 按钮。

</Accordion>
</Accordions>

## Inbox / 出站

<Accordions>
<Accordion title="GitHub PR 评论从 Inbox Composer 发不出去">

**症状.** 在 `/inbox/c/gh:owner/repo/pr-42` 会话里打字 + 发送,但 GitHub PR 没出现评论,
Composer 显示 "queued" 状态卡很久。

**排查清单.**

1. **插件启用了吗?** Settings → Plugins。`PlatformAdapter` 适配器是 plugin activate 时注册的,
   不启用就拿不到 `github` 适配器。
2. **出站队列被熔断了?** Settings → Connections → Outbound 查看 `github` 的熔断器状态。
   失败率 ≥ 50%(10 事件窗口)会跳 30 秒。
3. **安静时段中?** 同样的 quiet-hours 工具也作用于 outbound runner。Settings → Connections
   → Conversations 可以看 mute 状态。

</Accordion>
</Accordions>

## 数据 / Dexie

<Accordions>
<Accordion title="插件卸载后想恢复 audit 数据怎么办">

**前提.** 默认卸载是"保留数据"(`removePluginTables(..., "keep")`)。这种情况下:
重新启用插件,4 张表自动出现,数据还在。

**如果选了 "Delete data" 卸载.** 数据已被 drop。如果你之前在 Audit Tab "Export CSV"
保存过文件,可以再 import 回来(M4 之后):Audit Tab → Import CSV。**不在生产数据里
依赖此能力 —— 请定期导出。**

</Accordion>

<Accordion title="`pluginDexieMeta` 行是干嘛的?">

记录每个插件已应用到 CogniaDB 的 dynamic schema 版本。GitHub Delivery 启用时,
`applyPluginTables` 把当前的表声明 hash 记进去;下次启用如果 hash 没变,直接跳过 schema 升级,
是 idempotent 的。详见
[Plugin Dexie Tables 开发指南](/zh/plugin-dev/dexie-tables)(M3 阶段写)。

</Accordion>
</Accordions>

## 其它

<Accordions>
<Accordion title="为什么编号是 0018 而不是 0012?">

最早的 GitHub Delivery ADR 起草时,文件路径在 `docs/content/docs/adr/` 下(尚未进入 zh/en
分树),临时编号 0012。后来发现 `zh/adr/0012-transport-abstraction.md` 早就占了 0012,
两者冲突。规范化后 GitHub Delivery 改成 0018,transport-abstraction 保留 0012。
原 `docs/content/docs/adr/0012-github-delivery.md` 已被移除,引用请用
[/zh/adr/0018-github-delivery](/zh/adr/0018-github-delivery)。

</Accordion>

<Accordion title="模板里那一堆 `{{ ... }}` 是什么语法?">

工作流的表达式语言,见 [Workflows → Expression language](/zh/workflows/expression-language)
(M2 阶段写)。可以索引 `$trigger.payload.body...`(webhook 原始 payload)、
`$node['n_id'].out.<field>`(上游节点输出)、`$static.<key>`(工作流静态变量)等。
Inspector 里所有标注"supports {{ }} expressions"的字段都接受这种表达式。

</Accordion>

<Accordion title="测试时怎么不真的开 PR / 评论?">

工作流编辑器右上角的 "Run" 按钮有一个 "Dry run" 模式 —— 节点会被执行但
`guardedExecutor` 在所有 deny 路径上都返回 `{ output: { skipped: true } }`,
具体每个执行器的 dry-run 行为请看
[nodes 参考](/zh/github-delivery/nodes)。生产路径用真实 Run,审阅历史可以重跑同一个
snapshot(`runs/[runId]` 详情页有 "Re-run from snapshot")。

</Accordion>
</Accordions>
