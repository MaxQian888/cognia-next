# 安装与凭据

## 前置条件

| 条件                                    | 必需 | 说明                                                                      |
| --------------------------------------- | ---- | ------------------------------------------------------------------------- |
| cognia 0.1.0+                           | 是   | 插件 manifest 写明 `engines.cognia >= 0.1.0`                              |
| Tauri 桌面构建(macOS / Windows / Linux) | 否   | Web 仍可运行节点 + 轮询,但不能注册 webhook                                |
| GitHub 账号 + 仓库写权限                | 是   | App 模式需要在仓库或组织内安装 App;PAT 模式需要 token 至少含 `repo` scope |
| 公网入口或 cloudflared                  | 否   | 仅当用 webhook 触发器时需要;否则继续用轮询                                |

## 1. 启用插件

<Steps>
<Step>
**进入插件中心。** Settings → Plugins(`?section=plugins`)→ Marketplace。在列表中找到
"GitHub Delivery"。
</Step>
<Step>
**点击 Enable。** 插件管理器会:

1. 校验 `manifest.dexie.tables` 中的 4 张表 schema,通过 `applyPluginTables(db, "github-delivery", ...)`
   将 `repos` / `workOrders` / `events` / `audit` 注入 CogniaDB。
2. 写入 `pluginDexieMeta` 行,标记 schema 版本已应用。
3. 调用 `activate(ctx)`(`plugins/github-delivery/src/index.ts`),它会:
   - 触碰 4 张表(发现 schema 不匹配在此抛错)。
   - 注册 13 个 `action.github.*` 节点执行器到工作流注册表。
   - 通过 `setGithubRuntime(...)` 安装运行时单例(`getRepo` / `getOctokit` / `recordAudit` /
     `checkPolicy` / `getWorkOrder` / `upsertWorkOrder`)。
   - 注册 Issue → PR loop 的 Claude sidecar 驱动器。
   - 通过 `registerPluginAdapters` 把 `github` 连接器适配器登记到 ConnectorBus。
</Step>
<Step>
**确认 Settings → GitHub Delivery 可见。** 侧边栏在 "Extensions" 组下出现 GitHub Delivery
入口。点开后看到 5 个 Tab:Repos / Credentials / Policies / Audit / Usage。
</Step>
</Steps>

<Callout type="warn">
**桌面前提.** Tauri 桌面端启动时,内置 axum 接收器(`src-tauri/src/workflow/triggers/webhook_router.rs`)
会在 `127.0.0.1:<随机端口>` 绑定 webhook 路由。Web 模式没有这层,所以 `trigger.github.webhook`
节点在 Web 上跑不起来 —— Repos Tab 会显示一条 "desktop only" 提示。
</Callout>

## 2. 选择凭据模式

<Tabs items={['GitHub App(推荐)', 'PAT(快通道)']}>
<Tab value="GitHub App(推荐)">

**特点**

- 每小时 5K Octokit 调用(单仓 PAT 通常 5K/账号,App 是 5K/installation)。
- 按 installation 隔离,审计粒度细。
- token 自动按 1 小时过期 + 提前 5 分钟刷新(`lib/github/auth-app.ts:getInstallationToken`)。
- cognia 不持有共享 App,App 私钥归用户。

**步骤**

<Steps>
<Step>
**在 GitHub 创建 App。** Settings → Developer settings → GitHub Apps → New GitHub App。

- Repository permissions(最少够用):
  - Contents: Read & write
  - Issues: Read & write
  - Pull requests: Read & write
  - Metadata: Read
  - Checks: Read(用于 CI failure diagnosis)
- Subscribe to events:勾选下列即可(覆盖 cognia 支持的 11 个 `NormalizedGhEventKind`):
  - Pull request、Pull request review、Issues、Issue comment、Check run、Release。
- Webhook URL:留空,稍后回来填(我们要等 cognia 端给出真实路径)。
- Generate a private key,下载 PEM 文件。
</Step>
<Step>
**在目标仓库或组织里 Install 该 App。** 安装完成后从 URL 抓取 `installation_id`
(例如 `https://github.com/settings/installations/12345678` → 12345678)。
</Step>
<Step>
**在 cognia 填入凭据。** Settings → GitHub Delivery → Credentials,选择 App 模式,填:

| 字段              | 来源                           |
| ----------------- | ------------------------------ |
| App ID            | GitHub App 设置页顶部的 App ID |
| Installation ID   | 安装该 App 后的 URL 路径里     |
| Private key (PEM) | 下载的 `.pem` 文件全文         |

私钥在桌面端会被搬到 OS keyring(`ctx.secrets.set`)并从 IndexedDB 行里抹掉;
Web 端继续留在加密 blob 里。

</Step>
</Steps>

</Tab>
<Tab value="PAT(快通道)">

**特点**

- 配置最简单:粘贴一个 token 就可以跑。
- 速率限制 5K/小时 per token,被 token 创建者的所有应用共用。
- 没有 installation 概念,审计只到"这个人"的粒度。
- 必须使用 fine-grained PAT 或经典 PAT 的最小 scope。

**步骤**

<Steps>
<Step>
**创建 PAT。** GitHub → Settings → Developer settings → Personal access tokens
→ Fine-grained tokens → Generate new token。

- 选择目标仓库。
- Repository permissions:Contents (RW)、Issues (RW)、Pull requests (RW)、Metadata (Read)、
  Checks (Read)。
- 不要勾选 Organization permissions(以最小权限为原则)。
</Step>
<Step>
**在 cognia 粘贴 token.** Settings → GitHub Delivery → Credentials → 选择 PAT,
粘贴 token。桌面端会在 OS keyring 保存,并把 row 里的 `patToken` 清掉(以 `patKeyringId`
为唯一来源)。
</Step>
</Steps>

</Tab>
</Tabs>

## 3. 注册仓库

Settings → GitHub Delivery → Repos:

| 字段                    | 含义                                                      |
| ----------------------- | --------------------------------------------------------- |
| Full name(`owner/name`) | 仓库的标准全名                                            |
| Credential mode         | `app` 或 `pat`(决定 `octokit-factory` 的路径)             |
| Trigger mode            | `webhook` 或 `polling`(见下节)                            |
| Worktree mode           | `local`(默认,简单 git clone)或 `e2b`(走 e2b-sandbox 插件) |
| Push target             | `source-branch` 默认 / `fork`(向 fork push)               |
| Policy                  | 可选,仓库级覆盖。完整字段见 [policies](./policies)        |

行被写到 `github-delivery:repos` 表;主键 = `fullName`。

## 4. 暴露 Webhook URL(可选)

webhook 模式比轮询更实时,但需要公网可达的 URL。三种做法:

<Tabs items={['cloudflared 一键(推荐)', '自己反向代理', '使用轮询']}>
<Tab value="cloudflared 一键(推荐)">

桌面端内置 cloudflared 一键暴露:

<Steps>
<Step>
**确认 cloudflared 在 PATH 里。** macOS:`brew install cloudflared`;Windows:`scoop install cloudflared`;
Linux:`apt install cloudflared`。Tauri 已经在 `tauri.conf.json` 给 cloudflared scope 留好了
allow rule。
</Step>
<Step>
**在 Repos Tab 点 "Expose webhook"。** cognia 调用 `lib/github/cloudflared-tauri.ts`:
启动一个 quick tunnel,把 `https://<random>.trycloudflare.com/<repo-id>` 路由到本地的
Rust 接收器。返回的 URL 会自动写回 Repo 行。
</Step>
<Step>
**把 URL 回填到 GitHub App / 仓库的 webhook 设置。** Content type:`application/json`,
Secret:任意强随机字符串(cognia 会请你输入并存入 OS keyring),Events:勾选
"Send everything" 或上面列的几个事件。点 "Update webhook"。
</Step>
<Step>
**测试投递。** GitHub Webhook → Recent Deliveries → Redeliver。Audit Tab 应该立即看到
一条记录。
</Step>
</Steps>

</Tab>
<Tab value="自己反向代理">

如果用 ngrok、Caddy、nginx 反代到本机:

1. Repos Tab 上点 "Show local webhook URL" 看到形如 `http://127.0.0.1:<port>/<repo-id>` 的本地 URL。
2. 在你自己的反代里把外网域名映射到此 URL。
3. 把外网域名填进 GitHub Webhook URL。
4. 在 Settings → GitHub Delivery → Credentials → Webhook secret 输入一个强随机字符串,
   并在 GitHub 端的 Webhook → Secret 填一样的值。

</Tab>
<Tab value="使用轮询">

无公网入口时,把 Repo 的 `triggerMode` 改成 `polling`:

轮询后备路径已停用。无直接公网入口时，请使用内置 cloudflared tunnel 暴露 webhook URL。
已有 `triggerMode: "polling"` 的仓库需要切换为 `"webhook"`。

</Tab>
</Tabs>

## 5. 验证

<Steps>
<Step>
**注册一个 webhook 触发器。** 工作流编辑器 → 新建 → 拖入 `trigger.github.webhook` 节点,
events 选 `pull_request.opened`,保存。
</Step>
<Step>
**手动触发一次。** 在目标仓库开一个 draft PR(或在已有 PR 上 "Redeliver" 最近的 webhook)。
</Step>
<Step>
**确认事件落库。** Settings → GitHub Delivery → Audit Tab 应该看到一条 `pull_request.opened`
记录,`source: "webhook"`,`deliveryId` 与 GitHub Recent Deliveries 一致。
</Step>
<Step>
**确认 Inbox 出现。** 打开 `/inbox`,左侧栏会多出一条 `gh:<owner>/<repo>/pr-<n>` 会话,
最新消息是 `<sender> opened PR #<n> in <repo>`。
</Step>
</Steps>

## 故障速查

| 现象                                           | 可能原因                                   | 排查                                                                            |
| ---------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------- |
| Webhook 进来但 audit 没有任何行                | 签名校验失败                               | 确认 `x-hub-signature-256` 在头里;Settings → Webhook secret 与 GitHub 端一致    |
| `401 Bad credentials`                          | App private key 错误或 installation 未授权 | 检查 PEM 完整(包括 `-----BEGIN` / `-----END` 行);确认 installation 仍存在       |
| `404 Not Found`(只读 endpoint)                 | App 安装时未勾选必要 repo permission       | 修改 GitHub App permissions,然后在仓库里 "Re-authorize" App                     |
| 仓库收不到事件                                 | 仍使用旧的 `triggerMode: "polling"`       | 切换为 webhook 模式并检查公网 webhook URL                                  |
| 节点抛 `No issue-loop AI driver`               | sidecar 未启动                             | 在 Settings → Providers 连接 Claude Code provider,然后重启插件                  |
| `tauri.conf.json` shell scope 拒绝 cloudflared | 升级前的旧配置                             | 拉一下 main,确认 shell scope 含 `cloudflared` 的 allow 行                       |
