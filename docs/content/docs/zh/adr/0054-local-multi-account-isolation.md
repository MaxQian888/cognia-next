# ADR-0054 — 本地多账户隔离

**状态**：已接受（2026-06-21）**作者**：Max Qian + Codex **基于**v86 project/workspace隔离模型、AppSettings单例、本地订阅密钥环保险库、伴随同步以及ADR-0037公开分享链接。

## 背景

Cognia的本地应用目前设计上是单用户。Dexie数据库物理上命名为`cognia-claude`，`AppSettings`是一个单例行，ID为`singleton`，活跃workspace/project ID存在于该单例中。v86 项目层已经通过确保有作用域的数据解析为非空`projectId`，实现了本地用户内部工作区间的隔离。

新的要求不同：多人必须能够使用同一设备并拥有独立的本地账户，且一个账户的数据必须对另一个账户隐形。没有云后端，主应用仍是Next.js静态导出（`output: "export"`），桌面端由Tauri壳覆盖，移动端则Capacitor。任何特权本地工作，如密码验证助手，都保留在Tauri Rust中，而非Next.js路由处理器。

我们评估了三种方案：

- **A. 按本地账户单独Dexie数据库**。每个账户都拥有一个实体数据库，如`cognia-account-<accountId>`。现有的project/workspace隔离在该数据库内保持不变。该应用保持一个用户独立的账户注册表，存储账户元数据、活跃账户指针和遗留迁移状态。
- **B. 单Dexie数据库，每个表都有`userId`**。这需要在每个持久化的表和每个有作用域的查询中添加`userId`，包括未来的表。它还会让所有用户集中在一个实体浏览器数据库中。
- **C.A或B加上静态加密**。通过Rust KDF支持，将从本地密码中获得每用户密钥，并加密磁盘上的持久化数据。它提供了更强的保密性，但实质性地扩展了迁移、恢复和移动端的复杂性。

批准阶段选择**A，带有本地密码应用层lock/unlock且无静态加密**。加密技术仍是可能的后续发展ADR;该ADR不声称对拥有文件系统访问权限的本地攻击者提供磁盘机密性。

## 决策

### 账户隔离模型

- 添加一个用户独立的本地账户注册表。它不存储在每个账户的 `AppSettings` 里，因为`AppSettings`只有在账户数据库已知后才存在。
- 每个账户拥有稳定的不透明`accountId`、显示名称、密码验证元数据、creation/update时间戳和生命周期状态。
- 运行时应用数据存储在每个账户的一个Dexie数据库中，名为`cognia-account-<accountId>`。
- 活跃账户指针存在账户注册表，而不是`AppSettings`。
- `CogniaDB`解决方案变得对账户感知。账户初始化后，普通应用只读取当前账户数据库。切换账户会关闭当前Dexie处理并重新加载账户本地商店。
- 现有的project/workspace层保持在账户层的下一层。`AppSettings.activeProjectId`、项目、会话、消息、连接器、配对设备、同步光标和工作区范围的本地数据保持账户本地，因为它们存在于所选账户数据库中。

### 认证

- 账户使用本地密码来解锁账户门禁。
- 密码验证通过Tauri Rust 命令运行，因此桌面可以使用原生KDF实现，未来的静态加密也可以重复使用相同的边界。
- 该阶段不加密静止Dexie行。“相互隐形”意味着应用层和数据库选择隔离，以及账户范围的 密钥环 和同步路由。
- web/static-export构建不得导入仅服务器代码，也不能依赖`app/api`路由处理器登录。

### 遗留单用户迁移

- 已有的`cognia-claude`安装会自动被封装到升级后的第一个本地账户中。
- 迁移会将所有遗留表复制到第一个账户数据库，只有在副本完成并验证后，才在账户注册表中记录成功。
- 迁移过程中，遗留源数据库不会被删除。它仍是一个回滚源，直到未来明确的清理流程设计出来。
- 迁移测试必须做种代表性的 v86 数据，并证明设置、项目、会话、消息、连接器行、伴行、共享链接和同步光标在账户 #1 中完整落地，而账户 #2 则缺失。

### 凭证与密钥环命名空间

- 接受`(namespace, key)`的现有密钥环原语会被重复使用。
- Subscription/provider金库和其他本地秘密会获得本地账户维度。有效身份是`localAccountId × provider × providerAccountId`的，而不仅仅是提供商层的身份。
- 遗留提供商秘密会尽可能被采纳到第一个迁移的账户中;否则UI必须要求该账户重新认证。其他账号不得看到或重复使用这些秘密。

### 伴随同步作用波

- 伴侣同步是针对活跃账户的。
- Pairing/JWT/device身份获得一个账户绑定。在账户A下配对的移动设备在桌面账户切换后无法拉取账户B。
- 同步拉取事件会承载或解析账户ID，TypeScript桥会拒绝与激活解锁账户不匹配的请求。
- 同步光标仍保留在每个账户的Dexie数据库中，但RPC验证在读取数据前仍会拒绝跨账户不匹配。

### 股份链接所有权

- 公共分享链接保持其现有的Worker端`ownerToken`隔离。
- 本地共享链接镜像行通过每个账户数据库转为账户本地。
- 如果后续功能需要服务器可见的账户分组来管理所有者令牌，那就应该放在后续ADR;局部隔离时不需要。

## 后果

- 物理Dexie分离避免了在每个表和查询路径中进行后期配置`userId`。
- project/workspace隔离模型保持完整，并在账户层下自然组合。
- 主动账户指针在`AppSettings`外有一个明确的自助回家，避免了先有鸡还是先有蛋的依赖。
- 更换账户比更换项目更具破坏性，因为它改变了活跃的数据库。需要有意识地重新加载应用级或全仓补水。
- 应用层隔离不同于静止加密的机密性。需要磁盘机密性的用户需要未来加密阶段。

## 超出范围

- 对Dexie行进行静态加密。
- 云端身份、账户同步或远程登录。
- Next.js 运行时路由处理器进行账户认证。
- 在第一次迁移时移除遗留`cognia-claude`数据库。
- 取代现有的project/workspace模型。
