# ADR 0162：SFTP 等同于 shell

**Status:** Accepted  
**日期：** 2026-09-01  
**基于：** [ADR-0082](./0082-remote-development-remote-host)、[ADR-0031](./0031-integrated-terminal)

## 背景

仓库里有一个完整的 SSH 客户端。`crates/cognia-terminal/src/ssh.rs` 支持口令、
私钥、agent 三种认证，带 TOFU 的 `known_hosts` 与主机密钥变更时的失败关闭，
深度五的跳板链，`-L` 与 `-R` 转发，以及在远端 shell 上注入 OSC 633。
它没有 SFTP，也没有 SCP。没有客户端，没有协议帧，没有界面，
在此之前也没有任何记录说明文件传输是被拒绝了还是只是没做。

配对的手机或浏览器已经可以在保存的 SSH 主机上打开 shell。`/ws/terminal` 的
Spawn 帧只携带一个 profile 标识符，`TerminalHost::spawn_synchronized_profile`
在它自己桌面同步过来的 `ssh_profiles` 表里解析它，用永不离开宿主进程的凭据拨号。
这是 ADR-0082 的第 8 条决定，并且已经在跑。

加文件传输最顺手的做法是照抄工作区文件 API 的词表。`fs_list_workspace_dir`
和它的九个兄弟都是 `execution` 作用域，走 http、websocket、webrtc，
读用 `host.observe` 授权，写用 `workspace.write`。照抄是错的，
而原因正是这份记录的全部主题。

那些调用之所以能安全地用那两个名字，是因为 `authorize_workspace_root`
把每一次调用都限制在宿主已注册的目录里。客户端给出 `root` 和 `relPath`，
一个逃出自己 root 的 `relPath` 会在落盘前被拒绝。**SFTP 没有等价物。**
SFTP 路径是远端的绝对路径。拒绝 `..` 挡不住 `/etc/shadow`，
也挡不住远端机器管理员自己放的一个符号链接。没有可以校验的根，
因为被访问的是别人的文件系统。

ADR-0082 的第 9 条决定拒绝了配对设备开启端口转发。这里值得把
「那条拒绝为什么不延伸到这里」讲清楚，而不是悄悄放宽或者悄悄照搬。

## 决定

### SFTP 给出的就是 shell 给出的，界面不装作不是

在一台机器上开一个 shell，本来就能读写它的整个文件系统。`cat`、`>`、`tar`、
`scp` 全都能从配对设备已经能打开的那个提示符里够到。
用同一个已保存 profile 走 SFTP，增加的是界面，不是权限。

所以这份 ADR 不声称一个自己无法强制的限制。文档、授权说明、设备控制台三处
都会写明：持有该授权的设备可以以该 profile 的用户身份读写目标机器。

### 只能通过桌面已经同步过的 profile 到达

与 shell 同一条规则。配对设备只能给出一个 profile 标识符，再无其他。
它不能创建或修改 SSH profile：`TerminalHost::sync_ssh_profile` 与
`replace_synchronized_profiles` 仍然只接受本机身份，
携带 `sshProfiles` 的设备 hello 仍然被拒。这里没有放宽第 8 条决定。

### 专用的 `ssh.files` 授权，不借用工作区词表

复用 `host.observe` 和 `workspace.write` 会谎报这些调用的作用域。
一个审查设备授权的人会看到同样两个名字既表示「读一个已注册的工作区目录」
又表示「读生产服务器上的任意文件」，而这不是同一种权限。

因此 `ssh.files` 是它自己的授权，默认关闭，
在设备控制台上与既有授权并列，说明里写清「等同 shell」。
被授予 `terminal.open` 的设备不会隐式获得它，
哪怕持有 `terminal.open` 的设备绕一圈也能拿到同样的字节。
让用户单独授予它，正是审计线索保持诚实的原因。

### 永远不绑定监听端口，这就是第 9 条决定原封不动的理由

第 9 条决定拒绝转发，是因为转发会让宿主，或者宿主能到达的机器，**绑定一个套接字**。
那是新的入站面，也是当时被拒绝的东西。SFTP 不绑定任何东西，
它在 shell 用的同一条出站连接上打开一个 subsystem 通道。

同步过去的 profile 仍然像以前一样丢掉跳板链和转发规则。
配对设备指定一个 profile，得到的是 shell 和文件传输，仍然永远不是监听端口。

### 审批在 open 上做一次，绝不是每个分块一次

传输命令是分块的，因为 RPC 报文上限是 64 KB。一个带 `approval: "interactive"`
的分块命令会让用户每个分块被问一次，对一个 100 MB 的文件就是三千多次。
那不是安全控制，那是对被保护的人发起的拒绝服务。

`sftp_upload_open` 与 `sftp_download_open` 承担审批。两者各铸造一个短期
transfer token，绑定发起设备、profile、路径、声明大小与方向。
`sftp_upload_write_chunk`、`sftp_download_read_chunk`、`sftp_upload_commit`
只校验该 token，自身不带任何审批。这正是 `session_attachment_upload_*`
已经采用的形状，也是它能做到 `approval: "none"` 的原因。

### 一个传输句柄只属于一台设备

token 绑定打开它的设备。一台手机不能把字节写进另一台手机的上传里，
泄漏出去的句柄对别人也没有用。写指针由宿主掌握，
所以客户端无法指定一个宿主没有到达过的偏移。

### SFTP 会话出现在终端会话出现的地方

一条带闲置回收、谁都看不见的池化连接，会是它与 shell 之间唯一真实的不对称。
shell 会出现在宿主的会话列表和审计事件里，SFTP 会话也一样。
「某台手机正在读生产机上的文件」必须是可观测的，
否则上面那条授权就是不可审计的。

### 连接池按配置指纹做键，不是按 profile 标识符

`sync_ssh_profile` 是按标识符覆盖写入的。只按标识符做键的池，
会保留一条连到该 profile 曾经指向的那台机器、用它曾经携带的凭据认证过的活连接，
并把它交给下一个请求新配置的调用者。键是标识符加上一个覆盖
解析后的目标、凭据引用与跳板链的指纹。

### 独立的 SSH 会话，不是终端那条会话上的一个通道

Termius 和 VS Code Remote 都是各开各的。把传输绑到终端标签上，
意味着关掉一个无关的标签就会中断正在跑的传输，
也意味着不先开一个没人想要的 shell 就没法浏览文件。
代价是第二次认证，由宿主进程用同一个 keyring 支付，以及第二次走跳板链。

主机密钥的判定是复用而不是重新推导，所以同一台机器不会在一次会话里被要求信任两次。

## 后果

- 持有 `ssh.files` 的配对设备可以以该 profile 的用户身份读写目标机器。
  这一点是明说的，不是暗示的，写在三个地方：这份记录、授权说明、控制台行。
- 没有 `ssh.files` 的配对设备不能传文件，即使它持有 `terminal.open`
  并且能通过 shell 够到同样的字节。这两个授权是刻意不合并的。
- 配对设备做的任何事都不会导致一个套接字被绑定。第 9 条决定原封不动。
- 被打断的传输从宿主的写指针恢复，而不是从客户端自己的算术恢复，
  过期的 token 会强制重新审批。
- 传输过程中被编辑的 profile 会在下一次 open 时让池化连接失效，因为指纹变了。
  正在跑的传输不会中途改指向。
- 没有 SCP。SFTP 覆盖同样的范围，而且是一个会报错的协议，
  再加一套传输词表只会让这份记录要描述的面翻倍。

## 备选方案

**把 SFTP 限制在一个声明的远端根里。** 否决，因为这个限制无法强制。
远端机器自己解析符号链接，客户端可以指定绝对路径。
一个在界面上写着、在线路上不存在的限制，比没有限制更糟，
因为它对读者说了一件关于授权范围的假话。

**复用 `host.observe` 和 `workspace.write`。** 否决。
这两个名字会谎报调用的作用域，设备控制台会用同一个权限表示两种差别极大的触及范围。

**把批量传输放到终端的 26、27 号帧上。** 否决。注册成本更低，
代价是整条授权链：帧平面只认证一次 `terminal.open`，所以 SFTP 会继承那个授权，
而能力检查、审批、审计账本三样都得在帧处理器里重新实现一遍。
`remote_execution.rs` 对一条 RPC 已经把四样都做了。
吞吐改用并发在途分块与宿主协商的分块大小来解决。

**把 SFTP 绑到一条已经打开的终端会话上。** 出于上面同样的理由否决：
一个会因为无关标签被关闭而中断的传输，比第二次认证是更糟的失败。
