## 状态

已接受。于2026年7月15日实施。选择加入（`taskReview.enabled`），默认关闭。

## 背景

Agent Team已经能产出作品，但没有什么能阻止糟糕的作品继续发展。存在的三种机制都以相同方式失误：

| 机制 | 它的作用 | 为什么它不会被阻挡 |
| ------------------------------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `prFeedback.reviewer`（PR反馈环） | 真正的审稿人角色，并有`approved`/`changes_requested`的评价。 | 在DAG安定下来后，观察并推动。还需要有GitHub信用证明+已发表的出版PR;桌面外的默认拒绝。 |
| `governancePolicy.approval.requireResultReview` | 将完成的任务送至董事会的`review`栏。 | 一个**人类**门禁，而波次跑者的依赖进程忽略了它——依赖者无论如何都会消耗输出。 |
| `pattern.*` 超代码节点 | 对抗性验证/评审小组/完整性批评者。 | 限制了超代码激活，并且作为*发现*的验证，而不是对队友差异的审查。 |

因此，一个团队如果第一个任务产生了微妙错误的代码，就会乐意把代码交给三个下游任务，操作员最终会发现。

推动这一问题的目标是：一个负责规划和审查的**Opus lead**，以及编写代码的**Codex Worker**。这其中的前半部分没有实现。

## 决策

添加一个内部工作流节点类型，`action.team.task.review`，由团队合成器在每个任务的调度节点与该任务的依赖节点之间输出。

```
  taskA ──▶ review:taskA ──▶ taskB ──▶ review:taskB
```

**门禁由调度器强制执行，而非惯例。** 合成器将`taskA`的每个依赖边重新定位到`review:taskA`，因此未批准任务的依赖项根本无法运行。下游无需记住检查标志——DAG使错误的事物变得不可能，而不仅仅是被检测到。

### 为什么要用新的节点类型，而不是重复使用PR审核员

`pr-feedback/reviewer.ts`共享词汇（`approved` / `changes_requested`），我们有意镜像它，但不能重复使用：

- 它告诉模型用自己的工具去变换一个GitHub PR，而审核主管根本没有工具;
- 它假设PR已公开且可解决的GitHub 凭证;
- 它运行于后期，这正是我们正在修复的属性。

两者现已共存：PR评论聚焦于GitHub已存在的一个分支;任务审查关注的是工作是否能在运行中继续进行。

### 主审：它从不进行编辑

线索已经被排除在调度之外（`workers = allMembers.filter(m => m.role === "teammate")`）——正是这种排除让它成为可信的评审者，这也是为什么审核是线索的工作，而不是同行的职责。因此，审核调用会传递**无工具**，其系统提示也明确说明了这一点。一个“自己解决了”的线索，就是拿到Worker worktree之外未经审核的作品。

### 证据：差异，而非主张

一位只展示Worker文笔的评论者是在审阅一个*主张*。一个说“新增验证和测试”但什么都没改的代理，读起来和做过工作的完全一样。所以`review-evidence.ts`确定性地组装任务实际改变了什么——没有模型，没有工具，没有网络：

1. **任务是worktree分支**（优先）。提交未提交的Worker——Worker不强制提交，`dispatchTeammate`虽然通常已经提交了，所以通常不执行——然后进行差异`baseRef...agent/<runId>/<teammate>/<taskId>`。以基准差价（而非上一次提交）意味着修订轮仍能看到**累计**工作，而不仅仅是自上次反馈以来的差异。
2. **未提交的更改**——当有变更时指该worktree（例如提交本身失败），或在隔离关闭时显示在共享工作指令中。只要有worktree，就绝不会有共享目录：作品在worktree中，这就说明目录不对。
3. **没有任何内容**——那么交付文本是唯一的证据，提示词也说明了这一点，告诉负责人将一个没有支持的代码变更主张作为请求修改的理由。

每一个梯级在失败时都会落差，或者发现没有变化时，所以如果 git 在分支上出现小插曲，如果树有差别，仍然会得到领先。

UTF-8数量限制在**64 KiB**，直接丢弃整个文件而不是拆分：一个截断的补丁读起来就像是完整的补丁，所以提示词里会提到遗漏部分。Git失败会降级为`kind: "text"`——永远不会被认可。

### 修订循环

`changes_requested`会把**同一个Worker**重新派到**同一个worktree*，并附上主管的反馈，然后再进行复审。两半都是承重的：

- **同样Worker**——该池获得了一个精确Worker的权利（`ClaimOptions.requireTeammateId`），可以返回 `null`，而不是轮流转入替代者。把“请修正这个”交给没写差别的人毫无意义，所以作者不可用是失败，而不是替代的信号。
- **同理worktree**——分配者已经通过分配键（`workspaceKey ?? taskId`）重用了worktree，因此传递任务ID后，修订版本会落在正在审核的分支上。

预算：`taskReview.maxRevisions`，默认的**2**，在合成时冻结在节点参数中，因此中途配置编辑无法更改DAG已经被塑造的预算。`0`有意义：只复习一次，绝不修改。

### 所有未解决的问题都会导致任务和运行失败

预算耗尽、原始Worker不可用、reviewer/provider失败、无法解析的决策，或无法接线的审查lead/reviewer——这些都会标记任务`failed`并不可重试。节点是故意的`retryable: false`：重试时会把Worker重跑到同一个墙里，更糟的是，最终会让不靠谱的审核者橡皮图章。**一个放弃并认可的门禁不是门禁。**

### 董事会地位归谁所有

当 review 开启时，**review 节点拥有终端状态**——`dispatchTeammate` 不会写出状态。完成的派遣还未已接受，正在等待审核，任务会`in_progress`直到主管决定。让调度员先写`completed`会让董事会声称工作在审核期间完成，拒绝时`completed → failed`转。`in_progress`也是运行时拥有的专栏（`task-move-guard.ts`），所以没人可以在审核中转卡片。结果消息仍然会在发送时发布——只有接受决策会移动。

`requireResultReview`是正交的，并且会合成：自动审批在卡片被设置时将卡片路由到`review`（最终由人类决定），未设置时路由到`completed`。

## 后果

- **成本。** 每项任务多做一个潜在客户LLM轮，每修订一次加一Worker轮。这就是为什么默认是选择加入和关闭的。
- **线索现在进入关键路径。** 在复核时，无法解决提供商线索将失败所有任务。这与决议规划使用的提供商相同——通过`lead-execution.ts`有意共享，因此潜在客户不能只规划一个提供商，而审查另一个。
- **延迟。** 审查会在他们的发件后进行序列化;独立任务仍需并行复习。
- **不是安全边界。** 评审者是模特。它提高了质量的底线;这并不意味着不信任的Worker安全。工作空间隔离和沙盒仍然是遏制的故事。

## 考虑的替代方案

- **在调度执行者内部进行审查。** 已拒绝：阻塞属性将存在于下游节点必须遵守的标志中，而非图中。
- **整个运行只有一个审查节点。** 已拒绝：它不能阻断任何东西——运行时，所有依赖节点都已经消耗了坏输出。
- **为评审者重复使用`dispatchStructured`。** 已拒绝：它声称有队友来自池中，且评审必须是领头，但该组别不在池中。
