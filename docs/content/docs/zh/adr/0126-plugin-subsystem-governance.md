# ADR 0126 — 插件体系治理

**Status:** Accepted
**Rollout:** 未开始 —— 下面的决策是已接受的契约；它们授权的修复尚无一项落地。
**Date:** 2026-08-15

## 背景

插件子系统体量很大，结构上也是健康的。51 个 `create*API` 工厂全部被
`createFullPluginContext` 组装进运行时上下文。57 个 canonical extension point
全部有活的 JSX 挂载点，由 `pnpm audit:slots` 钉住。49 个首方插件里 41 个已注册，
未注册的 8 个每一个都有交代——5 个在 `INTENTIONALLY_UNBUNDLED` 白名单里附书面
理由，3 个走 Tauri host 而不进浏览器 bundle。权限目录、Rust capability 集合和
SDK helper 都各有 parity 门禁。

缺陷不在 API 层，也不在 slot 层。它们聚在四个地方，而且共用同一个根因。

**这个子系统宣称的比它强制的多。** `native:filesystem` 和 `native:process` 在
`permission-guard.ts` 里只以一个分组标签和一句描述文本的形式存在，没有任何代码
读它们——而 `cognia-sandboxed-tools` 正在用 manifest 向用户索要这两项同意。
`configSchema.secret` 在 `validation.ts` 里被校验，其类型文档承诺该值存进操作
系统 keyring、通过 `ctx.configuration.getSecret()` 读回；这个方法根本不存在，
表单渲染的是一个普通输入框，值落进明文配置存储。23 个生命周期 hook 带着
dispatcher 发货，零发射点。`manifest.dexie.migrations` 有类型、有校验、有 SDK
导出，而 `runPendingMigrations` 有完整测试套件、没有任何生产调用者。

**有些门禁不可能失败。** `contract-path-audit.ts` 的存在就是为了堵住「契约引用
了一个不存在的文件」这个洞，但它只走 `PLUGIN_CAPABILITY_CONTRACTS`——
`RUNTIME_POINT_BINDINGS` 里有五条路径不在磁盘上，其中一条把一个目录当成文件来
引用。比幽灵路径更糟的是：`workflow.task` 和 `modal.mount` 是真正实现了的，却
待在 `KNOWN_DORMANT_RUNTIME_POINTS` 里，于是可达性门禁永久跳过它们，那里真出
回归也抓不到。而 `RUNTIME_RISK_AUDITS`——专为追踪这一类风险而建的台账——是一个
空数组。

**已注册不等于可触达。** 插件贡献的 skills、MCP server 预设和 density preset
落进了能正常工作的注册表，却没有任何面向用户的界面去读它；应用里每一个 skill
picker 查的都是 Dexie。9 个 browser-blocked 和 11 个 mobile-blocked 内建插件被
当作普通的、可启用的行列出，唯一的反馈是点击之后一个笼统的错误 toast——manager
自己的注释写着被阻止的插件会「visible in `/plugins` (flagged incompatible)」，
而那个标记从来没有被做出来。

**有一项能力和它自己断开了。** VS Code 复用层有大约 880 行 webview、terminal
和文档管道代码，实现完整、带测试、UI 侧还在生产里挂着——与此同时 68 个 RPC
方法待在一个显式不可用列表里，处理器直接抛错。这一层没有 ADR；授权它的计划
文件已经不在磁盘上；而子系统文档把它描述成能用的，连「Doc pool | 50 models」
这样的实时统计都写了。

共同的根因是：**「插件是给谁用的」这个问题从来没有落成过记录。** 没有这个答案，
一个没有任何首方插件调用的 API 就是含混的——是死重量，还是给一位尚未到场的
作者的承诺？于是每一次这样的判断都被推迟，而不是被做出。

## 决策

### 第三方插件作者是真实受众

支持这一点的证据已经在仓库里了，而且不是无意写下的：
`packages/plugin-sdk/contract/compat/` 下有签名的向后兼容 fixture、有
`api-surface-baseline.json`、有四个带结构化排除码的哈希锚定 VS Code 1.128
parity 文件。没有人会为一个纯内部的模块边界做这些。

最强的反面证据——`@cognia/plugin-sdk` 引用了约 390 个 `@/` 应用内路径、无法独立
构建，因此不在 `pnpm build:packages` 门禁里——是**技术债，不是意图声明**。它正是
横在外部作者和一个可安装 SDK 之间的那个具体障碍，现在按债务来跟踪。

直接后果，也是这条决策排第一的原因：**零首方消费的 API 不自动等于死代码。**
它可能是给一位还没到场的人的承诺。下面的休眠判定规则存在的意义，就是把这个区分
做出来。

### 插件代码是半信任的，边界是 import 图

有三种姿态可选。完全信任——外部代码拥有宿主自身的权限，只靠审核把关——是今天
在跑的状态，它撑不过与第三方受众的接触。完全隔离（Worker、iframe 或 WASM 沙箱）
会终结 frontend 插件贡献 React 组件的能力，而 UI slot、message renderer 和
context panel 恰是被用得最多的几类贡献；对整个插件群来说这个代价太高。

**半信任**是中间态：插件代码仍在渲染器上下文里，但它的能力面是封闭的。禁止深度
`@/lib/*` import 进宿主内部；插件通过 `ctx.*` 和 SDK 触达宿主，于是权限门禁是
有意义的——因为它是唯一的门。

这是今天就能执行的，而不是愿景：`lib/plugin/security/import-boundary.ts` 已经
实现了 `findHostPrivateImports` 和 `assertNoHostPrivateImports`。它只是从来没被
打开过。

### 边界先冻结，再按 import 路径逐条还债

首方插件违反这条边界的程度很重，光 `workflow-ai` 一个就有 27 处深度 import。
在打开门禁之前先迁完全部 41 个已注册插件，等于把本 ADR 里其它所有修复都堵在一次
大重构后面；而只对外部插件执行这条规则，则意味着首方插件群不是一份「外部作者能
写出什么」的可用样本——SDK 的真实可用性永远不会被任何一个有能力修它的人验证到。

所以把现存违规冻结进白名单，门禁只拦新增。白名单按 **import 路径**逐条登记，而
不是按插件：插件级豁免会让该插件可以无限新增违规，门禁就沦为装饰。逐条登记还让
这份清单同时成为 SDK 能力面的需求文档——每一行记录一个插件需要了哪个宿主模块、
以及什么样的 SDK 能力可以消除这个需要。债务一次删掉一行地还。

### 权限分三类，同意书说明每条属于哪类

有意思的数字不是 manifest 接受 110 个 canonical 权限而
`ctx.permissions.requestPermission` 只接受 44 个。有意思的是有少数几个权限**什么
都不 gate**，而用户仍被要求对它们表示同意。

给全部 110 个强加运行时检查是噪音——`lib/plugin/api/media-api.ts` 里解释得没错，
`media:image:read` 没有任何宿主资源需要保护。把 manifest 收窄到 44 个会破坏现有
manifest，而且忽略了有些权限是跨 Rust 边界强制的、不在 API 层。诚实的修法是分类：

- **`api-gated`** —— 在 API 调用处经 `hasApiOrGuardPermission` 检查。
- **`bridge-enforced`** —— 在 contribution 注册时由 bridge 检查。
- **`declarative-only`** —— 元数据。安装时告知，运行时永不拦截。

类别编码进类型，于是一个 parity 测试就能断言每个权限恰好属于一类、且每个
`api-gated` 权限都有真实调用点。

安装同意书随之**分区**而不是隐藏。删掉 `declarative-only` 条目会丢失真实信息——
用户仍然想知道一个插件打算碰图像。把它们和被强制的权限不加区分地并列，恰恰就是
本 ADR 要关掉的那个假承诺。两个带标签的分组同时保住这两个性质。

### 插件 hook 默认是观察者，拦截需单独授权

那 23 个休眠 hook 即将在 session 创建、消息增删改、定时任务触发和 workflow 节点
注册处获得发射点。如果这些 dispatch 是同步且可拦截的，一个慢的或抛异常的插件就
能阻塞 session 创建。

因此 hook 是 fire-and-forget：异步、不阻塞、且做隔离，抛异常的处理器不能破坏宿主
路径。拦截能力没有被移除——它继续走现有的 `CHAT_INTERCEPT_HOOKS` 机制，那条路径
已经由 `hooks:chat-intercept` 权限把关，于是「改变宿主行为」这件事仍然是用户同意
过的，而不是每个 hook 隐式自带的。

### 休眠能力按证据判定，默认接通

| 判定 | 条件 | 动作 |
|---|---|---|
| 保留 | 被 ≥1 个已注册首方插件消费 | 不动 |
| 保留（对外承诺） | 零首方消费，但出现在 `api-surface-baseline.json`、某个 SDK `define*` 工厂或契约 catalog 中 | 保留，**并且**补一个 fixture 插件调用证明它能用 |
| 降级宣称 | 已实现，但生产者被显式禁用 | 改掉声明的 `status`，返回明确的 unsupported 错误，停止宣称 `implemented` |
| 有意休眠 | 零消费，但有 ADR 背书或属于作者模板 / E2E fixture | 三轴标注：类型上标为休眠、UI 上标 inert、测试钉住 |
| 删除 | 零消费、不在任何契约里、无 ADR 背书、且已被另一实现取代 | 移除 |

默认动作是把能力接通，不是移除。删除只留给真正的重复实现——被
`core/wasm-loader.ts` 取代的 `core/wasm-runtime.ts` 就是符合这一档的形态。

第二行上的 fixture 要求是承重的部分。一个对外承诺了却从未被执行过的 API，比一个
死 API **更**危险：它的第一次执行发生在外部作者手里，那里的失败是支持成本，而不
是一条测试失败。现有的 `ui-surface-reference` 插件是 E2E-only fixture 的现成先例；
API 契约符合性拿一个兄弟插件，而不是并进它。

### 不可能失败的门禁不是门禁

三个缺陷共用同一种形态，修法也一样。`contract-path-audit` 必须走
`RUNTIME_POINT_BINDINGS` 和 docs 常量，而不只是 capability 契约。
`KNOWN_DORMANT_RUNTIME_POINTS` 里不能装着已实现的 point——一份把工作代码吞进去
的豁免清单，会把回归探测器变成盲区。

而 `RUNTIME_RISK_AUDITS` 的条目要带 `owner` 和 `dueDate`，门禁在条目过期未处理时
失败。这份台账当前的状态——机制正确、已建成、从未填过——正是本 ADR 要处理的那种
失败模式；没有到期日，它会重新变回空表，而且没人会注意到。

### VS Code 复用层要有自己声明的兼容水位

两个子系统很容易混淆，而它们不是一回事。`code-1.128-*.json` 这组契约文件治理的
是**Cognia 插件投射进 VS Code**——即 managed IDE 平台——它们是哈希锚定的、有生成器
校验、进了 CI 门禁。复用层跑的是真实 VSIX 扩展**进入 Cognia**，方向相反，且与它们
零共享代码。

那一层的全部兼容性声明就是 `EXPLICITLY_UNAVAILABLE_VSCODE_RPC_METHODS`：一个
手工维护的数组，没有上游出处、没有摘要、没有生成器。对着它接线只是把一份未经审计
的清单变短，而且无法回答外部作者第一个会问的问题——到底哪些扩展能跑。

因此从同一份锚定的 `vscode.d.ts` 生成一份兄弟契约，把每个 dispatcher 方法分类为
supported 或 excluded 并给出理由码，用同样的方式加门禁。这是接线的前置条件，不是
后续补充。

### 能力归属写下来，但不加门禁

五套扩展机制并存，能力互相重叠。这个边界作为指导被记录下来，好让「这个该做成插件
还是 skill」有一个成文的答案；但它**刻意不**由测试强制：这些边界会移动，现在钉死
只会挡住合理的调整，换不来任何安全收益。

| 机制 | 承载 | 理由 |
|---|---|---|
| 插件 | 任何需要宿主 API、UI 贡献、生命周期或权限的能力 | 它是唯一同时拥有 `ctx.*`、React 贡献和同意模型的机制 |
| Skill | 提示词层面的流程与领域知识，不执行代码 | 它塑造模型行为；给它宿主访问权等于重复一遍插件权限模型 |
| Hook | 生命周期切点上的自动化 | 它不新增能力面——它观察或拦截一个已存在的能力 |
| MCP server | 由独立进程提供、且能在本应用之外复用的工具 | 进程边界就是重点；进程内工具属于插件 |
| Slash command | —— | 不是同级。它是前四者的调用面 |

最后一行是一个发现，不是定义。Slash command 曾被当作「能力可以放的第五个地方」来
权衡；它其实是触达能力的一种方式。

## 后果

- 打开 import 边界会产出一份很长的白名单——上百条是大概率。那份清单看着不舒服，
  而这正是它的作用：它是对「SDK 距离够用还差多远」的第一次诚实度量。进展以「删掉
  了几行」的形式可读。
- 把一个权限归类为 `declarative-only`，是公开承认它什么都不保护。这就是预期效果。
  如果某个权限值得被强制，分类这道工序就是决定这件事的地方，而不是又一次推迟。
- 只做观察者的 hook 意味着插件无法否决 session 删除、也无法阻止一个定时任务。若
  真出现需要拦截的场景，走那条带权限的拦截路径——答案不是把所有 hook 改成阻塞式。
- 休眠规则偏向接通，意味着子系统的维护面是变大而不是变小，而且每接通一项能力都
  会带上仓库 ≥90% 改动文件覆盖率的要求。这是有意接受的：一项项目留着却不接通的
  能力，维护成本一样，产出为零。
- 声明 VS Code 兼容水位会把相当数量的方法归类为 excluded。把「不支持什么」点名说
  出来，比一个没有任何扩展能依赖的、隐含的完整兼容声明更有价值。
- 本 ADR 不会让 `@cognia/plugin-sdk` 变得可独立构建。它被度量并分层为纯类型依赖和
  真实值依赖，其中纯类型的那一半被抽离。在剩余量归零之前，第三方作者身份仍是一个
  声明的目标而非可用的现实——而这个差距现在是被记录的，不再是隐含的。
