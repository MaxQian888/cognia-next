# ADR 0168 - 一次编辑是同一条消息的新版本

**状态：** 已接受
**日期：** 2026-09-05
**相关：** [ADR-0027](./0027-mobile-sync-orchestrator)、[ADR-0063](./0063-optical-compaction)、[ADR-0139](./0139-artifacts)、[ADR-0155](./0155-plugins-reach-the-host-through-one-door)、[ADR-0163](./0163-provider-operation-contract)

## 背景

会话里的图片走到头就没路了。`ImageLightbox` 能缩放、能旋转视图、能在一轮里翻页、
能下载，词汇量就这些。想再做点别的，只能把文件下载下来、打开另一个应用、把结果
当成新消息贴回去，而那条把两者连起来的线索就此丢失。

与此同时，这个应用里其实已经装着大半个图像编辑器，只是放错了地方而且没做完。
`lib/plugin/api/media-api.ts` 里有加载、缩放、变换和调整用的 canvas 辅助函数，还有
一段手写的、发往服务商 `/images/edits` 的 multipart 请求，自带一套 base URL 归一化、
自带超时、自带 xAI 特例。它的 `ImageAdjustmentOptions` 声明了十一项调整，实现了四项。
曝光、伽马、自然饱和度、色温、色调、模糊和锐化会被插件传进来、被丢掉，然后原样返回
输入，且不报任何错。它的对比度曲线把一个 0..2 的量喂进一个期望 -255..255 的公式，
所以超过大约正负 40 之后系数变成负数，图像先反相再被裁到纯黑纯白。

两个界面想要同一种能力、其中一个还在谎报自己做了什么，这就是缺一个共享组件的形状。

## 决策

### 一套图像引擎，除了两端都是纯函数

`lib/images/` 为整个应用承载解码、裁剪、缩放、旋转、翻转、调整、蒙版和编码。
除 `codec.ts` 外全是对结构化 RGBA 缓冲区的算术，全程没有 canvas，这带来两个值得写下来
的后果。这些数学可以跑在快速的 `node` Jest 项目里而不是 jsdom。以及结果是确定的：
canvas 的 `drawImage` 重采样取决于宿主图形栈当天的决定，否则两个壳会对同一次编辑的
字节产生分歧，而这个存储是按内容哈希寻址的。

插件 Media API 改为委托到这里。十一项调整现在全部真正执行，对比度换成线性映射。

### 蒙版方向只在一处翻转

在应用内部，蒙版是灰度图，白色表示「在这里编辑」。工作台就是这么画的，覆盖层也是这么
渲染的，因为在即将被改动的区域上覆盖一层亮色，正是用户预期看到的样子。

到了服务商边界，约定正好相反：OpenAI 的 `images/edits` 端点把完全透明的像素读作待编辑
区域，而 AI SDK 会把蒙版原样透传。`maskToProviderBuffer` 是唯一被允许执行这次反转的函数。

之所以把它单独写出来，是因为搞反了不会有任何动静。服务商会去编辑选区的补集，并返回一张
看起来很合理的图，于是这个 bug 以「AI 改错了照片的地方」的形式抵达用户，而任何日志里都
找不到解释。

### 编辑走统一的 Provider Operation 平面

通往模型只有一条路：Operation 平面上的 `images.edit`（ADR-0163）。为聊天再复制一份插件
API 那套手写请求，意味着每个服务商怪癖要在两处修，PII 闸门要在两处漏掉。路由、代理、
凭据亲和、闸门和失败分类在那边都已经定好了。

编辑端点不接受蒙版的服务商，仍然可以做整图 Prompt 编辑。区域编辑被禁用并说明原因，而不是
把面板藏起来，因为藏起来等于把该服务商确实具备的能力也一起藏了。

### 保存是追加，永不替换

原始 part 从不被改写。结果作为另一个带 `cogniaImageEdit` 记录的 `file` part 追加到同一条
消息上，版本轨让原图始终只有一次点击的距离。

这个字段是附加的、可忽略的。早于它的客户端只会看到一个普通图片 part 并按普通图片渲染，
这正是正确的降级：消息末尾多一张缩略图，而不是一张坏图。这也是这个特性不需要 Dexie
migration 的原因。

**lineage id 就是原始 part 的 url**，不是新铸的标识符。铸一个新的就必须在首次编辑时写回
原图，而那恰恰是本设计要避免的破坏性写入，并且会让这个特性之前保存的每一张图都落在所有
lineage 之外。用 url 作键让版本 0 成为隐含的，无需回填，并且因为聊天媒体是内容寻址的，
这个键跨设备稳定。

**追加会在事务内重新读取消息。** 编辑会话很长：打开工作台、拖一个裁剪框、等一次模型往返。
在这个窗口里，同一条消息可能被流式回合、同步腿或另一台设备改写。把调用方手里的快照写回去
会把这些改动悄悄抹掉。

**`versionId` 是幂等键**，由调用方铸造并在重试之间复用。双击的保存、传输层的重试、失败后
重连的客户端，三者都必须产生一个版本而不是三个。

### 两种分辨率，各有各的理由

规范化的聊天图片是 1568px，一次色调调整就要碰约 250 万个像素，跟不上手指拖动滑杆。预览从
一份缩小的副本渲染，几何步骤按同一系数缩放；保存则用同一份历史在全分辨率上重新渲染。

每个几何步骤必须按同一系数缩放，否则管线就不再可组合，因为一个裁剪的坐标是相对它前一步
产出的结果而言的。

### 本地步骤与 AI 步骤共享时间线，但不共享上限

一次裁剪是几十字节的描述，可以重放。一次 AI 结果是几 MB 的解码帧，无法从任何东西重算。
所以历史保留 50 个本地步骤和 5 个 AI 检查点，渲染时回溯到最近的检查点，只重放它之后的
步骤。重放它之前的步骤会把那些步骤应用两次，因为模型的输出里已经包含了它们。

掉出撤销窗口的步骤仍然在像素里，所以它移入一个「已烘焙」列表：继续被重放，但不再可撤销，
而且放弃编辑的确认仍然会把它算进去。掉出窗口的检查点则成为新的原点，这正是被淘汰的位图
可以安全释放、而不是被编辑器一直持有到关闭的原因。

### 编码取决于内容，而不是请求

本地编辑过的照片以 WebP 0.92 保存。带透明度的结果无论偏好如何都存为 PNG，这样去背景不会
被压到黑底上。未经本地改动的模型输出保留服务商自己的字节，因为重新编码相同的像素只会
损失质量。

记录的 media type 永远描述实际产出的字节，而不是请求的格式。没有 WebP 编码器的运行时会用
PNG 回应一个 WebP 请求，相信请求就会在内容寻址存储里给这些字节打上永久错误的标签。

### 记录什么，不记录什么

版本记录编辑的**种类**（`crop`、`adjust`、`ai.region` 等）、发生时间，以及模型编辑时的
服务商与模型。它不记录 Prompt。那是已经送给模型的用户输入，在会话记录里留一份副本会把它
带进每一次备份和每一条同步腿，而没有任何产品收益。

只归属**最后**一个模型步骤。更早的那个也参与了这张图，但这条记录写的是谁产出了这个结果，
而声称两个模型共同做了一张图，比只写完成它的那个更糟。

## 后果

聊天图片不再是死路，插件 Media API 也不再声明自己会丢弃的能力。两个界面对相同设置产出
相同的像素，因为只有一套引擎。

没有任何迁移。这个特性之前保存的每一张图片，按构造就是它自己 lineage 的版本 0，没有一条
历史消息被触碰。

版本链存在消息上，所以它能扛过刷新、随会话一起走备份与导出、通过既有同步路径抵达其他
设备，且不需要新表。

编辑需要本地像素访问，而驱动远程宿主的伴侣客户端对宿主的媒体没有这种访问。要让它工作，
结果必须经宿主暂存并提交，而不是直接写入，这属于后续切片，这里刻意不做承诺：在这类客户端
上工作台可以打开、查看、做本地编辑并下载，并明确告知保存需要宿主。
