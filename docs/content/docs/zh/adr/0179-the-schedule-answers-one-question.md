# ADR 0179 — 调度页面只回答一个问题

**状态：** 已接受**日期：** 2026-09-13 **相关：** [ADR-0079](./0079-scheduler-extension-contract)、[ADR-0128](./0128-scheduler-host-neutral)、[ADR-0167](./0167-the-schedule-belongs-to-the-account)、[ADR-0174](./0174-the-bot-control-plane)

## 背景

2026-09-13 的两次审计逐一核对了 `/scheduler` 和 `/me/scheduler` 的面板及数据。共同问题是：页面重复展示容易计算的信息，却遗漏用户需要采取行动的信息。

**重复。** 各类型计数同时出现在侧栏分组、筛选菜单、页脚和概览栏。“即将执行”和“最近执行”重复出现在概览、右栏、日历和时间线中。右栏仅在打开详情时存在，展示的两块内容与刚被滚出视野的概览相同。应用任务、其他五种任务及系统任务抽屉使用三套详情布局、标题和最近执行列表，各自硬编码绿、黄、红色。

**遗漏。** `ScheduledTask` 已有 `lastError`、`consecutiveFailures`、自动暂停结果及提升记录；`useSystemScheduler` 已有待确认的操作系统操作；主机目标知道本地调度是否暂停；写入权限策略已有每个来源的配额；统一 hook 知道哪些来源加载失败。这些信息都未显示。用户可以用四种方式统计任务，却无法查看昨晚失败的任务。

**无法定位。** `app/scheduler/` 和 `app/me/scheduler/` 没有读取查询参数，但已有四个入口发送参数：两个来源使用 `?taskId=`，命令搜索使用 `?task=`，操作系统来源使用 `?systemTaskId=`。任务中心、工作区环境列表和输入框调度建议则只打开裸路由，丢失选择意图。输入框交接的草稿只有桌面页面消费；手机先重定向，导致草稿未读便过期。

**两套调度页。** 手机只复用数据层。详情没有传入 `executions`，因此每个应用任务都显示零统计、空图表和“尚无执行记录”。统计条只计算应用任务，但列表是统一任务列表；计数忽略工作区范围，删除没有确认。桌面页面还保留完整的手机覆盖层，但窄屏在更早的位置被重定向，永远无法进入它。

## 决策

### 1. 六种任务共用一种详情组合

`ItemDetail` 统一呈现所有 `UnifiedScheduledItem`：滚动容器外的标题区、警报，以及容器查询网格中的 `ConsoleSection` 卡片，沿用 `/bots` 和 `/devices` 的组合方式。任务类型提供 `FactList` 和额外章节，不另建布局。删除系统任务检查抽屉；操作系统不提供执行历史时明确说明，而非显示空列表。

来源声明不支持的能力显示禁用控件及原因。直接隐藏会混淆“不存在”“修复一步即可使用”和“已损坏”三种情况；审计在缺失按钮背后发现了三者。

### 2. URL 表示选择，store 保存筛选

两条路由都只通过 `?item=<unifiedId>` 选择任务，通过 `?run=<unifiedId>` 打开执行抽屉。`lib/scheduler/page-query.ts` 将三种旧参数转换一次并替换地址栏，因此旧入口无需协同更新。动态 `[id]` 路由会破坏 Tauri 静态导出，所以和 `/bots` 的 `?bot=` 一样使用查询参数。

搜索、状态、类型及仅循环筛选进入持久化 scheduler store。两页各存一份筛选状态，是手机与桌面计数不一致的根源。

### 3. 概览说明哪些事情需要处理

首块 `AttentionBlock` 使用纯函数 `deriveAttention`，输入统一任务、应用任务、正在运行的执行及进程、待确认操作、主机目标、来源错误和相对于 `maxTasksPerSource` 的来源计数。按严重程度排序：失败任务和失败来源优先；其次为待确认、主机暂停、不支持的类型及超过 80% 的配额；最后是运行中的工作，存活进程提供停止操作。

下方用一份议程代替日历、时间线和即将执行列表，三者本来就是同一批事件的不同分组。类型汇总只出现一次。用详情共用的 CSS 结果条代替硬编码十六进制颜色的 recharts 柱状图。

### 4. 列表不分组，移除右栏

行不再按类型分组，依次按需要关注、正在运行、最近下次执行时间、名称排序。删除每行悬浮菜单；操作放在详情、键盘及批量工具栏中，工具栏真正挂载到所属列表面板内。右栏不再渲染，外壳保留槽位。

### 5. 主机与权限放在标题区

主机条和权限控件移入标题主机摘要后的 Popover。标题 `summary` 表示正在管理的主机，`status` 表示暂停或仅打开期间运行。删除仅在每次渲染读取一次 `getSchedulerDataSource().host`、无法响应主机切换的侧栏徽标。

### 6. 手机使用同一页面的窄屏布局

`/me/scheduler` 复用统一统计的 `StatStrip`、相同的分面计数、`ItemDetail`、执行抽屉和删除确认，并消费输入框草稿。手机仍只创建应用任务；批量操作、模板、导入导出和非应用任务创建保留在桌面，因为手机外壳没有这些操作所需的界面。

### 7. 用独立提交删除死代码

通过一次 chore 提交删除桌面页不可达的手机覆盖层、无人调用的 store 操作及 hook 返回值、两条被替代的插件取消入口，以及新面板取代的组件。仅删除此次修改确认没有消费者的 `scheduler.*` 翻译键，并从拆分源文件重新生成聚合文件。

## 影响

每个问题在页面上只有一个答案。失败任务出现在概览首位、列表首行和详情首条警报中，由一个经过测试的函数统一计算。

所有意图为“打开此任务”的入口都能正确定位；执行记录可以通过链接打开。手机和桌面使用相同 store 与组件，因此计数、筛选和详情不会各自解释数据。

本次刻意不重做表单，仅修复审计发现的三点：已有九种文案却仍显示普通输入框的事件类型预设选择器；搜索后缩窄的依赖选择器；除唯一拥有报告器的 `plugin` 类型外，进度通知开关明确标为无效（工作规则 7）。

未实现：平台不提供的操作系统任务 `listRuns`；跨主机任务交接（继续遵循 ADR-0128 决策 6）；手机上的非应用任务创建。

## 修订（2026-10-03）

第二次审计对照同一份数据检查各面板，补上了第一次遗漏的部分。

**详情没有说明任务做什么。** 它展示触发时间和运行结果，却从不展示提示词、命令、工作流或处理器。现在每个应用表任务都有“执行内容”区块，由 `summarizeTaskPayload`（`lib/scheduler/payload-summary.ts`）生成，按名称解析所引用的角色、工作流、计划、团队、代理和会话，引用已不存在时会明确说明，原始 JSON 收在折叠开关后。结果区块以 `summarizeItemRuns`（`lib/scheduler/item-run-stats.ts`）开头：有累计计数时取自任务行，耗时和最近结果取自运行记录。

**标签只能写不能改。** 之前没有任何入口可以设置或清除标签，搜索也忽略标签。现在表单可以编辑标签（`task-tags-input.tsx`）并始终提交完整列表；搜索会匹配标签，`#标签` 只匹配标签。

**修订 §4（桌面）。** 列表面板最小宽度改为 280px 而非百分比（此前在笔记本上被压到约 170px）；主机弹出层移到刷新按钮旁，不再单独占一行页头；键盘高亮会滚动到可见区域；日程默认只列三天，其余点击“显示更多”。

**修订 §6（手机）。** “需要你处理”保留在两个标签页之上：任务（搜索、与桌面相同的筛选栏、去掉了无法勾选任何东西的复选框）和动态（统计条、结果、日程、最近运行）。页头增加刷新按钮。详情新增复制、补跑和依赖图（均为对话框）；提升到操作系统调度仍只在桌面提供。批量操作、模板、导入导出和非应用任务创建仍留在桌面。
