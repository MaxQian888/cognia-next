# ADR 0241 — 共享 Run 实时流向成员

**状态：** 提议中
**日期：** 2026-10-26
**相关：** [ADR-0149](./0149-a-person-is-not-a-device)（协作平面及其共享 AI 会话更新）、[ADR-0177](./0177-a-room-is-one-conversation-shape)（共享会话即 `shared` 房间类型）、[ADR-0206](./0206-a-workspace-streams-its-changes-instead-of-being-polled)（本通道同样使用的进程内广播）、[ADR-0103](./0103-cross-host-session-handoff)（为什么共享会话不能靠复制迁移）
**计划：** `docs/plans/2026-10-26-shared-run-live-projection.md`

## 背景

claude-share 的核心是多人共同观看一个 Claude Code 会话。我们对比了它，想看看 Cognia 有哪些值得借鉴。它的大部分机制在这里已经有了更完整的实现：服务端权威的成员与角色、有序事件日志、持有租约的单一执行端、FIFO 队列、审批、审计和按成员的文件授权。

应用里的多方形态包括 team 房间、组织 Host 上的成员对话、IM 群、分享链接和画布。其中只有共享会话是不同真人账号观看同一个 Agent。2026-10-26 的源码核查发现，这条路径又慢、又丢信息，还有一部分不安全。

1. **执行端每秒重发整条回复，而且每份都落库。** `shared-run-coordinator.ts` 每 1 秒重读一遍进行中的 assistant 消息。任何有变化的消息都会作为 `message.corrected` 事件发出，事件里带着完整的 `parts` 数组，每一份都是一行 Postgres 记录。
2. **成员不读推流内容。** 会话 WebSocket 会转发每条持久化事件，但 `connectSharedSessionStream` 忽略载荷，转而从游标处走 HTTP 重新拉取。2026-08-29 的计划写的是 socket“承载低延迟增量”，代码从未这样实现过。
3. **工具卡片是空的。** `sharedAssistantParts` 发布的输入永远是 `input: {}`。它把输出变成 JSON 字符串，并丢弃推理、文件、图片、来源和数据 part。成员只能看到“Bash 运行过”，看不到命令；编辑也看不到 diff。
4. **这条路径上有三个缺陷。**
   - `stream_loop` 转发事件时，没有做 `list_events` 那样的已脱敏消息投影。于是消息被脱敏之后再发来的更正，会以原文落库并广播。
   - `sharedAssistantParts` 里的 PII 检查一旦抛错，1 秒定时器会把错误吞掉。这条消息以及它之后的所有 assistant 消息都再也发布不出去。
   - 发布链没有在途保护，服务端慢的时候，一轮轮发布会排起队。
5. **分享就意味着分享全部。** `convertLocalSessionToShared` 会导入全部本地消息和附件。服务端路由和 `createSharedSession` 其实已经接受 `importing: false`，`ensureLocalProjection` 也能把空的远端会话落到本地，但没有任何调用方这样用。

parts 级别的实时协议已经存在。`lib/chat/transcript/live-frames.ts` 的规则如下：

- 把同一条回复的连续 parts 数组编码成补丁和周期性关键帧；
- 以 `settled` 或 `reset` 帧结束一条回复；
- 设备漏收一帧后标记为 stale，直到下一帧关键帧。

多用户 Host 的成员回复路径（`transcript://live`）在用它，只有传输层是按人隔离的。

对比材料建议把 `CanonicalAgentEvent` 推给成员，这与代码不符。canonical 信封至少有四个生产者，各自维护序号，写入 `workflowRunEvents`，没有任何聊天界面基于它们渲染。所有聊天界面渲染的都是 message parts，由 `applySdkEvent` 或 `applyExternalAgentEventToParts` 构建。成员应该收到的是 parts。

## 决定

### 持久化日志仍是记录；在旁边新增实时通道

`message.created` 和 `message.corrected` 仍是共享回复唯一的记录。实时帧从不被当作历史读取；从未收到实时帧的成员，也能从日志收敛到最终结果。

回复流式生成期间，执行端改为**在回复 settled 时写入一次，在此之前最多每 10 秒写入一次**，不再每秒写入。本版本的成员在两次写入之间靠实时帧绘制回复；未协商实时通道的客户端则以 10 秒为步长看到回复。如果执行端连接的协作服务端没有在 `/health` 中声明 `shared-chat-live-v1` 特性，执行端保持 1 秒节奏，因此旧服务端永远不会比现在更慢。

### 实时帧复用成员回复编解码器

执行端把每条进行中回复的投影 parts 交给 `createTranscriptLiveEncoder`：间隔 250 ms，沿用编解码器的 2 秒关键帧和 200 KiB 帧预算。以下规则都不变：

- 帧结构；
- 补丁与关键帧规则；
- `settled` 和 `reset`；
- 关键帧前一直 stale 的规则。

编解码器从按人隔离的模块迁出到与传输无关的模块，由两条路径共同引用。

- `replyTo` 是排队请求的消息 id，`messageId` 必须是本 Run 创建的消息。
- `settled` 只在最后一次 `message.corrected` 被服务端接受之后发送，它的 `afterRevision` 就是该事件的服务端序号。成员沿用现有的 `settledReplyCaughtUp` 规则及其 10 秒上限，一直绘制已完成的回复，直到已应用游标追上这个序号。
- 超出预算的帧变成 `reset`，成员退回读持久化日志，与 Host 上一致。

### 上行是 run-token 请求，不落库

`POST …/sessions/{session}/runs/{run}/live` 每次接收一帧。服务端的鉴权与 run 事件完全相同：`x-cognia-run-token` 必须对应一个存活且未过期的租约，持有者仍需拥有该会话的 `StartRun`。服务端还会做以下检查：

- `messageId` 必须是本 Run 创建的消息；
- 帧结构必须符合编解码器的定义；
- 请求体不超过 256 KiB；
- 目标消息未被脱敏。

帧只广播，从不写入。这项检查就是持久化消息事件经过的 store 层准入，包括共享聊天和共享执行的灰度闸门（终态 run 事件保留较弱的闸门，以便已被停用的 Run 仍能收尾），并且从不缓存，因此紧急停用或切换为只读会立即让帧停止。

### 下行是同一 socket 上协商的子协议

客户端把 `cognia.chat.v2` 放在 `cognia.chat.v1` 之前提供。v2 socket 上的每条消息都是一个信封：持久化事件为 `{type: "event", event}`，实时帧为 `{type: "live", frame}`。v1 socket 完全不变，从不会收到实时帧，所以旧客户端不会每秒重新拉取十次。

实时帧走独立的按会话广播通道。接收端在这条通道上落后时，会跳过帧，而不是关闭 socket：下一帧关键帧就能修复。一个慢的观看者不应该因为丢了预览而失去持久化事件流。持久化事件通道保持落后即关闭的规则。

每条转发的持久化事件仍会重新检查可见性。实时帧依赖每个 socket 的资格检查，这个检查至少每秒刷新一次，收到 `member.updated` 策略帧时立即刷新。因此被撤权或移除的成员会在 1 秒内收不到实时帧。服务端还为每个会话维护一份墓碑记录：脱敏在广播之前写入，每个实时帧发出时都会检查它。因此脱敏前排队的帧永远不会把消息重新画出来。

### 一个投影、安全的输入、不再静默丢弃

`sharedAssistantParts` 仍是唯一的投影器，持久化更正和实时帧都用它的输出。

- **按源 part 缓存。** 投影结果以源 part 的对象标识为键缓存。聊天 store 没有替换的 part，投影对象保持不变。这样编码器的标识前缀比较依然成立，脱敏也只对变化的 part 执行。
- **工具细节分两档，按共享会话设置。** 默认是 `summary`：工具名、工作区相对路径、编辑和补丁的 diff 统计、抓取 URL 的主机名，不共享命令、模式、查询和编辑正文。所有者或维护者可以在看过风险提示后把会话切换为 `full`。能通过正则脱敏，不代表命令或编辑正文就可以分享，所以是否分享它们由会话明确选择。该设置存放在服务端会话上，每个执行端使用同一档位，修改从下一次发布起生效。
- **在 `full` 档下，工具输入经过按工具的白名单。** 内置工具及外部 Agent 的同类工具，只保留各自卡片会读取的字段：
  - shell 工具的命令；
  - 文件工具的工作区相对路径；
  - 编辑的新旧字符串；
  - `apply_patch` 的补丁；
  - 搜索的模式；
  - 抓取的 URL；
  - 网络搜索的查询；
  - 待办列表。

  每个字段都经过脱敏和长度限制，工作区外的绝对路径直接丢弃。MCP 和插件工具只保留名称和脱敏后的输出。
- **仍不共享的内容。** 推理、图片、文件、来源和数据 part 不共享，文件继续走 ADR-0222 的 FileSpace 授权。
- **PII 检查失败的 part 会被保留下来，而不是抛错。** 它被替换为 `data-shared-withheld` part，成员端渲染为带标签的占位。回复的其余部分照常发布，执行端记录一条诊断，所有者自己的会话保留原文。
- **未写完的密钥永远不会被放出。** 脱敏器只在秘密完整后才能匹配，而且有几种模式会跨越空格和换行。因此回复流式生成期间，放出的文本按整条消息计算：所有文本 part 按顺序拼接，从不逐个 part 计算。
  - 先对全文脱敏，只放出距离末尾 256 个字符之前的脱敏文本；截断点通过脱敏偏移量映射。
  - 有一个测试把这个窗口固定为不小于每一种有界秘密类型的最长模式。
  - 无界类型从起始符开始一直保留，直到脱敏器完成匹配为止。无界类型包括私钥、JWT 和 URL 凭据。settled 时如果仍未匹配，记录里也保持保留。
  - 同一规则同时约束实时帧和 settled 之前写入的持久化更正。
  - 工具输入要等参数完整后才共享。
- **档位变化不会被错过。** 每次发布都会标明投影时使用的工具细节版本，服务端拒绝过期的版本。错过策略通知的执行端，会在下一次发布时被纠正。

### 三个缺陷先修

- `stream_loop` 对转发的内容应用已脱敏消息投影。
- 追加 run 更正时，如果目标已被脱敏，直接拒绝。
- 发布在途时，下一次 tick 什么也不做，而不是再排一轮。
- PII 检查失败按上面的保留规则处理。

### 成员在自己的列表上叠加实时回复

成员的聊天列表仍由聊天 store 渲染，store 由 Dexie 投影提供数据。临时的实时回复按消息 id 合并进列表，沿用 `withLiveTurn` 的尾部规则。帧里的消息 id 是远端 id，成员用投影所用的同一个函数把它映射为本地投影 id。Run 是否活跃由 run 事件和租约决定，而不是由帧决定；活跃期间，成员的输入框显示 Run 正在进行。以下任一情况都会丢弃实时回复：

- 6 秒内没有收到任何帧；
- 消息被脱敏；
- socket 关闭；
- 会话被拆除。

因此执行端崩溃不会留下一条永远在流式显示的回复。一个 Run 同一时间只流式发送一条回复：执行端先排空上传，并让上一条 settled，再开始下一条；成员会拒收已结束回复的帧。终态 run 事件结束 Run 的进行中状态，但已 settled 的回复会一直保留显示，直到成员的日志追上它。执行端自己的设备本来就在本地流式显示，所以会忽略本 Run 的实时帧。

### 可以“从现在开始”分享

分享私有会话时会打开一个对话框，二选一，默认 **从现在开始分享**。

- **从现在开始分享**：通过 `createSharedSession(importing: false)` 创建一个空的 Active 共享会话，打开它的 `shared:` 投影，并在私有会话行上记录一个指向它的链接。私有会话及其历史不变，不上传，也不展示给任何人。
  - 所有者可以附加背景。草稿来自现有的先摘要再分支流程（`summarizeMaterial`，经过 PII 闸门）。所有者可以编辑，只有确认后才发布。背景作为所有者的第一条消息发布，因此每个执行端都能从日志重建出相同的上下文。
  - 共享分支里的 Agent 只知道日志里有的内容。这正是目的：共享会话的上下文不能取决于由哪位成员的设备来执行。
- **分享完整历史**：就是现在的转换流程，沿用现在的警告。
- Team 会话在两种模式下都继续拒绝，共享会话目前还不能承载 team。

## 非目标

- 真人在线状态、已读回执、表情回应，以及只供真人讨论的频道。这些仍在 ADR-0177 的 “Later” 行。
- 为会话成员提供开发预览、把共享会话的执行端迁移到常在线 Host、分享 team 会话。这三项各自需要独立的传输或身份决策，分别另立 ADR。
- 向成员设备上未打开的共享会话实时投递。这些会话维持 30 秒拉取和 ADR-0207 通知。
- 协作服务端的水平扩展。两条广播通道都在进程内，ADR-0206 已有记录。
- 向成员推送 canonical Agent 事件。

## 后果

- 一条流式回复的 Postgres 写入，从每秒一行完整回复，降到每 10 秒一行，外加 settled 时一行。
- 成员约 0.25 秒内就能看到新输出，工具卡片显示实际运行了什么。
- 未协商 v2 的客户端，在执行端使用本版本时会以 10 秒为步长看到回复。这是降低写入频率的代价，已接受。
- 旧服务端保持原来的 1 秒行为，因为执行端会自动回退。
- 实时通道带来两项新开销：
  - 执行端每帧一次 HTTP 请求，每个 Run 每秒最多四次；
  - 服务端为每个实时 socket 每秒做一次资格检查，并对每一帧做一次准入查询。
- 默认情况下，成员现在能看到工具动了哪些文件、改了多少。在切换为 `full` 的会话里，成员还能读到 2026-08-29 的设计曾刻意不共享的命令和 diff。这些内容经过脱敏且受白名单限制，切换开关会明确说明。

## 实现说明（2026-10-26）

按决定实现，并做了以下在实现中发现的细化。在双成员实测（计划 WP7）完成前，状态保持 Proposed。

- **单飞行靠跳过，而非排队。** 实时 POST 进行中时，下一次流式 tick 直接跳过、不排队；再下一次 tick 编码最新内容。编码器因此不会跑在线路前面，队列里不会丢补丁，也不需要强制关键帧。`settled` 或 `reset` 帧会等待进行中的 POST，并且一定发送。（`lib/collab/shared-run-live-publisher.ts`）
- **级别变化时保留编码器。** 成员端 reducer 会丢弃同一消息中 `seq` 不大于当前值的帧，所以收到 `409 tool_detail_stale` 后若新建编码器，其帧会被忽略。Run 保留原编码器；重新投影后的部件引用都是新的，下一帧会从下标 0 起替换全部部件。
- **`afterRevision` 等于最终 correction 的 sequence 减一。** `settledReplyCaughtUp` 在时间线 revision 大于 `afterRevision` 时放开已结束的回复；成员的 revision 是其同步游标，即最后应用的 sequence。
- **截断点从不拆开占位符。** `translateOffsetsThroughRedaction` 新增可选的 `snap`，把落在脱敏区间内的偏移移到占位符边缘。没有它时，比原文短的占位符会让区间内的偏移看起来落在占位符之后。
- **引用 URL 凭据的文本部件整体隐藏。** PII 检查即使在脱敏后也会刻意拒绝 `user:<占位符>@`（由 `packages/redact` 的测试固定）。无界起始标记的保留规则会忽略已被脱敏的 URL 凭据，因此回复的其余部分不会被它卡住。
- **成员端的新鲜度规则以帧的形式实现。** 静默、撤回、Run 结束、已结束回复和 socket 关闭这些规则集中在 `lib/collab/shared-live-frames.ts`，通过拒绝帧或发出编解码器自带的 `reset` 生效。`useTranscriptLiveTurn` 和编解码器原样复用；`withLiveReply` 是配对 transcript 与共享成员共用的唯一尾部规则。
- **缺省 `toolDetailRevision` 会被接受。** 早于 D18 的执行端完全不共享工具输入，比 `summary` 更严格。
- **输入框行为不变。** 实时回复生成期间，成员的消息列表显示为生成中。其他成员持有租约时，本成员发送的消息仍像以前一样在服务端排队。
- **唯一的实时帧契约。** Host 桥接（`cognia-companion`）、协作服务端和 TypeScript 编解码器都以 `protocol/transcript-live-frame-v1.json` 校验各自的准入规则（id 最多 256 个 UTF-16 单元、安全整数、200 KiB）。第 4 轮审查发现服务端新写的一份已漂移到 512。
- **出口在 tombstone 锁内从不等待网络。** 实时帧在锁内与会话的撤回集合比对，释放锁后再发送；发送设 5 秒超时，超时即关闭卡住的 socket。顺序仍有保证：每个 socket 的循环是串行发送的，通过检查的帧一定先于同一循环发出的撤回事件，而成员会拒收已撤回消息的帧。
- **成员也从拉取中得知 Run 边界。** 成员 socket 断开期间开始的 Run 只会由重连后的拉取告知，因此注册表会读取每一条拉取到的事件，而不只是 socket 通知。
