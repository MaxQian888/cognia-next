# ADR 0153 — 确认由宿主自己取得

**状态：** 已接受
**日期：** 2026-08-27
**相关：** [ADR-0009](./0009-platform-connectors)、[ADR-0059](./0059-server-ops-controller)、[ADR-0136](./0136-cross-device-placement)、[ADR-0152](./0152-connector-controls-name-their-host)

## 背景

`host_admin_lease_issue` 铸造的是每一条 step-up 命令都要出示的、短期且绑定设备的租约：
skills 安装、external-bridge 控制，以及 ADR-0152 之后的连接器 keyring。它的清单条目声明
`approval: interactive`。

它并不 interactive。审批是一个布尔**参数**：

- `admin_lease::issue` 拒绝 `confirmed: false`。
- `authorize_approval` 对这条命令特判，用 `args.confirmed == true` 代替了其他每一条
  `interactive` 命令都必须出示的租约。
- `lib/tauri/admin-lease.ts` —— 唯一的调用方 —— 无条件写 `confirmed: true`，而它的测试
  以「绑定显式确认」为名断言它确实这么写。

于是调用方自证了自己的确认，宿主照单全收。三层互相印证，没有一层是检查。租约真正的权威
一直是那条常驻的 `host.admin` 能力；interactive 这一半是装饰。

在可达的 step-up 面还只有 skills 与 external-bridge 时，这并不紧迫 —— 设备很少碰它们。
ADR-0152 把凭据的读与写放上了设备面，于是它变成了横在配对浏览器与宿主上每一个机器人令牌
之间的那道门。

## 决定

**1. 确认是被取得的，不是被声称的。**
`companion_api::host_consent` 记录某台设备就一组具名操作申请租约、发布这个请求，并把答复
恰好交回一次。`host_admin_lease_issue` 不再读 `confirmed` —— 这个参数已从请求 schema、
从 `admin_lease::issue` 的签名、从客户端一并消失。`authorize_approval` 的特判保留，但现在
说的是实话：铸造租约的那条命令没法出示租约，它的审批在派发臂里执行。

**2. 批准者永远不是请求者。**
持有 `host.admin` 的配对设备可以回答别人的请求，永远不能回答自己的；`host_consent_pending`
把调用方自己的请求从返回列表里滤掉，因此界面根本不会给出一个宿主马上要拒绝的动作。
`owner` 与 `service` 作用域豁免 —— Owner API 的 DPoP 证明主体与回环控制台都在设备面之外，
没有设备可供冒充。

**3. 租户的 Owner 设备就是它自己的根。**
Owner 设备到达 `_rpc` 时和其他人一样带着 `scope: "device"`，所以不做这一条，它面对的就是
和 member 一样的提示。有两点让那样做不是「更严」而是「错」。一个全新的 headless 部署只有
一台配对设备：要求先存在第二台，第一台才能配置任何东西，等于任何东西都永远配置不了。而
要求 Owner 批准**它自己**，正是本 ADR 要移除的自证，只是往上挪了一层。

`host.admin` 不是同一个判据。它是 Owner 可以授予 member 的一项能力，而持有它的 member 的
提权仍然需要有人批准 —— 这也正是连接器审计里的决定 L23：配连接器是管理员行为，member 设备
在管理员的注视下做这件事。

**4. 一次批准换一段租约。**
`take_approved` 会消费掉那条记录。窗口随后由租约提供 —— 默认十分钟、最长三十分钟、
设备断开即撤 —— 所以批准本身没有理由活得比它被花掉的那一刻更久。租约失效后的重试会重新申请。

**5. 提问是幂等的，回答不是。**
设备是靠被拒绝才知道自己需要同意的，所以它会重试。同一设备、同一组操作上已有的未决请求
会被原样返回而不是再排一条 —— 否则一个反复挂载的设置对话框会让批准者面对一串一模一样、
却各带不同请求码的行。已回答的请求则是终局：一个任何还留着请求码的人都能推翻的拒绝，
不是拒绝。

**6. 一条通道、两种宿主，而帧只是提醒。**
`host-consent://requested` 同时承载请求与答复。桌面端 `emit`，由 `event_channels` 的转发器
中继给配对设备；headless 宿主直接发到总线，因为它没有可供 emit 的 Tauri 运行时。订阅者
重新读 `host_consent_pending` 而不是渲染帧内容：这条帧会到达每一个订阅者，包括发起请求的
那台设备，而只有宿主知道某台设备可以处理什么。这也让那次读取顺带成了能力探测 —— 被拒绝
就什么都不渲染，这正是「你不是批准者」的正确界面。

**7. 批准界面在每一种壳上都是同一个组件。**
`HostConsentPrompt` 挂在 `app/layout.tsx`，而不是 `DesktopOnlyInitializers` 后面。
headless 部署的宿主根本没有屏幕，另一台配对设备就是它唯一的交互式批准者 —— 一个只在桌面
存在的提示，会让那种部署留下一道没人能打开的门。

## 后果

- member 设备从手机上配置连接器，现在要等一位管理员回答。这是有意的代价；另一种选择是
  一份既无时限也无第二方的常驻授权。
- `stored` 凭据状态多了一个同类 `awaiting-consent`。两者都表示「这里读不到」，但只有一个
  会自己结束，把它们渲染成同一个样子等于让操作者放弃一件本来马上就要成功的事。
- `host_admin_lease_issue` 的响应被定型为 `HostAdminLease` 而不是 `LegacyRecord`，
  顺带还掉了响应 schema 棘轮记的一行债。
- **控制台回落没有实现。** `cognia-server admin approve <code>` 原本是计划里为「唯一一台
  配对设备就是提问者」准备的答案。决定 3 移除了它存在的那个场景 —— 那台设备就是 Owner ——
  剩下的是「Owner 不在线而 member 在提问」，那会在 Owner 回来时自行解决。请求码照常铸造
  并发布，所以这个回落将来可以在不改协议的前提下补上。
- 批准存在内存里。宿主重启会丢掉未决请求与未被领取的批准，请求方的下一次重试会重新申请。
  持久化换不来任何东西：它们授予的租约本来也活不过那次重启。

## 考虑过的替代方案

**保留 `confirmed`，让客户端去证明它。** 客户端能发送的东西，客户端就能伪造。确认必须由
那个被要求信任它的一方亲自观察到。

**复用 automation 的 `ConsentBroker`。** 它已经有提示、有浮层、有移动端 sheet、有 resolve
命令。它同时也在构造上就是 `headless_unsupported` —— 两条臂都要 `tauri::AppHandle` ——
所以复用它只会交付桌面那一半，而把云端部署留在完全没有批准者的状态，恰恰是最需要这件事的
那一半。

**要求包括 Owner 在内的每台设备都取得同意。** 纸面上更严，实际不可用：全新部署的第一台
设备没有人可问，唯一的出口是一条还不存在的控制台命令。
