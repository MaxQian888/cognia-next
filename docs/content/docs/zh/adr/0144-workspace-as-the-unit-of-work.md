# ADR 0144 — 工作区是工作的单位

**状态：** 已接受
**日期：** 2026-08-25
**相关：** [ADR-0111](./0111-managed-workspace-registry)、[ADR-0090](./0090-unified-agent-execution)、[ADR-0129](./0129-unified-global-search)、[ADR-0128](./0128-scheduler-host-neutral)、[ADR-0122](./0122-first-run-onboarding)、[ADR-0042](./0042-notification-center)、[ADR-0136](./0136-cross-device-placement)

## 背景

多会话其实早就建好了，只是从未浮出水面。`ChatSession.projectId` 自 Dexie v86
起就存在，并带有 `[projectId+updatedAt]` 复合索引；聊天控制器的每一项可变状态
都按 sessionId 键控；执行 broker 是一个 16 permit 的信号量，而不是一把锁。
地基是稳的。缺的是：它之上没有任何东西对「这属于哪个工作区」达成一致，而好几个
本该代表整个应用发声的界面，只描述了用户恰好在看的那一个会话。

三类缺陷，都要到出现第二个工作区或第二个会话时才会显形：

**归属错乱。** 一次发送通过一条六来源的兜底链解析工作目录，而这条链里根本没有
会话自己的 `executionContext`，于是绑定到托管 worktree 的会话，命令实际跑在它
被切出来的那个 checkout 里。新建会话被打上 store 的 `activeProjectId`，而它比
持久化的 `AppSettings.activeProjectId` 领先一次异步写——切换工作区后立刻开一个
新对话，它会被归到你刚离开的那个工作区。技能与 MCP 服务器是全机范围的，没有任何
方式表达「这个 Jira 服务器属于工作仓库」。

**撒谎。** `useChatStore` 把**聚焦**会话的切片投影到 store 顶层，好让约 130 处
遗留调用点继续工作。托盘、状态栏和移动端 shell 读的都是这份投影，于是两个后台
会话正在流式输出、而屏幕上那个会话闲着时，三者一致显示「空闲」。⌘K 默认
`workspace: all`，19 个 provider 里只有 2 个真的读了这个过滤条件，于是每次搜索
都会漏出其它工作区的会话与记忆，且没有任何标记说明它们来自别处。一条「需要批准」
的通知无法说出是哪个工作区、哪个会话发出的。

**只做了一半的模型。** 调度器完全没有工作区概念——只有 payload 里一段自由文本
`cwd`。终端、编辑器与源代码管理各自用不同方式算根目录，且没有一个读执行上下文。
产品里也没有任何地方，提出把它明明已经在使用的那些目录收编进来。

## 决策

### 工作区 = 一个仓库 + N 个执行位

不是「一个工作区多个仓库」，也不是 Workspace > Project 的两层模型。工作区挂载
根目录；**执行位**是它内部的工作树——主 checkout、每个托管 worktree、每个远程
沙盒。这条区分是本 ADR 其余部分的基础：**归属按工作区，互斥按执行位**。

归属是强制且可纠正的。每个会话、日程与能力差异都指名一个工作区；会话可以迁移到
另一个工作区（`lib/chat/move-session-workspace.ts`），且运行中禁止迁移——一次
正在跑的 turn，它的 cwd 不能在脚下被换掉。

### 执行上下文是工作目录的唯一来源

`SessionExecutionContext` 本来就是持久的、也本来就是对的。遗留的六来源 cwd 链
退化为「创建时的种子」；`resolveEffectiveCwd` 与 `resolvePanelRoot` 都从这个
绑定解析。

`resolvePanelRoot` 是所有面向目录的面板共用的唯一规则：固定 → 会话的执行根 →
工作区主根 → 无。**只有**以「对照」为职责的面板才提供固定（源代码管理、编辑器、
搜索——「这个在 main 上长什么样」是真实需求），而执行型面板上的固定是**被忽略
而不是被遵守**的，因此一个陈旧的固定不可能把 shell 指向 agent 并未工作的树。
每个面板都渲染自己解析出的根目录，并在它是 worktree 别名而非用户自己的 checkout
时明说。

### 能力是叠加的，从不被「拥有」

技能与 MCP 服务器仍然是全机定义一次。工作区只在自己的行上记录差异——能力 id →
开/关，缺省表示继承——与 `terminalConfig`、`knowledgeSettings` 已有的形状一致。

在定义表上加 `projectId` 列被否决了：那会让一个定义**归属于**某个工作区，于是
同一个 MCP 服务器要按工作区重新注册、重新授权，并在其工作区被删除时从库里消失。

只有一套机制，而不是设计期草拟的「启用集 + 覆盖」二元组：两者回答同一个问题，
而「同一件事有两种表达方式」正是各个界面开始互相矛盾的起点。启用集是一个投影，
不是第二份存储。这也与成熟编辑器的做法一致——VS Code 的
「Disable (Workspace)」是逐扩展的差异，而不是一份工作区清单。

**插件被有意排除。** `plugins.enabled` 是运行时的加载状态，由
`manager.setPluginIntent` 作为激活的**结果**写入。按工作区叠加它，等于每次切换
工作区都重写「当前实际在运行什么」的记录。要做对，需要再加一列把「已安装且默认
启用」与「此刻已加载」分开——而这正是本层存在的意义所要避免的定义表改动。

### 并发按执行位串行，而不是按应用串行

Broker 的上限回答的是「同时跑多少」。它从来没有回答过「这两个能不能在**同一个
目录**里跑」，而绑定到同一个 checkout 的两个会话，在 16 个 permit 下绰绰有余地
共存，然后在同一棵树里交叉进行编辑、构建与 git 操作。

租约现在可以指名它会改动的执行位，broker 保证每个执行位最多一条腿。有三条性质
把它撑住：

- 续跑豁免优先。被豁免的腿**就是**已经占着这棵树的那份工作；让它等自己的执行位
  会把它所属的会话锁死。
- 执行位在**准入时**占用，而不是在 acquire 时——一条只是在等 permit 的腿，不能
  占着一个根本没人在工作的目录。
- 让出目录并不会凭空造出 permit，因此执行位的等待者会重新走一遍正常准入路径。
  池的排空先于执行位的排空，于是排队更久的 permit 等待者保住自己的位置。

### 代表整个应用的界面，读的是整个应用

`aggregateRunState` 一次性算出全应用的答案：`awaiting_approval` 高于
`streaming`（它是唯一需要用户介入的状态），`error` 高于 `idle` 但低于两个活跃
状态（一次旧的失败不能盖住一个正在跑的 turn）。托盘、状态栏、标题栏 pill 与
移动端 shell 都读它。输入框的草稿状态搬进了按会话的切片，于是切换焦点是**重新
投影**而不是清空，未聚焦的分屏面板也不再往它旁边那一屏里写东西。

### 搜索限定在当前工作区；实体过滤，定义降权

`workspace` 默认为 `current`。**实体**——会话、记忆、issue——属于某个工作区，
超出范围就是噪音。**定义**不属于：把本工作区关掉的技能藏起来，会产出最糟糕的
搜索结果——「我明明有这个，它却不在」——所以它排在本工作区实际使用的条目之后，
但依然可被搜到。**没有**工作区的行是共享的、不是外来的，因此永远通过。对话框会
说出自己被限定在哪个工作区，并提供一次点击放宽：一个用户看不见的默认值，与
「这次搜索本来就漏了东西」无法区分。

### 通知标注来源，永不过滤

跨工作区的提醒正是让并发工作成立的反馈闭环；把通知中心折叠到当前工作区，会丢掉
它一半的价值。记录携带来源工作区，行上也会写出来——但仅当它与屏幕上的工作区不同。

## 影响

**收益。** 会话的工具现在指向会话真正在工作的地方。两个工作区可以同时运行，而
它们的日程、搜索、技能与服务器不会互相渗透，也不会有两个 turn 抢同一棵树。应用
不再在忙碌时声称自己空闲。

**代价。** `SchedulerDatabase` 增加 v5 索引与一次启动期回填——回填不能放在
upgrade hook 里，因为答案在主数据库中，而在 upgrade 事务内跨 Dexie 实例访问会
死锁。创建者未指名会话的 v5 之前的行**保持未归属**而不是猜测：对一个有五个工作
区的用户，用升级那一刻恰好活跃的工作区去打标，五次里会错四次，并且会悄悄把他的
日程重绑到错误的仓库上。

**有意未做。** 跨工作区分屏、弹出窗口、定义表的真正按工作区隔离，以及把
`.cognia/workspace.json` 接为真实来源（它被标记为休眠，不被读取）。移动端是
「并发可见」级别的客户端——能看到并跳转到后台运行、也能远程发起工作——但不是
工作区宿主。

**门禁守住的东西。** 五道，每一道守的都是「写错的那种代码更短」的地方：基线化的
投影/cwd 审计（`pnpm audit:workspace-attribution`）、逐 provider 的搜索作用域
分类、针对 `lint:i18n` 会跳过的动态 key 的目录覆盖，以及上面两处有意拒绝的
三轴休眠钉死。

**与 ADR-0111 的关系。** 本 ADR 关闭了其中「非 chat 调度执行器未证明
Registry-only」这条 P0 的一半：日程现在有工作区，其根目录也走统一解析器。
ADR-0111 本身仍为 **Proposed**，注册表自身的生命周期问题不在此处触碰。

**对 ADR-0122 的更正。** 它「首次运行无法产出项目目录」的说法已不再成立——引导
现在会提供打开或新建，`AppSettings.projectsRoot` 为其提供默认父目录。
