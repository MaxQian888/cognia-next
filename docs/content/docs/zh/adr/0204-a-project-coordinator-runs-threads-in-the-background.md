# ADR 0204 — 项目协调者在后台运行线程

**状态：** 已接受**日期：** 2026-09-29 **相关：** [ADR-0144](./0144-workspace-as-the-unit-of-work)（工作区）、[ADR-0022](./0022-agent-team-runtime-hardening)（PR 反馈循环）、[ADR-0042](./0042-unified-notification-center)（通知）、[ADR-0188](./0188-a-routed-turn-spends-only-what-its-ledger-reserved)（花费）、[ADR-0059](./0059-cloud-deployment-headless-brain) 与 [ADR-0182](./0182-a-project-names-the-image-it-runs-in)（云端执行的来源）

## 背景

Claude Code 的 Projects 让一个长期运行的对话成为一组工作的协调者。协调者把工作拆成并行线程，每个线程在自己的分支上工作并回报结果，总览页显示每个线程的状态和拉取请求，项目还带有自己的指令、目标、记忆和用量。

Cognia 已经具备其中大部分零件：

- 工作区（ADR-0144），带有指令、根目录、环境、计划任务和记忆作用域；
- Squad 运行使用的托管 worktree 与分支；
- `AttachedChildSession`，让子对话把摘要交还给父对话；
- 会话间消息，带 PII 闸门、去重和不可信数据包装；
- 智能体团队的 `PrFeedbackController`；
- 带 `[projectId+at]` 索引的 `sessionUsage.projectId`。

这些零件没有连接起来，而且有一个缺口挡住了其余一切：**没有窗格的对话无法运行。** 它的审批会被自动拒绝，发给它的会话间消息被当作"目标不可用"拒收，也没有东西能让它的 store 切片保持存活。

## 决策

### 1. 角色放在直接会话上，而不是新的会话类型

协调者和线程都是普通的 `kind: "direct"` 会话，用 `ChatSession.projectRole`（`"coordinator" | "thread"`）标记。线程还带有 `projectThread`（所属协调者、任务简报、根目录、由谁提议、解决状态、上次汇报、声明状态、PR 引用）。新的 `SessionKind` 会波及会话暴露、导出以及聊天控制器里每一个按类型分支的地方；角色不会，而且线程始终是一个人可以打开、阅读和引导的对话。

配置放在工作区行上，即 `Project.coordinator`：是否开启、协调者会话 id、目标、线程运行位置、偏好（软并发上限、先提议后启动、每日线程上限、自动修复 PR）、暂停、各角色的默认模型与思考强度、图标，以及一次性设置建议的提出时间。所有读取都经过 `resolveCoordinatorConfig`，因此缺失或只写了一部分的配置含义唯一。每项设置只有一个事实来源：预算在花费预算策略里，通知规则在通知偏好里（见 §9、§11），从不放在工作区行上。

`ensureCoordinatorSession` 依次按指针、按角色查找协调者，都找不到才创建（本地运行、不激活、`rememberChoice: false`，不改写用户的默认值）。并发调用共享同一次创建。

### 2. 线程是拥有独立 worktree 的附属子会话

`createThreadSession` 建立在 `createAttachedSession` 之上：线程的 `attachedChild` 以协调者为父会话和生命周期所有者，工作区为独立；任务简报暂存为 `spawnedTask.pendingPrompt`。创建任何东西之前，简报先通过 PII 闸门。

运行位置取决于 `threadExecution`：`auto`（默认）在所选根目录是 git 仓库时为线程创建独立的托管 worktree 和分支，否则使用文件夹本身；`managedWorktree` 与 `local` 强制二选一。线程可以指定任意工作区根目录（`rootId`）；根目录多于一个时，协调者的状态摘要会把它们列出来。

### 3. 后台持有让会话在没有窗格时保持存活

聊天 store 新增 `backgroundHolds`：`holdInBackground(sessionId, holder)` 保留会话切片并让 `isSessionOpen` 返回 true；最后一个持有释放时，空闲且无人保留的切片被丢弃。持有永远不会从真实窗格手里夺走决策权。由此：

- 被持有会话的审批不再被自动拒绝——它们在"待处理"面板中等待；对完全没有窗格、仅被持有的会话，设置 24 小时的兜底超时；
- 控制器像对待已打开的会话一样，为被持有会话投影子智能体、投递会话间消息。

线程在回合运行期间被持有；只要协调者还有活跃线程，宿主就持有协调者，以便汇报能唤醒它。

### 4. 启动线程走同一条发送路径

线程状态为 `staged → running → completed | interrupted`，记录在 `attachedChild.status` 上。`startThread` 先做准入，再标记为运行中、持有它，并用 `sendChatMessage` 提交暂存的简报——这正是用户发消息所走的完整发送路径，因此 worktree、租约、预算以及每一道发送时闸门都会生效。只要简报还在，线程就处于"已启动但未送达"，宿主在重新加载后会重新投递（`resumeProjectThreads`）；回合随上一个进程终止的运行中线程会被标记为已中断。

准入（`admission.ts`）在协调关闭、项目暂停或达到每日上限时拒绝创建；启动时还检查软并发上限，用户明确点击"启动"时可以越过这一上限。

### 5. 汇报是生命周期关联会话之间的会话间消息

线程回合结束时（`thread-watcher`，一个聊天 store 订阅者），结果以会话间消息的形式汇报给协调者，因此会经过该通道的 PII 闸门、去重、容量限制、不可信数据包装，并在对话中显示为可见的一行。通过 `lifecycleOwnerSessionId` 关联的会话可以越过彼此的会话间消息限制（`resolveInboundPolicy`）；发给暂时不可达的关联接收方的消息会继续排队，而不是失败。

两条上限防止汇报风暴：5 秒内到达的汇报合并为一条消息；每个协调者每小时触发超过 6 次回合后，后续汇报以便签形式送达（可见，但不触发回合）。暂停项目的协调者收到的所有汇报都是便签。用户主动要求的停止不会被汇报。

### 6. 协调者的工具、协议和每回合状态

内置工具沿用现有插件工具模式（手写 schema 的清单、从不抛异常的执行器、一个 IPC 分支、在 `resolveSendOptions` 中门控）：协调者有 `spawn_thread`、`propose_threads`、`start_thread`、`message_thread`、`list_threads`、`read_thread_report`、`stop_thread`、`resolve_thread`、`remember_project_note`、`set_project_preference`，线程有 `report_to_coordinator`。除 `set_project_preference` 需要询问外，其余全部放行。

提示词布局保持缓存稳定：项目目标是位于工作区指令之后、经过 PII 闸门的段落；角色协议在会话内保持不变。项目状态摘要（偏好、根目录、最多 12 个最近线程及其状态、分支、PR 和最近结果，上限 6000 字符）放在动态尾部。新项目的协调者第一回合，动态尾部还会带上一次性的设置建议——每个根目录一个探索线程，以及工作区已有的计划任务——要求以 `propose_threads` 给出，并记录到 `setupOfferedAt`。

### 7. 线程看板

看板状态由推导得出，从不存储：等待（审批或声明受阻）、待评审、进行中、已暂存、合入中、空闲、已解决，依据切片状态、待处理审批、线程声明的状态和 PR 状态计算。安静 7 天的线程自动标记为已解决。看板位于工作区总览中协调卡片旁边；每一行都是普通的对话链接，带有启动、停止、解决、重新打开和 PR 操作。

### 8. 线程的拉取请求复用智能体团队观察器

`PrFeedbackController` 对其绑定类型泛型化（`PrWatchTarget` 加上 `identify` 函数和 `untrack`），智能体团队行为不变。`ProjectPrWatch` 跟踪每个在 github.com 仓库上有分支的活跃线程，把观察结果写入新表 `sessionPrObservations`（schema v233），并把 PR 引用同步到线程上。项目开启 `autoFixPr` 时，CI 失败、要求修改和冲突会发送给该线程；否则只在看板上显示。创建 PR（草稿）和合并（squash，需确认）都是显式操作。

### 9. 项目预算与用量

花费预算策略新增按项目的每日和每月上限（`costBudget.perProjectDailyUsd` / `perProjectMonthlyUsd`），以发送所在工作区自己的花费来判断，花费从 `sessionUsage[projectId+at]` 读取（只计本机花费）。聊天回合现在会在用量行上写入 `projectId`，这笔花费由此才存在。项目范围只在被问到时才评估，因此从不指定项目的调用方不受影响。工作区页面新增"用量"标签页：该工作区的预算进度条、最近 30 天总额与热力图，以及按对话、按模型的花费，全部来自共享的汇总函数。

### 10. 暂停

暂停会停止协调者的回合以及所有正在运行回合的线程（标记为已中断并释放持有），并停止 PR 监视。保持项目停止的逻辑放在每类回合的起点：聊天控制器拒绝发往暂停项目的协调者或线程的任何消息（`projectPaused` 诊断），准入拒绝启动线程，`sendToThread` 和重新加载时的对账跳过该项目，指向其会话的计划目标任务会被拒绝，汇报以便签送达。同一工作区里的普通对话照常运行。恢复时会投递之前被搁置的简报。输入框上方和协调卡片中的横幅说明原因，并提供"恢复"。

### 11. 通知

会话通知监视器跟踪每一个存活的切片——打开的窗格和被持有的会话——当用户没在看的会话完成、失败或等待审批时发出通知（审批是 `directed`，会计入角标）。通知偏好新增按工作区的规则（`perProject`：静音、渠道、更严格的系统通知级别），存在这类规则时，`notify` 会在路由前先解析工作区。

### 12. 设置与接续已有对话

工作区管理器新增一个即时写入的"项目协调"区块：目标（可能触发 PII 闸门时先保留不保存）、图标、线程运行位置、上限、先提议后启动、自动修复 PR、各角色的默认模型与思考强度、工作区的花费上限和通知规则，以及一个链接到按该工作区筛选的记忆页（`/memory?workspace=`）。

对话菜单中的"作为项目继续"把一个空闲、无关联的直接对话变成其工作区项目的第一个线程：它被重新挂到协调者下，成为已完成的线程（不复制任何内容）；协调者的第一回合带上该对话经 PII 闸门的交接投影，并被要求提议剩余工作。

## 未采纳的方案与阻塞项

- **云端常驻线程。** 线程在聊天控制器所在的地方运行，也就是渲染进程。要在没有设备打开时运行线程，需要把控制器的发送路径放到无头大脑上（ADR-0059），并为每个线程提供环境（ADR-0182）。在此之前，线程的工作会随应用暂停，恢复时重新投递或标记为已中断。
- **自动推送进行中的工作。** 线程分支在从看板创建 PR 时推送。持续推送需要按根目录的推送策略和凭据，目前尚不存在。
- **暂停整个工作区。** 暂停只覆盖项目工作：协调者、它的线程以及指向它们的目标任务。工作区里的计划任务和普通对话不会暂停。

## 影响

- 被后台持有的会话可能把一个审批挂起长达一天；看板、"待处理"面板和通知会让它可见。
- 线程会累积 worktree 和分支。不会自动删除任何东西；解决线程会保留它的分支、对话记录和 worktree。
- `sessionPrObservations` 表（v233）已加入数据治理目录。
- 协调可以随时关闭；会话保留各自的角色，在重新开启之前表现为普通对话。
