# ADR-0097 — 跨设备设置契约与 Companion 覆盖范围

**状态**：已接受（2026-07-29）**作者**：Max Qian + Claude **基于**构建**：ADR-0012（传输抽象）、ADR-0021（WebRTC WAN 传输）、ADR-0027（移动离线与发现）、ADR-0056（移动设置对等性）、ADR-0059（云部署/无头 Brain）、ADR-0085（云共享浏览器）

## 背景

移动↔桌面↔云基底构建广泛：五个`Transport`实现、四个可达通道、一个带有持久光标和出站队列的同步编排器、Dexie优先读取、远程主机路由和无头 Brain。对这些部分之间的*接缝*进行审计，发现了一群无声的失败，它们共享一个形状——一份在两个地方描述的合同，没有任何东西能与之相比;或者是一个能力限制在一个比它所保护对象更广泛的限制运行时检查。

**设置根据两份手写列表交叉。** Rust `APP_SETTINGS_MOBILE_ALLOWED_KEYS`决定客户可以写什么;TypeScript `CROSS_PLATFORM_SETTING_KEYS`决定主持人如何镜像。没有什么能让他们相互比较，他们已经漂流了：

- ~51 字段可写入，但无法向下镜像，因此手机的外观、文本转语音、通知和网页搜索偏好与桌面永久不同。
- `defaultCharacterId`被允许列入名单，但存在于`AdapterInstanceRow`，而非`AppSettings`——手机可能通过验证后写入不存在的字段。
- `signalingUrl` / `iceServers` / `turnServers` 被完全错误地分类了。客户端从自己的行读取这些信号来拨号约会，且从未被镜像下行，因此主机上配置的自托管信令服务器或中继TURN无法访问电话。症状WebRTC在严格NAT下逐渐消失。
- `remoteBrowserEnabled`也有同样的反转，这使得ADR-0085云共享浏览器无法被任何non-Tauri客户端访问：它被限制在那些客户端永远无法接收的值上。

**主机镜像是按页面负责的。** `useSettingsPatch`本地保存并排队`app_settings_update`;九`/me/*`页就这么说了。移动路由中*嵌入桌面设置部分*——`/me/appearance`渲染桌面的`<AppearanceSection />`——直接进入了设置商店，而设置商店只在本地写入。有十三个允许名单条目专门为了避免这些标签达到400，而且从未被动用过。

**`sync_pull`将主机的整个设置行都放在线路上。**客户端只应用了镜像子集，看起来无害，但整行已经发送过：API密钥、提供商和搜索提供商 凭证、订阅令牌、WebDAV密码、代理认证、工作目录路径。所有配对设备都收到了所有这些信息。允许列表自己的评论说提供商配置保持桌面功能;这总是限制写作。

**伴随连接逻辑被Capacitor限制。** 通道库存刷新、重新连接编排、网络恢复重新探测、TURN配置和WebRTC层都被提前返回`isCapacitor()`，因此指向云端`cognia-server`的浏览器都没有这些功能——只有WebSocket自身的退回。这五人中只有一个需要原生网络。

## 决策

### D1 — 一个分类表，四个类别

`packages/agent-config-types/src/settings-sync.ts`对每个`AppSettings`场进行了分类：

| 类别 | 客户端→主机 | 主机→客户端 |
| --- | --- | --- |
| `shared` | 是的 | 是的 |
| `server-authoritative` | 不 | 是的 |
| `device-local` | 不 | 不 |
| `desktop-only` | 不 | 不 |

`device-local`和`desktop-only`都“从未跨线”，但并非同一主张：前者说每个设备都有自己的答案，后者说该字段根本不属于移动合同。这两个非对称范畴带有**强制理由**（由并集类型强制执行），因为未解释的不对称性与后续的错误无法区分。

### D2 — 按类型完成，按门禁漂移

该表被声明为`satisfies Record<keyof AppSettings, SettingsSyncEntry>`，因此添加设置字段而不进行分类`pnpm typecheck`失败——无需新门禁以确保完整性。`scripts/build/gen-settings-sync.mjs` 生成Rust常数和表中的OpenAPI `propertyNames.enum`;`settings-sync:check`在门禁注册表里以`--check`模式运行。漂移从“将被检测”转变为“无法表达”。

### D3 — 传输配置是服务器权威的

`signalingUrl` / `iceServers` / `turnServers`，`remoteBrowserEnabled`仅向动**。它们描述的是部署过程，而不是手机本身。`webrtcEnabled`是`device-local`：是否尝试该层次是每个设备自己的通话，尽管它拨打的终端并非该终端。

`turnProvider`本身保持桌面功能，因为它携带主机本地密钥环引用。主机解析静态TURN秘密，并通过镜像`turnServers`字段发布由Cloudflare Calls或Twilio铸造的短命ICE服务器;配对客户永远无法获得或解决提供商长期隐藏的秘密。

有三个字段停止被记录，因为这样做是错误而非有用：`biometricRequiredFor`（该设备自身认证器的属性——将手机策略推送到没有生物识别硬件的笔记本可能会被锁定）、`workflowEditorPerformanceTier`（为某一设备的GPU选择）和`selectedMicId`（一个不指向其他地方的标识符）。

### D4 — 镜像挂在持久漏斗上，而不是页面上

每个设置都会通过`lib/db/settings.ts:saveSettings`写漏斗。排队会移到那里（`lib/settings/mirror-to-host.ts`），这样可以一次性修复所有嵌入的桌面部分，并在到达时使下一个重复使用的部分正确。`saveSettings`会为用户未完成的写入——启动时修复路径——进行`{ mirrorToHost: false }`，因此本地清理不会作为有意的编辑重播到主机上。

已拒绝：通过十六个出现组件串联可注入补丁回调。这样可以固定一个部分，保持模式完整。

### D5 — 待写掩盖下镜

拉取可以跳过任何仍然有`app_settings_update`排队的字段（`pending`、`sending`或`failed`）。没有这个，离线编辑在重新连接时会明显恢复，队列耗尽后又会变。`sent`被排除，因为宿主已经拥有该值;`deadlettered`是有意排除的——这些写入永远不会被重试，所以掩盖它们会让客户端固定到主机永远不会保持的值上。

已拒绝：每个字段的时间戳。它们解决了真正的并发编辑问题，而这对单一用户来说很少见，但代价是改变行形、同步路径和Rust写路径，以及时钟偏移处理。

### D6 — 源代码编辑

`readSettingsDelta` 在离开主机前，将单例的设置缩小到镜像字段。在客户端进行删减无济于事：客户端无法撤回接收的秘密，而线路协议由多方客户端使用。

### D7 — 默认为主机中立，仅在主机实际不同时进行门控

伴随控制器运行在实时传输所在的`CompanionTransport`——Capacitor和带有配置服务器的浏览器中。只有本地网络发现（mDNS加子网扫描）才会保持Capacitor门控;浏览器使用主机报告的地址，通过`companion_endpoints`，这也是它唯一的路径。入口点也被重新命名为`installCompanionSignalingController`以配合。

### D8 — 四个通道的一张表

伴随设置新增通道表，将绑定模式、mDNS路由、隧道和 WebRTC 连接为一个视图：状态、地址和最后一次探针结果。它区分了*关闭*的路由和*开启但无法工作的路由（服务器停止、绑定回环、WebRTC无交会服务器）以及适用的名称。它取代了连接诊断卡，后者运行相同的探针，但打印出一个平面URLs列表，不知道每个节点属于哪个路由。

### D9 — 云端登录并非仅限桌面

Logto卡会移动到与移动路由（`/me/cloud-account`）的共享接口。在桌面之外，会话存在于加密的IndexedDB库中，该库拒绝写入，直到其密钥被注入;没有任何方法注入了 Logto 的代码，所以在手机上登录会完成整个浏览器往返，但会失败，同时保留令牌。`session-store.ts`现在的条款和`lib/plugin/api/secrets-api.ts`一样关键。

### D10 — 每个主机都可以授予提升能力，代理是独立的授权

两个问题，一个形状。

`control_allow_list` 是一个内存内集，其唯一的写入者是启动时桌面渲染器调用的Tauri 命令。无头 `cognia-server`没有渲染器，因此进程生命周期内列表是空的，**所有CONTROL-tier RPC都无法通过JWT云主机上的设备**——你可以将桌面与桌面配对，读取文档ADR-0082能力边界，却找不到任何机制能实现。`device_grants.rs`增加了缺失的一半：一个JSON文件，放在其他无头 凭证文件旁边，启动时读取以做种允许列表，由`cognia-server devices grant|revoke|grants`编写。资助申请将在下一`serve`申请，CLI指出，匹配`rotate-master-key`。

另外，四个外部代理臂被`SERVICE_ONLY`，因此ADR-0082的R4被结构阻挡：配对会产生一个*设备*JWT，且没有任何方法能将其转化为服务令牌。他们会进入第四层，`AGENT_CONTROL_COMMANDS`，服务范围限制**或**明确的代理控制授权，在HTTP 处理器镜像和`dispatch`镜像都强制执行，WebRTC路径无法绕过。

Agent控制是**与远程控制**分开的授权**，而不是一个标志。远程控制转向工作是主持人已经选择运行的;这会启动新的流程。一个开关意味着用户启用远程控制，以便手机批准提示，同时也释放了进程执行。两者都作为独立的设备切换，在启用方向上都采用生物识别门控。

安全底线不会变化：每个生成仍然清除`SpawnPolicy`预设允许列表（固定列表中的裸二进制，工作区根的 CWD，默认拒绝环境），且每次允许和拒绝都会用调用者的设备 ID 和范围进行审计。该检查只针对请求本身，而不是呼叫者，因此被授权的设备与Brain完全一样。

### D11——主机为自身能力负责

ADR-0061 `remoteCapabilityUnion`聚合器`pairedDevices`——这些设备与这台机器配对。配对是运行客户端→主机，所以客户端*驱动**的主机在结构上不在列表中，没有其他方式可以请求。因此，工作流程预检测试根据本地基线和服务器可能运行的已拒绝 `always-on`/`headless`工作来判断远程云服务器。

`host_capabilities`是通过`desktop_writes_bridge`路由的READ-tier RPC，所以主机自身的TypeScript层负责回答——桌面上的渲染器和无头服务器上的Brain，这两者都已经安装了`installDesktopWriteSource`。用Rust回答意味着会获得第二份能力词汇，这正是D1存在的目的。

客户端在激活时询问，将答案存储在`RemoteHost`行，并`remoteCapabilityUnion`合并。无法回答的主机保留了其最后已知的列表，而不是被空白：陈旧的答案仍然比默默回归本地基线强。主机列表显示了回复内容，或者明确表示尚未请求。

这是P5 ADR-0061能见度半段。放置——在桌面离线时将cron或webhook触发器路由到云节点——是**不完成**的;见下文。

## 后果

- Rust常数和OpenAPI枚举是产物生成的。手动编辑会被下一次发电机运行时恢复，CI会发现。
- 有三个设置停止在设备间传播（D3）。每个设备仍然能在设置的设备上正常工作;变更集说明了这一点。
- 镜像子集现在是配对客户端唯一能观察到的主机设置，这对任何（错误地）依赖整行的内容进行了行为缩窄。
- 浏览器伙伴现在负责在通道间协商WebRTC并进行故障切换。这是运行时 接口新区域，之前两者都没有。

### D12 — 同步状态的作用域是指向它来自的主机

`syncCursors`仅凭桌子名称来标记。没有记录水印来自哪个主机，重新配对时也没有清除，所以一个在别处配对的客户端从前一个主机的水印恢复，向新主机请求自某个时间戳以来的所有内容，而时间戳对方毫无意义——将两台机器的会话、消息和字符默默混合到一个本地存储中。

光标键为`[serverKey+table]`（v130），其中`serverKey`是主机在配对时发出的**设备ID**，而非主机自身的`serverId`：该光标是每个（客户端、主机）对唯一的，从配对那一刻起就存在，且没有首次连接往返，已经在`CompanionConfig`中持续存在，且当重新拉取是安全答案时，光标会准确变化。

划分光标是必要但不够的——从前一主机拉取的*行*保持在同一表中。因此，编排器在观察到主机键变化时会清除镜像表。`settings`被排除：它是客户端本地写入的唯一镜像表，清除该表会丢弃主机从未拥有过的设备本地偏好。

有两个实施需要注意的说明：

- Dexie **不能更改已有表的主键**;尝试会破坏数据库中所有多版本升级路径，而不仅仅是新版本。因此，每个主机的光标存在于一个新商店（`hostSyncCursors`），而在同一版本中旧的光标被丢弃。
- 版本**129被故意跳过**。同一工作树上有一个并发分支正在运行，之前曾两次因该方式丢失模式编号（v66、v69）。Dexie只需要增加版本，所以让下一个数字免费，不会产生任何费用，并且避免了两个分支发布不同版本定义的可能性。

### D13 — 配对记录存放在凭证册中，公开面与秘密面分离（2026-08-02）

D12 让切换主机变得*安全*，但并没有让它变得*可行*。`CompanionConfig` 只有一条记录 ——
一个 `baseUrl`、一个设备 JWT、一个 TLS 指纹 —— 所以客户端只能持有一个配对，
凡是需要按主机隔离的东西，都只能从「碰巧唯一」的某个字段里反推出来。

这条记录现在按它真正的两条接缝被拆开：

- **`CompanionHostRecord`** —— 公开面：标签、端点、TLS 指纹、主机在配对时签发的设备 id，
  以及 `cursorNamespace`。刻意存放在普通存储中：Vault 处于锁定状态时，设置页仍必须能列出
  全部已配对主机，而「Vault 已锁」绝不能看起来像「没有配对过任何主机」。
- **`CompanionHostCredential`** —— 秘密面：设备 JWT 与信令私钥。只存放于浏览器 Vault
  （PBKDF2/AES-GCM）或平台密钥库，并且永远不会出现在记录列表中。
- **`CompanionCredentialBook`** —— 覆盖两者的 list/get/upsert/remove/set-active。

配对按 `{hostId, accountNamespace}` 寻址。两半都必不可少：同一台物理桌面可以从两个本地账户
分别配对，而这两个配对绝不能共用令牌、水位线或镜像行。

实现需要守住三条不变量：

- **`cursorNamespace` 只分配一次，永不迁移。** 同步游标、出站队列行与 runtime-target
  数据库都归档在它下面；一旦它随重新配对或改名而变动，这三者都会被孤立。
- **`remove` 先删秘密面，再删记录。** 记录是唯一能寻址到凭证的东西，顺序颠倒会在密钥库里
  留下一个再也够不到的设备 JWT。
- **连接状态更新受 generation 保护。** 探测是并发竞态的 —— LAN 探测器较慢的「offline」
  可能晚于隧道探测器较快的「online」落地 —— 因此携带过期 generation 的更新会被拒绝而非应用。

`CompanionConfig` 本身保持不变，仍是所有下游消费者读取的形状；凭证册位于该接口之后，
对外回答该账户当前**活跃**主机的配对。需要多主机语义的调用方直接与凭证册对话。

既有配对只迁移一次，且顺序保证「被中断可重跑、而非破坏性」：记录 → 凭证 →
把已持久化的游标改归到新命名空间 → **把两半都读回来逐项比对** → 通过后才删除旧记录。
校验失败会保留旧记录并报告原因；丢失配对意味着必须重新做一次物理配对。

### D14 — 是否清空镜像由数据库决定，而不是由「切换」这一事件决定（2026-08-02）

D12 用主机签发的 **device id** 作为游标键，并在该键变化时清空镜像表。这两半都太粗。

`deviceId` 是**每次配对**新签发的，不是每台主机一个。于是「重新配对同一台桌面」会被读成
换了一台主机：所有镜像表全量重拉一遍，外加一次镜像清空 —— 而那台机器的状态其实什么都没变。
现在游标按主机的 **`cursorNamespace`**（`{accountNamespace}:{hostId}`，见 D13）取键：它在
重新配对时保持稳定，且按账户区分 —— 也就是镜像真正归属的那一对。旧版本写在旧键下的游标会
在首次运行时被认领，而不是被当成别的主机的；少了这一步，升级本身就会把「仍然配对着的那台
主机」的镜像清掉。

清空现在只回答一个问题，而且是问数据库、不是问内存：**这个数据库里是否已经存在属于其他主机
的游标？** 游标与镜像行写在同一个数据库里、按主机分键，所以这里出现一个陌生键，就意味着那台
主机的行正躺在这些表中 —— 除此之外没有别的判据。

正是这条规则让切换主机不再具有破坏性。一旦账户有了 runtime target，每台主机的镜像各自位于
自己的 Dexie 数据库（`activateAccountDatabase(accountId, targetId)`），于是切换会激活另一台
主机的数据库，而这次扫描找不到任何陌生键：两台主机各自保留镜像与水位，切回去时一行都不用
重拉。当两台主机**确实**共用一个数据库时 —— 没有 runtime target 的安装，或旧的账户级数据库
—— 扫描会发现陌生键，清空照旧触发。原先那个基于内存的「主机变了」判断被移除了：它分不清这
两种世界，而且会漏掉所有在进程没运行时发生的切换（这在 iOS 上是常态，系统经常在写入
`CompanionConfig` 与下一次同步之间把 App 杀掉）。

凭证册的迁移也会改归同一批旧键。同步的某一拍可能跑在它前面，因此两条路径对「哪个水位留下」
的判断必须一致 —— 已经落在新键下的那条胜出 —— 否则后跑的一方会把先跑的一方的水位回退。

### D15 — 多 Host 协同已在生产路径可达（2026-08-13）

Web 现有的 Runtime Target 菜单与 Mobile 的已配对服务器 Sheet 现在直接调用凭证册。两端都可通过
`/pair?mode=add` 添加 Host、按稳定 `hostId` 切换、显示当前标记并完整移除。Web 的离线、不兼容、
缺少授权统一进入 `/pair?mode=recover`；缺少授权时会显示准确能力，并明确要求在 Host → 设置 →
Companion → 已配对设备中处理，不会暗示浏览器可以自行授予 Host 权限。

Mobile 将 Companion 工作绑定到 `local_acct_a`，并以稳定 `hostId` 作为 runtime context、Runtime
Snapshot、出站队列和目标数据库的作用域。带日志的收养迁移会从 `__local__` 复制并校验凭证册记录与
秘密、保留当前 Host 指针、把旧数据迁入该 Host 的数据库并归属旧 Mobile 队列行；只有校验完成后才
删除源数据。其他 Host 的数据库保持为空，直到第一次权威同步。

切换会先等待出站 runner 静默，再停止旧 Host 订阅，然后切换凭证册/registry 指针、数据库和
runtime context，重载 transport、协商 manifest、执行权威同步、重绑 Host 服务并发布 snapshot。
失败会恢复全部状态；若回滚不完整，则清空 runtime context 与 transport 缓存，禁止向不明确的 Host
发送工作。

移除以远端完成为前提。客户端使用被移除 Host 的显式凭证和 TLS pin 调用
`DELETE /api/devices/{deviceId}`。只有成功或明确的 `device_revoked` 响应才允许本地清理；离线、超时、
普通认证失败与 `last_owner` 都保留配对、密钥、数据库、镜像、游标和全部队列状态以便重试。活动 Host
存在替代项时必须先显式选择并验证备用 Host；Web 无替代 Host 时回到 standalone，Mobile 唯一 Host
则保持活动完成撤销后进入未配对流程。

## 还没完成

- **工作流程布局（ADR-0061 P5正统）。** 没有任何东西能选择执行*哪里*。接收到的进程会触发cron或webhook——`trigger-bridge`调用`runWorkflow()`——没有桌面实时探测、执行者选择，也没有切换。D11使云主机的功能可见;桌面关闭时，它不会让任何程序运行。这需要分布式调度语义（谁算离线，时间长短，双方都认为应该跑什么`run-lease`），并且是刻意规划的。

- **同伴设置master/detail。** 该部分仍然是一卷可折叠分组，而不是像Gateway或外观那样的导航+面板分割。故意推迟：它是导航形式，而非破损的机制。
