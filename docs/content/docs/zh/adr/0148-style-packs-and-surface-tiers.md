# ADR 0148 — 风格包与层级语义表面

**状态：** 已接受
**日期：** 2026-08-25
**相关：** [ADR-0007](./0007-theme-and-background-fix)、[ADR-0114](./0114-chat-message-presentation)、[ADR-0127](./0127-chat-render-transport-efficiency)、[ADR-0092](./0092-official-website-workspace)

## 背景

三条诉求同时出现：希望有一种没有圆角的硬朗风格、图片背景支持不好、不同组件之间极其割裂。调查发现第一条被 token 层的缺口挡住，而第二、三条其实是同一个缺陷的两个侧面。

**旋钮早就有了，缺的是"成套"。** `lib/appearance/` 有 77 个文件——圆角滑杆、密度、动效、排版、逐组件的 tonality 与 elevation、五种作用域的壁纸（含模糊、不透明度、焦点与可读性 scrim）、9 套手写主题、VSCode `.json`/`.vsix` 导入、OKLCH 变体推导与 WCAG 守卫。但 `lib/themes/preset-meta.ts` 里的 8 个 preset **只管强调色**。没有任何东西把"形"打包，所以"调成硬朗"意味着手动拨十几个分散的控件。

**而且即便拨完也做不到。** 把 `--radius` 设为 0 能方化约 1,777 处使用 `rounded-sm/md/lg/xl` 的地方，因为 `@theme inline` 让它们派生自同一个基值。但它碰不到 491 处 `rounded-full`、24 处 `rounded-2xl`/`rounded-3xl`，以及 252 处 `shadow-*`——这些没有任何设置能够触及。更糟的是，shadcn 把各档写成固定像素偏移（`--radius-xl = base + 4px`），所以即使基值为 0，最大的一档仍然停在 4px。真正方正的界面在当时是**无法表达**的。

**壁纸的半透明只覆盖 28 个组件。** `component-style-registry.ts` 列出 28 个 `data-slot`，每个各自挑选自己的档位，`globals.css` 用约 830 行未分层规则去绘制它们。所有自研表面——页面外壳、导轨、侧栏、功能卡——对这套系统完全不可见，因此始终 100% 不透明。于是开启壁纸后图只在缝隙里露出来，相邻面板的透明度差异肉眼可见。另有七个路由（`/logs`、`/devices`、`/agent-runs`、`/templates`、`/goals`、`/integrations`、`/servers`）根本没有 `data-bg-target`，壁纸完全不显示——这与 ADR-0007 记录的 E1 缺陷同型：作用域选择器写在 CSS 里，却没有任何组件真的打上它所依赖的属性。

**设计语言其实已经存在。** `web/app/globals.css` 里写着 `--radius-control: 8px`、`--radius-panel: 12px`、`--radius-stage: 14px`，注释是 "No oversized pills"，还有发丝线与 `--action: #35cedd`——后者产品端已经原样拷贝。官网就是产品自身外观的克制版本。

## 决策

### 1. 与配色正交的风格包层

`types/appearance/style-pack.ts` 引入三个包：**Soft**（当前默认）、**Studio**（官网语言）、**Sharp**（除真正的圆形外一律方化）。每个包同时设定圆角基值、胶囊圆角、层级上限、边框调性、密度、微标签处理与 composer 皮肤。

风格包**不携带任何颜色 token**，因此 Sharp × Catppuccin、Sharp × 任意导入的 VSCode 主题都成立。一条测试断言任何包值都不得包含颜色。

数据形状是 `{ packId, overrides }`，刻意沿用仓库已有的 `MessageDisplayPreferences`，好让设置界面、变更审阅与分区重置的行为与用户既有预期一致。

### 2. Soft 由构造保证惰性，而不是靠承诺

`resolveStylePackDom` 在 Soft 下返回全 null，applier 什么也不写。默认外观不可能回归，因为根本不存在会改变它的代码路径——这与 `RadiusApplier` 的默认分支、`classic` composer 皮肤是同一范式，并由测试锁定，而不是交给评审。

### 3. 圆角与密度仍归各自的 applier 所有

`StylePackApplier` 只写形状属性与两个自定义属性，**不写** `--radius` 和 `data-density`；改由 `RadiusApplier` 与 `DensityApplier` 把风格包当作基值读取。两个 applier 争写同一个内联属性会产生竞态，输的一方会在每次设置变更时抹掉赢的一方。

两者的优先级是显式的：风格包提供基值，用户自己的控件**只在离开默认值之后**才覆盖它。因此"没动滑杆"意味着"交给风格包决定"，这正是选中 Sharp 能真正方化界面的原因。风格面板会明说当前由谁做主，而不是让那个数字与实际显示悄悄矛盾。

### 4. 命名尺度是现有链的别名，并且按比例缩放

`--radius-control`/`-panel`/`-stage` 以同一基值的倍数（`0.8`/`1.2`/`1.4`）加入，在默认的 0.625rem 下精确落到 8/12/14px——即官网的尺度——于是那约 1,777 处已经在用 `rounded-sm/md/lg/xl` 的调用点**零迁移**即可跟随风格包。

现有四档也改为倍数（`0.6`/`0.8`/`1.0`/`1.4`）。它们在默认基值下命中同样的 6/8/10/14px，而与上游的 ±px 偏移不同，它们会随基值一起归零。这个问题是把三个包并排渲染出来才发现的，不是读代码读出来的。

### 5. 胶囊自成一条轴

`--radius-pill` 是独立 token，因此方化界面永远不会把状态圆点、spinner、单选按钮或头像也方掉。划分标准是语义的：带内边距的胶囊属于装饰性 chrome，跟随风格包；圆形就是圆形。共转换了 74 个文件中的 89 处胶囊与 shadcn 原语中的 11 处声明；头像按产品决策保持圆形。`rounded-2xl`/`rounded-3xl` 与 `--radius` 毫无关联，因此由风格包在 CSS 中重新挂靠，而不是去改 24 个调用点——这同时也让默认外观纹丝不动，因为没有风格包属性时该规则根本不匹配。

### 6. 表面声明层级，而不是声明数值

`components/surface/surface.tsx` 用"声明你属于哪一层"替代"逐组件配置一个档位"：`base`（页面底面）、`raised`（卡片与面板）、`overlay`（浮层、菜单、弹窗）。只有三条规则决定一层长什么样，因此同层的两个面板不可能各走各的。

机制和模型同样重要。`Surface` 读 `--surface-bg` 而不是直接刷 `bg-card`，而层级规则**只设置自定义属性**。自定义属性从不与 Tailwind 工具类争特异性，所以与现有壁纸层不同，这里完全不需要未分层覆盖：15 条选择器替代了按 slot 写的约 830 行，并且任何表面一旦接入 `Surface` 就立即被覆盖。旧规则作为兼容垫片保留，服务尚未迁移的部分。

`Card` 与 `Alert` 在外观不变的前提下完成改造。仅 `Card` 就有约 559 个调用点，`SettingsCard` 又建立在它之上，因此整个群体无需改动任何调用方即可参与进来。

两条刻意的限制：`Surface` 只负责背景、绝不负责前景色（若接管前景，`text-[var(--surface-fg)]` 会与元素上显式的 `text-destructive` 相争，而 Tailwind 把任意值排在具名值之后，层级会悄悄把警示文案重新上色）；`backdrop-filter` 只由 `globals.css` 在壁纸开启时施加，绝不作为类挂在元素上——它即便在 `blur(0px)` 也会提升合成层，而这些容器就渲染在虚拟化的聊天列表里。

### 7. 由外壳持有壁纸作用域标记

`FeaturePageShell` 与 `SubPageShell` 自己打上 `data-bg-target`，一次覆盖 14 个功能路由与 51 个移动子页，新路由不可能再忘。原先携带该属性的 9 个页面包装层交出它——嵌套的作用域目标会绘制第二层 `::before`，把壁纸的有效不透明度翻倍。

### 8. 一条带棘轮的门禁，因为这种损坏创建极廉价、发现极昂贵

`pnpm audit:surfaces` 拒绝新的裸面板容器（同时带圆角、边框与背景的 `div`），以及任何设置都触及不到的新圆角/阴影值。454 个文件中的 816 处存量写入基线，只准变小、不准变大；计数按文件记录，因此在一处还债并不能为别处的新面板买单。

配套测试遍历每个 `app/*/page.tsx`，对任何无法抵达 `data-bg-target` 的路由报错，并会跟随 barrel 的再导出，以免经由 `@/components/plugins` 引入的路由被误判为未标记。两个扫描都断言自己确实扫到了足量文件——因为"什么都没匹配到"的扫描和"确实没有问题"的扫描一样是绿的。

## 影响

- 选中 Sharp 会方化界面、去掉阴影、收紧密度，并把微标签设为等宽大写。三个包均已在浏览器中验证。
- 圆角滑杆变成风格包之上的覆盖项，并迁入新的"风格"面板——一个值只有一个控件。
- `stylePack` 是 `shared` 同步键：它必须与 `density`、`radius` 一同传递，否则手机会拿到桌面端算出的圆角，却没有产生它的那个风格包。
- 取消移动端最小圆角下限。触控**尺寸**仍强制 44px；圆角属于审美，而那条下限会让手机上的 composer 成为一片方正界面中唯一圆润的物体。

## 不在范围内

- 统一四条互相独立的编辑器/图表主题通道（Monaco、CodeMirror、chart.js、Mermaid）。那是四次独立迁移，而 code-server 是 CSS 完全够不到的原生子窗口。
- 迁移 816 处已进基线的存量。门禁负责守住底线，债务随手偿还。
- 重命名背景作用域词表（`chat` 被当作通用内容作用域使用）。它造成的功能缺口已由决策 7 解决；重命名属于人体工学改进，且会牵动约 35 个文件与 103 处 CSS 选择器。

## 已知缺口

- `settings-sync:gen` 无法重新生成 Rust 镜像：OpenAPI 文件在本次工作之前就已丢失生成标记，`cursor`、`componentStyles`、`monacoLink` 与 `usageDisplayMode` 也因同一原因早已缺席。`stylePack` 在该问题解开之前与它们同列。
- `wallpapers` 位于 `MOBILE_WRITABLE_SETTING_KEYS` 中，因此手机会把一份包含设备本地 `blobKey`/`relPath` 引用的壁纸数组镜像到根本无法解析它们的桌面端。这是既有缺陷，与本次改动无关，值得单独修复。
