# ADR 0150 — 仓库供给与对象缓存

**状态：** 已接受
**日期：** 2026-08-26
**相关：** [ADR-0111](./0111-managed-workspace-registry-and-bundle)、[ADR-0144](./0144-workspace-as-the-unit-of-work)、[ADR-0147](./0147-repository-declared-workspace)、[ADR-0151](./0151-stacks-as-first-class)

## 背景

关于「给任务准备工作副本」的两条抱怨一起到达：慢，以及仓库被反复克隆。两条都没说时间去了哪
里，而那个显而易见的答案——克隆——对最要紧的那条路径恰恰是错的。

这些路径上一个埋点都没有，所以第一件事是加 span 并对本仓库录基线（280.2 MB、25,138 个受跟踪
文件）：

| 每任务开销 | 实测 |
| --- | --- |
| `git worktree add --detach`（完整检出） | **3.1 s** |
| 读取并哈希全部受跟踪文件（`capture_with_policy` 的下限） | **5.5 s** |

快照的真实代价比它的下限更高：它把 280 MB 的 blob 同时握在一个
`HashMap<String, Vec<u8>>` 里，再逐个压缩写进 SQLite——为的是 git 已经持有的内容，而这条路径
的隔离手段本身就是 git worktree。

## 决策

**先测再改，并把数字写下来。** 每条供给路径都带 `cognia_instrument` span，下面每个批次落地后
都重录一次基线。没有这一步，力气会花在克隆上——因为看上去就该花在那里。

**快照只存 git 不掌握的部分。** git 隔离下，已提交内容用 commit SHA 引用，只捕获脏状态与未跟踪
的增量。在基线仓库上 13.67 s → 0.546 s，287.8 MB → 13.8 MB。`transfer.rs` / `bundle.rs` /
`ledger.rs` 同批改造，否则 ADR-0111 的回滚与转移读到的会是一个不复存在的快照形状。

**每个 remote 一个裸镜像，按规范化后的 URL 作键。** `https://host/o/r`、`.../r.git` 与
`git@host:o/r.git` 是同一个仓库，因此必须是同一个镜像；按原始字符串作键会把同一个仓库缓存最多
四份、各自单独 fetch。凭据在算键之前就被剥掉——这个键会变成磁盘上的目录名。

**用 partial，绝不用 shallow。** 凡是应用替用户克隆的地方一律 `--filter=blob:none`。`--depth`
会截断历史，而截断的历史无法 rebase 到边界之外、无法回答 `merge-base`、对 `git log` 只显示一个
提交——而同一批检出恰恰会被交给要问这些的调用方。GitHub 自己公开的测量也表明，浅仓库的 *fetch*
明显慢于完整仓库，工作区里后续每次 fetch 都继承这个代价。

**缓存未命中永远不是错误。** 镜像损坏、远端不可达、上次 fetch 之后上游才创建的分支：每一种都
退回到普通网络克隆，且不留下半成品目录。缓存的代价必须是一次慢克隆，绝不能是一次坏掉的运行。

**依赖供给靠推断，再由用户确认。** lockfile 推断出供给策略（JS 走 pnpm 全局虚拟 store，
`target` 与 `.venv` 走链接缓存），作为本机 Workspace 设置呈现给用户接受。它不写进仓库声明：那会
把一台机器的便利塞进 ADR-0147 的信任门里，而那道门管的是「仓库有权声明什么」。

## 后果

**克隆不是代价的计量单位。** 每任务那条路径本来就不克隆；镜像真正的受益者是那些确实克隆的路径
——issue loop、插件工作区、沙箱——现在同一个仓库的第二次获取是本地的。

**blobless 克隆是把代价推后，不是消除。** 需要历史文件内容的命令（`git log -p`、对旧修订
`blame`）会按需取回，协议 v0 下每缺一个对象一次往返。这也是用户自己在源代码管理里克隆的仓库
保持完整的原因：URL 是他们敲的，跑 `blame` 的也是他们。

**pnpm 自己的警告仍然成立。** 「不要让互不信任的 agent 或用户共用一个可写的 pnpm store。」全局
虚拟 store 面向的是单个用户自己的工作区，不是共享构建缓存。

## 考虑的替代方案

**`--reference` / alternates。** 比镜像更省，但被否决：git 文档直说参考仓库的 gc 会让克隆变成
损坏状态，而按计划刷新的镜像正是会被 gc 的那种仓库。从镜像克隆会把需要的东西复制过去，此后两者
彼此独立。

**硬链接式本地克隆。** 从本地路径 `git clone` 默认共享 pack 的 inode，还要更快。而这些克隆中
有几份会交给带 shell 权限的 agent，且那条路径的指令来自任何人都能提交的 issue 正文；一次写入
共享 pack 就会让这个仓库的所有其他使用者的缓存一起损坏。`--no-hardlinks` 是「不和不受信任的进程
共享可变 inode」的代价。

**`git maintenance register`。** 它会把仓库写进用户的**全局**配置，并为其安排全机范围的后台
任务。这些是我们的缓存目录，不是用户的仓库。改为直接写 commit-graph 与 multi-pack-index——对
[ADR-0151](./0151-stacks-as-first-class) 每次栈校验都会跑的祖先遍历同样有效，且没有全局状态。

**受保护克隆的前置体积探测。** 它需要向各个 forge 询问仓库多大，而这是一个按宿主而异的 API 调用
——`cognia-git` 刻意做不到：这个 crate 编译时根本没有网络传输。blobless 默认让常见情况保持小，
克隆后的体积检查仍然是兜底。

**去掉 `commit_and_push` 里的第二次克隆。** 它看着像浪费，实际是信任边界：`mirror_worktree`
把 agent 的文件复制过去但从不复制它的 `.git`，于是提交与推送跑在一个 agent 无法写入的仓库上。
在 agent 自己的工作区里提交，会在我们的 token 已经在环境里的情况下执行它留在 `.git/hooks`
里的任何东西。

## 被测量推翻的前提

- **克隆不是代价所在。** `create_execution` 直接对用户仓库 `git worktree add`，那条路径上从来
  就没有克隆。
- **快照才是。** 它在读取并哈希 git 已经持有的内容，峰值内存等于整棵树。
- **`--depth 1` 不是节省。** 它是在一个调用方要问历史的检出上做截肢，而且按 GitHub 的测量它
  甚至不更快。
- **按仓库加互斥锁比并行化 bundle 更划算。** 对仓库 common dir 加锁之后，同仓库的工作本来就
  串行；多仓库 bundle 罕见到并行化的风险大于收益。
