# ADR 0138 — 阅读区布局稳定

**状态：** 已接受
**日期：** 2026-08-21

## 背景

会话转录在抖。两条反馈，最后发现它们大半是同一个成因：

- **回复流式输出时**，正文会上下微跳一两个像素，光标下方最明显；
- **什么都没在流的时候** —— 一次工具密集的长轮次、内容早已上屏 —— 阅读列的底部
  仍然在自己抽动。

阅读区不是一个朴素列表，下面每一个机制当初都有充分的理由。这正是抖动难以被看见的
原因：单独看每一件都站得住，抖的是它们凑在一起做的事。

### 五个滚动写入者

`MessageList` 在五个地方写 `scrollTop`，各带各的门控：

| 写入者 | 触发时机 | 相位 |
| --- | --- | --- |
| `useEffect([messages, status, isAtBottom, autoScrollOnStream])` | 每一次转录提交 | **绘制之后** |
| 内容 `ResizeObserver` | 延迟 markdown、Shiki、图片 | 绘制之前 |
| 视口 `ResizeObserver` | 拖 dock、缩窗口 | 绘制之前 |
| 思考指示器 `onPhaseChange` → `pinToBottom` | 每一次 tip 轮换 | **绘制之后** |
| finalise 重测后的 `requestAnimationFrame` | 轮次封口 | **绘制之后** |

……而这些又同时和 `virtual-core` 自己的 `scheduleScrollReconcile` rAF 循环互相追
逐，`handleScroll` 再把结果读回 `isAtBottom`，闭合成环。

五个里有三个跑在**浏览器绘制之后**。`useEffect` 不是绘制前钩子：React 在这一帧已
经上屏之后才冲刷 passive effect。于是每一次合并后的流式提交都是——先把变高的内容
画出来（阅读列被顶上去一个增量），下一帧才把滚动补回来。在大约每帧一次提交的节奏
下，这就是持续的单帧震颤，也就是"正文上下微跳"的全部。

### 流式那一行是被"估"出来的

正在流的那一行是虚拟列表里唯一被刻意不挂 `measureElement` 的行——按 token 测量会
把观察者泵起来——所以它的槽位来自 `Math.max(220, 220 + textLen * 0.55)`。真实文本
按约 22px 的行高阶跃增长，而这个估值按每字符 0.55px 连续增长。于是
`getTotalSize()` 下游的一切，包括自动吸底所对齐的 `scrollHeight`，追的都是一个从
来不等于渲染高度的数。

### 动效落在一个被测量的盒子里

`MotionCollapse` 在 `0` 与 `auto` 之间补间 `height`。在设置面板里这是一次动画；在
转录里，每一行都被 `ResizeObserver` 盯着（`measureElement`，加上自动吸底背后的内
容观察者），于是它是**整段动画期间每帧一次布局变化**，每一次都重新发布虚拟化偏移
并重新吸底。

每个 Streamdown 块上的 `content-visibility: auto` 从另一侧闭合了类似的回路：块在
"已渲染/被跳过"之间翻转会改变它的高度，行高随之改变，块被移动，于是再次翻转。

### 思考指示器是一台常开的动效机器

这是"什么都没在流也在抖"的全部。指示器在整个轮次期间都在跑——工具密集时是好几分
钟——就坐在回复正下方，而它内部有三样东西挂在定时器上：

- 标签自挂载起**每 3 秒**轮换一个动词，普通 `<span>` 的宽度随之改变，把跳动的圆点
  横向推来推去；
- tip **每 5 秒**轮换一次；不同 tip 长度不同，于是有的折成两行有的一行，而
  `AnimatePresence mode="wait"` 让单元格在两者之间短暂为空——行先塌陷再弹回；
- 每次轮换都调用 `onPhaseChange`，强制一次绘制后的滚动吸底。

在 `compact` 模式下——内容已上屏，也就是长轮次的大部分时间——tip 仍在轮换，于是它
就在可见回复的下方顶着它。

### 排查过但**不是**成因的

`parseIncompleteMarkdown` 默认为 `true`，但 `remend@1.3.0` 只补全**行内**标记（加
粗、斜体、行内代码、链接、KaTeX、删除线），不会猜列表和表格。块级结构随 token 到
达而沉降是流式 markdown 的固有行为，不是一个可关的开关——它靠"同帧吸底"吸收，而不
是靠关掉什么。

## 决定

### 1. 唯一的滚动写入者，写在 layout 相

`hooks/chat/use-stick-to-bottom.ts` 是转录 `scrollTop` 的唯一所有者。状态驱动的吸
底跑在 layout effect（DOM 变更之后、绘制之前）；两个 `ResizeObserver` 回调同步吸
底，因为观察者回调本来就在 layout 之后、绘制之前送达。

每一次写入都经由同一个 `pin()`，当容器对当前 `scrollHeight` 已经在底部时它什么都
不做。于是**"一次提交至多一次滚动写入"是一条可断言的事实**，而不是一句愿望。

它的职责止于锚定。跳转到某条消息、落地闪烁、返回原位的提议、以及向 viewport store
的发布，属于导航，它们没有坏，保持原样。

### 2. 流式尾行移出虚拟列表

只有已完成的消息被窗口化。正在流的那一行与思考指示器以真实文档流渲染在虚拟容器之
下，构成一个 `[data-slot="conversation-live-tail"]` 区域，在虚拟化与文档流两种模式
下都统一持有转录的底部。

窗口化对那一行本来就无可提供：它必然在屏幕上，且必然是最后一行，所以它下面没有任
何行会被推动。真实高度、真实 `scrollHeight`、没有估值——而那个递增估值以及它所补偿
的测量跳过，一并删除。

轮次封口时该行带着 `measureElement` 回到虚拟列表，在同一次提交中被测量。由于它是最
后一行，下方没有东西会被顶动，所以这次交接不需要预置测量值，只需要一次 layout 相的
重新吸底。finalise 时那次全量 `rowVirtualizer.measure()` 也随之删除：它为了校正一
行的估值而丢弃了每一行的测量结果。

有两个契约跟着这一行离开了窗口：

- `jumpToMessage` 对 `virtualCount` 及其之后的索引改走 DOM 锚点路径。尾行和其它行
  一样带 `data-msg-id`，而查找栏命中正在流的回复恰恰就落在这里。
- 迷你地图把尾部区域的高度计入它归一化标记位置所用的总长，通过 `getTailSize`
  **getter** 传入——绝不能传数字，因为尾部高度每秒变化很多次，不得引发列表重渲染。
  该 hook 内部用 ref 持有它，这样调用方给出的不稳定标识也不会把它的 rAF 循环搅起
  来。

### 3. 转录内部的动效只允许触及合成层

只允许 `opacity` 与 `transform`。任何改变盒子尺寸的东西要么去掉，要么包进一个不参
与测量的容器。

`ReadingCollapse` 就是去掉高度的 `MotionCollapse`：内容在一次布局中取到最终尺寸，
只有绘制被动画（快速淡入加 2px 落位）。收起是瞬时的——这里刻意没有
`AnimatePresence`，因为让退出的内容留在树上直到动画结束，正是它要避免的那个高度动
画。失去的是"内容展开"的那种感觉；换来的是展开一张卡片只付一次重排，而不是十七次。

阅读区的四个折叠面用它——工具行、活动分组、子 agent 主体、思考指示器。十个设置面板
的消费者继续用 `MotionCollapse`，那里没有任何东西测量这个盒子，展开动画值得保留。

### 4. `content-visibility` 只保留在已完成消息上

从流式块包装器上去掉，在 `FinalizedMarkdownSection` 上保留。流式路径上根本没有屏外
内容可跳过，而那一行**是**被测量的，于是它纯粹是一条反馈回路。已完成消息则确实会
把块滚出视口，而且它们记住的尺寸本来就是真的。

包装器保留它真正需要的那一个职责——给会渲染 `<pre>` 的块挂上 typeset 的豁免标记
——而不渲染 `<pre>` 的块现在完全没有包装元素。

### 5. 思考指示器保留表达，但移出布局流

- 标签坐在一个由**所有动词不可见地堆叠**撑开的 grid 单元里，于是这个单元从第一帧
  起就有最长动词那么宽，切换纯粹是 opacity。圆点再也不会动。
- tip 区固定两行（`text-xs` 下的 `h-8`）并对文本做截断，相邻两条 tip 在同一个 grid
  单元里交叉淡入而不是轮流出场。没有 `mode="wait"`，没有 `y` 位移。
- `onPhaseChange` 删除。`useStickToBottom` 观察内容盒，于是唯一真实的那次增长——骨
  架与 tip 的显现——被自然跟随，这一行不需要知道任何关于滚动的事。

### 6. 光标改用 Streamdown 自带的

`caret="block"`，而不是手写元素。我们那个是 `MessageContent` 弹性列里
`<MessageResponse>` 的兄弟节点，于是在每一条流式回复下方常驻 16px 一行加 8px 间距，
并在封口时一次性消失 24px。Streamdown 把 `▋` 渲染成最后一个块的 `::after`：行内、
不贡献任何盒子，并且会在未闭合的代码围栏里自我抑制——这是那个兄弟 span 从来没做到
的。降低动效时保留光标，只去掉闪烁。

## 验证

### 指标是方向，不是距离

`lib/chat/jitter-probe.ts` 每个动画帧采样一次位置，统计的是**方向变化**而非位移
量。平滑滚过一段长回复是很大的位移却完全不抖；一个像素预算会把它误报，而且会随内
容长度、字体、视口宽度漂移成一个易碎的门禁。已渲染内容的方向变化，其正确值是零。

门禁是 0.5px 容差下的 `reversals === 0`——亚像素舍入既不能制造出方向反转，也不能给
一个静止的哨兵赋予它从未有过的方向。

Storybook 里的 `Chat/MessageList → JitterProbe` 以大约每帧一次提交的节奏驱动一段假
流式输出，采样转录底部并打印报告。这是唯一能观测到该故障的地方：jsdom 没有布局引
擎，而 `__mocks__/motion-react.js` 把 `AnimatePresence` 的子节点直通渲染，从不运行
时间线。

### 规则是可执行的

`components/chat/reading-area-motion.guardrail.test.tsx` 读取阅读区源码，在出现被动
画的盒子尺寸、或绘制后的 `scrollTop` 写入时失败。它之所以是源码扫描，正是因为这两
类故障在 jsdom 里根本无法复现——在进入桌面壳之前，源码是唯一能拦住回归的地方。往阅
读区新增组件，就意味着把它的路径加进去。

## 后果

- 转录的可滚动总长现在只是**已完成消息**的函数，因此不会随每个 token 起伏。
- 展开一张工具卡是一次重排，而不是 280ms 内每帧一次。
- 思考指示器的表达得以保留——动词仍在轮换，tip 仍在循环——但两者都够不到布局。
- 长 tip 会被截到两行。接受：另一种选择是让回复下方的那一行每五秒改变一次高度。
- 阅读区的折叠不再有展开动画。理由同上；淡入仍然承载了这次变化。
- 尾行是同一行的第二条渲染路径。它是有界的（至多一条消息加指示器），而且正是这条
  路径消除了估值、测量跳过与 finalise 重测——净减少特例，而不是增加。
