# ADR 0141 — 首次运行：两条路径，一张画面

**状态：** 已接受
**日期：** 2026-08-23
**部分取代：** [ADR-0122](./0122-first-run-onboarding)

## 背景

ADR-0122 把一个 597 行的对话框换成了一条以「一件真实、可当场验证的工作」收尾的路由化流程。那个决定仍然成立，它的大部分论证也仍然成立——扫描的双计时器策略、`hasModelAccess` 的锁存判定、连接凭据时写入的三处指针、按能力门控的启动卡、五种退出路径、内置 skill 的防伪造论证。这些都不在本文重议之列。

没有站住的是它的**形状**，有两条轴。

**四屏，四个问题。** 序列先问这台机器，再问凭据，最后问第一个任务。而在一台已经装了 Claude Code 且已登录的桌面上——也就是扫描步骤存在的意义所在的那台机器——其中三个问题的诚实答案都是「是，显然」。流程其实知道这件事：探测到已认证的 CLI 时它已经会跳过登录步。但一步一步地知道仍然要花四屏，而每一屏都横在新用户和「产品做点什么」之间。

**每一屏长得都一样。** `--primary`、`--accent`、`--card`、`--muted` 在明暗两套下都是 `oklch(… 0 0)`——应用的色板是有意无彩的，彩色留给语义（`--success`/`--warning`/`--info`）和工作流节点分类。于是这条流程就是四屏 `text-sm text-muted-foreground` 装在通用的 `rounded-xl border bg-card` 里，左边一条 `w-[15.5rem] lg:w-[18rem]` 的 rail 装着三个标签和三行描述，右边一列 `max-w-[44rem]` 的内容飘在窗口正中。九个词的侧栏，大半个桌面屏什么都没干，而且屏幕上没有任何东西是属于你当前所在这一步的。

品牌并不是没有。它在官网上：`web/app/globals.css` 带着完整的 ADR-0092 V2 色板——`--paper`、`--ink`、`--stone`、青色 `--action`、琥珀 `--approval`——明暗两套齐全，每个 token 都有 WCAG 论证。它停在了应用门口，所以从 cognia 官网走进来的用户，迎面看到的是一屏和官网毫无共同之处的界面。

## 决定

### 1. 欢迎屏分出两条路径

`OnboardingMode` 是 `"express" | "custom"`，持久化在 `onboardingProgress.mode` 上（与该记录其余部分一样，属于设备本地）。

```
express  →  welcome → express                             （2 屏）
custom   →  welcome → [scan] → [provider] → first-run     （不变）
```

`resolveStepSequence` 接过这个答案并据此过滤，所以下游没有任何东西需要知道自己在哪条路径上——序列本身已经编码了它。在分叉被回答之前，序列**只有欢迎屏**，这正是让那一屏上的「返回」和「继续」保持诚实的原因。

**呈现为一个主按钮加一行轻链接，而不是两张对等的卡。** 它们不是两个平等选项；其中一个是绝大多数人应该按的那个。画成一对会给「以减少决策为职责的那一屏」再加一个决策——而在手机上，独立/配对的分叉已经占了两张卡，再来一对就是首屏四张卡。

**运行模式分叉现在只提交不前进。** 一台手机在一屏里回答两个问题：它怎么跑，以及它想被问多少。两个路径控件在第一个问题回答前都是禁用的，因为运行模式正是决定序列的东西——不选就开始会为一个用户还没选定的 shell 构建计划。

### 2. 推荐路径是一屏，并且把底牌摊开

`buildExpressPlan`（`lib/onboarding/express-plan.ts`）从自定义路径用的同样三个探测源推导出一张清单，屏幕在 `plan → applying → ready` 之间推进，全程不跳转。

| 条目 | 来源 | 类型 |
| --- | --- | --- |
| `migrate-config` | `probeVendors()`（ADR-0107） | 动作，可取消 |
| `import-history` | ADR-0062 来源遍历 | 动作，可取消 |
| `use-runtime` | 已认证的 `ScannedRuntime` | 事实陈述 |
| `sign-in` | `hasModelAccess === false` | 交互 |
| `pair` | shell 为 `mobile-paired` | 交互 |
| `capabilities` | `resolveCapabilities` | 事实陈述 |

**先确认，再写入。** 其中两条会往用户机器上写东西——配置迁移把另一个 agent 的命令、设置、技能和 MCP 服务器复制进 Cognia，历史导入把每一份可读的记录写进 Dexie。两者都没有撤销。仅仅因为用户按了一个写着「推荐」的按钮就默默做掉，这不是捷径，这是替他做了决定。所以清单先出现，任何动作条目都可以去掉。

**一条要么是动作，要么是事实陈述。**「我们会用这台机器上已登录的 Claude Code」不给复选框，因为取消它并不意味着「少做一点」——它意味着「那现在来问我登录吧」。只有真的有东西可决定的条目才渲染复选框。

**在一台什么都没有的机器上，清单收缩成两条**——接一个模型，以及你将能做什么——标题和副标题也跟着变。这是设计出来的形状，不是退化情形：这一屏是一张会自适应的清单，不是一张带空行的固定表单。而且它才是首次运行的多数情况。

**登录内联，因为它是唯一无法自动化的一步。** OAuth、设备码、贴 key 都必须用户亲自参与，所以「推荐」永远不可能等于零交互。但它可以等于**一次**交互、且不离开这一屏：`ExpressSignIn` 给出该 shell 下最可能的那一个选项——能访问钥匙串时是 Anthropic 订阅按钮，standalone 模式下是 key 输入框（因为 `resolveAccountEnv` 在那里什么都不返回）——完整目录只隔一次展开。展开挂载的是真正的 `ProviderStep`（隐藏标题），不是第二个精简版选择器。

**终局步骤就地渲染。** `FirstRunStep` 由 `ready` 相位承载，而不是一个目的地，这正是这条路径端到端只有两屏的原因——也是启动卡得以保留原有 test id 的原因。

### 3. rail 变成叙事面板

`NarrativePanel`（26rem，`lg` 以上 30rem）同时取代了 `StepRail` **和**那个只在 `md` 以下出现的 `StepProgressBar`。它占用真实的宽度并配得上：里面装着由实时数据绘制的画面、一句叙述，以及——仅在自定义路径上——`StepStepper`，一行横向的进度，保留 rail 真正被需要的那唯一一件事。

`md` 以下面板变成顶部的一条带，而不是换成另一个组件，所以没有第二套布局要维护，也没有会漂移的窄屏替身。

**推荐路径不显示 stepper。** 它的序列是两屏，其中一屏还是引言；一行写着「1 / 1」的进度除了「你走了短路径」什么都没说。它的进度是计划条目逐条完成。

### 4. 画面由真实数据驱动

`components/onboarding/scenes/` 下五张 SVG 共用同一套词汇——机器边框、核心、条块、连线——所以整条流程读起来是一张连续的画。核心在各步之间从不移动；扫描画面里那一列条块**就是**推荐画面里的计划。

手绘矢量而非截图，三个理由：应用是静态导出，这里的一切都进包并由首次运行路径买单；矢量仅凭 CSS 变量就能适配明暗两套；以及最关键的一条——它能被实时状态驱动。截图没法为探测真正找到的每一个 runtime 点亮一个节点，没法把「装了但没登录」的 CLI 的连线画成虚线，也没法在计划条目落地的那一刻打上勾。

首跑画面是唯一一张信息流反向的：别处都是条块喂给核心，那里是核心往外写，因为那正是整条流程存在的目的。

### 5. 入场动效用 CSS，不用 `motion/react`

第一版用的是 `motion.g` 加 `initial={{ opacity: 0 }}`。它有一个这一屏承受不起的失败模式：如果动画没能推进——帧循环被节流、子树被合成器停住、启动时标签页在后台——元素就停在它的**初始**值上，而初始值是不可见的。这不是假设，它在组件预览里就复现了，整张画面一片空白。

CSS 的 `animate-in` 朝相反方向退化。`tw-animate-css` 默认 `animation-fill-mode: none`，所以一个从未运行的动画会把元素留在它自己的样式上，也就是最终态。为此加进 `globals.css` 的每一条 keyframe 都把起始态写在 keyframe **内部**：`onboarding-draw` 在 `from` 和 `to` 里都设了虚线模式，所以一条动画没跑起来的连线会被画成实线，而不是被虚线吞成不可见。

它的覆盖也更好。`globals.css` 的守卫会把 `animation-duration` 压到 1ms、`animation-iteration-count` 压到 1，且覆盖全部三条减少动效信号——系统查询、`.reduce-motion` class、`[data-reduce-motion="true"]`；而 `useReducedMotion()` 只看得到第一条。画面仍然会读 `useFlowMotion()`，因为交错**延迟**不在那些守卫的覆盖范围内，否则减少动效的用户会对着一片空白面板等完整个交错时长。

三种动效，全都承载状态：连线自己画出来；仍在执行中的连线走蚂蚁线（虚线没法同时自己画出来——两者都要用 `stroke-dasharray`）；已激活的核心每四秒呼吸一次，好让一个可能要在上面等完一轮 OAuth 的屏幕不是一张静物。

### 6. `--brand-action` / `--brand-approval`，从官网抄来

以十六进制加进 `globals.css`，**逐字抄自 `web/app/globals.css`**，好让两个文件可以直接 diff 是否漂移——四舍五入的 oklch 转换只会让它们「近似地」是同一个颜色。作用域和 `--effort-ultra` 一样：目前只有首次运行接管界面在用。

只借强调色。应用自己的中性底色保持不动，所以走完设置进入工作区不会有色温跳变。官网规范的用法约束也一并带过来：`--action` 在浅色底上只有 1.69:1，`--approval` 是 2.15:1，所以它们是描边、填充和状态点——绝不是文字色，也绝不是某个状态的唯一载体。画面里每一种色调同时也是一种形状：实线还是虚线、空心点还是实心点、点还是勾。

### 7. 一个凭据写入口

`lib/onboarding/connect-provider.ts` 现在同时拥有两条凭据路径，因为两条各有两个调用方。在登录步和推荐屏之间漂移的凭据写入几乎无法调试：症状是几屏之后第一个任务被派给了错误的 provider，而中间没有任何线索指向原因。

## 后果

- `components/onboarding/step-rail.tsx` 删除。`onboarding-rail-{id}` 这些 test id 在 `StepStepper` 上保留——行为没变，所以测试套件和 e2e spec 挂靠的钩子也不变。`onboarding-progress-bar` 随之消失，它已经没有可替身的对象了。
- `OnboardingStepId` 新增 `"express"`；`ONBOARDING_STATE_VERSION` 升到 2。没有 upgrade 回调也没有 Dexie 版本号变更：`mode` 是可选的，`resolveOnboardingMode` 会为旧行从 `lastStep` 推导——任何越过引言的步骤都属于拥有那些步骤的那条序列，而只有一条路径拥有它们。仍停在 `welcome` 的记录会被重新询问，而不是被替它猜。
- `advanceOnboarding(step, mode?)` 在步骤之外带上路径。不传 mode 表示「没有新答案」，而不是「忘掉旧的」。
- `vendorLabel` 移入 `lib/onboarding/scan.ts` 并共享。顺手修掉了一个既有缺陷：扫描步的迁移行原本写着「Import commands, settings and past sessions from claude-code」，把一个内部 slug 印给了只见过「Claude Code」这几个字的人。
- `ProviderStep` 新增 `heading?: boolean`，好让推荐屏能把它挂在自己的计划条目下面，而不产生第二个 `<h1>` 或破坏标题层级。

## 考虑过的其他方案

**保留四步，把分叉做成第五屏。** 否决：那样推荐路径就变成「替你多按几下继续」，而屏数反而**增加**。收益来自把问题折叠到一起，不是来自把它们问得更快。

**推荐路径完全不确认。** 按上面的理由否决——其中两条会往磁盘写且没有撤销。确认只花了这条路径本来就要渲染的一屏，而它是「捷径」和「替人做决定」之间的分界。

**整套搬用官网色板，包括 `--paper` 底色。** 否决：官网是暖白、应用是冷白，设置的最后一步会把用户交给一个色温明显不同的工作区。重调应用的中性色是动到里面每一个页面的改动，不该由这条流程夹带。

**面板里放产品截图而不是自绘画面。** 否决：首次运行路径上的明暗两套位图，而且截图无法报告**这台**机器上有什么——那正是面板占用这些宽度的全部理由。

**顺便重构自定义路径。** 否决：选它的人要的就是每一步都在自己手里，压缩它会把两条路径之间唯一的区别抹掉。
