# ADR 0137 — 委派运行时

**状态：** 已接受
**日期：** 2026-08-21

## 背景

"把这件事交出去"没有载体。执行日志里的每一个 kind 命名的都是**正在执行的引擎**
—— `agent-turn`、`team`、`workflow`、`plan`、`goal`、`scheduled` —— 而它们都活不
过一次尝试。一次失败的委派就只是一次失败的轮次：没有任何东西持有那份承诺，于是这
份工作无法作为一个整体回报，无法交给人，也无法在不假装"已终结的 run 没有终结"的
前提下重试。

由此产生三个各自独立可观测的缺口：

- **从聊天线程派出的团队 run 是不可见的。** `putExecutionRunBinding` 只有三个调用
  点，没有一个是团队 run，所以从 IM 派出的团队没有卡片、没有进度，每一个控制回调
  都会被判为会话不匹配而拒绝。run 存在，但提出请求的那个线程既看不见也够不着它。
- **没有任何东西可以被纠偏。** 只有停止和暂停两个动词。一个人看着 agent 在做错的
  事情，要么结束 run 重新讲一遍任务，要么继续看着。没有第三种选择。
- **`parentRunId` 一直存在却从未建索引。** 这一列自 v114 起就在 `executionRuns`
  上 —— "本 run 续接某次恢复尝试时指向的上一条不可变日志 run" —— 但"哪些 run 属于
  这一个？"是一次全表扫描，这正是从来没有人问过它的原因。

## 决定

### 委派是一个 run kind，它命名的是承诺

`ExecutionRunKind` 新增 `"delegation"`。它刻意不是旁边任何一个 kind 的同义词：那些
命名的是此刻在执行什么，这一个命名的是承诺了什么，而承诺比任何单次引擎尝试都活得
更久。引擎 run 通过 `parentRunId` 指向它（**v176** 建索引，含
`[parentRunId+status]`），它们的进度被重新投影到父 run 上。

**一次委派只有一张卡片。** 没有这层投影，委派派生的每个引擎 run 都会开自己的
binding，提了一个问题的人要盯着三张互相漂移的卡片 —— 这恰好就是"把它交出去"本该
消除的失败形态。

三层权重，只有第一层是自动的：

| 层 | 触发 | 建了什么 | 用户看到 |
| --- | --- | --- | --- |
| T0 一次性 | 轮次同步作答 | 1 × `agent-turn` run + binding | 一张活动卡片，跑完冻结 |
| T1 委派 | 轮次被接受为异步 | + 1 × `delegation` run + binding；子 run 带 `parentRunId` | 确认 + 里程碑，就地更新，可 steer 可停 |
| T2 追踪 | 显式提升 | + `issues` + `issueRuns` | 同时进看板，有编号有状态列 |

T2 保持显式：每次委派都铸 Issue 会烧掉 `issueCounters` 的永久编号，并污染一块人们
用来做计划的看板。

### 桥是对账器，不是订阅

订阅只能看见它在场时发生的状态迁移，而委派的设计目标就是活过重载、宿主切换和崩
溃。所以父 run 的日志是在任意时刻**从子 run 的当前行推导**出来的，每一次发射都带
一个按 `(子 run, 状态)` 生成的 `sourceEventId`。重放安全来自日志自身的幂等，而不是
来自"记住已经发过什么" —— 这正是它在一次自己没有观测到的崩溃之后依然正确的原因。

结算刻意保守。委派不是因为子 run 用完了才关闭，而是在没有任何东西还能推进**并且**
没有人被问了问题时才关闭。一次停在人身上的委派按构造就没有活跃子 run，所以仅凭
"没有活跃子 run"会在交接发生的那一刻就把每一次交接都关掉。

### 接受即开卡

`createExecutionRun` 不产生事件，而呈现 runner 的门是
`snapshot.revision > binding.lastProjectedRevision`。一个建好之后安静地去做规划的
run，在人正想着"我的请求被听见了吗"的整段时间里都是不可见的。因此接受时会在同一
tick 里写下 `run.started`（以及已有里程碑骨架时的 `plan.created`），并且**先绑定再
写日志**，使 runner 不会在 binding 还不存在时就被事件唤醒。

### Steer

`RunControlAction` 新增 `"steer"`，而消息本体走**命令**，永不进日志。那份日志会被
投影到十二个平台的卡片上，所以其中的自由文本会一次性成为十二个平台上的同一个脱敏
漏洞；只有回执 id 被记录。

按 kind：

- **team** —— 协调器的 `steer` 在尝试实时投递**之前**先持久化回执，所以"此刻没有
  挂上实时控制"是耐久路径在正常工作，不是失败。它会扇出给每一个还能行动的子
  run；只 steer lead 会让 worker 继续按刚被纠正的指令跑下去。
- **agent-turn** —— 会话自己的实时输入通道，它自带 PII 门。
- **delegation** —— 转发给正在承载这份工作的子 run。
- 其余 —— `unsupported_for_kind`，于是没有任何卡片会渲染一个不可能生效的按钮。

**无法应用的 steer 是降级，不是拒绝。** 两者不同：拒绝意味着用户的消息已经被消费
掉了，降级意味着它完好无损、仍然由用户支配。`steer_degraded` 让 IM 路径把文本交还
给普通入站管道，由它作为一轮排队 —— 于是一次纠偏永远不会被丢掉，也永远不会被发两
次。没有这个区分，每一个调用方都只能在这两种失败之间二选一。

从线程里够到它只需要一条新的匹配规则：注册项可以按**前缀**匹配（`steer: …` /
`调整：…`），因为 steer 带载荷，而既有的精确标签规则做不到。前缀命中刻意**不**消
费注册 —— 按钮是一次性的，但一个人在一次长 run 的生命里会说好几句纠偏。

### 转交给人

简报是**投影，不是表**。要求什么、谁在要、做完了什么、试过什么、卡在哪、还有什么
决定悬着、产出了什么 —— 这些日志里全都有，把它们抄进一条交接记录只会制造第二个
真相源，而它在 run 一动就过期。

两个现成的信封都不合适。`HandoffEnvelope` 是一次 run 内部的父→子交接，其校验器拒
绝 URL 和绝对路径：对机器接收方是对的，对一个首要问题是"到底停在哪"的人是错的。
`ThreadHandoffTicket` 迁移的是会话在**宿主**之间的位置，它对谁拥有这份工作只字未
提。

交接**不会终结委派**。承诺仍然开着，它汇报的线程仍然是那个人作答的线程，而交还是
同一个 run 上的 `resume`，不是一次新请求。交还时附带的批注作为 steer 传递，经过与
其他每一次纠偏相同的门。

两条边是承重的：

- 记录 interrupt 之后指派失败 → 解回 interrupt 并恢复 run。一个停在没人被告知的
  人身上的委派，比根本没有交接更糟。
- 超时的交接是**标记，不是过期**。`recoverPendingRunInterrupts` 会过期一切超过截止
  时间的项，这对工具授权是对的，在这里是错的：过期会悄悄取消一个人仍然拥有的工作
  的指派，并让 agent 在别人做到一半的任务上继续跑。恢复现在按 interrupt 类型分支。

### 在发起 run 的那个界面上问计划

`resolveGatePolicy` 是一张二值映射：交互式阻塞，其余都算 headless，而 headless 的
计划门 fail fast，理由是"没有人时批准毫无意义"。这个前提对凌晨三点的定时 run 完全
正确，对 IM 则是假的 —— 线程那头有人，而且他们要作答的那套审批机制早就存在。

第五个 `GateBehavior`——`"delegate"`——补上了它。提供 delegate 就是调用方"有一个可
达的人"的**证明**，也正是它翻转策略；没有投递目标的派发继续 fail fast，因为宣称一
个自己无法服务的通道会把一次响亮的失败变成一次沉默的挂起。只有 `planApproval` 移
动：deadlock 和 budget 本就设计成无限阻塞，把它们交给卡片只会让 run 停在一个任何
答案都解不开的问题上。

卡片与工具授权卡形状相同 —— 同一个 registry、同一套 binding 机制、同样的 fail-
closed 姿态 —— 因为不同的只有它说什么、以及一次拒绝携带什么。计划拒绝的反馈会落进
lead 现成的改稿循环，于是聊天线程里的一句回复就成了下一版的修改指令。

### `retry` 铸造替身；已终结的日志保持最终

形状就是恢复策略已经在用的那个：一个用 `parentRunId` 挂上去的**新** run，日志写在
那里，已终结的行不动。日志仍然拒绝终态之后的任何事件 —— 这条不变量没有被放松，整
个设计正是从守住它推导出来的。

因此已终结 run 留下的凭证是**行上的印记**而不是事件（`ExecutionRun.retry`）。它带
着命令的幂等键和替身的 id，这正是"平台重投的那一次按下"能回答"替身已存在"而不是又
分叉一个的原因。带着**不同**幂等键的按下会被拒为 `already_retried` 而不是接受：一
个承诺有两个活着的后代，就没人说得清"它"是哪一个，正确的答案是去重试那个替身。

"铸一个新 run"对每个引擎含义不同，所以这个接缝是**注册表**
（`registerRunRetryHandler`）而不是 switch。这也诚实地回答了问题的另一半：
`allowedActions` 直接问注册表"这个 kind 到底有没有重新派发"，没有就不提供按钮。三
个条件共同把关 —— 已终结、已注册、尚未重试过 —— 而 `completed` 被刻意排除：重做已
经成功的工作是一个新请求，不是对这一次的重试。

有两个 kind 注册了：

- **workflow**（以及 `scheduled`）—— 走既有的运维重试 `retryWorkflowRun`，所以这是
  增加一个调用方而不是第二条重试路径。它多给了桌面历史视图不需要的两样东西：种子
  run 的 `triggeredBy`，让从"提出请求的那个会话"重试的 run 继续汇报回那里而不是无
  声启动；以及 `onAdmitted`，让控制命令在 run id 被持久预留时就返回 ——
  `executeDeployedWorkflow` 是在**完成**时才 resolve 的，等它会把控制门的按 run 锁
  持有整个工作流那么久。
- **delegation** —— 它自己不执行任何东西，所以它重试最近一个已终结的子 run，并把替
  身**认领到承诺上**。挂在失败的子 run 下面会让第二张卡片从人正在看的那张上漂走。

`agent-turn`、`team`、`goal`、`plan` 刻意什么都不注册。一次 agent turn 的替身是一条
新的入站 turn，而不是同一个 run 的新一次；而 team/goal/plan 的重试需要重新推导已终
结行上没有的目标与权限上限 —— 重新推导上限恰恰是重试会悄悄放宽原 run 权限的方式。
它们的卡片不显示重试，这正是"这里没有任何东西能重启它"的诚实呈现。

workflow 重试的父子链接由桥从新 run 已经持久化的 `lineage.retryOfRunId` 推导，而不
是跟按按钮的人协调。因此从桌面历史视图发起的重试与走控制门发起的重试进入同一条链。

## 复用的所有权

没有第二套执行日志、控制门、审批 registry、权限模型或出站队列。本决定扩展的是
`executionRuns` / `executionRunEvents` / `executionRunBindings` /
`executionRunInterrupts`、`executeRunControlCommand`、
`lib/connectors/hitl/approval-registry.ts`、受治理的出站网关，以及 run 呈现
runner。只需要一个 Dexie 版本（**v176**），且是纯索引变更、无回填：没有
`parentRunId` 的行不出现在索引里，这正是对的 —— 它们是根。

## 兼容与回滚

每个新字段都是可选加法。`delegation` 是新 kind，所以没有任何既有 run 的形状或行为
发生变化。`steer` 只对三个真有 steer 轨的 kind 出现在 `allowedActions` 里，`retry`
只对注册了重新派发的 kind 出现 —— 空注册表逐字节复现此前的行为。
`ExecutionRun.retry` 是可选、非索引列，不需要自己的 Dexie 版本。`retryWorkflowRun`
仍然默认 `triggeredBy: { source: "ui" }`，桌面历史视图不变。
`resolveGatePolicy` 默认**没有**审批通道，所以每个现有调用点逐字节保持原行为。回滚
不需要反向迁移；没有委派行时 v176 索引完全惰性。

## 后果

被委派的任务成为一等对象：它作为一个整体汇报、活过启动它的进程、可以在不被杀掉的
前提下改向、可以在不结束的前提下易手。代价是对开放委派的一次对账扫描、每个被提升
的轮次多一行 run，以及一套大到必须逐动词回答"哪些 kind 真的能做这件事"的控制词表
—— 这正是 `unsupported_for_kind` 和 `steer_degraded` 作为两个不同答案存在、而不是
合成一句泛化拒绝的原因。
