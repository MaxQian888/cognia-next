# ADR 0232 — 长运行只给预估，不做预算

**状态：** 已接受
**日期：** 2026-10-17
**关联：** ADR-0019、ADR-0022、ADR-0090、ADR-0165、ADR-0188、ADR-0230

## 背景

用户启动长 Agent 运行（`/goal`、Agent Team、best-of-N、Bot、定时任务）时，
在运行结束前无从知道它大概要花多少钱、跑多久。而从历史回答这个问题所需的
数据都已存在：

- `sessionUsage` 是唯一的用量账本（ADR-0165），每行带 `runId`、`surface`、
  `model`、`providerId`、输入/输出/缓存读/按 TTL 拆分的缓存写 token，以及
  冻结时的价格。
- `executionRuns` 为每次运行记录 `kind`、`startedAt`、`endedAt` 和终止状态
  （ADR-0090）。
- `lib/usage/pricing.ts` 可按当前价格为任意模型的 token 计价。
- 外部 harness 历史以 `imported` 行索引，从不计入预算。

费用控制也已覆盖：成本预算闸门、网关票据与透传账本、Router + Fusion 账本
（ADR-0188）、`RunBudgetGovernor`（ADR-0090），以及 goal、team、best-of-N、
Bot 各自的上限。曾考虑过更重的方案：逐请求预留、梯度提升分位数回归、
conformal 校准、剩余成本预测、预算内成功概率和模型预测控制。该方案被否决：
控制部分与现有机制重复；学习部分需要的带标签轨迹远超单机安装所能产生的量，
没有 Python 运行时来训练或推理，且多数运行没有可验证的成功标签。

## 决策

Cognia 新增一个只读预估器，用于给出心理预期，从不改变执行。

**只做提示。** 预估不拦截、不预留、不路由、不压缩、不重规划、不停止任何运行。
现有预算机制仍是唯一的强制手段。不展示成功概率。

**展示位置。** 仅在长运行的启动入口展示：新建目标对话框和 `/goal` 创建后的
系统卡片（斜杠命令没有确认步骤）、Squad 的开始按钮旁、best-of-N 启动对话框
（按各候选的 agent 汇总）、定时任务表单，以及 Bot 的运行按钮旁（休眠，见下文）。
普通聊天发送不展示。

**展示内容。** 费用、token 和墙钟耗时各给出典型值与 P10–P90 区间，附可信度
标签和同类运行中途停止的占比。费用一律写作“按 API 价”：对 API Key 用户就是
账单，对订阅用户是等价金额，因此无需判断用户类型。不从 token 推算额度百分比。

**样本。** 一个样本是一次已结束的运行，汇总其整个运行树（含子运行和队友）。
样本整体保存各类 token 数，而不是分别取分位数。每个样本按启动所选模型（未指定
时用样本自身的模型）在 `lib/usage/pricing.ts` 的当前价格计价，再对这些样本总额
取分位数，因此价格变化不会扭曲历史。取消、失败和触及上限而停止的运行都计入；
预估的含义是“这类运行跑到结束大概花多少”。不做删失建模。

各入口的历史存放位置不同，因此各有一个样本构造器（`lib/usage/run-estimate/samples.ts`）：

| 入口 | token | 状态与耗时 | 模型 |
|---|---|---|---|
| goal | `goal:<goalId>` 下的用量行 | goal 记录 | goal 存续期间该会话聊天行的主模型；无头 goal 没有 |
| team（Squad） | `team:<runId>` 下的用量行 | team 的 `ExecutionRun` | 用量行的主模型 |
| best-of-N | 无：候选不写用量行 | 每个候选 | 候选的 agent |
| 定时任务 | 任务创建的会话（`origin.kind === "scheduled-task"`），不含定时 goal | 用量行的时间跨度 | 用量行的主模型 |
| 外部会话 | 每个来源会话的导入行 | 用量行的时间跨度 | 用量行的主模型 |

best-of-N 候选只有冻结的美元金额，无法按现价重算；一个候选为一个样本，启动 N 个
时相乘。Bot 原生 agent 轮次完全不记录用量，因此 Bot 入口是有意休眠的：在
`RunEstimateSurface` 上注明，在 Bot 运行按钮旁显示“暂无估计”，并由
`estimate.test.ts` 固定。这两个缺口都是账本问题（ADR-0165），另行修复；Bot 轮次
写入用量行后，再为 Bot 入口增加样本构造器。

**分桶。** 启动入口 × harness × 模型族。查询时从细桶回退到 入口 × harness，再到
仅入口；查询无法填写的键直接跳过，而不是去匹配“未知”。模型族对具体 model id
做归一（`claude-sonnet-4-5-20250929` → `claude-sonnet`）。运行记录都不存
harness，因此只在来源带有时恢复（队友的 `runtime`、best-of-N 候选的外部 agent
preset、导入的 `sourceId`）；Codex 的各种形态映射为同一个键。无法恢复 harness
的运行只进入不区分 harness 的桶。曾考虑按 prompt 长度和是否绑定仓库细分，最终
放弃：只有 goal 记录了 prompt，加上这两个维度几乎会让所有桶为空。特征只来自
启动配置和已有元数据，预估过程不调用模型。

**外部历史。** 导入的 Claude Code、Codex 会话每个会话计为一个样本，放入独立的
“外部交互会话”入口桶。只在同一外部 harness 的启动中、且在该入口自身在此 harness
上的历史之后才参考，不混入 goal、team 等桶；仍不计入预算。

**漂移。** 只使用最近 90 天的数据，按 30 天半衰期加权。

**可信度。** 由样本数不少于 5 的最细桶给出结果：5–19 个标为“样本较少”，20 个
及以上标为“基于 N 次运行”。没有任何桶达到 5 时，由样本最多的桶给出并标为
“粗略”（阶段 3 起由内置先验填补）。没有任何可用来源时显示“暂无估计”。分位数
按权重计算（中点插值），越近的运行权重越大。

**计算。** `lib/usage/run-estimate/load-samples.ts` 在启动时按需读取窗口内的
现有表（`sessionUsage`、`chatGoals`、`executionRuns`、`agentTeamChildRuns`、
`bestOfNRuns`、`sessions`），配合五分钟内存缓存，其余由纯函数完成。不新增
Dexie 表，不升 schema。

**运行中。** 运行界面显示“已花 X / 典型总量 Y”，超出该桶常见范围时加以标注。
不做剩余成本模型。

**内置先验。** 用 `packages/eval-core` 对每个 harness × 模型族运行一组固定的
长任务，产出分位数 JSON 随应用发布，像价格目录一样重新生成并受 gate 约束。
先验只填补本机历史无法覆盖的桶。

## 阶段

1. 本机分桶预估器及其在长运行启动入口的展示。
2. 运行中的“已花 vs 典型”对照。
3. eval-core 先验、生成脚本及 gate。

## 后果

- 预估如实交代依据：每个数字都带样本数或“粗略”标签，不以任何形式作为保证。
- 新安装在阶段 3 发布先验或本机历史积累前，大多只显示粗略预估或暂无估计。
- 由于计入中途停止的运行，区间描述的是跑到终止的成本，而非成功所需成本；
  展示中途停止占比以让这一差别可见。
- 若将来带标签的结果足够多（如来自验收检查），可在新的 ADR 中重新考虑
  感知成功的预估。
