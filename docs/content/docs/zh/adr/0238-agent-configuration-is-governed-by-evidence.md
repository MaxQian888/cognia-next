# ADR 0238 — 智能体配置以证据治理

**状态：** 已接受
**日期：** 2026-10-20
**相关：** ADR-0122、ADR-0189、ADR-0198、ADR-0236、ADR-0237

## 背景

智能体作为指令加载的内容分散在许多所有者手中：仓库指令文件（`CLAUDE.md`、`AGENTS.md` 及其分层）、
`.claude/agents` 下的 Markdown 智能体文件、技能、角色及其变体、子智能体与团队模板、自定义模式、预设、
工作区指令、默认系统提示词，以及内置的提示词槽位。ADR-0236 把这些文本放到了统一的提示词中心之后，
每段文本都只有一个所有者；但还没有任何机制去问：这些文本现在还对吗？

治理要回答三个问题，每个问题需要不同的证据：

1. **这条规则该不该存在？** 规则可能过时（大写强调、思考脚手架、针对旧模型的变通写法），可能脆弱
   （路径已不存在、脚本已改名、两个文件说法不一），也可能从未被用到。
2. **它是否被遵守？** 智能体不理会的规则，写得再好也没有起作用。只有智能体过去的工具调用能回答这个问题。
3. **修改后是否更好？** 在遵守情况或评测给出结论之前，一次修改只是一个假设。

### 对原始材料的评估

设计参考了一组面向 Claude Code 的 Anthropic 与社区工具。它们各自解决了问题的一部分，但都不能原样装进
Cognia：它们假定单一运行时、磁盘上的工作树和特定的模型家族，其中几个还会读取可能含有密钥的文件。

- **`prompt-audit.md`**（Anthropic，Apache-2.0）是最有价值的部分。它给出了具体的反模式分组，明确列出
  “看似冗余实则承重”的**保留清单**，每条发现都报告位置、证据、模式、理由、置信度和处理方式，只对高、中
  置信度提出修改，冲突只按版本控制的日期排序，绝不让文件对自身的描述来做裁决。它的局限在于：针对某一代
  Claude 模型调校、读取工作树、结论来自单个模型的判断，并且出于密钥考虑刻意跳过 `settings*.json`、MCP
  配置和钩子配置——因此它无法判断一条文字规则其实已经由钩子强制执行。**采纳**为审计方法，原文未改动地
  放入仓库并固定在 `9d630808e4add0a7146de4af9384155d5dee350a`，并做了改编（见下文）。
- **`claude-md-management`** 通过修订和追加保持指令文件最新。单独使用时文件只会越来越长：没有删减文本的
  反向力量。**仅采纳**“通过所有者写回结果”这一点，绝不做自动追加。
- **`claude-md-doctor`** 通过读取会话记录来衡量指令是否被遵守，这是问题 2 唯一的证据来源，但它读的是
  Claude Code 的会话记录。**采纳**为基于 Cognia 自身存储的工具调用的确定性回测，跨运行时归一化，支持
  用户标记误匹配，并给出上下文稀释信号。
- **`skill-creator`** 用测试提示词评估技能。Cognia 已经有包含数据集、评分器和 pass@k 的评测实验室。
  **采纳**为通过 `ctx.eval` 进行的评测 A/B，而不是再造一个评测运行器。
- **`hookify`** 把规则变成 Claude Code 钩子。Cognia 插件本来就能收到 `onPreToolUse` / `onPostToolUse`。
  **采纳**为插件自有的强制规则；用户的 Claude Code 钩子文件从不被写入。
- **`ngmeyer/claude-md`** 是一套主观的模板，选择背后的证据很少。**不采纳**；其中关于篇幅和结构的建议只
  保留为“技能过长”信号。
- **`claude-code-setup`** 推荐初始配置。在 Cognia 中这由首次引导（ADR-0122）负责。**不采纳。**
- **`plugin-dev`** 是 Claude Code 的插件开发套件。Cognia 有自己的 SDK。**不采纳。**
- 同一材料中的**“方案 B”**——一个治理插件，用 `normalize.py` 把各运行时的文件解析成统一的发现 JSON——
  输出是对的（所有来源共用一种发现结构），输入是错的：一个解析配置文件的插件必然也要读取含密钥的文件。
  **采纳**统一的发现模型，但建立在宿主读模型之上，插件从不解析文件。

## 决策

### `ctx.agentConfig`：受治理的读模型，经由所有者写回

新的插件命名空间暴露智能体的配置，而不暴露其存储方式：

- `listSurfaces` / `readSurface`——提示词中心列出的所有配置面（经由其所有者适配器）以及 Markdown
  智能体文件，附带加载顺序、分层、路径、编辑能力、版本前置条件；对技能还附带使用与校验信息。
- `readFacts`——对已有强制措施的**结构化**摘要：钩子的事件、匹配器、类型和安全标签（可执行文件的
  基本名，绝不含参数、环境变量、请求头或提示词文本）；权限规则的工具、模式和判定（记住的命令中
  携带的凭据会被遮盖，仍可能泄露的条目直接丢弃）；MCP 服务器的 id、传输方式和启用状态；技能数量。
  设置文件本身从不返回。
- `checkReferences`——指令中提到的路径是否存在于工作区根目录内（符号链接只报告、不跟随；根目录之外的
  不探测），以及包脚本是否已定义。
- `readProvenance`——来自版本控制的逐行提交与时间，不含作者。
- `redactForModel`——宿主的 PII 脱敏，保持行号不变；无法确保安全时返回 `null`。
- `applyEdit`——通过所有者写入完整的新文本（文件、来源为 `plugin` 的提示词中心覆盖，或内置资源的自定义
  副本）。每个配置面单独弹出一次确认，显示插件提供的摘要；版本过期时拒绝写入。

权限为 `agent-config:read` 和 `agent-config:write`（敏感；写入需要确认）。`ctx.eval.runDataset`
新增 `cwd`，并按工作区根目录校验，使评测针对某个仓库的指令运行。顺带修复了两个宿主缺陷：插件的
`denyReason` 现在能传达给模型；提示词中心支持 `?resource=&workspace=` 深链接。

### 配置治理插件

一个第一方、浏览器内置的插件（`plugins/config-governance/`），只基于公开 SDK 构建。所有来源共用一种
发现模型，因此一条被信号、引用检查和模型同时报告的规则，是一条带三个来源的发现。

**审计（问题 1）。** 对每个配置面：切分为规则单元；把 prompt-audit 的信号作为线索运行；检查提到的路径
和脚本；用版本控制为每行标注日期；然后——只有在配置了模型且文本可以脱敏时——请求模型判断并**校验**：
模式必须已知、行号真实存在、证据确实引自这些行、改写必须给出替换文本、移动必须指向已知目标，否则降为
待审阅。模型看过但未确认的信号会被丢弃；没有模型时，它们保留为低置信度的待审阅项。冲突检查对同时加载
的配置面中的规则对只问一次，仅在日期能排定先后时修改较旧的一方，且绝不自行削弱禁令或加入命令。修改块
基于原始文本计算，而非脱敏副本；覆盖脱敏行的写入会被扣留。冲突和失效事实类修改**仅作提议**，从不替
用户选中。

对方法的改编：目标模型是一项设置，而非默认 Claude，关于模型行为的判断以目标模型为前提；钩子和权限规则
以宿主事实的形式提供；请求代码（方法中的第 4 组）不在范围内，因为用户不编写 Cognia 的请求构建器；所有
面向模型的措辞都是提示词中心的槽位。

**遵守情况（问题 2）。** 可能涉及工具使用的规则通过一次模型调用转换为检查项——`forbid`、
`require-after`、`require-before`，作用于 shell / 编辑 / 读取调用，带命令模式和路径通配，范围为本轮或
本会话。可能引发灾难性回溯的命令模式会被拒绝，且只在命令行的有限前缀上运行。回放在本地进行、不产生费用：
统计适用次数、遵守、违反、样例，排除用户标记的误匹配，并比较长会话前半段与后半段的违反率。未被遵守的
规则成为 `enforce` 发现；后段失效的规则成为稀释提示（更可能需要调整的是位置而非措辞）；在足够多会话中
从未适用的规则被标记为可能已过时。

**强制。** 用户可以把一个检查项采纳为某个工作区或所有会话的规则：*提醒*会把规则附加到工具的文本结果中；
*阻止*会拒绝调用并以规则作为理由。`require-after` 规则无法阻止尚未发生的调用，因此总是提醒。规则运行在
插件自己的钩子中，出错时放行，并可通过一项设置整体暂停。

**验证（问题 3）。** 对每次应用的改动：在改动之前创建的会话和之后创建的会话上回放相同的检查项；并在该
工作区以基线和候选两次运行同一个评测数据集。每次对比在给出“更好”或“更差”之前，先说明数据是否充足。

**界面与调度。** 侧栏视图包含概览、发现、遵守情况、强制、验证和清单标签页，并把每个配置面链接到其提示词
中心条目；`/governance [audit|adherence|open]` 命令；命令面板快捷操作；两个只读智能体工具
（`config_governance_report`、`config_governance_adherence`），配套一个告诉模型“不能应用修改”的技能；
五个提示词中心槽位；以及每周一次的漂移检查——不调用模型重新审计，在配置面发生变化或出现新的高置信发现
时通知用户——在用户恢复之前保持暂停。存储有界，保持在插件配额之内，且从不保存完整的配置面文本。

## 影响

- 治理工具经由所有者而非文件读取配置，因此对仓库文件、技能和角色的处理方式一致，并且从结构上就不可能
  读到凭据。
- 一条发现是证据加提议；修改按配置面逐个确认后才写入。审计本身从不改动任何内容。
- 插件注册了 `onPostToolUse`，启用期间每次工具调用都会经过工具结果审阅；没有采纳的规则时钩子立即返回。
- 遵守情况回测只能看到工具调用。关于语气或判断的规则会被报告为“不可检查”，而不是找一个代理指标。
- 评测 A/B 会调用模型，且只会由用户发起。

## 考虑过的替代方案

- **直接安装 Claude Code 插件。** 它们针对单一运行时及其文件布局，其中两个还会读取含密钥的设置。否决。
- **在插件中解析配置文件（方案 B）。** 否决：插件将不得不读取含密钥的文件，并重复每个所有者的存储规则。
- **直接采信模型的结论。** 否决：每个判断都要对照文本、仓库和版本控制进行校验，低置信度从不触发修改。
- **用 Claude Code 钩子实现强制。** 否决：钩子文件属于用户且可能含有密钥；插件钩子覆盖 Cognia 驱动的所有
  运行时。
