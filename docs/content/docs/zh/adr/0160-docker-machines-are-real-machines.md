# ADR 0160 — Docker 机器是真的机器

**Status:** Accepted  
**日期：** 2026-08-31  
**基于：** [ADR-0020](./0020-computer-use-completeness)、[ADR-0143](./0143-device-console)

## 背景

`lib/sandbox/` 早就搭好了一个与厂商无关的机器管理器骨架：`SandboxProviderAdapter`
有 11 个操作，11 个规范化生命周期状态，一张逐操作的禁止状态表，以及一张能力矩阵，
其中的 `false` 是契约而不是提示。缺的是一个能真正承载这些操作的适配器。

底下有三处是错的。

**容器是用 `docker run --rm` 创建的。** 这让 `docker stop` 顺带把容器删掉，于是停止
和删除塌缩成同一个操作，用户写在机器里的文件每次停止全部丢失。适配器的 `delete`
方法调的是 `client.stop()`，看起来对，只是因为有 `--rm`。一台每次停止都会失忆的机器
不是机器。

**注册表只把容器记在进程内的表里，而且每次都新建。** 容器名由连接 id 确定性推导，
所以一个在非正常退出后活下来的容器会把名字占住，之后每一次 `docker run --name`
都失败。那条连接从此再也起不来，UI 上只能显示一条 Docker 错误。

**`cua-desktop` 档位是被撤回的**，理由在三条休眠轴上都有记录：绑定桌面只能证明远程
GUI 隔离，shell 与文件操作并未被沙盒化。

## 决定

### 容器要留下来，并且是接管而不是重建

`--rm` 去掉了，删除变成显式操作。`docker inspect` 成为生命周期状态的唯一真相源，
取代那张只记录「我们要求了什么」而非「Docker 做了什么」的进程内表。每个入口都先按
确定性名字 inspect，然后接管它找到的东西：暂停的就 unpause，停止的就 start，运行中
的直接复用，只有真的不存在才创建。

应用退出时丢弃缓存的驱动连接，容器继续运行。用户启动过的机器，下次打开应该还在。
代价是空闲机器会持续占用资源，这一点 UI 上说明了。

### 挂起是 `pause`，绝不是 `stop`

`docker pause` 会 SIGSTOP 容器内所有进程并保留内存，桌面会话因此得以存活，恢复后
还是同一台机器。`docker stop` 做不到，用它冒充挂起等于报告了一台其实悄悄重启过的
机器。Docker 把暂停的容器报为仍在运行，把停止的报为未运行，两者可区分，并有一个
实机测试钉死。

### `cua-desktop` 的撤回是被证据解除的，不是被删掉的

撤回理由的前提是没有任何东西能把 shell 与文件操作带进容器。`docker exec` 能，而且
这是实测出来的而不是论证出来的：`docker exec <id> hostname` 返回的是容器 id 而不是
宿主的，容器内 `/etc/os-release` 在一台 macOS 宿主上报告的是镜像的发行版。四个默认
跳过的测试让这条主张可以随时复验。

该档位依然是有条件的。它需要一个所属 provider 确实支持 `workspaceExec` 的已绑定
连接，所以 `cua-cloud` 与 `lume` 和之前一样被拒绝；没有这样的连接时，档位保持
「列出但不可用」，而不是隐藏。

### 逐次策略只做背书，不做事后强制

Docker 在创建容器时就把网络模式与 cpu、内存上限定死，`docker exec` 无法为单条命令
收紧其中任何一项。因此，一个要求比机器实际配置更强隔离的请求会被以
`policy-not-attested` 拒绝，而不是照跑，沿用 e2b microvm 档位已有的先例。照跑意味着
在比调用方所以为的更弱的隔离下执行，而这正是沙盒存在的意义所要防止的失败。

宿主路径要么被拒绝，要么被重定位到工作区挂载点，绝不原样透传。宿主路径在容器里
什么也不是，更糟的情况是指向了别的东西。`allowlist` 网络被当作容器标志无法提供的
一种隔离，而不是被悄悄降级为 `off` 或放宽为 `on`。

### 能力默认值带上修订号

存储下来的能力矩阵此前在读取时只能收窄。这条规则保护的是握手收窄，也就是对端实际
支持的比声称的少这种情况，但它同时意味着 `false && true` 仍然是 `false`：一行在适配器
出现之前写下的数据，永远学不到现在已经有适配器了。所有既有数据库都会永远把新控件
显示为灰色，只有全新创建的库看起来才是对的。

`capabilitiesRevision` 把这两种主张分开。默认值是应用自己的真相，跨版本可升可降，
所以落后于当前修订号的行会从默认值重算。握手收窄仍然是逐连接的，并且在同一个修订号
内依然只减不增。

## 影响

- 停止机器会保留它和它的文件系统。删除是唯一的破坏性操作，并已如此标注。
- 机器比应用活得久。空闲机器在被停止前仍然占用 cpu 与内存。
- 新增 7 个 `cua_sandbox_*` 命令。它们是 `target: "client"` +
  `transports: ["internal"]`，不走 companion 线，始终作用于运行渲染端的那台机器。
  `exec` 与 `read_file` 被记为高风险，因为它们能在机器内运行任意命令、读取任意路径。
- 绑定到一台配置了工作区挂载的 Docker 机器的会话，其 `Bash`、`Read`、`Edit`、
  `Write` 都在机器内执行。没有挂载时，带可写路径的请求会被拒绝，而不是被悄悄改道。
- 不接入任何云控制面。`cua-cloud` 与 `lume` 保持空能力矩阵、无适配器，对它们的任何
  操作都会拒绝。适配器注册表就是未来 provider 要填的那道接缝。

## 备选方案

**保留 `--rm`，把能力矩阵收窄到与之匹配。** 诚实，而且工作量小得多，但那等于接受一个
无法在两次运行之间保存状态的沙盒。矩阵将不得不彻底去掉 `stop`，并在 UI 上说明。

**做通用的宿主路径到容器路径翻译。** 暂时否决。没有声明挂载点的路径翻译，是在猜一台
机器可以访问哪些宿主目录，猜错就会写到调用方从未指名的地方。声明单个挂载点、挂载点
之外一律拒绝，是有边界的那个版本。

**通过重建容器来强制逐次策略。** 技术上可行，否决：一次 `Bash` 调用如果悄悄销毁并
重建它所运行的那台机器，就会丢掉这个档位存在的意义，也就是会话本身。
