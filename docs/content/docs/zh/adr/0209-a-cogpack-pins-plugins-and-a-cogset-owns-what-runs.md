# ADR 0209 — 齿轮包锁定插件，齿轮组决定运行什么

**状态：** 已采纳
**日期：** 2026-09-30
**相关：** [ADR-0100](./0100-unified-template-platform)（包封装格式）、[ADR-0164](./0164-templates-squads-and-commands-are-portable-and-iterable)（发布者身份与信任账本）、[ADR-0030](./0030-character-pack-overlay-capability)（独立签名包导入）、[ADR-0144](./0144-workspace-as-the-unit-of-work)（工作区）、[ADR-0001](./0001-backup-schema-v3)（备份）、[ADR-0027](./0027-mobile-offline-and-discovery)（镜像客户端）

## 背景

用户想要 Minecraft 玩家从整合包里得到的东西：一个文件就能装好一套经过验证的插件组合，并且能保存多套组合、在它们之间切换。本 ADR 之前，相关零件各自存在，但没有一个是这个东西。

- **市场预设**（`lib/plugin/package/github-marketplace.ts`、`lib/plugin/marketplace/preset-install.ts`）可以一键安装某个 GitHub 目录里的一组插件。成员只写名字、不锁版本，总是安装最新修订；不带配置和启用状态；只能在仓库里手写。
- **依赖**（清单中的 `dependencies` / `optionalDependencies`）会为已安装的插件排序并自动启用（`lib/plugin/core/load-order.ts`），但 GitHub 安装路径不会安装缺失的依赖。
- **数据备份**（`lib/data/build-package.ts`）导出插件记录但不含插件代码，恢复时强制 `enabled` 为 false，而且它是整个应用的备份，不适合交给别人。
- **没有任何地方记录已安装插件的来源。** GitHub 安装器解析出 commit SHA 后就丢弃了；git WASM 安装器根本不知道自己克隆的是哪个提交。插件组合无法带着锁定信息导出，因为锁定信息从来没被保存过。
- **插件刻意不按工作区区分。** `lib/workspace/capability-overlay.ts` 解释了原因：`plugins.enabled` 是运行时的加载状态，是激活的*结果*；按工作区覆盖它，就会改写那个记录“实际在运行什么”的字段。要正确实现，需要一个独立于加载状态、专门承载*意图*的东西。

有两个词已经被占用。`lib/plugin/core` 中的 “profile” 指运行时宿主档位（`PluginRuntimeProfile`：browser、tauri、mobile）；“pack” 指角色包、主题包或风格包。新名字取自 Cognia 自己的 “cog”（齿轮）：插件是机器里的一个齿轮；**齿轮组（cogset）**是一起转动的一组齿轮，像自行车换挡一样，换一组齿轮就换一种运转方式；**齿轮包（cogpack）**是打包好、可以交给别人的齿轮组。

## 术语

- **齿轮包（Cogpack）**：带签名、有版本、可分享的文件（`.cogpack`），列出一组插件，每个都锁定到确切修订，并带有每个成员的非机密配置。每个成员都应当运行；标记为 `optional` 的成员可以由导入方跳过。_避免_：整合包、modpack、plugin pack、bundle、preset。
- **齿轮组（Cogset）**：本地具名的插件集合，这些插件应当一起运行，并带有每个成员的非机密配置。一个宿主上同一时间最多应用一个齿轮组。_避免_：配置档、loadout、profile（运行时宿主档位）、instance。
- **常驻集（Always-on set）**：在任何齿轮组下都保持启用的插件。只存在于本地宿主，永远不会随齿轮包分发。
- **安装来源（Install origin）**：已安装插件的来源，锁定到实际安装的内容（提交、插件仓库版本、安装包哈希、Open VSX 版本及 VSIX 哈希、“随应用提供”或“本地”）。
- **生效齿轮组（Effective cogset）**：当前应当运行的齿轮组：会话覆盖，否则是当前工作区的绑定，否则是全局选择。
- **预设（Preset）**：含义不变，指市场目录中具名、不锁版本的插件列表。预设可以另存为齿轮组，但它不是齿轮包。

## 决策

### 1. 齿轮包对可重新获取的插件写引用，其余内嵌

齿轮包是一个 zip，其清单采用 RFC 8785 规范化 JSON（与角色包签名所用的规范化方式相同），每个文件都有 sha256 记录，解压经过加固，并对规范化清单做 Ed25519 签名。归档部分——确定性输出、路径/大小/数量/压缩比限制、逐文件校验、未声明文件规则和签名校验——与模板包共用 `lib/packaging/signed-zip.ts`；两种格式各自维护自己的清单。

清单（`lib/plugin/cogpack/manifest.ts`，严格校验：本版本不理解的内容一律拒绝）包含 `schemaVersion`、`kind: "cognia.cogpack"`、`id`、`version`、`name`、`description`、`compatibility.minHostVersion`（导出方的应用版本，内置成员需要至少该版本），以及每个成员一个条目：

- `id`、`name`、`version`、`optional`；
- `source`，取以下之一：
  - `builtin`（随应用提供）；
  - `github`（owner、repo、subdir、完整提交）；
  - `git`（https URL、完整提交）；
  - `registry`（插件仓库 URL、版本、校验和）；
  - `url`（安装包 URL、已校验安装包的 sha256、签名 URL 和公钥）；
  - `openvsx`（namespace、name、版本、VSIX sha256、目标平台）；
  - `embedded`（插件目录位于 `plugins/<id>/` 下，每个文件都有哈希）；
- `config`：非机密配置；
- `secretFields`：导入方需要填写的 `secret: true` 配置字段，只有字段名。

只有当成员记录的来源可重新获取、*并且*记录时的版本与当前安装版本一致时才写引用，否则直接内嵌。这就是 Modrinth `.mrpack` 中 downloads 与 overrides 的划分。通过 VS Code 文件安装的插件无法随包携带（目录安装器无法重新安装解包后的扩展），会被明确列出，而不是悄悄丢弃。

机密信息永远不会被打包。`secret: true` 的值目前与插件的其余配置保存在一起（`plugin-config-form.tsx` 中有说明），因此导出器会去掉所有机密字段（`lib/plugin/core/config-secrets.ts`），只写入字段名。导出对话框会列出即将写入的每一个非机密值，并允许按成员排除配置，因为没有标记为 secret 的字段里也可能有隐私内容。

### 2. 每次安装都在独立的表中记录来源

`pluginInstallOrigins`（以插件 id 为键）为每个已安装插件保存一条记录。它是一张独立的表而不是插件记录上的字段，因为有些安装器根本不写插件记录（HTTP 插件仓库路径交给插件发现来写），而插件发现每次启动都会重新投影插件记录。

每条安装路径都通过 `recordInstallOrigin` 写入：

- GitHub 安装器：先把分支或标签解析为完整提交，因此来源记录的正是实际下载的内容；
- git WASM 安装器：其宿主命令现在可以按指定提交精确检出，未指定时会报告实际克隆的提交；
- HTTP 插件仓库（版本和校验和）、签名 URL 安装包（已校验的哈希）、Open VSX（版本和 VSIX 哈希）；
- 本地目录、本地 WASM 文件、拖入的 VSIX 文件和手动导入的清单（`local`，不可重新获取）；
- 安装包自带的插件（`builtin`）；浏览器内置插件通过 `builtin://` 路径识别，不需要记录；
- 齿轮包导入，额外记录齿轮包的 id、版本和指纹。

记录失败永远不会导致安装失败；没有来源的插件导出时按内嵌处理。在镜像客户端上，安装实际发生在宿主，因此记录会发送到宿主（`plugin_install_origin_record`）。不是由本宿主上的安装产生的记录（配对客户端转发的，或从备份恢复的）会经过 `parseInstallOriginRecord` 校验，检查项与齿轮包成员来源相同（https URL、完整提交 id、sha256 锁定），因为之后的导出会原样锁定记录的内容。被拒绝的记录只意味着该插件导出时按内嵌处理。`lib/plugin/origin/install-paths.test.ts` 会在某个宿主安装命令被未记录来源的模块调用时失败。

### 3. 齿轮组拥有意图，切换由插件管理器执行

`plugins.enabled` 和 `lifecycle.actual` 依旧表示“此刻加载了什么”。齿轮组拥有的是*应当*运行什么，激活它（`lib/plugin/cogset/reconcile.ts`）就是通过 `togglePluginEnabled` → `PluginManager.setPluginIntent` 进行调和，与每一次手动开关走同一条路径，从不直接写那个字段。

切换是**独占的**：

- 目标集合 = 齿轮组成员 ∪ 常驻集 ∪ 两者的必需依赖闭包，由 `lib/plugin/cogset/plan.ts` 预先规划。
- 目标集合之外的插件会被停用（先停用依赖方），不会卸载任何插件。
- 在任何变更之前，先把正在离开的齿轮组中成员的当前非机密配置存回该齿轮组，因此每个齿轮组都保有自己的配置。
- 启用前先应用成员配置（保留插件自己的机密信息），然后按 `resolveLoadOrder` 顺序启用。
- 每个插件的结果都会以结构化字段记录（未满足的依赖及其版本范围、实际找到的版本、循环中的插件），由界面翻译；只有插件管理器自身的失败带有自由文本。某个插件失败时，它停留在管理器留下的状态，齿轮组被标记为“部分应用”；已成功切换的插件不会回滚，“重试”会重新执行调和。缺失的可选成员不会让齿轮组变为部分应用。
- 激活按顺序串行执行。

齿轮组处于应用状态时，手动启用、停用和修改设置都会同步写回该齿轮组（`write-through.ts`，由 `setPluginIntent` 新发出的插件意图事件和宿主级配置变更订阅驱动）。调和本身产生的变更会被忽略。首次运行时，宿主会根据当前已启用的插件创建一个 **Default** 齿轮组，因此开启该功能不会带来任何可见变化。

### 4. 每个插件只安装一个版本

一个宿主上每个插件只装一个版本：运行时的一切都以插件 id 为键。齿轮组成员可以声明 `expectedVersion`；不一致时在激活时报告（仍运行已安装的版本），而且自动更新绝不会安装会让插件偏离当前齿轮组锁定版本的更新，而是改为提示用户。

### 5. 导入齿轮包会生成一个齿轮组

导入（`lib/plugin/cogpack/import.ts`）依次是规划、一次审核、执行安装：

1. 校验文件（`inspectCogpack`）：结构、哈希、签名。
2. 按插件策略判定信任（见决策 6）。
3. 用各来源已有的安装器在锁定修订上解析每个成员（`resolvers.ts`），并与已安装插件对比：已安装且版本一致、版本不同、新增或不可用。
4. 在一个对话框中一次性展示：每个成员的权限、缺失的外部程序和冲突（复用市场安装流程自身的检查）、需要填写的机密字段、齿轮包未携带的必需依赖（只展示，绝不静默安装），以及激活后会被关闭的已安装插件。对于已安装其他版本的成员，用户可以选择安装锁定版本或保留自己的版本（此时齿轮组锁定用户的版本）。

WASM 成员按审核中展示的能力授权安装（`defaultWasmGrantDecision`，即授权面板自身的默认值）。git 成员在不克隆的情况下无法预览，因此在安装完成后立即审核其能力。内嵌成员由宿主写入并安装（`plugin_install_from_files`），走与“加载已解压插件”相同的目录安装器，在阻塞线程上执行。该命令接收审核中展示的成员 id，若树中的 `plugin.json` 指向其他插件则拒绝，因此内嵌成员永远无法替换另一个已安装的插件。以下路径会被拒绝：在不区分大小写的文件系统上会被存成同一个文件的两个路径（`plugin.json` 旁边的 `PLUGIN.JSON`），以及包含 NTFS 流、Windows 设备名或以点、空格结尾的路径；审核同样会拒绝这样的树，因此安装的内容就是审核过的内容。用户输入的机密信息写入插件配置，永远不会写入齿轮组。结果是一个记住来源齿轮包的新齿轮组；激活是可选的，不会强制。未能安装的成员仍保留在齿轮组中，并列为缺失。

导入之前导入过的齿轮包的新版本时，会提供更新对应齿轮组的选项。`update-diff.ts` 比较之前的清单、新清单和当前的齿轮组：上游的变化会被应用；用户在本地改过的成员默认保留用户的版本，除非用户按插件选择新版本。删除齿轮组时也会删除指向它的导入记录，因此之后再导入会新建齿轮组，而不是去更新一个已不存在的齿轮组。删除齿轮组永远不会卸载插件，只会提示可以卸载那些已不被其他齿轮组或常驻集使用的插件。

### 6. 齿轮包默认签名；未签名的可以导入，但会有警告

只要用户保持签名开启，导出时就用 ADR-0164 的发布者身份签名（首次使用时创建密钥），因此模板发布者、插件发布者和齿轮包发布者在信任账本中是同一条记录。导入时显示可信发布者、未知发布者签名或未签名。插件策略的适用方式与插件相同：“要求签名”拒绝未签名的齿轮包，“仅限受信任发布者”还会拒绝未知签名者。导入时信任某个签名者，会把它加入信任账本。

### 7. 工作区可以绑定齿轮组

`Project.pluginCogsetId` 把工作区绑定到齿轮组。生效齿轮组依次为：会话覆盖，否则当前工作区的绑定，否则全局选择；指向已删除齿轮组的引用会被跳过。在工作区绑定生效时进行的切换会成为会话覆盖；切换工作区会清除它。

跟随器（`follower.ts`）在生效齿轮组与已应用齿轮组不一致时进行调和。这类自动切换会等到执行代理（execution broker）中没有任何智能体任务时再进行——它能看到每一轮 AI 执行（聊天、工作流、定时任务、子智能体、团队）——因为在任务运行中停用插件会拿走它正在使用的工具。等待状态会记录为 `pending` 并在界面上展示。手动切换则改为询问用户。

### 8. 各部分在哪里运行

- **齿轮组状态**保存在 `pluginCogsets` 和 `pluginCogsetState` 单例中，以宿主为准，像 `plugins` 一样只读同步到镜像客户端。镜像客户端通过排队发送 `plugin_cogset_activate` 来切换；宿主记录作用范围，交由跟随器执行。编辑只能在宿主上进行，界面会明确说明。
- **无界面宿主**（headless）运行同样的初始化、同步写回和跟随器。
- **齿轮包导入和导出**需要一个有安装器的宿主（桌面端）。
- **备份**（ADR-0001）携带齿轮组、齿轮包导入记录、安装来源以及宿主的选择（常驻集、全局齿轮组），但不携带宿主最近一次应用了什么；恢复时会重新映射插件 id。
- **预设**保留。预设安装完成后，会提供“保存为齿轮组”的选项。

## 考虑过的方案

- **每个齿轮组一个安装目录**（Minecraft 实例式的多版本并存）：否决。插件存储、插件 Dexie 表、钥匙串命名空间和运行时注册都以插件 id 为键，同一插件的两个版本无法并存，除非为运行时重新设计键结构。
- **按工作区覆盖 `plugins.enabled`**：否决，理由同 `capability-overlay.ts` 所述。由齿轮组拥有意图，由管理器执行。
- **叠加式切换**（只启用、不停用）：否决。齿轮组之间会互相渗透，“切换到 X”就不再意味着“运行 X”。
- **齿轮包只写引用**：否决。无法携带本地或私有插件，而且本 ADR 之前的每一次安装都没有来源信息。
- **全部内嵌**：否决。文件会很大，齿轮包会再分发第三方代码，而且会失去引用所保留的出处信息。
- **把预设扩展成齿轮包**：不作为格式采用。预设存在于单个 GitHub 目录内，按目录名称引用成员。它保留为发现入口，用于生成齿轮组。
- **把安装来源作为插件记录上的字段**：在实现过程中否决，见决策 2。
- **把齿轮组状态放进 `AppSettings`**：否决。这会为一份有自己生命周期的状态改动设置契约包及其同步键；像 `plugins` 一样同步的两张表既保持以宿主为准，又不需要改契约。

## 影响

- Dexie v235 新增 `pluginInstallOrigins`、`pluginCogsets`、`pluginCogsetState` 和 `cogpackInstalls`，并登记到治理目录、备份包以及（两张齿轮组表）伴随同步中。
- 伴随契约新增两个宿主命令（`plugin_cogset_activate`、`plugin_install_origin_record`），Tauri 外壳新增两个桌面命令（`plugin_export_tree`、`plugin_install_from_files`）。
- 切换齿轮组会重启插件，耗时与变化的插件数量成正比，界面会按插件报告进度。
- 锁定的版本只是期望，不是保证：自动更新会保留被锁定的更新，但用户主动更新仍会改变插件版本，下一次激活时会报告不一致。
