# ADR 0147 — 仓库自己声明工作区

**状态：** 已接受
**日期：** 2026-08-25
**相关：** [ADR-0144](./0144-workspace-as-the-unit-of-work)、[ADR-0111](./0111-managed-workspace-registry)、[ADR-0090](./0090-unified-agent-execution)

## 背景

`lib/project-environment/workspace-config.ts`——`.cognia/workspace.json` 的
schema、校验器、受限相对路径检查与合并函数——已经完整写好、带有自己的测试，
并且**没有任何调用者**。不是部分接线：`readWorkspaceConfig`、
`parseWorkspaceConfig`、`mergeWorkspaceConfig` 在整个仓库里的调用数是零。三个
原生字段（`sparsePaths`、`cacheLinks`、`include`）在两侧都没有实现。

与此同时，回合开始前加载项目环境的两个界面——聊天控制器与日程执行器——用的都
是未经处理的本机行。于是仓库可以描述自己的初始化方式，而 Cognia 从不去看；每
一个新贡献者都得靠口头被告知。

这正是本代码库反复出现的那类缺陷：造好了，从没接上。

## 决策

### 这个文件是真实来源，并且带门禁

文件里有 `setup` 与 `actions`——回合前运行的 shell 脚本——还有会成为该进程环境
的 `variables`、会把目录软链进工作树的 `cacheLinks`、以及会把被 gitignore 的
文件复制进来的 `include`。读它就是执行由 `git pull` 投递的代码。

**是两个决定，不是一个。** Workspace Trust 已经回答了「这个检出是不是我的」：
按目录授予一次、可撤销，也是守护 `.claude/settings.json` hooks 的同一道门。它
是必要的，但**不充分**——它在仓库后来的提交存在之前就被授予了，一个三月份信任
了某个目录的贡献者，并没有批准八月份落进去的初始化脚本。所以：

1. **未信任 → 完全不读这个文件。** 不是「读了但忽略脚本」：`roots` 会扩大
   agent 的文件系统触及范围，`variables` 会进入同一个进程，因此在用户尚未担保
   的检出里，这个文件没有哪一半是可以安全采纳的。
2. **已信任 → 内容必须被批准过。** 已批准的摘要存在信任行上；撤销信任会删除整
   行、连带丢掉它。首次见到与此后被改动，在门禁看来是同一个状态、只是措辞不
   同，因为它们需要用户给出同一个答案。

### 摘要覆盖全部字段，且基于解析后的形态

不是人工挑选出的「危险子集」。判断这个文件哪一半安全，是一个迟早会判断错的判
断——单是 `variables` 就能设置 `NODE_OPTIONS=--require ./evil.js`。摘要基于**解
析并规范化后**的配置，因此重新格式化、调整键顺序、注释变动都不会重新弹窗，而任
何语义变化都会。数组保持原序：`actions` 是按顺序执行的，排序会让两份不同的配置
碰撞到同一个摘要上。

### 变量冲突时本机赢

这与 `mergeWorkspaceConfig` 原先的写法相反。两边配置的是同一个工作区，区别在于
「本设备」与「随仓库共享」，更具体的那一层必须赢——否则用户为自己机器设置的值会
在一次 pull 之后静默失效，而屏幕上没有任何东西能把这两件事联系起来。反方向的失
败通过明说来覆盖：`overriddenVariables` 会列出每一个被本设备遮蔽的仓库值。

### 建议，而不是指令

有三个字段描述的是工作区本身而非要运行的脚本，三者都是**播种**而非强加：

- `defaults.execution` / `defaults.base` 只在工作区自己没有记住的默认值时生效，
  并且输给新建对话时的选择器。
- `roots` 与 `capabilities`（schema 新增）在**批准那一刻**应用——用户对这份确切
  内容点头的时刻——且每一条声明都会被记录为「已提议过」。

**播种一次，永不重播。** 种子键在它创建出来的东西被删掉之后依然被记住，所以删掉
一个被播种的根、或清空一个被播种的能力，都会保持住。仓库告诉新贡献者「本项目用
Jira 服务器」是有价值的；仓库在下一次 pull 时悄悄推翻这位贡献者的回答则不是。

### 供给是创建工作树的一部分

`sparsePaths`、`cacheLinks`、`include` 在工作树**创建过程内**应用，而不是事后补
一刀：一棵只供给了一半的工作树交到 agent 手里，比没有更糟，所以失败时会像
materialize 失败一样回滚整次获取。顺序是承重的——先做 sparse-checkout（它会删除
被排除的路径，从而抹掉在它之前建立的链接），再做便宜的软链，最后做文件复制。

每一个路径都会在宿主侧**重新**校验。渲染端的解析器已经拒绝 `..` 与绝对路径，但
`apply_provisioning` 对获取命令的任何调用方都是可达的——插件、CLI、配对设备——而
「上游有人检查过了」正是路径穿越得以出货的方式。一个经由软链解析到检出之外的
`include` 会被跳过：那是同一种逃逸，只是多了一层间接。

只对 Git 工作树隔离做供给。影子工作区物化的是一份显式快照，对它做裁剪或链入会与
它据以构建的那份快照自相矛盾。

## 影响

**收益。** 仓库可以把自己的初始化方式描述一次，每个贡献者都能得到——包括那些在
全新工作树里根本不可见的部分（被 gitignore 的 `.env`、包缓存），以及那些搞错了
代价很高的部分（该检出哪些子包、这里的工作是否该在独立的树里进行）。

**代价。** `TrustedWorkspace` 增加三个可选字段（`approvedConfigDigest`、
`approvedConfigAt`、`seededDeclarations`）。无需 Dexie 版本升级：它们不是索引。
`AcquireWorkspaceBundle` 两侧各增加一个可选的 `provisioning` 字段；它是
`#[serde(default)]`，旧调用方不受影响，也不需要重新生成契约（该命令不在
companion 面上）。

**一块新的共享件。** `lib/i18n/runtime-translator.ts`——给非组件代码用的
`useTranslations`。工作规则 4 关心的是用户读到什么，而不是 `.tsx`；lib 侧的通知
此前无从遵守它，`lib/scheduler/notification-integration.ts` 里只有英文的字符串
就是这个缺口在生产环境里的样子。

**有意未做。** `.cognia/workspace.json` 的编辑器（这个文件在仓库里编辑，和其它
所有提交进版本库的配置一样）、按分支的配置，以及全机范围的批准——批准是按设备
的，因为信任就是按设备的。

**对 ADR-0144 的更正。** 它的「有意未做」清单里把 `.cognia/workspace.json` 列为
已标记休眠、不被读取。这一条不再成立。
