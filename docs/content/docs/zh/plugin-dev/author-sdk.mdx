# 公共插件 SDK 与运行时契约

第三方 TypeScript 插件应只依赖发布后的 `@cognia/plugin-sdk`。该包同时提供 ESM、CommonJS 和类型声明；宿主注册表、执行器、工厂、测试重置函数、PKCE 辅助函数和内部会话构造器都不属于公共 SDK。

## 公共导入映射

| 导入 | 受支持内容 |
| --- | --- |
| `@cognia/plugin-sdk` | `define*` 辅助函数、稳定常量和公共作者类型 |
| `@cognia/plugin-sdk/manifest` | manifest、能力、权限和 contribution 类型 |
| `@cognia/plugin-sdk/context` | `PluginContext`、`FullPluginContext` 与可调用 context API 接口 |
| `@cognia/plugin-sdk/hooks` | hook 载荷与接口 |
| `@cognia/plugin-sdk/contracts` | 只读规范契约元数据 |
| `@cognia/plugin-sdk/events` | 稳定事件常量与事件载荷类型 |
| `@cognia/plugin-sdk/permissions` | 公共权限值与权限类型 |
| `@cognia/plugin-sdk/extensions` | 扩展点常量与 contribution 类型 |
| `@cognia/plugin-sdk/api/tool`、`/api/native-anthropic-tool` | 明确支持的兼容子路径 |

不要导入 `@/lib`、`@/types`、`@cognia/plugin-sdk/host` 或应用私有的 `@cognia/*` 包。`host` 入口只服务一次仓库内迁移，不在 npm exports 或 tarball 中。

## 契约驱动的插件开发

修改 manifest 或选择运行时之前，先使用 `cognia plugin contract`。它读取生成后的 canonical catalog，因此未来新增的能力、contribution、权限、入口和路径字段无需更新人工清单即可被发现。

```bash
# 新插件：只查询 tool 与 context panel 所需契约。
cognia plugin contract \
  --plugin-type frontend \
  --capability tools \
  --contribution contextPanels \
  --point chat.input.actions \
  --point-kind ui-slot \
  --permission extension:ui \
  --json
cognia plugin new support-panel --kind ts --json

# 扩展现有插件：先检查，再查询扩展需要的记录。
cognia plugin info . --json
cognia plugin contract \
  --plugin-type hybrid \
  --capability python \
  --contribution tools \
  --json

# 确定运行时之前，对比兼容的 runtime entry 规则。
cognia plugin contract --plugin-type frontend --plugin-type hybrid --json
```

选择器可以重复使用。Point kind 包括 `ui-slot`、`hook`、`activation` 和 `runtime`。不带筛选时返回完整目录；带筛选时返回选中及关联的契约记录，并保留完整目录计数。v2 JSON envelope 会在 capability、contribution、permission、runtime entry 与 path field 之外返回生成后的 `pluginPoints` 目录。未知选择器会以结构化 input error 失败，命令本身不会写入文件。

必须检查结果中的 `support`、`pythonExecution`、`execution`、point `status`/`stability`、`formFactor`、替代 id、permission、入口路径、最低宿主版本和路径字段契约。生成任何标记为 experimental 的行为前都要取得用户明确确认，并在完成报告中保留实验性警告。新功能不得使用 deprecated point，应改用其 `replacementId`。依赖 JavaScript 执行的 contribution 与纯 Python 或 WASM 运行时不兼容；必须在写入前停止，并仅提供契约报告的兼容类型，通常是 `frontend` 或 `hybrid`。

批准后，新项目使用 `cognia plugin new ... --json`；扩展现有项目时保留无关文件。随后运行 `cognia plugin sync-types`，仅使用 `@cognia/plugin-sdk` 与 `@cognia/plugin-ui` 实现，并依次通过 `doctor`、`lint --json`、运行时测试/typecheck、`build --json` 和 `info --json`。密钥生成、签名、安装、reload、export 与发布都是需要明确请求的独立操作。

## 运行时矩阵

| Manifest 类型 | 必需入口 | JavaScript 延迟 contribution | 说明 |
| --- | --- | --- | --- |
| `frontend` | `main` | 允许 | Browser/Tauri 可用性由 `runtimeCompatibility` 决定 |
| `python` | `pythonMain` | 拒绝 | Python 声明不能执行 JavaScript contribution factory |
| `hybrid` | `pythonMain`；存在 JS contribution 时还需 `main` | 提供 `main` 后允许 | 两个运行时分别加载 |
| `wasm` | `wasmMain` 与 `wasm.apiVersion` | 拒绝 | 桌面 Component Model 宿主 |
| `vscode-extension` | `vscodeMain`、theme、grammar、icon theme、snippet 或 language 至少一项 | 仅 VS Code contribution | 纯声明式扩展无需 `vscodeMain`；代码扩展仍需要 |

## UI 扩展要求

编写组件前先查询准确的 UI point。返回的 `formFactor` 是宿主布局契约：`icon` 表示方形控件，`row` 表示紧凑操作行，`block` 表示纵向堆叠区块，`panel` 表示自带滚动的完整区域。UI primitive 必须从 `@cognia/plugin-ui` 导入；`cognia plugin build` 会把它与 React 保持为 external，使插件复用宿主的 shared React 与主题。不要导入宿主组件，也不要使用 `react-dom` portal。

插件自行负责展示文案。必须提供 manifest i18n，以及本地化的 accessible name、placeholder、空态/错误态和 dialog close label。`@cognia/plugin-ui` 无法读取宿主的 `next-intl` catalog。

`engines.cognia` 是兼容性权威。lint/install 会拒绝未知能力，也会拒绝低于任何已声明能力目录最低版本的下界。

桌面 JavaScript 插件运行在 Cognia 的进程级 Node runtime profile 中。默认构建使用校验固定 SHA-256 后随应用打包的 Node 26，最低已修补版本为 26.3.1；轻量构建要求通过校验的系统 Node 26 或更高版本。插件不能自行选择或覆盖该 profile。文件系统授权路径必须 canonical、无符号链接，每个路径使用独立的 Node permission flag，并且不得覆盖不可变安装树或宿主持有的权限账本。

## 路径规则

所有可执行或资源入口都必须相对插件根目录。空路径、控制字符/NUL、URI scheme、POSIX/Windows 绝对路径、盘符相对路径、UNC 或 Windows 设备命名空间路径、编码后的路径控制字符，以及使用任一斜杠形式的 `..` 都会被拒绝。安装归档只能包含常规文件和目录：符号链接与硬链接会导致整个归档失败。运行时在消费可执行入口前会重新校验 containment，并拒绝经过符号链接的路径段。

Character pack 头像仅接受 `webDataUrl`。原 `avatarImage.tauriPath` 没有运行时消费方，也绕过 contained asset reader，因此已移除。

有效：`dist/index.js`、`providers/session/importer.js`。

无效：`../outside.js`、`C:outside.js`、`C:\\outside.js`、`\\\\server\\share\\entry.js`、`dist/%2e%2e/outside.js`。

## Context 表面

`PluginContext` 描述有意保留为部分能力的基础 context；`FullPluginContext` 描述宿主创建的完整运行时表面。完整 context 中的 `memory`、`pet`、`webview`、`auth`、`uri` 均为必需字段，核心 logger、storage、UI、agent 和其他全部可调用 API 也由宿主挂载。实现与 `create*API` 工厂仍然只属于宿主。

```ts
import { definePlugin, type PluginContext } from "@cognia/plugin-sdk"

export default definePlugin({
  manifest,
  activate(ctx: PluginContext) {
    ctx.agent.registerTool(tool)
    return {
      onCommand(command, args) {
        if (command !== "example.greet") return false
        ctx.ui.showToast(`Hello, ${args.join(" ") || "world"}`)
        return true
      },
    }
  },
})
```

## 迁移表

| 旧作者代码 | 受支持替代方案 |
| --- | --- |
| `@/types/plugin` | 从包根、`/manifest` 或 `/context` 导入类型 |
| 直接访问 slash-command registry | 声明 `commands`，并由 `activate` 返回 `hooks.onCommand` |
| 导入宿主 registry/executor | 使用 manifest contribution 与对应的 `ctx.*` 可调用 API |
| `create*API` 工厂 | 使用已经挂载在 `ctx` 上的 API |
| 假设 PII helper 是公共接口 | 提供插件自有 `canUseTool`/guardrail；宿主 PII gate 是内部实现 |

新项目使用 `cognia plugin new <name> --kind ts` 生成。`pnpm plugin:create` 仅是该命令的兼容适配器。
