# 扩展点 v2

ADR-0026（2026-05）补齐了 cognia-next 插件平台的 17 个真实缺口。本页是实战参考——新增的 manifest 字段、runtime 点位、`ctx.*` 命名空间的最小可用形状。

背景和动机参见 [ADR-0026 — 插件扩展点扩充](/docs/zh/adr/0026-plugin-extension-point-expansion)。

## Manifest 字段

每个新贡献统一使用懒加载工厂形状：

```jsonc
// plugin.json 根级，与 themes / connectors / mcpServerPresets 并列
{
  "ocrProviders": [
    {
      "id": "baidu",
      "label": "百度 OCR",
      "entry": "providers/baidu.js",
      "export": "createBaiduProvider",
    },
  ],
}
```

`entry` 是相对于插件安装根的路径（禁止 `..`、绝对路径、NUL 字节）。`export` 是 host 首次需要时 dynamic-import 出来的具名函数。

六个新 manifest 块：

| 字段                | 作用                          | 权限            |
| ------------------- | ----------------------------- | --------------- |
| `ocrProviders`      | OCR registry 贡献             | `network:fetch` |
| `workspaceBackends` | Issue-loop / sandbox runner   | `process:spawn` |
| `messageRenderers`  | 自定义 `part.type` React 组件 | `extension:ui`  |
| `aiProviders`       | 插件内部 LLM / embedding      | `network:fetch` |
| `modalMounts`       | 声明式 modal 预注册           | `extension:ui`  |
| `chatMiddlewares`   | 围绕式 chat 管道              | `agent:control` |

另加 `configComponent?: { entry, export }`，提供每个插件的自定义设置 UI。

## ctx.ocr — 注册 OCR provider

```ts
export async function activate(ctx: PluginContext) {
  const handle = ctx.ocr.registerProvider({
    id: "my-engine", // 自动前缀为 `<pluginId>:my-engine`
    label: "我的 OCR 引擎",
    category: "specialist",
    shells: { browser: true, tauri: true, capacitor: false },
    credentialKeys: ["myocr-key"],
    extract: async (input, providerCtx) => {
      /* 返回 OcrResult */
    },
  })

  // 可选——host 在 disable 时也会自动清。
  ctx.onDeactivate?.(() => handle.unregister())
}
```

## ctx.workspace — 注册 issue-loop 后端

后端形状沿用 `E2BBackend`（`clone / commitAndPush / remove`）。这是唯一的注册路径——旧的 `setE2BBackend()` singleton 已移除；宿主按未加前缀的 kind 解析你的后端：

```ts
ctx.workspace.registerBackend({
  id: "my-sandbox",
  label: "我的沙箱",
  backend: {
    async clone({ repoFullName, branch, token }) {
      /* ... */
    },
    async commitAndPush({ workspace, message, remoteBranch }) {
      /* ... */
    },
    async remove(handle) {
      /* ... */
    },
  },
})
```

## ctx.renderer — 自定义 message-part renderer

按 `part.type` 注册 React 组件。保留类型（`tool-*` / `text` / `reasoning` / `file` / `a2ui` / `subagent` / `agent-team-dispatch` / `artifact` / `sources` / `canvas`）会被拒绝，使用插件前缀的 type：

```ts
ctx.messagePart.registerPartRenderer("x-my-custom-block", MyBlockRenderer)
```

或者通过 `manifest.messageRenderers[]` 声明：

```jsonc
{ "partType": "x-my-block", "entry": "renderer.js", "export": "MyBlockRenderer" }
```

## ctx.ai — 插件内部 LLM / embedding

**重要：** 主聊天链路永远不会解析到插件 AI provider。这些调用仅供插件自己的后台任务（总结、分类、向量化）使用。想影响主聊天请用 `ctx.chat.use()`。

```ts
const { text } = await ctx.ai.chat([{ role: "user", content: "总结一下这段" }])

const vectors = await ctx.ai.embed(["hello", "world"])
```

## ctx.modal — 在任何地方打开 modal

```ts
const handle = ctx.modal.openModal(MyModalComponent, { initialTab: "general" })
// 关闭：
handle.close()
```

插件组件收到 `{ onClose, modalId, args }`。调用 `onClose()` 把条目从栈里 pop 出去。

在 `manifest.modalMounts[]` 里声明的 modal 会被注册（懒加载——组件在首次打开时才导入），可按 id 打开：

```ts
const handle = await ctx.modal.openById("wizard", { step: 1 })
// → id 未知或组件加载失败时返回 null
```

## ctx.chat — 围绕式中间件

中间件包裹**非流式整段回复**的一轮（`runAndCaptureAssistantReply`——连接器 / headless 回复路径），而非流式 UI 聊天（那里文本已在屏幕上、不存在"最终响应"可包裹）。**执行由默认关闭的开关门控**（`setChatMiddlewareExecutionEnabled(true)`）：注册始终发生，但开关开启前没有中间件运行，因此默认零开销。流式 UI 聊天请用更轻的 `onBuildOptions` hook 改选项。安全网：每个中间件 5s 超时（最大 60s）、错误隔离（抛错跳过该中间件、不影响主链路）、3 次连续失败熔断。

```ts
const dispose = ctx.chat.use(
  async (req, next) => {
    const before = Date.now()
    const res = await next()
    ctx.logger.info(`turn 用时 ${Date.now() - before}ms`)
    return res
  },
  { id: "telemetry", priority: 10, timeoutMs: 3000 }
)
```

只想改字段、不想短路的，用更轻量的 `onBuildOptions` hook：

```ts
export const hooks: PluginHooks = {
  async onBuildOptions(options) {
    if (options.systemPrompt) {
      return {
        ...options,
        systemPrompt: options.systemPrompt + "\n\n请简洁回答。",
      }
    }
  },
}
```

## ctx.capabilities — 平台探测

替代直接 `isTauri()` / `isMobile()` import：

```ts
if (ctx.capabilities.tauri) {
  // Tauri 路径
} else if (ctx.capabilities.mobile) {
  // Capacitor 移动端路径
} else {
  // 浏览器路径
}
```

## 每个插件的自定义设置 UI

在 manifest 加 `configComponent`。host 会在插件设置 tab 里渲染你的组件，**替代**由 `configSchema` 自动生成的表单：

```jsonc
{
  "configComponent": { "entry": "settings.js", "export": "MySettings" },
}
```

```tsx
export const MySettings: ConfigComponent = ({ config, onSave }) => {
  return <button onClick={() => onSave({ ...config, enabled: true })}>启用</button>
}
```

## 主题 CSS 变量

插件主题现在可以在运行时覆盖 CSS 自定义属性（变量名匹配 `^--[a-z][a-z0-9-]*$`，值 ≤200 字符，`</style>` 会被拒绝）：

```jsonc
{
  "themes": [
    {
      "id": "midnight",
      "name": "Midnight",
      "isDark": true,
      "cssVariables": {
        "--background": "#0a0a0a",
        "--foreground": "#fafafa",
        "--accent-1": "oklch(0.7 0.15 220)",
      },
    },
  ],
}
```

## 复活的槽位

v2 复活两个之前 deprecated 的槽位：

- **`chat.message.actions`** — 每条消息上方的 hover action bar，与 `chat.message.footer`（host copy/regenerate）区分。
- **`settings.ai`** — `api-key-section` 顶部，统一 AI 设置卡片的标准 host。
- **`sidebar.right.top` / `sidebar.right.bottom`** — 共享 Context Workbench 内资源面板的上方与下方。
- **`panel.header` / `panel.footer`** — 活动 Context Workbench 面板的紧邻头部与尾部。

## Context Workbench 资源面板

可信前端插件可以声明式贡献面板：

```jsonc
{
  "permissions": ["extension:ui", "canvas:read", "project:read"],
  "contextPanels": [
    {
      "id": "insights",
      "entry": "context/insights.js",
      "export": "InsightsPanel",
      "resourceKinds": ["canvas-document", "project-file"],
      "activity": "inspect",
      "labelKey": "context.insights",
      "label": "洞察",
      "icon": "search-code",
      "requiredCapabilities": ["inspect"],
      "preferredMode": "wide",
      "retention": "stateful",
      // 可选行为钩子，从与 renderer 相同的 `entry` 模块按具名导出解析。
      "onFirstActivateExport": "onInsightsOpened",
      "getBadgeExport": "insightsBadge"
    }
  ]
}
```

`activity` 只能是 `ai`、`comments`、`inspect`、`review`、`preview-run`、
`templates` 或 `workspace`。

`resourceKinds` 必须是 `canvas-document`、`project-file`、`artifact`、`workflow`、
`session` 的非空子集。**`session` 是聊天右栏的兜底资源** —— 没有打开产物时 dock
显示的就是它，所以不声明它的面板不会出现在右栏的默认状态里。

Host 通过插件现有 i18n bundle 解析标签，`label` 是确定性的 fallback；不支持的
icon 回退为宿主面板 icon。

`retention` 决定用户切走后面板的命运：`stateful`（默认）让它留在 React
`<Activity>` 后面，状态与滚动位置得以保留；`ephemeral` 则卸载它。持有昂贵资源
（例如一条实时连接）的面板应选 `ephemeral`。

命令式 API 与声明式贡献共用同一个命名空间 registry，同样的字段以内联值而非导出名
传入：

```ts
const dispose = ctx.contextPanels.register({
  id: "live-insights",
  activity: "inspect",
  labelKey: "context.liveInsights",
  label: "实时洞察",
  resourceKinds: ["canvas-document"],
  icon: "search-code",
  getBadge: (resource) => unreadFor(resource),
  onFirstActivate: (resource) => warmUp(resource),
  renderer: LiveInsightsPanel,
})

ctx.contextPanels.reveal("live-insights", "wide")
const context = ctx.contextPanels.getActiveContext()
const unsubscribe = ctx.contextPanels.onDidChangeActiveContext((next) => {
  // 只有身份、revision、selection、capabilities；绝不包含资源内容。
})
```

`reveal()` 只能打开调用插件自己的适用面板，并遵守用户 pin，因此请求可能进入
pending 而不替换当前面板。它还会先请求宿主把自己的容器带回屏幕上，所以对着折叠的
聊天 dock 或关闭的移动端 Sheet 调用它会打开容器，而不是在用户看不见的地方静默切换
面板。

每个面板需要 `extension:ui`，以及声明资源对应的 `project:read`、`canvas:read`、
`artifact:read`、`workflow:read` 或 `session:read`。缺任意一个时注册直接失败；已注册
的面板在权限被撤销的瞬间从活动栏消失。

### Webview 面板（沙箱）

面板不必是受信 React 组件：`webview` 字段引用同一 manifest `webviews[]` 里的一项，
宿主会把该 webview 的沙箱 iframe（`sandbox="allow-scripts"`、不透明 origin、CSP 按
插件 `networkAccess` 收紧）渲染成面板主体。`webview` 与 `entry`/`export` 及各
lifecycle-export 字段互斥——没有模块可供解析。

```jsonc
{
  "permissions": ["extension:ui", "session:read"],
  "capabilities": ["context-panel", "webview"],
  "webviews": [{ "id": "inspector", "html": "<main>…</main>" }],
  "contextPanels": [
    {
      "id": "inspector",
      "webview": "inspector", // ← 取代 entry/export
      "resourceKinds": ["session"],
      "activity": "inspect",
      "labelKey": "panel.inspector",
      "label": "Context Inspector"
    }
  ]
}
```

内联 `html` 的 webview 完全不经过模块 importer，所以这是唯一对**内置插件**也生效的
声明式 `contextPanels` 形态——树内参考实现是 `cognia-context-inspector`。

iframe 内部由宿主注入 `acquireCogniaContextPanelApi()`：完整面板 API 经 postMessage
镜像。每个方法返回 Promise（5 秒超时），且每次调用都在宿主侧重新过权限门：

```js
const api = window.acquireCogniaContextPanelApi()

await api.setBadge("inspector", 3)
await api.reveal("inspector", "wide")
const context = await api.getActiveContext()
const state = await api.getWorkbenchState()
await api.setMode("focus")
await api.setPinned(true)
// 动态注册另一个面板——由另一个已声明 webview 渲染（React renderer 无法跨
// postMessage）。返回 registration id，供 api.dispose(id) 使用。
const registrationId = await api.register({
  id: "extra",
  webview: "extra-view",
  label: "Extra",
  labelKey: "panel.extra",
  resourceKinds: ["session"],
  activity: "inspect",
})

api.onDidChangeActiveContext((context) => {})
api.onDidChangeWorkbenchState((state) => {})
// 本 iframe 实例的显示状态——false 时应暂停轮询/动画。
api.onDidChangeVisibility(({ visible }) => {})
```

宿主会把 `activeContext` / `workbenchState` 变化推进 iframe，并在客户端接入时回放
一份快照，因此脚本随时订阅都不会漏状态。`visibility` 是按 iframe 实例的：桌面 dock
与移动端 Sheet 可能各挂着同一 webview 的活 iframe，各自只会听到自己实例的状态。

<Callout type="warn">
  `stateful` webview 面板在隐藏期间保留 iframe（及全部帧内状态），但**折叠工作台或
  切换资源会整个卸载 iframe**。需要跨卸载存活的状态请用
  `acquireCogniaWebviewApi().setState(...)`：宿主会暂存并在下一个 iframe 加载时回放，
  acquire 之后 `getState()` 即可拿到上一帧最后一次保存（迟到的回放可用
  `onDidChangeState` 订阅）。这仅在运行期有效——插件禁用或应用重启后即失效；
  需要持久化的内容仍应经插件逻辑侧（`ctx.storage`）。
</Callout>

### 宿主侧可见性

命令式 API 有同样的信号且无需 webview：
`ctx.contextPanels.onDidChangeVisibility(panelId, listener)` 在面板成为 / 不再是
活动工作台的前台面板时以 `true`/`false` 触发（折叠视为隐藏），仅在跳变时触发。

### 驱动工作台

只有注册无法让面板知道自己是否在屏幕上、右栏有多宽，也无法在活动图标上推送计数。
同一套 API 覆盖了这些：

```ts
// 活动栏角标。与定义自带的 `getBadge` 相加；传 0 清除。
ctx.contextPanels.setBadge("live-insights", 3)

// 右栏当前状态；没有挂载的工作台时返回 null。
const state = ctx.contextPanels.getWorkbenchState()
// { resource, mode, activePanelId, ownsActivePanel, userPinned, panelIds }

// 资源切换与布局变化两侧都会触发。
const stop = ctx.contextPanels.onDidChangeWorkbenchState((next) => {
  if (next?.ownsActivePanel) startExpensiveWork()
  else stopExpensiveWork()
})

// 布局控制，仅在本插件的面板处于可见状态时生效。
ctx.contextPanels.setMode("focus") // "collapsed" | "narrow" | "wide" | "focus"
ctx.contextPanels.setPinned(true) // 让自动 reveal 变成角标排队
```

当可见的是其他插件或原生面板时，`setMode()` / `setPinned()` 返回 `false`，因此插件
永远无法在用户眼皮底下把右栏全屏化。`panelIds` 只列出本插件自己的面板，工作台其余
部分对它不可见。以上方法同样需要 `extension:ui`，其中 `getWorkbenchState()` 还需要
当前资源类型对应的读权限。

<Callout type="warn">
  `setMode("narrow")` 与 `setMode("wide")` 依赖宿主。在工作台自己拥有宽度的地方
  （编辑器与工作流侧栏）它们会真的改变宽度；而在**聊天 dock** 里宽度归外层可调整
  面板所有，这两个值只会更新记录下来的模式，屏幕上不会有任何变化。`"focus"` 与
  `"collapsed"` 在所有宿主都生效。把 narrow/wide 当作提示，不要让布局依赖它。
</Callout>

## 状态与参考插件

经过 SDK 补全后，下列每个表面都已**完整接线到宿主**——不只是注册表，宿主渲染器 / 消费端都已存在：

| 表面               | 宿主消费端                                                      | 参考插件                                  |
| ------------------ | -------------------------------------------------------------- | ----------------------------------------- |
| `themePacks`       | 外观 → **主题包** tab + 一键 `applyThemePack`                  | `cognia-appearance-demo`（声明式）        |
| `wallpapers`       | 外观 → **壁纸** tab（插件项合并 + "Plugin" 徽章）              | `cognia-appearance-demo`（声明式）        |
| `densityPresets`   | 通过 `applyDensityPresetVars` 按名解析（如来自主题包）         | `cognia-appearance-demo`（声明式）        |
| `scheduledTasks`   | 启用时创建真实的 `ScheduledTask` Dexie 行                      | `cognia-scheduling-demo`（声明式）        |
| `configComponent`  | 在插件设置面板渲染（失败回退到 schema 表单）                   | bridge 单测（`config-component-bridge`）  |
| `modalMounts`      | 懒加载的声明式 modal 注册表 → `ctx.modal.openById`            | bridge 单测（`modal-mount-bridge`）       |
| `chatMiddlewares`  | `runAndCaptureAssistantReply`（默认关闭开关）                  | bridge 单测（`chat-middleware-bridge`）   |
| `contextPanels`    | Context Workbench 活动栏（聊天 dock / 编辑器 / 工作流）        | `cognia-context-inspector`（声明式 webview）、`cognia-prompt-templates`（命令式） |

> **Builtin 限制**：基于 import 的字段（带 `entry` / `export` 模块的——
> `ocrProviders`、`workspaceBackends`、`messageRenderers`、`aiProviders`、
> `modalMounts`、`chatMiddlewares`、`configComponent`、`contextPanels`）只有**磁盘 / 市场安装**
> 的插件才能解析其模块（安装路径是真实可 fetch 的目录）。内置插件
> （`builtin://…`）无法 fetch 单独的 entry 文件，必须改用 `ctx.*` API 命令式
> 注册这些表面。声明式数据字段（`themePacks`、`wallpapers`、`densityPresets`、
> `scheduledTasks`、`modes`）对内置插件同样有效——这也是上面的参考 demo 都是
> 内置插件的原因。**例外**：`contextPanels` 里以内联 `html` webview 为后端的条目
> 不涉及模块 import，因此该声明式形态对内置插件同样可用（见
> `cognia-context-inspector`）。

## 迁移速查表

旧路径仍能跑（`@deprecated` shim 兜底）。建议在后续 PR 中迁移：

| 旧                                        | 新                                                               |
| ----------------------------------------- | ---------------------------------------------------------------- |
| 全局 `installOcrRuntime()`                | `ctx.ocr.registerProvider(...)`                                  |
| `setE2BBackend(impl)`（**已移除**）        | `ctx.workspace.registerBackend({ id: "e2b", ... })`              |
| `registerNodeExecutor` side-effect import | `ctx.workflow.registerNode(...)` 或 `manifest.workflows.nodes[]` |
| `registerPluginI18n({ ... })`             | `manifest.i18n`（已自动 wire）                                   |
| 直接 `isTauri()` import                   | `ctx.capabilities.tauri`                                         |
