# 运行常驻 host

常驻 host 是你自己的一台机器，全天候运行 Cognia 的 headless server 和 brain（ADR-0224）。
它是桌面端的对等设备，而不是替代品。它运行放在它上面的一切：从手机发起的对话、定时任务、
bot 和连接器，所以笔记本休眠时这些照常工作。

有两种运行方式：

| 机器                       | 方式                                    |
| -------------------------- | --------------------------------------- |
| Linux VPS、NAS、家用服务器 | Docker Compose 的 `server` profile      |
| Mac（例如 Mac mini）       | host 安装包，安装为 LaunchDaemon        |
| 一直开着的桌面电脑         | 桌面应用的**常驻 host 模式**（见下文）  |

两种方式下，手机和桌面都经 Cognia 的加密中继配对，所以机器可以待在家用路由器后面，
不需要公网域名，也不需要开放端口。

<Callout title="状态">
  本页介绍安装、配对和保护 host 数据。把桌面上已有的 bot、定时任务和连接器迁移到 host、
  按条目归属以及每个任务一个容器正在构建中（ADR-0224 阶段 A）；在此之前，
  需要全天候运行的内容请直接在 host 上创建。

## 用 Docker Compose 运行在 Linux 上

```bash
git clone https://github.com/MaxQian888/cognia-next.git && cd cognia-next/deploy/compose
cp .env.example .env
# 编辑 .env：设置 SHARE_UPLOAD_SECRET（openssl rand -hex 32），并把 COGNIA_AGENT_BUNDLE_IMAGE
# 设为按摘要固定的智能体工具包镜像，可用下面的命令得到：
#   docker buildx imagetools inspect ghcr.io/maxqian888/cognia-agent-bundle:latest \
#     --format '{{.Name}}@{{.Manifest.Digest}}'

export COMPOSE_FILE=docker-compose.yml:docker-compose.t2.yml:compose.host-updates.yaml
echo "COGNIA_COMPOSE_DIR=$PWD" >> .env                         # 更新代理在这里找到这些文件
docker compose --profile server run --rm cognia-server init   # 一次性写入 /data/master.key
docker compose --profile server up -d --wait
docker compose --profile server run --rm host-updates host-updates adopt   # 固定当前运行的镜像
docker compose exec cognia-server cognia-server pair
```

`init` 在数据卷里创建主密钥，永远不会替换已有的密钥。容器会自动重启
（`restart: unless-stopped`），机器开机后随 Docker 一起启动。把同样的 `COMPOSE_FILE`
一行也写进 `.env`，之后每条 `docker compose` 命令都会用同一组文件启动 host。

`compose.host-updates.yaml` 让 host 能够自行更新（见[更新](#更新)）。`adopt` 把服务器当前运行的
镜像按摘要固定在 `.env` 中，在更新替换它之前，host 一直运行这个确切的构建。

`docker-compose.t2.yml` 让 host 在容器里执行任务（见[host 在哪里执行任务](#host-在哪里执行任务)）。
服务器只能通过 Cognia 自己的代理访问 Docker，只能创建和运行自己的加固容器。
在 `COGNIA_AGENT_BUNDLE_IMAGE` 指向按摘要固定的工具包之前，容器无法启动，
不要求隔离的任务会改在服务器进程中执行。

## 用 host 安装包运行在 Mac 上

下载 `cognia-host-<version>-darwin-arm64.tar.gz`（或 `darwin-x64`），解压到一个固定位置，
例如 `/opt/cognia-host`，然后：

```bash
sudo /opt/cognia-host/bin/cognia-server service install
```

这会安装一个 LaunchDaemon（`/Library/LaunchDaemons/com.cognia.server.plist`），开机即启动、
无需任何人登录，并以**你的**账号运行，而不是 root。它会创建数据目录
（`~/Library/Application Support/cognia-server`）和其中的主密钥，把解压出的目录复制到数据目录的安装区
（`install/versions/<版本>`，经 `install/current` 运行），以便 host 更新时替换它，并打印配对命令。
之后解压出的那份副本就不再需要了。常用参数：

| 参数             | 默认值             | 含义                                    |
| ---------------- | ------------------ | --------------------------------------- |
| `--scope user`   | `system`           | 改为登录时启动的 LaunchAgent，无需 sudo |
| `--run-as NAME`  | 执行 `sudo` 的用户 | 守护进程运行的账号（永远不是 root）     |
| `--data-dir DIR` | 该账号的默认目录   | host 存放数据和主密钥的位置             |
| `--public-url`   | 无                 | 如果你有公网 HTTPS 地址                 |
| `--no-mdns`      | 在局域网广播       | 不通过 mDNS 公布 host                   |

```bash
sudo /opt/cognia-host/bin/cognia-server service status      # 是否已安装、在运行、已就绪
sudo /opt/cognia-host/bin/cognia-server service uninstall   # 保留数据和密钥
```

在没有 Docker 的 Linux 上，同一命令会安装 systemd unit；系统级服务会以 root 专属的 systemd
credential 从 `/etc/cognia-server/master.key` 读取主密钥。

如果希望 Mac 像服务器一样工作，还要在「系统设置 → 能源」中开启断电后自动启动，并在显示器关闭时阻止休眠。

## 一直开着的桌面电脑

如果要常开的那台机器已经运行着 Cognia 桌面应用，它自己就可以当 host：打开
**设置 → 桌面 → 常驻 host 模式**。模式开启时，应用会：

- 持有系统唤醒断言，电脑不会因空闲而休眠（显示器仍可关闭；`pmset -g assertions` 中显示为
  “Cognia is the always-on host for this account”）；
- 注册登录时启动，并在系统于登录时启动它时**隐藏**窗口。点击托盘图标（macOS 上也可点 Dock 图标）
  打开窗口；
- 点击窗口的关闭按钮时最小化到托盘。托盘菜单的**退出**仍会退出应用，在应用再次运行之前停止托管。

关闭该模式会释放唤醒断言，下一次登录启动会重新显示窗口。登录时启动和关闭按钮的选项保持不变，
可在同一页面修改。

该模式只属于这台电脑，不会同步到你的其他设备。**设置 → 连接 → 总览**会显示桌面是否正在托管，
或在使用另一台 host 时处于待命。与 host 安装包不同，桌面应用在电脑重启后需要有人登录，
所以断电后必须自行恢复的机器请使用安装包。

## 配对手机和桌面

```bash
COGNIA_DATA_DIR="$HOME/Library/Application Support/cognia-server" \
  /opt/cognia-host/bin/cognia-server pair
```

`pair` 向正在运行的 server 请求邀请，打印一个带中继房间的 `cgnp4|…` 字符串、一个可以直接
从终端扫描的二维码，以及过期时间（五分钟）。在设备的配对页粘贴或扫描即可，任何网络下都能用。
兑换它的人会成为 host 的 owner，所以只交给你自己的设备。

| 参数       | 含义                                       |
| ---------- | ------------------------------------------ |
| `--port N` | host 监听的端口（不是 27890 时）           |
| `--direct` | 接受没有中继房间的邀请（见下文）           |
| `--no-qr`  | 只打印字符串                               |

只有中继接受了配对房间，`pair` 才会给出邀请。做不到时（host 没在运行、中继被关闭或不可达），
它会停下并说明原因，而不是打印一个只能在 host 所在网络里使用的邀请。请排除原因，
或者在设备能直接访问 host 时加上 `--direct`。

### 从桌面端配对

打开「设置 → 连接 → 远程主机」，粘贴邀请并打开 **常驻 host**。桌面端会把它记录为常驻 host，
自己照常在本机工作：不会切换过去，列表里会标记为 **常驻**。

之后桌面端大约每分钟通过一条独立的连接检查一次 host，不会把任何请求路由过去；host 的地址
没有响应时会走中继。**设备**页把它显示为 **常驻 host** 并标出是否在线，Presence 卡片里的
**最近检查**会给出最后一次响应（或没有响应的原因），并提供 **立即检查** 按钮。调度器的计时
权威读取的是同一个结果，所以不会再因为桌面端当前没有在使用常驻 host 就把定时任务收回。
持续无响应的 host 检查得越来越少，最长十分钟一次。

### 从命令行配对

```bash
cognia-agent host login home --invitation 'cgnp4|…'
```

CLI 能直接访问 host 时就直接配对，否则通过邀请里的中继房间配对。配对还会让 CLI 在 host 上
拥有自己的中继房间（和设备密钥一起保存在 `hosts.json`；`host show` 会脱敏显示）。命令会先尝试
host 的地址，地址没有响应时再通过这个房间发送，所以放在家用路由器后面的 host 在任何地方都能用。
原始的 `api request` 路由和 `--wait` 没有中继形式，仍然需要能访问该地址。

## 把任务迁移到 host

定时任务、Bot 和连接由拥有它们的设备运行。在 **设备** 页打开 host，用它的 **常驻任务** 区块把
它们迁移过去，这样桌面电脑休眠时它们也会继续运行。**将任务迁移到 …** 会先逐项询问 host，
再把它们分成三组：

- **可以迁移。** 默认全部选中。
- **需要主机安装插件。** host 缺少该项用到的插件，或装的是另一个版本。桌面应用可以把插件发过去：
  它把这些插件打成一个签名的 cogpack，由 host 按 **它自己的** 插件策略安装，所以拒绝未签名或
  未知发布者的 host 也会拒绝它。之后会再询问 host 一次。
- **留在本设备。** 与本机绑定的项，并逐项说明原因：维护本设备自身数据的任务、桌面 / 文件监听 /
  终端触发器、本地项目目录、系统级定时、stdio MCP 服务器，或 host 无法运行的内容。

属于某个工作区的任务或 Bot，若该工作区有一个 `https` remote 的 git 仓库，会把工作区一起带过去，
该项的说明会写明这一点和 host 克隆的仓库，详见 [host 上的代码](#host-上的代码)。没有仓库的工作区会让
该项留在本设备。

迁移时先在 host 上创建一份暂停的副本，再停掉本设备上的这一份，最后在 host 上启动。连接会带上
它的凭据（存入 host 的钥匙串）和在聊天里设置的定时消息。本设备上留下的是一个不运行的占位，
列表行和详情里会显示 **在 … 上运行** 和 host 的名字。

host 可能会先要求有人批准这台设备。对话框会给出批准码，在 host 上、或在另一台管理它的设备上
批准后即可继续。

**收回** 会撤销迁移：host 上的副本被删除，该项按它在 host 上的状态回到本设备运行。host 连不上时
也可以收回：它会立即在本设备运行，host 上的副本要等 host 下次响应时才删除，所以一段时间内两边
可能都会运行。被中断的迁移或收回（应用关闭、网络中断）会列在 **中途停止的操作** 里，用
**继续** 或 **完成** 从中断处接着做。

常驻 host 在线时，新建定时任务、安装 Bot 或添加连接都会询问运行位置，默认选中 host。选
**本设备** 就留在本地；否则先在本设备创建，再立即迁移过去，host 接收不了的项会留在本设备并
说明原因。

## 主机上的密钥

无人值守时运行的任务同样需要密钥。模型提供商密钥是各设备自己的设置，不会同步，所以 host
自身的设置里通常没有。在 **设备** 页打开 host，用 **此主机上的密钥** 把密钥密封保存到它上面：

- **提供商密钥。** 当 host 自身设置中没有某个提供商的密钥时使用，定时任务、Bot 以及其他运行
  都会用到。host 设置里的密钥始终优先。
- **Git 令牌**，按 Git 主机（`github.com`）保存。当 host 从该主机克隆仓库且未提供令牌时使用。
- **连接凭据** 也会列出。它们属于各自的连接，由连接设置和移除，包括连接迁移到 host 时。

密钥只会通过本设备与 host 的连接发送一次，并在 host 上以其主密钥密封保存。列表只显示名称、
设置时间和设置它的设备，从不显示值。密封或移除密钥需要 host 批准（与其他主机管理操作相同），
且只有所有者设备可以操作。某台设备被吊销时，它在 host 上设置的密钥会一并删除。

从已配对设备配置推送凭据、修改 Bot 安装和启用其触发器，现在也需要同样的批准。

## 更新

host 会自行更新。它跟随主人桌面的发布通道（桌面在配对时以及每次更改时发送其更新中心的通道），
检查签名的发布目录，有适合它的新版本时：

1. **等到不会打断任何事情**：没有正在运行的任务、后台作业、远程工作机轮次、正在保存的更改，
   也没有人正在管理它。
2. **同时替换服务端和大脑。** 新版本经下载、按签名目录校验、解压到正在运行的版本旁边，再切换过去，
   由系统服务启动。
3. **证明新版本可用，否则退回。** 新版本必须在十分钟内启动并接受自己的大脑。做不到，或反复退出，
   host 会切回原来的版本并说明原因。

在 **设备** 中打开该 host，使用 **主机更新** 查看它进行到哪一步、在等什么、上次更新的结果；
修改它的通道或关闭自动更新；或立即检查、立即更新。当 host 与本应用的命令契约不一致时，
host 名称下的提示会说明该更新哪一方；若该更新的是 host，一键即可更新：host 自己的更新命令
在契约不一致时依然可达。

容器无法替换自己的镜像，所以 Compose host 的替换在它旁边完成。`compose.host-updates.yaml`
中的 `host-updates` 服务是 Cognia 部署代理的独立主机模式：它持有服务器永远接触不到的 Docker
套接字，并在一个只与服务器共享的套接字上监听。服务器发现更新且空闲时，会停止接收写入并发出请求。
代理自己检查签名目录和发布节奏（服务器只说明它期望的版本），按摘要拉取新镜像，把它作为
`COGNIA_SERVER_IMAGE` 固定在 `.env` 中，然后只重建 `cognia-server`。如果新服务器十分钟内没有就绪，
或拒绝了自己的大脑，代理会重新固定旧摘要并重建它。代理可以改动哪些内容，见
`deploy/compose/README.md`。

在自更新功能之前安装的 host 需要手动更新一次。在系统服务之外启动的 host，或直接从解压目录运行的
host，会在 **主机更新** 中说明；重新运行 `cognia-server service install` 即可解决。未使用
`compose.host-updates.yaml` 启动的 Compose host 会说明它没有部署代理。

host 只信任其构建自带密钥（`COGNIA_UPDATE_TRUST_ROOT`）签名的版本，并向 `COGNIA_UPDATE_URL`
（默认 `https://update.cognia.cn`）的更新服务查询。

## 无人值守运行可以做什么

Bot 和定时任务在 host 上运行时无人看守。每个 Bot 和任务都带有一份权限配置，规定四类操作是可以直接执行，
还是必须先询问你：

| 类别           | 默认               | 可调低为     |
| -------------- | ------------------ | ------------ |
| 工作区文件与命令 | 在已验证的沙箱中允许 | 询问我、禁止 |
| 对外发送       | 询问我             | 禁止         |
| 使用密钥       | 询问我             | 禁止         |
| 主机配置       | 询问我             | 禁止         |

只有当运行的沙箱工具在 host 验证过的隔离沙箱中执行时，工作区操作才会无需询问直接执行；其他情况下它和另外三类一样需要询问。
任何一类都不能调高到默认值以上。

在 Bot 的 **设置** 里的 **无人值守时** 中设置，或在定时聊天任务、目标任务的编辑器里同名的区块中设置。
插件或你的组织可以进一步调低 Bot 的配置，Bot 的 **策略上限** 会显示是哪一层调低了什么。调低后会停止该 Bot 正在进行的运行。

运行需要你确认时会暂停，而不是失败。已配对的手机会收到通知，通知只说明等待的是哪类审批，从不包含运行想发送的内容。
打开通知后在 **Bots** 或 **定时任务** 页面查看请求并批准或拒绝。30 分钟内无人回应的请求会被拒绝。
等待的时间不计入任务的超时。Bot 自身的审批步骤也会出现在同一个列表里。

## host 在哪里执行任务

用 `docker-compose.t2.yml` 启动的 host 会把你派发的任务放进容器执行，从不在 host 自己的进程里执行。
这包括手机聊天、Bot、定时任务、目标、智能体团队和插件。

- 对话中的 Bash、Edit 和 Write 在项目的运行环境中执行：即 host 沙箱池里的容器，以该环境的用户身份运行，
  任务工作区的路径保持不变。其他会在 host 上写文件或启动进程的工具在这些运行中会被关闭。
- 外部智能体（Claude Code、Codex、Pi 等）也在同一个环境中启动。
- 没有选择运行环境的项目使用部署的默认镜像。
- 无法放置的运行会被拒绝，而不会改在 host 上执行。例如项目的运行环境可能仍在等待你批准。

由于这些运行在 host 验证过的沙箱中执行，[无人值守运行可以做什么](#无人值守运行可以做什么)中会把它们视为在沙箱中运行。

有两类运行会留在 host 上。不属于任何项目的对话没有可供容器挂载的工作区，因此它的沙箱工具会被拒绝，
外部智能体则在 host 上的智能体沙箱中运行。项目也可以选择不使用容器：在项目的工作区页面打开 **环境** 标签页，
进入运行环境的运行时设置，开启 **在常驻主机上以主机进程运行**。其他设备会忽略这个开关。

没有沙箱池的 host（启动时未使用 `docker-compose.t2.yml`，或设置了 `COGNIA_SANDBOX_POOL_ENABLED=false`）
无法提供容器。在这样的 host 上，对话中的 Bash、Edit 和 Write 会被拒绝，外部智能体在 host 上的智能体沙箱中运行。
如需在这样的 host 上以主机进程运行项目的工具，请让该项目选择不使用容器。

对话不再使用的容器会被移除。服务器上一次运行遗留的容器会在启动时移除。

## host 上的代码

工作区不会在设备之间同步。定时任务或 Bot 迁移到 host 时，它的工作区会以一份副本随行，副本只包含
工作区的名称、描述、文件夹和仓库 remote。对话、知识文件和设置都留在原设备上。默认工作区从不迁移，
因为每台设备都有自己的默认工作区。

桌面应用从每个工作区主文件夹的 `origin` remote（没有 `origin` 时取第一个 remote）读取仓库地址，
文件夹变化时会重新读取。只认 `https` remote，保存时不含用户名或令牌。

host 为某个工作区执行任务时，如果该工作区的文件夹在 host 上存在，就直接使用它；否则通过共享镜像缓存
克隆仓库，使用为该 git 主机保存的令牌（见 [主机上的密钥](#主机上的密钥)），并在克隆中执行。设置在工作区
子文件夹中运行的任务，会在克隆的同一子文件夹中运行。文件夹和仓库都无法访问时，运行会失败并给出原因，
不会改在其他目录执行。

克隆里是最近一次推送的内容。尚未推送的改动仍留在你的设备上，除非你随对话一起移交。

### 带着代码在 host 上继续对话

要把正在进行的对话移到 host，打开对话菜单，选择 **在其他设备上继续…**，选中常驻 host，并保持勾选
**带上代码**。host 的所有者会在 host 上批准一次请求。之后：

1. 对话所属的工作区以副本形式发到 host，即使它没有仓库。
2. 桌面打包当前工作副本。如果工作区记录了 `https` 仓库，包就是相对该仓库已有的最新提交的补丁：
   未推送的提交、未提交的改动、新增和删除的文件、二进制文件和文件权限都包含在内，无需先推送。
   否则包是该文件夹文件的归档。两者都遵循 `.gitignore`，归档从不包含 `.git` 文件夹。
3. 包按经过校验的分块上传到 host。host 获取起点提交，在新的 `cognia/handoff-…` 分支上检出一份
   全新副本并应用补丁，只有结果与桌面上的文件完全一致才会保留。
4. 对话随后移交，在 host 上的这份副本中继续。和任何接力一样，桌面上的副本变为只读。

包默认最大 100 MiB。要修改 host 接受的上限，在 host 上设置 `COGNIA_CODE_SNAPSHOT_MAX_BYTES`（单位为
字节）。任何一步失败都不会移交任何内容，对话仍留在桌面，并提示原因，例如起点提交还没推送到远程，
或包太大。

### 取回改动

已移到 host 的对话，其桌面副本会显示一条横幅，写明对话所在的 host。如果代码也一起带过去了，横幅上会有
**取回改动**。host 的所有者再批准一次，之后：

1. host 取其副本当前的内容：agent 的提交，加上一个包含所有未提交改动的提交。host 自己的分支和文件保持不变。
2. host 用它为该仓库所在主机存储的 git 令牌，把结果作为 `cognia/<agent>-…` 分支推送到工作区的仓库。
   无法推送时（没有令牌、没有仓库或推送被拒绝），同样的提交以 git bundle 直接传回桌面。没有 git 的文件夹以
   其文件的归档传回。
3. 桌面用你自己的 git 凭据获取该分支，或分块校验下载 bundle，并在**新的 worktree** 中的新分支上检出。
   对话最初所在的文件夹不会被改动。没有 git 的文件夹会解包到一个新文件夹。

横幅会显示 worktree 所在位置，并提供 **在文件夹中显示**。仓库在 GitHub 上且已连接 GitHub 账号（或 `gh`
登录）时，**创建拉取请求** 会从该分支向对话最初所在的分支创建一个草稿拉取请求。之后可以再次取回较新的
工作，它会放入另一个新的 worktree；没有新改动时再次取回，会返回同一个 worktree。

## 保护好主密钥

host 加密存储的一切（设备身份、provider 和连接器凭据）都用主密钥封存，丢失密钥就无法读取。
请备份数据目录里的 `master.key`。host 按以下顺序读取主密钥：

1. `COGNIA_MASTER_KEY`（64 位十六进制）
2. `COGNIA_MASTER_KEY_FILE`
3. systemd credential `cognia-master-key`
4. 设置 `COGNIA_MASTER_KEY_SOURCE=keychain` 时读取钥匙串项 `com.cognia.server`
   （用 `cognia-server init --keychain` 创建；LaunchDaemon 无法使用）
5. `<数据目录>/master.key`

## 持久化

brain 把数据存在 SQLite（`<数据目录>/serve/durability/<账号>/`）里，崩溃或断电不会丢失已提交的内容。
运行过旧版本的 host 会在首次启动时从之前的快照存储导入，旧存储原样保留作为后备。
