# WebRTC 真机验证清单

## 链路实测 — 2026-09-07

ADR-0170 已加入加密的信令数据中继。`open` **不等于 WebRTC 已连通**，必须
确认 `cognia.signaling` DataChannel 真正打开。需要区分直连 `rtc-direct`、
TURN 中继 `rtc-relay`、信令数据中继 `relay`。同局域网下产品优先使用
`ws-lan` 并关闭 WAN 通道，因此局域网验收不要求显示 WebRTC。

真实 Chromium ↔ Rust 测试在以下四种模式中均通过七项场景：

| 信令服务 | ICE | 已验证的实际通道 |
| --- | --- | --- |
| 本地 Axum | 开启 | 真实 DataChannel，候选类型 `prflx` |
| 本地 Axum | 无可用候选 | 加密信令数据中继 |
| 公网 `signaling.cognia.cn` | 开启 | 真实 DataChannel，候选类型 `prflx` |
| 公网 `signaling.cognia.cn` | 无可用候选 | 公网加密信令数据中继 |

每轮检查 RPC 回包、有序事件、宿主重启恢复、客户端先启动、重复重连防护，
以及对端确实观察到关闭。测试使用隔离的内存设备注册；由于没有应用后端，
RPC 预期收到 `service_unavailable`，不能据此声称会话加载或聊天已验收。
两端都在同一台 Mac 上，直连候选或公网信令均不能证明跨 NAT 打洞成功。
公网模式的页面资源来自本地 E2E 构建，在允许的 HTTPS Origin 下运行；
WebSocket 连接真实访问公网，未被拦截。

先用 `rtk pnpm test:e2e:build` 生成最新 E2E 构建，再运行：

```bash
rtk pnpm webrtc:pair
rtk env WEBRTC_PAIR_SKIP_BUILD=1 WEBRTC_PAIR_FORCE_RELAY=1 pnpm webrtc:pair
rtk env WEBRTC_PAIR_SKIP_BUILD=1 WEBRTC_PAIR_FORCE_RELAY=1 WEBRTC_PAIR_SIGNALING_URL=wss://signaling.cognia.cn/signaling WEBRTC_PAIR_BROWSER_ORIGIN=https://cognia.cn pnpm webrtc:pair
```

最后一条去掉 `WEBRTC_PAIR_FORCE_RELAY`，即可测试经公网信令协商 DataChannel。
强制中继使用真实浏览器 ICE，设置 `iceTransportPolicy: "relay"` 且不提供 TURN，
验证的是信令数据中继兜底，**不是 TURN**。仅当二进制已由当前源码编译时，
才能使用 skip-build。

**已复现的上线阻断：**公网 `/healthz` 返回 200，网页 Origin
`https://cognia.cn` 可收到 WebSocket challenge，但 iOS 的
`capacitor://localhost` 和 Android 的 `https://localhost` 均返回 403。
本次修复允许显式配置 iOS Origin，并在生产 Worker 配置中加入两种移动端 Origin。
经用户授权，已于 **2026-09-07T08:38:29Z** 部署，100% 流量使用版本
`aa6f8062-1eb0-49f1-8268-0c961808795a`；上一版本为
`0c92a528-b1a3-4d5d-bede-de87f71732d7`。

上线后复测：健康接口返回 200 且报告 `relayDataLane: true`；原生、网页、iOS、
Android Origin 均获得 WebSocket 101 和 challenge，未授权及仿冒 Origin 仍为 403。
使用 iOS Origin 的 Worker 签名认证协议测试通过；在 Android Origin
（`https://localhost`）下运行的真实浏览器 ↔ Rust 公网测试，直连 DataChannel
和强制信令中继两种模式均通过七项场景。以上 Origin 模拟不替代下述真机验收。

尚待验收：两台真机同局域网、手机蜂窝网络连接桌面、Wi-Fi/蜂窝切换、真实业务 RPC，
以及配置 TURN 后实际选中 relay 候选。本轮没有可用的第二网络设备或 TURN 配置。
不能仅凭 ICE 失败断言是对称 NAT。

同时通过 282 项定向 TS 测试、36 项信令核心测试、65 项 Axum 测试与 4 项 Rust
测试程序测试。信令 Clippy 和 Worker release 构建通过。全量 `pnpm test:coverage`
遇到其他 agent/workflow/UI 测试失败，随后第一个分片在 4 GiB 测试堆限制下以
Node `SIGABRT` 退出，不能声明仓库整体覆盖率验收通过。Rust 格式检查还报告
`services/signaling-server/src/server.rs` 中原有的 `healthz` 签名格式问题，
不在本次修改行内。

任何可能影响 WebRTC 通道端到端的改动（信令信封 schema、SDP/ICE 握手、
配对流程、汇合点升级、`TransportRtc` 状态机）落地后请走一遍本清单。
自动化的 `pnpm webrtc:smoke` 只覆盖汇合点服务器自身——这份清单同时覆盖
移动端（Capacitor）↔ 桌面端（Tauri）和浏览器（Web Companion）↔ 桌面/云宿主路径。

## 准备

需要：

- 一台跑着最新 `pnpm tauri dev` 的桌面机器。
- 一部装好对应移动端构建（`pnpm mobile:sync` + Xcode / Android Studio）
  的手机。
- 一个从已授权 HTTPS Origin 提供的生产 Web 构建。解锁浏览器 Vault，
  并通过邀请链接或 payload 与同一宿主配对。
- 手机切到**蜂窝网络**（与桌面不同 Wi-Fi）——这样才能强制 WebRTC 通道
  做真实的 NAT 打洞，而不是落在 `ws-lan`。
- 在 Chromium 客户端打开 `chrome://webrtc-internals`（手机使用 WebView 远程调试），两端打开 Cognia 应用的
  设置 → Mobile companion → WebRTC 卡片以便观察。

## 步骤 1 — 配对并观察通道展开

1. 在桌面端点击 设置 → Mobile companion → Pair device → Generate QR
   生成配对二维码。
2. 在手机上跑应用内配对流程：发现 → 配对 → 扫描 `cgnp4`（仍支持 `cgnp3`）。手机通过
   challenge + P-256 流程调用 `POST /api/auth/device/register`，返回
   `RoomDescriptor`，并把独立的 mobile 角色信令私钥写入安全存储。
3. 大约 5 秒内，桌面 WebRTC 卡片应当显示新设备依次经过
   **offline → awaiting → negotiating → connected**。
4. 移动端的设置面板上，Transport 一行应当落在
   `relay`、`rtc-direct` 或 `rtc-relay`，取决于实际使用的通道。

如果一分钟后通道仍停在 `ws-tunnel`（Cloudflared）或 `offline`，跳到
[步骤 4](#%E6%AD%A5%E9%AA%A4-4--%E5%AF%B9%E7%A7%B0-nat--turn)。

## 步骤 2 — 已选中的 ICE 候选类型

1. DataChannel 打开后，检查客户端的 PeerConnection。桌面 Chromium 的
   诊断页面无法观察 Rust 宿主的 WebRTC 栈。
2. 找到 `RTCDataChannel:cognia.signaling` 那一行 → 展开父 PeerConnection →
   `RTCIceCandidatePair` → 查看**本地候选**的 `type` 字段。
3. 直连候选可以是 `host`、`srflx` 或 `prflx`。`host` 也可能使用公网 IPv6，
   所以候选类型不能单独证明是局域网。如果是 `relay`，
   见[步骤 4](#%E6%AD%A5%E9%AA%A4-4--%E5%AF%B9%E7%A7%B0-nat--turn)。
4. 给 PR 描述截一张这一行的图。

确认连接使用 `/signaling`，状态显示 `角色隔离协议`。出现任何
替代路由或协议降级都属于发布阻断问题。

## 步骤 3 — 会话中断后的重连

1. DataChannel 已打开的情况下，把手机切到飞行模式。
2. 桌面 WebRTC 卡片应当在 ~5 秒内从 `connected` 闪过 `failed`。
3. 关掉飞行模式。在 `1 秒 + 第一档退避（1 秒）` 内，那一行应当
   再次走过 `awaiting → negotiating → connected`。这一步验证
   `lib/tauri/transport-rtc.ts:RECONNECT_BACKOFF_MS` 的 TS 侧中断重连。
4. 再用移动设置面板上的"重连 WebRTC"按钮跑一次——它应当立刻
   （零退避）发起重握手并弹出 "已发起重连" toast。

## 步骤 4 — 对称 NAT 与 TURN

直连失败时，检查 ICE 错误和实际选中的候选对。NAT、UDP 被阻断、STUN 不可达
以及 TURN 凭据过期的处理方式不同，不能仅凭兜底通道判断原因。

- **配了 TURN。** 通道应当落在 `WebRTC（TURN 中继）`。延迟比直连稍高，
  但仍然绕开了 Cloudflared 隧道。
- **没配 TURN。** 对端已通过认证且在线时，加密信令 `relay` 可以承载业务流量
  （ADR-0170）。健康的局域网或隧道可以优先使用；不可达的局域网不算有效兜底。

跟随 [companion/turn-byo](./turn-byo) 接入 Twilio / Cloudflare TURN
凭据，重跑[步骤 1](#%E6%AD%A5%E9%AA%A4-1--%E9%85%8D%E5%AF%B9%E5%B9%B6%E8%A7%82%E5%AF%9F%E9%80%9A%E9%81%93%E5%B1%95%E5%BC%80)。

## 步骤 5 — 信令汇合点健康度

DataChannel 打开期间，curl 你正在用的汇合点：

```bash
rtk curl -s https://signaling.cognia.cn/healthz
# Worker → { "backend": "worker", "ok": true, "version": "0.1.0" }
```

Worker 健康接口没有全局房间/连接数，也没有 Axum 的 Prometheus `/metrics`。
该部署应使用 Worker 可观测性；自托管 Axum 的 `/metrics` 才包含房间、连接和帧计数。
健康检查成功不等于 WebSocket Origin 准入通过。

## 步骤 6 — 浏览器安全与故障转移

1. 在 Web 构建中重新配对。确认 `localStorage` 的公开目标簿不包含 device JWT、
   Provider key、OIDC token 或私有 JWK；这些值只能加密保存在已解锁 Vault 中。
2. 拒绝宿主证书（或使用未受信的本地 CA），确认 UI 明确报告证书信任问题，
   而不是统一显示“离线”。安装 CA、刷新后验证 HTTPS 恢复。
3. 从宿主白名单移除 Web Origin，确认 UI 能区分 CORS/PNA，并且不会退回明文
   HTTP；随后恢复精确 Origin。
4. 屏蔽直连 ICE candidate。已配置 TURN 时通道必须变为 `rtc-relay`；
   未配置 TURN 时 UI 必须明确说明中继不可用。
5. 切换到另一个已保存目标再切回。订阅、IndexedDB 数据和排队写入必须始终
   绑定原来的 `accountId` 与 `targetId`。
