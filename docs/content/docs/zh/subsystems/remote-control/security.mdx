# 安全模型

<Status variant="stable">allowlist.rs · rate_limit.rs · keyring.rs</Status>

<TLDR>
  三个小巧、各自独立做了单元测试的模块支撑起监听器的纵深防御。
  `allowlist.rs` 是一个 IPv4 CIDR 匹配器，会将调用方 IP 与每个条目进行掩码比对。`rate_limit.rs`
  是一个由互斥锁保护的固定窗口计数器（默认 60/分钟，使用单调 `Instant` 时钟，在锁被毒化时*失败开放*）。`keyring.rs`
  在操作系统密钥环中以服务名 `com.cognia.remote-control` 存储 bearer 令牌与出站签名密钥，将 `NoEntry`
  映射为 `None`，并从两个 UUIDv4 生成一个 256 位令牌。
</TLDR>

## IPv4 CIDR 允许列表 — `allowlist.rs`

`ParsedAllowlist` 持有一个 `Vec<(Ipv4Addr, u8)>`，存放已解析的（网络, 前缀）对。垃圾数据、IPv6
以及超出范围的前缀会在**解析**时（服务器启动时）被拒绝，而非在请求热路径上。没有斜杠的裸 IP
默认作为 `/32` 主机路由。

```rust
// allowlist.rs:37
fn parse_cidr(raw: &str) -> Result<(Ipv4Addr, u8), String> {
    // "127.0.0.1/32" → (127.0.0.1, 32); bare "192.168.1.1" → prefix 32
    // errors: "prefix is not a number", "prefix > 32", "address is not IPv4"
}
```

匹配是一次线性扫描；第一个命中者胜出，空列表则拒绝所有人。其核心是一次直接的前缀掩码比较——
`prefix == 0` 会短路为"匹配全部"：

```rust
// allowlist.rs:53
fn matches_cidr(addr: Ipv4Addr, network: Ipv4Addr, prefix: u8) -> bool {
    if prefix == 0 {
        return true;
    }
    let mask: u32 = (!0u32) << (32 - prefix as u32);
    let a = u32::from(addr) & mask;
    let n = u32::from(network) & mask;
    a == n
}
```

| 条目 | 匹配 | 拒绝 |
| --- | --- | --- |
| `127.0.0.1/32`（默认） | `127.0.0.1` | `127.0.0.2`、`10.0.0.1` |
| `192.168.1.1`（裸 IP → `/32`） | `192.168.1.1` | `192.168.1.2` |
| `10.0.0.0/8` | `10.0.0.1` … `10.255.255.254` | `11.0.0.1` |
| `0.0.0.0/0` | 所有 | — |

渲染端在客户端用 `validateCidrOrIp`
（`types/remote-control/index.ts:135`）镜像了这套校验，因此 Inbound 标签页在条目到达
Rust 之前就能拒绝格式错误的条目——参见 [渲染端与设置](./renderer-and-settings)。

## 固定窗口限流器 — `rate_limit.rs`

`FixedWindowRateLimiter` 是单个 `Mutex<RateLimiterInner>`，持有 `window_started_at: Instant`、
一个 `count` 和 `limit`。因为只有恰好一个 bearer 令牌，所以单一全局窗口等价于按令牌限流。窗口是*固定的*
（一旦过去 60 秒即重置为 `now()`），而非滑动窗口；时钟为单调的 `Instant`，不受墙上时钟变更的影响。

```rust
// rate_limit.rs:40
pub fn try_acquire(&self) -> bool {
    let mut inner = match self.inner.lock() {
        Ok(g) => g,
        Err(_) => return true, // poisoned mutex must not lock users out
    };
    if inner.window_started_at.elapsed() >= Duration::from_secs(60) {
        inner.window_started_at = Instant::now();
        inner.count = 0;
    }
    if inner.count >= inner.limit {
        return false;
    }
    inner.count += 1;
    true
}
```

有两处刻意的设计值得注意：**被毒化的互斥锁失败开放**（返回 `true`），这样别处的 panic
永远无法对一个合法用户永久性地返回 429；以及窗口在过期后于下一次 `try_acquire` 时*惰性*重置，
而非通过后台定时器，因此一个空闲的限流器不产生任何开销。

## 操作系统密钥环存储 — `keyring.rs`

两个密钥都通过 `keyring = "3"` crate（`Cargo.toml:169`，按平台分别使用
`windows-native` / `apple-native` / `sync-secret-service` 后端）存放在操作系统密钥环中。服务名与账户名
是常量：

```rust
// keyring.rs:11
const SERVICE: &str = "com.cognia.remote-control";
const TOKEN_ACCOUNT: &str = "inbound-token";
const SIGNING_SECRET_ACCOUNT: &str = "outbound-signing-secret";
```

私有的 `read` 辅助函数将缺失的条目映射为 `Ok(None)`，因此"尚无令牌"是一个正常值，
而非错误：

```rust
// keyring.rs:19
fn read(account: &str) -> Result<Option<String>, String> {
    match entry(account)?.get_password() {
        Ok(v) => Ok(Some(v)),
        Err(keyring::Error::NoEntry) => Ok(None),
        Err(e) => Err(format!("keyring read failed: {e}")),
    }
}
```

公开包装函数（`read_token` / `write_token` / `clear_token` / `read_signing_secret` /
`write_signing_secret` / `clear_signing_secret`，`keyring.rs:44-67`）是模块其余部分唯一会触及的
接口。两个密钥都绝不会进入 Zustand 或 Dexie。

### 令牌生成 — 256 位

一个新的 bearer 令牌是两个 UUIDv4 拼接为 64 个十六进制字符（256 位熵）：

```rust
// keyring.rs:70
pub fn generate_token() -> String {
    let a = uuid::Uuid::new_v4().simple().to_string();
    let b = uuid::Uuid::new_v4().simple().to_string();
    format!("{a}{b}") // 64 hex chars
}
```

它由 `remote_control_rotate_token`（`commands.rs:41`）调用，后者会持久化新令牌并
记录其存在——参见 [状态与命令](./state-and-commands)。

## 威胁模型

单一 bearer 令牌 + `127.0.0.1` 绑定 + IPv4 允许列表足以抵御：

- 一个**同主机的用户态进程**，它无法读取操作系统密钥环（防御：bearer 认证）；
- 一个**非回环的网络攻击者**（防御：回环绑定 + 默认为
  `127.0.0.1/32` 的允许列表）；
- 向接收方**重放被窃取的 webhook 报文体**（防御：HMAC 签名——一旦出站
  路径接通——加上常量时间的入站认证）。

它**不**足以抵御：

- 一个**能读取操作系统密钥环**的同主机攻击者——无防御；任何 Cognia API 密钥
  都面临同样的暴露风险；
- Cognia WebView 内的一个**恶意浏览器扩展**（Tauri 的默认 CSP 适用）；
- **出站投递上的中间人**——接收方应固定（pin）TLS 并验证签名。

<Callout type="info">
  健康检查（`GET /api/v1/health`）刻意要求认证。中间件门控会在每条路由上运行，因此
  一个未认证的扫描器无法通过读取内嵌的
  `CARGO_PKG_VERSION` 来识别构建指纹。
</Callout>
