# 构建流水线 —— `cognia plugin build`

<TLDR>
  `cmd_build::run()` 先做 lint（出现 error 即中止 —— `cmd_build.rs:47-75`），再按
  `manifest.type` 分发（`cmd_build.rs:104-128`）：**wasm** → 工具链预检 → `cargo component
  build --release` → 在 `target/wasm32-wasip{2,1}/release` 下定位产物 → 剥离并
  重新嵌入 `cognia:api-version` 自定义段（手写 LEB128，`packaging.rs:30-65`）→
  打包成 zip；**frontend** → 解析 TS 入口 → 以 13 个固定参数调用 `npx --no-install esbuild`
  （`build_ts.rs:116-132`）→ 打包成 zip；**python / hybrid / vscode-extension** → 通过
  `pack_existing_entry_bundle()`（`packaging.rs:278-294`）打包 manifest 声明的现有入口文件
  （`pythonMain`、`main`、`vscodeMain`、可选 `styles`）以及 `bundle_include[]`。所有 bundle 都落在
  `target/cognia/<id>-<version>.zip`，基础布局相同：先是漂亮打印的 `plugin.json`，然后是运行时产物条目，
  再是去重后的 `bundle_include[]` 附加文件，全部经 Deflate 压缩。
</TLDR>

## Flags

`cognia plugin build [--path .] [--out <zip>] [--skip-build] [--json]` —— 对有编译/打包步骤的运行时
（`wasm`、`frontend`），`--skip-build` 会跳过该步骤，直接把磁盘上已有的内容重新打包。
从 CLI 视角看，Python、hybrid 和 VS Code-extension 插件始终是 build-free：声明的入口文件必须在打包前已经存在。
`--json` 模式下，缺失或不可读取的插件根目录 / manifest 使用 `stage: "input"` 并带上 `{path, error}`；
lint 失败使用 `stage: "lint"` 并嵌入 lint 报告；工具链、构建、嵌入和打包失败则输出
结构化的 `{ok:false, action:"build", stage, pluginId, version, pluginType, bundle, error}` payload，
所有 JSON 失败都会保持 stderr 为空。

## WASM 路径

### 工具链预检（`cmd_build.rs:287-304`）

两项检查，都附带可直接复制粘贴的补救命令：

```text
cargo-component is required to build WASM plugins but was not found.
Install it with:
    cargo install --locked cargo-component
then re-run `cognia plugin build`.
```

```text
the wasm32-wasip2 compilation target is not installed.
Add it with:
    rustup target add wasm32-wasip2
then re-run `cognia plugin build`.
```

target 检查运行 `rustup target list --installed` 并寻找完全匹配的行；当
rustup 本身缺失时（例如发行版打包的 Rust），该检查会被跳过而非失败。

### `cognia:api-version` 自定义段

host 通过读取一个名为 `cognia:api-version` 的自定义段，把 WASM bundle 路由到匹配的 WIT linker，
其载荷是来自 `manifest.wasm.apiVersion` 的原样版本字符串。嵌入用的是一个从零写起的编码器
—— 不依赖 `wasm-encoder`：

```rust
// crates/cognia-cli/src/packaging.rs:30-50
pub fn embed_api_version(wasm: &[u8], version: &str) -> Result<Vec<u8>> {
    if wasm.len() < 8 || &wasm[..4] != b"\0asm" {
        bail!("input is not a wasm module (bad magic)");
    }
    let stripped = strip_section(wasm, API_VERSION_SECTION)?;  // wasmparser walk
    let mut out = stripped;
    let name = API_VERSION_SECTION.as_bytes();
    let payload = version.as_bytes();
    let mut body = Vec::with_capacity(5 + name.len() + payload.len());
    write_leb128(&mut body, name.len() as u64);
    body.extend_from_slice(name);
    body.extend_from_slice(payload);
    out.push(0);                          // section id 0 = custom
    write_leb128(&mut out, body.len() as u64);
    out.extend_from_slice(&body);
    Ok(out)
}
```

`strip_section`（`packaging.rs:67-106`）用 `wasmparser` 丢弃任何已存在的副本，因此
重新构建和手动重新嵌入都是幂等的。独立的应急出口是
`cognia plugin embed-version <wasm> <ver> [--out wasm] [--json]`，它用 `looks_like_semver`
校验版本（`--version must be MAJOR.MINOR.PATCH`），默认就地覆盖输入。JSON 模式下失败会用
`stage: "input" | "read" | "embed" | "write"` 标明失败阶段。

<Callout type="info" title="一句话说清契约版本管理">
  CLI 把 WIT 契约版本（当前为 0.1.0）写入每一个 WASM bundle；没有匹配 linker 的 host
  会以 `no linker registered for v0.N.x` 拒绝加载 —— host 一侧见
  [插件系统文档](../plugin-system)。
</Callout>

## Frontend 路径

`resolve_ts_entry`（`build_ts.rs:70-93`）优先采用 `manifest.tsEntry`（若它指向不存在的
文件则报错），然后依次尝试 `src/index.ts`、`src/index.tsx`、`src/main.ts`。打包器调用
被完全固定：

```rust
// crates/cognia-cli/src/build_ts.rs:111-132
let npx_program = if cfg!(target_os = "windows") { "npx.cmd" } else { "npx" };
cmd.current_dir(crate_root)
    .arg("--no-install")
    .arg("esbuild")
    .arg(entry…)
    .arg("--bundle")
    .arg("--format=cjs")
    .arg("--platform=neutral")
    .arg("--target=es2022")
    .arg(format!("--outfile={}", outfile.display()))   // = manifest.main
    .arg("--external:@/types/plugin")
    .arg("--external:@/lib/*")
    .arg("--external:react")
    .arg("--external:react-dom")
    .arg("--log-level=warning");
```

两个有意为之的选择：

- **`--no-install`** —— CLI 拒绝背着作者全局安装 esbuild；以插件自己 `package.json`
  里的版本为准。失败提示会指明正确方向：
  `esbuild failed for <entry>. If npx says "could not determine executable", run pnpm install in
  <crate_root> first.`（`build_ts.rs:134-138`）
- **host 模块用 `--external`** —— `@/types/plugin`、`@/lib/*`、`react`、`react-dom` 由
  host 在加载时提供；把它们打进去会重复打包 React 并破坏 shim。

## Build-free 运行时路径

`python`、`hybrid` 和 `vscode-extension` 的 manifest 已经描述了 host 直接加载的文件：

- `pythonMain` 会被 subprocess host 转成 Python import module。
- 当 hybrid 插件有 JS 侧时，`main` 由 frontend module loader 加载。
- `vscodeMain` 会作为扩展入口脚本传给 VS Code sidecar。
- `styles` 存在时会随这些入口一起复制。

`pack_existing_entry_bundle()`（`packaging.rs:278-294`）会确认每个声明入口都是插件目录内的相对文件，
拒绝缺失文件，然后写入 `plugin.json`、去重后的入口文件和 `bundle_include[]` 附加文件。这匹配 host 的
build-free 本地安装契约，而不是猜测 Python 打包、hybrid frontend 构建或 VSIX 编译方式。

## Bundle 布局（所有类型）

| 顺序 | 条目 | 来源 |
| --- | --- | --- |
| 1 | `plugin.json` | 漂亮打印（`serde_json::to_vec_pretty`），这样 `unzip -p bundle.zip plugin.json \| jq` 能正常工作 |
| 2 | 运行时产物条目 | wasm：`manifest.wasmMain`；frontend：`manifest.main`；python：`manifest.pythonMain`；hybrid：声明的 `main` / `pythonMain` / `styles`；VS Code extension：`manifest.vscodeMain` / `styles` |
| 3… | `bundle_include[]` 附加文件 | 相对于 crate 根的路径，去重，缺失文件 = 硬错误 |

各处压缩一律为 `zip::CompressionMethod::Deflated`（`packaging.rs:217`、
`build_ts.rs:156`）。输出约定 `target/cognia/<id>-<version>.zip` 也正是
[`dev`](./bridge-client) 在每次重建后计算出来、用以找到应当热重载的 bundle 的路径。

<Callout type="warn" title="近似确定，但非逐字节可复现">
  写入器注释（`packaging.rs:12-14`）指出，bundle 字节只在 `bundle_include[]` 的
  文件系统排序这一层面上是确定的 —— 条目按 manifest 顺序写入，但不做任何
  时间戳归一化。请签署你**自己构建**的 bundle，而非你复现出来的 bundle。
</Callout>
