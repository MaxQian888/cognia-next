# Headless Service Plane

<Status variant="beta">developer surface</Status>

<TLDR>
  `pnpm dev:headless` 会启动原生 Companion server 与所有已配置 agent runtime，但不启动 Next.js
  或 WebView。本地 Brain 通过 `/internal/events`、`/internal/bridge` 和
  `/internal/_rpc/{name}` 连接。加上 `--local-debug` 后，listener 只绑定 loopback，并自动生成
  仅当前进程有效的 Apifox/Postman 凭据。
</TLDR>

## 不启动前端

```bash
pnpm dev:headless --local-debug --data-dir .cache/headless-apifox
```

启动器会监管原生服务器与启用的 agent runtime 进程、转发日志，并在退出时一起关闭进程组。查看 CLI
选项：

```bash
pnpm dev:headless --help
```

`--data-dir` 同时持有 master key、加密 secret store、SQLite 数据库和 TLS 证书。已有 data dir 如果
只剩加密 store、却丢失原 master key，将无法恢复并报 `secret-store decrypt failed`。本地 API 调试应
使用独立目录，不要让启动器为未知的旧 store 生成一把不匹配的新 key。首次构建完成后可加
`--skip-build` 快速启动。

## 自动本地调试鉴权

启动器会在 data dir 下写出权限为 `0600` 的 Postman 环境文件、输出其路径，并在服务退出时删除。
进程运行期间，可把它导入 Apifox，或读取其中的 `serviceToken` 变量。该随机 token 仅接受 loopback
对 `/internal/*` 与 `/ide/content*` 的请求，不能访问 paired-device 路由。

如需直接用 shell 验证，可在另一个 shell 中使用原有的持久 token 备用方案：

```bash
TOKEN="$(pnpm --silent dev:headless token --data-dir .cache/headless-apifox)"
curl --insecure \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"limit":20,"offset":0}' \
  https://127.0.0.1:27890/internal/_rpc/session_list
```

该 token 具有 service scope，24 小时后过期，并且只在 peer 为 loopback 时接受。它不能用于移动端或
远程设备鉴权。签发 token 与启动服务必须使用同一个 `--data-dir`，否则二者使用不同的签名 secret。

如需在图形化客户端中调试，请使用 [Apifox 本地调试](./apifox-debugging) 中的导入、证书和环境配置。

## 内部路由

| 路由 | 用途 |
| --- | --- |
| `POST /internal/_rpc/{name}` | 调用共享 dispatcher 接受的任意命令 |
| `GET /internal/operations/{operation_id}` | 查询持久化操作，而不重放原始变更请求 |
| `GET /internal/events?token=…&since=…` | 带 replay cursor 的 Brain 事件流 |
| `GET /internal/bridge?token=…` | Rust 与 Brain 间的双向 data-plane bridge |
| `GET /integrations/mcp/oauth/callback` | 完成 MCP authorization-code + PKCE 流程 |
| `POST /ide/content` | 通过 loopback broker 发布受管 IDE 内容 |
| `GET /ide/content/{handle_id}` | 读取 broker content handle |

生成的 HTTP 契约位于 `docs/api/headless-service-api.openapi.yaml`；事件流与 bridge frame 位于
`docs/api/headless-service-api.asyncapi.yaml`。它们与配对设备 spec 刻意分离，避免 service-only
命令被误认为公开移动端接口。

当前 catalog 包含 **450** 个 Headless 命令。服务启动时会编译内嵌的 Draft 2020-12 输入与输出
schema，在 dispatch 前校验输入，并在写入成功 receipt 前校验输出。请求不符合契约时返回
`422 contract_input_violation`；实现输出与 schema 不一致时返回
`500 contract_output_violation`。违规详情只包含 instance path 与 schema path，不包含被拒绝的
值。`COGNIA_HEADLESS_CONTRACT_ENFORCEMENT=off` 只用于紧急回滚，不是兼容模式。

变更命令仍在执行时返回 `202`。`cognia host call` 会轮询 operation 路由直到 receipt 进入终态；
仅当旧服务对 operation 路由返回 `404` 时，才兼容性地重放完全相同的 `POST`。进程重启后，原先
处于 `queued`、`running` 或恢复中状态的操作会以 `operation_interrupted` 终止失败，不会永久
停留在 pending。

## Headless MCP OAuth

现有的 `mcp_oauth_status`、`mcp_oauth_load_entry`、`mcp_oauth_authenticate`、
`mcp_oauth_refresh` 与 `mcp_oauth_clear` 均为 service-owned，并按 account 隔离。将
`COGNIA_PUBLIC_URL` 设置为外部可访问的 HTTPS origin；授权 redirect 为
`$COGNIA_PUBLIC_URL/integrations/mcp/oauth/callback`。认证流程把 PKCE state 与动态 client 信息
写入加密 secret store，返回 authorization URL；每个 256-bit state 最多存活三分钟且只能消费
一次。access token 不会出现在 callback HTML 或完成事件中。只有明确的 local-debug 配置才允许
loopback HTTP callback。

## Agent-first 运维 CLI

Rust `cognia` 二进制内嵌生成的 Headless 命令目录，并通过 `cognia host` 暴露。命令发现、
schema 查看、skills 和 dry-run 均可离线工作；实际调用和事件流始终受 loopback service-token
边界约束。

```bash
cognia host categories
cognia host resources --category development
cognia host skills list
cognia host skills list --kind workflow
cognia host skills install --scope project
cognia host skills read cognia-host-development
cognia host commands --query session
cognia host commands --resource git --operation read
cognia host schema session_list
cognia host call session_list --data '{"limit":20,"offset":0}'
cognia host events --event claude://message
```

未设置 `COGNIA_SERVICE_TOKEN` 时，CLI 会调用同机的
`cognia-server issue-service-token`，令牌只保留在内存。CLI 信任 `COGNIA_DATA_DIR` 中持久化的
自签证书，不提供跳过 TLS 校验的选项。high 和 critical 风险命令需要交互确认，或使用已经由
用户明确批准的全局 `--yes`；该确认只是运维防误触层，不是第二套授权系统。

生成的 catalog 会把每个命令严格归入一个稳定领域：`sessions`、`agents`、`tasks`、
`automation`、`connectors`、`extensions`、`knowledge`、`development` 或 `system`。
`cognia host categories` 会输出各领域的操作数、风险分布及对应内嵌 skill。
`cognia host resources` 会列出各领域中由生成器确定的资源组，`commands --resource <id>` 可以在
不复制、也不猜测 RPC 树的前提下进一步缩小搜索范围。`cognia-host` skill 维护共用安全和输出
规则，另有九个领域 skill 负责聚焦命令选择，以及六个 workflow skill 覆盖只读观测、安全 Git、
agent 事故处理、备份恢复、扩展发布和 connector 投递。可通过
`skills list --kind core|domain|workflow` 过滤清单。

### 安装内嵌 Agent Skills

安装过程完全离线，并且必须明确指定目标 scope：

```bash
# 对当前用户的兼容 Agent 生效。
cognia host skills install --scope user

# 安装到最近的 Git worktree 根；不在 Git 中时使用当前目录。
cognia host skills install --scope project
```

两个 scope 分别使用 `$HOME/.agents/skills` 和 `<project>/.agents/skills` 这一共享 Agent
Skills 布局，因此 Codex、Gemini CLI、OpenCode 及其他兼容客户端可以发现同一组 16 个 skills。
安装后应刷新客户端的 skill 清单或重启会话。该命令不会连接 `cognia-server`，也不会读取凭据。

隐藏文件 `.cognia-host-manifest.json` 会记录 CLI bundle 版本以及每个受管文件的 SHA-256
哈希。后续安装只会更新或删除仍与上次 manifest 一致的文件。写入前会预检整个 bundle；被修改或
未登记的受管文件、损坏的 manifest，以及以符号链接存在的 `.agents`、skills 根目录或受管目标
都会返回 `skill_install_conflict`，且不会写入任何文件。仅当 Cognia 遗留的完整临时文件与当前
bundle 完全一致时，下一次成功重试才会恢复它；其他临时内容会报告冲突而不会被删除，并且 manifest
始终最后替换。应先把有意保留的修改移到别处，再通过
`cognia host skills read <skill> [path]` 恢复报错路径；也可以把全部 Cognia 受管目录和
manifest 一并移走后重试。安装器刻意不提供强制覆盖或部分安装模式。

在 Compose 或 Kubernetes 中，应在 server 容器或同一 Pod 内执行 `cognia host`。独立管理
Pod 不受支持，因为非 loopback peer 提交的 service token 会被服务端拒绝。

## 契约维护

Headless RPC 路径与公开 spec 共享命令 manifest 和 Rust allowlist 作为生成来源：

```bash
pnpm companion-api:gen
pnpm companion-api:check
pnpm companion-api:lint
```

dispatcher 新增命令后，生成器和 Rust parity test 会要求 Headless spec 同步公开；公开设备暴露仍需
通过更严格的 target 与 transport 分类。
同一生成器还负责内嵌 catalog hash、Brain bridge 的精简 identity 模块、OpenAPI 和 AsyncAPI。
Bridge protocol v2 会在 `hello` / `hello_ack` 的 catalog hash 或 contract version 不一致时拒绝
连接，因此旧 Brain 不会进入 ready 状态。
