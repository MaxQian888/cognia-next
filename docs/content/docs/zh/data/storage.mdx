# 本地存储与数据库治理

<TLDR>
  Cognia 使用多类本地存储。账号数据、浏览器凭据、Headless 持久化和原生 SQLite
  数据库分别拥有不同的负责人及恢复规则。核心表目录治理 CogniaDB 表，并不代表所有本地数据库。
</TLDR>

## 核心数据与 schema

`lib/db/schema.ts` 定义 `CURRENT_SCHEMA_VERSION` 和累计的 `CURRENT_SCHEMA`，构造函数只注册当前 schema。旧的逐版本声明链已不是现有实现，不能假定每次打开数据库都会执行历史行迁移。

数据库名称由账号和 runtime 初始化流程选择。`cognia-claude` 是历史名称及构造函数默认值，不代表所有账号数据库。复用 `lib/accounts/account-db.ts` 和现有 runtime 选择器，不要自行创建命名或重命名已有数据库。

`lib/db/storage-layout.ts` 在打开已有账号数据前检查布局标记。缺少标记表、布局不同或 schema 较新时拒绝打开，原数据仍保留在磁盘上；重置需要单独的用户操作。同一受支持布局内较低的 schema 可以获得新表，但不会自动转换旧行结构。

策略权威来源是 `lib/data-governance/table-catalog.ts`，包含表角色、保护方式、账号作用域、备份和同步范围、保留执行方、级联关系及查询预算。`docs/data-governance.generated.json` 记录当前 schema 和同步覆盖，使用原生命令更新并校验：

```bash
pnpm db:governance:write
pnpm audit:data-governance
pnpm audit:data-governance:test
```

新增核心表时，扩展现有领域模块，声明行类型及 `Table` 字段，修改 `CURRENT_SCHEMA`、提高 `CURRENT_SCHEMA_VERSION`，并登记目录策略。检查备份、同步、删除及保留策略的调用链；测试受支持的重新打开及失败行为。仅提高版本号不能替代数据迁移。

## 浏览器与移动端归属

| 存储类别                    | 源码负责人                                                                          | 治理边界                                            |
| --------------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------- |
| 账号内容和动态插件表        | `lib/db/schema.ts`、`lib/plugin/dexie/`                                             | 账号选择、内容加密、目录策略、领域事务              |
| 账号注册表                  | `lib/accounts/account-db.ts`                                                        | 账号元数据、绑定和 profile 状态，与内容重置分别管理 |
| Runtime target 注册表       | `lib/runtime/target-registry.ts`                                                    | 目标定义及每个账号的当前目标                        |
| 浏览器 vault                | `lib/runtime/browser-vault.ts`                                                      | 凭据材料，不能作为普通缓存清除                      |
| Target 迁移和移动端接管日志 | `lib/runtime/target-database-migration.ts`、`lib/companion/mobile-host-adoption.ts` | 恢复及续跑依据，不适用普通 TTL 清理                 |
| 快速解锁和浏览器 keyring    | `lib/accounts/quick-unlock/device-pepper.ts`、`lib/keyring/index.ts`                | 设备解锁材料与凭据存储                              |
| 壁纸 blob                   | `lib/appearance/wallpaper-storage.ts`                                               | 独立的原生 IndexedDB 存储                           |
| Companion 配对配置          | `lib/tauri/companion-storage.ts`                                                    | 平台安全存储及浏览器降级实现                        |
| UI 偏好持久化               | `stores/persist-storage.ts`                                                         | Web Storage 适配器，不是账号数据权威库              |

`lib/scheduler/scheduler-db.ts` 的旧 SchedulerDB 适配器现在访问账号数据；不要根据历史名称推断它仍是独立可写数据库。

## Headless 持久化与恢复

`cli/src/db/bootstrap.ts` 恢复默认的逐表快照格式：manifest 加每张表一个 JSON 文件。脏表刷盘避免读取无关表，但仍读取和序列化整张脏表。生产 snapshot-v3 的文件操作已异步化，并保留文件同步、备份、替换及目录同步顺序。整表 JSON 序列化仍在 JavaScript 线程上执行，异步文件 I/O 不等于增量序列化。

快照通过临时文件、文件同步、上一代备份及替换落盘。损坏或不兼容的快照会被隔离。当正式文件缺失但隔离代仍存在时，启动持续拒绝该存储，直至恢复兼容的正式快照；supervisor 重启不能把损坏误当作全新空库。修复后的正式文件优先于历史隔离文件。

`cli/src/serve/persistence/` 的 ledger 路径另有快照、journal 和可选 SQLite 后端。压缩必须包含准备 checkpoint 期间已接受的提交，保持序号连续，并由关闭流程等待完成。后端选择由 runtime 单独决定；修改实现不会自动切换已有安装的后端。

## 原生 SQLite 归属

| 存储类别                                 | 源码负责人                                                    |
| ---------------------------------------- | ------------------------------------------------------------- |
| 向量与 payload                           | `crates/cognia-vector/src/db.rs`                              |
| Agent 会话、转录和摘要                   | `crates/cognia-agent-state/src/agent_session_store/`          |
| Provider profile 和目录修订              | `crates/cognia-agent-state/src/provider_profiles/`            |
| 任务和监视器                             | `crates/cognia-jobs/src/store.rs`                             |
| Scheduler 元数据                         | `crates/cognia-scheduling/src/scheduler/metadata_store.rs`    |
| Workflow 运行、等待点、游标及事件        | `crates/cognia-scheduling/src/workflow/run_mirror.rs`         |
| Integration spool 和 deadletter          | `crates/cognia-scheduling/src/workflow/integration_spool.rs`  |
| 任务 workspace 注册、bundle 和 blob 文件 | `crates/cognia-task-workspace/src/store.rs`                   |
| 每插件 SQL 和 managed IDE 状态           | `crates/cognia-plugin-runtime/src/api_bridge.rs`              |
| Companion 消息与会话                     | `src-tauri/src/companion_api/store.rs`                        |
| Companion 安全状态                       | `src-tauri/src/companion_api/security_store.rs`               |
| Signaling 注册                           | `src-tauri/src/companion_api/signaling/registration_store.rs` |
| RPC 幂等凭据                             | `src-tauri/src/companion_api/idempotency.rs`                  |

Integration spool 与 workflow mirror 共用数据库路径，Companion AppStore 和 SecurityStore 也可能共用文件。负责人数量和数据库文件数量应分别统计，连接设置可能影响其他负责人。当操作仍共享单连接互斥锁时，WAL 不会使其自动并行。

外部 Agent 会话、CCSwitch 和浏览器 cookie 导入读取其他应用拥有的数据库，不属于 Cognia 的写入及清理权限范围。

原生向量 Tauri 命令通过 blocking worker 执行初始化、SQLite 操作、锁等待及文件元数据读取。`VectorState` 副本共享同一个 lazy store 和 reset 锁。这避免阻塞 async executor，不会让底层单连接自动并行或改变搜索结果；取消等待不会中断已经开始的工作。

## 删除与保留

使用领域删除入口，包括 `lib/db/sessions.ts` 和 `lib/db/project-scope.ts`。删除父记录时，应在事务内清理其拥有的派生数据及引用，并记录适用的同步 tombstone。普通会话分支和共享媒体有独立归属。

媒体清理复用 `lib/db/message-media-refs.ts` 中的引用 hash 和宽限期。少量候选不得扫描整个媒体库；提交后的垃圾回收失败，不应把已提交的父记录删除报告为回滚。

草稿 revision 分配、写入及父会话/删除标记检查处于同一事务。乐观创建的草稿可以先于父会话落库；已明确删除且父会话缺失时拒绝迟到的草稿。未读写入要求父会话存在。项目删除在事务内确定成员，并同时写入删除标记；标记写入失败时整体回滚。

受治理的 tombstone 清理仅在存在明确会话删除标记、父会话及其消息历史均缺失时，回收遗留草稿、未读状态、输入历史、转录缓存和媒体引用。每页读取 250 个标记，候选 Blob 逐个读取。共享媒体、上传宽限期及重试依据会保留；没有标记的缺失父会话不会触发回收。标记通常保留 90 天，尚未完成的回收继续保留所需证据。修改代码本身不会扫描用户真实数据库。

插件 SQL 按插件复用连接，Host 管理的 IDE 状态使用独立缓存和文件，并保持既有 scope 分区。两种缓存均拒绝锁定/未绑定账号，并在账号切换及退出时清空。这防止复用旧缓存，但不会中断已经获得连接的 SQL。

`lib/storage/retention.ts` 调用既有保留执行器。新增高频写入表应扩展其领域策略及执行器。审计历史、deadletter、迁移日志和已消费上传凭据不能默认丢弃，清理前须明确保留及重试要求。

## 性能与验证

- 交互查询使用索引及有限分页；加载整张加密表还会支付每行解码和解密成本。
- SQLite 批处理在事务内复用 prepared statement，同时保留回滚及向量、正文一致性。
- 测试并发写入、关闭、写入失败、恢复重试、共享引用及账号边界。
- 区分受控样本的前后对比和真实桌面端、移动端延迟；单元测试及临时 SQLite 基准不能代表用户实际耗时。
