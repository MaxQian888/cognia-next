# 账号同步协议 v1

<Status variant="beta">§2–7 与 §9 已实现，受构建开关控制 · §8、§10–13 计划中</Status>

[ADR-0215](../adr/0215-one-person-one-encrypted-sync-space-many-writable-hosts) 的规范性配套文档。
ADR 记录"为什么"，本页记录"具体字节"。只要 §0 的不变量成立，本页可以细化而无需修订 ADR。
每次变更都要提升 `protocolVersion` 或只新增可选字段。第 2 阶段实现了 §2–5（密钥与设备登记），第 3a 阶段实现了 §6、§7 和 §9（操作日志、实时更新与合并）；快照（§8）、大文件、租约、计数器和账号生命周期尚未实现。

## 0. 不变量（由 ADR 固定）

1. 服务器从不接收明文的行内容、字段名、表名、资源名或密钥值。
2. 服务器从不持有能解密用户数据的密钥。
3. 每个操作都由一台已加入、未被吊销的设备签名；设备登记表本身是一条由客户端校验的签名链。
4. 合并只在客户端进行。服务器负责排序、去重、存储和转发。
5. 一个账号 ⇄ 一个 Durable Object。在每台设备上，一个账号 ⇄ 最多一个本地档案。

## 1. 原语

所有原语在各端的 WebCrypto 中都可用，Rust 侧也都有仓库已在使用的 crate（`p256`、`hkdf`、`aes-gcm`）。

| 用途 | 原语 |
| ---- | ---- |
| 设备签名 | ECDSA P-256，SHA-256，IEEE P1363 签名（64 字节） |
| 把密钥密封给设备 | HPKE base 模式（RFC 9180）：DHKEM(P-256, HKDF-SHA256)、HKDF-SHA256、AES-256-GCM |
| 对称加密 | AES-256-GCM，96 位随机 nonce |
| 密钥派生 | HKDF-SHA256 |
| 哈希 | SHA-256 |
| 线上的二进制 | base64url，无填充 |

下文的 `label(x)` 表示 ASCII 字符串 `cognia-sync/v1/x`。

## 2. 标识符

| 标识 | 形式 |
| ---- | ---- |
| `spaceId` | `base64url(SHA-256(label(space) ‖ 0x00 ‖ iss ‖ 0x00 ‖ sub))`。Durable Object 为 `idFromName(spaceId)`。与签发方绑定，所以 staging、生产和自托管签发方永远不会共用一个空间。 |
| `deviceId` | `dev_` + 16 个 CSPRNG 字节的 26 位 Crockford base32（`^dev_[0-9A-HJKMNP-TV-Z]{26}$`） |
| `requestId` | `req_` + 同样的 26 位形式 |
| `epoch` | 无符号整数，从 1 开始 |
| `entryHash` | `SHA-256(label(entry-hash) ‖ 0x00 ‖ JCS(entry))`，对**不含**签名的条目计算（ECDSA 签名不需要私钥就能改写成 `(r, n−s)`，所以绝不能参与哈希） |
| `genesisHash` | 登记表第 0 条的 `entryHash` |
| `serverSeq` | 无符号 53 位整数，由 DO 分配，每个账号内无间隙（第 3 阶段） |
| `deviceSeq` | 无符号整数，每台设备从 1 开始，无间隙（第 3 阶段） |
| `opId` | `(deviceId, deviceSeq)`（第 3 阶段） |
| 行 id（在密文内） | 新行用 UUIDv7；已有 id 原样保留（第 3 阶段） |

凡是哈希或签名覆盖结构化数据的地方，规范编码都是 RFC 8785 JCS。JCS 里的二进制值用不带填充的 base64url；数字是小于 2^53 的整数。下文的每个哈希、签名和 HKDF `info` 都作用于 `utf8(label) ‖ 0x00 ‖ bytes`。

## 3. 密钥

### 3.1 设备密钥

每台设备生成：

- `signKey`：ECDSA P-256。
- `encKey`：ECDH P-256（HPKE 接收方密钥）。

公钥以原始非压缩点（65 字节，base64url）传输，即 HPKE 的序列化形式。它们与配对用的 P-256 ES256 密钥（ADR-0021/0059）分开，吊销同步权限不会破坏配对，反之亦然。在本地，两把私钥以 JWK 形式存在本地配置文件的保险库里（`lib/runtime/browser-vault.ts`），使用时重新导入为不可导出的密钥。

### 3.2 恢复密钥

- `rk`：128 个随机位，显示为 26 个 Crockford base32 字符，`XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XX`（最后一个字符含两个零位）。解析时忽略大小写、连字符和空格，并把 `I`/`L` 视为 `1`、`O` 视为 `0`。
- `seed = HKDF-SHA256(ikm = rk, salt = utf8(spaceId), info = label(recovery), L = 32)`。
- `encIkm = HKDF-Expand(seed, label(recovery-enc), 32)`，`signIkm = HKDF-Expand(seed, label(recovery-sign), 32)`。
- 两者分别按 RFC 9180 §7.1.3 `DeriveKeyPair`（DHKEM(P-256)，掩码 `0xff`，候选计数器）得到 P-256 密钥对：`recoveryEnc`（ECDH，HPKE 接收方）和 `recoverySign`（ECDSA）。只有公钥部分会上传。
- 任何设备都能把新纪元密钥密封给 `recoveryEncPub`，无需知道 `rk`。`recoverySign` 让持有恢复密钥的人在手边没有其它设备时也能加入设备，并为恢复密钥的每次更换会签，所以除此之外没有人（包括服务器）能设置它们。

### 3.3 纪元密钥

- `SK_e`：纪元 `e` 的随机 256 位同步密钥。
- 子密钥：`HKDF(SK_e, salt = utf8(spaceId), info = label(<用途>))`：
  - `commit` → `keyCommit_e = HMAC-SHA256(commitKey, JCS({spaceId, epoch: e}))`，写在开启该纪元的签名条目里；
  - `chain` → `prevWrap_e = AES-256-GCM(chainKey, nonce, SK_{e-1}, AAD = label(chain) ‖ 0x00 ‖ JCS({spaceId, epoch: e-1}))`，写在同一条目里，所以当前密钥能打开全部历史；
  - `name` → 设备显示名（`nameCt`，见 §4）；
  - `op` → 操作加密（§7.1，第 3a 阶段）；
  - 之后的阶段再加 `snap`、`blob-id`、`res-id`。
- 服务器上只存密封后的形式：每台活跃设备一个 HPKE base 模式信封，再加一个给 `recoveryEncPub` 的，`info = label(epoch-envelope)`，`AAD = JCS({v: 1, spaceId, epoch, recipient, recipientEncPub})`。
- 设备只对登记表**当前**纪元使用信封，而且打开后的密钥必须与该纪元已签名的 `keyCommit` 一致。base 模式 HPKE 不认证封装者，认证靠这个承诺。
- 在本地，设备把密钥链作为保险库机密保存。

### 3.4 纪元轮换的触发条件

- 吊销一台设备（吊销条目开启新纪元）。
- 用恢复密钥加入设备。
- 重新生成恢复密钥（旧的恢复信封被删除）。
- 用户主动“轮换密钥”。

每次轮换都删除上一纪元的信封；历史仍可通过已签名的 `prevWrap` 链访问。

## 4. 设备登记表

只增不改的哈希链。每个元素是 `{entry, sigs: [{signer, sig}]}`，`signer` 是一个 `deviceId` 或 `"recovery"`，`sig` 是对 `label(entry) ‖ 0x00 ‖ JCS(entry)` 的 ECDSA 签名。

```
entry = { v: 1, spaceId, seq, prev, type, at, ... }     // seq 0 时 prev = null，否则为上一条的 entryHash
DeviceDescriptor = { deviceId, platform: "desktop"|"mobile"|"web", signPub, encPub, nameCt: { epoch, nonce, ct } }
EpochBlock       = { epoch, keyCommit, prevWrap?: { nonce, ct } }   // epoch > 1 时必须有 prevWrap
RecoveryKeys     = { signPub, encPub }
```

| 类型 | 字段 | 签名者 | 效果 |
| ---- | ---- | ------ | ---- |
| `genesis`（seq 0） | `device`、`recovery`、`epoch`（1） | 设备本身**和** `recovery` | 第一台设备；固定恢复密钥 |
| `add-device` | `device`、`via: "approval"`、`requestId`、`transcriptHash` | 批准的活跃设备 | 在当前纪元加入设备 |
| `add-device` | `device`、`via: "recovery"` | `recovery` **和**新设备 | 加入设备；同一批次中必须紧跟它发出的 `epoch-rotate` |
| `revoke-device` | `deviceId`、`epoch`（n+1） | 目标以外的活跃设备 | 吊销；新纪元 |
| `recovery-rotate` | `recovery`（新）、`epoch`（n+1） | 活跃设备**和**新的 `recovery` | 更换恢复密钥；新纪元 |
| `epoch-rotate` | `epoch`（n+1） | 活跃设备 | 新纪元 |

`platform: "headless"` 已保留；第 2 阶段拒绝它（无头主机还没有保险库）。

`validateAppend`（客户端与 Worker 共用）：`seq` = 头部 + 1，`prev` = 头部哈希；每个签名者在该条目之前处于活跃状态；`deviceId`、`signPub`、`encPub` 永不复用（含已吊销的）；不能吊销自己；不能吊销最后一台活跃设备；最多 32 台活跃设备；每条最多 8 KiB；纪元块的 `epoch` = 当前 + 1。

`nameCt` 是用 `nameCt.epoch` 的 `name` 子密钥加密的显示名：`AES-256-GCM(nameKey, nonce, pad64(utf8(name)), AAD = JCS({spaceId, deviceId, epoch}))`。

### 4.1 客户端校验（`foldRegistry`）

1. 第 0 条是两个签名都通过的 `genesis`。已有固定值的设备要求 `genesisHash` 等于固定值。没有固定值的设备只通过批准记录（§5.2）或恢复密钥匹配（§5.3）信任它。
2. 之后每一条都通过 `validateAppend`。
3. **回滚与分叉：**保险库里的固定值是 `{genesisHash, seq, hash, epoch}`。取回的链必须包含 `entries[pin.seq]` 且其 `hash = pin.hash`。更短的链，或该位置哈希不同，即报错“服务器返回了更旧或不同的设备列表”：不写入、不删除任何东西。固定值只会前移。
4. **纪元：**只对当前纪元打开自己的信封并核对 `keyCommit`；沿 `prevWrap` 回溯到尚未持有的最早纪元，每个解包出的密钥都与它自己的 `keyCommit` 核对。
5. 设备密封所用或信任的每把公钥都来自折叠后的登记表，绝不来自服务器的其它响应。

### 4.2 剩余风险

服务器可能向不同设备展示不同但各自有效的链（分裂视图）。设备列表显示“设备列表指纹”（头部哈希），用户可在设备之间比对。第 3a 阶段的操作还不携带签名者的头部；把它作为信封的可选字段加入，留给第 3b 阶段。

## 5. 加入

以设备身份发出的请求携带 `Cognia-Device-Proof: b64url(JCS({v: 1, spaceId, deviceId, method, path, bodySha256, iat})) "." b64url(sig)`，由设备的 `signKey` 签名（`label(device-proof)`），在 `|iat − now| ≤ 120 s` 内有效。每个响应都带 `Cognia-Server-Time`，客户端据此校正时钟。

### 5.1 创世（第一台设备）

1. `GET /v1/space` 返回 `empty`。
2. 生成设备密钥、`rk`、`SK_1`。
3. 恢复确认关卡：用户重新输入随机挑选的四个字符，或下载恢复包并确认已保存。完成之前什么都不上传。
4. `POST /v1/space/genesis`，带创世条目（两个签名）和两个信封（自己、恢复）。`409 space_exists` 表示另一台设备抢先了；客户端改走 §5.2。
5. 服务器确认之后，设备才保存自己的密钥、密钥链和固定值。

### 5.2 由已有设备批准

先承诺后揭示，服务器无法针对替换的密钥穷举六位码。

1. 新设备 R 获取并折叠登记表；它的 `genesisHash`（`G_R`）此时尚未验证。
2. R 生成密钥和 `nonceR`（32 字节），`commit = SHA-256(label(sas-commit) ‖ 0x00 ‖ nonceR)`，并把显示名密封给每台活跃设备（`info = label(request-name)`，`AAD = JCS({spaceId, deviceId, recipient})`）。
3. `POST /v1/enroll/requests` `{deviceId, platform, signPub, encPub, commit, names, pop}`（`pop` = `signKey` 对请求体的签名，`label(enroll-request)`）→ `{requestId, expiresAt}`（15 分钟）。
4. 活跃设备在轮询（§5.6）中看到请求并发出通知。
5. 用户在批准方 A 上打开请求时，A 生成 `nonceA`，只保存在内存中并提交。服务器每个请求只接受一个批准方。
6. R 看到 `nonceA` 后提交 `nonceR`；服务器用 `commit` 核对。
7. 双方各自用自己的值计算 `T = JCS({v: 1, spaceId, genesisHash, requestId, deviceId, platform, signPub, encPub, commit, approverDeviceId})`，`code = uint64be(HKDF-SHA256(ikm = nonceR ‖ nonceA, salt = SHA-256(label(sas) ‖ 0x00 ‖ T), info = label(sas-digits), L = 8)) mod 10^6`，显示为 `123 456`。A 绝不从服务器重新读取 `nonceA`；R 在揭示被接受之前不显示码。
8. 用户确认两边的码一致后，A 追加 `add-device {via: "approval", requestId, transcriptHash: SHA-256(T)}`，并为 R 附上 `SK_e` 的信封。
9. R 获取登记表，要求 `genesisHash = G_R`、自己的条目由活跃的 `approverDeviceId` 签名、`transcriptHash = SHA-256(T)`；然后打开信封、核对 `keyCommit` 并保存。

服务器必须在 A 选定 `nonceA` 之前确定给 A 看的密钥，在 R 揭示 `nonceR` 之前确定给 R 看的随机数；每次可见的尝试替换成功的概率为 10^-6。给 R 看伪造的链会改变 `genesisHash`，从而改变码。

### 5.3 恢复

1. 折叠登记表；从输入的恢复密钥派生恢复密钥对，必须与登记表当前的 `recovery` 一致（否则提示“这个恢复密钥与此账号不匹配”）。
2. `GET /v1/envelopes/recovery`，打开并核对 `keyCommit`。
3. 生成设备密钥并提交一个原子批次：`add-device {via: "recovery"}`（由 `recovery` 和新设备签名），紧跟 `epoch-rotate`（由新设备签名），附上给每台活跃设备、自己和恢复的信封。
4. 提议重新生成恢复密钥（默认是）。其它设备显示“有设备用你的恢复密钥加入了”。

### 5.5 吊销、重新生成、轮换

- **吊销：**`revoke-device` 带新纪元，信封给`(active − target) ∪ {recovery}`。被吊销的设备从 `403 device_revoked` 得知，但只有在找到针对自己 id 的有效签名吊销条目之后才行动：删除设备密钥和密钥链，保留固定值，并记录何时被哪台设备移除。无法验证的 403 不删除任何东西。（锁定配置文件和删除已同步的机密随机密类在第 5 阶段到来。）
- **重新生成恢复密钥：**新的 `rk` 通过确认关卡后，追加 `recovery-rotate`；服务器删除旧的恢复信封。
- **轮换：**`epoch-rotate`。

### 5.6 第 2 阶段服务器 API

| 路由 | 认证 | 用途 |
| ---- | ---- | ---- |
| `GET /v1/space` | bearer | `{state: empty \| ready, genesisHash?, head, epoch, protocolVersion}` |
| `GET /v1/registry?after=N` | bearer | 条目 |
| `POST /v1/space/genesis` | bearer | 创世；`409 space_exists` |
| `GET /v1/envelopes/recovery` | bearer | 当前恢复信封 |
| `POST /v1/enroll/requests` | bearer + `pop` | 创建（待处理 ≤ 3，每小时 ≤ 10） |
| `GET /v1/enroll/requests/:id` | 待加入设备证明 | 状态、批准方随机数 |
| `POST /v1/enroll/requests/:id/reveal` | 待加入设备证明 | `nonceR` |
| `DELETE /v1/enroll/requests/:id` | 待加入设备证明 | 取消 |
| `GET /v1/enroll/requests` | 活跃设备证明 | 轮询（前台时每 20 秒） |
| `POST /v1/enroll/requests/:id/nonce` | 活跃设备证明 | `nonceA`，只一次 |
| `POST /v1/enroll/requests/:id/deny` | 活跃设备证明 | `denied` 或 `mismatch` |
| `GET /v1/envelopes/self` | 活跃设备证明 | 当前信封 |
| `POST /v1/registry` | 签名设备证明 | 原子追加 1–2 条及信封；`409 head_moved` |

服务器强制执行 `validateAppend`、完整的信封集合（恰好是该条目之后的活跃设备加恢复，每个 `recipientEncPub` 与登记表中的密钥一致）、请求状态与过期，并在每条证明路由上先拒绝已吊销设备，再读取任何内容。Bearer 是签发方的访问令牌（`aud` = 同步 API，`typ` = `at+jwt`，ES256，第一方客户端）。

### 5.4 带着本地数据加入（ADR Q5）

第 3a 阶段。登记完成后，负责某个数据库的设备（每个数据库一个窗口，或无界面主机的 brain）启用变更捕获，并决定如何处理它已有的同步行：

- **播种**，自动进行：本设备没有同步行，或账号的操作日志为空（第一台设备）时。每个同步行按 `hlc = (row.updatedAt ?? row.createdAt ?? now, 0, deviceId)` 合成字段时钟，整行放入待发送队列。
- **询问**，双方都有数据时，并先给出预览（本机每张表的行数、账号日志中的操作数）：
  - **合并**（默认）：按上面的方式播种，之后账号的操作逐字段合并（§9）；
  - **替换**：在捕获忽略的事务中删除本设备的同步行，然后从 0 开始拉取账号的日志。

两种选择都会改动本地数据，所以先写入一份加密的 ADR-0001 备份并记入备份历史；备份失败则什么都不改。无界面主机使用事先用 `cognia-agent account-sync data --merge|--replace` 给出的答案。被移除后重新加入的设备保留字段时钟（它们在同一空间里仍是真实的先后顺序），但游标和序号从头开始。第 3b 阶段会把“从 0 拉取”换成最新快照加其后的操作。

## 6. 会话与实时更新

第 3a 阶段。没有单独的会话令牌：和第 2 阶段一样，每个请求都带 bearer 令牌和 §5 的设备证明。

1. `POST /v1/socket/ticket`（活跃设备证明）→ `201 {ticket, expiresAt}`：32 个随机字节，一次性，有效期 60 秒，绑定到空间和设备。
2. WebSocket `GET /v1/socket?space=<spaceId>&ticket=<ticket>`。浏览器无法给 WebSocket 设置请求头，所以这个路由跳过 bearer 检查：Worker 把它转发给空间，由空间消费票据，拒绝未知、已用或过期的票据（`401 bad_ticket`）以及已吊销的设备（`403 device_revoked`）。Durable Object 用休眠 API 接受连接，并发送 `{type: "hello", lastSeq, registryHead}`。
3. 每次存入推送后，服务器发送 `{type: "ops", lastSeq}`；每次登记表追加后发送 `{type: "registry", head}`，因此已连接的设备会立刻看到等待中的加入请求，而不用等下一次 20 秒轮询。客户端每 30 秒发送 `ping`，服务器回 `pong`，不会唤醒对象。被吊销设备的连接以代码 `4403` 关闭。
4. 退路：连接被拒、断开或不可用时，改用长轮询 `GET /v1/ops?after=<serverSeq>&wait=25`（中国大陆风险，见 ADR 风险部分），同时按退避重试 WebSocket。

WebSocket 只负责通知，操作总是通过 §7.5 的拉取获得。

## 7. 操作

### 7.1 信封

```
Op {
  deviceId, deviceSeq,         // deviceSeq: gapless per device, from 1
  hlc: { ms, c },              // the latest clock among the fields it carries
  epoch, schemaVer,            // schemaVer: the writer's sync schema version (§9)
  cls: "c"|"s"|"k"|"x"|"a",    // content, settings, secrets, crdt, append-only
  nonce, ct,                   // ct padded to the next bucket (§7.4)
  sig                          // ECDSA P-256 (P1363) by the device's signKey
}
opKey = HKDF(SK_epoch, salt = utf8(spaceId), info = label(op))
ct    = AES-256-GCM(opKey, nonce, pad(utf8(JSON(payload))), AAD)
AAD   = label(op)     ‖ 0x00 ‖ canonical(spaceId, cls, schemaVer, epoch, deviceId, deviceSeq)
sigIn = label(op-sig) ‖ 0x00 ‖ canonical(spaceId, deviceId, deviceSeq, hlc.ms, hlc.c,
                                          epoch, schemaVer, cls, nonce, ct)
```

`canonical(...)` 按给出的顺序拼接各字段，每个字段编码为 `u32-be 长度 ‖ 字节`（整数用十进制 ASCII，`nonce` 和 `ct` 用其 base64url 文本）。表名在 `ct` 内传输，只有粗粒度类别是可见的。第 3a 阶段只写 `c`（内容）和 `s`（设置），其余类别保留。填充前超过 512 KiB 的载荷不会发送：该行留在本地，设备会说明原因。

### 7.2 明文载荷

```
{ t: <table>, id: <rowId>, k: "upsert",
  f: { <field>: [<value>, <hlc>] },   // the fields this op writes, each with its clock
  u?: { <field>: [<value>, <hlc>] } } // fields from a newer schema, kept untouched (§9)

{ t: <table>, id: <rowId>, k: "delete", at: <hlc> }
```

时钟是编码后的 HLC（§9）。每个字段带着自己的时钟，所以一个操作可以携带不同时间写入的字段：待发送队列只记录*哪些*字段变了，操作在推送时由行的当前值构造，一连串写入（例如正在生成的回复）因此合并成一个操作。设置以虚拟行 `t: "settings", id: <key>` 传输，值放在字段 `value` 中。`k: "append"` 和 `k: "crdt"`（Yjs 更新）保留。

### 7.3 推送

`POST /v1/ops` `{ops: Op[]}`（1–256 个操作，请求体 ≤ 1 MiB），活跃设备证明。DO 依次：

1. 操作日志超过只读配额（§14）时拒绝推送；
2. 检查每个操作都来自推送设备且 `deviceSeq` 连续；不大于该设备已存最大序号的操作只确认不存储（丢失应答后的重发），之后若有间断返回 `409 seq_gap {expected}`；
3. 检查每个新操作都在登记表的当前纪元下，否则返回 `409 epoch_stale {epoch}`（客户端获取新密钥后重新封装）；
4. 用该设备在登记表中的 `signPub` 校验每个 `sig`；
5. 把新操作存为**一行 SQL** `{firstSeq, lastSeq, deviceId, at, bytes}`，分配一段连续的 `serverSeq`；
6. 返回 `{deviceSeq, firstSeq, lastSeq}`（没有新操作时 `firstSeq`/`lastSeq` 为 `null`），并发出 `{type: "ops", lastSeq}`（§6）。

客户端只结清应答中确认存储的那部分操作，因此应答丢失后带着更新操作重发的推送不会丢失任何操作。

### 7.4 填充

加密前，明文以 `0x80 0x00…` 后缀填充到下一个 PADMÉ 桶，密文长度最多泄露 O(log log n) 位。

### 7.5 拉取

`GET /v1/ops?after=<serverSeq>[&wait=<0–25>]`，活跃设备证明 → `{batches: [{firstSeq, lastSeq, deviceId, ops}], more, lastSeq, registryHead}`：按顺序返回完整批次，最多约 1 MiB 或 64 批（至少一批）。带 `wait` 且没有新操作时，应答会挂起，直到有推送到达或等待超时。`after` 记为该设备确认到的序号（供第 3b 阶段回收墓碑使用）。第 3b 阶段会在 `after` 早于压缩下限时返回 `410 {snapshot: <manifestId>}`。

客户端只信任服务器给出的顺序。它对照已验证的设备列表检查每个操作的签名者（被移除设备的操作只有在移除前的纪元下封装才算数，且同一设备的纪元不会倒退），校验签名，用该纪元的密钥解开，然后在每批一个本地事务中合并（§9）并移动游标。它跳过自己的操作（写入时已应用），把暂时无法应用的操作（§9 的模式版本差异，或尚未持有的纪元密钥）原样暂存在本地收件箱，等能应用时再重放。

## 8. 快照

- 只有持有 `compaction` 租约（§11）的设备写快照。
- 内容：`upToSeq` 处的物化状态（行加每字段时钟），按 4 MiB 分块，每块用 `snap` 子密钥做 AES-GCM，`AAD = label(snap) ‖ spaceId ‖ snapshotId ‖ chunkIndex ‖ chunkCount`。
- `PUT /v1/snapshots/{snapshotId}/chunks/{i}` 以随机键流式写入大文件存储；`POST /v1/snapshots/{snapshotId}` 登记 `{upToSeq, epoch, schemaVer, chunks: [{key, size, sha256}], sig}`。
- DO 保留最新两个快照，并删除 `lastSeq < upToSeq − 10 000` 的操作批次。
- 只有当所有活跃设备确认的 `serverSeq` 都越过墓碑（`isDeleted` 行）后，快照才会丢弃它们。90 天未出现的设备标记为 `stale`，必须从快照重新开始。

## 9. 合并规则（客户端）

- HLC：`{ms, c}`（48 位墙钟、16 位计数器），编码为 12 位十六进制的 `ms`、4 位的 `c`，再接 `deviceId`，所以字符串顺序就是时钟顺序。发送时 `send = max(local, now)`，同一毫秒内由计数器区分先后；接收时最多只采纳到 `now + 5 min`。超出的远端时钟会被应用，但不推进本地时钟（时钟偏快的设备无法永远获胜）。
- 时钟按行保存在本地附表 `syncFieldClocks`（`[table+rowId] → {fields: {field: hlc}, tombstone?}`）中，从不写入用户的行。
- `upsert`：逐字段比较，时钟更大的获胜。
- `delete`：按行处理。记录墓碑时钟并删除该行；但如果该行有字段是在删除之后写入的，该行保留，保留它的设备会重发整行，让已经删除它的设备重建。比墓碑旧的 upsert 不会让该行复活；更新的 upsert 会带着它携带的所有字段重新创建该行。
- 消息和其他行一样逐字段合并，而不是只追加：应用在回复流式生成时以及在图片工作台中会原地修改消息。
- `local` 字段（路径、运行时 id、向量索引、对尚未同步的表的引用）从不发送，也从不应用。
- 模式版本差异：客户端遇到 `schemaVer` 大于自身的操作时暂存不应用，并提示“更新 Cognia 以查看来自其他设备的修改”。它不认识的字段连同时钟保存在 `u` 中，下次写该行时原样回写。
- 设备关闭的类别的操作会被跳过；重新打开该类别时会重新播种并从 0 拉取。

## 10. 大文件

- 大文件 ID：`HMAC(blob-id 子密钥, SHA-256(明文))`，可去重且不暴露明文哈希。
- 每个大文件有自己的随机内容密钥，放在引用它的操作内；内容以 4 MiB 分块做 AES-GCM。
- `PUT /v1/blobs/{id}`（已存在则 409），`GET /v1/blobs/{id}`。
- 大文件存储接口：Cloudflare R2 绑定，或任意 S3 兼容端点（自托管，§15）。

## 11. 租约（执行放置）

```
POST /v1/leases/{resId}/acquire  {ttlMs: 30000}  → {generation, expiresAt} | 409 {holder, expiresAt}
POST /v1/leases/{resId}/renew    {generation}    → {expiresAt} | 409 lost
POST /v1/leases/{resId}/release  {generation}
```

- `resId = HMAC(res-id 子密钥, resourceName)`；资源名（`connector:<id>`、`schedule:<id>`、`session-turn:<id>`、`credential-refresh:<id>`、`compaction`）从不到达服务器。
- 每 10 秒续约；世代号在每个 `resId` 内单调递增，必须随每次对外操作一起携带，以隔离过期的持有者。
- 放置在客户端决定：租约过期后，设备在 `rank × 5 s` 后重试，排位依次为无头服务器 → 最近活跃的桌面 → 其他桌面；被固定的资源只由其设备尝试。手机和网页从不获取执行租约。
- 连不上 DO 的设备在租约本应过期时停止所持资源，从不自行授予。

## 12. 计数器

`POST /v1/counters/{counterId}/next` → `{value}`；`counterId` 与 `resId` 一样是 HMAC。用于议题编号（`issueCounters`）。

## 13. 账号生命周期

| 操作 | 端点 | 效果 |
| ---- | ---- | ---- |
| 吊销设备 | `POST /v1/devices/{id}/revoke {wipe}`（签名记录） | 关闭连接；拒绝请求；吊销方轮换纪元 |
| 移除本设备 | 以 `wipe: true` 自我吊销，然后在本地删除 | |
| 退出登录 | 无（本地操作） | 保留待发送队列；只在同一个 `spaceId` 下恢复 |
| 注销账号 | `POST /v1/account/deletion` → `{purgeAt: now + 7 d}`；`DELETE` 撤销 | `purgeAt` 时 DO 闹钟删除 DO 存储、大文件前缀和身份服务中的用户；通知各设备解绑，本地数据保留为普通本地档案 |

## 14. 配额

服务端可调。默认：操作日志加快照软上限 2 GB，大文件软上限 10 GB。超过软上限：大文件上传返回 `413 {code: "quota_blob"}`，操作仍被接受。超过软上限 × 1.25：除删除外一律拒绝（`413 quota_readonly`）。客户端显示用量并提供清理入口。

第 3a 阶段只强制操作日志的上限：已存操作超过 2.5 GB 后，每次推送都返回 `413 quota_readonly`。服务器无法从 `ct` 中分辨删除操作，所以在第 3b 阶段的压缩释放空间之前，删除也会被拒绝。

## 15. 自托管

同一套 Worker 运行在 `workerd` 下，Durable Object 的 SQLite 存在本地磁盘，大文件使用 S3 兼容存储（诊断服务器的技术栈已带有 MinIO）。作为 `deploy/compose` 的一个 profile 打包。在依赖这两点之前，先在第 3 阶段的 spike 中验证。

## 17. 测试向量

`packages/sync-protocol/fixtures/`（客户端和 Worker 共用的、不依赖 `@/` 的包）存放冻结的向量：`v1.json`（规范编码、签名、HPKE 密封、登记表）和 `v1-ops.json`（HLC 顺序、填充、规范操作与 AAD、一个封装好的操作、合并）。客户端、Worker 以及任何 Rust 使用方都必须通过这些向量。这是防止格式漂移的唯一手段（对照今天三份授权格式实现的情况）。
