# 数据模型与 Store

一支小队由一个类型模块 `types/agent/agent-team.ts` 描述，并在运行时由 `stores/agent/agent-team-store/` 下的一个 Zustand store 持有。自 **persist v8** 起，store 已经不是小队的家：Dexie 才是小队、队友和任务的权威来源，`localStorage` 那一份只剩模板、默认配置和少数视图偏好。

<Callout title="两个名词，一个子系统">
  ADR-0140 把产品名词改成了 **Squad（小队）**，并刻意没有动代码里的名词。下文每一个类型、store、
  action 和 Dexie 表仍然写作 `AgentTeam*`，包括改名之后才新增的那几张表，因为 `teams` 这个名字
  早已属于角色团队（Character Teams），那是另一个完全不同的功能
  （`lib/db/agent-team-definitions.ts:12-17`）。
</Callout>

<TLDR>
  `types/agent/agent-team.ts` 是权威 schema：`AgentTeam`（`:1409`）、`AgentTeamConfig`
  （`:410`）、`AgentTeammate`（`:955`）、`AgentTeamTask`（`:1018`）。store
  （`stores/agent/agent-team-store/store.ts:83`）是 `persist` **v8**，其 `partialize`
  （`:263`）只保留 `templates`、`defaultConfig`、`tasksView`、`editorSession`、
  `lastAdapterSyncVersion`，外加两个刻意保持惰性的字段。小队、队友和任务在 Dexie 中才是权威
  （`agentTeams`、`agentTeammates`、`agentTeamTasks`，在 schema v215 加入），由 `dexie-bridge.ts`
  镜像。消息、事件、共识、共享内存和委派这类运行态仍仅驻留内存。运行历史持久化在 `agentTeamRuns`
  与 `workflowRuns` 中。
</TLDR>

`riskGating`（ADR-0070）只会*抬高*计划闸门。操作者设置的 `requirePlanApproval` 永远不会被风险评估降下来。`allowedTools`、`disallowedTools`、`defaultPermissionMode` 和 `sandboxPolicy` 都是上限：队友只能收窄，永远不能突破。

### `AgentTeam`

这个聚合体由身份、配置、id 列表和汇总构成。

- **身份与作用域**：`id`、`projectId`、`name`、`description`、`task`、`sessionId`、`metadata`
- **配置与路由**：`config`、`routingAssessment`、`selectedExecutionPattern`、`dispatchDecision`、`externalPickup`
- **成员**：`leadId`、`teammateIds`、`taskIds`、`messageIds`
- **协作**：`sharedMemory`、`consensusIds`、`delegationIds`、`parentDelegationId`
- **汇总**：`status`、`progress`、`totalTokenUsage`、`finalResult`、`error`、`executionReport`
- **时间**：`createdAt`、`startedAt`、`completedAt`、`totalDuration`

`projectId` 是工作区边界。在搬到 Dexie 之前它虽然存在，却只是三处列表界面各自应用的一个过滤条件，所以清空工作区从来不会真的删掉一支小队。现在它是表上的索引。

## Store

### 状态

`AgentTeamState`（`stores/agent/agent-team-store/types.ts:32`）持有十个数据字段（`teams`、`teammates`、`tasks`、`messages`、`templates`、`events`、`consensus`、`sharedMemory`、`delegations`、`lastAdapterSyncVersion`）、五个视图字段，以及 `defaultConfig`。

其中三个视图字段是刻意的休眠，在类型上、初始状态里都有标注，并由 `store.test.ts` 和 `selectors.test.ts` 钉死。

| 字段 | 状态 |
| --- | --- |
| `activeTeamId` | 只有 `createTeam` 会写。作为最后兜底被 `selectActiveTeamConsensus`、`getActiveTeam` 和 `DelegationsPanel` 读取。不持久化，所以重新加载后它是空的，这正是每个真实界面都自己点名 team id 的原因。 |
| `displayMode` | **刻意惰性。** 持久化只是为了让旧版本写下的 blob 能原样往返，自紧凑/展开开关随工作区一同退役后就没有读取方了。 |
| `workspaceTab` | **刻意惰性**，原因相同。它的类型上带着同一条标注的类型层一半。 |

`tasksView` 和 `editorSession` 是有真实读取方的活跃视图偏好。

### 持久化

```ts
// stores/agent/agent-team-store/store.ts:263-277
export function partializeAgentTeamState(state: AgentTeamState) {
  return {
    templates: state.templates,
    defaultConfig: state.defaultConfig,
    displayMode: state.displayMode,
    workspaceTab: state.workspaceTab,
    tasksView: state.tasksView,
    lastAdapterSyncVersion: state.lastAdapterSyncVersion,
    // teams / teammates / tasks are Dexie's from v8 on. Leaving them here as
    // well would give the subsystem two durable copies with no rule for which
    // wins, and the localStorage one cannot be workspace-scoped or synced.
    // `dexie-bridge.ts` owns them; only what is left is UI-shaped preference.
    editorSession: state.editorSession,
  }
}
```

存储键是 `cognia-agent-teams`，由 `activateAgentTeamAccountStorage`（`:303`）按账户改指到 `cognia-agent-teams:<accountId>`。那条路径绕开了 `migrate` 和 `onRehydrateStorage`，所以它自己又跑了一遍 `resetStaleTeamStatuses` 和 `backfillTeamProjectIds`。

`PERSIST_VERSION` 是 **9**。文件头的迁移阶梯记录了每一步，其中三步对读取旧数据尤其重要。

- **v8 到 v9**（ADR-0169）从每个已持久化的定义、模板和 `defaultConfig` 上剥掉旧的运行时选择器（`config.runtimeVersion`）。同样的剥离也在 Dexie 水合（`migrateHydratedDefinitions`）、同步入站行以及 CLI 与插件边界上执行，因此任何读者都不会再看到它。

- **v3 到 v4** 才第一次让 `teams`、`teammates` 和 `tasks` 变成持久的，这样一个定时的 `agent-team` 任务才能在应用重启后重新实例化它的小队。
- **v7 到 v8** 又把这三者从 `localStorage` 搬回 Dexie。这次迁移*不*自己搬行：它把行留在 rehydrate 后的状态里，让 `dexie-bridge.ts` 在第一次同步时把内存里有、表里没有的写进去，因为一个同步的存储回调根本没办法 await 一个账户数据库。

`migrate` 和 `onRehydrateStorage` 都会把停在 `planning`、`executing` 或 `paused` 的小队重置为 `idle`。只靠 `migrate` 不够：版本相同的普通重载会让它短路，于是一次幽灵般的 "executing" 就被 rehydrate 出来了。

### Dexie 镜像

自 persist v8 起，Dexie 是定义的权威。`dexie-bridge.ts` 订阅一次并按引用做差分，而不是往 1300 行同步 `set()` 里逐个穿一个 `await`，并用 **400 毫秒** 去抖，因为一支运行中的小队几乎每个 token 都会发出进度。它遵守本仓库每个 dexie-bridge 都付过学费的两条安全规则。

1. **绝不写入不是自己所对应的那个数据库。** 锁定账户时会*先*清掉 Dexie 选择再清 store，否则一个仍然活着的订阅就会看到一个指向别人数据库的空 store，然后把里面每一行都删掉。
2. **hydration 失败就整体停用镜像。** 删除是由「镜像里有、内存里没有」推导出来的，而如果 hydration 抛过错，内存就是表的一个未知子集。

模板和 `defaultConfig` 不在镜像范围内。小队模板按设计是跨 profile 共享的，由统一模板平台拥有。桥由有序的小队引导（`lib/agent-team/bootstrap.ts`，由 `components/providers/initializers/squad-bootstrap-initializer.tsx` 挂载）启动，引导先等它水合完成，再安装运行时、导入旧历史、恢复活跃运行。在引导翻转就绪之前到达的启动请求会以 `runtime_not_ready` 被拒绝，绝不竞态。

### 运行记录（ADR-0169）

`AgentTeam` 只是定义。关于一次*运行*的一切（状态、进度、结果、成本、恢复原因）都在 `agentTeamRuns` 的 `AgentTeamRunRecord` 上，`ExecutionRun`（`execution:team:<runId>`）是所有界面读取的单向投影。`createSquadRunRecords` 在任何派发之前于一个事务内写入两者以及 `run.started` 事件。store 的 `status` 字段是生命周期运行器写的镜像，别处不写。`__team__:` 前缀的旧 `workflowRuns` 行由 `backfillLegacyTeamRunHistory` 一次性导入，不再有任何界面实时查询它们。

| 表 | 主键与索引 | 行类型 |
| --- | --- | --- |
| `agentTeams` | `&id, projectId, status, createdAt, updatedAt, [projectId+createdAt]` | `AgentTeamRow` |
| `agentTeammates` | `&id, teamId, role, updatedAt, [teamId+createdAt]` | `AgentTeammateRow` |
| `agentTeamTasks` | `&id, teamId, status, assignedTo, updatedAt, [teamId+order]` | `AgentTeamTaskRow` |

行会把 `Date` 摊平成 epoch 毫秒，并补上一个领域类型从来没有的 `updatedAt`，因为同步需要游标，而镜像是唯一知道某一行真的变了的地方（`lib/db/agent-team-definitions.ts:24-49`）。这三张表在 schema **v215** 落地。运行态那一半（`agentTeamRuns` 加十张子表）自 v145 起就在 Dexie 里了。`lib/db/schema.ts` 现在把整套 schema 一次性声明在 `CURRENT_SCHEMA_VERSION` **217** 上，而不是重放一条迁移链，所以上面那些版本号是历史，而不是 `version(N)` 代码块。

### 持久化矩阵

| 数据 | 存放位置 | 重载后是否还在 |
| --- | --- | --- |
| 小队、队友、任务 | Dexie `agentTeams` / `agentTeammates` / `agentTeamTasks` | 在，且按工作区限定 |
| 模板、`defaultConfig` | `localStorage` blob，以及模板平台的 `templateDefinitions` 表 | 在，跨 profile |
| `tasksView`、`editorSession`、`lastAdapterSyncVersion` | `localStorage` blob | 在 |
| `displayMode`、`workspaceTab` | `localStorage` blob | 在，但没人读 |
| 消息、事件、共识、共享内存、委派 | 仅内存 | 不在 |
| `activeTeamId` | 仅内存 | 不在 |
| 运行历史 | Dexie `agentTeamRuns` 及其子表，投影到 `executionRuns` / `executionRunEvents`（旧 `workflowRuns` 行在引导时一次性导入） | 在 |
| 会话绑定 | `sessions.squadId`，带索引。在 Dexie v177 引入，如今属于合并后的单一 schema | 在 |

`sessions.squadId`（这段对话交给哪支小队跑）与 `sessions.teamId`（这段对话本身*是*哪个角色团队房间）是刻意分开的两件事，`lib/db/schema.test.ts` 把这对关系钉死。

本子系统的备份快照是 `lib/data/snapshots/agent-teams.ts`，它对同一处命名冲突给出了同样的提醒：Dexie 的 `teams` 表是角色团队，不是小队。

## ADR-0140 移除了什么

`/agent-teams/workspace` 这个外壳曾经拥有一大簇再无他人调用的 store 状态与 action。它们都没了。这张表的作用是让拿着旧书签的读者停止寻找。

| 已移除 | 替代 |
| --- | --- |
| `setActiveTeam`、`setWorkspaceTeamFromRoute`、`closeAgentTeamWorkspaceDetail`、`setIsPanelOpen`、`setDisplayMode`、`setWorkspaceTab`、`setWorkspaceFocus`、`setSelectedTeammate` | 没有替代。界面自己传 `teamId` prop。 |
| `selectedTeammateId`、`isPanelOpen`、`workspaceFocus`、`workspaceDetailOpen` | 没有替代。共识面板改为从花名册里挑投票人。 |
| `setTeammateStatus`、`setTeammateProgress`、`claimTask` | 运行时改经 `updateTeammate`、`setTaskStatus` 和 `moveTask` 写入。 |
| `cancelAllTasks`、`shutdownAllTeammates`、`cleanupTeam`、`requestTeammateShutdown`、`addStructuredMessage` | `agentTeamManager.shutdown` 与 `addMessage`。 |
| `upsertMessage`、`markMessageRead`、`markAllMessagesRead`、`markTeamMessagesRead`、`getUnreadMessages` | `addMessage` 与 `removeMessage`。已读状态早已没有读取方。 |
| `importTemplates`、`exportTemplates` | 模板平台上的 `service.exportPackage` 与 `service.importPackage`。 |
| `updateDefaultConfig`、`clearStaleCapabilityIds` | `defaultConfig` 改在设置表单里编辑。失效的 id 由能力审计闸门呈现，而那道闸门比替它做清理的 action 活得更久。 |
| 整个 `selectActiveTeam*` 家族，以及 `selectActiveTeamId`、`selectSelectedTeammateId`、`selectDisplayMode`、`selectIsPanelOpen`、`selectWorkspaceTab`、`selectWorkspaceFocus`、`selectWorkspaceDetailOpen`、`selectTeamUnreadCount`、`selectTotalUnreadCount` | 上文那些按小队限定的 selector。`selectActiveTeamConsensus` 是唯一的幸存者。 |
| `agent-team-compat.ts` 上的 `dispatchAgentTeam` | `startSquadRun`，ADR-0140 唯一的派发漏斗。 |

## 相邻模块

- `lib/ai/agent/agent-team-compat.ts` 如今只剩两个纯函数 `normalizeAgentTeamConfig` 和 `normalizeAgentTeamTask`，store 在每次创建和更新时都会调用它们。它们裁剪字符串、夹紧计数，并在什么都没变时返回原引用。
- `stores/agent/pending-gates-store.ts` 是 HITL 闸门队列，由 ADR-0022 的小队闸门和 ADR-0045 的计划闸门共用。七种闸门类型：`budget`、`deadlock`、`plan`、`teammate_fix`、`replan`、`capability_audit`、`plan_step`。`gateTypeFromScope` 把审批总线的 scope 映射到它们上，而 rehydrate 会把每个恢复出来的闸门盖成 `interrupted`，因为等待审批总线的那一方随页面一起死了。参见 [HITL 闸门](./hitl-gates)。
