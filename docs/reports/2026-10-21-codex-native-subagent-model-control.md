# Codex native subagent model control — implementation and verification

Date: 2026-10-21

Related: [plan](../plans/2026-10-21-codex-native-subagent-model-control.md), [evidence ledger](../evidence/2026-10-21-codex-native-subagent-model-control.md), [initial native protocol probe](2026-10-21-codex-subagent-model-probe.json).

## Implemented behavior

- The native app-server adapter owns a bounded, generation-scoped child registry. It reconciles native spawn/thread events, ancestor-filtered persisted threads, loaded ephemeral threads and authoritative history. Parent/root ownership is preserved; native children never become fabricated Cognia sessions. Missing children and completed turns are reconciled on refresh.
- Diagnostics preserve model metadata, effective feature flags, direct-input permission, observed versus inferred backend evidence and separate settings-method support. A disabled `multi_agent_v2` flag does not imply V1. Backend certification is limited to verified Codex 0.159.2 native spawn evidence: public V1 spawn events or a fresh root's canonical named V2 child source. Child input permission controls that child and does not certify its parent; historical children alone do not certify a resumed parent. Unknown releases retain inference.
- Model-role policy V2 adds finite spawn candidates to the existing compiler. Candidates replace the highest applicable candidate layer; an empty list clears extra candidates. The task catalog/ticket retains the union of primary, slot and candidate models, within the existing provider/account and 32-model limits. Candidate-only configuration now generates the Codex catalog. Existing CLI/Rust catalog materializers already accept this finite model array; they were reused.
- The existing gateway task lease remains authoritative. Candidate changes require a new task. Native account mode remains subject to Codex's own catalog/authentication; it does not gain the gateway's ticket enforcement.
- V1 current-turn changes use `turn/settings/update` and require the typed experimental `stepModelSwitching` opt-in plus the exact active turn. Future defaults use `thread/settings/update`. Neither starts a turn. Both validate root, child, generation, model/effort and task plan before sending.
- Per-child serialization, operation-ID deduplication and scope-specific unsupported caching prevent accidental replays. A transport failure or unknown response reports `outcome-unknown` and locks further changes to that child until reconnect. Server acceptance is displayed separately from inference observation.
- V2 children remain controlled by their parent: direct settings controls are disabled. V1 requested settings are joined from the start event by parent/turn/call identity and kept distinct from resolved settings. V2 public activity events do not expose requested spawn-model metadata; the UI shows unknown rather than copying the resolved thread model into that field. Internal raw Responses events were not enabled to fill this gap.
- Local create/editor and Host create/editor reuse the existing shared model fields, `ResponsivePicker`, `ProviderModelList`, `NativeSelect` and session-operation panel. Host policy V2 and native control have separate capability markers, with explicit old-Host refusal at both UI and programmatic boundaries. The remote operation remains a narrow validated request, not arbitrary vendor RPC.
- Native discovery and model-change request/result diagnostics use the existing adapter logger and contain identity/settings metadata, without adding prompt or reasoning payloads.

## How to use

1. Select the native Codex app-server integration. In Cognia model mode, configure the default child model and optional finite spawn candidates from the same provider/account. The default must remain in a nonempty candidate policy.
2. Enable the experimental current-turn model switch option if current-turn control is needed. Saving candidates or changing the experimental option applies to newly launched tasks/processes; it does not widen an existing task lease.
3. Start the task and let Codex spawn a native child. Open **Session controls → Native subagents**, then refresh. The panel shows the native child/root identity, backend evidence, thread settings and current turn.
4. For a child that accepts direct input, select a model/effort and explicitly choose either **Apply to next steps of current turn** or **Set future-turn defaults**. An accepted current-turn change affects later sampling steps; an already-issued request continues with its previous settings.
5. For V2, request the model when the parent next spawns a child. Existing V2 children cannot be switched through direct app-server input.

## Remaining acceptance and design adjustments

- Full Tauri UI, the user's authenticated provider route, one paired Host, and Windows/Linux native acceptance remain unverified. An earlier Tauri launch failed with `No space left on device`; the user subsequently requested skipping further builds. Native CLI acceptance and browser fixture acceptance are distinct from those missing checks.
- Keep the adapter as the native registry owner and expose its snapshot through the existing session-operation panel. The proposed projection into `subagent-runtime-store` was not added: that store coordinates Cognia-dispatched jobs and would introduce a second owner with misleading native lifecycles. No new global store or duplicate picker was introduced.
- The public app-server does not supply general per-step inference telemetry. UI status remains accepted/awaiting-step, even when an offline verification fixture can inspect the next request body. V2 requested spawn settings can remain unknown while its resolved thread settings are readable.
- The full workspace static-export gate must be restored by the owners of the unrelated import paths before claiming a green production static export. No production build or deployment is claimed here.

Changes are uncommitted. Concurrent work, including OpenCode model-plan/gateway changes, was retained.
