# CI setup and artifact reuse follow-up

Date: 2026-10-15. Scope: current working-tree workflows and their setup/build/report scripts. This source audit includes one historical job measurement collected by the coordinating agent; it is not a controlled before/after benchmark. Existing affected Quality selection, the shared Git change manifest, and the prepared CLI bundle/plugin artifact are treated as implemented and are not proposed again. No workflow or source was changed for this report; no tests or builds were run.

Source references below use working-tree line numbers. Workflow shorthand resolves to [test.yml](../../.github/workflows/test.yml), [quality.yml](../../.github/workflows/quality.yml), and [report.yml](../../.github/workflows/report.yml). `check-all.mjs` is [the gate registry](../../scripts/gates/check-all.mjs); build-driver shorthand is under [scripts/build](../../scripts/build), and report-module shorthand is under [scripts/ci/report](../../scripts/ci/report).

The remaining opportunities concern when preparation happens and which consumers need it. Download caches already exist; they do not eliminate dependency installation, lifecycle scripts, compilation, or unnecessary artifact transfers. The recommendations below preserve selected tests and blocking gates.

## 1. Publish runtime impact decisions before preparing Jest prerequisites

**Evidence.** `test.yml:89–98` resolves committed changes early, but `jest-plan` then installs dependencies, builds workspace packages/webclone (`:126–136`), freezes the Jest inventory (`:155–166`), and prepares selected CLI/native artifacts (`:167–195`) before the job completes. Independent jobs depend on that entire job: docs (`:596–598`), diagnostic-server (`:1741–1743`), PostgreSQL (`:1695–1697`), and Rust workspace (`:1611–1613`). Their `impacts` conditions do not require the Jest inventory or CLI artifact.

**Change and reuse.** Move the existing pure `classifyCiImpact()` from `scripts/test/coverage-changed.mjs:213–270` into a dependency-free CI module consumed by both an early impact job and Jest planning. Feed it the existing validated change manifest. Let independent runtime jobs depend on the early job; retain artifact-producing dependencies only for consumers that actually download those outputs. Avoid copying the path rules into YAML.

**Safeguards.** Preserve exact HEAD identity, conservative full mode, and every existing impact predicate. Jobs consuming `jest-runtime-prerequisites` must retain a producer dependency or explicitly prepare their own required outputs. Keep the Windows Tauri dependency on the production static export (`test.yml:1574,1597–1601`); that dependency is real. Runtime work should still report failures if later Jest preparation fails.

**Acceptance.** Identical impact outputs for existing planner fixtures. In a diagnostic-only or PostgreSQL-only change, the relevant job becomes runnable before Jest installation/build completes. Measure decision latency, queue time, critical-path duration, and total runner-seconds separately; earlier scheduling need not reduce total work.

## 2. Derive setup prerequisites from selected gates, not just group/runtime names

**Evidence.** Every surviving Quality group still runs root installation (`quality.yml:229–230`). Root postinstall installs sidecar dependencies, builds linked packages and A2UI, and builds the VS Code extension host (`scripts/postinstall.mjs:42–45`). Also, every `matrix.rust` group installs the desktop GTK/WebKit system stack (`quality.yml:248–262`), although `rust:deny` in supply-chain and SDK Rust checks have different needs (`scripts/gates/check-all.mjs:339–365`). Worker installs and webclone preparation are keyed to whole groups (`quality.yml:234–238,278–280`).

**Change and reuse.** Extend the existing gate registry and `groupManifest()` (`check-all.mjs:537`) with explicit prerequisite capabilities, initially for the easily proven cases: desktop system libraries, standalone Workers, webclone, and extension-host build. Use the selected gate set already produced by `buildQualityPlan()` to union those capabilities. Introduce an explicit repository setup profile through the existing `scripts/postinstall.mjs`, with full local/default behavior retained.

**Safeguards.** Do not globally disable dependency lifecycle scripts or infer “no runtime” from a gate's name. Preserve native-package installation and the macOS node-pty permission repair (`postinstall.mjs:15–34`). Unknown/unclassified gates retain complete setup until their imports and subprocesses are audited. Verify each narrowed profile in a clean checkout, not against populated local outputs.

**Acceptance.** Selected gate commands and verdicts are unchanged. A supply-chain-only lane installs no GTK/WebKit packages unless a selected check demonstrably links them. Record root install duration, nested install/build counts, setup bytes, and gate execution time per group. This reduces preparation scope beyond the already implemented gate selection.

## 3. Reuse the remaining compiled prerequisites without adding duplicate freshness rules

**Evidence.** Cold root installation already calls `buildLinkedPackages()` through `build-sidecar-linked-packages.mjs:114–120`; the planner then invokes the full `build:packages` command (`test.yml:135`, `package.json:28`). Their package sets overlap. The shared artifact includes `packages/*/dist` and webclone, but not VS Code extension-host or A2UI output (`test.yml:205–214`), so fresh consumer jobs still execute those postinstall builds. Quality only restores this compiled cache for the plugin-sdk group (`quality.yml:219–227`); other consumers construct their own prerequisites. Repeated invocation within one checkout can already skip work, so command repetition alone is not a measured rebuild count.

**Change and reuse.** Separate the intentional package build-validation gate from preparation for downstream consumers. For consumer preparation, reuse the existing `linkedPackageDirs()`/`buildLinkedPackages()` and build drivers rather than another hard-coded package list. Evaluate extending the existing compiled-prerequisite artifact/cache to the required extension-host/A2UI outputs, restored before postinstall. A broader artifact should be adopted only if avoided compilation outweighs transfer and verification cost.

**Safeguards.** Current freshness checks use filesystem mtimes (`scripts/build/lib/build-linked-packages.mjs:24–31`; `build-vscode-ext-host-sidecar.mjs:75–86`; `build-webclone-sidecar.mjs:213–224`). These are local fast paths, not proof of matching source after transfer. Bind restored outputs to source/config/lockfile/runtime digests, preserve executable bits, and validate their output closure. Reuse the input/output hashing machinery in `scripts/build/esbuild-input-cache.mjs:101–174` where appropriate; its root-bound cache format must not simply be copied across checkouts. Keep package export resolution checks (`build-sidecar-linked-packages.mjs:122–133`) and webclone's physical `file:` package validation (`build-webclone-sidecar.mjs:101–127`).

**Acceptance.** Instrument actual compiler invocations before changing policy. On a same-source restore, covered consumer prerequisites compile zero additional times and runtime imports still pass in a different checkout path. Missing or modified output forces a rebuild/failure. Run source, lockfile, export-map, and compiler-config invalidation cases. Keep deliberate cold build verification in the responsible gate/full run.

## 4. Reduce the remaining Jest prerequisite transfer and standalone-install fanout

**Evidence.** All Jest shards download the combined `jest-runtime-prerequisites` artifact (`test.yml:253–257`), which includes the native helper tar whenever any selected suite needs it (`:192–195,205–214`). Each shard also installs webclone's standalone dependencies (`:260–261`). The shard's test list is read only afterward (`:262–270`); native extraction is selective later (`:288–308`). CLI artifact transfer is already selective and needs no redesign.

**Change and reuse.** Publish/download the small frozen plan first. Extend the existing per-shard prerequisite decision pattern to webclone and the remaining native/runtime artifact components. Separate components only where there is a proven consumer boundary; retain workspace outputs for suites whose dependency graph requires them. Reuse the current immutable shard assignment rather than re-deriving affected tests at download time.

**Safeguards.** Do not equate a test's directory with all its runtime dependencies: transitive and dynamic imports need explicit prerequisites or a conservative fallback. Full mode and unknown suites keep the complete required setup until classified. Preserve webclone's `--install-links`, linked-package freshness, and physical-package checks (`build-webclone-sidecar.mjs:189–205`). Missing selected prerequisites must fail instead of skipping a suite.

**Acceptance.** No changes to assigned/executed suite identities. A proven frontend-only shard downloads no native tar and invokes no standalone webclone install. Measure downloaded bytes and install time per shard, plus total producer cost; do not trade a small transfer saving for additional redundant builds.

## 5. Give the report workflow a small dependency boundary and an artifact allowlist

**Evidence.** `report.yml:70–71` installs the complete root workspace, triggering the application postinstall chain. Both current and baseline downloads omit `name`/`pattern` (`:73–79,107–114`), so they fetch unrelated build/runtime artifacts. The actual report consumes current JUnit plus current/baseline Playwright JSON, coverage, and bundle metrics (`:118–131`). It does not consume CLI bundles, native helpers, static exports, Playwright HTML, or baseline JUnit. The direct module graph is local code and Node builtins except `istanbul-lib-coverage` (`scripts/ci/report/coverage.mjs:14`); `junit.mjs:11–14` explicitly implements a dependency-free parser. There is no `fast-xml-parser` requirement in the current report graph.

**Observed cost.** [Report run 38563492338, job 115850209343](https://github.com/MaxQian888/cognia-next/actions/runs/38563492338/job/115850209343) took 147 seconds: dependency installation took 25 seconds, baseline downloading 52 seconds, and report generation 4 seconds. The coordinating agent's read-only log analysis found 66 baseline artifacts from run 38535819287 totaling 2,400,606,155 reported bytes: 64 Jest shard artifacts (2,383,223,723 bytes), a test plan (285,653 bytes), and runtime prerequisites (17,096,779 bytes). None supplied the three baseline inputs read by the report: coverage, Playwright JSON, or bundle metrics. All approximately 2.40 GB of that baseline transfer was therefore unused by this report. Artifact-reported sizes are not a measurement of network wire bytes. The observed 52 seconds is avoidable work in this run, not a guaranteed reduction in future job duration.

**Change and reuse.** Keep `build-report.mjs`, its existing modules/tests, and `pr-comment.mjs`. Provide a lockfile-controlled report-only install boundary, without application lifecycle builds. Download current `jest-shard-*`, `playwright-json`, `coverage-report`, and `bundle-size`; download only the latter three categories for the baseline. Discover available matching artifact IDs first or perform individually optional downloads, because incremental/failed runs legitimately omit categories. A later small report-data artifact could avoid transferring per-shard coverage maps and coverage HTML that accompany those initial allowed artifacts.

**Safeguards.** Preserve the base-repository checkout and `workflow_run` trust boundary (`report.yml:45–49`); never execute downloaded PR code with the report token. Preserve missing-data labels and the triggering run's actual conclusion (`build-report.mjs:5–9,59–65,130–138`). Retain all current JUnit batch documents. Do not borrow baseline coverage when the current run has none.

**Acceptance.** The same archived successful, failed, incremental-without-coverage, and missing-baseline inputs produce identical report content. Root sidecar installs/builds are zero in the report job. Download logs contain only allowed categories, with current and baseline bytes recorded separately. Measure report dependency setup and download duration before asserting time savings.

## Suggested order and measurement

Start with the report artifact allowlist and early runtime-impact job: both have explicit existing input boundaries. Then add prerequisite metadata for a small number of Quality gates. Expand reusable compiled outputs and per-shard requirements only after observing actual build/install counts and transfer sizes. Compare the same SHA and selection mode on cold and warm runners; report runner-seconds, critical-path elapsed time, artifact bytes, cache hits, compiler invocations, and unchanged gate/suite inventories. The initial two historical runs diagnosed a planner failure, so their timings do not establish a healthy end-to-end baseline or a guaranteed saving.
