## What upstream provides

| Surface           | Pinned upstream behavior                                                                                                                                                                                                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fresh local child | `dsh-subagent` + `dsh-subagent-spawn-in-process` + `dsh-tool-subagent` compose the `subagent` tool. Each call starts managed background work and returns the durable child id immediately. The child has no parent conversation.                                                      |
| Fork child        | `dsh-subagent-fork-in-process` seeds the parent's last completed-turn prefix; the current in-flight turn is excluded. The shipped paired tool names are `subagent` and `subagent_fork` (tool names are configurable). Local spawn/fork children support continuation and cold resume. |
| Follow-up         | `dsh-tool-subagent-control` exposes `send_message` and `interrupt_agent`; its separately mounted `/list-agents` plugin adds `list_agents`. These are not implied by merely loading a spawn provider.                                                                                  |
| Wait/result       | The delegation tool does not block and there is no corresponding model-facing `wait` tool in this bundle. The runtime delivers completion notices. Programmatic callers can await the activation result, and host entry points use `waitForChildren`/SDK `session/wait`.              |
| External provider | Optional DSH SDK, ACP, Codex, and Claude Code subagent backends exist upstream. External activations execute one task; they do not accept follow-up messages as local continuable children do. They are separate optional providers, not what Cognia's current managed profile loads. |

## Child model selection

**Default inheritance:** local children inherit provider, model, reasoning effort, and `maxTokens`. Importantly, the parent's latest persisted request header supplies the effective provider/model/effort after request-time selection; creation options are only the fallback before the first request. Child options then overlay that baseline. Changing provider/model without an explicit effort clears the inherited route-owned effort. [Actual option resolution](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/subagent/src/child-agent.ts).

**Selection at spawn is supported but opt-in:** `modelSelectionSettings` defaults to `false`. Enabling it requires the Host-side model-selection settings plugin and a provider advertising `agentOptions`. An enabled, non-empty exact provider/model allowlist is sampled when a fresh top-level Session is composed, recorded in its log, and inherited by child Sessions. Later settings edits do not silently change that Session's authorization. Historical restored sessions without a recorded policy remain disabled. The model then sees optional `provider`, `model`, and `reasoning_effort` fields plus `list_subagent_models`. Provider and model must be supplied together; exact-route preflight enforces authorization independently of advisory catalog discovery. `maxTokens` remains deployment controlled. [Tool implementation](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/tool-subagent/src/index.ts), [route validation and merge](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/tool-subagent/src/model-selection.ts).

Both in-process providers advertise low-level `agentOptions` capability. However, shipped fork tool compositions intentionally do not expose route selection to preserve copied-prefix cache reuse; do not confuse a provider capability with a composed tool's schema. Spawn supports independent preset selection; fork does not. The optional DSH SDK provider also accepts per-spawn provider/model/effort overrides, using its own configured route defaults (`deepseek-official` / `deepseek-v4-flash` by default), rather than automatically inheriting the parent's route. ACP/Codex/Claude Code provider compositions reject unsupported `agentOptions`. [Documented fork/tool limit](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/tool-subagent/README.md#known-limitations-and-deferred-work), [SDK child provider](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/subagent-dsh-sdk/README.md).

**Existing child model switching has no exported SDK/ACP child-control operation in this release.** This conclusion comes from the complete wire request map and actual server ownership checks, not an unsuccessful text search. The subagent service/control contracts expose start, send/queue/steer, interrupt, discovery, and disposal; they do not define a child-model mutation. A reusable lower-level `installModelSelection(agentCtx, ModelSelectionRef)` does exist: a Host can own a mutable selection whose next value is captured at prompt assembly for a later step. Native local subagent composition does not itself export that primitive as a child control endpoint; a new managed Host extension would need explicit authorization, identity, persistence, and lifecycle semantics. Cold resume currently reconstructs the child's saved descriptor model settings. [Model-selection primitive](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/core/agent/src/model-selection.ts), [subagent manager](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/subagent/src/manager.ts).

## Parallelism, nesting, permissions, and stopping

- The default depth limit is `1` (direct children only); `0` rejects delegation. Tool-specific numeric limits override the Host setting, and `provider-managed` leaves depth policy to an external child runtime. Enforcement runs at start even if a model ignores the depth notice.
- `maxActiveSubagents` defaults to `8` per activation tree, including local/external descendants and children still materializing or stopping. The root consumes no slot. Lowering the limit leaves existing children running and blocks further admissions. Independent starts may overlap.
- A local child retains parent origin and permission roots while its own working directory is captured at start. Delegated effective sandbox policy is captured at the boundary; when approval is composed, child approval is pinned to `never`. Child code cannot widen the delegated scope. Agent-local parent tool restrictions are not automatically copied: inherited or explicitly chosen preset composition owns child tools.
- `send_message` is authorized between direct local parent/child agents. Running targets receive steering at a step boundary; inactive continuable children can resume. Acceptance returns a message id, not a reply, and accepted delivery cannot be revoked by cancelling the sender's tool call.
- `interrupt_agent` stops a local child's current turn while preserving its inbox, descendants, and ability to receive a later follow-up. Acceptance does not mean quiescence. External execution interruption ends its one-shot work. Owned activation disposal/draining is the stronger operation that awaits cleanup, including descendants.
- `list_agents` lists continuable children, optionally recursively through descendant catalogs. `running`/`inactive` are activity states, not proof of task completion. Arbitrary sessions, siblings, and unrelated forks do not become valid targets just because their ids are known.

Sources: [service limits and delegated scope](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/subagent/README.md), [control semantics](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/tool-subagent-control/README.md), [child policy capture](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/subagent/src/child-agent.ts).

## What SDK and ACP export

The SDK wire request map is: `initialize`, `session/prompt`, `session/resume`, `session/wait`, `session/working-directory/get`, `session/working-directory/set`, and `shutdown`. Initialization supplies process-wide defaults for SDK-created agents. There is no wire `subagent/spawn`, `subagent/send`, `subagent/interrupt`, or model-update method. Notifications include all runtime `session.event` events, `session.status`, `subagent.started` (parent/child ids), and `subagent.finished` (provider, ids, status, stop reason, optional final assistant output). These observe actually composed local children; protocol support alone does not load the native bundle. [Complete SDK protocol types](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/sdk/protocol/src/types.ts).

ACP supports root-session standard config selection through `session/set_config_option`, but looks the target up in its own ACP Session records. Its session listing and resume admission explicitly exclude child/subagent-origin Sessions. Therefore an observed native child id is not automatically an ACP model-control target. ACP's existing root model selector cannot be assumed to switch native children. [ACP implementation](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/acp/acp/src/index.ts), [ACP model control](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/acp/acp/src/model-control.ts).

## Current Cognia composition and handling

This section follows the current Cognia call paths, separately from the upstream package capabilities above.

- [Managed launcher](../../runtime/deepseek-harness/launcher.mjs) mounts only `dsh-sdk-minimal` in its managed manifest and rejects changed manifests/extra profile patches. [Channel inventory and capability refinement](../../packages/agent-dsh/src/channel.ts) mark the five native service/provider/tool plugins as `not-composed`, and effective profile capability `subagents` is `false`. [Runtime manifest](../../packages/agent-dsh/src/manifest.ts) marks all three managed presets unsupported with `profilePluginNotComposed`, and has no native subagent ecosystem source id. Native delegation is therefore **not enabled in Cognia's managed DSH profile today**.
- [SDK client](../../packages/agent-dsh/src/sdk-client.ts) can map native child ids to parent ids and wait for root plus descendants. [Event codec](../../packages/agent-dsh/src/event-codec.ts) translates lineage into progress and strips child `lastAssistantMessage`; the SDK client suppresses child session content from the root answer stream. That is preparatory observation/routing support, not a child registry/control panel and not proof that the managed profile exposes delegation tools.
- SDK runs use one DSH process per Cognia session and enforce immutable initialized model selection. The adapter's `children` set tracks these session-runtime instances, not native subagent identities. ACP does not advertise equivalent child-lineage support in Cognia's channel capabilities.
- [Model slots](../../lib/ai/agent/external/config/model-slots.ts) do not declare a DSH child role. [Gateway task assembly](../../lib/ai/agent/external/config/gateway-task.ts) currently emits a DSH route with one primary model. Consequently the existing gateway is not yet a native child model-candidate policy or a child-model switching API.
- Cognia's independent [external teammate dispatch](../../lib/ai/agent/team/teammate/dispatch-teammate.ts) calls `manager.execute`. This is a separate Cognia-managed execution path, not a silent substitution for upstream DSH native plugins.

Verification: four focused Jest suites (`manifest`, `channel`, `event-codec`, `sdk-client`) passed, 203 tests; log `.cache/dsh-subagent-research-tests-2026-10-22.log`. This is contract/adapter evidence. No real provider-backed child run or native UI acceptance was performed in this investigation.

## Integration implications

1. Enabling native children first requires an intentional managed-profile composition change, dependency/profile validation, permission review, and truthful capability refinement. Existing upstream plugins should be composed rather than rebuilding a second delegation engine.
2. Spawn-time dynamic selection can reuse upstream session-frozen exact-route authorization, `agentOptions`, and discovery. Cognia must first project the task's finite gateway model set and route credentials into those controls; a single primary-model route is insufficient.
3. Child identity/progress can reuse SDK lineage events, but durable ownership, final-result presentation, generation guards, and host UI controls need explicit integration. Never expose child output by simply merging it into the root assistant answer.
4. Existing-child model switching is a distinct feature. Neither this release's SDK wire nor the current Cognia adapter exports it. The shared `installModelSelection` primitive offers a possible implementation seam, subject to new bounded Host-side control and persisted resume behavior; ACP root config mutation is not an equivalent child operation.
