# 数据库性能与对话恢复实测 — 2026-09-22

本次直接修改生产路径，覆盖 IndexedDB 流式保存、恢复索引、SQLite 会话目录和原生恢复状态文件。测试使用隔离合成数据，没有操作用户真实数据库，也没有 schema 迁移或清库。

## 已修复的行为

- **持续输出不落盘**：原来的 trailing debounce 每次收到事件都重置，连续输出一小时可以一次检查点都不提交。保留普通 debounce 语义，为会话持久化增加默认 1000 ms 的最大等待时间；flush/cancel 会清理全部定时器。
- **旧检查点覆盖最终结果**：在数据库入口按数据库名、会话串行执行完整保存、增量提交和流式检查点。慢写入期间只保留一个待执行的最新流式快照，完整保存/删除/截断/元数据更新等形成顺序边界。失败不会永久阻塞下一次写入。
- **恢复索引回退**：在同一个事务内读取和更新 revision、水位及 complete。旧 revision 不覆盖新 checkpoint，同版本的完成标记不会被较新的局部页面清除。
- **作用域和引用正确性**：预处理各阶段检查数据库身份；增量消息归属验证移入写事务；缓存按数据库实例隔离。WeakRef 不保留整段消息正文；移除会导致第九个并发会话反复全量保存的固定缓存上限。
- **重复附件引用写入**：流式文本增长时，附件 hash 集合不变便不重写引用表；只对实际移除的 hash 运行垃圾回收检查。改变/清空附件的路径仍更新引用。
- **SQLite 目录扫描所有历史正文条目**：复用既有 covering index，最多探测 129 个会话；项目不超过 128 个会话时直接返回完整目录，更多会话退回既有 GROUP BY。没有引入需要另行恢复的目录副本。
- **长期会话保留不一致**：将摘要和 transcript 的最近活动一起纳入整会话过期判断，避免近期仍更新摘要的旧对话丢失正文，也避免有新正文的会话被删掉旧摘要。删除保持同一事务。
- **恢复状态文件并发损坏**：同一 store 的 clones 串行保存/清除；controller 在状态锁内保存，防止旧快照覆盖新状态；时间戳在锁内取得，避免旧时间戳把并发产生的新失败记录裁掉。文件先 sync，再 rename，Unix 再同步目录。

## 性能实验

环境：macOS arm64；Chromium 151.0.7922.34，真实 IndexedDB、Dexie 4.4.5。消息负载为 1000/10000 条，每条 2048 字节文本；附件场景为已有媒体引用，并非大型二进制上传。浏览器每场景 2 次预热、10 次采样，比较 median/MAD；收益要求至少 20%，并超过两组较大 MAD 的 2 倍。

| 场景                         | 修改前 median ± MAD | 修改后 median ± MAD | 判定                  |
| ---------------------------- | ------------------: | ------------------: | --------------------- |
| 10000 条、附件引用、流式保存 |      3.70 ± 0.25 ms |      0.60 ± 0.10 ms | 降低 83.78%，超过门槛 |
| 1000 条、附件引用、流式保存  |      1.30 ± 0.15 ms |      0.80 ± 0.15 ms | 降低 38.46%，超过门槛 |
| SQLite：100000 条 / 100 会话 |   16.683 ± 0.205 ms |    0.472 ± 0.058 ms | 降低 97.17%，超过门槛 |

SQLite 数据来自实际 Rust `list_sessions` 方法、bundled SQLite 3.50.2、内存数据库、未优化 cargo test 构建；1 次预热、10 组 AB/BA 交替采样。它证明查询工作量的改善，不代表生产磁盘/发布构建的绝对延迟。

保护指标和不成立的收益也保留：SQLite 1000/10000/100000 会话场景因有界探测增加 2.55%/7.37%/0.88%，符合预设 `max(10%, 0.5 ms)` 稀疏场景容忍值。无条件递归和 UNION 候选因稀疏场景退化而淘汰。完整对话保存、完整历史恢复没有达到收益门槛，不宣称它们加速。首轮最终对照中的 10000 条附件 recent-80 读取出现 0.70 → 0.95 ms 的退化；原始结果没有删除。随后 30 组 AB/BA 交替复测：10000 条 recent-80 为 0.80 ± 0.20 → 0.85 ± 0.20 ms，配对差值中位数为 0，没有重现超门槛退化；1000 条则为 0.70 → 0.70 ms。附件流式保存收益再次成立：10000 条 4.10 → 0.75 ms（降低 81.71%），1000 条 1.30 → 0.55 ms（降低 57.69%）。[配对原始结果与方法](database-recovery-2026-09-22/paired.md) 单独保存，不覆盖初次观察。

## 恢复与复杂条件

| 验证                                       | 证据                                                                                             |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| 模拟 1 小时、100 events/s                  | 360000 次更新：原来 0 次检查点提交；现在 3600 次，调度待提交间隔不超过 1000 ms                   |
| 真实 renderer crash，持续流未停止/未 flush | 约 3.15 秒产生 315 事件：原来恢复 token 0；修改后恢复 token 303，观测损失 12 事件、约 120–121 ms |
| 真实 IndexedDB 事务中止                    | 消息、附件引用、session revision、sync clock 一起回滚                                            |
| 9 个并发保留会话，各 1000 条消息           | 9000 条内容完整，流式保存没有触发全会话扫描；原始耗时含异常值全部保留                            |
| 1000 个等待中的检查点                      | 合并为一个最新快照，不跨越最终保存顺序边界                                                       |
| 保存/删除/截断并发                         | 回归测试验证后执行的删除、截断不会被先前在途保存恢复                                             |
| 原生 8 线程，320 次保存、64 次 clear       | 基线 91 次保存失败；修复后 0 次失败                                                              |
| 原生 320 次并发恢复事件                    | 修改过程中暴露时间戳乱序，仅剩 86 条；最终保留 320 条，重新读取等于内存最新状态                  |
| 长期保留与失败回滚                         | 覆盖旧正文+新摘要、新正文+旧摘要、两者过期、摘要独存、作用域同名会话、删除事务中止               |
| 临时文件损坏/写入失败                      | 保留上一次完整状态，后续保存可以恢复                                                             |

1000 ms 是事件循环正常运行时的检查点调度期限，不是磁盘提交保证。renderer crash 实验没有覆盖整个浏览器进程被杀、操作系统崩溃或断电。恢复文件写锁覆盖同一 store 的 clones，不宣称独立进程或独立 new 实例互斥。
