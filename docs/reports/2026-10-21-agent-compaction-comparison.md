# Agent 压缩策略对比与本次草稿复核

调研日期：2026-10-21，Asia/Shanghai。此次按用户要求先核对官方文档、开源实现与本地源码；暂停优化实现和真实模型验收，没有启动 Tauri、运行 typecheck 或新增付费模型请求。跨模型审查按用户选择跳过，已完成独立上下文的源码对抗审查。

本报告独立于既有真实模型验收报告：后者记录执行结果，本报告记录策略依据、反例与修订方向。Claude Code/Pi 的详细来源见[专项调研](./2026-10-21-compaction-claude-pi-research.md)。

## 结论

**刚才的草稿不能直接采用。** 减少过大的默认输出请求、保留研究进度的方向有依据，但“全局输出上限改为 32K、摘要改为 4096、追加已读行范围”没有形成完整的上下文管理策略。源码审查发现预算计算、摘要发布和进度来源问题，不能据此声称已解决重复调研。

1M 是窗口容量，不是必须填满才允许压缩的阈值，也不保证模型对全部历史保持同等有效记忆。压缩时机需要结合请求能否容纳、上下文质量及续跑效果验证。Anthropic 建议用复杂执行轨迹检验关键信息召回，再减少多余内容；没有提供适用于所有模型的最佳固定比例。[上下文工程说明](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

### 原生压缩的边界

OpenAI Responses 的原生压缩会返回加密的不透明状态；独立 `/responses/compact` 的输出窗口应完整使用，不能自行解析、剪裁。该能力不是任何 OpenAI-compatible endpoint 都自动具备，不能直接假设 DeepSeek 当前调用链支持同一契约。[OpenAI 压缩文档](https://developers.openai.com/api/docs/guides/compaction)

Claude API 的工具结果清理、阈值压缩和按需压缩也是独立接口，不能当作 Claude Code 的内部实现证据。保留尾部时，工具调用与结果必须留在同一侧。[Claude API 压缩概览](https://platform.claude.com/docs/en/build-with-claude/compaction)、[保留尾部](https://platform.claude.com/docs/en/build-with-claude/compaction-keep-recent-turns)

## 原始实测能支持什么

DeepSeek 当前官方规格确认为 1M context、最大输出 384K；模型最大输出能力不意味着每次请求都应预留同样大的输出。[官方规格](https://api-docs.deepseek.com/quick_start/pricing/)

在第三次验收使用的缓存代码与配置中，模型 catalog 的 1,000,000 窗口、393,216 输出上限形成 606,784 的输入预算。结合 0.83 与 soft factor 0.8，软准备点约 402,905，硬触发约 503,631。**这是配置计算复现，不是服务端实际输入 token 的精确测量**；后台准备与最终发布也不是同一事件。

`renderer-long-3` 的既有记录：约 504 秒、258 次 HTTP-200 请求、320 次工具调用，最终 `error_max_turns`，没有自然完成。压缩发布附近之后的 99 次 read 中，76 次请求行范围被此前请求范围覆盖；这提示重读现象，但不能证明 76 次均无价值，也不能证明它们全由压缩丢失信息引起。范围重叠没有说明截断后的模型可见内容、源码版本或重读目的。

该验收还有独立混杂因素：15 次 grep 全部因宿主 RPC 不兼容失败，glob 和 bash_output 也有失败；任务范围覆盖多条执行链。测试宿主标记已在早先草稿中修正，**尚未重新真实验收**。因此不能用这次轨迹宣称模型正常完成这类任务必需 256 轮，或宣称优化必然降低到某个轮数。

历史产物：[真实验收报告](./2026-10-21-builtin-agent-budget-live.md)、本地 `.cache/builtin-agent-live/renderer-long-3/evidence.json`。原始摘要内容与每次请求的完整预算快照不足以支持更强因果结论。

## 修订后的设计与验收要求

以下是基于上述证据的 Cognia 设计建议，不是行业统一实现，也尚未完成代码修复。

1. **先统一请求预算。** 分别表达模型窗口/输入硬上限、协议最终输出请求、压缩提前量、近期尾部和摘要输出预算。最终请求必须满足实际协议的容量约束；用户显式上限不能被重试静默提高。输入 usage 与估算须区分，避免把累计计费 tokens 当成当前窗口。
2. **保留可续跑的状态。** checkpoint 包含任务、用户约束、已证实结论与来源、已排除路线/失败原因、待解决问题、下一具体动作。活动任务 ID、执行状态等可信元数据单独恢复；不要强迫摘要永久罗列全部历史读取。
3. **按 token 与合法边界保留近期过程。** 优先扩展既有 planner，保留当前请求与成对工具消息；在小窗口或超大批次无法容纳时显式处理。现有显式 `preserveRecentMessages`、自定义 summary prompt 和策略必须保持语义；持久化设置的来源/迁移需另行核对。
4. **压缩作为受校验的替换。** 校验正常结束、非空、工具配对、最终大小和 snapshot 边界；新追加内容原样保留。失败/取消保留原历史。短时间压缩后立即再次触发应有可观察的失败/退避，不能无限重复摘要。
5. **先修工具验收，再做对照实验。** 对应文件测试覆盖截断摘要拒绝、显式配置、协议 thinking 预算、大小边界、并发追加、多次压缩、取消、预算耗尽及续跑；保存输入预算/compaction 前后计量与 checkpoint，隐藏凭据。真实代码任务比较完成率、事实保留、合理重读、请求/工具数、时间和成本；不强迫优化后的任务至少运行五分钟。

验收重点是“压缩后继续完成原任务”，不能只断言更少 tokens、更少轮数或摘要里出现某个路径。先前移除 20 轮硬限制和桌面默认五分钟超时的独立证据保持原有边界，不应被本次尚未完成的压缩优化覆盖。

## 调研后的实现进展

上面的“未实现/草稿”结论记录调研阶段的状态。随后用户已授权直接修复。修订实现移除了通用32K预留和读取范围附录，按实际请求区分主调用与摘要预算；保留显式配置；以 token 和工具配对选择默认尾部；拒绝截断、失败或不缩减的自动替换；保存有界且标为不可信的 checkpoint 供预算耗尽后显式续跑。

真实代码实验进一步复现了两个输入信息缺口：默认裁剪工具结果的中段，会使已经读到的事实不进入摘要；增量摘要不接收旧 checkpoint，会丢失原始目标。当前实现默认保留完整工具证据，将旧 checkpoint 与新增材料分开输入，输出新增进度及简短目标锚点；旧事实继续保存在原有 frozen prefix 中。摘要默认生成上限为16K，覆盖推理在内的生成消耗；实际实验中4K曾返回 length，不能把这种截断结果当成成功。

对应文件的956项测试已通过，真实模型最终验收继续记录在[验收报告](./2026-10-21-builtin-agent-budget-live.md)和[evidence ledger](../evidence/2026-10-21-builtin-agent-budgets.md)。不把轮数、耗时或 token 缩减单独当成完成证明；最终结果须同时满足事实保留、压缩后继续工作及原任务自然完成。本阶段未启动 Tauri、未运行 typecheck。

2026-10-22 最终验收已通过 CLI/sidecar 执行连续性断言：Explore 在显式续跑中发起42次主调用、9次摘要，394359ms自然结束；Plan为77次主调用、16次摘要，591929ms自然结束。两者均从10步预算耗尽的真实持久记录恢复；所有续跑主请求保留选定源码事实，23次增量摘要均带上旧 checkpoint。实验强制12消息触发、1500-token尾部以覆盖多次压缩，不代表默认1M窗口也会如此频繁压缩，更不是与旧256步实验的受控性能对照。

默认摘要预算还按所选模型适配：仅无有效显式设置时，采用 min(16384, 模型输出上限, 窗口的四分之一)。四分之一是本项目的折中策略；8K窗口保留2048输出/6144输入，防止默认值占满输入空间。显式值即使等于16384也不重分类；旧调用无 provenance flag 时视为显式，重试到大模型会重新计算默认上限。DeepSeek1M实测预算保持不变。

原始模型交付仍有待查范围、错误路径和未经独立核实的建议。此次通过的是自然终止、压缩后的继续工作及选定事实保留；没有据此宣称语义审计全覆盖、消除全部重读或性能提升。原始交付及完整统计见[最新验收报告](./2026-10-21-builtin-agent-budget-live.md)。
