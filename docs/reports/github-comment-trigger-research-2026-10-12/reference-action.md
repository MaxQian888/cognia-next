## What the reference mechanism actually does

This is a repository workflow integration. GitHub delivers an event to a workflow; the workflow starts a runner; the action validates actor and trigger, fetches issue/PR context, runs Claude Code, and writes results to GitHub. It is not inherently a desktop application's remote-control endpoint. The action is a composite action and executes on the runner chosen by the workflow. Its model calls use the configured provider. [`action.yml`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/action.yml), [`README`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/README.md), [`tag mode preparation`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/modes/tag/index.ts)

| Input event                      | Reference support and requirements                                                                                                        |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Issue or PR conversation comment | `issue_comment`; trigger phrase in comment body. GitHub uses the same event for both entities; `issue.pull_request` distinguishes them.   |
| PR inline/diff comment           | `pull_request_review_comment`; trigger phrase in comment body.                                                                            |
| PR review submission             | `pull_request_review`; trigger phrase in review body; the action checks `submitted` and `edited`.                                         |
| New issue                        | `issues: opened`; trigger phrase in title/body.                                                                                           |
| Assignment or label              | `issues: assigned` plus `assignee_trigger`, or `issues: labeled` plus `label_trigger`.                                                    |
| Automatic/manual jobs            | Explicit `prompt`, with recognized events such as PR changes, `workflow_dispatch`, `repository_dispatch`, `schedule`, and `workflow_run`. |

The action checks an escaped, case-insensitive trigger phrase with whitespace/punctuation boundaries. The default is `@claude`; a custom phrase such as `/claude` is configurable. The workflow must also subscribe to the event and permit the job through its `if:` condition. The supplied example subscribes to assignment events but its default `if:` still requires an issue title/body mention; assignment-only operation needs that condition adjusted. [`trigger.ts`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/github/validation/trigger.ts), [`example workflow`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/examples/claude.yml), [GitHub event documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment)

**Actual event whitelist:** current `parseGitHubContext()` recognizes `issues`, `issue_comment`, `pull_request`, `pull_request_target`, `pull_request_review`, `pull_request_review_comment`, `workflow_dispatch`, `repository_dispatch`, `schedule`, and `workflow_run`. Unknown event types throw. Thus the official documentation's “any GitHub event” description should not be interpreted as verified support for `push`, `discussion_comment`, or arbitrary events. [`context.ts`, lines 170–251](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/github/context.ts#L170)

## Modes, execution, and result writeback

Without `prompt`, a qualifying comment/issue trigger selects tag mode. It gathers issue/PR context, comments, and diffs, creates a tracking comment, and prepares a working branch. Inline-comment triggers get a reply in the review thread, with a conversation-comment fallback. The action supplies read tools, comment-update/CI tools, and constrained commit/push tools; arbitrary build/test Bash commands require explicit grants. Local file edits use `acceptEdits`. [`tag mode`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/modes/tag/index.ts), [`initial comment`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/github/operations/comments/create-initial.ts)

With `prompt`, agent mode runs from that explicit prompt and bypasses mention matching. It does not automatically create the tracking comment or gather the interactive comment context; tools and posting behavior must be supplied by the workflow/prompt. `track_progress: true` can force tag mode on supported entity events. [`mode detector`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/modes/detector.ts), [`agent mode`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/modes/agent/index.ts)

For interactive work, an open PR uses its existing branch; an issue or closed/merged PR gets a new branch from the configured/default base. Default issue implementation ends with commits and a prefilled **Create a PR** link for the human, rather than guaranteed automatic PR creation. Fork PR checkout is implemented via `refs/pull/<number>/head`, but that does not establish permission to push to the fork. [`branch setup`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/github/operations/branch.ts#L155), [`final comment link`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/entrypoints/update-comment-link.ts#L163)

## Setup and trust boundaries

Setup requires a checked-in workflow, a GitHub identity with appropriate permissions, and model-provider authentication. The official quick setup uses `/install-github-app`; manual setup installs the app, adds a provider secret, and copies a workflow. The supplied workflow uses checkout, `ubuntu-latest`, Contents/Issues/PR write permissions, `id-token: write`, and Actions read. `issue_comment` workflows must exist on the default branch. [Official setup guide](https://code.claude.com/docs/en/github-actions#setup), [`example workflow`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/examples/claude.yml), [GitHub `issue_comment`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment)

The default GitHub token path exchanges a GitHub OIDC token for an app installation token through Anthropic's token-exchange service; `github_token` can override it. Model authentication is separate. [`token.ts`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/github/token.ts)

The action checks repository write access for entity events and `workflow_run`; the latter also checks the actor of the upstream run. Both modes reject bots unless explicitly allowed. `allowed_non_write_users` bypasses write access only with a supplied token. Allowed bots have a separate trust path and do not need repository write permission; avoid wildcard bot enablement for public comments. [`execution gate`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/entrypoints/run.ts#L193), [`permissions.ts`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/github/validation/permissions.ts), [`actor.ts`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/src/github/validation/actor.ts)

Fork `pull_request` runs normally lack repository secrets and have a read-only `GITHUB_TOKEN`. `pull_request_target` and `workflow_run` provide privileged base-repository context and must not execute untrusted head code with secrets. The action restores selected Claude/configuration paths from the base branch, but leaves other project files at the PR head; executable package scripts/configuration remain relevant attack surfaces. [`action security guidance`](https://github.com/anthropics/claude-code-action/blob/1d6de8cb0c237e7c15e9e1bdf973826ebae490cc/docs/security.md#using-this-action-with-pull_request_target-or-workflow_run), [GitHub fork behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request), [GitHub Security Lab](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)

For an equivalent integration, the necessary contract is: authenticated event intake → authorized actor/command → deduplicated execution on a configured runner → bounded tools/provider credentials → progress/final GitHub writeback. This is an architectural inference from the reference; it does not assert that another application's existing GitHub event connector already implements that complete contract. Pinning the third-party action to its full commit SHA makes the inspected source immutable. [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions)
