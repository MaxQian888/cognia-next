# Pi subagent implementations: source comparison

Research date: 2026-10-21, Asia/Shanghai. Scope: read-only source and published-package research. No extension was installed, no provider request was made, and no typecheck or coverage command was run. Package versions below are observed snapshots, not a promise that their latest tags will remain unchanged.

## Findings

Pi subagents are an extension ecosystem, not one stable native configuration schema. This representative survey covers the official example, six published executors, and two model-routing add-ons. Similar names conceal materially different model selection, execution, and lifetime rules. Upgrading a package can replace its execution architecture or remove named-agent model configuration altogether.

## Official Pi v1.3.0 example

This is an example extension distributed with the Pi source, not a mandatory core subagent service. Its `subagent` tool discovers user Markdown agents in `~/.pi/agent/agents`, and optionally project agents in `.pi/agents`. Definitions contain name, description, tools, model, and the Markdown system prompt. The example ships sample agents and prompt workflows. See the [tagged README](https://github.com/badlogic/pi-mono/blob/v1.3.0/packages/coding-agent/examples/extensions/subagent/README.md) and [agent discovery](https://github.com/badlogic/pi-mono/blob/v1.3.0/packages/coding-agent/examples/extensions/subagent/agents.ts).

Exact model behavior in `runSingleAgent`:

1. An agent definition's `model` wins.
2. Otherwise use the parent's current `provider/id`, captured when the tool executes.
3. If neither exists, omit `--model` and leave selection to the child Pi CLI.

The example has no call-level model parameter, shared child default setting, or special `inherit` sentinel of its own. When an agent has no model, it also receives the parent's thinking level; an explicitly modeled agent does not inherit that thinking flag through this code path. The child runs `pi --mode json -p --no-session`, with explicit tools when defined, an appended agent prompt, and a task. It inherits the process environment and normal Pi discovery because the example does not add `--no-extensions` or equivalent isolation flags. See [dispatch and launch source](https://github.com/badlogic/pi-mono/blob/v1.3.0/packages/coding-agent/examples/extensions/subagent/index.ts).

Single, parallel, and sequential chain execution are supported. A parallel call accepts at most eight jobs and runs at concurrency four; chains substitute `{previous}`. Results stream while the foreground tool is pending. The example does not implement persistent worker handles, detached background dispatch, steering, session resume, or a separate lifecycle management API. Abort sends a termination signal to the immediate child; the source's escalation condition should not be treated as proof that a whole descendant process tree was stopped.

The execution tool is not guarded by a TUI requirement and consumes structured JSON subprocess output, so it is structurally usable from noninteractive/RPC parents. Interactive project-agent confirmation is conditional on `ctx.hasUI`, requested scope, and project trust; it is not an unconditional noninteractive admission gate. No Cognia PII hook or gateway binding is supplied by this example. Those must be established by the host before relying on it.

## nicobailon/pi-subagents

### Latest 0.80.0

This is the richest inspected option for named-agent models and host integration. Markdown frontmatter, ordinary settings, provider-specific settings and per-launch inputs all participate in selection. The documented priority, corroborated by the discovery/preflight implementation, is:

`per-run model > provider-scoped role override > agentOverrides.<name>.model > agent frontmatter model > subagents.defaultModel > parent model`.

User and trusted project settings can set child defaults and role overrides; project settings take precedence. `defaultProvider` disambiguates bare model IDs and does not override a fully qualified provider/model choice. The explicit `inherit` sentinel resolves to the current parent model and bypasses a shared child default. Thinking suffixes are resolved separately. Latest launches select one model; provider failures are returned rather than silently trying another. See [model documentation](https://github.com/nicobailon/pi-subagents/blob/80f8f79d51ee8075fd39baf7fe8ff36b43c3a790/docs/models.md), [agent discovery](https://github.com/nicobailon/pi-subagents/blob/80f8f79d51ee8075fd39baf7fe8ff36b43c3a790/src/agents/agents.ts), and [preflight](https://github.com/nicobailon/pi-subagents/blob/80f8f79d51ee8075fd39baf7fe8ff36b43c3a790/src/api/preflight.ts).

Foreground Pi children are SDK `AgentSession` objects inside the parent process. Background Pi children run SDK sessions inside a detached runner process. Therefore “each child is an isolated Pi subprocess” is inaccurate for this version. Foreground sessions inherit registered parent providers without replaying all ambient extensions; background sessions may load ambient extensions unless a definition or capability ceiling suppresses them. A provider whose behavior depends on its extension's session hooks needs additional care even when the provider itself resolves. See [child-session implementation](https://github.com/nicobailon/pi-subagents/blob/80f8f79d51ee8075fd39baf7fe8ff36b43c3a790/src/runs/shared/child-session.ts) and [extension inheritance rules](https://github.com/nicobailon/pi-subagents/blob/80f8f79d51ee8075fd39baf7fe8ff36b43c3a790/docs/agents.md).

The package supports single, parallel and chain work, detached jobs, artifacts, steering, interrupt/stop and retained-session resume. A public event-bus API exposes async spawn/status/steer/interrupt/stop/resume and launch preflight. This is an **in-process extension API**, distinct from Pi's external LF-delimited JSONL RPC transport; a host must bridge it deliberately. Normal launches can run headlessly; optional inspectors are a separate surface. See [extension APIs and lifecycle contracts](https://github.com/nicobailon/pi-subagents/blob/80f8f79d51ee8075fd39baf7fe8ff36b43c3a790/docs/extension-api.md).

The package offers model-scope policy and host-registered capability ceilings. A model scope with only `enforce: true` can still merely warn for inherited/frontmatter/default selections; `strict: true` is needed to reject those out-of-scope selections too. Capability ceilings intersect permitted agents/tools and can forbid extensions, propagate to nested/background work, and persist for recovery. They are cooperative policy inside a trusted process, not protection from malicious extensions already executing in that process. These mechanisms do not by themselves establish Cognia's outbound PII boundary. See [model scope](https://github.com/nicobailon/pi-subagents/blob/80f8f79d51ee8075fd39baf7fe8ff36b43c3a790/docs/models.md#model-scope-enforcement) and [capability ceilings](https://github.com/nicobailon/pi-subagents/blob/80f8f79d51ee8075fd39baf7fe8ff36b43c3a790/docs/extension-api.md).

The published package peers on Pi AI `>=1.2.0` and other Pi packages with open version ranges. This supports investigation against Pi `1.3.0`; it does not prove Cognia's RPC, PII, placement, cancellation or resume integration. Independent external CLI runners also have their own provider/model semantics, so a Pi model ID must not automatically be forwarded to them.

### Catalog pin 0.47.1 differs

The pinned package is not behaviorally equivalent to latest. Its documented order is:

`per-run model > frontmatter model > agentOverrides.<name>.model > subagents.defaultModel > parent model`.

In particular, ordinary role overrides fill fields absent from custom frontmatter instead of replacing them. Its foreground source spawns a CLI process, and its old model documentation includes backup/fallback model settings that latest no longer promises. Its Pi AI peer floor is `>=0.80.0`. These differences require a versioned adapter or an explicitly supported version range, rather than one projection for every package release. See [pinned models](https://github.com/nicobailon/pi-subagents/blob/5d158bf6c8f63855a1b89d135f0cec528e4fde91/docs/models.md), [pinned agent merging](https://github.com/nicobailon/pi-subagents/blob/5d158bf6c8f63855a1b89d135f0cec528e4fde91/src/agents/agents.ts), and [pinned foreground execution](https://github.com/nicobailon/pi-subagents/blob/5d158bf6c8f63855a1b89d135f0cec528e4fde91/src/runs/foreground/execution.ts).

## @narumitw/pi-subagents

### Latest 3.3.0 is deliberately parent-model-only

The current tool schema accepts task, tools, local skills/extensions, thinking level and optional timeout. It has **no agent name, agent file, model or provider field**. `resolveChildModel` requires a selected parent model and returns exactly its `provider/id`; it does not search a child default. Thinking is call override, then effective parent thinking. There is no shared child-model default or independently selectable named-agent model in this runtime. See [current tool schema and model resolver](https://github.com/narumiruna/pi-extensions/blob/a0d200d98683a257ecedc9c34a4773c288d822cf/packages/pi-subagents/src/tools.ts).

Each job starts an isolated Pi subprocess in RPC mode with session persistence, automatic extension, skill and prompt-template discovery disabled. It attaches only its communication bridge and explicitly allowed resources, then passes the captured model, thinking level, tools and project-trust posture. A broker authenticates parent/child messaging. A readiness step verifies requested extension tools before the model task starts. See [process launch](https://github.com/narumiruna/pi-extensions/blob/a0d200d98683a257ecedc9c34a4773c288d822cf/packages/pi-subagents/src/process.ts).

Jobs return IDs immediately and support inspect, wait, cancel, bidirectional requests and parent steering. Multiple starts provide parallel work, capped at eight active jobs; there is no legacy chain/fan-in workflow API. A caller can implement sequencing itself through waits. Completed jobs do not remain as resumable child sessions. Session replacement, reload and shutdown cancel owned jobs and close the broker. Timeout is optional and has no default in v3; this differs from legacy timeout documentation. See [runtime lifecycle](https://github.com/narumiruna/pi-extensions/blob/a0d200d98683a257ecedc9c34a4773c288d822cf/packages/pi-subagents/src/runtime.ts) and [current README](https://github.com/narumiruna/pi-extensions/blob/a0d200d98683a257ecedc9c34a4773c288d822cf/packages/pi-subagents/README.md).

RPC/noninteractive operation is central to the child transport. UI management commands require appropriate UI support, but core job tools are not a TUI-only implementation. Child credentials must be accessible to the subprocess: a process-local runtime API key is explicitly refused. A dynamically registered parent provider is refused when no extension attachment can recreate it. This matters for Cognia-hosted providers even before adding per-agent model selection.

The default work tools are read, grep, find and ls; attached extensions require trusted local resources. The child still inherits `process.env`, runs as the same user, and can access host resources through authorized tools/extensions. Privacy-filtered inspection metadata and attachment-path redaction are implemented; they do not demonstrate redaction of all outbound task/context/model payloads. No Cognia PII or gateway bridge was found in the inspected execution path.

The package's development dependencies target Pi `1.3.0`, but its wildcard peer ranges are not compatibility proof. Both npm `3.3.0` and source contain the v3 implementation despite the stale publication paragraph noted above.

### Catalog pin 1.0.0 is a different product contract

The published `1.0.0` tarball includes named Markdown agents, settings-backed per-agent models/thinking/tools/timeouts, blocking single/parallel/chain/fan-in calls, and retained jobs with subprocess, RPC or same-process transports. Its in-process model resolver uses an explicit configured agent model first, then the parent model, then the first authenticated model if no parent exists. The CLI transport delegates omitted-model resolution to the child CLI rather than promising identical inheritance. See [legacy README](https://github.com/narumiruna/pi-extensions/blob/c98af43a6c71c5839b2e0671db71ed1cc1fc0c51/packages/pi-subagents/README.md) and [legacy in-process resolver](https://github.com/narumiruna/pi-extensions/blob/c98af43a6c71c5839b2e0671db71ed1cc1fc0c51/packages/pi-subagents/src/in-process-transport.ts).

A Cognia adapter written against that catalog pin cannot assume it remains valid after upgrading to v3. Adding a model property to the current v3 launch arguments would fail its strict schema; per-agent model support would require an upstream API change or a separately owned implementation.

## pi-cli-subagents 0.4.0

This package orchestrates persistent native conversations across three CLI families. It is not a generic Pi agent-Markdown loader. A role includes description/instructions, CLI choice, optional model/provider/thinking or effort, permission mode and capability trims. Roles are loaded from `~/.pi/agent/cli-subagents.roles.json` and, for trusted projects, `.pi/cli-subagents.roles.json`. Later role documents replace an earlier role object; configuration should include the required description and instructions. See [tagged role loader and validation](https://github.com/joshua-zyy/pi-cli-subagents/blob/v0.4.0/src/roles.ts).

Model behavior is backend-specific:

- Pi: explicitly configured role model/provider/thinking win. Each missing field is filled from the current parent; when the parent lacks a value the flag is omitted and native Pi selection remains. There is no documented `inherit` string sentinel. Pinning a provider alone still fills the omitted model with the parent's model ID, which may not exist on that provider.
- Codex: an explicit role model is passed to native app-server; an omitted model uses its own native configuration. The Pi parent's provider/model is not copied.
- Claude: an explicit role model is passed as the CLI's native model/alias; an omitted model follows Claude's native defaults. The Pi parent's provider/model is not copied.

The start tool selects a configured role; its strict schema has no per-call model override. These rules are implemented by [parent inheritance](https://github.com/joshua-zyy/pi-cli-subagents/blob/v0.4.0/src/index.ts), [Pi RPC adapter](https://github.com/joshua-zyy/pi-cli-subagents/blob/v0.4.0/src/pi-adapter.ts), [Codex adapter](https://github.com/joshua-zyy/pi-cli-subagents/blob/v0.4.0/src/codex-adapter.ts), and [Claude adapter](https://github.com/joshua-zyy/pi-cli-subagents/blob/v0.4.0/src/claude-adapter.ts).

Detached workers have separate lifetimes from their parent UI and retain native session identity. `start`, `send`, `interrupt`, `stop` and `reclaim` are distinct operations. Parallelism comes from multiple starts; no built-in chain abstraction is required. Default per-parent caps are four potentially active turns and twelve unreleased runtimes. Reaching a cap refuses admission rather than queuing. Stop retains history and refuses to discard an in-flight accepted turn; release, uncertainty and dead-process reclamation are tracked explicitly. Protocol v1/v2 records are read-only to current v3 workers and are not silently migrated. See [manager implementation](https://github.com/joshua-zyy/pi-cli-subagents/blob/v0.4.0/src/manager.ts) and [operational contract](https://github.com/joshua-zyy/pi-cli-subagents/blob/v0.4.0/docs/subagent-tool-contract.md).

The underlying transports are Pi RPC, Codex app-server over stdio and Claude stream-json. Results and questions return asynchronously to the originating parent session; interactive panes are supplemental. Runtime/version capability checks matter: published documentation supports Claude `2.1.x` patch `283` or later, and requires revalidation of later minor/major versions. The package requires Node `>=22.19.0`; it reports Pi load/register checks through `1.3.0`. Its README explicitly separates historical real-provider tests from fixture coverage and does not claim fresh Codex/Claude live acceptance for the latest cwd-only interface. We did not repeat those live tests. See [published/tagged README](https://github.com/joshua-zyy/pi-cli-subagents/blob/v0.4.0/README.md).

Its native approval bridge is materially more involved than setting a Pi child model. Tool replies answer one task question or review one permission request; they are not permanent authority. CLI credentials, permissions, filesystem access and outbound requests remain backend-specific. A Cognia Pi gateway plan alone would not authorize the Codex/Claude backend calls. The extension does not manage worktrees or sandbox a selected cwd, and no Cognia PII bridge is supplied by the inspected source.

The source credits tintinweb/pi-subagents as inspiration for status/conversation UI, plus adapted code from other named projects. That supports an inspiration relationship, not a claim that these implementations share execution/model semantics or are interchangeable Git forks. See [credits and NOTICE](https://github.com/joshua-zyy/pi-cli-subagents/blob/v0.4.0/NOTICE).

## Consequences for a future Cognia change

1. Identify the actual extension and supported version before projecting models. Package names and old catalog metadata are insufficient.
2. Treat explicit per-agent selection, per-run overrides and an optional child default as separate layers. Preserve the target extension's precedence, or explain and enforce a deliberate Cognia contract at a supported public host seam.
3. Admit every effective model before launch. Discovery in Markdown/settings is not enough when the extension also accepts per-run changes, nested children, recovery or external CLI backends.
4. Keep runtime model providers, credentials, request redaction and cancellation available in the actual child execution boundary: same-process SDK, detached SDK runner and RPC subprocess require different integration work.
5. Test explicit models, omitted models, `inherit` where supported, invalid models/provider mismatches, late per-run overrides, nested/background work and resume. Verify RPC and placement separately from TUI behavior, and distinguish loopback fixtures from real-provider/native-host acceptance.

The official example is a small baseline for controlled subprocess integration. Nico latest is the closest native configuration fit for individual explicit models plus a shared child default, with a correspondingly larger integration surface. Narumitw latest is useful for bounded parent-model jobs but does not meet independent model selection as written. CLI subagents is a separate multi-backend orchestration product and should be evaluated as such. A short proof of concept should compare the locally installed gotgenes extension against Nico's native defaults/overrides, while separately proving gateway admission, outbound PII interception, cancellation and placement for each actual execution boundary.

## Gotgenes, tintinweb and community implementations

These belong to the tintinweb lineage; they are separate maintained packages, not interchangeable versions. The old gotgenes repository was archived after moving into its [pi-packages monorepo](https://github.com/gotgenes/pi-packages/tree/main/packages/pi-subagents). Archival alone does not mean the package was abandoned. Its historical upstream-comparison document compares old releases and should not be used as a current feature matrix.

The installed `@gotgenes/pi-subagents@19.2.2` resolver selects `agentConfig.model ?? params.model`: **agent file > call > parent**. Published `25.0.1` instead defaults to **call > agent file > parent**; `locked: true` or a field lock such as `locked: [model]` can preserve operator-owned fields. These are meaningful precedence changes. Latest unresolved winning caller models error, but unresolved agent-file models fall back silently to the parent. Preserving a frontmatter string therefore does not establish that the selected model actually ran. Evidence: installed `src/config/invocation-config.ts`, and the [published 25.0.1 artifact](https://registry.npmjs.org/@gotgenes/pi-subagents/-/pi-subagents-25.0.1.tgz), specifically `src/config/invocation-config.ts` and `src/session/model-resolver.ts`.

Gotgenes uses same-process SDK sessions and a typed service/lifecycle API. Its `session-created` event fires synchronously before binding child extensions, with child and parent session IDs. This is a useful integration seam, not proof that Cognia can already attach every required guard. Permission and worktree behavior are companion-package concerns. The inspected package has no general native child-only `defaultModel` equivalent; omitted custom-agent models normally inherit the parent, while built-in agents may have their own defaults. The published peer floor is Pi `>=1.0.0`; compatibility with the installed Pi `1.3.0` was not runtime-tested here.

Tintinweb `0.22.0` and community `0.20.2` both retain **agent file > call > parent**. Both can silently inherit when an agent-file model is unavailable. Tintinweb additionally tolerates model-ID variation and can resolve a qualified model through another provider. Cognia must validate the intended exact route before allowing such resolution. See the pinned [tintinweb invocation resolver](https://github.com/tintinweb/pi-subagents/blob/85a704cb8f35c96c0cabfa665b572bab296942e5/src/invocation-config.ts), [model resolver](https://github.com/tintinweb/pi-subagents/blob/85a704cb8f35c96c0cabfa665b572bab296942e5/src/model-resolver.ts), and [community invocation resolver](https://github.com/mt-code/pi-subagents-community/blob/deed66cdb15f47ea75236394a99297fae8f2fe0d/src/invocation-config.ts).

Tintinweb's model scope is **opt-in and off by default**. Even when enabled, out-of-scope frontmatter models still run with a warning; nested warning cases proceed silently. Missing/empty supported allowlist entries skip enforcement. This is an orchestrator guardrail, not an authoritative gateway admission boundary. Its workflows, nested delegation, scheduling and worktree features broaden the integration surface. See [the pinned Model Scope contract](https://github.com/tintinweb/pi-subagents/blob/85a704cb8f35c96c0cabfa665b572bab296942e5/README.md#model-scope).

The three published artifacts' SHA-512 integrity values were checked against npm metadata successfully. Their cached metadata preserves exact artifact URLs and available git heads. No package was installed or upgraded.

## Smaller model-routing add-ons

Two additional published packages offer routing without owning child execution. Neither implements the requested fallback contract unchanged.

| Add-on                        | Inspected release | Actual behavior                                                            | Fit for preserving explicit agent models                                                                                   |
| ----------------------------- | ----------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `pi-subagent-models`          | `0.2.0`           | Forced session model > forced global model > caller > native configuration | Forced mode overwrites existing call and agent choices; `Default` disables injection rather than defining a child fallback |
| `@sencha930511/pi-model-sync` | `0.3.1`           | Maps spawning-session model and agent name to an injected child call model | Preserves explicit call models, but intentionally overrides agent-file models when injecting                               |

`pi-subagent-models` targets Pi `0.84.1` plus Nico `pi-subagents@0.40.0` event contracts and must load before the executor. It mutates tool, slash-command, prompt-template and RPC launch requests; global state lives under `PI_CODING_AGENT_DIR` or the normal Pi agent directory. Its documented version contract is not evidence of compatibility with Nico `0.80.0` or gotgenes. See the [published artifact](https://registry.npmjs.org/pi-subagent-models/-/pi-subagent-models-0.2.0.tgz) and [tagged request patching source](https://github.com/Yivas/pi-subagent-models/blob/v0.2.0/src/index.ts).

Model-sync's upstream-Pi path specifically recognizes `@mjakl/pi-subagent` calls shaped as `{ calls: [...] }`; it does not cover every tool named `subagent`, including Nico's different schema. Its OMP path uses a separate host hook and cannot be assumed available in upstream Pi. The published README explicitly treats profile routing as stronger than agent frontmatter. This is a useful reference for profile-based routing, but violates the requested explicit-file preservation rule as supplied. See the [release-pinned README](https://github.com/SenCha930511/pi-model-sync/blob/717a835d07dcd2639ae4637ec3d560d59fa0c8e2/README.md#pi-subagent-routing-rules) and [implementation](https://github.com/SenCha930511/pi-model-sync/blob/717a835d07dcd2639ae4637ec3d560d59fa0c8e2/index.ts).

Both add-ons' published npm artifact integrity checks passed. Their executors were not installed or exercised. Other catalog entries surfaced during discovery, including `pi-submarine`, `pi-sub-agent` and `pi-agent-suite`; those are not included in the detailed compatibility assessment above.

## Current Cognia gaps

The local CLI reports Pi `1.3.0`; the inspected non-secret package settings select gotgenes `19.2.2`. This does not imply that Cognia automatically loads that global package stack.

1. **No Pi child-model slot.** [model-slots.ts](../../lib/ai/agent/external/config/model-slots.ts) declares child-model slots for Claude, Codex and OpenCode, but no Pi branch. The present Pi model plan has no native child default projection.
2. **Only the primary gateway model is exported.** The Pi branch of [gateway-task.ts](../../lib/ai/agent/external/config/gateway-task.ts) emits one model in `pi/models.json` and only `cognia/<primary>` in `enabledModels`. Changing an agent Markdown field alone cannot make another Cognia model available or authorized.
3. **The importer discards the active model hint.** [subagent-importers/pi.ts](../../lib/claude/subagent-importers/pi.ts) sets `model: undefined`, while retaining raw frontmatter. Its comment that Pi agents have no model field is too broad for the researched extension formats. Retention must distinguish model provenance and extension semantics rather than invent a universal Pi schema.
4. **Extension loading is explicit in hosted tasks.** [rpc-client.ts](../../packages/agent-pi/src/rpc-client.ts) supplies isolation flags and a verified Cognia extension. Operator-opted plugin packages from `metadata.piPackages` can still load through explicit `-e` entries before Cognia's extension. An installed global package is not evidence that a hosted task uses it, and explicit loading is not proof that its nested SDK sessions inherit Cognia's gates.
5. **Catalog pins describe older contracts.** [catalog.ts](../../lib/pi-packages/catalog.ts) pins gotgenes `19.2.2`, Nico `0.47.1` and narumitw `1.0.0`. These cannot be upgraded based on package names alone. The catalog also places them in the same `subagents` overlap group; enable one execution family deliberately rather than stacking competing tool registrations.

Relevant architecture: [ADR-0119 Pi native RPC](../content/docs/en/adr/0119-pi-native-rpc-integration.md), [ADR-0210 plugin Pi packages](../content/docs/en/adr/0210-a-plugin-can-carry-a-pi-package.md), [ADR-0217 host ports](../content/docs/en/adr/0217-agent-integrations-are-packages-behind-host-ports.md), and the existing gateway model-plan/projector modules. The implementation should extend these boundaries rather than create a second unrelated model-routing system.

## Recommended next scope

For the exact configuration goal, Nico latest is the closest native fit: project a shared fallback into `subagents.defaultModel`, preserve explicit model choices and `inherit`, and avoid using higher-priority per-agent overrides to represent a fallback. For reuse of the installed ecosystem and child lifecycle hooks, gotgenes is the other useful candidate; its exact supported release and locking behavior must be explicit. Narumitw v3 lacks the required API. Cross-CLI workers and forcing add-ons solve different problems.

A future implementation should first preserve imported model hints and compile all chosen models through Cognia's existing admission/catalog plan, then add extension/version-specific projections. An invalid or unauthorized explicit model must produce a clear error, not silently become the parent/default or another provider. Foreground, background, nested and resumed children must then prove gateway routing, PII interception, approvals and cancellation through their actual SDK/process boundaries. These are recommendations from source inspection, not completed implementation or live acceptance.
