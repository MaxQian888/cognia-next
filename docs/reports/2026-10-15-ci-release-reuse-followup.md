# Release and deployment reuse follow-up

Date: 2026-10-15. Research-only review of the current working tree, based on HEAD `f3b0e5ca9fa9dc1930156564a3939be60f09ff3c` plus the authorized, uncommitted CI changes. Source line references describe that working tree. No workflows, source code, releases, deployments, or caches were modified by this audit; no build was dispatched. This report is separate from the incremental-test audit because it covers release packaging and deployment handoff.

## Decision

Fix the fresh-run SDK publisher prerequisite gap first. Then add a small, verified artifact handoff within the release run before attempting cross-run reuse. Keep full release Quality/tests, native smoke, package checks, signing, notarization, and deployment health checks. The next highest-confidence performance opportunities are the service Docker dependency layers and deploying an already-verified image by digest. Sharing Tauri frontend output is plausible but needs an explicit build-input contract first.

## Confirmed gaps and safe next steps

### 1. SDK publication starts without the native/runtime inputs its smoke requires

The verified chain is:

`release.publish-agent-sdk` → fresh checkout/install → `pnpm agent:sdk:smoke` → **raw** `node scripts/build/build-cli.mjs` → esbuild/staging → native helper existence check → Node RPC smoke.

The publisher has no native build, Rust cache restore, or artifact download before the smoke. The script uses raw Node, so it does not invoke `precli:build`. Root postinstall installs sidecar dependencies and builds linked packages/a2ui/VSCode; it does not build the three Rust helpers or webclone. The webclone runtime is also a CLI bundle input, so a cold job can fail before reaching the native check. Sources: [release.yml:343](../../.github/workflows/release.yml#L343), [release.yml:378](../../.github/workflows/release.yml#L378), [package.json:130](../../package.json#L130), [package.json:411](../../package.json#L411), [postinstall.mjs:42](../../scripts/postinstall.mjs#L42), [entry.ts:44](../../cli/src/cli/entry.ts#L44), [build-cli.mjs:81](../../scripts/build/build-cli.mjs#L81), [native-host-files.mjs:43](../../scripts/build/native-host-files.mjs#L43).

The preceding host jobs having succeeded does not make their workspaces available here. They publish npm packages, but this job neither downloads those packages as local host inputs nor restores a release artifact. Its later `pack:test` also omits `--require-host`: the pack test explicitly skips the default-host leg when `packages/agent-host-linux-x64/bin` is absent. Sources: [release.yml:332](../../.github/workflows/release.yml#L332), [release.yml:383](../../.github/workflows/release.yml#L383), [pack-test.mjs:24](../../packages/agent/scripts/pack-test.mjs#L24), [pack-test.mjs:152](../../packages/agent/scripts/pack-test.mjs#L152).

**Next step:** give the SDK job a complete, verified same-run Linux host artifact and make the default-host pack test required. Preserve the Node RPC crash-recovery smoke separately: a Bun host readiness smoke does not establish equivalent Node bundle behavior. Either supply the full Node smoke prerequisites explicitly or prepare its Node artifact once upstream. On an artifact miss, run the canonical prerequisite/build path and all smoke checks; never turn a missing prerequisite into a skipped test. Add a cold-checkout contract test proving the caller cannot reach smoke without its inputs. This is a source-confirmed wiring gap, not a hosted failure reproduced during this audit.

### 2. “Complete release” promotion occurs before all release products finish

Quality/test gating itself is present. The ordering concern is later: the reusable Tauri workflow publishes the draft after its Tauri matrix succeeds; only after that reusable workflow finishes can `publish-agent-hosts` start, followed by `publish-agent-sdk`. Therefore a public GitHub release can exist while CLI archive/npm publishing is pending or has subsequently failed. Sources: [build-tauri.yml:206](../../.github/workflows/build-tauri.yml#L206), [build-tauri.yml:230](../../.github/workflows/build-tauri.yml#L230), [release.yml:219](../../.github/workflows/release.yml#L219), [release.yml:345](../../.github/workflows/release.yml#L345).

Separately, `images.yml` responds to the same tag push, sets `should_push=true`, and its publishing jobs depend on `vars`, not the release Quality/test workflow. The agent-bundle image has its own native smoke barrier; fast images/server images are not gated by the release workflow's complete Quality/test outcome. Sources: [images.yml:33](../../.github/workflows/images.yml#L33), [images.yml:99](../../.github/workflows/images.yml#L99), [images.yml:114](../../.github/workflows/images.yml#L114), [images.yml:401](../../.github/workflows/images.yml#L401).

**Next step:** decide whether GitHub release visibility and stable image tags represent the complete product release. If so, keep building/staging in parallel, but have one final promotion job depend on all required successful checks and artifact producers. Reuse tested digests at promotion; do not rebuild them. If these products intentionally release independently, make that boundary explicit instead of claiming an aggregate release is complete. Do not weaken the current full release checks to reduce wall-clock time.

### 3. Integrity manifests do not yet establish cross-run source provenance

The CLI layout manifest records schema/target/variant/file digests; the npm host manifest records schema/target/file digests. These verify closure and bytes, but neither binds the payload to a Git commit, producer workflow/run, runtime/compiler version, feature/profile, or signing state. Sources: [cli-artifact-integrity.mjs:17](../../scripts/build/cli-artifact-integrity.mjs#L17), [verify-agent-host-package.mjs:103](../../scripts/build/verify-agent-host-package.mjs#L103).

**Next step:** start with a same-run artifact handoff. Before cross-run reuse, add a small producer envelope with exact commit and repository, workflow/run/attempt, OS/architecture/target, Node/Bun/Rust versions, Cargo profile/features, relevant lock/config hashes, payload digest, and signing/notarization state. Verify a successful trusted producer and every identity field before consuming. Continue running consumer smoke/package checks. Missing, expired, corrupt, wrong-SHA or mismatched-runtime artifacts must fall back to a complete build, not a permissive restore key. A digest alone proves consistency with a manifest, not who produced either file.

GitHub distinguishes reusable dependency/build caches from workflow artifacts, and its artifacts API exposes a digest plus producer run/head SHA. Those are useful inputs to validation, not a substitute for the repository's acceptance contract. [GitHub workflow artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts), [GitHub artifacts API](https://docs.github.com/en/rest/actions/artifacts).

### 4. Signaling/share Docker source edits discard the dependency compilation layer

Both small service Dockerfiles copy manifests **and all application sources/tests** before one `cargo build --release --locked`. There is no dependency-cooking stage or target cache mount. The GHA cache in `fast-images` can reuse an unchanged build layer, but a changed copied source invalidates that layer; it does not isolate the unchanged Rust dependency graph. Sources: [signaling Dockerfile:5](../../services/signaling-server/Dockerfile#L5), [share Dockerfile:5](../../services/share-server/Dockerfile#L5), [images.yml:207](../../.github/workflows/images.yml#L207). Docker documents `COPY`-based invalidation of subsequent layers. [Docker cache invalidation](https://docs.docker.com/build/cache/invalidation/).

**Next step:** extend the existing cargo-chef dependency-stage pattern to these two service workspaces, preserving their lockfiles, exact features, Rust image and runtime/health checks. Prefer a dependency layer already exportable by the existing BuildKit cache over adding another broad cache system. Benchmark unchanged build, application-only edit, dependency edit, and inaccessible-cache cold fallback. Do not promise a speedup magnitude without those measurements.

### 5. Fly deployment rebuilds service images already produced by the image workflow

`images.fast-images` builds signaling/share from their service Dockerfiles. The two Fly deploy jobs check out sources and call `flyctl deploy --remote-only`; their `fly.toml` files specify the same Dockerfiles. They do not consume a previously tested image digest. Sources: [images.yml:122](../../.github/workflows/images.yml#L122), [deploy.yml:366](../../.github/workflows/deploy.yml#L366), [deploy.yml:385](../../.github/workflows/deploy.yml#L385), [signaling fly.toml:11](../../services/signaling-server/fly.toml#L11), [share fly.toml:18](../../services/share-server/fly.toml#L18).

**Next step:** for a matching trusted SHA, deploy a verified image digest through Fly's supported `--image` input. Keep environment approval, secrets, configuration, volume handling and health/smoke checks in the deploy job. Validate registry pull access and architecture before enabling this path; the current GitHub token does not prove Fly can pull a private GHCR image. When no eligible image exists, retain the current source build as fallback. [Fly deploy command](https://docs.fly.io/flyctl/cmd/fly_deploy).

### 6. Tauri repeats frontend production work across four targets

The Tauri matrix has four targets. Each calls tauri-action, whose configured `beforeBuildCommand` prepares native sidecars and then runs the root `pnpm build` plus frontend check. That build includes the sizeable root `prebuild` asset/sidecar chain. Sources: [build-tauri.yml:85](../../.github/workflows/build-tauri.yml#L85), [build-tauri.yml:185](../../.github/workflows/build-tauri.yml#L185), [tauri.conf.json:10](../../src-tauri/tauri.conf.json#L10), [package.json:25](../../package.json#L25), [package.json:410](../../package.json#L410).

**Next step:** profile the pure static-export portion separately from native/resource preparation. Consider one same-SHA frontend artifact for compatible desktop targets, with native sidecars and signing still built/tested on each target. Do not share `target/`, all of `sidecar/node_modules`, or the whole prebuild output across platforms. The current frontend embeds `NEXT_PUBLIC_BUILD_TIME` and has a mobile platform switch, so use one defined build timestamp and record platform/environment inputs before expecting equivalent output. Sources: [next.config.ts:29](../../next.config.ts#L29), [next.config.ts:72](../../next.config.ts#L72), [next.config.ts:388](../../next.config.ts#L388). This is a verified repeated command path but only a candidate artifact boundary; output equivalence has not been demonstrated.

- Status deployment runs the entire root static export and a Chromium asset crawl, but unlike docs/web deployment it has no Next compilation cache. Add a dedicated status build-profile cache first; preserve extraction/crawl and Worker typecheck/tests/migrations. Cross-environment final-output reuse needs an environment-input contract. ## Suggested implementation order and acceptance

1. **Release SDK correctness:** cold checkout reaches every smoke with canonical prerequisites; required default-host pack leg cannot silently skip. Keep the Node crash-recovery and native bundled-host tests distinct.
2. **Same-run release handoff/promotion:** produce once, transfer verified artifacts, smoke each native target, publish only after required producers/checks succeed. Assert rejected SHA/runtime/digest and artifact-miss fallback cases.
3. **Service image efficiency:** split Rust dependencies from source, then deploy the exact tested digest. Compare cold and warm application-edit runs and preserve health failures as deployment failures.
4. **Frontend/SDK shared artifacts:** instrument first, then extract only proven portable outputs. Keep full nightly and release checks as the acceptance layer.

No hosted timing, cache hit-rate, registry access, signing, or deployment success is claimed by this static audit. Source references and official documentation support the call-chain findings; performance value and platform equivalence still need dedicated measurements.
