## Experiments and evidence

Each experiment has its own pre-registered contract and raw evidence under `account-sync/`, `event-batching/`, `shared-chat-batching/` or `attachment-append/`. Workloads use synthetic data and isolated test databases. No user data is uploaded, production feature flag enabled, schema changed, or external service reconfigured.

### Native browser outbox drain

Production `pushOutbox`, native Chromium 151 IndexedDB and WebCrypto; one warmup and ten samples per variant/workload with alternating order. This fixture seeds a minimal Dexie schema directly, then measures reading, sealing, signing, locally acknowledging and settling the complete outbox. It excludes capture, at-rest encryption, enrollment, network transfer and receiving-device apply. Every emitted operation was decrypted after timing and checked for its expected id/title and contiguous sequence.

| Queued title updates | Baseline median / MAD | Result median / MAD | Interpretation                                                                            |
| -------------------- | --------------------- | ------------------- | ----------------------------------------------------------------------------------------- |
| 8,192                | 1,351.15 / 6.35 ms    | 1,009.80 / 3.10 ms  | **25.26% faster**; 341.35 ms saved, above both the 10% practical bar and 2×MAD (12.70 ms) |
| 300                  | 31.45 / 0.80 ms       | 31.10 / 0.75 ms     | Within noise; no speedup claim and no guardrail regression                                |
| 1                    | 0.85 / 0.15 ms        | 0.70 / <0.001 ms    | Within noise; no speedup claim and no guardrail regression                                |

The 8,192-row fixture still emits 8,192 operations / 3,859,933 JSON bytes. All variants and samples match on op counts and bytes. The optimization bounds each eligible outbox result to 512 rows rather than loading the entire remaining backlog before slicing. The skipped-oversize branch filters before limiting, so an oversized prefix cannot starve valid rows behind it. The 256-op wire cap, encryption, field clocks, retry behavior and revision-checked acknowledgment settlement are unchanged.

Evidence: [contract](browser-contract.md), [raw samples](browser-raw.json), [validated metrics](browser-metrics.json), [browser harness](browser-benchmark.ts.txt), [build script](build-browser-benchmark.mjs), [metrics reducer](summarize-browser.mjs). Reproduction uses a loopback-only server and a separate agent-browser session; the session/server used here have been closed. Bundles remain under `/tmp/cognia-transfer-browser-2026-10-07` and can be regenerated. The baseline source is preserved under `account-sync/baseline-pusher.ts.txt`.

### WebSocket batch preparation

Release-mode Rust on Apple M4 Pro / macOS; two warmups and twelve measured samples per workload. Each timing below is **20 complete batching-plus-encoding executions**, including the existing input cloning. Live time is simulated; no socket or 60-second real-time wait is included.

| Workload per execution            | Baseline median | Result median | Improvement |
| --------------------------------- | --------------- | ------------- | ----------- |
| 1,024-frame reconnect replay      | 30.0204 ms      | 17.0899 ms    | **43.07%**  |
| 6,000-event synthetic live stream | 195.2238 ms     | 111.8467 ms   | **42.71%**  |
| 128 × 16 KiB replay               | 28.5186 ms      | 24.0969 ms    | **15.50%**  |

All deltas exceed the pre-registered noise rule and practical threshold. The encoder now serializes a borrowed envelope instead of materializing/cloning a second JSON tree. Parsed values, frame order, batch counts, wire byte lengths and omission of private routing metadata match. Object key order may differ, which is immaterial to the JSON-parsing receivers. No batching window or first-frame behavior changed. This optimization applies to the WS encoder; RTC uses a different envelope.

Evidence: [detailed report](event-batching/report.md), [contract](event-batching/contract.md), [raw samples and MAD](event-batching/metrics.json). A potentially contended preliminary result was retained but excluded; the final result uses the clean complete rerun.

### Full CogniaDB account-sync fixture

The separate co-located Jest experiment runs the current CogniaDB schema, captured writes and real cryptography on fake-indexeddb, draining 2,048 rows. Its original ten-before/ten-after comparison **failed** the acceptance rule: median 29,839.74 → 30,990.40 ms (3.86% slower; MAD 337.40 / 216.11 ms). All samples are retained. It is not reported as a performance win.

A subsequent diagnostic alternated the original and candidate in one process: three pairs were 34,131.51 → 34,159.44 ms, 33,877.65 → 34,003.83 ms and 33,226.95 → 33,259.47 ms. Both variants had shifted upward; their paired differences were only 0.08–0.37%. This supports a time-dependent confounder in the grouped comparison but does not replace the pre-registered ten-sample experiment or prove a CogniaDB latency gain.

The deterministic resource result is consistent: 9,216 → 3,840 outbox rows materialized (**58.33% fewer**), maximum selection 2,048 → 512, unchanged 2,048 ops / 1,317,603 wire bytes and decrypted digest. Counts refer to returned arrays, not all cursor entries inspected in the oversized-prefix branch.

Decision: retain the bounded query on the separately pre-registered **native browser** evidence and deterministic read bound; make no full-CogniaDB/fake-indexeddb throughput improvement claim. The browser experiment was registered before the grouped after-result was known. Its minimal schema and title-update fixture are a different workload, not a substitute measurement of the full application. Evidence: [grouped metrics](account-sync/metrics.json), [paired diagnostic](account-sync/diagnostic-metrics.json), [contract and diagnostic amendments](account-sync/contract.md). Native browser and fake-indexeddb durations are not pooled.

## Follow-up: conversation catch-up and attachment persistence

The continuation began on 2026-10-07 and completed validation on 2026-10-08. Both experiments froze their original production modules and measured a baseline before editing; their decisive comparisons use ten alternating samples per variant after warmup on native Chromium IndexedDB. The acceptance rule remains at least 10% improvement and a median delta greater than twice the larger MAD. Timing runs were serialized to avoid competition between these experiments.

| Local user path                                                                                                | Baseline median / MAD | Result median / MAD | Decision                           |
| -------------------------------------------------------------------------------------------------------------- | --------------------: | ------------------: | ---------------------------------- |
| Shared conversation catch-up: 1,024 messages, 4 KiB each; full CogniaDB, encrypted storage and account capture |     582.50 / 10.75 ms |    227.40 / 3.00 ms | **60.96% faster**, 355.10 ms saved |
| Complete attachment upload: 10 MiB, 320 chunks                                                                 |   2,202.70 / 49.15 ms | 1,729.90 / 89.55 ms | **21.46% faster**, 472.80 ms saved |
| Complete attachment upload: 1 MiB, 32 chunks                                                                   |       52.25 / 3.70 ms |     41.25 / 1.30 ms | **21.05% faster**, 11.00 ms saved  |

Shared-chat projection batches up to 128 distinct message IDs within the existing transaction. A repeated ID flushes the preceding writes: intermediate changes are required for account capture to propagate metadata removal after redaction. Installed creating/updating hooks retain sequential writes and their intermediate database view. All 1,024 events, message writes, outbox entries and 4,491,755 response bytes remain; database mutation calls decrease from 1,024 to 8. Single-message, repeated-correction/redaction and hook-enabled workloads pass their guards without a speedup claim. Native encrypted rollback testing rejects the second batch and verifies that the first batch, event cache, session, outbox and field clocks do not survive.

The first implementation awaited an empty async enqueue for each buffered row. The rollback and pagination tests caught premature Dexie transaction completion; that implementation was corrected before timing the candidate. Buffering now runs synchronously and only actual persistence returns a promise to await. No required write or await of database work was removed.

Attachment append now performs its owned-row read, validation, byte assembly and full-row put in one transaction. This avoids Dexie's second accumulated-body read during update. For 10 MiB, measured get/getMany row selections fall from 642 to 322; all 320 chunks, 14,009,809 request bytes and 321 writes remain. Concurrent adjacent chunks, database-reopen resume and overlapping abort are checked. Already-completed dedup stays 8.60 ms; the resume workload's lower median does **not** exceed its noise threshold and is not claimed as an improvement. Accumulated-body copying/writing remains quadratic.

These are local client/host or response-to-durable-projection measurements. Shared-chat uses the full schema, real encryption and capture, deterministic paged responses and a counted search-scheduling stub. Attachment uses actual client/host functions and an exact minimal native attachment schema, joined by local JSON/base64 RPC. Real sockets, service authorization, RTT, physical devices, UI rendering and background search rebuilding remain outside the measured outcome. Identical payload bytes mean no bandwidth-reduction claim.

Detailed evidence and reproducible harnesses: [shared-chat report](shared-chat-batching/report.md), [attachment report](attachment-append/report.md). Follow-up checks and remaining global-gate failures are recorded in [follow-up verification](followup-verification.md).

## Interpretation limits

- Local preparation/encoding time is one component of transfer latency. These experiments do not establish physical-device, WAN, relay, packet-loss, battery, UI-render, or server-load performance.
- Identical payload sizes mean identical bandwidth demand for the fixture; faster serialization must not be described as bandwidth reduction.
- A production-disabled feature benefits only builds where it is enabled.
- Tests establish the exercised cases, not a guarantee that every existing feature on every device is unaffected.
