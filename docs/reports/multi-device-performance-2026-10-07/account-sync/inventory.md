## Evidence-backed candidate list

1. **Measured experiment here:** `pusher.ts` materialized the entire remaining outbox before slicing 512 each iteration. A drain of 8192 valid rows in 256-op batches reads 135168 row objects at the selection stage. The equivalent bounded selection reads 16128, preserving the current 512 lookahead and crypto/wire logic.
2. **Not changed or measured:** `shared-chat-sync.ts:projectEvents` reads every existing message for the session whenever any message event arrives. Incremental single-message traffic in a long conversation incurs O(history) reads per pull. Avoiding this requires care for legacy message ids, correction/redaction lookup, event ordering, and atomic cursor recovery; test matrix already in `shared-chat-sync.test.ts`.
3. **Not changed or measured:** shared session discovery uses `sessions.filter` scans; history is drained into one large events array before atomic projection. Indexed lookup or incremental projection requires schema/recovery design and was deliberately not folded into the pusher change.
4. **Not changed or measured:** `pullCollabWorkspaces` serially requests all workspace rosters, while `pullCollabActivity` serially fetches plans then runs. Bounded network prefetch could reduce RTT, but membership/identity ordering and partial failure semantics must remain. Existing `sync.test.ts`, `refresh.test.ts`, `feed.test.ts`, `refresh-scheduler.test.ts` are starting points.
5. **Not changed or measured:** WebDAV sends two identical encrypted bodies for historical snapshot and latest. Server-side COPY with fallback could cut upload bytes, but transport method support, permissions, atomic latest semantics, and provider compatibility need real WebDAV fixtures. Existing `lib/webdav/client.test.ts`, `lib/data/destinations/webdav.test.ts`, and `sync-now.test.ts` cover present contracts.
6. **Not changed or measured:** account applier prepares crypto ops sequentially and reads full parked inbox every round. Broad crypto parallelization or transaction read concurrency is unsafe without profiling: encrypted-content middleware explicitly requires serialized Dexie.waitFor reads. Preserve authentication, origin verification and transaction atomicity.

## Governing decisions consulted

- ADR-0215: one person, one encrypted sync space, writable replicas; phase-3a data engine exists behind feature flag. It preserves companion pairing and collaboration separately.
- `docs/content/docs/en/subsystems/account-sync-data.mdx`: transactional capture, outbox/inbox, seed/join and encrypted application lifecycle.
- `docs/plans/2026-09-30-collaboration-multi-device-gap-analysis.md`: gap inventory updated 2026-10-01; its initial gap statements are historical. P0 tombstones/quota and P1 live feed/field merge/notifications later marked implemented.
- ADR-0206 was read directly: accepted and implemented 2026-09-30, invalidations only, per-leg 250ms coalescing, one trailing refresh, 60s fallback polling, authorization-first mirror refresh. ADR-0158 describes opaque Yjs snapshots with maintainer-driven compaction; its durable replay/automatic compaction amendment is still marked Proposed. Existing code references ADR-0149 for collaboration authority. No governing model changes are required for a bounded outbox read.

No existing account-sync benchmark command was found in package scripts or relevant tests. The experiment reuses the existing real cryptography/fake-indexeddb `test-support.ts` and co-located pusher tests rather than inventing a second sync implementation.
