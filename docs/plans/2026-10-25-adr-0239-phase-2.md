## 1. 总体做法

**第二期只收紧，不放宽。** 引擎对 GitHub 写入给出 `allow` 时，现有的门（sidecar 卡片、能力授予、集成审批队列、Bot 的 `bot_approval` 中断）照常生效；引擎只在以下情况改变结果：执行模式下无人值守写入的仓库没有任何授予（改为停泊）、仓库被人拒绝过（屏障，拒绝）、交互聊天里发往非发起线程的仓库（卡片写明仓库并提供“本次请求允许”）。

**目标模型扩展一类，模式按类别分开。**

```
目标种类（OutboundTargetKind）  新增 repository（2a）、site（2b）
  repository  channel "github"   recipient "github:<host>/<owner>/<repo>"（全小写，host 缺省 github.com）
              thread（可选）     "github-thread:<host>/<owner>/<repo>#<n>"，只用于发起线程匹配，不持久化
  site        channel "browser"  recipient "site:<origin>"（scheme://host[:port]）
类别（OutboundCategory）        messaging（第一期全部）| github | browser，由目标种类推出
模式                            messaging 仍读 agentPermissions.outboundAuthorization；
                                github / browser 读 agentPermissions.outboundAuthorizationByCategory.<类别>，缺省 shadow
```

一次计划只要有一个目标所在类别为 `enforce` 就按执行处理该目标，其余目标按各自类别的模式记录（receipt 的 `plan.enforced` 按目标所属类别计算；一次调用跨类别的情况只出现在 `gh api` 之类的命令里，按最严处理）。

**咽喉点。** 2a 新增两处，都在宿主侧：

```
lib/integrations/action-runner.ts  executeIntegrationAction：broker 写动作入队前规划
lib/integrations/action-runner.ts  authenticatedIntegrationRequest：非 GET 的原始请求规划（Issue Loop 的 POST /pulls 走这里）
lib/policy/action-review/plan-tool-call.ts  既有工具咽喉点：GitHub 集成工具与 Bash 里的 gh 写命令
lib/ai/agent/team/delivery/github-delivery-adapter.ts  Squad 堆叠发布前规划
```

聊天工具调用到 broker 时，broker 经 `authorized-tool-calls.ts`（第一期 WP8 的内存记录）认出这是已规划、已放行的调用，不重复询问；与 connector 投递的处理一致。

每个工作包单独提交，带 co-located 测试。顺序：WP0 → WP1 → WP2 → WP3、WP4 → WP5 → WP6、WP7 → WP8 → WP9（2a 收尾）→ WP10（spike）→ WP11 → WP12 → WP13（2b 收尾）。

#### WP3 broker 与宿主 fetch 边界的咽喉点

- `lib/policy/action-review/plan-integration.ts`（新增，结构照 `plan-delivery.ts`）：输入为动作（或原始请求的方法与路径）、账号、调用方授权（`tool-call` / `workflow` / `plugin` / `bot` / `issue-loop` / `human`）；输出 `proceed`（维持现有流程）/ `park` / `deny`，附 receipt。
- `executeIntegrationAction`：写动作入队前规划。`park` 时无论现有状态如何（含能力授予自动批准、Bot 绑定直接 `queued`），一律置为 `awaiting_approval`，并通过与无人值守工具审批相同的推送（`createUnattendedPark` 的通知通道）把批准 / 拒绝回写到该 job；`deny`（屏障）直接以 `outbound_fenced` 失败。job 记录 `authorizedBy`。
- `authenticatedIntegrationRequest`：非 GET 请求按路径 `/repos/<owner>/<repo>/…` 取仓库目标后规划；取不到仓库的非 GET 为 `unknown`。Issue Loop 的 `POST /pulls` 由此覆盖。

### 2b 浏览器提交

#### WP10 提交信号 spike（只产出结论，不写生产代码）

- 在四种引擎上实测，产出 `docs/research/2026-10-xx-browser-submit-signal.md`，逐引擎给出“可靠 / 部分 / 无”与所用机制：
  - **动作前判定**：目标元素是提交控件（`input[type=submit|image]`、表单内无 type 或 type=submit 的 `button`、无表单的按钮）、表单输入框内按 Enter（区分可信与合成事件：合成 `KeyboardEvent` 不触发隐式提交）、`contenteditable` 的发送组合键；
  - **请求挂起**（Playwright 路径）：动作窗口内由页面发起的非 GET 请求与表单提交经 `page.route` 挂起，规划后放行或中止；验证 SPA（fetch / XHR）、表单 GET、`navigator.sendBeacon`、WebSocket、跨源与同源；
  - **内嵌 webview**：注入脚本拦截 `submit` 事件、`HTMLFormElement.prototype.submit/requestSubmit`、`fetch` / `XMLHttpRequest`，能否在页面脚本之前装上、能否被页面绕过；
  - **扩展引擎**：在 cognia-browser-extension 仓库确认 `chrome.webRequest` / `declarativeNetRequest` 能否挂起请求。
- 退出条件：每个引擎有结论；挂起机制给出误判（把非提交的请求挂起）与漏判样例；结论回写到本计划 WP11–WP12 后才开工。
- **已完成**（2026-10-25）：[`docs/research/2026-10-25-browser-submit-signal.md`](../research/2026-10-25-browser-submit-signal.md)，脚本与原始结果在同名目录。Chromium 153 与 Playwright WebKit 26.6 上 24 个场景、5 个绕过页，扩展引擎另测 `chrome.debugger` 与 `webRequestBlocking`。
  - 本地 Chromium、远程 Chromium **可靠**：`context.route` 挂起了每一个非 GET（表单 POST、可信 Enter、合成点击、`select` 自动提交、延时 1.8 s 的 `form.submit`、fetch、XHR、beacon、`<a ping>`、worker、跨源 iframe），`routeWebSocket` 挂起 WebSocket 帧。拒绝导航用 `fulfill 204`（页面保持原样；`abort` 会让 Chromium 落到 `chrome-error://`），拒绝 fetch 类用 `abort`。
  - 内嵌 webview **部分**：注入脚本（主框架、页面脚本之前）看得见并能延后主文档的 submit、`form.submit`、fetch、XHR、beacon、WebSocket 与 Navigation API 导航，但看不见 worker、`<a ping>`、图片 GET、跨源 iframe，同源子框架取来的原生函数可绕过。
  - 扩展引擎在现有权限下 **部分**（同注入）；`webRequestBlocking` 在 MV3 未按策略安装时无效，`declarativeNetRequest` 不能挂起；只有 `chrome.debugger` + `Fetch.enable`（加 auto-attach）对 HTTP 可靠，但看不见 WebSocket 帧，且与 ADR-0228 §6 冲突。
  - 动作前判定在所有引擎上只作提示：合成 Enter 不提交（误判），页面脚本发出的发送全部漏判。
  - 误判样例：页内链接的统计 beacon、自动保存、后台遥测；漏判样例：GET 携带数据（所有引擎，固有）、WebSocket 帧（debugger）、worker / ping / 框架（注入）。

#### WP11 站点目标与名单

- `siteTarget` 以请求目标（表单 action 或请求 URL）的 origin 为收件人；跨源 iframe 里的提交以 iframe 表单的 action origin 为目标，不取顶层页面（WP10 s16）；“可能提交”分支以动作时的页面 origin 为目标；发起线程概念不适用（浏览器没有“请求所在的站点”），交互聊天靠“本次请求允许”。
- 名单：安全设置里一份全局站点名单（无人值守的定时任务、workflow 使用），Bot 安装名单支持 `site` 种类；编辑器加 `site` 种类（输入 URL 规范化为 origin）。
- **测试**：`siteTarget` 规范化（端口、IDN、`http`/`https` 区分）、名单校验、编辑器、设置组件。

#### WP12 浏览器咽喉点（按 WP10 结论实施）

- 可靠引擎（WP10：本地 Chromium、远程 Chromium）：挂起提交，以请求目标的 origin 规划；`allow` 放行，执行模式下 `ask` / `park` / `deny` 分别询问、停泊、中止并告诉 agent 原因。
  - 远程路径在已有的 `authorizeRoute`（`services/workspace-runtime/src/browser-service.mjs`）里加挂起分支；本地路径（`launchLocalContext`）补上同一个 `context.route`；两条路径另加 `context.routeWebSocket`，共用一个挂起函数。
  - 挂起范围：动作开始到动作结束后 3 s 宽限期内、由该页面发出的非 GET、非 `OPTIONS` 请求与 WebSocket 帧算作该动作的提交，同一窗口同一 origin 只规划一次；窗口外的请求放行，影子报告记作“后台”。GET 携带数据不挂起（固有漏判，写进 ADR 已知缺口与界面说明）。
  - 拒绝：资源类型 document 用 `route.fulfill({ status: 204 })`，其余用 `route.abort()`；WebSocket 帧拒绝即不转发并关闭该连接。
  - 补一个 service worker 夹具，确认被 service worker 接管的请求是否经过 route，再决定 agent 控制的 context 是否 `serviceWorkers: "block"`。
- 无可靠信号的引擎（WP10：内嵌 webview、扩展引擎）：执行模式下对未授权站点的 `browser_click`、`browser_type`、`browser_press_key`、`browser_fill_form`、`browser_select`、`browser_drag` 按“可能提交”处理（目标取当前页面 origin），按第一期规则询问或停泊。注入式拦截不作为可靠信号，不在本工作包范围；扩展不加 `debugger` 权限（与 ADR-0228 §6 冲突），开工前向用户确认一次。
- 覆盖：插件 `cognia-browser-tools` 的工具、外部桥接的同名工具（`lib/external-bridge/handlers/browser.ts`）、workflow 浏览器节点（`act`、`fillForm`、`replayFlow`）。
- 宿主决策需要页面 origin：由引擎在动作请求里附带当前页面 URL（或挂起时的请求 URL），不信任 agent 输入。
- **测试**：每个引擎的提交挂起或“可能提交”分支、外部桥接、workflow 节点、`shadow-mode.test.ts` 扩展到浏览器类别。

## 5. 风险

| 风险                                                                                                           | 应对                                                                                                  |
| -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `gh` 解析漏掉写子命令或别名（`gh alias`、`gh extension`）                                                      | 未识别的 `gh` 子命令按 `ask`（不再整条 `allow`）；`gh alias set` 与扩展命令一律 `ask`                 |
| 仓库从 cwd remote 推断错误（fork、多 remote）                                                                  | 优先显式 `-R`；取 `origin`，多个 remote 且无 `-R` 时为 `unknown`                                      |
| 停泊覆盖能力授予的自动批准，可能让已在跑的 workflow 卡住                                                       | 能力授予本身算 `policy` 授予（WP5），只有未授予的写入会停泊；影子报告在开启前列出受影响的 workflow    |
| broker 与工具咽喉点重复询问                                                                                    | broker 识别 `tool-call` 授权（`authorized-tool-calls.ts`）；测试固定“只问一次”                        |
| 浏览器信号在某些引擎上不可靠                                                                                   | WP10 已出结论：内嵌 webview 与扩展按“可能提交”处理，在 ADR 与界面标明；GET 携带数据在所有引擎上不挂起 |
| 扩展引擎源码在另一个仓库                                                                                       | WP10 在 cognia-browser-extension 实测；需要改扩展时按其仓库流程另行提交，本仓库只做宿主侧             |
| GitHub MCP 未纳入                                                                                              | 维持普通阶梯，在 ADR 实施说明列为已知缺口                                                             |
| 范围之外的 GitHub 写入：数据备份写到用户自己的私有仓库（`lib/data/destinations/github.ts`）、CI 的 PR 评论脚本 | 不是发给第三方，不纳入；在 ADR 第二期决定中写明                                                       |
| 共享工作区里他人改同一批文件（`command-safety.ts`、设置类型、i18n 聚合文件）                                   | 每个工作包单独提交，只提交自己的路径，共享文件按 hunk 暂存                                            |
