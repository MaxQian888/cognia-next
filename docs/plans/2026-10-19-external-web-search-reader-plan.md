## 1. Repair policy and result correctness, then decouple readers, then add providers

Keep the existing canonical search executor and the existing `web_search` / `web_fetch` host tools. First repair lifecycle, result loss, configuration precedence, policy filtering, caching, and cancellation. Then add an independent Reader policy around the existing extraction paths. Add new providers only after both contracts have acceptance evidence.

Cognia already has ten registered search adapters and several page-reading paths. Registration currently overstates effective availability: some endpoints or default models have retired, some supported output is dropped before reaching the agent, and hosts apply different defaults and reader dependencies. More adapters alone would preserve these defects.

The proposed first addition wave is **DeepSeek Search + Fetch, TinyFish Search + Fetch, and SearXNG Search**. It is a recommendation for review, not an approved provider list. Existing Tavily Extract and Exa Contents are Reader wiring work, not new provider integrations. Parallel remains a separately labeled MCP option until a REST integration is approved.

Provider quotas and marketing descriptions are evidence about commercial access, not acceptance evidence about relevance, browser compatibility, extraction quality, or zero cost. No provider is activated automatically, and configuring Search does not activate that vendor's Reader.

## 4. Search contracts preserve explicit intent and expose only effective capabilities

### Provider identity, engine, and search type are separate values

Extend the existing provider descriptor with integration kind (`api`, `serp`, `self-hosted`, `grounding`), lifecycle (`active`, `legacy`, `retired`), operation support, engine/type support, and auth requirements. These are metadata additions, not separate registries.

- Keep existing provider IDs stable. An engine belongs to a provider; a search type such as `news` belongs to a query. Model IDs are separate provider options only for generating search.
- An omitted engine retains that provider's current default. Expose only tested engine/type combinations. SearchAPI/SerpAPI advanced options do not qualify every engine's response shape automatically.
- An explicit unsupported engine/type fails validation before network I/O. In automatic mode, fallback can select another eligible provider supporting the same request semantics; it cannot silently downgrade to general search or a different explicitly requested engine.
- Preserve legacy `provider` calls as a preferred-provider request with the configured fallback behavior. Add an explicit optional `allowFallback` control for callers needing a strict pin; `false` never switches provider. Correct the current misleading “force” description.
- Keep common query options in the existing `SearchOptions`. Add engine and operation-control fields only where they are validated and carried end to end, including CLI, cache, test connection, schema, and SDK/tool projection.
- Tool callers may narrow mandatory domain/safe-search policy, not relax a host-imposed constraint. Provider `defaultOptions` cannot override a user blocklist. The proposed mapping treats host `strict` safe search as mandatory and `moderate` as an advisory preference unless explicitly required by a caller. An adapter unable to enforce a mandatory level is ineligible before any request; fallback and cache eligibility use the same requirement. Host-side domain filtering cannot substitute for safe-search enforcement. Disclosing degradation is allowed only for advisory controls. This strengthens legacy strict-mode behavior and must be included in migration messaging and tests.
- Ordinary provider fallback does not silently cross into generating search. A generating provider may be explicitly selected; automatic use requires a separate explicit opt-in and model-budget accounting through the existing generation seam.

For Search settings, add optional `engine` and descriptor-approved `baseUrl` fields to `SearchProviderSettings`; `baseUrl` is initially accepted only for SearXNG. Parse it as an absolute HTTP(S) URL without embedded credentials, query, or fragment; preserve a validated deployment path prefix and append the adapter-owned `/search` path. Public endpoints require HTTPS. Plain HTTP or private/local endpoints require an explicit endpoint grant on a host that can enforce it. A redirect cannot widen the grant or move credentials to another origin. Engine values must belong to the configured adapter/instance; arbitrary endpoint substitution for existing cloud vendors is excluded. CLI strict schemas, profile transfer, and connection tests use the same validation contract.

Search output keeps `provider`, `query`, `answer`, and `results`. Add optional bounded `images`, effective engine/type, applied/degraded-control diagnostics, and truncation metadata. Preserve published dates and URLs; a rank-derived score must not be presented as factual confidence. For compatibility, existing snippet output remains bounded; a requested excerpt mode uses an explicit per-result cap and never duplicates the same content in multiple fields.

Apply hard include/exclude/block constraints and source-verification filtering before returning any result, including cache hits and images. If filtering removes any grounding result, clear synthesized `answer` conservatively. Recomputing an answer is a separate explicit model call with its own budget, never an automatic fix that silently charges the user.

### Connection testing proves one operation against one effective configuration

Replace the current “nonempty Key” precondition with descriptor validation. A test uses the configured endpoint, engine, type, and auth requirements, with a bounded safe query/page and visible possible charge. No connection test runs automatically on load, save, or migration. Retired providers cannot be tested; endpoint-only SearXNG can be tested without a fake Key. Search and Reader tests have separate results and timestamps. A last-successful test is historical evidence, not a durable online guarantee.

## 5. Reader routing preserves HTTP semantics and restricts external delegation

### Settings select readers independently without copying secrets

Add a versioned optional `webReader` settings object, leaving `webTools` as the existing capability/policy switch. An explicit direct-only profile uses `defaultReader: direct`, `externalFallback: off`, and disabled platform/cloud readers; it does not remove current target or required-distillation policy. An absent object means upgrade compatibility, never a rollback switch. The proposed fields are:

| Field                       | Proposed meaning / default                                                                                                                                           |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`                   | `1`; unknown future versions stay stored but are not activated                                                                                                       |
| `defaultReader`             | `auto` or a configured reader ID; new installs use direct-first auto                                                                                                 |
| `readers`                   | Per-reader enabled flag, priority, supported options, and optional credential reference; direct/platform/Jina/Tavily/Exa are existing-provider readers               |
| `externalFallback`          | `off` or `configured`; new installs use `off`; upgrading an existing settings row preserves its prior native Jina/platform eligibility; no usage history is inferred |
| `distillation`              | `off`, `best-effort`, or `required`; legacy `alwaysDistill: true` is proposed to normalize to `required`, subject to Q2                                              |
| `timeoutMs` / `maxAttempts` | Bounded validated operation budget; proposed defaults are specified in section 7                                                                                     |

A strictly pinned direct reader skips platform/cloud readers. Auto routing honors each reader's enabled flag; a disabled platform reader is never tried as a hidden pre-stage. New-install defaults keep remote platform recipients off until selected.

Search keys remain owned by their existing credential/config boundary. A Reader may reference a specific configured vendor credential after the user enables it, without duplicating the key into another record. Search enablement does not imply Reader enablement, and Reader enablement does not require enabling Search. Do not silently borrow an active model provider's key, subscription token, or an unrelated session's credentials.

Extend `web_fetch` additively with an optional `reader` selector and `allowFallback`. With neither present, apply the configured Reader policy. A strictly pinned reader either serves the request or returns a structured failure; it does not silently use another reader.

### Raw HTTP is a direct operation, not a cloud extraction request

| Request class                                                                 | Allowed route                                                                                         | Forbidden behavior                                                                                                                                    |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `format: raw`, non-GET, request body, or caller-supplied target headers       | Existing direct HTTP path, with policy and cancellation enforcement                                   | Sending body/headers/cookies to a cloud Reader; substituting extracted Markdown for a raw response; replaying a non-idempotent method during fallback |
| Public bodyless GET, `auto` / `text`, no target headers                       | Configured permitted readers; direct/platform first in auto, then explicitly enabled external readers | Activating a cloud service just because it has a Search Key                                                                                           |
| Private/loopback/link-local target                                            | Direct path only, and only when explicitly permitted on an enforcing host                             | Jina/FxTwitter/cloud Reader delegation, even if `allowPrivateHosts` is enabled                                                                        |
| HTTP authentication challenge, login/paywall requirement, or credentialed URL | Direct failure / actionable unsupported result                                                        | Copying a browser login, using a hidden session, or attempting a cloud-reader access-control bypass                                                   |

Required distillation conflicts with direct-only requests (`raw`, non-GET, body, or caller target headers): reject the combination before I/O using `invalid-arguments` plus a conflicting-mode reason. A model-supplied argument cannot turn required policy off. The user can deliberately change that policy to make raw HTTP available. For ordinary readable GETs in required mode, normalize HTML, plain text, and JSON into readable text and distill before returning anything; unsupported binaries fail without returning raw content. This is an intentional stricter contract under Q2, not a silent rewrite of raw responses.

URL validation rejects embedded username/password, unsupported schemes, and malformed targets. Private-target classification includes DNS/redirect handling at the host transport; a string-only hostname check is not accepted as proof of DNS-rebinding protection. Browser builds cannot inspect arbitrary DNS resolution: direct requests rely on browser enforcement and expose that limit; a user-configured cloud Reader may read public URLs under its own target restrictions.

`auto` first tries an applicable existing platform reader and direct/local parsing within the attempt/deadline budget. X reading currently uses FxTwitter, so “platform reader” must disclose that third-party recipient; it is not advertised as on-device-only. Known remote recipients remain separate policy capabilities. External fallback is eligible for network failure, insufficient extracted content, supported binary/PDF conversion, or a public anti-bot response; 404/410, policy refusal, cancellation, or login/paywall requirement are terminal. The classifier must distinguish an anti-bot page from an authentication challenge; ambiguous failures stop with diagnostics.

Selecting a cloud Reader directly does not first require a successful browser fetch. This is necessary for a CORS-limited browser to use a CORS-enabled configured Reader. If the vendor endpoint itself is not browser-accessible, report that host restriction or use an already selected paired host; never create a hidden backend or move execution automatically.

### Result semantics identify which path actually succeeded

- Preserve the existing `PluginWebFetchResult` union and its guards. Direct HTTP continues to report the actual HTTP `status`, including 404 outcomes.
- Reader-produced content reports the successful retrieval service status in the legacy `status` field and adds `statusSource: reader-service`, reader ID, source URL, and `originStatus` only when actually known. Never invent an origin 200. If direct returned 403 and an eligible Reader succeeds, preserve 403 as origin metadata without labeling the resulting content retrieval failed.
- Add optional `distilled`, extraction method, warnings/reason, effective reader, truncation, and read-window metadata. Keep `text` / `body` consumable and the single `untrustedNotice`; external content and summaries remain untrusted.
- Required distillation never returns raw text if the model is absent, fails, is cancelled, or exceeds its budget. Best-effort `prompt` extraction may return text with `distilled: false` and a visible degradation reason. Do not claim a utility summary eliminates prompt injection.
- Read-window offsets and the legacy `maxBytes` field remain **character** counts for compatibility. Document that unit; a separate transport byte limit protects memory. A future byte-based field would need a distinct name.
- Provider envelope success does not guarantee per-URL success. TinyFish's `errors[]`, Exa/Tavily partial results, missing content, and unsupported binary types map to a useful failure rather than empty successful content. Single-page reads issue one URL, not a batch.

Public failures retain existing `PluginHostToolErrorCode` values. Internally classify unsupported capability, auth, quota, timeout, cancellation, blocked target, inaccessible host, and extraction failure; expose an optional bounded `reason` plus a localized user-facing explanation. Any new public enum value requires a separately versioned SDK contract change rather than silently extending a fixed vocabulary.

## 6. Caches, credentials, and policy remain scoped to the executing runtime

Evaluate the current web capability, caller permission, URL/domain policy, reader/provider eligibility, and account/runtime binding **before** reading a cache. Recheck active scope and cancellation before publishing a result or writing a cache entry. Cache hits must pass current output filtering; they never resurrect blocked grounding or removed readers.

| Boundary                          | Required behavior                                                                                                                                                                                                      |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fetch identity                    | Runtime/account scope, URL, effective reader/config revision, format, prompt, and extraction policy revision identify a bounded pre-window document representation; offset and requested window cap do not participate |
| Sensitive fetch                   | Bypass cache for private targets and caller-supplied target headers; no tokens/headers in cache keys or diagnostics                                                                                                    |
| Search identity                   | Include engine/type, effective defaults, eligible provider revisions, policy, and runtime/account credential revision; use opaque revisions, not raw keys                                                              |
| Account/profile/credential change | Invalidate the owning scope; an in-flight request cannot write into the new scope                                                                                                                                      |
| Content retention                 | In-memory only: retain 5-minute TTL / 100-entry bound; additionally cache at most 256 Ki characters per representation and 4 Mi characters in aggregate, evicting by LRU; no disk Reader cache                         |
| Legacy cache                      | Drop entries on policy-contract upgrade; no stale-while-revalidate across security changes                                                                                                                             |
| Private-reader configuration      | A SearXNG endpoint grant is limited to its validated search endpoint; it does not grant `web_fetch` access to that network                                                                                             |
| PII                               | Preserve query redaction and final gates; validate URL, origin headers/body, provider-bound extraction text, and utility prompts at their existing owning boundaries before external send                              |

The fetch cache stores the normalized representation after any required/best-effort distillation and before window slicing. Reapply current authority/output policy on every hit, then compute the requested offset/cap window. This avoids a second network/model call and unstable re-summarization while the same cacheable representation remains resident. Oversized representations are returned with a cache-bypass diagnostic; stable paging without refetch is not guaranteed for them or after eviction. Cached text payload is bounded by the character budget above (approximately twice that count in bytes for UTF-16 strings, excluding object overhead); transport byte ceilings remain independent.

Reuse the existing settings secret-reveal gate, profile-transfer scrubber, CLI credential resolution, and session-scoped plugin runtime. The current settings writer stores Search keys inside settings; this proposal does **not** claim they are already in an OS vault. Do not introduce another secret-bearing settings copy. First-wave vendor readers reference existing vendor credentials; adding a protected credential reference for a new secret kind uses the existing credential owners and explicit tests. A global credential-storage migration is excluded.

CLI secrets stay in its credential file/environment rather than shareable config; preserve the existing owner-only POSIX permission behavior and document its Windows limitation. Search/Reader keys, authorization headers, target queries, page text, and private endpoints do not enter logs or portable profile exports. Import/export/reset and host sync must explicitly recognize `webReader`; the existing recursive key-name scrub alone is insufficient proof for nested `headers` values. Portable profiles exclude credential references, endpoint grants, target headers, and self-hosted endpoint addresses by explicit field policy. Importing a portable profile requires the receiving host to configure its endpoint/credential again; account-scoped encrypted backup remains a separate existing feature, not an implicit source of network grants.

No new credentialed custom headers are proposed for SearXNG in the first wave: support a public or explicitly granted unauthenticated local instance. Authenticated reverse proxies need their own credential contract before they can be supported safely.

## 7. Failure, cancellation, and resource limits are end-to-end contracts

One logical operation has one settings snapshot, runtime identity, cancellation signal, deadline, and terminal outcome. Provider retries and fallback consume the same overall budget. A restart does not automatically replay an interrupted fetch or bill a provider again; a subsequent caller request is a new operation.

| Event                                                     | Required transition / recovery                                                                                                                                                                      |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Success                                                   | Validate schema → policy-filter → normalize → optional bounded distillation → cache if permitted → publish once                                                                                     |
| Invalid config, retired provider, unsupported engine/type | Fail before network; show specific corrective setting; no provider health penalty                                                                                                                   |
| Auth / quota failure                                      | Do not rotate/retry the same permanently rejected credential; fallback only to already permitted candidates when enabled; never auto-recharge or change subscription                                |
| 429 / transient network / 5xx                             | Bounded retry using existing backoff and Retry-After within deadline; then eligible fallback; no multiplied retry loops                                                                             |
| User cancellation / runtime teardown                      | Abort adapter fetch and extractor; cancel backoff; prohibit new attempts, cache writes, and late visible output                                                                                     |
| Host lacks physical transport cancellation                | Return logical cancellation promptly and suppress late effects; enforce a native timeout and disclose that already-sent vendor work cannot be recalled; do not claim provider billing was cancelled |
| Source/reader disabled during flight                      | Reject output at the final active-scope/policy check; do not retain it in the active cache                                                                                                          |
| Crash/reconnect                                           | In-memory work/cache is disposable; surface interrupted state; no durable job queue is introduced                                                                                                   |

Proposed deterministic budgets are **30 seconds total Search**, **60 seconds total reading**, **20 seconds maximum per reader attempt**, and **3 adapter attempts total per operation**, including retries/fallback. Search attempts are bounded by their remaining overall budget. Existing user retry settings remain upper bounds and cannot multiply the operation limit. Platform readers' internal subrequests share their attempt deadline. These are design limits, not measured latency promises; reviewers can change them as explicit policy values.

Keep result caps at current defaults: 64 Ki characters raw, 40 Ki characters extracted, 32 Ki characters into the utility extractor, and 1,024 utility output tokens. Add a proposed **8 MiB decoded response byte ceiling** before parsing, enforced by each selected transport, not merely by output truncation. Oversized content returns a typed reason and recovery guidance; no full-body buffering beyond the ceiling. Per-session concurrency is proposed at 2 Search / 2 Reader operations with cancellation-aware bounded admission of 8 pending operations; full admission returns a retryable rate-limit result. These bounds must live in one shared policy definition and have fake-clock tests.

The existing desktop proxy already exposes `proxy_http_cancel` through [`proxy-fetch.ts`](../../lib/network/proxy-fetch.ts); prefer wiring it over a second cancellation IPC. Check actual native response buffering and Capacitor cancellation/byte limits during implementation. Any missing primitive is a dependent host work item, not an excuse to label output truncation a network memory bound.

## 10. Migration is additive and does not change accounts or silently enable vendors

Use the existing settings row and normalization path; no new Dexie table/index or native schema bump is proposed. If implementation proves a structural schema change necessary, stop that work package and follow the repository's migration procedure before allocating a version.

1. Add lifecycle/capability interpretation without deleting old provider IDs, credentials, priorities, or defaults. Retired Bing is preserved as an inactive tombstone and excluded by runtime eligibility. Legacy Google retains explicit current-user selection with its end-date warning.
2. Add optional engine fields; absence preserves current provider defaults. Do not replace a user's Google Custom Search selection with a billed SERP provider. An invalid/retired default yields an actionable diagnostic and only uses existing permitted fallback settings.
3. Before merging `DEFAULTS`, inspect the persisted row itself. No existing row means a fresh install and the explicit new direct-first/cloud-off defaults. An existing row without its own `webReader` property means legacy compatibility: preserve existing platform eligibility and native-only Jina eligibility, visibly identify their recipients, and enable no Tavily/Exa or new vendors. Current code has no per-reader usage history, so migration preserves prior eligibility, not inferred historical use. An explicit valid object is authoritative. Materialize a normalized profile only on explicit save; ordinary reads remain pure. Factory reset uses new-install defaults; importing an older portable profile must not reactivate legacy remote readers or recreate endpoint grants.
4. On native-to-browser/CLI transfer, preserve the stored reader preference but recompute host eligibility. Do not infer permission to use a newly available cloud service from a source host's fallback behavior.
5. Migrate legacy `alwaysDistill` according to Q2, and map legacy `preferCognia` as in section 8. Keep original compatibility fields readable through the migration window. No silent account/model/key selection occurs.
6. Update section ownership, defaults/normalization, store setters, CLI strict schema and config projection, credentials, profile export/import/reset, and host sync together. Search/Reader secrets remain excluded from ordinary preference sync/export. Unknown future config is preserved but inactive; CLI import/export must report unsupported fields rather than erase them.
7. Flush old memory caches on contract activation and scope changes. Reader enable/disable and provider configuration changes take effect on the next request and the final check of in-flight operations.

Tool and result additions are optional fields in the existing tools. Publish the next compatible SDK minor version and packed examples when these fields ship; do not reuse a previous release number. Old plugins using `isPluginWebFetchSuccess` and `pluginWebFetchText` continue to work. Existing raw/direct response status semantics remain unchanged.

An old binary cannot reliably interpret new provider IDs or reader policy. Retain a pre-upgrade settings export and validate downgrade behavior on a copied profile before claiming rollback compatibility. Emergency containment uses the new build's disable controls; do not recommend downgrading to a build with the cache/policy defects or silently discarding unknown fields.
