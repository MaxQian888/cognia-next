## 1. Preserve the unified system and correct implementation ownership

Claude is already a runtime family in Cognia's unified execution system. The migration removes the historical `lib/claude` ownership inversion while preserving the existing contracts, context assembler, control ports, engines, tools, policy boundaries and host-specific execution semantics.

The recommendation is to account for the initially audited 175 source files and 181 tests: retain three source/test pairs relocated by concurrent work, then migrate the remaining 172 sources and 178 tests into existing owners, and retain old import paths temporarily as forwarding exports to the same implementation. Mixed files need explicit splits; moving a filename does not prove that its behavior is vendor-neutral.

No application-side runtime registry, Agent engine, prompt assembler, permission bus, tool catalog, protocol vocabulary or integration package is introduced. Claude Agent SDK remains in the sidecar's existing engine directory; external Claude Code remains an ACP integration. File migration and event-protocol migration are separate decisions.

### 1.1 Acceptance goals are dependency and behavior properties

| Goal                            | Baseline                                                                                     | Required result                                                                                                                                                          |
| ------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| G1 Explicit ownership           | 175 source files under a vendor-named application directory                                  | Every source has one primary destination or an already-relocated disposition, and an explicit split decision where necessary; section 10 records all 175 audited origins |
| G2 Correct dependency direction | Unified handle, CLI context assembler, MCP coordinator and usage modules import `lib/claude` | Migrated implementations do not import the old namespace; existing callers migrate in bounded cohorts                                                                    |
| G3 One authority                | Shared context, controls, registries and policy already exist                                | The same objects, singleton state, prompt precedence, capability checks and execution authorities remain reachable                                                       |
| G4 Host and runtime parity      | Legacy transport and SDK-shaped messages serve multiple runtimes                             | Claude SDK, AI SDK and representative external agents retain their supported behavior across the applicable desktop, CLI and paired/headless paths                       |
| G5 Auditable cutover            | Old paths occur in source, tests, build scripts and gate metadata                            | Consumers and path-sensitive checks move together; any remaining compatibility path has an identified consumer and owner                                                 |

### 1.2 Scope deliberately preserves stored and wire contracts

Included: source/test relocation, internal function extraction, application import updates, path-sensitive build/gate metadata, co-located behavioral tests, documentation and temporary forwarding exports.

Unchanged during P0–P3: `SendOptions` wire keys including `claudeAgentSdk`, runtime ids, command/event names, protocol JSON schemas, stored session ids and codecs, Dexie/SQLite versions, configuration formats, prompt wording, account selection, capability semantics and engine selection. P4 moves UI consumers without switching their event source. A protocol cutover, new schema or capability redesign needs a separate proposal and acceptance record.

The goal is correct ownership. Deleting the old directory is conditional on verified consumer retirement, not a reason to remove working compatibility.

### 2.1 Inventory method and limits

Initial inventory on 2026-10-20: **175 non-test `.ts` files, 181 `.test.ts` files and 43,677 source lines** under `lib/claude`. During documentation validation, concurrent work relocated three prompt source/test pairs. The reconciliation snapshot is **172 sources, 178 tests and 43,322 source lines**. Current source grouping: root 82; `agents` 33; `agents/subagents` 6; `permissions` 20; `hooks` 7; `instructions` 7; `subagent-importers` 12; `chat-middleware` 3; `builtin-mcp` 2. The source register retains all 175 audited origins, marking the three completed moves as P0 / retain, so the plan cannot move them again.

A literal import-specifier scan found **431 distinct non-test files outside the directory** referring to `@/lib/claude/…`: `lib` 205, components 119, CLI 67, hooks 30, stores 4, packages 4 and app 2 in the reconciliation snapshot. The scan covered `app`, `components`, `hooks`, `lib`, `stores`, `cli`, `packages`, `sidecar`, `mobile` and `web`, excluding generated/dependency directories. This is a source-reference count, not a runtime reachability proof; it includes type imports and possible story/fixture consumers. Scripts, relative imports, string aliases and gate metadata need the separate search in section 7.

Initial-snapshot highest external import counts by unique source file: `ipc` 83; `run-and-capture` 53; `parts-extensions` 39; `build-options` 36; `adapter` 33; instruction path helpers 30. These counts explain the staged cutover; they are not performance estimates.

Confirmed means inspected source or a measured inventory. Proposed means a destination or invariant in this document. Runtime equivalence, performance and platform acceptance remain unverified until implementation. This plan does not claim the architecture is fully migrated merely because a facade already exists.

## 3. Keep execution, engine, integration and domain ownership distinct

```text
Application surfaces: Chat / CLI / Connector / Scheduler / Workflow / Team
                              |
                existing context and execution resolution
                (shared options, frozen spec, capability gates)
                     /                         \
       existing sidecar client           existing ExternalAgentManager
                  |                                |
       sidecar host + engine registry        package adapter + host ports
            /                  \               ACP / Codex / Pi / ...
    Claude Agent SDK           AI SDK

Application-owned tools and plugin hooks keep their existing relay/MCP paths.
Contracts remain shared; hosts retain credentials, policy and persistence.
```

The diagram describes existing execution boundaries whose application files are being relocated. It does not require every caller to use one physical process or one method signature.

### 3.1 Dependency rules apply to responsibilities, not directory spelling

| Layer                              | May depend on                                                                                             | Must not gain                                                                                     |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `agent-contracts`                  | Existing portable types and tiny helpers                                                                  | Application aliases, React, Tauri, Dexie, stores or runtime SDK dependencies                      |
| Integration packages / runtime kit | Existing contracts, declared package dependencies and injected host ports                                 | Application data access, direct renderer transports or imports of other vendor clients            |
| Sidecar engines                    | Existing sidecar layers and their allowed SDK adapters                                                    | Application imports or direct imports between Claude and AI SDK engines                           |
| App contract leaves                | Portable contracts and neutral types, including the extracted application usage/capture types             | Imports of the capture runner, dispatcher or React hooks solely to obtain a type                  |
| App context/execution composition  | Existing domain contributors, provider routing, permission policy, plugin ports and transport             | Another runtime resolver, independent prompt stack, or a registry duplicating existing authority  |
| App tool dispatch composition      | Domain tool relays, existing plugin registry, permission/PII checks and narrow transport response methods | Imports of the whole options assembler to discover a tool, or tool execution in contract packages |
| UI projections                     | Message parts, source metadata, usage/context helpers and explicit persistence bridges                    | Runtime selection or treating a filtered event log as the source of live message content          |
| Compatibility exports              | New implementation exports only                                                                           | State, subscriptions, timers, default instances or imports back from migrated implementations     |

`execution` is an application subsystem, not a claim that all files below it are portable or pure. Existing `external/policy` remains external-protocol policy; the proposed `execution/permissions` group owns the existing shared application approval helpers. Neither replaces the sidecar's enforcement ladder.

### 3.2 New subdirectories organize existing implementations

Proposed groups below existing owners are `execution/{permissions,hooks,delegation}`, `mcp/{config-adapters,builtin}`, `agents/instructions`, `agent-migration/subagents` and `plugin/messaging/chat-middleware`. Each gathers multiple already implemented modules. They introduce no new service, runner, catalog, store or package. Other destinations are moved leaf files in existing directories.

Use `lib/agents` for application-authored/discovered agent definitions, `lib/agent/builtin-catalog` for the existing shipped identity catalog and its projections, `lib/agent/composition` for the current composition model, and `lib/workflow/editor` for workflow-specific prompt/tool definitions. The migration does not consolidate these distinct models by naming similarity.

### 3.3 Alternatives and consequences

| Option                                                                               | Decision              | Reason / cost                                                                                                     |
| ------------------------------------------------------------------------------------ | --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Rename `lib/claude` wholesale                                                        | Reject                | Retains mixed responsibilities and reversed dependencies under a different name                                   |
| New app-side runtime hierarchy or `agent-claude-sdk` package                         | Reject for this scope | Existing sidecar engine loading already supplies the execution boundary; a second hierarchy creates another owner |
| Force built-in engines through external `ProtocolAdapter`                            | Reject                | The external protocol/host-port contract and in-process engine contract have different responsibilities           |
| Move every vendor-named parser into integration packages                             | Reject                | ADR-0217 keeps migration readers application-owned; MCP file adapters are not runtime clients                     |
| Migrate ownership with forwarding exports, then consider event cutover independently | Recommend             | Preserves one implementation and supports bounded consumer migration; compatibility exports need explicit cleanup |

## 5. Keep security and compatibility at their existing boundaries

| Boundary                                                | Required preservation                                                                                           | Acceptance case                                                                                                                  |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Outbound prompt/steer/model calls                       | Existing required PII gates run before transport; runtime projection cannot bypass them                         | A rejected payload produces no outbound call on send, steer, capture, external and feature-model paths                           |
| Plugin tool responses and editor/file/knowledge content | Existing result-review interceptors, redaction and review decisions retain order                                | Modified/redacted output cannot be replaced by the original through another relay                                                |
| Permissions                                             | App approval logic, sidecar hard enforcement and external protocol mapping retain their own meanings            | Explicit deny survives both renderer and sidecar; unsupported protocol modes do not gain authority                               |
| Paired-host requests                                    | Controller ownership and server-issued remote context remain checked; stale/replayed approval remains rejected  | Reconnect or host switch cannot approve an old request against a new execution target                                            |
| Accounts and credentials                                | Per-session/character/default account precedence, config-dir isolation and credential affinity remain unchanged | Concurrent sessions bound to different accounts do not inherit each other's environment; logs/specs contain no raw credentials   |
| Workspace and filesystem                                | Trust, confinement, allowed roots, symlink/traversal checks and sandbox grants remain host-owned                | Unauthorized paths and untrusted project hooks remain refused                                                                    |
| Native Claude session APIs                              | Engine and capability checks remain mandatory                                                                   | AI-SDK-only host refuses Claude session management before work is attempted                                                      |
| Public SDK/plugins and stored sessions                  | No public export, wire, stored id or schema change in structural phases                                         | Existing callers compile; imported/native sessions resume on their recorded configuration                                        |
| Web/mobile/headless                                     | Static export stays valid; UI modules stay out of Node/CLI closures and Node SDK stays out of the renderer      | Standalone web does not spawn; paired mobile still uses host authority; CLI/headless do not import a React hook to obtain a type |

Keep `sidecar/src/policy/permission/resolver.ts` and the renderer ruleset as separate implementations unless a later proposal proves a safe shared boundary. Their defaults intentionally differ; [the parity test](../../lib/claude/permissions/ruleset.sidecar-parity.test.ts) requires explicit-deny equivalence, not identical unmatched-command behavior.

`claude_*` commands, `claude://message`, `SDKMessage`-shaped compatibility events and `SendOptions.claudeAgentSdk` do not disappear because application files move. Existing canonical/legacy coexistence remains unchanged. A newer application paired to an older Host must not begin sending renamed commands or fields through a source-only refactor.

No data backfill is needed: schema and serialized values stay unchanged. If implementation discovers that a proposed split requires a data or wire change, stop that work package and amend the plan before proceeding. Rollback restores imports/exports and code bodies, not user data or published history.
