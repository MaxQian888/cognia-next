## A. 系统性偏离（跨插件，主循环独立验证）

### A1 · `deactivate()` 从不接收 context ⇒ 14 个插件的清理代码全是死的 【已修复】

`PluginDefinition.deactivate?: (context?: PluginContext) => ...`，其文档明写 _"The runtime passes the same `PluginContext` used in `activate`"_。实际上每个调用点都是空参：

- `lib/plugin/core/manager.ts:3475` — `definition.deactivate()`
- `lib/plugin/core/loader.ts:605` — hybrid 包装器同样不转发

而第一方插件普遍写成 `deactivate: async (ctx?) => { if (ctx?.pluginId) unregisterCommandsByPlugin(ctx.pluginId) }`。`ctx` 恒为 `undefined` ⇒ **守卫恒假 ⇒ 清理恒不执行**。宿主侧也没有任何代码调用 slash registry 的 `unregisterCommandsByPlugin`（`lib/plugin/vscode-shim/runtime-handlers.ts:369` 调的是另一个 commands registry）。

实际后果：

- `clipboard-history` 的 `setInterval` **剪贴板轮询在插件禁用后继续运行** —— 用户撤销了 `clipboard:read`，读取循环还活着。这是隐私缺陷。
- `/cu`、`/ocr`、`/screenshot`、`/web-clone`、`/clipboard-history` 等斜杠命令在禁用后仍留在面板里，handler 闭包钉住陈旧 context。

各插件的测试都手工传 `ctx` 调用 `deactivate(ctx)`，钉住了一条**生产环境永不走的路径** —— 典型的断言剧场掩盖真实泄漏。

**修复**：`manager.ts` 传 `this.contexts.get(pluginId)`（`contexts.delete` 在其后执行，此处仍然有效）；loader hybrid 包装器转发 `ctx`。新增 `manager.test.ts` 断言 `deactivate` 收到 `objectContaining({ pluginId })`。

### A2 · ~~20 个 API 权限无法在清单里声明~~ 【❌ 本节结论已被推翻 — 见 C3 #17】

> **这段最初的分析是错的，保留仅作教训。** `ai:chat` 等属 `PluginAPIPermission`，本就不该出现在清单里；
> catalog 省略它们是**正确的**。既定获取路径是 `ctx.permissions.requestPermission()`。deep-research 已按此修好，catalog 未动。

`lib/plugin/api/permission-api.ts` 的 `permissionMapping` 有恒等映射，`createApiGuardedAPI` 按其**失败关闭**。但 `validatePluginManifest` 的白名单来自 `CANONICAL_PLUGIN_PERMISSIONS`（= catalog 的 77 项），**不含**这些键。实测：声明 `ai:chat` → `manifest.permissions.unknown` 警告。

```
ai:chat  ai:embed  vector:read  vector:write
canvas:write  canvas:run  canvas:collaborate  artifact:write
project:write  project:delete  session:delete
export:session  export:project  events:publish  events:subscribe
fs:read  fs:write  theme:read  theme:write  notification:show
```

（`theme:read` / `notification:show` 是默认授予，实际不受影响；其余 18 项是真缺口。）

这解释了 `deep-research` 为何完全不可用：它调 `ctx.ai.chat`/`ctx.ai.embed`，但**没有干净的办法声明这两个权限**。

**修复路径**：把这 20 项补进 `packages/plugin-sdk/contract/catalog.json` 的 `permissions`，再跑 `scripts/plugin/generate-contract.mjs` 重新生成 Rust/Python 镜像。

> ⚠️ **本次未执行**：该生成器的输出目标是 `crates/cognia-cli/src/engine/contract.rs`，而另一个会话正在重构整个 `crates/cognia-cli`（22 个源文件处于未提交的删除/新增状态）。在其落地前改动会正面冲突。

### A3 · 斜杠命令：14 个插件停留在已被替换的写法

直接 `import { registerSlashCommand, unregisterCommandsByPlugin } from "@/lib/slash-commands/registry"`；全仓 `hooks.onCommand` 采用数 **0**。`author-sdk.mdx` 迁移表首行即 `direct slash-command registry → declare commands and return hooks.onCommand`，且旧写法的模板 shim 已在 `95a2fc93a` 删除。

声明式路径在宿主侧完全就绪且更强（`manager.ts:3534 registerPluginSlashCommand`）：`pluginId.commandId` 命名空间、冲突检测、**aliases**、命令面板条目（`store.registerPluginCommand` + `registry.registerCommand`）、调用时刷新 `updateLastUsedAt`。手工注册这些全都拿不到。

叠加缺陷（`lib/slash-commands/plugin-commands.ts:40` `name: def.id`）：composer 投射的是 **id 而非 name**，所以手工注册时声明的 `name` 是惰性的 ——

| 插件             | 声明的 name     | 实际可调用               |
| ---------------- | --------------- | ------------------------ |
| playwright-mcp   | `/browser`      | `/playwright.attach`     |
| stagehand-mcp    | `/stagehand`    | `/stagehand.attach`      |
| e2b-sandbox      | `/sandbox`      | `/e2b.attach`            |
| anthropic-skills | `/skill`        | `/skill.list`            |
| skill-recorder   | `/record-skill` | `/skill-recorder.record` |

`prompt-templates` 是唯一能用的，且属巧合（id 恰好等于 name 去掉斜杠）。

### A4 · `definePlugin` 采用率 0/38，SDK helper 采用率 9/58

38 个内置插件全部手写 `const definition: PluginDefinition = {...}`（类型来自 `@/types/plugin`），无一使用 `definePlugin`。已用 helper 仅 9 个；`defineCommand`、`defineTool`、`defineCliTool`、`defineScheduledTask`、`definePetAchievement`、`definePetItem`、`defineExternalAgentPreset`、`defineExternalAgentAdapter`、`defineLspServer`、`defineThemePack`、`defineWallpaper`、`defineFontContribution`、`defineDensityPreset`、`defineOcrProvider` **零使用** —— 即便插件正好贡献那类东西。`github-delivery/src/workflow/nodes.ts:39` 甚至自写本地 `defineNode` 顶替 `defineWorkflowNode`。

多个插件用 `as never` / `as PluginManifest` 关掉 manifest 层的类型检查（zhihu、backend-refactor、agent-team-examples、scheduler-tools、sandboxed-tools、character-seeds、builtin-characters、ripgrep-tools）。实测这些 cast 只掩盖了一个必填 `description`，代价却是**所有贡献数组的元素类型不再被校验** —— 字段名拼错（`characterPack` vs `characterPacks`）会静默通过并让整个能力消失。

### A5 · 懒激活整条链路无人使用

宿主实现了 `onCommand:` / `onTool:` / `onAgentTool:` / `onView:` / `onUri:`（`manager.ts:3125`）。35 个 frontend 内置**全部**是 `activationEvents: ["startup"]`，零采用。另有 3 个完全未声明激活事件：`ripgrep-tools`（已修）、`cognia-python-demo`、`wasm-example-formatter`。

### A6 · 模块 overlay 覆盖 plugin.json 的静默陷阱

`builtinManifest()` 是浅合并 `{ ...base, ...rich, id: base.id }` ⇒ **TS overlay 胜出**。手写一个字段子集时：它命名的键覆盖 JSON，它省略的键仅靠运气存活。已确认的实例：

- `clipboard-history` TS overlay 声明 `["tools","commands"]`，plugin.json 有 `themes` ⇒ **`themes` 能力从持久化清单中消失**。
- `agent-team-examples` 反向漂移：TS 有 `balance-adapter` + `balanceAdapters`，plugin.json 没有 ⇒ runtime 正确但清单说谎，且因为 allowlist 与被审计对象**同源**，漂移自洽、检测不出。
- `ripgrep-tools`（已修）、`scheduler-tools`、`sandboxed-tools`、`character-seeds`、`builtin-characters`、`github-delivery` 同型。

### A7 · `EXPECTED_WARNINGS` allowlist 正在掩盖真实休眠

allowlist 的自述理由是"贡献在 TS overlay 上或在 activate() 里命令式注册"。逐条核对后，**`field_missing:commands` 系列不成立**：这些插件既无 `commands[]`，也无 `hooks.onCommand`，只有手工 registry 调用。它压掉的正是唯一能暴露 A3 的那条警告。同类：`workflow-ai` 的 `commands` 能力零贡献；`github-delivery` 的 `tools`/`components`/`providers`/`exporters` 四项全休眠。
