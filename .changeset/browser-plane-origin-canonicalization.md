Browser access: an allowed origin is now stored in the exact form a browser sends it, so entries that used to save cleanly and then refuse every request work. `https://app.example.com:443`, an origin typed in mixed case, and an internationalised domain were all kept verbatim and compared to the `Origin` header by string equality, which they could never match — the result was a listed origin that answered 403 with nothing wrong to see in Settings. They are now canonicalised on save (default port dropped, scheme and host lowercased, IDN host in punycode), which also lets the duplicate check see two spellings of one origin as one entry. Reading the config back repairs it the same way instead of refusing it: before, a single entry that a later release stopped admitting sent the whole file to its default — access off, port reset, every other still-valid origin gone, and nothing in Settings to explain it. Now only the unusable entry is dropped, with a line in the log. One shape this drops on sight is the `extension://` scheme, which was accepted as a cross-browser alias and no longer is; the extension is Chromium-only, so the alias never had a client, but an entry saved under it has to be re-added as `chrome-extension://`. The rejection message names the three shapes that are actually accepted instead of only mentioning http(s).

A "pair in browser" link no longer targets a `chrome-extension://` origin. Now that the Browser Companion asks users to add their extension's origin to the same list, the first entry could be one, and an extension page is not something a link can open; the first web origin is used instead.

Two hardening fixes on the same path: `/api/apps/*/embed-token`, which admits an origin on shape rather than from the allowlist, no longer accepts extension origins — it briefly opened to every extension installed in the user's browser — and a browser device's bound origin is now enforced on the socket-ticket and Owner paths as well as the device path, rather than only on the one door it was added to. Editing a browser device's grants also works again: `browser.submit` and `browser.read-own` were absent from the assignable-capability list, so every edit came back as `InvalidCapabilities`; assignability is now decided by the device's class rather than by a list that had to remember them.
