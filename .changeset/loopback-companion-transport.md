Fix two guards that assumed the companion plane is always TLS and so made the plaintext loopback listener — the only address a browser tab can reach the Host on — unusable. Pairing a browser against it registered the device and then refused to store its key with "Companion runtime targets require HTTPS", burning the one-shot invitation on every attempt; plaintext loopback is now accepted on its address, exactly as the pair screen and the Host's own origin check already accept it, while cleartext aimed off the machine still needs the explicit development flag. The Host also advertised `wss://` for its same-origin signaling endpoint whatever listener the request arrived on, handing browsers a TLS URL for a port that speaks none; each listener now states its own transport plane, and a reverse proxy's `x-forwarded-proto` still outranks it. The client's own auth-config check made the same assumption — it required the advertised signaling URL to start with `wss://`, so an honest `ws://` answer read as a malformed response and failed pairing at the config fetch; it now accepts a WebSocket rendezvous on loopback and still refuses cleartext signaling aimed off the machine.
