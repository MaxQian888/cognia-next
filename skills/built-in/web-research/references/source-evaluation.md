# Source evaluation

Research is only worth as much as the sources behind it. A confident answer built from unread snippets is worse than none — it looks authoritative and can be wrong.

## Trust hierarchy (prefer the top)
1. Official docs / primary sources (the project's own docs, repo, the standard itself)
2. Maintainer writing (release notes, maintainer blog, RFCs)
3. Reputable secondary (well-known technical publications)
4. Q&A sites (Stack Overflow) — useful but dated; check the date and accepted-answer comments
5. Tutorials / content farms — leads, not authority

## Recency
- Note publication / last-updated dates. For fast-moving tools, a 2-year-old answer may be stale or wrong for the current version.
- Match the version: an answer about v2 may not hold for v4. Search with the version number when it matters.

## Corroboration rubric
| Claim type | Bar before you state it |
| --- | --- |
| Stable concept | One good source |
| Version-specific behavior | Official docs for that version |
| Surprising / contested | Two independent sources, or say it's contested |
| Security / safety / legal / financial | Primary source; flag if uncertain |

## Read, don't snippet
Open the page; don't answer from the search-result summary. Fetch with a specific extraction goal, not "summarize this long page."

## Citation
Name or link the source for each load-bearing claim. Distinguish what the sources state from what you're inferring by connecting them. When you couldn't confirm something, say so — "I couldn't verify this" is honest and useful. End substantive research with the sources you relied on.
